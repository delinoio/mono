# packages-sandrun-sdk foundation contract

## Scope

This contract owns the SandRun SDKs of [`sandrun`](project-sandrun.md):

- `packages/sandrun-sdk/` (workspace package `sandrun-sdk`), component `sandrun-sdk-ts`: TypeScript SDK.
- `go/sandrun/`, component `sandrun-sdk-go`: Go SDK in the root Go module, import path `github.com/delinoio/mono/go/sandrun`, and its test fake `go/sandrun/sandruntest`. It is under `go/` because external users import it (see the [workflow contract](repository-workflow-contract.md#public-go-packages)).

The SDKs give programs and the [CLI](cmds-sandrun-cli-foundation.md) typed access to the public services of the [protos contract](protos-sandrun-api-contract.md).

## Runtime and Language

- TypeScript SDK: ES modules for Node.js 24 and browsers, built on Connect-ES and the generated TypeScript code.
- Go SDK: Go in the root module `github.com/delinoio/mono`, built on connect-go and the committed Go bindings. Logging: `log/slog` through a logger that the caller passes.
- Both SDKs use Apache-2.0 and must not import code from `servers/`.

## Users and Operators

- The SandRun CLI and the `sandrun mcp` MCP server (Go SDK).
- Programs of SandRun users that read the queue or manage runner profiles with a Logto access token, or that use dev sessions with a Logto access token or a personal API key.

## Interfaces and Contracts

- A client takes the API origin (default `https://sandrun.api.delino.io`) and a token source that returns a Logto access token for the API resource `https://sandrun.api.delino.io`, or a personal API key.
- The SDKs expose every public service of the protos contract with the generated request and response types. They add no behavior that the server does not define.
- Helpers:
  - Pagination iterators for every list RPC.
  - A `WatchQueue` helper that reconnects after each stream end with exponential backoff (1 second to 30 seconds) and reports a gap when it reconnects, so the caller can reload the state.
  - Both SDKs: an exec helper that generates the `exec_id`, continues with `AttachDevSessionExec` after each stream end and reports lost output.
  - Go SDK only: a dev session wait helper (repeated `GetDevSession` until the session is `RUNNING`, ends, or the caller's deadline passes), and the [sync](servers-sandrun-api-foundation.md#dev-session-sync) and [download](servers-sandrun-api-foundation.md#dev-session-download) helpers that the CLI and the MCP server share. The Go SDK owns their file selection, manifest, lock, archive, limit and path-safety rules, and the exact guest commands per guest OS, which it records with the implementation.
- Errors keep the Connect error code.

### TypeScript SDK surface

- `SandRunClient({ origin?, token, fetch?, clock? })`. To catch paths that URL parsing can remove, the SDK requires an `http` or `https` origin written as `scheme://host[:port][/]` with no credentials, path, query, fragment or backslash. `token` is a string or a function that returns one (a Logto access token or a personal API key); the client calls the function before every call and stores no token. The signal of a call stops the token wait. If the signal is already aborted, the SDK skips the token function. Once the call is canceled, a later token starts no request, and a later provider failure causes no unhandled rejection. The transport is Connect-Web with the binary Connect protocol. An interceptor and a guarded fetch refuse every URL outside the configured origin. The client trims whitespace from both ends of the token before sending it. If the trimmed token is empty, the SDK rejects it before calling fetch. A static token throws a `SandRunConfigError` when the client is created. A token from a provider fails the call with a `ConnectError` whose cause is a `SandRunConfigError`. It redacts the original and trimmed forms from error messages, including messages in the `cause` chain. A token that is not a valid HTTP header value fails the call with a `SandRunConfigError` that does not contain the token.
- Service clients with the generated types: `organizations`, `members`, `ownSandLink`, `gitHub`, `agentIntegrations`, `runnerProfiles`, `work`, `apiKeys`, `devSessions` and `audit`. `createSandRunServices(transport)` creates the same clients on another transport, for example the console's.
- Pagination: `client.iterate.<list>` (`organizations`, `invitations`, `members`, `gitHubInstallations`, `agentIntegrations`, `runnerProfiles`, `requests`, `runners`, `apiKeys`, `devSessionProfiles`, `devSessions` and `auditEvents`), one async iterator for each list RPC with a page token, built on `paginate`. An iterator ends with a `SandRunError` when the server repeats a page token.
- `watchQueue(work, { organizationId, signal })` (also `client.watchQueue`) yields `Request`, `Runner`, `SnapshotComplete` and `Gap` events and skips keepalives. After a clean end or a retryable failure it waits 1 second, doubled for each stream that ended before its snapshot was complete, at most 30 seconds, then yields `Gap` and opens a new stream. A complete snapshot resets the delay. Retryable failures are transport interruptions without a server status and the codes `unavailable`, `resource_exhausted`, `aborted` and `deadline_exceeded`; every other status ends the iterator with that `ConnectError`. Aborting the signal ends the iterator without an error. The helper closes the upstream iterator, discards buffered responses and skips reconnecting.
- `execDevSession(devSessions, input)` and `runDevSessionExec` (also on the client) generate a UUID v7 `exec_id` (Web Crypto), call `ExecDevSession` at most once and continue with `AttachDevSessionExec` from the next stdout and stderr offsets after each stream end: at once after a clean end, with the same backoff after a retryable failure. They yield output in order without duplicates, report missing ranges (`output_truncated` or a skipped offset) as `OutputLost`, and end with `Exited`, `Failed` or `SandboxEnded`. The first start event yields `Started` and resets the backoff. New output also resets the backoff. Replayed start events and keepalives do not yield events, change offsets or reset the backoff. If `ExecDevSession` fails and neither stream delivers a command event before `AttachDevSessionExec` answers `not_found`, the helper ends with the error of `ExecDevSession`.
  - If the caller cancels, the exec iterator closes the active stream and ends without yielding more events or starting another attach. The command keeps running in the guest. `runDevSessionExec` rejects with the exact `AbortSignal.reason` if cancellation occurs before the iterator delivers a terminal event. It keeps a terminal outcome that the iterator already delivered.
- Errors: server errors stay `ConnectError` values with their code; `connectCodeOf` reads the code through `cause` links. The SDK's own errors are `SandRunError` and `SandRunConfigError`. If the token source throws or rejects, the SDK reports a `SandRunConfigError` with the original failure in its cause chain. This ends the call and stops any stream retries.
- `UuidV7Generator.next()` returns canonical UUID v7 values in strictly increasing order within one generator. It floors finite clock readings to whole milliseconds and treats readings before the Unix epoch as zero. If the resulting timestamp is unchanged or moves backward, the generator increments the counter at the last timestamp. When the counter runs out, the generator advances one millisecond and picks a random counter in the lower half of its range. If the clock reading is non-finite or the floored reading or a counter carry exceeds `2 ** 48 - 1` milliseconds, `next()` throws `RangeError` and keeps the timestamp and counter from the last successful call.
- Runtime sources import no `node:` module, so the package runs in Node.js 24 and in browsers.

### Go SDK surface

- `sandrun.New(sandrun.Options{BaseURL, APIKey | TokenSource, HTTPClient, Logger})` returns the client. `BaseURL` defaults to `sandrun.DefaultBaseURL`. An explicit `BaseURL` must be an `http` or `https` origin with a nonempty hostname. The client rejects a port without a hostname, such as `http://:18400`. A nonempty port must be a decimal number from `0` to `65535`. The constructor rejects an out-of-range port with an invalid base URL error that omits the configured URL. The client sends the credential as `Authorization: Bearer` only to that origin, follows no redirects and uses no cookie jar. An `http://` origin uses HTTP/2 with prior knowledge (h2c).
- An empty token or a terminal `TokenSource` failure returns Connect `unauthenticated` immediately, with a `*sandrun.CredentialError` that unwraps to the provider's error when present. Network and context errors from the source follow the operation's existing retry and cancellation rules.
- `Organizations()`, `Members()`, `OwnSandLinks()`, `GitHub()`, `AgentIntegrations()`, `RunnerProfiles()`, `Work()`, `APIKeys()`, `Audit()` and `DevSessions()` return the generated `sandrunv1connect` clients. Errors are `*connect.Error` values with the server code; the SDK removes the credential from error messages and keeps the code, details and wire flag.
- Pagination: `AllOrganizations`, `AllInvitations`, `AllMembers`, `AllGitHubInstallations`, `AllAgentIntegrations`, `AllRunnerProfiles`, `AllRequests`, `AllRunners`, `AllAPIKeys`, `AllAuditEvents`, `AllDevSessionProfiles` and `AllDevSessions` return `iter.Seq2` iterators. The first RPC uses the caller's starting token, and the iterator leaves the caller's request unchanged. If a response repeats a nonempty token already used by the iterator, including the starting token, the iterator yields that response's items, then reports an error once and stops before requesting the token again. `sandrun.Collect` returns the items it collected before the error along with the error.
- `WatchQueue(ctx, organizationID, handler)` reports `QueueEventRequest`, `QueueEventRunner`, `QueueEventSnapshotComplete` and, before each reconnect, `QueueEventGap`. It reconnects after transient failures and normal stream ends and stops on other server codes.
  - After each successful receive, the SDK checks the caller context before processing the response. If the context has ended, the SDK discards the response, closes the stream and returns `ctx.Err()`. It skips the gap callback and reconnect for that stream. Once a handler call starts, the SDK returns any error from that call unchanged.
- `Exec` and `AttachExec` report `ExecEventStdout`, `ExecEventStderr` and `ExecEventOutputTruncated` (with the missing byte ranges) and return an `ExecResult` (`exited`, `failed` or `sandbox_ended`, `Incomplete` and the next offsets). After local validation, `Exec` attempts `ExecDevSession` at most once. It returns an initial credential failure or a terminal server status before the first event unchanged. A later failure, or the end of the caller context, returns `*ExecStreamError` with the next offsets.
  - `Exec` rejects a negative `ExecParams.Timeout` with `invalid_argument` before it sends a request or calls `OnEvent`. A zero timeout omits the request field. A positive timeout is sent unchanged.
  - `Exec` reports the first start event as `ExecEventStarted`. `AttachExec` suppresses the callback for this event. `ExecStreamError.Started` is true if the SDK received a start event during the current call. If the attach returns `not_found` before any start event, the error wraps that status, keeps both offsets and sets `OutcomeUnknown` to true. If the SDK received a start event, `Started` stays true and `OutcomeUnknown` stays false even when the final result is unavailable.
  - Each continuation uses the same exec ID and resumes at the last acknowledged stdout and stderr offsets. A transient failure or a short clean stream end without command progress starts a two-minute recovery window. The SDK uses exponential backoff from 1 second to 30 seconds, with jitter. The window bounds both backoff and active attach requests. If it expires, the SDK returns `*ExecStreamError` with the current offsets and wraps the last retryable error when available.
  - The first start, acknowledged new output and accepted truncation that advances either offset count as command progress. Progress clears the recovery window and backoff. A clean end after progress continues immediately. A clean end also continues immediately and clears retry state if the stream remained open for at least two minutes after receiving a keepalive or replayed start. Keepalives, replayed starts and previously acknowledged output otherwise leave the retry state unchanged.
  - A nil `OnEvent` callback or a nil return from the callback acknowledges the complete stdout or stderr range offered after overlap trimming. If the callback rejects a chunk, `*ExecStreamError` wraps the callback error. The affected offset points to the first byte offered to the callback. The other offset keeps its current value.
  - A nil callback also accepts a truncation notice. When the callback accepts the notice, the SDK advances each affected offset to the first available byte and marks the result `Incomplete`. If the callback rejects the notice, `*ExecStreamError` wraps the callback error and reports both offsets from before the notice.
  - If the caller context ends while the callback accepts an inferred gap, the SDK closes the stream before delivering the chunk that revealed the gap. It does not retry. The `*ExecStreamError` wraps the context error and reports the accepted gap offset and the other stream's current offset. A later attach can replay the chunk if the server still retains it.
  - Pass the exec ID and offsets from `*ExecStreamError` to `AttachExec` to resume. This can replay a rejected truncation notice or rejected output bytes that the server still retains. If the sink saved a prefix before returning an error, replay can include that prefix. To avoid duplicate writes, use an atomic sink for each chunk or track durable bytes by stream and offset.
- `WaitDevSession` polls `GetDevSession` every 2 seconds by default. If the caller context ends before the SDK accepts a poll result, the wait returns the last accepted dev session (or `nil` if it has accepted none) and the caller context error.
- `Sync` returns `SyncResult` (uploaded, deleted and skipped counts, submodules, bytes sent, warnings). `Download` returns `DownloadResult` (local path, file count, bytes, warnings). Both report `TransferProgress`. SDK-side failures are `*connect.Error` values: `failed_precondition` wraps `*LimitError`, `*PathRuleError`, `ErrSyncLocked` and `ErrNotGitWorkTree`, `not_found` a missing guest path. For a selected path with invalid UTF-8, `PathRuleError` has rule `PathRuleInvalidUTF8` (`invalid_utf8`). It lists each offending path in its own group and quotes each path in the error message.
- `go/sandrun/sandruntest` is an in-memory fake of `sandrun-api` for tests. Its guest is the local machine: exec runs local processes and file RPCs read and write local paths, so a test uses a local directory as the workspace path. It is not a sandbox. On Linux and macOS, canceling a running exec stops the command and descendants that stayed in its process group. Both `Server.Close` and request timeouts cancel running execs. On Windows, cancellation stops only the direct process.
  - `GetOwnSandLink` succeeds for an existing organization and leaves `link` unset when the organization has no link. An unknown organization returns `not_found`.
  - `UpdateOrganizationSettings` requires a nonempty field mask that contains only `max_dev_sessions_per_user`. If the mask is empty or contains an unsupported path, the fake returns `invalid_argument` and leaves the stored limit unchanged.
  - `DeleteDevSession` closes exec admission for the session, including requests still in `BeforeExec`. It cancels the session's admitted commands and waits for them to finish before replying. Other sessions continue running. Only expiry of an exec request's timeout reports a timed-out exit.
  - `SendQueueEvent` queues each request or runner update for one `WatchQueue` stream of that update's organization. The watch delivers these updates in order after its snapshot marker. Each sent update counts toward `WatchEventLimit`. Updates without an organization ID are ignored. Other event types can go to any one watch.
  - When a poll reaches `PromoteAfterGets`, the fake promotes a `QUEUED` or `STARTING` dev session to `RUNNING` and assigns a start time and runner ID. Later get and list responses retain the runner ID.
  - For a bare command name, the fake searches the request `PATH` when supplied. An empty request `PATH` prevents fallback to the test process `PATH`. When the request omits `PATH`, lookup uses the test process `PATH`. On Windows, request environment names are case-insensitive and lookup with a request `PATH` uses the effective `PATHEXT`. Explicit command paths bypass the `PATH` search.
  - The fake binds each `read_id` on a server to the organization, dev session and resolved path of its first snapshot. Matching reads resume at the requested offset with the original bytes. A different session returns `already_exists`. A different resolved path in the same session returns `failed_precondition`. Both errors occur before the fake sends file events.
  - The fake tracks each `write_id` separately for each dev session. It returns `invalid_argument` before accessing write state if the chunk end offset exceeds the maximum signed 64-bit integer. The first chunk binds the ID to the resolved destination. Requests that change that destination return `invalid_argument`, even after the write completes. A retry of the original final request returns the completed size.
  - Each finalization attempt creates its own staging file in the destination directory. The fake applies the requested permissions, with a default of `0644` when the permission bits are zero, and closes the staging file before renaming it to the destination. If finalization fails, the fake returns `failed_precondition`, attempts to remove the staging file it created, and keeps the buffered bytes for an identical final-chunk retry.

### Go SDK sync and download rules

The SDK implements the [sync](servers-sandrun-api-foundation.md#dev-session-sync) and [download](servers-sandrun-api-foundation.md#dev-session-download) rules with these details:

- File selection: `git -C <dir> -c core.quotepath=off ls-files -z --cached --others --exclude-standard`, after `git rev-parse --is-inside-work-tree`. `git ls-files -z --stage` finds submodules (mode `160000`), which are skipped. An untracked nested repository (a listed path that ends with `/`) is also skipped. A tracked path that is missing locally counts as deleted. Sync treats paths below a file or symbolic link as missing, even when Git ignores the replacement. An unignored file that replaces a tracked directory can sync without staging the replacement. A symbolic link that Git selects is synced as a link. The SDK uses one open sync directory for file checks, hashing and upload. The root confines file reads to that directory even when a path contains a symbolic link. The SDK requires the opened file to match the regular file it checked. On a Windows local machine the executable bit comes from the index mode.
- When the effective Git setting `core.symlinks` is false, Sync uses a regular file as a symbolic link placeholder if its stage-zero index mode is `120000`. Sync uses the exact bytes of that file, including local edits, as the link target. The target must contain 1 to 131,072 bytes without NUL. Conflict stages alone never classify a regular file as a link. Windows guests reject targets containing a line break because the link list has one entry per line.
- If the caller cancels Sync or its deadline expires during the local scan, Sync stops when the Git command ends or at the next file or read boundary. It returns the context error before reading the guest manifest, taking the lock or uploading files.
- Manifest `<workspace_path>.sandrun-sync.json`: `{"version":1,"files":{"<path>":{"size":N,"sha256":"<hex>","mode":M}},"paths_validated":true}`. The path is slash-separated and relative to the workspace. The mode is the Git mode: `0o100644`, `0o100755` or `0o120000` for a symbolic link, whose size and SHA-256 describe the link target. The encoded manifest can be at most 256 MiB (268,435,456 bytes). Before taking the lock or uploading files, the SDK checks the encoded candidate with every selected entry, including links. A larger candidate or guest manifest returns `failed_precondition` with a manifest size error. A manifest within the limit counts as empty if it has invalid JSON or another version. The optional `paths_validated` field records that the SDK checked the UTF-8 of the paths before writing the manifest. Older SDKs can read the same v1 format.
- Legacy manifest entries: without the validation marker, a path with U+FFFD may represent either a valid name or a name that JSON changed by replacing invalid bytes. If the local file list omits such a path, the SDK preserves the guest file, reports a warning and removes the stale entry from the new manifest. If the list contains the path, the SDK uploads the local file before recording it as validated. A validated entry with U+FFFD follows the regular deletion rules. If only the manifest changes, the SDK writes it under the lock without running the guest apply command.
- Path rules: all selected local paths must be valid UTF-8 on every guest OS. The SDK rejects invalid UTF-8 before reading the guest manifest. On Windows and macOS guests, the case collision check compares every file and every parent directory after Unicode upper-then-lower case mapping. On Windows guests, a path element is invalid when it is a reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `COM1` to `COM9`, `LPT1` to `LPT9` and the superscript variants), also with an extension, when it contains `<>:"\|?*` or a control character, or when it ends with a space or a dot.
  - On macOS guests, after the case-only check, the SDK also compares the selected files and their parent directories after Unicode canonical decomposition and the same case mapping. A collision between any two of these paths, including a file and a parent directory, returns `failed_precondition` before the lock or any guest mutation. `PathRuleError` has rule `PathRuleNormalizationCollision` (`normalization_collision`) and groups the original paths. The message quotes non-ASCII characters with escapes so the spellings are distinguishable. The archive and manifest keep the original paths of accepted files.
- Manifest check under the lock: after the lock command succeeds and reports an existing workspace, the SDK reads the manifest again and compares its entries and validation marker with the first read. If either differs, it plans the changes and deletions again and checks the size limits before uploading anything. If the lock command finds that the workspace is missing, the SDK plans against an empty manifest and removes any stale manifest before apply recreates the workspace.
- Order of step 7: the archive `<workspace_path>.sandrun-sync-<uuid>.tar` (PAX tar, regular files with mode `0644` or `0755`, parent directories with `0755`) is uploaded. The SDK hashes each file again while it writes the archive: when the size or the SHA-256 of a file changed after the SDK listed it, the upload fails before the guest extracts the archive, and the sync asks for a new sync. Then the deletion list `<workspace_path>.sandrun-sync-<uuid>.delete` is uploaded: NUL-separated on Linux and macOS, newline-separated with backslashes on Windows. The SDK puts former file paths that are parents of incoming paths in a separate list, `<workspace_path>.sandrun-sync-<uuid>.replace`. This list uses the same format as the deletion list. When a changed file or link has the path of a guest directory that holds deleted entries, the prune list `<workspace_path>.sandrun-sync-<uuid>.prune` (same format) is uploaded. It lists the directories from the parent of each such deleted entry up to that path, deeper directories first. On macOS, if the paths match only after case folding, the SDK uploads a separate NUL-separated list, `<workspace_path>.sandrun-sync-<uuid>.prune-alias`. Each record holds the old ancestor, the incoming spelling and the directory to remove. The list uses the old directory spelling and puts deeper directories first. The guest prunes an alias candidate only when the two spellings resolve to the same directory. On Windows guests, the symbolic links are not in the archive. They are in the link list `<workspace_path>.sandrun-sync-<uuid>.links` (`<path>\t<target>` lines). One apply command deletes the listed files, removes the listed directories when they are empty, extracts the archive and creates the links. The SDK deletes before it extracts, so that a path can change from a file to a directory, and from a directory to a file. For paths in the replacement list, apply leaves an existing regular directory in place and removes a file or symbolic link. On Windows, apply removes a directory reparse point without recursing into its target. If apply creates a directory and the manifest write then fails, the next sync retries the upload using the previous manifest if it is still present. Files created by the guest under that directory stay. A failed deletion still stops apply before extraction. When the SDK replaces a directory with a file, apply fails if the directory still holds other files after deletion. The guest keeps those files. Then it writes the new manifest with `WriteDevSessionFile`, and one clean-up command removes the temporary files and the lock. A symbolic link that a Windows guest cannot create is a warning and is left out of the manifest, so the next sync tries it again. The SDK reads every `SANDRUN-LINK-FAILED` line of the apply output, not only the start of the output that it keeps. When the apply output is incomplete (the exec lost output, or a line is longer than 64 KiB), the SDK cannot tell which links the guest created. It then leaves every link of that sync out of the manifest with a warning. If sync commits the manifest and clean-up fails, the SDK returns a successful result with a warning.
- Failed sync after taking the lock: the SDK returns the original error. If sync fails before the manifest write, the old manifest stays unless apply removed a stale manifest while restoring a missing workspace. A missing or invalid final write acknowledgement leaves the manifest commit outcome uncertain. If the SDK loses the apply stream, it attaches to the same exec for up to 30 seconds, even if the caller canceled sync. It uses the result only to decide whether to clean up. A terminal result permits clean-up. If the outcome remains unknown, the SDK keeps the lock and temporary inputs in the guest. The SDK logs any clean-up failure at debug level. Use `force` to clear a retained lock only after confirming that the previous apply has stopped.
- Uploads use one `write_id` per file, chunks of at most 1 MiB and `final` on the last chunk. The SDK retries a chunk after a transient RPC failure with the same request. Before counting bytes or reporting upload progress, it requires the reply to match the request's `write_id`, `offset`, and chunk length, with `finished` equal to `final`. On the final chunk, `size_bytes` must equal the end offset. A missing or inconsistent acknowledgement returns a local `data_loss` error without retrying the chunk. Sync stops before apply if the archive acknowledgement fails. If the manifest acknowledgement fails, sync returns an error and omits `TransferDone`. A read uses one `read_id`: after a transient failure, or a stream that ends without its end message, the SDK continues from the last offset with the same `read_id`, so the guest serves the rest from the same file snapshot.
- Each upload chunk has a two-minute budget for its first request, retries and backoff. After the SDK validates a chunk acknowledgement, the next chunk gets a new budget. A read has a two-minute idle budget that starts before the first request and continues across stream reconnects and backoff. The SDK renews it after it accepts bytes that advance the offset. An empty chunk leaves the budget unchanged. On budget expiry, the SDK cancels any active RPC and returns a local Connect `deadline_exceeded` error. If the caller's context ends first, the SDK returns the caller's context error.
- Order of step 7: the archive `<workspace_path>.sandrun-sync-<uuid>.tar` (PAX tar, regular files with mode `0644` or `0755`, parent directories with `0755`) is uploaded. The SDK checks the identity of each regular file before it writes the file's tar header or contents. If it cannot confirm the identity, it fails the upload with `sandrun: <path> changed during the sync; sync again` and logs the reason at debug level without the path. The SDK hashes each file again while it writes the archive: when the size or the SHA-256 of a file changed after the SDK listed it, the upload fails before the guest extracts the archive, and the sync asks for a new sync. Then the deletion list `<workspace_path>.sandrun-sync-<uuid>.delete` is uploaded: NUL-separated on Linux and macOS, newline-separated with backslashes on Windows. The SDK puts former file paths that are parents of incoming paths in a separate list, `<workspace_path>.sandrun-sync-<uuid>.replace`. This list uses the same format as the deletion list. - During sync archive upload, `TransferProgress.BytesDone` counts the tar bytes acknowledged by the guest. `BytesTotal` is zero during this phase because the SDK streams the archive. During `Applying` and `Done`, both counters report `SyncResult.BytesSent`, including the archive and any auxiliary lists. An unchanged sync sends zero bytes and has no upload phase.
- Uploads use one `write_id` per file, chunks of at most 1 MiB and `final` on the last chunk. The SDK retries a chunk after a transient failure with the same `write_id` and offset. A read uses one `read_id`: after a transient failure, or a stream that ends without its end message, the SDK continues from the last offset with the same `read_id`, so the guest serves the rest from the same file snapshot.
- Each upload chunk has a two-minute budget for its first request, retries and backoff. After the SDK receives a chunk acknowledgement, the next chunk gets a new budget. A read has a two-minute idle budget that starts before the first request and continues across stream reconnects and backoff. The SDK renews it after it accepts bytes that advance the offset. An empty chunk leaves the budget unchanged. On budget expiry, the SDK cancels any active RPC and returns a local Connect `deadline_exceeded` error. If the caller's context ends first, the SDK returns the caller's context error.
- Download: the probe command reports `file <size>` or `dir <archive size>`. For a directory, it first packs the directory into `<workspace_path>.sandrun-download-<uuid>.tar`. Exit code `66` means that the path does not exist. The SDK always attempts to remove the guest archive afterwards. It logs a clean-up failure at debug level and preserves the download result. Local extraction uses `os.Root` in a temporary directory `.sandrun-download-*` next to the destination. It rejects absolute entries, entries outside the destination, symbolic links whose targets leave the destination and hard links to entries that are not in the archive. A link target that stays inside as text can still leave the destination through other links of the archive (for example `a/b -> ..` and `a/b/l -> ../x`). After the last entry, the SDK therefore resolves every symbolic link of the extracted tree from the directory where the link is, through the other links, and rejects the download when a target leaves the destination or a chain has more than 255 links. It skips other entry types with a warning. A symbolic link that the local system cannot create is a warning. The result replaces an existing destination only after the download succeeded.
- Download path resolution: the SDK passes absolute guest paths to the probe unchanged and resolves relative paths against the session workspace. On Windows, a UNC prefix uses either slash or backslash in each of its first two positions.
- Download progress: `BytesDone` counts file or archive bytes received and never decreases. During `Downloading`, `BytesTotal` is zero because the SDK has yet to verify the stream size. The SDK sets both counters to the verified byte count at `Applying` for an archive and at `Done` for a file or archive. It reports `Done` only after installation succeeds. `DownloadResult.Bytes` counts regular-file bytes written locally.
- Download limits: if the local filesystem cannot create a hard link, the SDK checks the source file size against the per-file and remaining extraction limits before it writes a copy. The bytes in a successful copy count toward the extraction total and `DownloadResult.Bytes`. A successful hard link increases the file count and adds zero bytes.
- Download name conflicts: when two regular archive paths differ only in case and resolve to the same local directory entry, the SDK reports both names in a `failed_precondition` error. The SDK keeps an existing destination and leaves a missing destination absent. When the filesystem stores the paths separately, the SDK keeps both original names. Repeated regular entries with the same name can still replace that file during extraction.
- Download replacement: the SDK moves the existing destination to a short, uniquely named backup directory next to it. If installation fails, the SDK tries to restore the previous destination and remove the backup directory. If restoration fails, the SDK keeps the backup and reports its path in the error. After successful installation, the SDK tries to remove the backup. If removal fails, the SDK still returns a successful result and reports completion. It appends a warning with the absolute backup path and the removal error.
- Guest commands get every path through environment variables of the exec request (`SANDRUN_SYNC_LOCK`, `SANDRUN_SYNC_FORCE`, `SANDRUN_SYNC_WORKSPACE`, `SANDRUN_SYNC_STALE_MANIFEST`, `SANDRUN_SYNC_ARCHIVE`, `SANDRUN_SYNC_DELETE_LIST`, `SANDRUN_SYNC_REPLACE_FILE_LIST`, `SANDRUN_SYNC_PRUNE_LIST`, `SANDRUN_SYNC_PRUNE_ALIAS_LIST`, `SANDRUN_SYNC_LINK_LIST`, `SANDRUN_DOWNLOAD_PATH` and `SANDRUN_DOWNLOAD_ARCHIVE`), never in the command text. They run in the guest filesystem root (`/` on Linux and macOS, the drive root of `workspace_path` on Windows), so they can start when the workspace is missing. On macOS guests the SDK also sets `COPYFILE_DISABLE=1`, so that tar adds no AppleDouble files.
- Linux and macOS guests (`sh -c <script> sandrun`; GNU, BSD and BusyBox `tar`, `xargs -0`):
  - lock: `if [ "$SANDRUN_SYNC_FORCE" = 1 ]; then rm -rf "$SANDRUN_SYNC_LOCK" || exit 1; fi`, then create the lock with `mkdir "$SANDRUN_SYNC_LOCK"`. If the lock was acquired, the command exits with `0` when the workspace directory exists or `76` when it is missing. If lock creation fails, the command exits with `75` when the lock already exists or `1` otherwise.
  - apply: run `set -e`, remove the stale manifest when restoring a missing workspace, then run `mkdir -p "$SANDRUN_SYNC_WORKSPACE"; cd "$SANDRUN_SYNC_WORKSPACE"; xargs -0 rm -f -- < "$SANDRUN_SYNC_DELETE_LIST"` (only with a deletion list); `rm -f --` of each path in `$SANDRUN_SYNC_REPLACE_FILE_LIST` other than an existing directory, through `xargs -0 sh -c` (only with a replacement list; a symbolic link to a directory is removed); `rmdir` of each directory in `$SANDRUN_SYNC_PRUNE_LIST` that exists and is not a symbolic link, through `xargs -0 sh -c` (only with a prune list); the same `rmdir` for records in `$SANDRUN_SYNC_PRUNE_ALIAS_LIST` through `xargs -0 -n 3 sh -c` (only with an alias prune list). Apply stops if an invocation receives fewer than three paths. The command uses `test -ef` to confirm both ancestor spellings resolve to the same directory and skips symbolic links. Then it runs `tar -x -m -o -f "$SANDRUN_SYNC_ARCHIVE"` (only with an archive). `-m` gives the extracted files the current time, so that guest builds see them as changed. `-o` keeps the guest user as the owner.
  - clean-up: `rm -f` of the archive, the deletion list, the replacement list, the prune list and the alias prune list, then `rm -rf "$SANDRUN_SYNC_LOCK"`. The command skips unset or empty paths and attempts every requested removal, including the lock, even if an earlier removal fails. It exits nonzero if any removal fails. Already absent paths count as successful removals.
  - download probe: `tar -c -f "$SANDRUN_DOWNLOAD_ARCHIVE" -C "$SANDRUN_DOWNLOAD_PATH" .` for a directory, `wc -c` for the size, and exit code `66` for a missing path. The archive is removed with `rm -f "$SANDRUN_DOWNLOAD_ARCHIVE"`.
- Windows guests (`powershell.exe -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <base64 of the UTF-16LE script>`, Windows PowerShell 5.1 and `%SystemRoot%\System32\tar.exe` of Windows 10 and later). The encoded command contains only base64 characters, so no Windows command-line quoting applies:
  - lock: removes the lock with `Remove-Item -Recurse -Force` when force is set, then runs `cmd.exe /d /e:off /c 'mkdir "%SANDRUN_SYNC_LOCK%" 2>nul'`. The `mkdir` of `cmd.exe` fails when the lock exists or its parent is missing. Exit codes `75` and `76` have the same meanings as on Linux and macOS.
  - apply: remove the stale manifest when restoring a missing workspace, then run `[System.IO.Directory]::CreateDirectory` of the workspace; `Remove-Item -LiteralPath -Force` for each strict deletion. For paths in the replacement list, apply uses `Get-Item -LiteralPath -Force` to inspect each path. It skips missing paths and regular directories, uses `[System.IO.Directory]::Delete` without recursion for directory reparse points, and uses `Remove-Item -LiteralPath -Force` for files. It then runs `[System.IO.Directory]::Delete` without recursion for each existing directory in the prune list; `tar.exe -x -m -f <archive> -C <workspace>`; `New-Item -ItemType SymbolicLink` for each link, with a `SANDRUN-LINK-FAILED <path>` line on standard output when it fails.
  - clean-up: `Remove-Item -LiteralPath -Force` removes the temporary sync files and adds `-Recurse` for the lock. It also removes the directory download archive. Both commands skip unset or already absent paths and exit nonzero if any removal fails. Sync attempts every removal, including the lock, after an earlier removal fails.
  - download probe: `tar.exe -c -f <archive> -C <path> .` for a directory and `(Get-Item -LiteralPath <path>).Length` for the size.
- Verification: the Go tests run the Linux and macOS commands against the local `sh` and `tar` through `sandruntest`. The Go tests check the form of the Windows commands and run the Windows sync retry and clean-up scenarios on Windows hosts with a local fixture. The tests do not use real OwnSand guests.

## Storage

The SDKs store nothing. Token storage belongs to the caller.

## Security

- The SDKs send tokens only to the configured API origin.
- Credential fields go only in set requests; the SDKs never log request messages.

## Logging

The Go SDK logs retries and reconnects at debug level through the caller's logger. The TypeScript SDK does not log. No log contains tokens or credentials.

## Build and Test

- TypeScript SDK package scripts: `build` (`tsc -p tsconfig.build.json` into the ignored `dist/`), `lint` (`node scripts/lint.mjs`: the Apache-2.0 SPDX header, no `console` calls, no `node:` imports in runtime sources and no imports from `servers/`), `typecheck` (`tsc --noEmit`) and `test` (`rstest run`). The tests run the real Connect-Web transport against an in-memory fake server (`src/testing/fake-server.ts`, a Connect router behind a fetch function) and a recording clock.
- The linter requires the exact Apache-2.0 SPDX header on the first line of each TypeScript source file. The header line can end with LF or CRLF.
- Go SDK commands (from the repository root): `go test ./go/sandrun/...` (the POSIX sync and download tests need `git`, `sh` and `tar` and skip on Windows hosts. The Windows sync retry and clean-up tests need `git`, Windows PowerShell 5.1 and the Windows system `tar.exe`), `go vet ./go/sandrun/...`, and `GOOS=windows go vet ./go/sandrun/...` and `GOOS=darwin go vet ./go/sandrun/...` for the other targets. The Go SDK is not a workspace package and has no package scripts; CI runs it in the root Go jobs.
- Tests: pagination, `WatchQueue` reconnects, exec attach after stream rotation and error mapping against a fake server. Go SDK sync and download tests: file selection with tracked, untracked and ignored files, incremental upload and deletion with the manifest, the size limits, case collisions and invalid Windows names, invalid UTF-8 rejection and recovery after a rename, repeated sync with valid non-ASCII names, ambiguous legacy manifest entries, the lock, symbolic links, path traversal on extraction, and a restart after a stopped sync.

## Dependencies and Integrations

- Upstream: the generated code of `delino.sandrun.v1`, Connect-ES and connect-go.
- Publication (recorded decision): the workspace package is named `sandrun-sdk` and is `private`, so neither pnpm nor Changesets publishes it, like `ownsand-sdk`. The npm package name and the publication workflow of the TypeScript SDK stay an [open decision](project-sandrun.md#open-decisions), together with the same decision of OwnSand.
