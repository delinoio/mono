# protos-ownsand API contract

## Scope

This contract owns the Connect RPC schemas of [`ownsand`](project-ownsand.md):

- `protos/delino/ownsand/v1/`: `.proto` files of the protobuf package `delino.ownsand.v1`.
- The generated Go bindings, committed next to the schemas: message code in the Go package `github.com/delinoio/mono/protos/delino/ownsand/v1` (package name `ownsandv1`) and Connect handlers and clients in its `ownsandv1connect` subpackage.
- `protos/buf.yaml` and `protos/buf.gen.yaml`: the buf module, lint and breaking-change configuration and the Go generation plugins. `scripts/protos.sh` runs them (see [Build and Test](#build-and-test)).
- The generated TypeScript bindings in `packages/ownsand-sdk/src/gen/`, which the [SDK contract](packages-ownsand-sdk-foundation.md#runtime-and-language) owns together with their template `packages/ownsand-sdk/buf.gen.yaml`; `scripts/protos.sh` generates and checks them with the Go bindings.

Schema files:

| File                 | Content                                                                                                                      |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `common.proto`       | Shared enums, `Principal`, `Resources`, `DeviceLimits`, `ErrorDetail`, `RequestAccepted`, `Keepalive` and `SandboxRevision`. |
| `organization.proto` | `OrganizationService`.                                                                                                       |
| `member.proto`       | `MemberService`.                                                                                                             |
| `device.proto`       | `DeviceService`, `Device`, `DeviceCapabilities` and `DeviceAllocation`.                                                      |
| `api_key.proto`      | `ApiKeyService`.                                                                                                             |
| `sandbox.proto`      | `SandboxService`.                                                                                                            |
| `snapshot.proto`     | `SnapshotService` with templates.                                                                                            |
| `data_path.proto`    | `DataPathService`.                                                                                                           |
| `data_frame.proto`   | `DataFrame` and every payload, the exec and file messages and `RelayRequestBinding`.                                         |
| `relay.proto`        | `RelayService` and `RelayAgentService`.                                                                                      |
| `agent.proto`        | `AgentService` and `AgentEnvelope` with every case.                                                                          |
| `guest.proto`        | `GuestService`.                                                                                                              |
| `audit.proto`        | `AuditAction`, `AuditTargetKind` and the `AuditEvent` record. No RPC returns audit events in `v1`.                           |

The schemas are the single source of truth for the public API, the agent channel and the data path framing. The control plane, the device agent, the guest helper, the CLI, the web console and both SDKs consume them. The schemas and the generated code use Apache-2.0.

## Runtime and Language

- Language: Protocol Buffers (proto3), compiled for Connect RPC.
- Go bindings: committed to the repository in the root Go module `github.com/delinoio/mono`. Go consumers import them directly and do not run code generation.
- TypeScript bindings: generated with `protoc-gen-es` for the [TypeScript SDK](packages-ownsand-sdk-foundation.md) and the [web console](apps-ownsand-console-foundation.md) and committed in `packages/ownsand-sdk/src/gen/`. The SDK contract owns where the generated TypeScript code lives and the plugin version.
- Code generation tool (recorded decision): the [buf CLI](https://buf.build/docs/cli/) `v1.72.0` (`github.com/bufbuild/buf/cmd/buf`), run through `go run` with that exact version, so that no binary is installed and the Go module cache verifies the download against the Go checksum database. `go run` builds buf with the Go toolchain that the root `go.mod` selects, and CI sets `GOTOOLCHAIN=local`, so the buf version must not require a newer Go than the root `go.mod` `go` directive (`v1.73.0` and later require Go `1.26.7`). Raise the buf version together with that directive. The Go plugins are `protoc-gen-go` `v1.36.12` (`google.golang.org/protobuf/cmd/protoc-gen-go`) and `protoc-gen-connect-go` `v1.21.1` (`connectrpc.com/connect/cmd/protoc-gen-connect-go`), which `protos/buf.gen.yaml` also runs through `go run` with exact versions. Each plugin version equals the runtime version of the same module in the root `go.mod` (`google.golang.org/protobuf` `v1.36.12` and `connectrpc.com/connect` `v1.21.1`); change them together. The owner approved these dependencies with the OwnSand implementation.

## Users and Operators

- Callers of the public API: organization members with Logto access tokens and programs with organization API keys, through the SDKs, the CLI and the web console.
- Device agents, through the agent channel.
- Guest helpers, through the guest channel inside each sandbox.

## Interfaces and Contracts

### General rules

- Package: `delino.ownsand.v1`. A breaking change needs a new package version (`v2`). Within `v1`, do not reuse or renumber fields, do not change field types, and reserve the numbers and names of removed fields.
- Identifiers that OwnSand or its callers generate are UUID v7 values in canonical text form in `string` fields named `<entity>_id`. The server accepts either hex case in these fields, treats two spellings of one UUID as the same identifier (it compares and rate-limits by value) and always returns lowercase text. User ID fields (`user_id`) hold the Logto `sub` unchanged as an opaque string and are not validated as UUIDs.
- Times use `google.protobuf.Timestamp`. Durations use `google.protobuf.Duration`.
- Every enum has a zero value `<ENUM>_UNSPECIFIED`. The server rejects `UNSPECIFIED` in a required enum field with `invalid_argument`. Optional enum fields, such as list filters and placement filters, use proto3 `optional`; an absent optional field means no filter.
- Sizes use `int64` fields with a unit suffix: `memory_mib`, `disk_gib`, `size_bytes`.
- List RPCs use `page_size` (default 50, maximum 200) and an opaque `page_token`.
- Errors use Connect error codes. Detail messages never contain secrets or sandbox content.
- Request and response messages follow the buf `STANDARD` lint rules: each RPC has its own `<Rpc>Request` and `<Rpc>Response` message. A streaming RPC that carries a shared message wraps it in one field (for example `ExecResponse.event`, `ConnectRequest.frame` and `ChannelRequest.envelope`); the wrapper adds a few bytes to each stream message, which the 1 MiB plus 64 KiB frame limit does not count.
- `ErrorCode` carries an error inside frames and agent channel results. Its numeric values equal the Connect error codes. `ErrorDetail` carries the code, a message without secrets or sandbox content, an optional retry delay and, when a session end caused the error, the `SessionEndReason`.
- Every public RPC, including `RelayService`, is unary or server-streaming, so that clients without client or bidirectional streams can use it. See [the project transport rule](project-ownsand.md#protocol-and-api). Only the device-facing `RelayAgentService.Connect` and `AgentService.Channel` are bidirectional. `AgentService.Channel` is a Connect bidirectional stream (a recorded decision; only its WebSocket fallback stays open), as the [control plane agent channel section](servers-ownsand-api-foundation.md#agent-channel) records. Both need HTTP/2 from end to end, which the [control plane contract](servers-ownsand-api-foundation.md#runtime-and-language) requires from the proxy route.

### Sandbox state rules

| RPC                                                                                | Required sandbox state                                                                                                                                                                                                                                                                                                                                                           | Otherwise                                                                                                                           |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `OpenSession`                                                                      | `RUNNING`                                                                                                                                                                                                                                                                                                                                                                        | `unavailable` for `UNREACHABLE`; `failed_precondition` for every other state                                                        |
| `PauseSandbox`                                                                     | `RUNNING` (`PAUSED` succeeds without change)                                                                                                                                                                                                                                                                                                                                     | `unavailable` for `UNREACHABLE`; `failed_precondition` for every other state                                                        |
| `ResumeSandbox`                                                                    | `PAUSED` (`RUNNING` succeeds without change)                                                                                                                                                                                                                                                                                                                                     | `unavailable` for `UNREACHABLE`; `failed_precondition` for every other state                                                        |
| `CreateSnapshot`                                                                   | `RUNNING` or `PAUSED`                                                                                                                                                                                                                                                                                                                                                            | `unavailable` for `UNREACHABLE`; `failed_precondition` for every other state                                                        |
| `Exec`, `ReadFile`, `WriteFile` (`RelayService` RPC or data channel request frame) | `RUNNING`, checked by the agent before it dispatches the request; the relay forwards the agent's `failed_precondition` without its own state check                                                                                                                                                                                                                               | `failed_precondition` from the agent; for `UNREACHABLE`, `AuthorizeRelay` or `OpenSession` returns `unavailable` before any request |
| `AttachExec` (`RelayService` RPC or data channel request frame)                    | `RUNNING` or `PAUSED` (on a paused sandbox, only the kept output and result of the exec are returned; for an exec that has not ended, the stream returns its kept output and then ends with a `paused` event, and the SDK watches the sandbox until it resumes, the caller cancels, or the sandbox ends; when the sandbox ends first, the exec ends with the sandbox end reason) | `failed_precondition` from the agent; for `UNREACHABLE`, `AuthorizeRelay` or `OpenSession` returns `unavailable` before any request |
| `AuthorizeRelay`                                                                   | `EXEC` and `ATTACH_EXEC`: `RUNNING` or `PAUSED`; `READ_FILE` and `WRITE_FILE`: `RUNNING`. `UNREACHABLE` gives `unavailable` here, before any relay RPC                                                                                                                                                                                                                           | `unavailable` for `UNREACHABLE`; `failed_precondition` for every other state                                                        |
| `DeleteSandbox`                                                                    | any state except `DELETED` and `FAILED` (those succeed without change)                                                                                                                                                                                                                                                                                                           | —                                                                                                                                   |

`CreateSandbox` returns the sandbox in `CREATING` without waiting for the agent; the caller watches `GetSandbox` until a stable state: `RUNNING`, `PAUSED` (another caller paused it), or the terminal `FAILED` or `DELETED` with its `SandboxEndReason` (for example, a TTL that ended or a removed device). `CreateSnapshot` and `ExportSnapshot` also return at once with a snapshot in `CREATING` or `EXPORTING`. `ExportSnapshot` of an `EXPORTING` snapshot returns it without a new command while its export runs on the owning agent channel, and a retry of an `EXPORT_FAILED` snapshot starts one new export. An export whose agent channel, agent or control plane was interrupted becomes `EXPORT_FAILED` when the device reports on its replacement channel; the caller retries explicitly (see the [export recovery record](servers-ownsand-api-foundation.md#storage)). The export command and its result keep their message shapes: the server uses the `command_id` of the export command as the export attempt ID and ignores a result whose `command_id` is not the current attempt's. `PauseSandbox`, `ResumeSandbox` and `DeleteSandbox` wait up to 60 seconds for the agent result and then return the current state, which the caller can watch with `GetSandbox`.

### Create request

`CreateSandboxRequest` fields:

- `organization_id`.
- `idempotency_key`: a UUID v7 that the caller generates for each create. The server stores it with the reservation for 24 hours: a retry with the same `idempotency_key` and the same parameters returns the original sandbox, and a retry with different parameters fails with `already_exists`. A caller whose create response was lost retries with the same `idempotency_key`.
- `source`: exactly one of `base_image` (a `BaseImage` enum value), `snapshot_id` or `template_id`.
- `resources`: `vcpu_count`, `memory_mib` and `disk_gib`. All three are required and must be greater than zero. For a snapshot or template source, `disk_gib` must be at least the snapshot's disk size, and the server rejects a smaller disk with `invalid_argument`. Memory state restores only when `vcpu_count` and `memory_mib` equal the snapshot's values; other values are valid and boot the disk cold, according to the [control plane scheduler](servers-ownsand-api-foundation.md#scheduler).
- `idle_ttl` and `max_ttl`: required. Both must be greater than zero, `idle_ttl` must not be greater than `max_ttl`, and `max_ttl` must not be greater than 7 days. The server rejects a request that breaks any of these rules, including a missing TTL, with `invalid_argument`. Exactly 7 days is valid. There is no default TTL.
- `placement`: optional `device_id`, or optional `host_os` and `arch` filters. `guest_os` is derived from the source. With `device_id`, the scheduler does not select another device: the request fails with `unavailable` or `failed_precondition` according to the error-code rule of the [control plane scheduler](servers-ownsand-api-foundation.md#scheduler).
- `network`: `NETWORK_MODE_OUTBOUND` (the default when the field is absent) or `NETWORK_MODE_NONE`. A present `network` message with an unspecified mode fails with `invalid_argument`. The field is a message so that later policies can extend it without a new RPC.
- `labels`: optional string map (at most 32 entries; keys at most 63 bytes, values at most 255 bytes). Labels must not contain secrets; every member and API key of the organization can read them, and the console shows them. Components never log labels.

### Device limits

- Device limits are `vcpu_count`, `memory_mib`, `disk_gib` and `vcpu_overcommit_percent`. The first three are the upper limits of vCPU, memory and disk that sandboxes on the device may use together. `vcpu_overcommit_percent` lets the scheduler allocate more vCPUs than `vcpu_count`; the [control plane vCPU overcommit rule](servers-ownsand-api-foundation.md#vcpu-overcommit) owns its valid values and effect.
- `ReplaceDeviceLimits` replaces all four values together with the request-only message `DeviceLimitsInput`, whose four fields use explicit presence (`optional`). Every value must be present: the server rejects a request with a missing `limits` message or a missing value with `invalid_argument` that names the first missing field (`limits.vcpu_count`, `limits.memory_mib`, `limits.disk_gib` or `limits.vcpu_overcommit_percent`), before any write, so that the stored limits, the configuration events and the audit records stay unchanged. An explicit `0` for `vcpu_count`, `memory_mib` or `disk_gib` is a present value and is stored (the device then gets no sandboxes that need the resource). The numeric rules (no negative value, `vcpu_overcommit_percent` from 100 to 400 in steps of 25) apply after the presence check. `DeviceLimits` stays the response, agent configuration and legacy request message. `vcpu_overcommit_percent` uses an integer percentage, not a floating-point ratio, so that equal values compare exactly.
- `UpdateDeviceLimits` is the legacy RPC of v1 and keeps working for existing clients. Its request carries `DeviceLimits`, whose scalars have implicit presence, so a missing value reads as `0` and an omitted `disk_gib` is stored as `0`; an intentional zero still works, and a missing `limits` message or a negative or invalid value is `invalid_argument`. It has the same authorization, validation of the numeric rules, configuration notification and audit record as `ReplaceDeviceLimits`; the schema carries the legacy mark in comments only, without a deprecation option. New clients call `ReplaceDeviceLimits`; the Go SDK (`DeviceService.ReplaceLimits`), the CLI and the console already do. A client migrates by building a `DeviceLimitsInput` that sets all four fields (in TypeScript, set each field explicitly, also when it is `0`; in Go, use pointers such as `proto.Int32`) and calling `ReplaceDeviceLimits`.
- The `Device` message carries the device limits, the effective vCPU limit and the allocated vCPU, memory and disk.
- The effective vCPU limit is floor(`vcpu_count` × `vcpu_overcommit_percent` / 100) and can exceed the `int32` range (for example, 536870912 vCPUs at 400% give 2147483648). `Device.effective_vcpu_limit_count` (`int64`, tag 16) carries the exact value on every `ReplaceDeviceLimits`, `UpdateDeviceLimits`, `GetDevice` and `ListDevices` response; it is 0 for a device with zero limits, such as a newly enrolled device. The `int32` field `Device.effective_vcpu_limit` (tag 11) stays for v1 compatibility: it carries the same value when it fits and 2147483647 when the exact value is larger, so a client that only reads it never sees a negative or wrapped value. Clients read `effective_vcpu_limit_count`.
- The allocated vCPUs can also exceed the `int32` range, because the allocation is the sum over the active sandboxes of the device (for example, two sandboxes of 2147483647 vCPUs sum to 4294967294). `DeviceAllocation.vcpu_total_count` (`optional int64`, tag 5) carries the exact sum on every `Device` response and the server always sets it. The `int32` field `DeviceAllocation.vcpu_count` (tag 1) stays for v1 compatibility: it carries the same value when it fits and 2147483647 when the exact sum is larger, so a client that only reads it never sees a negative or wrapped value. Clients read `vcpu_total_count` and fall back to `vcpu_count` when the field is absent, which an older server never sends. The schema change is additive.

### Exec

- `ExecRequest`: `organization_id`, `sandbox_id`, `exec_id`, `command` (argument array, the first element is the program), `env` (string map), `working_directory`, optional `timeout` and `binding_salt` (see [relay grants](#relay-grants)), which is part of the idempotency comparison below. When the timeout ends, the guest helper stops the command (on Linux and macOS guests it sends `SIGTERM` and, 10 seconds later, `SIGKILL` to the process group, also when the direct child has already exited and the `exited` event is already sent; on Windows guests it terminates the process tree) and the `exited` event carries `timed_out` set to true with the exit code or signal. A command whose direct child exited before the timeout is not timed out, even while a descendant still holds its output pipes during the helper's bounded output drain: `timed_out` stays false and the helper sends no timeout signal. The encoded `command`, `env` and `working_directory` together must not exceed 256 KiB; the server and the SDKs reject a larger request with `invalid_argument` before they frame it, and the agent checks the decoded fields again before it dispatches an exec from either transport. A shell runs only when the caller passes one, for example `["/bin/sh", "-c", "..."]`.
- The caller generates the `exec_id` (a UUID v7) before it sends the request, so it can resume the exec even when the stream ends before the `started` event, and writes it in the lowercase text form that `uuidv7.UUID.String` returns, because the agent compares exec IDs as text: an `ExecRequest` or `AttachExecRequest` whose `exec_id` has an uppercase hex digit fails with `invalid_argument` before the agent admits it, so another spelling of one UUID cannot start a second command. The lowercase rule applies only to the `exec_id` of these two requests and to the `operation_id` of their relay grants; other UUID fields keep accepting either text case. The agent applies the same timestamp window and the 30-minute memory of ended IDs to `exec_id` as to `read_id` and `write_id` (see expired operation IDs below), so a delayed duplicate request never runs a command again. While the agent keeps an exec (until 10 minutes after it ends) and across agent restarts within that time, it runs each `exec_id` at most once: a second `ExecRequest` with a known `exec_id` and the same `sandbox_id`, `command`, `env`, `working_directory`, `timeout` and `binding_salt` attaches to the existing exec from offset 0 and does not run the command again. A known `exec_id` with any other value in these fields fails with `already_exists`. Callers must not reuse an `exec_id`. The same binding applies to `read_id` (sandbox, path and `binding_salt`) and `write_id` (sandbox, target path and `binding_salt`).
- The response stream carries `ExecEvent` messages in order: on the relay, first one `accepted` event that the agent sends when it accepts the request (for `Exec` and `AttachExec`; relay `keepalive` events may come before it and do not count as events of the sequence); then one `started` event with the `exec_id` (also for `AttachExec`, which repeats it); then, for an `AttachExec` whose requested offset is older than the kept output, one `output_truncated` event with the first available offsets, then `stdout` and `stderr` chunks (at most 64 KiB each), then exactly one `exited` event with the exit code (an `int64`, so that 32-bit Windows codes keep their value) or, when a signal ended the command, the signal number, or a `failed` event when the command could not start, or a `sandbox_ended` event with the `SandboxEndReason` when the sandbox ended (for example, while it was paused) before the exec result could be delivered. On both `AttachExec` transports, a continuation for an exec that has not ended, on a paused sandbox, ends the sequence with exactly one `paused` event instead of a result event, after `started`, any `output_truncated` event and the kept output; a continuation for an exec with a kept result returns the applicable result event, also on a paused sandbox. When the sandbox resumes, the caller sends a new `AttachExec` with the offsets it already received, and the exec continues from those offsets. Each output chunk carries its byte offset in its stream (stdout or stderr).
- The command runs on the agent independently of the stream. A stream may end before the command ends: the control plane ends a relay stream itself before it has run for 14 minutes, with an OK status and no final event (a stream rotation), and sends a `keepalive` event at least every 60 seconds while the command produces no output. A stream that ends without `exited` or `failed` does not stop the command.
- `AttachExec` takes the `exec_id` and the next stdout and stderr offsets, and continues the same event sequence. The agent keeps the last 8 MiB of each output stream and the exit result for 10 minutes after the command ends. When the requested offset is older than the kept output, the stream carries an `output_truncated` event with the first available offsets right after `started`, in the order given for the event stream above, on both transports. When the exec is unknown, or its result is no longer kept, `AttachExec` fails with `not_found`; the outcome of the command is then unknown.
- Schema: `ExecEvent` is a `oneof` with the cases `accepted` (`RequestAccepted`), `started` (`ExecStarted`), `output_truncated` (`ExecOutputTruncated` with the first available `stdout_offset` and `stderr_offset`), `stdout` and `stderr` (`ExecOutput` with `offset` and `data`), `exited` (`ExecExited` with a `oneof` of `exit_code` (`int64`) or `signal` (`int32`), and `timed_out`), `failed` (`ExecFailed` with an `ExecFailureReason` and a message), `sandbox_ended` (`ExecSandboxEnded` with the `SandboxEndReason`), `keepalive` (`Keepalive`) and `paused` (`ExecPaused`). `AttachExecRequest` carries the `exec_id` and the next `stdout_offset` and `stderr_offset`.
- On the peer-to-peer data channel, the same exec continues after a channel failure with an `AttachExec` request frame on a new session or on the relay.
- Stdin is not part of `v1`.

### File transfer

- `ReadFile` takes a `read_id` (a UUID v7 that the caller generates right before the first call), the absolute guest `path`, the `binding_salt` and an optional start `offset`, and streams `FileChunk` messages of at most 1 MiB with the `offset` of each chunk and a final message with the file `size_bytes`. At the first call for a `read_id`, the guest helper makes a private snapshot of the file (a reflink copy where the guest file system supports it, otherwise a full copy) and serves every call for that `read_id` from the snapshot. A full copy is a point-in-time view only when no process writes the file during the copy. The guest helper compares the file identity, size and modification time before and after the copy and fails the call with `aborted` when they changed, but a writer that keeps these values unchanged is not detected; for a full copy, the guarantee is only that every retry of the `read_id` returns the same bytes. A reflink copy is always a point-in-time view. After an interrupted stream, the caller calls `ReadFile` again with the same `read_id` from the next offset, so a resumed read never combines two versions of a file. The guest helper keeps the snapshot while any call for the `read_id` is open, and until 15 minutes after the last call for it ends, also after it sent the final message, so a caller that lost the last chunks or the final message can call again. A later call fails with `not_found`. While the guest helper prepares the snapshot or the next chunk, the stream carries a `keepalive` message at least every 60 seconds; a `keepalive` does not move the offset. On the relay, the first message of each `ReadFile` stream other than relay `keepalive` messages is an `accepted` message that the agent sends when it accepts the request; it does not move the offset either. The snapshot uses guest disk while the read is open.
- `WriteFile` is unary. The control plane requires the whole relay `WriteFile` call, including the upload of its request body and the agent's result, to finish within 5 minutes ([control plane relay streams](servers-ownsand-api-foundation.md#relay-streams)); the SDKs retry a chunk whose upload times out, which the `write_id` rules make safe. Connect can carry client streams over HTTP/1.1, but browser clients cannot send them, and unary chunks let a caller retry or resume one chunk after an interrupted upload. The caller generates the `write_id` (a UUID v7) right before the first call, so a retry after a lost response reaches the same write. Each call writes one chunk of at most 1 MiB at an `offset` to that `write_id`. The first call of a `write_id` also carries the absolute guest `path` and the `binding_salt`. The guest helper records the written ranges: writing the same bytes again is harmless, a chunk that overlaps written bytes with different content fails with `failed_precondition`, and `finish` fails with `failed_precondition` unless the written ranges cover exactly `[0, size_bytes)`. The last call sets `finish` with the total `size_bytes` and the file `mode`. The guest helper writes to a temporary file and renames it into place only after `finish`, so a failed upload never leaves a partial file at the target path. The guest helper deletes the temporary file of a `write_id` that receives no chunk for 15 minutes; a later call with that `write_id` fails with `not_found`. After a successful `finish`, the guest helper keeps the result for 15 minutes together with the `finish` fields (`size_bytes`, `mode`, and the offset and digest of the final chunk): a repeated `finish` for that `write_id` with the same fields returns the same result and does not write the target again, and one with different fields fails with `failed_precondition`.
- Expired operation IDs: the agent checks every new `read_id` and `write_id` when its first frame arrives, against its own host clock, which must be synchronized with NTP. It accepts an unknown ID only when the timestamp in the UUID v7 is less than 15 minutes old and not more than 5 minutes in the future. An unknown ID that is older fails with `not_found`, like a remembered expired ID, and the error message says that the operation expired or that the caller's clock may be behind; only an ID more than 5 minutes in the future fails with `failed_precondition` and a clock-skew message. The agent remembers the ID of each ended or expired operation for 30 minutes of its own monotonic time. After a memory-state restore and after a resume, the agent sets the guest clock from the host clock through the guest helper. A retry of an expired operation, also at offset zero, therefore fails with `not_found` and never starts a new snapshot or temporary file.
- Schema: a file read stream carries `FileReadEvent` messages, a `oneof` of `accepted` (relay only), `keepalive`, `chunk` (`FileChunk` with `offset` and `data`) and `end` (`FileReadEnd` with `size_bytes`, the final message). The relay `ReadFileResponse` wraps one `FileReadEvent`, and the data path carries it in the `FILE_READ_EVENT` frame, which is the "file chunk" payload of [data path framing](#data-path-framing). `WriteFileRequest` carries `write_id`, `path` and `binding_salt` (required on the first call), `offset`, `data` and the optional `finish` (`WriteFileFinish` with `size_bytes` and `mode`); `WriteFileResponse` reports the written `offset` and `length`, `finished` and the final `size_bytes`.
- Paths are absolute guest paths. The guest helper resolves them inside the guest; the device agent never resolves a guest path on the host file system.

### Data path framing

The peer-to-peer data channel and the relay carry the same `DataFrame` messages, so the agent and the guest helper handle both transports with one implementation.

- `DataFrame` has a `stream_id` (an unsigned 64-bit number; on a peer-to-peer session the caller chooses it, unique within the session, and on the relay the control plane allocates it, unique among all open relay RPCs on the agent's relay connection, so it can route every agent frame to its RPC; `stream_id` 0 with an empty `sandbox_id` is reserved for connection-level frames on the relay connection), the `sandbox_id` that the control plane authorized, a `kind` (`DataFrameKind`) and one payload: a relay stream open (with the relay grant ID and the control plane's first credit window for the agent's frames toward the caller; relay only), a relay stream close (relay only), a relay window update (with the number of bytes that it adds to the sender's window for that `stream_id`; relay only), a keepalive (relay connection only, on `stream_id` 0; it may ask for an echo), a supported frame kinds list (relay connection only, on `stream_id` 0, sent by each side when `Connect` opens), a session end (with a `SessionEndReason`), a request accepted notice (agent to control plane on the relay connection, sent when the agent accepts an `Exec`, `AttachExec` or `ReadFile` request; the control plane turns it into the `accepted` event or message; it uses no credit), an exec request, an exec attach request (with the `exec_id` and the next stdout and stderr offsets), an exec event, a file read request, a file chunk, a file write chunk, a file write result or an error.
- Schema: `DataFrame` has `stream_id` (`uint64`), `sandbox_id`, `kind` (`DataFrameKind`) and the `oneof payload`. Each `DataFrameKind` value other than `UNSPECIFIED` names exactly one payload field: the kind name without the `DATA_FRAME_KIND_` prefix in lowercase is the field name (`RELAY_STREAM_OPEN` and `relay_stream_open` with `RelayStreamOpen{grant_id, initial_window_bytes}`, `RELAY_STREAM_CLOSE`, `RELAY_WINDOW_UPDATE` with `increment_bytes`, `RELAY_KEEPALIVE` with `echo_requested`, `SUPPORTED_FRAME_KINDS` with the `kinds` list, `SESSION_END` with the reason, `REQUEST_ACCEPTED`, `EXEC_REQUEST` (`ExecRequest`), `EXEC_ATTACH_REQUEST` (`AttachExecRequest`), `EXEC_EVENT` (`ExecEvent`), `FILE_READ_REQUEST` (`ReadFileRequest`), `FILE_READ_EVENT` (`FileReadEvent`), `FILE_WRITE_CHUNK` (`WriteFileRequest`), `FILE_WRITE_RESULT` (`WriteFileResponse`) and `ERROR` (`ErrorDetail`)). A test in the generated package checks this rule. The sender always sets `kind` to the kind of the payload; a receiver that gets a known kind with a different or missing payload treats the frame as malformed. `kind` exists so that a receiver can recognize a payload kind that its schema does not know yet.
- On the WebRTC data channel, the frames form one byte stream: each frame is encoded as a varint length followed by the encoded `DataFrame`. The sender splits this byte stream into data channel messages of at most 16 KiB, which is below the 64 KiB default receive limit of [RFC 8841](https://www.rfc-editor.org/rfc/rfc8841.html#section-6.1). The receiver reassembles frames from the length prefixes. An encoded `DataFrame` is at most 1 MiB plus 64 KiB, which holds the largest file chunk and its envelope; the receiver checks the declared length before it buffers the frame and closes the data channel when the length is larger. The data channel is ordered and reliable. One data channel serves one `OpenSession` session and may carry several concurrent requests, distinguished by `stream_id`.
- On the relay connection (`RelayAgentService.Connect`), each Connect stream message carries one `DataFrame`, with the same 1 MiB plus 64 KiB size limit. The control plane opens each relay RPC with a relay stream open frame for a new `stream_id`; every later frame of that `stream_id` belongs to the grant ID of that stream open frame. Each relay RPC carries one operation request, in the first request frame after the stream open. The control plane allocates `stream_id` values in increasing order from 1 on each relay connection and never reuses one on that connection, so a late frame of a closed stream cannot reach another RPC; both sides drop frames of a closed `stream_id`.
- When a relay RPC ends for any reason other than an agent session-end or error frame (the caller cancels it, the caller connection fails, the control plane ends it at its stream limit, at its acceptance timeout or at a request deadline, or the request does not match the grant), the control plane sends a relay stream close frame for its `stream_id`. The agent then stops sending frames for that stream and releases its output subscription. A relay stream close does not stop an exec and does not end a read snapshot or a write: they keep the lifetime of the [exec](#exec) and [file transfer](#file-transfer) rules, so the caller can continue them with `AttachExec`, `ReadFile` or `WriteFile`.
- When the agent rejects a relay stream because the grant ID names no live grant (unknown, past its expiry plus the 30-second admission tolerance when the first request frame arrived, or revoked, for example after the agent channel was lost), it answers with a session-end frame with `GRANT_INVALID` for that `stream_id`, and the control plane ends the RPC with `unavailable` and that reason in the error detail. The agent rejects the first request frame of a stream with an error frame (`permission_denied`) when its kind, operation ID or request digest does not match the grant, and rejects a relay stream open with an error frame (`resource_exhausted`) at once when it is at its stream or credit capacity; the control plane ends the RPC with that status.
- Flow control: credit windows apply in both directions. A window counts the bytes of encoded `DataFrame` messages. Every per-stream buffer and every initial window is at least one maximum frame (1 MiB plus 64 KiB), so a maximum file chunk can always be sent. The outstanding credit may fall to zero; each window update returns exactly the bytes that the receiver's consumer freed. Only payload frames use credit (exec requests, exec attach requests, file read requests, exec events, file chunks, file write chunks and file write results); stream open, stream close, window update, keepalive, session-end and error frames do not. The agent sends the first window for its direction when it accepts a stream open frame. The agent sends payload frames of a relay stream toward the caller only within a credit window that the control plane grants for that stream. The control plane sends request payload frames (exec requests, exec attach requests, file read requests and file write chunks) toward the agent only within a credit window that the agent grants for that stream with relay window updates, and the agent buffers at most that window for each stream, so it never stops reading the shared connection because one guest is slow. The control plane opens each stream with a window equal to its per-stream buffer, carried in the relay stream open frame, and sends a relay window update as the caller consumes data. A slow caller therefore stops only its own stream, and the control plane never needs to stop reading the shared connection or drop frames.
- When a relay connection's transport closes, or another connection replaces it, the agent ends every stream of that connection as if it received a relay stream close frame for each, and keeps the exec and file operation state under the same rules.
- The agent serves a frame only for the sandbox bound to its peer-to-peer session, or, on the relay, for the `sandbox_id` of the live relay grant whose grant ID the relay stream open frame names and that the current agent channel sent, and rejects any other `sandbox_id`, an unknown or expired grant ID and a revoked grant. Expiry applies to the first request frame of a stream only: a grant that expires does not end streams whose first request the agent already accepted; it only stops new ones. The agent ends the streams that are still open at the grant's stream deadline, according to the [control plane contract](servers-ownsand-api-foundation.md#data-path-signaling-and-relay).
- The `RelayService` RPCs (`Exec`, `AttachExec`, `ReadFile`, `WriteFile`) translate their requests into `DataFrame` messages for the agent and translate the agent's frames back into responses.

### Relay services

| Service             | RPC       | Kind          | Caller       | Purpose                                                                                                                                          |
| ------------------- | --------- | ------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `RelayService`      | see above | see above     | SDK, CLI     | Relay exec and file requests to the agent of the grant's device. Authenticated with the caller's API key or Logto access token and the grant ID. |
| `RelayAgentService` | `Connect` | bidirectional | Device agent | Carry `DataFrame` messages between the control plane and one device agent. Authenticated with the device session credential (`osd_`).            |

`RelayService` uses the data path messages as its requests: `Exec` takes `ExecRequest` and streams `ExecResponse` (one `ExecEvent`), `AttachExec` takes `AttachExecRequest` and streams `AttachExecResponse` (one `ExecEvent`), `ReadFile` takes `ReadFileRequest` and streams `ReadFileResponse` (one `FileReadEvent`), and `WriteFile` takes `WriteFileRequest` and returns `WriteFileResponse`. `RelayAgentService.Connect` sends `ConnectRequest` (agent to control plane) and receives `ConnectResponse` (control plane to agent); each carries one `DataFrame` in `frame`.

The control plane serves both services at its origin `https://ownsand.api.delino.io`. Each `RelayService` request carries the grant ID that `AuthorizeRelay` returned in the `Ownsand-Relay-Grant-Id` request header, so the control plane can check the grant before it receives a unary request body. `RelayService` requests keep their `organization_id` and `sandbox_id` fields, and the control plane checks them against the grant. The [control plane contract](servers-ownsand-api-foundation.md#relay) owns relay authentication, timeouts, keepalives and limits.

### Relay grants

- A relay grant ID is a UUID v7 that the control plane creates for each grant. It is an identifier, not a credential: every relay RPC also carries the credential of the grant's principal. The control plane does not persist it.
- `request_digest` is the SHA-256 of a `RelayRequestBinding` message that the caller builds from the request it will send and the agent builds again from the first request frame. The message holds `binding_salt`, `sandbox_id`, `operation_kind`, `operation_id` and, for `EXEC`, `command`, `env` (as a repeated key and value entry list sorted by key bytes, so that map order does not change the digest), `working_directory` and `timeout`; for `READ_FILE` and `WRITE_FILE`, the absolute guest `path`. An `ATTACH_EXEC` grant has no request digest: `AttachExec` cannot start a command, so a caller that knows only the `exec_id` (for example, another program, or a program that restarted) can attach to an exec of the sandbox on either transport. The digest input is the protobuf binary encoding of that message with fields in field-number order and no unknown fields. A required test checks that the Go and TypeScript encodings of the same binding give the same digest.
- Schema: `RelayRequestBinding` has the fields `binding_salt` (1), `sandbox_id` (2), `operation_kind` (3), `operation_id` (4), `command` (5), `env` (6, repeated `EnvironmentEntry` with `key` and `value`), `working_directory` (7), `timeout` (8, `google.protobuf.Duration`, absent without a timeout) and `path` (9). Fields that the operation kind does not use stay empty and are not encoded. `request_digest` is the 32-byte SHA-256. The [SDK contract](packages-ownsand-sdk-foundation.md#shared-go-packages) owns the shared Go implementation and the golden test vectors.
- `binding_salt` is 32 random bytes that the caller generates for each operation and sends in the operation's request (`ExecRequest`, every `ReadFile` request and the first `WriteFile` chunk), never in `AuthorizeRelay`. The salt keeps a holder of the digest alone (for example, of an `AuthorizeRelay` request or a pending grant) from confirming a guessed command, environment value or path. On the relay, the control plane forwards the request itself in memory, so the salt does not hide the request from the control plane there.
- The agent records the digest of each exec, read and write when it first accepts the operation, on either transport (also for an exec that started on a peer-to-peer session). `AttachExec` and later `WriteFile` chunks do not carry the bound fields: under an `EXEC` or `WRITE_FILE` grant they are checked by comparing the grant digest with the recorded digest of the operation that the `exec_id` or `write_id` names. Under an `ATTACH_EXEC` grant, which has no digest, the agent checks only the sandbox, the `exec_id` and that the request is `AttachExec`. Every `ReadFile` request carries the path and the salt, so the agent builds the digest from the request and also requires it to equal the recorded digest of the `read_id` when one exists. A retry of the identical `ExecRequest` builds the same digest. A caller whose first `ReadFile` request was lost before the agent received it therefore resends the same request; when the agent already made the snapshot for that `read_id` and the digest matches, it serves the existing snapshot. When the agent no longer keeps an exec or write operation, the continuation fails with `not_found`, as without a grant check; a digest mismatch fails with `permission_denied`. The SDK keeps the original request fields and salt of each open operation, so it can call `AuthorizeRelay` for a continuation.
- `AuthorizeRelayRequest` fields: `organization_id`, `sandbox_id`, `operation_kind` (`RelayOperationKind`), `operation_id` (for `EXEC` and `ATTACH_EXEC`, the lowercase `exec_id`; an uppercase hex digit fails with `invalid_argument` before a grant is reserved), `request_digest` (absent for `ATTACH_EXEC`), `authorization_id` and optional `replaces_grant_id`, according to the [control plane relay authorization rules](servers-ownsand-api-foundation.md#data-path-signaling-and-relay). `AuthorizeRelayResponse` fields: `grant_id`, `expire_time` (the absolute expiry; `expireTime` in Connect JSON) and `expires_in` (the remaining duration when the control plane sends the response, which the SDK measures on its monotonic clock).
- The relay `accepted` event is an `ExecEvent` case for `Exec` and `AttachExec` and a `ReadFile` response message case; it carries no payload.
- `AuthorizeRelay` returns the `AuthorizeRelayResponse` fields listed above. The relay grant on the agent channel carries the same `grant_id`, `sandbox_id`, operation kind, ID and request digest, principal and `expire_time`.

### Agent channel

`AgentService` is the device-facing API. It is not part of the SDKs.

| RPC               | Kind       | Purpose                                                                                                                                              |
| ----------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Enroll`          | unary      | Exchange an enrollment token and the device public key for a `device_id`.                                                                            |
| `CreateChallenge` | unary      | Return a one-time nonce for the device.                                                                                                              |
| `Authenticate`    | unary      | Exchange a signed nonce for a short-lived `osd_` device session credential, or return the removal notice.                                            |
| `ConfirmRemoval`  | unary      | Confirm the local clean-up of a removed device with a signed nonce. Accepted only for removed devices.                                               |
| `Channel`         | long-lived | Carry `AgentEnvelope` messages in both directions. The [control plane contract](servers-ownsand-api-foundation.md#agent-channel) owns the transport. |

`AgentEnvelope` carries one of: heartbeat, capability report, state report (all sandboxes, snapshots and images on the device), command (create, delete, pause, resume, snapshot, export, import, clean up, update, delete snapshot), command result, configuration (STUN server URLs and the device limits), sandbox update (a sandbox ID, its state, its end reason when it ended, and its idle deadline), heartbeat acknowledgement (with the heartbeat sequence number), acknowledgement of a state report or sandbox update, signaling message (SDP offer with the session ID, sandbox ID, principal and absolute expiry; SDP answer), session revocation (with a revocation ID and its target, a `oneof` of the session ID or the relay grant ID that it ends), revocation acknowledgement, signed URL request and signed URL grant (snapshot ID and part numbers; the agent asks for fresh part URLs before the old ones expire, so an export or import may run longer than 15 minutes), relay grant (grant ID, the optional `replaces_grant_id`, sandbox ID, operation kind, ID and request digest, principal, expiry, stream deadline, `expires_in` and `stream_deadline_in` (the remaining durations when the control plane sends it)), relay grant acknowledgement (with the new grant ID, the `RelayGrantResult`, and the grant ID that the agent actually replaced, if any) and relay grant release (grant ID). The agent channel carries no `DataFrame`; relay data uses the separate `RelayAgentService` connection. Signaling is non-trickle: both peers finish ICE candidate gathering before they send the offer or the answer, which carry all candidates. Each sandbox entry in a state report, each sandbox update and each acknowledgement has the sandbox revision. Each sandbox entry in a state report has its state, its current idle deadline and, for an ended sandbox, its `SandboxEndReason`. The server acknowledges each state report, and the agent then drops the records of ended sandboxes that the report contained.

Schema decisions:

- `AgentService.Channel` is defined as a Connect bidirectional stream of `ChannelRequest` (agent to control plane) and `ChannelResponse` (control plane to agent) messages, each with one `AgentEnvelope`. The [control plane contract](servers-ownsand-api-foundation.md#agent-channel) still owns the transport decision; a WebSocket transport would carry the same `AgentEnvelope` messages.
- `AgentEnvelope` is a `oneof` with the cases `heartbeat` (sequence number, `AgentUpdateState` and the update target version), `heartbeat_ack`, `capability_report` (host OS, architecture, agent version and `DeviceCapabilities`), `state_report` (report sequence number, state epoch, `SandboxStateEntry` and `SnapshotStateEntry` lists and the built base images), `sandbox_update` (one `SandboxStateEntry`), `state_ack` (a `oneof` of a state report acknowledgement with its sequence number and the acknowledged sandbox revisions, or a sandbox update acknowledgement with the sandbox ID and revision), `command` (`AgentCommand` with a `command_id` and a `oneof` of the create, delete, pause, resume, snapshot, export, import, clean-up, update, delete-snapshot and withdraw-agent-update commands; `delete_snapshot` (`DeleteSnapshotCommand` with the snapshot ID, field 11) was added after the first schema version, so an older agent answers it with `UNIMPLEMENTED`; `withdraw_agent_update` (`WithdrawAgentUpdateCommand`, empty, field 12) was added the same way: the control plane sends it under the `HOLD` policy when no revocation recovery applies, and the agent drops its queued update before the installation starts, answers `failed_precondition` once the installation started or while the running version is revoked, and an agent without the command answers `UNIMPLEMENTED`, which the control plane only logs; see the [agent contract](cmds-ownsand-agent-foundation.md#agent-updates) and the [control plane contract](servers-ownsand-api-foundation.md#agent-version-policy)), `command_result` (`AgentCommandResult` with the `command_id`, an `ErrorDetail` on failure and a per-command result), `configuration` (STUN URLs and `DeviceLimits`), `signaling` (`SignalingOffer` or `SignalingAnswer`; an answer may carry an `ErrorDetail` instead of an SDP body), `session_revocation`, `revocation_ack`, `signed_url_request`, `signed_url_grant` (`SignedUrlOperation` `UPLOAD` or `DOWNLOAD`, part numbers and part URLs), `relay_grant`, `relay_grant_ack` and `relay_grant_release`.
- `SandboxRevision` is the pair of the agent's state epoch (a UUID v7) and a counter. The agent sends the epoch with `Authenticate` and in each state report.
- `Authenticate` returns a `oneof` of the `DeviceSession` (the `osd_` credential and its expiry) and the `RemovalNotice`, and fails with `not_found` for an unknown device; `ConfirmRemoval` also fails with `not_found` for an unknown device. The signed message is the purpose label (`ownsand-authenticate` or `ownsand-confirm-removal`) followed by the nonce.
- Snapshot parts: `SnapshotPart` has the part number (from 1), the size and the SHA-256. The export result reports the parts, and the import command carries them. The agent asks for part URLs with `signed_url_request` and does not choose object keys: the grant's URLs address the objects of the current export attempt (or of the successful attempt for a download), so the agent needs no attempt ID and the messages did not change.

### Guest channel

`GuestService` runs inside the guest over the hypervisor socket that the [agent contract](cmds-ownsand-agent-foundation.md#guest-helper) defines. It serves `DataFrame` exec and file requests and a readiness check. It never reaches the control plane.

- `CheckReady` returns the guest OS and the guest helper version.
- `SetClock` sets the guest clock from the host clock after a memory-state restore and after a resume, as [expired operation IDs](#file-transfer) require.
- `Serve` is a bidirectional stream of `ServeRequest` and `ServeResponse` messages, each with one `DataFrame`. The agent sends request frames and the guest helper answers with the frames of the same `stream_id`.

## Storage

The schemas define no storage. The [control plane contract](servers-ownsand-api-foundation.md#storage) and the [agent contract](cmds-ownsand-agent-foundation.md#storage) own persisted data.

## Security

- Signed URL fields (in the signed URL grant) and SDP offer and answer bodies are also never logged, and generated code that logs messages redacts them. Their field comments say `Never log.` Secret fields (`enrollment_token`, `invitation_secret`, `api_key_secret` and `device_session_credential`) appear only in the response that issues them and in the request that uses them. Mark them with a field comment `Secret: never log.` Generated code that logs messages must redact them.
- `DataFrame` payloads, `ExecRequest.command`, `ExecRequest.env` and file chunks are sandbox content. Components never log them.

## Logging

The schemas define no logging. Components log RPC names, identifiers, enum values, sizes and durations, never secret fields or sandbox content.

## Build and Test

- Generation: `scripts/protos.sh generate` from the repository root formats the schemas with `buf format --write`, then generates both languages into a temporary directory: `buf generate` with `protos/buf.gen.yaml` for Go, and `buf generate` with the template `packages/ownsand-sdk/buf.gen.yaml` for the TypeScript bindings of the `delino/ownsand` schemas. Only after both generators succeeded does it delete the generated `*.pb.go` and `*.connect.go` files under `protos/` and `packages/ownsand-sdk/src/gen/` and copy the generated files to the same paths, which removes stale bindings of both languages. When either generator fails, or the pinned `protoc-gen-es` is missing, the script prints the generator diagnostic, exits with a nonzero status and leaves every committed binding of both languages byte for byte unchanged. The format step is not rolled back. `scripts/ci/protos-generate.test.mjs` covers these cases. Commit the schemas and the generated files together. It needs the Go toolchain, network access to the Go module proxy and the workspace dependencies from `pnpm install`, which provide the pinned `protoc-gen-es`.
- Lint: `buf lint` with the `STANDARD` rules in `protos/buf.yaml`.
- Breaking changes: `scripts/protos.sh breaking <base>` runs `buf breaking` with the `FILE` rules against the schemas of the Git revision `<base>`, extracted with `git archive`. A base without `protos/buf.yaml` has nothing to compare.
- Drift check: `scripts/protos.sh check` runs the lint, checks the formatting with `buf format --diff --exit-code`, generates the Go and the TypeScript bindings into a temporary directory and fails when the set or the content of the committed generated files of either language differs from the generated output. The CI `protos` job, which the `go` planner output selects, installs the workspace dependencies and runs `check` and `breaking` against the comparison base whenever a `.proto` file, `protos/buf.yaml`, `protos/buf.gen.yaml`, `protos/buf.lock`, `scripts/protos.sh`, `packages/ownsand-sdk/buf.gen.yaml`, `packages/ownsand-sdk/package.json`, a file under `packages/ownsand-sdk/src/gen/` or a Go input changes, according to the [workflow contract](repository-workflow-contract.md#validation). CI therefore fails when the committed Go or TypeScript bindings differ from the generated output.
- `protos/delino/ownsand/v1/schema_test.go` checks the `DataFrameKind` to payload naming rule, the `_UNSPECIFIED` zero value of every enum, the `ErrorCode` numbers and the `AuditAction` values.
- Go consumers run `gofmt`, `go vet ./...` and `go test ./...` from the repository root according to `cmds/AGENTS.md` and `servers/AGENTS.md`.
