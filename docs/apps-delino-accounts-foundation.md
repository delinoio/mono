# apps-delino-accounts foundation contract

## Scope

This contract owns the `delino-accounts-web` component of [`delino-accounts`](project-delino-accounts.md) at `apps/delino-accounts/`:

- `apps/delino-accounts/rsbuild.config.ts`: build and development server configuration.
- `apps/delino-accounts/index.html`: HTML document template that sets `<html lang="en">`.
- `apps/delino-accounts/src/`: application source, entry point and unit tests.
- `apps/delino-accounts/public/`: static files copied to the build root, including the Cloudflare Pages `_headers` file. The directory must not contain a top-level `404.html` or a `_redirects` file with a rule that rewrites to `/index.html`; `src/static-hosting.test.ts` enforces this.
- `apps/delino-accounts/turbo.json`: package-local Turbo task configuration.
- `apps/delino-accounts/e2e.config.ts` and `apps/delino-accounts/e2e/`: end-to-end test config and tests, according to the [e2e contract](repository-e2e-contract.md).

## Runtime and Language

- Toolchain: Rsbuild `@rsbuild/core` 2.x with `@rsbuild/plugin-react`, React 19.
- Language: TypeScript.
- Test runner: Rstest `@rstest/core`.
- Runtime: Node.js from root `.nvmrc` for builds and tests. Production output is a static single-page application with no server runtime.
- Deployment target: Cloudflare Pages, production domain `accounts.delino.io`.
- Deviation from repository defaults: the app uses Rsbuild instead of Rspress because it is an authenticated application. See the [project index](project-delino-accounts.md).

## Users and Operators

- Signed-in Delino users who manage their account and billing information.
- Maintainers who develop and deploy the web app.

## Interfaces and Contracts

- Production origin: `https://accounts.delino.io`. The asset prefix is `/`.
- Content language: English (`lang="en"`).

- Billing pages, with `BillingAccountService`, `CreditService` and `BillingUsageService` of the [protos contract](protos-delino-accounts-api-contract.md):
  - Layout: `billing` lists the caller's billing accounts with the caller's role and creates one in a dialog. `billing-account` shows the name and the caller's role and groups the sections in tabs: Overview (balance, subscription and credit grants), Usage (usage summary and ledger), Members (members and invitations), Organizations, Invoices (only for `owner` and `admin`) and Settings (name, automatic top-up, low-balance alert and, for the `owner`, deletion). When a refetch of the account changes the caller's role so that the selected tab is no longer visible, the page selects Overview.
  - Failed refetches: only a request that failed before it returned data replaces a section with the error notice. A failed background refetch of data that is on screen (a window-focus refetch, a poll, or the refetch after a mutation) keeps the loaded content and shows a retryable error notice above it. The account page, its heading, its selected tab, its open dialogs and the typed input of its forms stay, and "Try again" reads the data again and removes the notice when it succeeds. The account list, the balance, the credit grants, the subscription, the usage summary, the ledger, the members, the invitations, the linked organizations, the invoices and the settings sections follow the same rule. The one exception is `GetBillingAccount`: a refetch that fails with `NotFound` or `PermissionDenied` means the caller cannot use the account any more, so the page is replaced with the notice and a link to `/billing`. The retry policy and the number of requests do not change; a list that has pages waits for the retry before it reads more pages after a failed refresh, keeps its rows and the refresh retry, hides the "Loading more" status and sends no continuation request meanwhile; after a successful retry it reads the remaining pages again and shows the status while a page request is active. The usage summary, ledger and invoices lists read further pages with a button; it stays disabled while a refresh of the list is in flight, so a continuation never cancels the refresh or sends the token of the cached last page, and it stays disabled after a failed refresh until the retry supplies a token (it disappears when that token is empty). When the request for a further page fails, the loaded rows and the button stay and a retryable notice shows above them; "Try again" requests the failed page again with the same token, appends its rows once and removes the notice, and the button stays available. A failure with `Unauthenticated` shows "Sign in with Delino" instead of "Try again".
  - Complete lists: the lists of billing accounts (`ListBillingAccounts`), members (`ListMembers`), invitations (`ListInvitations`) and linked organizations (`ListLinkedOrganizations`) request `page_size` 200 and follow `next_page_token` as `page_token`, with the same request scope, until the server returns an empty token, so every item shows in server order; an exact page with an empty token makes no further request. The list shows the loaded pages while later pages load. When a later page fails, the loaded rows stay, a notice offers a retry that resumes at the failed page without reading the first page again, and the app makes no further request until the user retries, including no refetch when the tab regains focus (a list without a failed later page still refetches on focus); when the failure is `Unauthenticated`, the notice offers "Sign in with Delino" instead of the retry.
  - Create and delete billing accounts. A successful creation closes the dialog and opens the new account without waiting for the refresh of the billing account list, which runs in the background; a failed creation keeps the dialog and the entered name so that the user can retry. Deletion is offered only to the `owner` and explains that it needs a balance of 0 or more and no linked organizations.
  - Members: invite by email with the role `admin` or `viewer`, change roles between `admin` and `viewer`, remove admins and viewers (every `admin` and `viewer` can also leave), revoke invitations and transfer ownership (`owner` only). The `owner` row has no role change or removal action. After a viewer or admin confirms leaving, the app opens `/billing` first and only then refreshes the cached billing account queries, so the left account never shows its not-found notice and is not listed; a failed leave stays in the dialog with its error and does not navigate. The invitation link is `<web origin>/billing/invitations/accept#token=<token>`. The token is in the URL fragment, so it does not reach Cloudflare Pages logs; the app removes the fragment from the address bar after it reads it and keeps the token only as long as the sign-in redirect needs it. Opening a new link, on the first load of the page and while the page is shown, also deletes any token that an earlier link left in `sessionStorage`, so a later load without a fragment cannot accept the earlier invitation; an address without a token leaves the stored token alone, because the sign-in return reads it. A new link opened while the acceptance of an earlier link is still pending gives the page a fresh "Accept invitation" button that is usable at once and sends only the new token, once; the late result of the earlier request does not navigate or change the page, and it does not delete the stored token that the new link saved for a sign-in redirect that is in progress, so the sign-in return opens the invitation route and the next acceptance sends the new token.
  - Subscription: start the $10/month subscription with the Paddle.js checkout for the `paddle_transaction_id` that `StartSubscription` returns, cancel it at the end of the paid period, and resume a scheduled cancellation before the period ends (`ResumeSubscription`). A subscription stays `PENDING` until the verified payment webhook arrives, so the page shows the pending state after the checkout closes. While the Overview is mounted in a foreground tab and the cached subscription is `PENDING` (also after a reload into that state), the page reads `GetSubscription` every 2 seconds with a React Query `refetchInterval`; the background tab pauses the interval, and the interval stops when the status leaves `PENDING` or the page unmounts. The first transition from `PENDING` to another status invalidates the `CreditService` reads once, so the balance, the credit grants and the Top up action refresh without a reload. Polling uses reads only: a subscription that stays `PENDING` (for example an unpaid, closed checkout) starts no `StartSubscription` or top-up call, and a subscription that is not `PENDING` has no recurring timer.
  - Balance and credit grants with their expiry; the ledger with usage by service, organization and meter; the usage summary of a selected UTC calendar month (`ListUsageSummary` with `year` and `month`) with its total. The month picker's upper limit is the current UTC month and follows the clock while the page is open: when the UTC month changes, or when the tab becomes visible after a rollover whose timers were delayed, "Next month" becomes available without a reload, the selected month stays, and selecting the new current month requests its `year` and `month` and disables "Next month" again.
  - Manual top-up of at least $25 and at most $10,000, in whole cents. The top-up dialog generates one UUID v7 `idempotency_key` when it opens and reuses it for every retry of that top-up. The credit appears after the payment webhook, not with the response. Automatic top-up settings: on or off, threshold (at least $10), amount (at least $25 and at most $10,000) and the required monthly cap. The low-balance alert threshold (at least $0, default $10). The app checks these minimums before it sends a request; the API server enforces them. Every amount that the user enters (the top-up amount, the automatic top-up threshold, amount and monthly cap, and the alert threshold) is also at most $9,223,372,036,854.77, the largest whole-cent value that fits the signed 64-bit `*_usd_micros` API field (9223372036854770000 micro-USD), also when automatic top-up is off; a larger value shows the inline message `Enter at most $9,223,372,036,854.77.` and sends no request. A smaller maximum (the $10,000 top-up amount) takes precedence. A successful automatic top-up save replaces the form values with the saved values, so an equivalent entry such as `50` shows as `50.00`; a rejected save keeps the draft and shows the error. A refresh that changes only the read-only counters keeps the unsaved draft, and a refresh that changes a saved editable value resets the form.
  - Linked organizations, read-only. Linking happens in the consuming service, for example in the [OwnSand console](apps-ownsand-console-foundation.md).
  - Invoices, for `owner` and `admin` only: the list from `ListInvoices` and a short-lived link to each Paddle invoice PDF from `GetInvoiceUrl`, fetched when the user opens it. The app never stores or logs the link. When the browser blocks the invoice pop-up, the app opens the PDF in the current browser tab only if the initiating Invoices view has stayed open. Leaving that view discards the fallback, even if the user returns before the link arrives. A pop-up that stays open still receives the PDF.
  - Role-based views: the app hides or disables the actions that the caller's role (`BillingAccount.caller_role`) does not allow, according to the [role table](servers-accounts-api-foundation.md#billing-accounts-and-members). A `viewer` sees read-only pages. The API server still enforces every permission.
- Display: English only. Amounts show in USD with 2 decimals. Usage costs below $0.01 show with up to 6 decimals. Rounding is for display only.
- UX follows the repository frontend rules: the Toss Design Guidelines, focus on the single critical input when a form with one critical input opens (for example the billing account name, the invitation email or the top-up amount), and dialogs that close with `Esc`. A dialog returns focus to the button that opened it when it closes, also when it focused a single critical input on open. A form dialog (top-up, invitation, billing account creation) ties the result of a submission to the opening that sent it: when a request succeeds after the dialog closed or opened again, the app still refreshes the cached billing data, but it does not close or reset the current opening, clear its draft, change its pending state, navigate or show the success toast of the form. Invalid input keeps the dialog open with the inline message and sends no request, and a failure of the current opening stays in the dialog and can be retried.

- Client-side routes load on direct navigation through the Cloudflare Pages single-page-application fallback: when a project has no top-level `404.html`, Pages assumes a single-page application and serves the root (`/`, the `index.html` document) for any path that does not correspond to a static asset. The fallback applies only while the build output has no top-level `404.html`, so the app must not emit a `404.html`. The app must not add a `_redirects` rule that rewrites to `/index.html` (for example `/* /index.html 200`): Cloudflare rejects it as an infinite loop and ignores it, so it provides no routing. Unknown paths return status `200`, so the app renders its own not-found view once routes exist.
- `public/_headers` sets Cloudflare Pages response headers: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and `X-Frame-Options: DENY`.
- API origin: `src/config.ts` resolves the API server origin from the build-time variable `PUBLIC_API_ORIGIN`. An unset value, an empty value and a value made only of tab, line feed, vertical tab, form feed, carriage return and space characters select `https://accounts.api.delino.io`. Unicode white space such as U+00A0, U+FEFF and U+3000 is not ignored and fails the build as an invalid URL, also when the value consists only of such characters. A value made only of other ignored characters, for example U+0001, is not empty and also fails as an invalid URL. The value must be an `http` or `https` origin with no credentials (user name or password), path, query or fragment, including an empty `?` or `#`; the build fails for other values. As the URL parser does, the check ignores leading and trailing C0 control characters (U+0000 to U+001F) and spaces, and tab, carriage return and line feed anywhere in the value, so a value such as `\u0001https://accounts.api.delino.io` resolves to the same origin that the parser reads. Error messages never echo the raw value because it may carry a credential. `readAccountsApiOrigin` is the only reader of the variable: `rsbuild.config.ts` calls it with `process.env` to fail the build and the dev server early, and `src/api-origin.ts` calls it with `import.meta.env` to export the validated `ACCOUNTS_API_ORIGIN` constant, which Rsbuild inlines into the client bundle. `src/index.tsx` sets the `data-api-origin` attribute of `<html>` to that constant so the build-time value is observable in the running app; it adds no visible markup, request or route.
- API calls: Connect RPC through `@connectrpc/connect-query` and React Query. The app must not call the API through Tauri-specific or ad-hoc bindings.
- Authentication: the app is registered as a Logto single-page application (`@logto/react`) in the shared tenant and requests access tokens for the API resource `https://accounts.api.delino.io` with the scope `accounts:billing`. The build-time variables `PUBLIC_LOGTO_ENDPOINT` (the tenant origin; an http or https origin without credentials, path, query or fragment; a single trailing slash is accepted, while a dot segment such as `/tenant/..` or `/%2e`, a backslash or any other path is rejected even when the URL parser collapses it to `/`) and `PUBLIC_LOGTO_APP_ID` configure it; they are public configuration, set together or not at all. Without them, the billing routes show that sign-in is not configured, and `home` still works. The sign-in redirect URI is `<web origin>/callback`, with the `https://accounts.delino.io` origin in production and the loopback or portless development origin locally; the sign-out redirect URI is the web origin. The Connect transport adds the access token only to requests for the configured API origin. A request that fails with `Unauthenticated` (the transport has no access token, or the server rejects it) shows "Your session ended. Sign in again." with a "Sign in with Delino" button that starts the sign-in redirect instead of "Try again", because the Logto SDK keeps the signed-in state after a failed token refresh; the invitation page saves the pending invitation token again before that redirect. The same notice and button appear for the direct actions that run on a button click (open an invoice, resume the subscription, change a member role, revoke an invitation) when they fail with `Unauthenticated`: the notice sits in the section above the loaded data, which stays visible, the redirect starts only when the user clicks the button, and the action is not replayed; the next successful action of that section removes the notice. Every other failure of these actions keeps its error toast, and a failed invoice link request still closes the tab that the click opened. A sign-in that fails before the redirect starts (for example because the Logto tenant is unreachable) does not reject: the Logto SDK stores the error and resolves. `Auth.signInFailed` is true when a new SDK error appears while the latest `signIn` call runs; an earlier error and the errors of token requests or the callback never set it, and the next `signIn` call clears it. The billing sign-in view ("Sign in with Delino" while signed out), the invitation page for "Sign in to accept", the sign-in button of an ended session and the sign-in button of the unreadable callback session failure show the fixed alert "Sign-in did not start. Check your connection and try again.", never the SDK error text, keeps the buttons usable, and keeps the pending invitation token for the retry.
- Monetary values from the API are `bigint` micro-USD amounts. The app formats them for display only and never converts them to `number` for arithmetic. Amounts that the user enters are parsed from decimal text into `bigint` micro-USD without floating-point arithmetic, and the top-up amounts must be whole cents.
- The billing account name check trims the same leading and trailing white space as the API server, the set of Go's `strings.TrimSpace` (U+0009 to U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F and U+3000), not `String.prototype.trim`: U+0085 is trimmed, and U+FEFF is kept, counted in the 100-code-point limit and accepted because it is not a control character. The check then rejects an empty name and control characters.
- Paddle checkout: the app loads Paddle.js on the first checkout, with its own script loader and the `@paddle/paddle-js` types and `getPaddleInstance`, and opens the overlay checkout for the `paddle_transaction_id` that `StartSubscription` returned. When the checkout closes or completes, the page reads the subscription again and shows the `PENDING` state, polling it as described for the subscription above, until the webhook confirms the payment. The build-time variables `PUBLIC_PADDLE_CLIENT_TOKEN` (the Paddle client-side token, which is public) and `PUBLIC_PADDLE_ENVIRONMENT` (`sandbox` or `production`) configure it; `turbo.json`, `.env.example` and the build validation in `src/config.ts` list them, and the Infisical `/apps/delino-accounts` development folder holds the development values. A token requires the environment, and the token must match it: a sandbox token starts with `test_` and a production token with `live_`; the build fails otherwise without echoing the token. A failed script load (a network error or a script without the Paddle global) removes its `<script>` element, rejects the checkout attempt without caching the failure and shows the error, so the next attempt requests the script again and opens the transaction; this replaces the `initializePaddle` loader of `@paddle/paddle-js` 1.6.6, which caches a rejected script load for the page lifetime, until a release of the package clears it. After a successful initialization, later attempts reuse it and request no script. A subscription start is tied to the billing account view that started it: when the user leaves that view before the response arrives, the page still reads its own account data again but opens no checkout, and the checkout adapter, given the view's `AbortSignal`, returns without installing the Paddle event callback or opening the overlay when the signal aborts while Paddle.js loads. The shared Paddle.js load stays available for a later attempt. Without a token, the subscription section shows that checkout is not configured. Development uses the Paddle `sandbox` environment.

## Storage

The app has no server-side storage. All account and billing state belongs to the [API server](servers-accounts-api-foundation.md). Browser storage is limited to the Logto SDK session data, per-user display preferences and, only during the sign-in redirect of the invitation flow, the billing account invitation token in `sessionStorage`. The app deletes the token when the current `AcceptInvitation` attempt returns, also after a failure, and when the user leaves the invitation flow; the late result of an attempt that a newer link replaced leaves the stored token of the newer link alone. The invitation flow is the `billing-invitation` and `callback` routes. Leaving the flow includes an in-app navigation to another route, a fresh page load whose route is outside the flow (an abandoned sign-in redirect, or the reload after sign-out), and a failed sign-in callback; a successful callback keeps the token until it opens the invitation page. Static assets of at least 512 KiB require Git LFS according to the repository workflow contract.

## Security

- Do not embed secrets in the build. Every `PUBLIC_` variable is public and is inlined into the client bundle.
- Logto application IDs and the tenant endpoint are configuration, not secrets. The app must not use a Logto application secret.
- Billing input that contains payment card data must go directly to the payment provider's hosted fields. The app and the API server must not receive raw card numbers. Payment details are entered only in the Paddle checkout.
- The Paddle client-side token is public configuration, not a secret. The app never holds a Paddle API key or webhook secret.
- Invitation tokens are never written to logs or kept in browser storage longer than the sign-in redirect needs.
- The page must not be framed (`X-Frame-Options: DENY`).

## Logging

The app has no server logs. Build diagnostics come from the Rsbuild CLI output in local runs and CI logs. Cloudflare Pages owns request analytics. Client-side logs must not contain access tokens, ID tokens or payment details.

## Build and Test

Run from the repository root:

- `pnpm install --frozen-lockfile`
- `pnpm --filter delino-accounts dev`: development server through portless at `https://accounts.delino.localhost`, in every checkout. See [Frontend development URLs](repository-environment-contract.md#frontend-development-urls). The `dev` script starts portless (`node node_modules/portless/dist/cli.js run --prefix=`) through the shared `scripts/dev/with-infisical.mjs`, which injects the public build values of the Infisical `/apps/delino-accounts` development folder, such as `PUBLIC_API_ORIGIN`, when the checkout has a local Infisical project configuration, according to the [environment contract](repository-environment-contract.md#local-development-injection). `dev:app` alone does not inject them.
- `pnpm --filter delino-accounts dev:app`, or `dev` with `PORTLESS=0`: development server at `http://127.0.0.1:13100`. The server fails when the port is in use.
- `pnpm exec turbo run build --filter=delino-accounts`: production build into `apps/delino-accounts/dist/`.
- `pnpm exec turbo run typecheck --filter=delino-accounts`: TypeScript type check, including the e2e config and tests.
- `pnpm exec turbo run test --filter=delino-accounts`: Rstest unit tests. `rstest.config.ts` runs the test process in UTC, so the UTC-midnight fixtures keep their calendar dates on any host time zone; the setting does not choose a display time zone for the app.
- `pnpm exec turbo run test:e2e --filter=delino-accounts`: browser end-to-end tests against the development server on a free loopback port. See the [e2e contract](repository-e2e-contract.md). `e2e.config.ts` passes `PUBLIC_API_ORIGIN=http://127.0.0.1:28100` to the app command, and `e2e/home.e2e.ts` asserts that the `data-api-origin` attribute of `<html>` equals it without a model key, so the test fails when the build-time variable does not reach the client bundle. The app command is `rsbuild dev --no-env --host 127.0.0.1 --port {port}`: `--no-env` stops Rsbuild from loading `.env` and `.env.local`, so a developer's local values, valid or invalid, cannot change or break the suite. Because the Rsbuild CLI then does not expose `process.env` values to `import.meta.env`, `rsbuild.config.ts` inlines the five `PUBLIC_*` variables through `source.define` (an unset variable becomes an empty string, which the readers in `src/config.ts` treat as unset). Regular `dev:app`, `dev` and `build` runs still load the dotenv files. `src/e2e-config.test.ts` fails when an e2e config of an app that has a `.env.example` drops `--no-env`. The suite checks that `home` links to `/billing` and that a direct load of `/billing` offers sign-in. The invoice test uses a seeded Logto session and intercepted Connect responses to delay the link in Chromium. The development server serves `index.html` for every route (`server.historyApiFallback`), like the Cloudflare Pages fallback.
- `pnpm --filter delino-accounts preview`: serve the production build locally.

Billing tests: `src/billing.test.tsx` renders every billing page against an in-memory fake of the three user services (`src/testing/fake-api.ts`, a Connect router transport) and a fake checkout, and covers the actions of each role, the hidden or read-only views of `admin` and `viewer`, the validation of the minimums before a request, the reuse of the top-up idempotency key, the invitation token handling and the invoice link. `src/money.test.ts` tests the amount parsing and the display rounding with `bigint` inputs, `src/logic.test.ts` the routes, roles and form checks, `src/config.test.ts` the configuration and `src/paddle.test.ts` the Paddle.js loader with the real `@paddle/paddle-js` module and faked script `load` and `error` events (a script error followed by a retry, the reuse of a successful initialization, and an attempt aborted while the script loads); `src/subscription-checkout.test.tsx` covers a subscription start whose response arrives after the user switched billing account. Checkout and top-up need a manual check on the Paddle sandbox, recorded separately from fixture and build checks.

`turbo.json` declares `PUBLIC_API_ORIGIN`, `PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, `PUBLIC_PADDLE_CLIENT_TOKEN` and `PUBLIC_PADDLE_ENVIRONMENT` as `build` environment variables and local `.env*` files as `build` inputs. It adds `apps/*/e2e.config.ts` and `apps/*/.env.example` of every app, together with the default package files, as `test` inputs, because `src/e2e-config.test.ts` reads those files of the sibling apps: a change to a sibling e2e config or `.env.example` changes the hash of the `test` task and forces a fresh run, so a sibling that drops `--no-env` fails the guard test instead of reusing a cached pass. It also declares the same five variables, `PORTLESS` and `PORTLESS_*` as `dev` pass-through variables, so root `pnpm dev` and `pnpm exec turbo run dev --filter=delino-accounts` honor a value provided by the shell and validate it at startup, like `pnpm --filter delino-accounts dev`. Remove `apps/delino-accounts/dist/` after validation. CI runs the e2e suite in the `e2e` job. CI runs its `build`, `typecheck` and unit `test` scripts in the `workspace-packages` job whenever a path inside the app changes and for every push to `main`, as the [workflow contract](repository-workflow-contract.md#validation) describes. That CI build does not deploy the app. The [deployment workflow](repository-workflow-contract.md#deployment-workflow) builds and deploys it when a pending changeset releases it; `PUBLIC_API_ORIGIN` is not set there, so the build uses the production API origin. The workflow maps `PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, `PUBLIC_PADDLE_CLIENT_TOKEN` and `PUBLIC_PADDLE_ENVIRONMENT` to the repository variables that the Cloudflare Pages entry of the dependency list names (`LOGTO_ENDPOINT`, `DELINO_ACCOUNTS_LOGTO_APP_ID`, `DELINO_ACCOUNTS_PADDLE_CLIENT_TOKEN` and `DELINO_ACCOUNTS_PADDLE_ENVIRONMENT`), and a variable that is unset or blank fails the deployment build before upload, so a deployed build always has the sign-in and checkout configuration. A local build without them shows that sign-in and checkout are not configured.

## Dependencies and Integrations

- `@rsbuild/core`, `@rsbuild/plugin-react`, `react`, `react-dom` and `@rstest/core`, pinned in `apps/delino-accounts/package.json`.
- Generated bindings: the workspace package `@delino/accounts-protos` (`workspace:*`), imported as `@delino/accounts-protos/v1/<file>_pb`, which the [protos contract](protos-delino-accounts-api-contract.md#runtime-and-language) owns, and the `@bufbuild/protobuf` `2.16.0` runtime, equal to the version of the binding package.
- Billing pages, at the exact versions that the [OwnSand console](apps-ownsand-console-foundation.md#dependencies-and-integrations) pins: `@connectrpc/connect` `2.3.0`, `@connectrpc/connect-web` `2.3.0`, `@connectrpc/connect-query` `2.3.1`, `@tanstack/react-query` `5.106.1` and `@logto/react` `4.1.3`; the shared UI [`delino-ui`](packages-delino-ui-foundation.md); `@paddle/paddle-js` `1.6.6` (Apache-2.0, released 2026-11-04) for the checkout; development: `@testing-library/react` `16.3.3`, `@testing-library/dom` `10.4.2` and `happy-dom` `21.0.4`, the versions of `delino-ui`. Record the [dependency security](repository-dependency-security-contract.md) results of each dependency change in the pull request.
- Paddle: the checkout of the subscription; the payment provider of the [API server](servers-accounts-api-foundation.md#payments-and-credits).
- `e2e`, `@e2e-dev/web` and `ai` for end-to-end tests, pinned in `apps/delino-accounts/package.json`.
- [`accounts-api`](servers-accounts-api-foundation.md) at `https://accounts.api.delino.io`.
- Logto shared tenant, according to the [authentication contract](repository-auth-contract.md).
- Cloudflare Pages: static hosting for `accounts.delino.io`. The `deploy` field of `apps/delino-accounts/package.json` names the Direct Upload Pages project `delino-accounts`. The deployment workflow builds with `pnpm exec turbo run build --filter=delino-accounts` and uploads `apps/delino-accounts/dist`. The `buildEnv` of the `deploy` field maps `PUBLIC_LOGTO_ENDPOINT` to the repository variable `LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID` to `DELINO_ACCOUNTS_LOGTO_APP_ID`, `PUBLIC_PADDLE_CLIENT_TOKEN` to `DELINO_ACCOUNTS_PADDLE_CLIENT_TOKEN` and `PUBLIC_PADDLE_ENVIRONMENT` to `DELINO_ACCOUNTS_PADDLE_ENVIRONMENT`, so a production build always has the sign-in and checkout configuration and a missing variable fails the deployment (see [Deployment environments](repository-workflow-contract.md#deployment-environments)). The production build uses the default of `PUBLIC_API_ORIGIN`.
