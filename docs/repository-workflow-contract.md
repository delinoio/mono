# Repository Workflow Contract

## Scope

The repository contains shared instructions, skills, documentation templates, formatting infrastructure, two static Rspress sites ([`delino-site`](project-delino-site.md) and [`delino-docs`](project-delino-docs.md)) and the [`delino-accounts`](project-delino-accounts.md) project with an Rsbuild web app and a Go API server, the shared React UI component package [`delino-ui`](project-delino-ui.md), and the [`delidev`](project-delidev.md) desktop and mobile app with a Tauri app crate. The root `Cargo.toml` defines the Rust workspace; its only member is `apps/delidev/src-tauri`. Generated protocol bindings: the Go and TypeScript bindings of the [OwnSand schemas](protos-ownsand-api-contract.md) and the [`delino-accounts` schemas](protos-delino-accounts-api-contract.md) are committed next to the schemas under `protos/delino/<name>/v1/`, the TypeScript bindings as the workspace packages `@delino/ownsand-protos` and `@delino/accounts-protos` in `protos/delino/<name>/`, and `scripts/protos.sh` regenerates and checks both languages. `.github/workflows/deploy.yml` deploys the servers and static sites and publishes the binary releases of the OwnSand device agent and CLI according to the [deployment workflow](#deployment-workflow) below and uses only the [deployment environments](#deployment-environments) below.

## Agent instructions

Agent instructions live only in `AGENTS.md` files: the root file for repository-wide rules and one file in each directory that has scoped rules. Codex and Claude Code (v2.1.277 or later) read these files directly. Both read the files from the working directory up to the repository root at session start, and Claude Code reads the `AGENTS.md` of a subdirectory when it opens a file there. Claude Code reads `AGENTS.md` only when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists in the working directory or a directory above it, and it reads a subdirectory's `AGENTS.md` only when that subdirectory has none of these files. Do not commit these Claude-only files: they would hide the `AGENTS.md` rules from Claude Code. A developer who keeps a personal, uncommitted `CLAUDE.local.md` sets the Claude Code **Project instructions** setting to `claude-md-and-agents-md` so that Claude Code reads both. The `AGENTS.md` files inside imported skill directories are upstream skill content, not repository instructions.

## Agent skills

`.agents/skills/` owns the shared workspace-local agent skills. `.claude/skills` is a tracked relative symlink to `../.agents/skills` so that Claude Code discovers the same skills as Codex. Add, edit and remove skills only in `.agents/skills/`; do not replace the symlink with a copy or add Claude-only skill directories. Checkouts on platforms without symlink support (for example, Windows without `core.symlinks`) get a plain file instead and do not expose the skills to Claude Code.

A repository-owned skill that must start only when a human invokes it explicitly (for example a skill with side effects on Linear, CI or shared configuration) turns off implicit invocation for both agents: `disable-model-invocation: true` in the front matter of its `SKILL.md` for Claude Code, which also removes the skill description from the model context, and `policy.allow_implicit_invocation: false` in its `agents/openai.yaml` for Codex. A sentence in the description alone does not stop an agent from selecting the skill. Imported skills keep their upstream front matter.

Install third-party skills with the [`skills` CLI](https://github.com/vercel-labs/skills) for the `codex` agent in copy mode, for example `npx skills add <owner>/<repo> --skill <name> -a codex --copy`. This command writes the skill to `.agents/skills/<name>/` and records its source repository, commit and content hash in the root `skills-lock.json`. Commit the skill directory and `skills-lock.json` together. Keep the upstream license and copyright notice with each imported skill, as the [license contract](repository-license-contract.md#imported-material) requires; add the upstream `LICENSE` file to the skill directory when the CLI does not copy it. When the upstream repository publishes no `LICENSE` file, add a `NOTICE` file to the skill directory instead. It names the source repository, skill path and commit exactly as `skills-lock.json` records them and cites where upstream declares its license (for example the `license` field of `SKILL.md`). Do not invent a copyright holder, year or license text. Adding a `NOTICE` file, like any local correction of imported skill files, changes the directory content hash that `skills-lock.json` pins for the skill; do not hand-edit the recorded hash.

## Installation

Use Node.js 24 from `.nvmrc` and pnpm 10.26.2 from `package.json`. The Go toolchain selected by the root `go.mod` (Go 1.26.1 or later) is also a prerequisite for the root `pnpm build`, `pnpm dev`, `pnpm lint` and `pnpm test` tasks, because they include `servers/accounts-api` and `servers/ownsand-api`, whose package scripts call `go`. Rust code uses the toolchain named in root `rust-toolchain` through rustup and the root Cargo workspace; root `cargo test` runs its tests. The workspace builds the CEF runtime of `delidev`, so it needs the Linux packages, macOS and Windows tools and the disk space listed in the [delidev contract](apps-delidev-foundation.md#build-and-test); the first build downloads the CEF distribution. Rust is not a prerequisite of the root pnpm tasks, because no package script calls `cargo`. Git 2.32 or newer is a local prerequisite for `pnpm test:tooling`: the `scripts/ci` fixtures isolate fixture repositories from the developer's global Git configuration with `GIT_CONFIG_GLOBAL`, which older Git ignores, so they fail with a clear error that names the found version on older Git. All Go code belongs to the single root module `github.com/delinoio/mono`; nested `go.mod` and `go.work` files are not used. Run `pnpm install --frozen-lockfile`. The prepare script installs Lefthook through `scripts/install-git-hooks.sh`. Archives without Git metadata skip hook installation, including archives extracted inside another Git work tree, because the installer runs only when the project directory is the root of its own work tree. Linked worktrees may use their shared Git hooks directory; unrelated custom hook paths remain protected. A missing custom hook path stays protected when the installer runs under `sh`, `dash` or `bash`, including `bash --posix`. Every spelling of Git's shared hooks directory, including spellings with a trailing slash or with `.` or `//` segments, counts as the shared hooks directory even when that directory does not exist yet. In the shared hooks directory the installer forces the Lefthook installation, which disables Lefthook's protection of an existing `pre-commit.old` backup. The installer therefore exits with an error that names both files, and leaves them unchanged, when `pre-commit` is not managed by Lefthook and `pre-commit.old` already exists. Move or merge one of the two files and run the installer again. A Lefthook-managed `pre-commit` with an existing backup, a backup without a current hook, and a custom hook without a backup are installed as before; the custom hook becomes the backup.

## Public Go packages

Go packages that users outside this repository import live under the root `go/` directory, in the root Go module `github.com/delinoio/mono`. Each top-level directory `go/<name>/` is one public package tree with the import path `github.com/delinoio/mono/go/<name>`. Its name is the Go package name of its root package, for example `go/ownsand/` with the package `ownsand`. The `go/` directory contains no other code.

- Put a Go package under `go/` when external users import it, or when the exported API of such a package uses it. A project contract names each of its packages under `go/` and owns their behavior.
- Keep Go code that only this repository uses in the directory of its owning project, preferably in an `internal/` directory, for example `cmds/ownsand-agent/internal/` or `servers/ownsand-api/internal/`. Generic code that several projects or components share goes to a [shared internal directory](#shared-internal-go-packages) instead. Do not put Go packages for external users under `apps/`, `cmds/`, `crates/`, `packages/` or `servers/`.
- Exception: the generated protobuf Go bindings stay next to their schemas under `protos/` (for example `protos/delino/ownsand/v1/`), also when packages under `go/` use their types in an exported API. The protos contracts own them.
- Packages under `go/` use Apache-2.0. They import only other packages under `go/`, the generated bindings under `protos/`, the standard library and external modules. They never import code from `servers/`.
- A package that is not specific to one project is a repository-wide public package. This contract owns it:
  - `go/uuidv7/` (`github.com/delinoio/mono/go/uuidv7`): UUID v7 generation (strictly increasing within a process: a 12-bit counter in `rand_a` that starts from a random value each millisecond), canonical parsing that rejects other versions and variants, and timestamp extraction. The OwnSand components and the OwnSand Go SDK use it. Its import path was `github.com/delinoio/mono/go/ownsand/uuidv7` before; that path no longer exists.
- The import path and the exported API of a package under `go/` are a public interface. Moving or renaming a package, or removing or changing an exported identifier, breaks external users; mark such a change as breaking in the pull request title (`!`) and record it in the owning contract.

## Shared internal Go packages

Go packages that several projects or components of this repository use, and that external users do not import, live in shared internal directories of the root Go module. The Go `internal` rule lets every package of the module import them and keeps them out of the reach of other modules.

- Root `internal/<name>/` (import path `github.com/delinoio/mono/internal/<name>`) holds generic Apache-2.0 packages that do not depend on one project, for example a backoff schedule, a directory tree copy or a version comparison. Code under `apps/`, `cmds/`, `crates/`, `packages/` and `servers/` may import them. Packages under `go/` do not import them, because the public packages import only other packages under `go/` (see [Public Go packages](#public-go-packages)). Root `internal/` packages import only other root `internal/` packages, the standard library and external modules; they never import code from `servers/` or from a project directory.
- `servers/internal/<name>/` (import path `github.com/delinoio/mono/servers/internal/<name>`) holds `FSL-1.1-ALv2` packages that only servers share, for example the validation of a listen address. Only code under `servers/` can import them. Code that apps, packages, crates or command tools also use belongs in root `internal/` instead; moving code between the two directories changes its license (see the [license contract](repository-license-contract.md)).
- Put a package in a shared internal directory only when it has no project-specific behavior. Keep project-specific code in the owning project directory, also when several components of the project use it. Each package documents its behavior in its package comment and keeps its tests next to it.
- Root `internal/` packages are not a public interface: a change to them must update every importer in the same change, and it needs no breaking-change marker.

## Task orchestration

The pinned `turbo` dependency and root `turbo.json` orchestrate packages selected by `pnpm-workspace.yaml`: `apps/*`, `packages/*`, `protos/delino/*` and `servers/*`, plus the single package directories `cmds/ownsand` and `cmds/ownsand-agent`. The workspace packages are `apps/delino-site`, `apps/delino-docs`, `apps/delino-accounts`, `apps/delidev`, `packages/delino-ui`, `packages/ownsand-sdk`, `apps/ownsand`, `protos/delino/ownsand` (`@delino/ownsand-protos`), `protos/delino/accounts` (`@delino/accounts-protos`), `servers/accounts-api`, `servers/ownsand-api`, `cmds/ownsand` (`ownsand-cli`) and `cmds/ownsand-agent` (`ownsand-agent`); the two `cmds/` packages are release-only: their private manifests declare no scripts and exist so that Changesets versions them and `deploy.yml` releases them (see [Binary releases](#binary-releases)), and `scripts/ci/plan.test.mjs` fails when one of them declares a script or when `pnpm-workspace.yaml` and the planner list different single package directories; a directory under `protos/delino/` without a `package.json` is not a workspace package; commands only run tasks that exist in package scripts. Go server packages wrap the Go toolchain in their package scripts and disable Turbo caching for their tasks because the toolchain and module cache are not declared inputs.

Root `pnpm build`, `pnpm dev`, `pnpm lint`, `pnpm typecheck` and `pnpm test:e2e` delegate to `turbo run`; `pnpm dev` first runs the portless proxy preflight `scripts/dev/start-portless-proxy.mjs` (see [Frontend development URLs](repository-environment-contract.md#frontend-development-urls)). The `test:e2e` task runs app end-to-end suites, is uncached and declares its pass-through environment according to the [e2e contract](repository-e2e-contract.md). Root `pnpm test` runs workspace tests and the repository-wide `test:tooling` task. The latter runs the existing formatter and hook fixtures in `scripts/ci/` and the development launcher fixtures in `scripts/dev/` (the Infisical development launcher and the Rspress preview launcher `rspress-preview.mjs`, which the `preview` scripts of `delino-docs` and `delino-site` run) directly and is registered as `//#test:tooling`. It is uncached so each invocation checks the current Git and hook environment. `prepare`, `format` and `format:check` remain direct commands: hook installation has side effects, and formatting depends on Git revisions, staged changes and untracked files rather than package inputs.

Root `pnpm dev` starts all workspace development servers together through the unfiltered `turbo run dev` command, after the portless proxy preflight. Each workspace package that owns a development server exposes it through its `dev` script. Packages without a development server do not need a `dev` script. Package-specific development is available through an explicit filtered command; the root command always selects all packages. It currently starts the Rspress development servers of `delino-site` and `delino-docs`, the Rsbuild development servers of `delino-accounts`, `ownsand-console` and the `delidev` frontend, the `accounts-api` Go server and the `ownsand-api` Go server. Both Go servers exit at once with a skip record when `DATABASE_URL` is unset (see the [API server contract](servers-accounts-api-foundation.md#development-launcher) and the [control plane contract](servers-ownsand-api-foundation.md#build-and-test)). Root `pnpm dev` does not start the `delidev` native shell; use `pnpm --filter delidev tauri dev` for it. The `dev` scripts of `accounts-api`, `ownsand-api`, `delino-accounts` and `ownsand-console` start through `scripts/dev/with-infisical.mjs`, which injects the Infisical `dev` variables of the package's folder when the checkout has a local Infisical project configuration and otherwise runs the command directly, according to the [environment contract](repository-environment-contract.md#local-development-injection).

Define each workspace task in its owning `package.json`. Declare workspace dependencies so Turbo can order tasks: builds depend on dependency builds, tests depend on dependency builds, and lint and typecheck tasks depend on their corresponding dependency tasks. Build output defaults to `dist/**`; packages with other outputs must override them in a package-local `turbo.json` that extends `//`. Declare any additional test reports or incremental compiler outputs there. Development tasks are persistent and uncached.

Turbo uses strict environment mode by default. Package contracts and package-local task configuration must declare environment variables, ignored configuration inputs and shared root inputs that affect results before enabling their caching. Keep side-effecting or environment-dependent tasks uncached when their inputs cannot be fully declared. Do not route Git-sensitive formatting through cached tasks or pass credentials through global environment wildcards. Development tasks pass the configuration variables that their owning package contract defines through task-level `passThroughEnv` in that package's `turbo.json`, so root `pnpm dev` honors shell-provided values like the package-specific commands. Use `passThroughEnv`, not `env`, so the values stay out of the hashes of these uncached tasks, and list only variables of the package that owns the task. Add a variable that a development server reads to the owning package's `turbo.json` in the same change. The `scripts/ci/turbo-env.test.mjs` fixture checks the resolved `dev` task definitions with a Turbo dry run. Remote caching is not configured. `.turbo/` is ignored local state; generated `dist` directories remain subject to the cleanup rule below.

For a package subset, use `pnpm exec turbo run <task> --filter=<package>`. Use `pnpm exec turbo run <task> --dry=json` to inspect the graph without running tasks. Root-only fixture execution is also available as `pnpm test:tooling`. New runtime projects must add their own contracts and package scripts before these commands can establish runtime acceptance.

## Formatting

Root `pnpm format` writes fixes and `pnpm format:check` checks without rewriting. Both use pinned Rstack and `rstack.config.ts`. The formatter resolves the repository root with `git rev-parse --show-toplevel` and uses it for every selector, the shared-exclusion probe and the Rstack run, so starting `scripts/ci/format-changed.mjs` from a subdirectory selects and formats the same repository-wide files as starting it from the root. The change planner `scripts/ci/plan.mjs` gives the same guarantee: it lists the changed paths for the fixtures, Go, Rust and end-to-end selectors with `git diff` run from that repository root, so starting it from a subdirectory gives the same selections and the same `ci_plan` record as starting it from the root, even when Git has `diff.relative=true`. Default local selection compares the merge base of `origin/main` and HEAD, including staged changes, working changes and untracked files. Explicit `--base <sha> --head <sha>` arguments select that committed comparison. Local `--all` selects existing tracked files, each path once in sorted order even when a conflicted merge leaves it unmerged in several index stages. Before the first commit, use `--staged`. Every selector matches the supported file extensions case-insensitively, so `notes.MD`, `Component.TSX` and `data.JSON` are selected like their lowercase spellings; the shared exclusions still decide which selected paths Rstack skips. The Lefthook glob needs no uppercase variants because Lefthook matches it case-insensitively on Linux (checked with Lefthook 2.2.2); macOS behavior is unchecked, and the script filter stays the authoritative one. A checkout whose own path is not valid UTF-8 cannot be used as the repository root, because that path cannot be passed to a child process: the formatter fails before it selects any file with a `ci_format_error` that names the checkout path with each invalid byte escaped as `\xNN` and asks to move or rename the checkout.

Lefthook runs `node scripts/ci/format-changed.mjs --staged --write` with `stage_fixed: true`. It preserves unstaged edits, supports initial commits and rejects parser failures. The hook supports `git add` followed by a plain `git commit`, `git commit -a` and `git commit -i`, including from a linked worktree; each formats the staged content and stages the fixes in the same commit. Git runs the hook of a pathspec commit (`git commit <path>`, `git commit --only` and `git commit --amend <path>`) against a throwaway `next-index-*.lock` index and later writes the real index from its own pre-hook snapshot, so a fix staged by the hook would leave HEAD formatted and the real index stale (`MM`). The formatter therefore detects that index through `GIT_INDEX_FILE` and runs the staged selection in check mode without writing or staging. It passes when nothing needs formatting and otherwise exits 2 with a `ci_format_error` that tells the user to run `git add` on the files and a plain `git commit`; because check mode also exits non-zero for parser failures, the message covers both causes. A pathspec run stopped by `SIGTERM`, `SIGINT` or `SIGHUP` keeps the `128 + signal` exit code (143, 130 or 129) with only the `ci_format_signal` event and is not reported as a formatting or parser failure. Select files with NUL-separated Git paths, skip deletions, symlinks and gitlinks, and preserve imported skills, generated files and lockfiles through shared exclusions. Staged deletions, staged paths with an unsupported extension, staged paths recorded as symlinks (mode `120000`) or gitlinks (mode `160000`, which have no blob to format) and staged paths that the shared exclusions skip (for example a skip-worktree lockfile removed from the working tree; Rstack evaluates the exclusions for a path that does not exist on disk through `--stdin-filepath`) are skipped even when their working-tree path is missing, as the unstaged selectors skip them. Every such exemption applies before the missing-path failure, but a staged added, modified, renamed or type-changed formattable path that is missing from the working tree (removed after `git add`, behind a replaced parent directory or outside a sparse checkout) fails the hook with a `ci_format_error` naming the path, so a staged blob cannot bypass formatting. A parent directory replaced by a symbolic link to a directory counts as a replaced parent directory in every selector, because the tracked path then resolves outside the repository and Rstack would format the file that the link points to: the `--all` and default local selectors skip it silently, and the staged and explicit selectors fail with a `ci_format_error` naming the path and saying that a parent directory resolves outside the repository through a symbolic link, unless the shared exclusions skip it. The same failure applies to a staged added, modified, renamed or type-changed formattable path that exists in the working tree as a non-regular entry, such as a directory that replaced the file, a symlink that the index does not record as one, a FIFO, a socket or a device: the `ci_format_error` names the path and the observed entry type, and the path is skipped silently only when the shared exclusions skip it. Git path lists are read as bytes and each name is checked with `node:buffer` `isUtf8` (not a fatal `TextDecoder`, which would strip a leading byte order mark from a valid name), because Rstack cannot address a file name that is not valid UTF-8. A staged or explicit-comparison (`--base`/`--head`) added, modified, renamed or type-changed formattable path that is present but whose name is not valid UTF-8 (for example the Latin-1 name `caf\xe9.ts` on Linux) fails with a `ci_format_error` that names the path with each invalid byte escaped as `\xNN`, states that the name is not valid UTF-8 and asks for a rename, instead of reporting the path as missing from the working tree. This check runs after the unsupported-extension, symlink, gitlink and shared-exclusion exemptions (the exclusion probe uses the lossy name, which keeps the valid directory prefixes), so those paths stay silent skips, and an explicit-comparison path that the range deletes stays skipped. The planner does not run the exclusion probe, because it runs without installed dependencies and cannot evaluate the shared exclusions: it selects formatting for such a present formattable path, and the `quality` job's formatter gives the verdict, skipping the path when the shared exclusions skip it and otherwise failing with the `ci_format_error` described above. An explicit-comparison formattable path that the range changes and the validation index tracks but whose working-tree entry is gone (removed, behind a replaced parent directory or a symlink loop, or outside a sparse checkout) is skipped when the shared exclusions skip it, as the staged and default local selectors skip it, and otherwise fails with a `ci_format_error` naming the path, because the comparison validates the full checkout. Selectors compare paths by their bytes, not by a lossy decoding: each byte that is not part of a valid UTF-8 sequence is held as a distinct escaped value, so a name that is not valid UTF-8 never equals the valid name that contains U+FFFD in its place. A rename from the raw `caf\xe9.ts` to the valid `caf�.ts` therefore selects the valid replacement, and the deleted or exempt raw name neither marks the replacement as invalid nor exempts it. `--all` and default local changed-file selection keep skipping such a path silently; this is a documented limitation until Rstack can format such names. The checkout path itself is subject to the same limitation. Linux file systems hold these names; APFS and Windows reject or normalize them, so the fixtures skip there. Unstaged deletions in `--all` and local changed-file selection stay skipped. Every selector (`--staged`, `--all`, explicit comparison and default local) skips a path that the validation index records as a symlink (mode `120000`) or a gitlink (mode `160000`), even when the checkout materialized it as a regular file (a symlink on Windows without symlink support or with `core.symlinks=false`, or a gitlink replaced by a regular file), so the placeholder bytes and the recorded mode stay unchanged. The mode comes from the current index (`git ls-files --stage -z`), never from the comparison head, and works before the first commit.

CI requires an explicit comparison and rejects local `--staged` and `--all` modes. Outside CI, the formatter also rejects `--all` combined with `--base`, `--head`, `TURBO_SCM_BASE` or `TURBO_SCM_HEAD`: it exits with status 2 and a `ci_format_error` before it selects or rewrites any file, because `--all` has no comparison to honor. An unset, empty or case-insensitive `false` CI value means local execution; every other nonempty value enables CI restrictions.

## Validation

Run `pnpm test` for the workspace package tests and the formatter, hook and change-planning fixtures; `pnpm test:tooling` runs only the fixtures. CI plans affected fixtures, formatting and workspace package tasks on Ubuntu for pull requests, main pushes and manual dispatch. The `quality` job runs plain `pnpm format:check` with `TURBO_SCM_BASE` and `TURBO_SCM_HEAD` set to the resolved comparison, and, when fixtures are selected, `pnpm test:tooling` and then `scripts/ci/validate-changesets.sh`, which runs `scripts/ci/deploy-plan.mjs --check` (the deploy planner's rules that need no release: changeset file names and the `deploy` manifest fields) and `pnpm exec changeset version` in its throwaway checkout when a changeset is pending (it counts the same files as the Changesets reader: no hidden files, `README.md`, `AGENTS.md`, `CLAUDE.md` or `GEMINI.md`; without one it has nothing to check; `changeset version` would exit 1) and so rejects a pending changeset for an unknown package or one that mixes the ignored `delidev` with other packages before it can reach `main` and stop every deployment; the formatter reads that environment as the explicit comparison. The `--base <sha> --head <sha>` arguments are the equivalent local form and select the same files. The `changes` job resolves the comparison with `scripts/ci/comparison.mjs`. Every comparison base is an ancestor of the checkout, which is the comparison head, so the two-dot `git diff` of the planner and the formatter lists only the changes that the head adds. A two-dot diff from a base that is not an ancestor of the head also lists the reverse of every change that only the base contains, and would select checks for changes that the head never made. A pull request run checks out the GitHub test merge commit of the pull request head into its base branch. Its comparison base is the first parent of that merge commit (the base branch revision that the run merges into) and its head is the merge commit, so the comparison lists the changes that merging the pull request makes. The comparison does not use `pull_request.base.sha` from the event payload: GitHub does not update that value when the base branch moves, so it can stay at an older base branch revision (for example the one from when the pull request was opened), and it is not always an ancestor of the pull request head. The script fails when the checkout is not a merge commit whose second parent is the `pull_request.head.sha` of the event. Push comparisons use the merge base of the prior and current commits, which is the prior commit unless the push rewrote history. Manual comparisons use the merge base of the checkout with `origin/main`, or with the revision of the optional `base` input. A root push has no previous commit, so CI creates a local empty-tree comparison commit without pushing it. The script appends the `base` and `head` outputs, writes the validation revision and the comparison to the job summary and logs one `ci_comparison` record with the event name, the requested base, the resolved base and head and the base source (`merge-parent`, `merge-base` or `empty-tree`). When it fails, for example because a revision does not exist, the event is not supported or the pull request checkout is not the expected merge commit, it prints one `ci_comparison_error` record on stderr, exits with code 2 and writes no outputs and no summary, and the `changes` job fails. No full manual mode is configured. The `go-platforms` and `rust-platforms` jobs run on macOS and Windows runners; every other job runs on Ubuntu.

The `changes` job resolves that comparison and runs `scripts/ci/plan.mjs` without installing dependencies. It publishes `base`, `head`, `format`, `fixtures`, `quality`, `go`, `rust`, `e2e`, `workspace` and `workflows` outputs. Formatting uses the existing formatter's changed-file selection; Rstack still owns exclusions, so a change that touches only a supported file with an uppercase or mixed-case extension (for example `notes.MD`) still publishes `format: true`. A present formattable path whose name is not valid UTF-8 and a formattable path that the comparison changes but that is missing from the working tree also publish `format: true` without an exclusion probe; the `quality` job's formatter decides whether the shared exclusions skip it or it fails. When the planner fails, for example because a comparison revision does not exist, the comparison is unset or malformed, or the comparison base is not an ancestor of the head (the only accepted exception is a parentless commit of the empty tree, the comparison commit of a root push), it prints one `ci_format_error` record on stderr like the formatter, exits with code 2, prints no `ci_plan` record and writes no outputs and no summary record, and the `changes` job fails, which fails `ci-result`. Fixtures run for changes, deletions or renames affecting `scripts/ci/`, `scripts/dev/`, `.changeset/`, `.github/workflows/deploy.yml`, `scripts/install-git-hooks.sh`, `scripts/droplet/start-caddy.sh`, `scripts/protos.sh` (which `scripts/ci/protos-generate.test.mjs` runs against a fake `go`; it also selects the `go` output as a protobuf input), `.github/workflows/CI.yml`, `.nvmrc`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `rstack.config.ts`, `lefthook.yml`, any `turbo.json` (the root file or a workspace package file) or the `package.json` placed directly inside a workspace package under `apps/`, `packages/`, `protos/delino/` or `servers/` or of a single workspace package directory (`cmds/ownsand` and `cmds/ownsand-agent`). Adding, removing or renaming a workspace package changes the packages that the Turbo fixtures resolve, so a nested `package.json` deeper in a package does not select fixtures. In pull request and manual comparisons, documentation-only changes select formatting without fixtures. The `quality` job runs when either check is selected, and on every push to `refs/heads/main` because the planner always selects fixtures there, and passes the exact comparison to formatting. In pull request and manual comparisons, empty comparisons or changes with no validation inputs skip `quality`. The `go` output is selected when a changed, deleted or renamed path is a `.go` file, `go.mod`, `go.sum`, a `.proto` file, `protos/buf.yaml`, `protos/buf.gen.yaml`, `protos/buf.lock`, `scripts/protos.sh`, any path under `packages/ownsand-sdk/` (the SDK sources, tests and rstest configuration that the OwnSand end-to-end suite runs), a generated `*_pb.ts` file under `protos/delino/<name>/` (the TypeScript bindings that the drift check compares), the `buf.gen.yaml`, `package.json` or `tsconfig*.json` placed directly inside a TypeScript binding package `protos/delino/<name>/` (the template and the `protoc-gen-es` pin of the bindings, and the package configuration that the OwnSand end-to-end suite resolves the bindings with), a schema migration under `servers/accounts-api/internal/db/migrations/` or `servers/ownsand-api/internal/db/migrations/`, a file under a `testdata` directory inside `go/`, `cmds/`, `internal/` or `servers/` (fixture data that Go tests read), `go/ownsand/relaybinding/testdata/request-digest-vectors.json` (which the TypeScript SDK digest test also reads, so it also selects the `workspace` output), `.github/workflows/CI.yml` (which defines the job), or one of the workspace inputs that the `go-test` and `protos` jobs install and run Node.js with (`.nvmrc`, `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml`), and for every `push` event to `refs/heads/main` regardless of the comparison. The `rust` output is selected when a changed, deleted or renamed path is a `.rs` file, a `Cargo.toml` or `Cargo.lock` at any depth, root `rust-toolchain` or `.rustfmt.toml`, `.github/workflows/CI.yml` (which defines the job), or any path inside a `src-tauri/` directory (a Tauri crate compiles its configuration, capabilities and icons into the binary), and for every `push` event to `refs/heads/main` in the same way. The `fixtures`, `e2e`, `workspace` and `workflows` outputs are selected for every `push` event to `refs/heads/main` regardless of the comparison in the same way; the forced `fixtures` also runs `quality`. Branch-wide cancellation can cancel a main-push run before its Go, Rust, fixtures, e2e, workspace or workflows jobs finish, and the next push compares only against its own parent, so the planner reads the runner-provided `GITHUB_EVENT_NAME` and `GITHUB_REF` and runs the Go checks, the Rust checks, the fixtures, the e2e suites, the workspace package tasks and the workflow lint against each main-push head; a later documentation-only push therefore cannot pass `ci-result` with Go, Rust, fixtures, e2e, workspace or workflows skipped. Pull request and manual comparisons keep affected selection, and the other outputs are unchanged. The `format` output stays derived from the comparison for every event, so this selection does not cover formatting that a cancelled main-push run lost: the formatter still compares only the range of the surviving push. The planner logs the reasons in the `goReason`, `rustReason`, `fixturesReason`, `e2eReason`, `workspaceReason` and `workflowsReason` fields (`diff` or `main-push`) of its record without publishing them as outputs; `main-push` means the output is true only because of the main push and the comparison alone did not select it. Five jobs run the Go and protobuf checks in parallel on separate runners. `go-fmt` sets up the Go toolchain of `go.mod` without a cache and runs `gofmt -l` on tracked `.go` files. It builds nothing and checks every tracked Go file, so it does not wait for the `changes` job and runs for every event; `ci-result` requires it to succeed. The `go` output selects `go-vet`, `go-test`, `protos` and `go-platforms`. Every protobuf input is a Go input, so the planner publishes no separate protobuf output. The `go-vet` job runs `go vet ./...` in the root Go module without a cache. The `go-test` job starts a Postgres service container (an exact `postgres` image tag pinned by digest, reachable only inside the job), installs the workspace dependencies with `pnpm install --frozen-lockfile --ignore-scripts` and runs `go test -count=1 ./...` in the root Go module with `ACCOUNTS_TEST_DATABASE_URL`, `OWNSAND_TEST_DATABASE_URL` and `OWNSAND_E2E=1`, so the Postgres-backed `accounts-api` and `ownsand-api` tests and the [OwnSand end-to-end suite](project-ownsand.md#end-to-end-test) run. Both test database variables point to the same Postgres service, and each suite creates its own uniquely named databases there. Each Go job records its commands and result in the job summary. The `protos` job checks out the full history, installs the workspace dependencies with `pnpm install --frozen-lockfile --ignore-scripts`, runs `scripts/protos.sh check` (buf lint, buf format check and the drift check that fails when the committed Go or TypeScript bindings differ from the generated output) and `scripts/protos.sh breaking` against the comparison base (skipped with a summary line only when the base is the local empty-tree commit of a root push, which the `protos` job does not have), and records the result in the job summary. The protobuf tools run through `go run` with the exact versions that the [protos contract](protos-ownsand-api-contract.md#build-and-test) records. The `go-platforms` job is a matrix with one entry on `macos-latest` and one on `windows-latest` and `fail-fast: false`, so it reports the failures of both platforms in one run; it compiles and runs the `_darwin` and `_windows` files and build-tagged code of the device agent, the guest helper and the CLI, which the Linux jobs do not build. On Windows it first sets `git config --global core.autocrlf false`, because Git for Windows on the runner image converts checked-out files to CRLF and the repository has no `.gitattributes`. It sets up the Go toolchain of `go.mod` with `cache: true` (the `actions/setup-go` key includes the runner OS and architecture, so the entries never share a key with the `go-test` job), runs `go vet ./...`, vets the other architecture of the host OS with `GOARCH` (on macOS with `CGO_ENABLED=1`, because the Virtualization.framework runtime has a cgo file for each architecture, and again with `CGO_ENABLED=0` for its fallback without cgo) and runs `go test -count=1` on every package except a per-platform list of known failing packages. As a documented workaround, that list names each package whose tests fail on the platform today with the cause; the job tests those packages again in a non-blocking run that reports each one that passes, and fails when a listed package no longer exists. The change that fixes a package's failures on a platform removes it from the list. A platform list can be empty; the job then skips the non-blocking run, and the step expands every array that can be empty in a form that the bash 3.2 of the macOS runners accepts under `set -u`. Docker service containers run only on Linux runners, so the job starts no Postgres service and sets none of `ACCOUNTS_TEST_DATABASE_URL`, `OWNSAND_TEST_DATABASE_URL` and `OWNSAND_E2E`: the Postgres-backed tests and the OwnSand end-to-end suite skip there and stay owned by `go-test`, and the Virtualization.framework and Hyper-V integration tests skip without their image variables. Four jobs run the Rust checks in the root Cargo workspace in parallel on separate runners. `rust-fmt` installs the `rust-toolchain` toolchain with `rustfmt` only and runs `cargo fmt --all --check`. It checks every tracked Rust file and builds nothing, so it does not wait for the `changes` job and runs for every event; `ci-result` requires it to succeed. The `rust` output selects `rust-clippy`, `rust-test` and `rust-platforms`. Each of them installs `pkg-config` and `libgtk-4-dev` and the `rust-toolchain` toolchain on the Linux desktop target: `rust-clippy` adds the `clippy` component and runs `cargo clippy --workspace --all-targets --locked -- -D warnings`, and `rust-test` runs `cargo test --workspace --locked`. Each Rust job records its commands and result in the job summary. The `rust-clippy` and `rust-test` jobs set `CEF_PATH` to `~/.cache/cef`, so the `cef-dll-sys` build script downloads the CEF distribution there instead of into `target/` and reuses it when it is present. The `rust-platforms` job is a matrix with one entry on `macos-latest` and one on `windows-latest` and `fail-fast: false`. On Windows it sets `core.autocrlf false` before the checkout like `go-platforms`. It installs the `rust-toolchain` toolchain with `clippy`, uses the CMake and Ninja of the runner image for the CEF C++ wrapper, sets `CEF_PATH` to `~/.cache/cef` (as a Windows path on Windows, because the build script is a native program) and runs `cargo clippy --workspace --all-targets --locked -- -D warnings` and then `cargo test --workspace --locked` on the host desktop target. These jobs do not run `tauri build`, launch the app or build the Android or iOS targets. The `e2e` output is selected when a changed, deleted or renamed path is inside an `apps/<app>/` package, or is `.github/workflows/CI.yml`, `.nvmrc`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `turbo.json`. The `e2e` job installs Chromium and runs every app suite with `pnpm test:e2e`, as the [e2e contract](repository-e2e-contract.md#ci) describes. It reads the `AI_GATEWAY_API_KEY` repository secret and excludes tests tagged `agent` when the secret is not available. The `workspace` output is selected when a changed, deleted or renamed path is inside a workspace package directory under `apps/`, `packages/`, `protos/delino/` or `servers/` (a file placed directly in one of these roots, such as `apps/AGENTS.md`, is not; any path inside a directory of `protos/delino/`, also a schema or a Go binding, is), is the `package.json` of a single workspace package directory (`cmds/ownsand` or `cmds/ownsand-agent`; their other files, such as the Go source, are not workspace inputs, because these packages declare no package tasks), or is `go/ownsand/relaybinding/testdata/request-digest-vectors.json`, `.github/workflows/CI.yml`, `.nvmrc`, `go.mod`, `go.sum`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `turbo.json`. The `workspace` output selects two jobs that run in parallel on separate runners. Each of them sets up the Go toolchain of `go.mod`, installs the workspace dependencies with `pnpm install --frozen-lockfile --ignore-scripts` and runs `pnpm exec turbo run build lint typecheck test --continue` with one package filter, so each package's build, lint, typecheck and unit test scripts run. `workspace-servers` adds `--filter=./servers/*` and runs the Go server package scripts without a database. `workspace-packages` adds the complementary `--filter=!./servers/*` and runs every other package. The Go server packages and the other packages share no workspace dependency, so neither job needs a task of the other, and the complementary filters select every package, including a package under a new workspace root. Each job records its filter, commands and result in the job summary. It does not use `--affected`, because Turbo 2.11.11 selects no package when only a root input such as `package.json`, `turbo.json` or `go.mod` changes. The `go-test` job, not `workspace-servers`, remains the owner of the Postgres-backed tests and the OwnSand end-to-end suite, and the `protos` job the owner of the protobuf checks. The `workflows` output is selected when a changed, deleted or renamed path is under `.github/workflows/` or `.github/actions/`. The `workflows` job runs `go run github.com/rhysd/actionlint/cmd/actionlint@v1.7.12`, which also checks every `run:` script with the shellcheck of the Ubuntu runner image, and zizmor 1.32.0 through `zizmorcore/zizmor-action` with online audits, annotations and without SARIF upload. Any finding fails the job. A zizmor finding that does not apply is suppressed only with an inline `# zizmor: ignore[<audit>]` comment and an explanation next to it; the `release` job of `deploy.yml` suppresses `artipacked`, because it pushes with the credentials that its checkout persists and uploads no artifacts. Renovate updates the pinned action digests, the `postgres` image digest and the zizmor action; update the actionlint and zizmor versions in the job by hand. The planner records the checkout revision, comparison and selections in logs and the job summary. New shared validation dependencies must update the planner inputs.

CI caches dependencies and build output with the GitHub Actions cache. The `quality`, `go-test`, `protos`, `e2e`, `workspace-packages` and `workspace-servers` jobs cache the pnpm store through `actions/setup-node` with `cache: pnpm`, keyed by the `pnpm-lock.yaml` hash. The `go-test` job caches the Go module and build caches through `actions/setup-go` with `cache: true`, keyed by the `go.sum` hash; `-count=1` keeps every test run uncached, so the cache only skips downloads and recompilation. The `protos` job caches the Go module and build caches of the buf CLI and the protoc plugins that `go run` builds, keyed by the hash of `scripts/protos.sh` and `protos/buf.gen.yaml`, which pin their versions; the key differs from the `go-test` job key, so the two jobs do not race to save different caches under one key. The `go-vet`, `workspace-packages` and `workspace-servers` jobs do not use the Go cache, because `actions/setup-go` cannot restore without saving and they would save different caches under the `go-test` job key. `go-fmt` uses no cache. The `rust-clippy` and `rust-test` jobs use `Swatinem/rust-cache` for `~/.cargo`, the dependency build output in `target/` and `~/.cache/cef`, keyed by the job ID, the toolchain and the Cargo manifests and lockfile; clippy and the test build write different `target/` content, so the two jobs keep separate entries. Only pushes to `main` save them, and pull requests restore them. The `rust-platforms` job uses `Swatinem/rust-cache` in the same way and adds the runner to the key, because both matrix entries have the same job ID. The `go-platforms` job caches the Go module and build caches through `actions/setup-go` with `cache: true` under keys that include the runner OS and architecture. `rust-fmt` uses no cache. The pnpm and Go caches save a new entry after any run that misses the key, including a pull request that changes the lockfile or `go.sum`. GitHub scopes a cache saved by a pull request to that pull request's ref, so it cannot replace the caches that `main` and other pull requests restore. The deployment workflow uses no caches, because its jobs build and deploy with deployment credentials. Turbo task output is not cached between runs.

Every `CI.yml` job sets `timeout-minutes`, so a hung service, download or test fails its job and `ci-result` instead of running until the six-hour GitHub default: `changes` 10, `quality` 15, `go-fmt` 5, `go-vet` 10, `go-test` 20, `protos` 10, `go-platforms` 30, `rust-fmt` 10, `rust-clippy` 45, `rust-test` 45, `rust-platforms` 60, `e2e` 20, `workspace-packages` 20, `workspace-servers` 20, `workflows` 10 and `ci-result` 5 minutes. Each limit is at least three times the longest observed run of the job without caches. Raise a limit in the same change that makes a job legitimately slower.

Each CI run records the validation revision, comparison revisions, commands and results in its logs and job summary. Runtime and platform acceptance must be added with the owning project. CI does not build `delidev` bundles or mobile targets. CI runs the e2e suites of `delino-site`, `delino-docs`, `delino-accounts` and `ownsand-console` against their development servers. The `workspace-packages` job builds these apps with their package `build` scripts but does not deploy them; the [deployment workflow](#deployment-workflow) builds and deploys them. The workspace unit tests, including those of `delino-accounts`, `delino-ui`, `ownsand-sdk` and `ownsand-console`, run in the `workspace-packages` job whenever the planner selects it. Passing shared fixtures does not establish runtime or release acceptance.

The `ci-result` job aggregates validation through `needs`, including `changes`, `quality`, `go-fmt`, `go-vet`, `go-test`, `protos`, `go-platforms`, `rust-fmt`, `rust-clippy`, `rust-test`, `rust-platforms`, `e2e`, `workspace-packages`, `workspace-servers` and `workflows`. It runs with `always()` so dependency failures do not skip the aggregate check. Its `job_outputs` table names the planner output that selects each validation job: `quality` for `quality`, `go` for `go-vet`, `go-test`, `protos` and `go-platforms`, `rust` for `rust-clippy`, `rust-test` and `rust-platforms`, `e2e` for `e2e`, `workspace` for `workspace-packages` and `workspace-servers` and `workflows` for `workflows`. The table marks `go-fmt` and `rust-fmt` with `always`, because they run without the planner. The `changes` job must succeed. A job marked `always` must succeed. Each other job passes when it succeeds, or when it is skipped and the planner did not select its output. Failed or cancelled jobs fail `ci-result`; a matrix job fails when any of its entries fails. The table must contain exactly the jobs of `ci-result.needs` other than `changes`; `ci-result` fails when the two lists differ, so every new PR validation job must be added to both. The aggregate job runs on Ubuntu for the same PR, main-push and manual-dispatch events.

## Deployment environments

The repository allows exactly three GitHub deployment environments. Do not create more environments, and do not split an environment by app, server, binary, stage or branch.

| Environment    | Deploys                                                                                                                           |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `static-sites` | Every static site under `apps/`, including Cloudflare Pages deployments.                                                          |
| `servers`      | Every backend service under `servers/`.                                                                                           |
| `releases`     | Every binary release under `cmds/`: the macOS signing and notarization and the GitHub Releases and signed manifests it publishes. |

Each deployment job sets `environment` to the environment of its deployable kind. A workflow that deploys both kinds uses separate jobs. Store deployment credentials as secrets of the matching environment, not as repository secrets. PR validation jobs do not reference a deployment environment. A new deployable joins the existing environment of its kind; a deployable of another kind needs a change to this contract first.

## Deployment workflow

### Hosting targets

| Deployable kind | Hosting                                                                                                                          | `deploy.target` value |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| Server          | The shared DigitalOcean Droplet                                                                                                  | `droplet`             |
| Static site     | Cloudflare Pages                                                                                                                 | `cloudflare-pages`    |
| Binary          | GitHub Releases of its version tag, plus a signed release manifest on the releases R2 bucket when it has `deploy.updateManifest` | `github-release`      |
| Database        | PlanetScale Postgres                                                                                                             | none                  |

A workspace package is a deployable when its `package.json` has a `deploy` field. Its package name must match `^(?!.*\.\.)[a-z0-9][a-z0-9._-]*$` (no scope and no two consecutive dots), because the workflow uses it in file paths, artifact names and tags, and the release script tags every deployable `<name>@<version>`, which Git rejects as a reference name when it contains `..`. The name of a `droplet` deployable must also be a container image repository name, `^[a-z0-9]+(?:(?:\.|_|__|-+)[a-z0-9]+)*$` (alphanumeric runs joined by one `.`, `_`, `__` or hyphens, with no leading or trailing separator), because the deploy workflow builds its image with `docker build --tag <name>:<sha>`; a `cloudflare-pages` deployable has no image and keeps only the first rule. The name of every other workspace package that a release can include, a package without a `deploy` field, must also form a valid Git tag `<name>@<version>`, because the release step tags every release whose version advances (see the `release` job below): the name must not contain `..`, `@{`, a space, an ASCII control character or one of `~ ^ : ? * [ \`, must not start with `-` or `/`, must not contain `//`, and no `/`-separated component may start with `.` or, except the last one, end with `.lock`. The scope and slash of `@scope/name` stay valid. A deployable that fails its own name rules keeps that diagnostic. The plan fails for a release (including a `none` release) whose name breaks this rule, and `deploy-plan.mjs --check` fails for any workspace package whose name breaks it, so the pull request that adds or renames the package fails before a release can; `--check` skips a non-deployable package whose manifest has no string name. The plan and `deploy-plan.mjs --check` fail with a diagnostic that names the package (or its directory when the manifest has no usable name) and the rule that failed. No two deployables may name the same Droplet service, Droplet host name, Droplet UDP port or Pages project; the plan fails when they do. Every deployable can set `deploy.needs`, a nonempty list of the names of other deployables that must deploy before it when one run deploys both, for a runtime dependency that is not a workspace dependency (for example, `ownsand-api` calls APIs of `accounts-api`). The field only orders: a needed deployable without a pending release is not added to the run, because its deployed version is current. Servers deploy before static sites, so a server cannot need a static site, and a static site that needs a server already comes after it. The deploy loops stop at the first failed target, so a run does not deploy a deployable when a deployable that it needs failed. The plan and `deploy-plan.mjs --check` check `deploy.needs` of every deployable, selected or not: a name that is not another deployable of the workspace, an empty or repeated entry, a server that needs a static site or a cycle fails them. `deploy.target` selects the hosting target. A `droplet` deployable must be under `servers/` and sets three fields: `deploy.service`, the service name (lowercase letters, digits and inner hyphens, at most 63 characters), which names its container (the prefix of the container names), its label value and its env file; `deploy.hostname`, the lowercase fully qualified public host name that the reverse proxy routes to it; and `deploy.port`, an integer from 1024 to 65535, the port that the server listens on inside its container. Two services may use the same port, because each container has its own network namespace. A `droplet` deployable can also set two optional fields. `deploy.upstreamProtocol` is the protocol from the reverse proxy to the container: `http1` (HTTP/1.1, the default) or `h2c` (HTTP/2 without TLS), for a server whose bidirectional streams need HTTP/2 from end to end; a server with `h2c` must also accept HTTP/2 without TLS on `ADDR`. `deploy.udpPorts` is a nonempty list of different integers from 1024 to 65535: the UDP ports that the Droplet publishes on the same host ports for the server (UDP 443 belongs to Caddy). A `cloudflare-pages` deployable must be under `apps/` and sets `deploy.project` to its Cloudflare Pages project name, which must match `^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$` (lowercase letters, digits and hyphens, beginning and ending with a letter or digit) because Cloudflare rejects other names only after the build, so the plan and `--check` fail first; the optional `deploy.output` is the build output directory relative to the package and defaults to `dist`; it must name a directory inside the package, not the package root (`""` or `.`) or a path outside it, and it must not contain a control character (including tab, line feed and carriage return), DEL or a backslash, because the deploy workflow carries it through tab-separated and line-separated transports that cannot represent them. A `cloudflare-pages` deployable can also set `deploy.buildEnv`, a nonempty map from a build-time variable name to a GitHub repository variable name, for the public values that its production build needs. Each key must match `^PUBLIC_[A-Z0-9_]+$`, so that the map sets only public bundle values and cannot change a variable that controls the build tools (such as `PATH` or `NODE_OPTIONS`); each value must be a GitHub variable name in upper case that does not start with `GITHUB_` (`^(?!GITHUB_)[A-Z_][A-Z0-9_]*$`). A `droplet` or `github-release` deployable must not set it, because a server reads its configuration from its env file on the Droplet and a binary build takes no repository variables. The plan and `deploy-plan.mjs --check` check the field of every deployable. A `github-release` deployable must be under `cmds/` and sets `deploy.binary`, the executable name (lowercase letters, digits and inner hyphens), which also names its release assets; `deploy.platforms`, a nonempty list of different `<GOOS>-<GOARCH>` values from `linux-amd64`, `linux-arm64`, `darwin-amd64`, `darwin-arm64`, `windows-amd64` and `windows-arm64`; and `deploy.licenseFiles`, a nonempty list of different file paths relative to the repository root that the release ships, whose base names must differ from each other, from the executable asset names and from `SHA256SUMS`, `GO-LICENSE` and `THIRD-PARTY-LICENSES.txt`. It can also set `deploy.cgoPlatforms`, a nonempty list of entries of `deploy.platforms` that build with cgo (only `darwin-arm64`, which builds on the arm64 macOS runner); `deploy.versionVariable`, the Go variable `<import path>.<name>` inside its own package directory that the build sets to the release version with `-ldflags -X` (the executable must then print the version with its `version` command, which the build checks for the host platform); `deploy.entitlements`, a `.plist` file inside the package that the macOS signature carries (it needs a darwin platform); and `deploy.updateManifest`, an object with `objectKey`, the `.json` object key of the signed release manifest in the releases bucket, and `publicUrl`, exactly `https://<host>/<objectKey>`, the public URL of that object. No two deployables may name the same executable or manifest object key. `deploy-plan.mjs --check` also fails when a license or entitlements file does not exist. A Droplet deployable also has a `Dockerfile` in its package root, reads its listen address from the `ADDR` environment variable and answers `GET /healthz` with a success status when it can serve traffic. The image build context contains only the `Dockerfile`, the package `dist/` directory, `servers/LICENSE` as `LICENSE` and the Go toolchain `LICENSE` as `GO-LICENSE`; the `Dockerfile` copies both license files into the image, so the deployed image carries the FSL-1.1-ALv2 terms and notice and the BSD-3-Clause notice of the statically linked Go standard library and runtime that the [license contract](repository-license-contract.md#distribution) requires.

### Release selection with Changesets

[Changesets](https://github.com/changesets/changesets) (`@changesets/cli`, configured in `.changeset/config.json`) selects the packages of a deployment. Add a changeset with `pnpm changeset` in each pull request whose change must be deployed, and select every changed package and its bump type. `pnpm changeset` asks its questions in a terminal; an agent or script without one writes the file that it would create: `.changeset/<id>.md`, where `<id>` is a plain file name (letters, digits, `.`, `_` and `-`, starting with a letter or digit; use a kebab-case summary of the change), with YAML front matter that maps the `name` of each selected package's `package.json` to `major`, `minor`, `patch` or `none` (for example `"ownsand-console": patch` for `apps/ownsand`), followed by a summary of the change. `node scripts/ci/deploy-plan.mjs --check <repository root>` checks the file names and the `deploy` manifest fields without changing files; the CI `quality` job also runs `changeset version` in a throwaway checkout and rejects an unknown package name. Private packages are versioned and tagged (`privatePackages.version` and `privatePackages.tag`); nothing is published to a registry. `delidev` is in the `ignore` list, because `changeset version` would change only its npm manifest and not the Cargo and Tauri versions of the native app. A changeset that lists only `delidev` stays pending and releases nothing; a changeset that lists `delidev` together with another package fails the plan. Remove `delidev` from `ignore` when its native versioning is supported. Changesets adds a dependent of a released package to the release only in some cases. It adds a dependent through `dependencies` or `peerDependencies` with a new version when it must update the dependency range (for example `workspace:*`, with `updateInternalDependencies: patch`). It does not add a dependent whose range still matches the new version (for example `workspace:~` within a 0.x minor version, or `workspace:^` from 1.0.0 on). It adds a dependent only through `devDependencies` with release type `none`, and an explicit `none` changeset has the same effect: the package keeps its version. Do not rely on dependent selection: when a dependent site or server must be rebuilt and deployed, select it in the changeset explicitly. Every listed deployable is deployed, but only releases whose version advances get a tag, because the tag of an unchanged version can already exist. A `github-release` deployable is the exception: it is published under its version tag, so a `none` release of it publishes nothing. The version of a `github-release` release must be `MAJOR.MINOR.PATCH` without a pre-release suffix, because the device agent accepts only that form as an update target; the plan fails for another version.

### Run

A maintainer starts `deploy.yml` from the Actions tab or with `gh workflow run deploy.yml --ref main`. The workflow has only the `workflow_dispatch` trigger and no inputs, and it fails on every ref other than `refs/heads/main`. One deployment runs at a time (concurrency group `deploy`, no cancellation). A dispatch from another ref gets its own concurrency group, so it fails in `plan` without replacing a pending `main` deployment in the queue.

1. `plan` fails when `.github/workflows/deploy.yml` or `scripts/ci/` differs between the dispatch revision and the current `main`, because GitHub runs the workflow file of the dispatch revision while the jobs check out the scripts of the planned revision; start a new deployment in that case. It checks out the current `main` (not the dispatch revision, so a run that waited in the concurrency queue does not see changesets that the previous run consumed), records the deployed revision, runs `changeset status --output` and runs `scripts/ci/deploy-plan.mjs`. The planner reads every workspace package, keeps the releases of the pending changesets, keeps the deployables among them and orders them. Servers come before static sites, because the static sites call the servers; binaries come last, because they are published from their tags after the `release` job. Within one kind, every workspace dependency and every deployable in `deploy.needs` comes before its dependents. A workspace dependency is an entry in `dependencies`, `devDependencies`, `peerDependencies` or `optionalDependencies` that uses the `workspace:` protocol, including `workspace:<name>@<range>` and relative `workspace:../<directory>` aliases, also through packages that are not selected; pnpm links a workspace package only through that protocol, so plain ranges and registry aliases add no edge; among the packages whose dependencies are already ordered or deployed in an earlier stage, the alphabetically first one comes next. A cycle of workspace dependencies and `deploy.needs` entries, an unknown target, a target outside its workspace root or a missing service or project name fails the plan. With no pending changesets, every later job is skipped. The later jobs check out the recorded revision. `plan` also records the Git blob SHA of every planned changeset file. `deploy-servers`, `deploy-static-sites` and `release` run `scripts/ci/check-pending-changesets.sh` at the start, and `scripts/ci/deploy-targets.sh`, which runs both deploy loops and fails when its target list is empty or malformed, runs it again right before each provider upload (after the site build, or after the server image push and before the Droplet deploy step), so a changeset withdrawn while an earlier target deploys or the current target builds stops the upload. A rerun of failed jobs reuses the outputs of the original `plan` job, so this check fails the job when the plan is stale: when `main` no longer contains the planned revision (GitHub compare status other than `identical` or `ahead`), when `main` changed (or renamed away) a `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `.changeset/config.json` since the plan (the release job would then refuse to version and tag the deployment) or changed so many files that the compare list may be truncated (300), when a newer run of `deploy.yml` on `main` has started (status `in_progress` or `completed`; the check reads the run list page by page until it reaches its own run; a newer run whose first attempt still waits in the concurrency queue does not count; a cancelled run, or a rerun that waits in the queue, counts only when a job of one of its attempts started; the check reads every page of the job list), when a planned changeset file is no longer on `main`, or when its blob on `main` differs from the plan. Each check reads the `.changeset` directory of `main` once (the GitHub contents API lists up to 1,000 files; when the listing is full, a planned file that is missing from it is looked up on its own) and compares all planned files locally, so the number of GitHub API requests does not grow with the number of changesets. Start a new deployment instead of rerunning a stale run. Only HTTP 404 means that a changeset is gone; the check retries other GitHub API errors twice (three attempts in total, `CHECK_RETRY_DELAY` seconds apart, 5 seconds by default) and then fails with the API error. The workflow and the `release` job (whose job permissions replace the workflow permissions) have `actions: read` for the run and job lists.
2. `build-servers` checks out the planned revision with Git LFS objects and builds every selected server in parallel, one matrix job per server, with `pnpm exec turbo run build --filter=<package>` and `CGO_ENABLED=0`, `GOOS=linux` and `GOARCH=amd64`. It builds the `linux/amd64` container image `<package>:<revision>` from the build context with `docker build` and uploads it as a compressed `docker save` archive. The job has no deployment environment and no secrets. One failed build stops the run before any deployment; `deploy-servers` also waits for `build-static-sites`, so a failed site build stops the run before the first upload as well.
3. `deploy-servers` (environment `servers`) logs in to DigitalOcean Container Registry with `DIGITALOCEAN_ACCESS_TOKEN` and writes an SSH client configuration for the host alias `droplet` (user `deploy`, the key and pinned host keys from the environment secrets, `StrictHostKeyChecking yes`, `BatchMode yes`). `scripts/ci/deploy-targets.sh servers` then deploys the servers one at a time in plan order. For each server it loads the saved image, pushes it as `registry.digitalocean.com/<registry>/<service>:<revision>`, reads the manifest digest of the pushed tag from the registry (`docker buildx imagetools inspect`) and fails when there is none. After the stale-plan check it runs `scripts/ci/droplet-deploy.sh` on the Droplet with `ssh droplet bash -s -- <service> <image>@<digest> <port> <hostname> <upstream-protocol> <udp-ports>`, the script on standard input (`<udp-ports>` is the comma-separated `deploy.udpPorts` list, or `none`), so the Droplet always runs the script of the planned revision. That script first takes the exclusive lock `/srv/delino/state/<service>.lock` (`flock`, one lock per service) and holds it until it exits, so that deployments and rollbacks of one service run one after the other and never stop a container that the route of another run names or write the route staging and backup files (`<service>.caddy.new`, `<service>.caddy.previous`) at the same time; a run that cannot get the lock waits up to `DROPLET_LOCK_TIMEOUT` seconds (default 600) and then fails without a change, and deployments of different services do not wait for each other. The script needs `flock` (util-linux, part of Ubuntu) and exits with an error without it. After the lock it pulls the image by digest and starts a new container next to the running one, on the `delino` network under its own unique network alias, with the env file `/srv/delino/env/<service>.env`, `ADDR=:<port>`, the label `io.delino.service=<service>` and the restart policy `unless-stopped`. It fails before it starts the container when the env file is missing or sets `ADDR`, or when it cannot list the existing containers of the service. It waits up to 120 seconds until `GET http://<container-address>:<port>/healthz` returns a 2xx status, and fails at once when the container stops. The check does not follow redirects, so a 3xx status, a 4xx or 5xx status and a failed request all count as not healthy until the deadline. The alias is `<service>-<timestamp>-<image suffix>` with the service name cut to its first 35 characters (without a trailing hyphen), so it is a DNS label of at most 63 characters, and it differs in every deployment. The replacement does not join the network alias `<service>` that the running container has (and that earlier script versions gave every container), so the live route selects only the current container while the replacement starts or fails its health check. It then writes the route `/srv/delino/caddy/sites/<service>.caddy` (`<hostname>` to `<unique alias>:<port>`, with a 10-second `lb_try_duration` retry, and for the `h2c` upstream protocol a `transport http` block with `versions h2c`) and reloads Caddy. The route names the new alias, so it differs in every deployment and Caddy reloads every time. The script checks every step of the route change: it creates the route directory, backs up an existing route to `<service>.caddy.previous`, writes the new route to `<service>.caddy.new` and renames it over the route file, so the route file changes atomically and Caddy reloads only after the route file is installed. A failed step fails the deployment with an error that names the operation (directory creation, backup, write or install) and leaves the previous route in place. Only then does it record the replacement image in the state files (below) and stop the old containers of the service (`SIGTERM`, then `SIGKILL` after 30 seconds) and remove them. A failed `docker stop` or `docker rm` does not skip the other old containers; the script then removes unused images and exits non-zero with an error that names each failed operation and container and says that the replacement already serves the service, and the state files already name the replacement. When the health check or the route change fails, it prints the last 200 log lines of the new container, removes it, restores the previous route when the reload failed and fails; the old container keeps serving and the recorded current image does not change. The proxy selects the new container only after the health check passed and the reload succeeded, so a container that is starting or unhealthy never receives a request; the old container keeps serving the requests that it accepted until it stops, and the retry window covers a request that reaches it while it stops. The first deployment with this script version switches the route of a service that an earlier script version deployed from the alias `<service>` to the new alias, and stops the old container by its label. The script records the deployed image in `/srv/delino/state/<service>.current` and the image that `<service>.current` held before in `<service>.previous` right after the reload succeeded and before the cleanup of the old containers, so a failed cleanup does not leave the state files naming an image that the route no longer serves; a rejected health check or reload changes neither file. A deployment of the image that `<service>.current` already names (a retry after a failed cleanup) keeps `<service>.previous` and stops and removes the remaining old containers. The script also removes images that no container uses. Its exit code is the deployment verdict.
   A server with `deploy.udpPorts` cannot run next to its replacement, because only one container can publish a host port, so for such a server the script changes the order. After the lock and the pull, it lists the running containers of the service and fails without a change when it cannot. It creates the replacement (`docker create` with the same settings and `--publish <port>:<port>/udp` for each UDP port), stops the running containers (`SIGTERM`, then `SIGKILL` after 30 seconds) to free the ports, and only then starts the replacement and runs the health check, the route change and the cleanup as above. The server does not answer from the stop until the route switch; the 10-second retry of the route covers only the start of this gap. When a running container does not stop, the replacement does not start, the health check fails or the route change fails, the script removes the replacement, starts the stopped containers again (the route still names them) and fails; a container that does not start again is named in an error. The state files change only after a successful route switch, as above.
4. `deploy-static-sites` (environment `static-sites`) runs after the servers, also when no server is selected. The sites build in the separate `build-static-sites` job, which has no deployment environment and no secrets, because the build runs third-party build plugins: it checks out the planned revision with Git LFS objects, builds every selected site in plan order (`deploy-targets.sh build-static-sites`) and uploads only the build output as an artifact. The build step receives every repository variable as the JSON object `BUILD_VARIABLES` (`toJSON(vars)`) and runs the build of each site with exactly the variables that its `deploy.buildEnv` maps (GitHub variable names are case-insensitive, so the lookup ignores case). It fails before the build of a site with one error that names each mapped variable that is not set, is empty or contains a NUL character; the log names the variables but not their values. Values of the runner environment that the map does not name stay as they are, and the Turbo `build` task of each site passes only the variables that its `turbo.json` declares. `deploy-static-sites` checks out the planned revision on a fresh runner, installs the locked dependencies with `--ignore-scripts`, unpacks only the planned output directories of that artifact into a directory outside the checkout (`SITES_ROOT`), so the artifact cannot replace a script that runs with the secrets, and fails when the output contains anything other than regular files and directories (Wrangler would follow a symlink), and only uploads and polls; no build code runs next to the Cloudflare and GitHub tokens. The build uses `pnpm exec turbo run build --filter=<package>`; the deploy step uploads the output with `pnpm exec wrangler pages deploy <output> --project-name <project> --branch main`. Wrangler is an exact root `devDependency`, so the lockfile pins it and its dependencies. Wrangler exits 0 also when it cannot determine the final deployment status, so the job uses `scripts/ci/deploy-provider.sh` to read the deployment ID from the `WRANGLER_OUTPUT_FILE_PATH` output and to poll the Cloudflare Pages deployment API until the deployment is in the `production` environment and its `deploy` stage reports `success`. A preview deployment (for example when the project's production branch is not `main`), a `failure` or `canceled` stage, five failed status reads in a row, or 10 minutes without a result fails the job. The Pages projects are Direct Upload projects with `main` as the production branch.
5. `build-binaries` (Ubuntu) and `build-macos-binaries` (`macos-15`, arm64; only when a binary has a cgo platform) check out the planned revision with Git LFS objects and build the selected binaries with `scripts/ci/release-binaries.sh build cross` and `build cgo`; `sign-macos-binaries` (environment `releases`, `macos-15`) signs and notarizes every darwin executable. Both build jobs have no deployment environment and no secrets, and `deploy-servers` and `release` wait for all three jobs, so a failed build or notarization stops the run before the first upload. [Binary releases](#binary-releases) describes the jobs.
6. `release` runs `scripts/ci/deploy-release.sh` only when every selected deployment and binary build succeeded, also when the pending changesets contain only `none` releases. When `changeset version` changes nothing (only changesets of ignored packages are pending), it creates no commit or tag. Otherwise it runs `changeset version`, which consumes the deployed changesets and writes the versions and changelogs, and then `pnpm install --lockfile-only`, because a new version can change a `workspace:<version>` range. It commits the result as `chore(release): version deployed packages` on top of the deployed revision and creates an annotated `<package>@<version>` tag on that version commit for every release whose version advances; an existing tag fails the job. The plan has already checked that every release name forms a valid Git tag (see the package name rules above), so a name that Git rejects fails the plan, not this job. Each tag therefore holds exactly the deployed tree plus the version files, and the tag message records the deployed revision. The job pushes the version commit to `main` and the tags in one atomic push. The push carries a lease on the expected `main` tip (first the deployed revision), so a `main` that was rewound or rewritten is never fast-forwarded back. When the push is rejected because `main` moved forward from the deployed revision, it first checks that every planned changeset is unchanged on the fetched `main` and that no package manifest, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `.changeset/config.json` changed since the deployed revision (either case fails the job without a push and needs a new deployment), then cherry-picks the version commit onto the new `main` and tries again, up to three attempts in total; changesets merged during the deployment stay pending. In that case `main` gets the cherry-picked copy, and the tags stay on the original version commit, which is not part of the `main` history. Any other rejection, such as a ruleset denial or an existing remote tag, fails the job at once.
7. `publish-binaries` (environment `releases`) runs only after `release` succeeded, and publishes every selected binary from its pushed tag: the GitHub Release with its assets and, for a binary with `deploy.updateManifest`, the new signed release manifest. A failure leaves the tags and the version commit in place; see [Binary releases](#binary-releases) for the rerun.

The `release` job pushes with `GITHUB_TOKEN` and `contents: write`. A branch ruleset on `main` must allow GitHub Actions to push the version commit. Pushes with `GITHUB_TOKEN` do not start other workflows, so `CI.yml` does not run for the version commit. Deployment does not roll back: when a later deployable fails, the earlier deployables of the run stay deployed, no version commit or tag is pushed, and the next run deploys the same changesets again.

Every `deploy.yml` job sets `timeout-minutes`, so a hung build, upload or SSH session fails its job instead of holding the single `deploy` concurrency slot (queued deployments never cancel) until the six-hour GitHub default: `plan` 10, `build-servers` 30, `deploy-servers` 60, `build-static-sites` 30, `deploy-static-sites` 30, `build-binaries` 30, `build-macos-binaries` 30, `sign-macos-binaries` 60, `release` 10 and `publish-binaries` 30 minutes. No run history of `deploy.yml` exists yet, so these limits are estimates and not three times an observed duration as for `CI.yml`: `plan` installs dependencies and calls the GitHub API; each `build-servers` matrix job builds one image; `deploy-servers` works through the servers one at a time, each with an image push and a health wait of up to 120 seconds; `build-static-sites` builds every selected site; `deploy-static-sites` uploads each site and polls it for up to 10 minutes; `release` versions, tags and pushes with at most three attempts; `build-binaries` cross-compiles every non-cgo platform of every binary and reads the module licenses; `build-macos-binaries` builds the cgo platforms; `sign-macos-binaries` waits up to 45 minutes for each notarization; `publish-binaries` uploads the assets and the manifests. Replace each estimate with at least three times the longest observed run without caches once real runs exist, and raise a limit in the same change that makes a job legitimately slower. Every limit stays below the six-hour default, and the job conditions and `needs` lists do not depend on it.

The PlanetScale Postgres database has no job in the workflow (recorded decision). Each server with a database applies its embedded, forward-only goose migrations at startup, before its health check passes ([`accounts-api`](servers-accounts-api-foundation.md#storage) and [`ownsand-api`](servers-ownsand-api-foundation.md#storage)), so the Droplet deploy step of the server is also its database stage: a failed migration fails the health check, and the old container keeps serving. Every migration therefore stays compatible with the code of the previous release. The owning server contract records the backup policy of its database. The billing rollout deploys `accounts-api` with its billing APIs before `ownsand-api` reports usage; within one run, the plan already orders `accounts-api` before `ownsand-api` because neither depends on the other.

`scripts/ci/deploy-plan.test.mjs` covers the planner. `scripts/ci/deploy-scripts.test.mjs` covers the stale-plan check against a stubbed `gh`, the provider helper against a stubbed `curl`, the deploy loops against stubbed CLIs (including a changeset withdrawn during a build, and the site build variables: mapped values with case-insensitive names, and missing, empty or malformed variables), the Droplet deploy script against stubbed `docker` and `curl` (health check failure, a stopped container, a rejected route, the `h2c` route, the stop-then-start order of a server with UDP ports and the restart of its stopped container after a failed stop, start, health check or route change, a failed cleanup of the old containers, a retry after it, concurrent runs of one service (serialized by the lock, a lock wait timeout, a lock file that cannot be opened) and of different services, route directory, backup, write and install failures, and invalid arguments or env files), the Caddy start script against a stubbed `docker` (a missing, running, stopped or different-image container and a failing Docker command), and the release script against a local bare remote, including a moved, rewound or manifest-changing `main`, an existing tag, `none` releases and ignored packages. `scripts/ci/release-binaries.test.mjs` covers the binary release steps against stubbed `go`, `gh`, `curl`, macOS signing tools and release manifest tool (see [Binary releases](#binary-releases)). All three run in `pnpm test:tooling`. The deploy shell scripts need Bash 4.4 or newer and refuse to run on older Bash; their fixtures are skipped there (for example on the Bash 3.2 that macOS ships). The provider wait commands also need GNU coreutils `timeout` (or `gtimeout`); their fixtures are skipped without it. The deploy fixtures also need `jq`, which the Ubuntu runners provide, and are skipped without it.

The job summaries record the deployed revision, the ordered deployables, the Droplet services, host names and image digests, the Pages projects and deployment IDs, the version commit on `main`, the tagged version commit and the tags, the SHA-256 of each built executable, the signing identity and notarization submissions, the GitHub Releases and the uploaded manifests. Each deploy job reads only the secrets of its own environment.

### Binary releases

Recorded decision: binary releases run in `deploy.yml`, not in a separate workflow. `changeset version` in the `release` job consumes every pending changeset, so a second workflow that versioned the agent or the CLI would race `deploy.yml` for the same changesets and version commit; one plan, one version commit and one tag push keep servers, sites and binaries consistent.

Assets: each GitHub Release `<name>@<version>` holds the executables `<binary>-<GOOS>-<GOARCH>` (`.exe` for Windows) of every platform, the license files of `deploy.licenseFiles` (`cmds/ownsand-agent/LICENSE` for the agent, root `LICENSE` and `NOTICE` for the CLI), `GO-LICENSE` (the Go toolchain license, because every executable statically links the Go standard library and runtime), `THIRD-PARTY-LICENSES.txt` and `SHA256SUMS` (`sha256sum` format over every other asset). The executables are bare files and not archives, because the agent update artifact is the executable itself. `THIRD-PARTY-LICENSES.txt` holds, for every module that `go list -deps` reports for one of the platforms (with the cgo setting of that platform), the license files at the module root (`LICENSE*`, `LICENCE*`, `COPYING*`, `NOTICE*`, `PATENTS*`) and in its `LICENSES/` directory; a module without one fails the build. The release is not marked as the repository's latest release, because the tags of every package share one release list, and its notes link the package changelog at the tag.

Build: `go build -trimpath -buildvcs=false -ldflags "-s -w [-X <versionVariable>=<version>]"` with `CGO_ENABLED=0` and the target `GOOS` and `GOARCH`, or `CGO_ENABLED=1` on the native runner for `deploy.cgoPlatforms`. `build cross` also builds the release manifest tool `cmds/ownsand-agent/release-manifest` (standard library only, `CGO_ENABLED=0`, for the Ubuntu runner that also runs `publish-binaries`) into the `release-manifest-tool` artifact, because `publish-binaries` has secrets and therefore runs no build. When a selected binary has an update manifest, it then runs `release-manifest check-keys` with that tool and fails before any binary build when the agent has no built-in release public key, so an unprovisioned key cannot stop a run after the tags exist. The release scripts need Bash 4.4 or newer and `jq`; the macOS runner image provides both.

macOS signing (`sign-macos-binaries`): the job downloads only the unsigned darwin executables, imports the Developer ID certificate into a temporary keychain that it deletes at the end, and requires exactly one `Developer ID Application` identity. It signs each executable with `codesign --options runtime --timestamp --identifier io.delino.<binary>` and the entitlements of `deploy.entitlements` (the agent's `com.apple.security.virtualization`), checks the signature with `codesign --verify --strict` and the entitlement with `codesign --display --entitlements`, and notarizes a zip of it with `xcrun notarytool submit --wait` (45-minute limit) and the App Store Connect API key. A status other than `Accepted` fails the job and prints the notarization log. A bare executable cannot carry a stapled ticket, so the job verifies the notarization with `spctl --assess --type install`, which must report `source=Notarized Developer ID`; on a user's Mac, Gatekeeper checks the ticket online when a quarantined download first runs, and an agent update written by the agent itself carries no quarantine attribute.

Publication (`publish-binaries`): the job checks out the planned revision without persisted credentials, downloads the build artifacts (including the `release-manifest-tool` artifact) outside the checkout and runs, one step each; it sets up no toolchain and compiles nothing, and the manifest steps refuse to run without the downloaded tool (`RELEASE_MANIFEST_TOOL`, a regular file; a linked or missing tool fails) instead of falling back to `go build` or `go run`:

1. `assemble`: accepts exactly the planned files of each binary (regular files only; a missing, linked or extra entry fails), adds the license files from the checkout and writes `SHA256SUMS`. No secret.
2. `github-releases` (`GITHUB_TOKEN`, `contents: write`): requires that `<name>@<version>` is an annotated tag whose commit has the deployed revision as its first parent (the version commit of the `release` job), then creates the release with `gh release create --verify-tag`. When the release already exists (a rerun), it uploads the assets again with `--clobber` and publishes a draft.
3. `fetch-manifests` (R2 credentials): downloads `<objectKey>` and `<objectKey>.sig` through the R2 S3 API (`https://<account>.r2.cloudflarestorage.com/<bucket>/<key>`, SigV4 through a curl configuration, so the credentials never appear in process arguments) and not through the cached public URL. Both missing (HTTP 404) starts the first manifest; one of them missing or any other status fails.
4. `prepare-manifests` (no secret): runs `add-release` of the downloaded tool, which verifies the current manifest with the agent's built-in keys before it changes anything, keeps every earlier release and `revoked_versions`, adds the release with the SHA-256 and the download URL `https://github.com/<repository>/releases/download/<name>%40<version>/<asset>` of every platform, makes it the only `default` release and fails when the manifest already lists a newer version, lists this version with other artifacts or revokes it.
5. `sign-manifests` (only `OWNSAND_AGENT_RELEASE_SIGNING_KEY`): signs the exact manifest bytes with `release-manifest sign`, which refuses a key that is not built into the agent, and verifies the result.
6. `upload-manifests` (R2 credentials): uploads the manifest and then its signature with `Cache-Control: no-cache`, then reads the public URL; a public URL that does not serve the new manifest yet is a warning. The job also keeps the signed manifests as the `release-manifests` artifact for 30 days.

The manifest steps do nothing and need no secret when no selected binary has an update manifest (a CLI-only release).

Rerun: every step is idempotent for the same run, so rerun `publish-binaries` after a failure. The tags already exist, so the job does not run the stale-plan check; the tag check instead binds the release to the deployed revision. `add-release` accepts the release that the manifest already lists with the same artifacts, and the Ed25519 signature of the same bytes is the same, so a rerun after a successful upload changes nothing. An upload that stopped between the manifest and its signature leaves a pair that no agent and no later run accepts; restore the pair from the `release-manifests` artifact (or the previous pair) in the R2 dashboard before the rerun. A rerun of an old run never replaces a newer default, because `add-release` refuses a version older than the newest listed one. Revoking a version needs a signed manifest change that this workflow does not make yet (follow-up).

### Droplet

Every server runs as a container on one shared DigitalOcean Droplet (Ubuntu 24.04 LTS, `linux/amd64`). The Droplet also runs the Caddy reverse proxy container, which listens on TCP ports 80 and 443 and UDP port 443, terminates TLS with automatic Let's Encrypt certificates for every route host name and forwards plain HTTP/1.1 (or HTTP/2 without TLS for the `h2c` upstream protocol) to the server containers on the `delino` Docker network. The only other host ports are the UDP ports in `deploy.udpPorts`, which the server container publishes itself: UDP 3478 of `ownsand-api` for STUN. A server that needs another public TCP port needs a change to this contract and to `scripts/ci/droplet-deploy.sh` before its first deployment.

Caddy route requirements: the `h2c` route must deliver HTTP/2 to the upstream while the client uses HTTP/2 over TLS, carry a bidirectional stream in full duplex (each message of the request body can come back before the request body ends), and keep a stream open through Caddy reloads with a changed configuration (as a deployment of another server does) until the server or the client ends it. The reverse proxy sets no stream or response header timeout by default ([Caddy `reverse_proxy`](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)), and the route sets none. The Caddy server has two idle timeouts of 1 minute by default that also apply to streams, and the Caddyfile keeps them: `read_body_idle` ends a request whose body sends no data for 1 minute while the proxy waits for it, and `write_idle` ends a request when one write to the client makes no progress for 1 minute, for example when the client does not read; a pause between writes does not count. A server whose clients keep a request body open must therefore make them send data at least once a minute. When the Caddy image or the route form changes, verify these properties with the pinned Caddy image, the route form that `droplet-deploy.sh` writes and an upstream that serves HTTP/1.1 and h2c, including a stream that stays open longer than the longest stream limit of the servers and a request body that sends no data for more than 1 minute, and record the results in the pull request.

Provision a new Droplet once:

1. Create the Droplet and a DigitalOcean Cloud Firewall that allows inbound TCP 22, TCP 80, TCP 443, UDP 443 and UDP 3478 (STUN of `ownsand-api`) and denies all other inbound traffic. Add a rule for every UDP port in a `deploy.udpPorts` list before the first deployment of its server. SSH stays open to all addresses, because GitHub-hosted runners have no fixed addresses; the `deploy` user accepts only its key.
2. Point the DNS record of every server host name to the Droplet address. The record of `ownsand.api.delino.io` must not go through an HTTP proxy such as a proxied Cloudflare record, because STUN needs the Droplet address and the agent streams need HTTP/2 from end to end.
3. Run `scripts/droplet/provision.sh <deploy-public-key-file> <acme-email>` as root on the Droplet. It installs Docker Engine from the Docker apt repository, sets the `local` log driver (rotated logs), creates the `deploy` user with the given key as its only `authorized_keys` entry (`restrict` option) and adds it to the `docker` group, creates `/srv/delino` (`env/` with mode 0700, `caddy/`, `caddy/sites/`, `state/`), writes `/srv/delino/caddy/Caddyfile` (ACME email and `import sites/*.caddy`), creates the `delino` network and then runs `scripts/droplet/start-caddy.sh` with the digest-pinned Caddy image, which keeps the certificates in the `caddy-data` volume. The script can run again, and `start-caddy.sh` handles the Caddy container in three cases: when the container is missing or uses another image than the pinned one, it removes the container if present and creates it (the only case that recreates it); when the container has the pinned image and is stopped (as after `docker stop`), it starts the container without recreating it; and when the container has the pinned image and is running, it reloads the configuration without recreating it. A failing `docker run`, `docker start` or `docker exec` makes `provision.sh` exit non-zero with the Docker diagnostic. Membership in the `docker` group is equivalent to root access on the Droplet, so the `deploy` private key is a production root credential.
4. As the `deploy` user, run `docker login registry.digitalocean.com` with a DigitalOcean API token that has read access to the registry, so that the Droplet can pull server images.
5. Create `/srv/delino/env/<service>.env` (mode 0600, owner `deploy`) for every server, with the configuration and secrets that its server contract lists, before its first deployment. The env file must not set `ADDR`.
6. Store the `servers` environment secrets. Get the host keys for `DROPLET_SSH_KNOWN_HOSTS` from the Droplet console (`/etc/ssh/ssh_host_*_key.pub`), not from an unverified network scan.

Roll a service back with the image in `/srv/delino/state/<service>.previous`: run `ssh deploy@<droplet> bash -s -- <service> <image> <port> <hostname> <upstream-protocol> <udp-ports> < scripts/ci/droplet-deploy.sh` from a checkout of `main`, with the values of the `deploy` field of the server's `package.json` (`http1` and `none` when the field does not set them). The rollback uses the same script, so it takes the same per-service lock as the workflow deployment and waits for a deployment that is running, and it uses the same health check and switch as a deployment; it does not change versions or tags. Delete old images from the registry with the DigitalOcean registry garbage collection when the registry storage limit requires it, and keep the images in the `.current` and `.previous` state files of every service.
