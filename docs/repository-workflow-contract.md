# Repository Workflow Contract

## Scope

The repository contains shared instructions, skills, documentation templates, formatting infrastructure, two static Rspress sites ([`delino-site`](project-delino-site.md) and [`delino-docs`](project-delino-docs.md)) and the [`delino-accounts`](project-delino-accounts.md) project with an Rsbuild web app and a Go API server, the shared React UI component package [`delino-ui`](project-delino-ui.md), and the [`delidev`](project-delidev.md) desktop and mobile app with a Tauri app crate. The root `Cargo.toml` defines the Rust workspace; its only member is `apps/delidev/src-tauri`. Generated protocol bindings: the Go bindings of the [OwnSand schemas](protos-ownsand-api-contract.md) are committed under `protos/delino/ownsand/v1/` and the TypeScript bindings under `packages/ownsand-sdk/src/gen/`, and `scripts/protos.sh` regenerates and checks both. `.github/workflows/deploy.yml` deploys the servers and static sites according to the [deployment workflow](#deployment-workflow) below and uses only the [deployment environments](#deployment-environments) below.

## Agent skills

`.agents/skills/` owns the shared workspace-local agent skills. `.claude/skills` is a tracked relative symlink to `../.agents/skills` so that Claude Code discovers the same skills as Codex. Add, edit and remove skills only in `.agents/skills/`; do not replace the symlink with a copy or add Claude-only skill directories. Checkouts on platforms without symlink support (for example, Windows without `core.symlinks`) get a plain file instead and do not expose the skills to Claude Code.

## Installation

Use Node.js 24 from `.nvmrc` and pnpm 10.26.2 from `package.json`. The Go toolchain selected by the root `go.mod` (Go 1.26.1 or later) is also a prerequisite for the root `pnpm build`, `pnpm dev`, `pnpm lint` and `pnpm test` tasks, because they include `servers/accounts-api` and `servers/ownsand-api`, whose package scripts call `go`. Rust code uses the toolchain named in root `rust-toolchain` through rustup and the root Cargo workspace; root `cargo test` runs its tests. The workspace builds the CEF runtime of `delidev`, so it needs the Linux packages, macOS and Windows tools and the disk space listed in the [delidev contract](apps-delidev-foundation.md#build-and-test); the first build downloads the CEF distribution. Rust is not a prerequisite of the root pnpm tasks, because no package script calls `cargo`. Git 2.32 or newer is a local prerequisite for `pnpm test:tooling`: the `scripts/ci` fixtures isolate fixture repositories from the developer's global Git configuration with `GIT_CONFIG_GLOBAL`, which older Git ignores, so they fail with a clear error that names the found version on older Git. All Go code belongs to the single root module `github.com/delinoio/mono`; nested `go.mod` and `go.work` files are not used. Run `pnpm install --frozen-lockfile`. The prepare script installs Lefthook through `scripts/install-git-hooks.sh`. Archives without Git metadata skip hook installation, including archives extracted inside another Git work tree, because the installer runs only when the project directory is the root of its own work tree. Linked worktrees may use their shared Git hooks directory; unrelated custom hook paths remain protected. A missing custom hook path stays protected when the installer runs under `sh`, `dash` or `bash`, including `bash --posix`. Every spelling of Git's shared hooks directory, including spellings with a trailing slash or with `.` or `//` segments, counts as the shared hooks directory even when that directory does not exist yet. In the shared hooks directory the installer forces the Lefthook installation, which disables Lefthook's protection of an existing `pre-commit.old` backup. The installer therefore exits with an error that names both files, and leaves them unchanged, when `pre-commit` is not managed by Lefthook and `pre-commit.old` already exists. Move or merge one of the two files and run the installer again. A Lefthook-managed `pre-commit` with an existing backup, a backup without a current hook, and a custom hook without a backup are installed as before; the custom hook becomes the backup.

## Public Go packages

Go packages that users outside this repository import live under the root `go/` directory, in the root Go module `github.com/delinoio/mono`. Each top-level directory `go/<name>/` is one public package tree with the import path `github.com/delinoio/mono/go/<name>`. Its name is the Go package name of its root package, for example `go/ownsand/` with the package `ownsand`. The `go/` directory contains no other code.

- Put a Go package under `go/` when external users import it, or when the exported API of such a package uses it. A project contract names each of its packages under `go/` and owns their behavior.
- Keep Go code that only this repository uses in the directory of its owning project, preferably in an `internal/` directory, for example `cmds/ownsand-agent/internal/` or `servers/ownsand-api/internal/`. Do not put Go packages for external users under `apps/`, `cmds/`, `crates/`, `packages/` or `servers/`.
- Exception: the generated protobuf Go bindings stay next to their schemas under `protos/` (for example `protos/delino/ownsand/v1/`), also when packages under `go/` use their types in an exported API. The protos contracts own them.
- Packages under `go/` use Apache-2.0. They import only other packages under `go/`, the generated bindings under `protos/`, the standard library and external modules. They never import code from `servers/`.
- The import path and the exported API of a package under `go/` are a public interface. Moving or renaming a package, or removing or changing an exported identifier, breaks external users; mark such a change as breaking in the pull request title (`!`) and record it in the owning contract.

## Task orchestration

The pinned `turbo` dependency and root `turbo.json` orchestrate packages selected by `pnpm-workspace.yaml`: `apps/*`, `packages/*` and `servers/*`. The workspace packages are `apps/delino-site`, `apps/delino-docs`, `apps/delino-accounts`, `apps/delidev`, `packages/delino-ui`, `packages/ownsand-sdk`, `apps/ownsand`, `servers/accounts-api` and `servers/ownsand-api`; commands only run tasks that exist in package scripts. Go server packages wrap the Go toolchain in their package scripts and disable Turbo caching for their tasks because the toolchain and module cache are not declared inputs.

Root `pnpm build`, `pnpm dev`, `pnpm lint`, `pnpm typecheck` and `pnpm test:e2e` delegate to `turbo run`. The `test:e2e` task runs app end-to-end suites, is uncached and declares its pass-through environment according to the [e2e contract](repository-e2e-contract.md). Root `pnpm test` runs workspace tests and the repository-wide `test:tooling` task. The latter runs the existing formatter and hook fixtures directly and is registered as `//#test:tooling`. It is uncached so each invocation checks the current Git and hook environment. `prepare`, `format` and `format:check` remain direct commands: hook installation has side effects, and formatting depends on Git revisions, staged changes and untracked files rather than package inputs.

Root `pnpm dev` starts all workspace development servers together through the unfiltered `turbo run dev` command. Each workspace package that owns a development server exposes it through its `dev` script. Packages without a development server do not need a `dev` script. Package-specific development is available through an explicit filtered command; the root command always selects all packages. It currently starts the Rspress development servers of `delino-site` and `delino-docs`, the Rsbuild development servers of `delino-accounts`, `ownsand-console` and the `delidev` frontend, the `accounts-api` Go server and the `ownsand-api` Go server, which exits at once with a skip record when `DATABASE_URL` is unset (see the [control plane contract](servers-ownsand-api-foundation.md#build-and-test)). Root `pnpm dev` does not start the `delidev` native shell; use `pnpm --filter delidev tauri dev` for it.

Define each workspace task in its owning `package.json`. Declare workspace dependencies so Turbo can order tasks: builds depend on dependency builds, tests depend on dependency builds, and lint and typecheck tasks depend on their corresponding dependency tasks. Build output defaults to `dist/**`; packages with other outputs must override them in a package-local `turbo.json` that extends `//`. Declare any additional test reports or incremental compiler outputs there. Development tasks are persistent and uncached.

Turbo uses strict environment mode by default. Package contracts and package-local task configuration must declare environment variables, ignored configuration inputs and shared root inputs that affect results before enabling their caching. Keep side-effecting or environment-dependent tasks uncached when their inputs cannot be fully declared. Do not route Git-sensitive formatting through cached tasks or pass credentials through global environment wildcards. Development tasks pass the configuration variables that their owning package contract defines through task-level `passThroughEnv` in that package's `turbo.json`, so root `pnpm dev` honors shell-provided values like the package-specific commands. Use `passThroughEnv`, not `env`, so the values stay out of the hashes of these uncached tasks, and list only variables of the package that owns the task. Add a variable that a development server reads to the owning package's `turbo.json` in the same change. The `scripts/ci/turbo-env.test.mjs` fixture checks the resolved `dev` task definitions with a Turbo dry run. Remote caching is not configured. `.turbo/` is ignored local state; generated `dist` directories remain subject to the cleanup rule below.

For a package subset, use `pnpm exec turbo run <task> --filter=<package>`. Use `pnpm exec turbo run <task> --dry=json` to inspect the graph without running tasks. Root-only fixture execution is also available as `pnpm test:tooling`. New runtime projects must add their own contracts and package scripts before these commands can establish runtime acceptance.

## Formatting

Root `pnpm format` writes fixes and `pnpm format:check` checks without rewriting. Both use pinned Rstack and `rstack.config.ts`. The formatter resolves the repository root with `git rev-parse --show-toplevel` and uses it for every selector, the shared-exclusion probe and the Rstack run, so starting `scripts/ci/format-changed.mjs` from a subdirectory selects and formats the same repository-wide files as starting it from the root. The change planner `scripts/ci/plan.mjs` gives the same guarantee: it lists the changed paths for the fixtures, Go, Rust and end-to-end selectors with `git diff` run from that repository root, so starting it from a subdirectory gives the same selections and the same `ci_plan` record as starting it from the root, even when Git has `diff.relative=true`. Default local selection compares the merge base of `origin/main` and HEAD, including staged changes, working changes and untracked files. Explicit `--base <sha> --head <sha>` arguments select that committed comparison. Local `--all` selects existing tracked files, each path once in sorted order even when a conflicted merge leaves it unmerged in several index stages. Before the first commit, use `--staged`. Every selector matches the supported file extensions case-insensitively, so `notes.MD`, `Component.TSX` and `data.JSON` are selected like their lowercase spellings; the shared exclusions still decide which selected paths Rstack skips. The Lefthook glob needs no uppercase variants because Lefthook matches it case-insensitively on Linux (checked with Lefthook 2.2.2); macOS behavior is unchecked, and the script filter stays the authoritative one. A checkout whose own path is not valid UTF-8 cannot be used as the repository root, because that path cannot be passed to a child process: the formatter fails before it selects any file with a `ci_format_error` that names the checkout path with each invalid byte escaped as `\xNN` and asks to move or rename the checkout.

Lefthook runs `node scripts/ci/format-changed.mjs --staged --write` with `stage_fixed: true`. It preserves unstaged edits, supports initial commits and rejects parser failures. The hook supports `git add` followed by a plain `git commit`, `git commit -a` and `git commit -i`, including from a linked worktree; each formats the staged content and stages the fixes in the same commit. Git runs the hook of a pathspec commit (`git commit <path>`, `git commit --only` and `git commit --amend <path>`) against a throwaway `next-index-*.lock` index and later writes the real index from its own pre-hook snapshot, so a fix staged by the hook would leave HEAD formatted and the real index stale (`MM`). The formatter therefore detects that index through `GIT_INDEX_FILE` and runs the staged selection in check mode without writing or staging. It passes when nothing needs formatting and otherwise exits 2 with a `ci_format_error` that tells the user to run `git add` on the files and a plain `git commit`; because check mode also exits non-zero for parser failures, the message covers both causes. A pathspec run stopped by `SIGTERM`, `SIGINT` or `SIGHUP` keeps the `128 + signal` exit code (143, 130 or 129) with only the `ci_format_signal` event and is not reported as a formatting or parser failure. Select files with NUL-separated Git paths, skip deletions, symlinks and gitlinks, and preserve imported skills, generated files and lockfiles through shared exclusions. Staged deletions, staged paths with an unsupported extension, staged paths recorded as symlinks (mode `120000`) or gitlinks (mode `160000`, which have no blob to format) and staged paths that the shared exclusions skip (for example a skip-worktree lockfile removed from the working tree; Rstack evaluates the exclusions for a path that does not exist on disk through `--stdin-filepath`) are skipped even when their working-tree path is missing, as the unstaged selectors skip them. Every such exemption applies before the missing-path failure, but a staged added, modified, renamed or type-changed formattable path that is missing from the working tree (removed after `git add`, behind a replaced parent directory or outside a sparse checkout) fails the hook with a `ci_format_error` naming the path, so a staged blob cannot bypass formatting. A parent directory replaced by a symbolic link to a directory counts as a replaced parent directory in every selector, because the tracked path then resolves outside the repository and Rstack would format the file that the link points to: the `--all` and default local selectors skip it silently, and the staged and explicit selectors fail with a `ci_format_error` naming the path and saying that a parent directory resolves outside the repository through a symbolic link, unless the shared exclusions skip it. The same failure applies to a staged added, modified, renamed or type-changed formattable path that exists in the working tree as a non-regular entry, such as a directory that replaced the file, a symlink that the index does not record as one, a FIFO, a socket or a device: the `ci_format_error` names the path and the observed entry type, and the path is skipped silently only when the shared exclusions skip it. Git path lists are read as bytes and each name is checked with `node:buffer` `isUtf8` (not a fatal `TextDecoder`, which would strip a leading byte order mark from a valid name), because Rstack cannot address a file name that is not valid UTF-8. A staged or explicit-comparison (`--base`/`--head`) added, modified, renamed or type-changed formattable path that is present but whose name is not valid UTF-8 (for example the Latin-1 name `caf\xe9.ts` on Linux) fails with a `ci_format_error` that names the path with each invalid byte escaped as `\xNN`, states that the name is not valid UTF-8 and asks for a rename, instead of reporting the path as missing from the working tree. This check runs after the unsupported-extension, symlink, gitlink and shared-exclusion exemptions (the exclusion probe uses the lossy name, which keeps the valid directory prefixes), so those paths stay silent skips, and an explicit-comparison path that the range deletes stays skipped. The planner does not run the exclusion probe, because it runs without installed dependencies and cannot evaluate the shared exclusions: it selects formatting for such a present formattable path, and the `quality` job's formatter gives the verdict, skipping the path when the shared exclusions skip it and otherwise failing with the `ci_format_error` described above. An explicit-comparison formattable path that the range changes and the validation index tracks but whose working-tree entry is gone (removed, behind a replaced parent directory or a symlink loop, or outside a sparse checkout) is skipped when the shared exclusions skip it, as the staged and default local selectors skip it, and otherwise fails with a `ci_format_error` naming the path, because the comparison validates the full checkout. Selectors compare paths by their bytes, not by a lossy decoding: each byte that is not part of a valid UTF-8 sequence is held as a distinct escaped value, so a name that is not valid UTF-8 never equals the valid name that contains U+FFFD in its place. A rename from the raw `caf\xe9.ts` to the valid `caf�.ts` therefore selects the valid replacement, and the deleted or exempt raw name neither marks the replacement as invalid nor exempts it. `--all` and default local changed-file selection keep skipping such a path silently; this is a documented limitation until Rstack can format such names. The checkout path itself is subject to the same limitation. Linux file systems hold these names; APFS and Windows reject or normalize them, so the fixtures skip there. Unstaged deletions in `--all` and local changed-file selection stay skipped. Every selector (`--staged`, `--all`, explicit comparison and default local) skips a path that the validation index records as a symlink (mode `120000`) or a gitlink (mode `160000`), even when the checkout materialized it as a regular file (a symlink on Windows without symlink support or with `core.symlinks=false`, or a gitlink replaced by a regular file), so the placeholder bytes and the recorded mode stay unchanged. The mode comes from the current index (`git ls-files --stage -z`), never from the comparison head, and works before the first commit.

CI requires an explicit comparison and rejects local `--staged` and `--all` modes. Outside CI, the formatter also rejects `--all` combined with `--base`, `--head`, `TURBO_SCM_BASE` or `TURBO_SCM_HEAD`: it exits with status 2 and a `ci_format_error` before it selects or rewrites any file, because `--all` has no comparison to honor. An unset, empty or case-insensitive `false` CI value means local execution; every other nonempty value enables CI restrictions.

## Validation

Run `pnpm test` for the workspace package tests and the formatter, hook and change-planning fixtures; `pnpm test:tooling` runs only the fixtures. CI plans affected fixtures, formatting and workspace package tasks on Ubuntu for pull requests, main pushes and manual dispatch. The `quality` job runs plain `pnpm format:check` with `TURBO_SCM_BASE` and `TURBO_SCM_HEAD` set to the resolved comparison, and, when fixtures are selected, `pnpm test:tooling` and then `scripts/ci/validate-changesets.sh`, which runs `scripts/ci/deploy-plan.mjs --check` (the deploy planner's rules that need no release: changeset file names and the `deploy` manifest fields) and `pnpm exec changeset version` in its throwaway checkout when a changeset is pending (it counts the same files as the Changesets reader: no hidden files, `README.md`, `AGENTS.md`, `CLAUDE.md` or `GEMINI.md`; without one it has nothing to check; `changeset version` would exit 1) and so rejects a pending changeset for an unknown package or one that mixes the ignored `delidev` with other packages before it can reach `main` and stop every deployment; the formatter reads that environment as the explicit comparison. The `--base <sha> --head <sha>` arguments are the equivalent local form and select the same files. PR comparisons use the pull request base and head. Push comparisons use the prior and current commits. Manual comparisons use the merge base with `origin/main`; an optional `base` input selects another existing revision. A root push has no previous commit, so CI creates a local empty-tree comparison commit without pushing it. No full manual mode or macOS runners are configured.

The `changes` job resolves that comparison and runs `scripts/ci/plan.mjs` without installing dependencies. It publishes `base`, `head`, `format`, `fixtures`, `quality`, `go`, `rust`, `e2e`, `workspace` and `workflows` outputs. Formatting uses the existing formatter's changed-file selection; Rstack still owns exclusions, so a change that touches only a supported file with an uppercase or mixed-case extension (for example `notes.MD`) still publishes `format: true`. A present formattable path whose name is not valid UTF-8 and a formattable path that the comparison changes but that is missing from the working tree also publish `format: true` without an exclusion probe; the `quality` job's formatter decides whether the shared exclusions skip it or it fails. When the planner fails, for example because a comparison revision does not exist or the comparison is unset or malformed, it prints one `ci_format_error` record on stderr like the formatter, exits with code 2, prints no `ci_plan` record and writes no outputs and no summary record, and the `changes` job fails, which fails `ci-result`. Fixtures run for changes, deletions or renames affecting `scripts/ci/`, `.changeset/`, `.github/workflows/deploy.yml`, `scripts/install-git-hooks.sh`, `scripts/droplet/start-caddy.sh`, `.github/workflows/CI.yml`, `.nvmrc`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `rstack.config.ts`, `lefthook.yml`, any `turbo.json` (the root file or a workspace package file) or the `package.json` placed directly inside a workspace package under `apps/`, `packages/` or `servers/`. Adding, removing or renaming a workspace package changes the packages that the Turbo fixtures resolve, so a nested `package.json` deeper in a package does not select fixtures. In pull request and manual comparisons, documentation-only changes select formatting without fixtures. The `quality` job runs when either check is selected, and on every push to `refs/heads/main` because the planner always selects fixtures there, and passes the exact comparison to formatting. In pull request and manual comparisons, empty comparisons or changes with no validation inputs skip `quality`. The `go` output is selected when a changed, deleted or renamed path is a `.go` file, `go.mod`, `go.sum`, a `.proto` file, `protos/buf.yaml`, `protos/buf.gen.yaml`, `protos/buf.lock`, `scripts/protos.sh`, any path under `packages/ownsand-sdk/` (the TypeScript bindings that the drift check compares and the SDK sources, tests and rstest configuration that the OwnSand end-to-end suite runs), a schema migration under `servers/ownsand-api/internal/db/migrations/`, `.github/workflows/CI.yml` (which defines the job), or one of the workspace inputs that the `go` job installs and runs Node.js with (`.nvmrc`, `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml`), and for every `push` event to `refs/heads/main` regardless of the comparison. The `rust` output is selected when a changed, deleted or renamed path is a `.rs` file, a `Cargo.toml` or `Cargo.lock` at any depth, root `rust-toolchain` or `.rustfmt.toml`, `.github/workflows/CI.yml` (which defines the job), or any path inside a `src-tauri/` directory (a Tauri crate compiles its configuration, capabilities and icons into the binary), and for every `push` event to `refs/heads/main` in the same way. The `fixtures`, `e2e`, `workspace` and `workflows` outputs are selected for every `push` event to `refs/heads/main` regardless of the comparison in the same way; the forced `fixtures` also runs `quality`. Branch-wide cancellation can cancel a main-push run before its Go, Rust, fixtures, e2e, workspace or workflows jobs finish, and the next push compares only against its own parent, so the planner reads the runner-provided `GITHUB_EVENT_NAME` and `GITHUB_REF` and runs the Go checks, the Rust checks, the fixtures, the e2e suites, the workspace package tasks and the workflow lint against each main-push head; a later documentation-only push therefore cannot pass `ci-result` with Go, Rust, fixtures, e2e, workspace or workflows skipped. Pull request and manual comparisons keep affected selection, and the other outputs are unchanged. The `format` output stays derived from the comparison for every event, so this selection does not cover formatting that a cancelled main-push run lost: the formatter still compares only the range of the surviving push. The planner logs the reasons in the `goReason`, `rustReason`, `fixturesReason`, `e2eReason`, `workspaceReason` and `workflowsReason` fields (`diff` or `main-push`) of its record without publishing them as outputs; `main-push` means the output is true only because of the main push and the comparison alone did not select it. The `go` output selects two jobs that run in parallel: `go` and `protos`. Every protobuf input is a Go input, so the planner publishes no separate protobuf output. The `go` job starts a Postgres service container (an exact `postgres` image tag pinned by digest, reachable only inside the job), installs the workspace dependencies with `pnpm install --frozen-lockfile --ignore-scripts`, runs `gofmt -l` on tracked `.go` files and `go vet ./...` and `go test -count=1 ./...` in the root Go module with `OWNSAND_TEST_DATABASE_URL` and `OWNSAND_E2E=1`, so the Postgres-backed `ownsand-api` tests and the [OwnSand end-to-end suite](project-ownsand.md#end-to-end-test) run, and records the result in the job summary. The `protos` job checks out the full history, installs the workspace dependencies with `pnpm install --frozen-lockfile --ignore-scripts`, runs `scripts/protos.sh check` (buf lint, buf format check and the drift check that fails when the committed Go or TypeScript bindings differ from the generated output) and `scripts/protos.sh breaking` against the comparison base (skipped with a summary line only when the base is the local empty-tree commit of a root push, which the `protos` job does not have), and records the result in the job summary. The protobuf tools run through `go run` with the exact versions that the [protos contract](protos-ownsand-api-contract.md#build-and-test) records. The `rust` job installs `pkg-config` and `libgtk-4-dev`, installs the `rust-toolchain` toolchain with `rustfmt` and `clippy`, runs `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings` and `cargo test --workspace --locked` in the root Cargo workspace on the Linux desktop target, and records the result in the job summary. It sets `CEF_PATH` to `~/.cache/cef`, so the `cef-dll-sys` build script downloads the CEF distribution there instead of into `target/` and reuses it when it is present. It does not run `tauri build`, launch the app or build the macOS, Windows, Android or iOS targets. The `e2e` output is selected when a changed, deleted or renamed path is inside an `apps/<app>/` package, or is `.github/workflows/CI.yml`, `.nvmrc`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `turbo.json`. The `e2e` job installs Chromium and runs every app suite with `pnpm test:e2e`, as the [e2e contract](repository-e2e-contract.md#ci) describes. It reads the `AI_GATEWAY_API_KEY` repository secret and excludes tests tagged `agent` when the secret is not available. The `workspace` output is selected when a changed, deleted or renamed path is inside a workspace package under `apps/`, `packages/` or `servers/` (a file placed directly in one of these roots, such as `apps/AGENTS.md`, is not), or is `.github/workflows/CI.yml`, `.nvmrc`, `go.mod`, `go.sum`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `turbo.json`. The `workspace` job sets up the Go toolchain of `go.mod`, installs the workspace dependencies with `pnpm install --frozen-lockfile --ignore-scripts` and runs `pnpm exec turbo run build lint typecheck test --continue` for every workspace package, so each package's build, lint, typecheck and unit test scripts run, including the Go server package scripts without a database. It does not use `--affected`, because Turbo 2.11.11 selects no package when only a root input such as `package.json`, `turbo.json` or `go.mod` changes. The `go` job remains the owner of the Postgres-backed tests and the OwnSand end-to-end suite, and the `protos` job the owner of the protobuf checks. The `workflows` output is selected when a changed, deleted or renamed path is under `.github/workflows/` or `.github/actions/`. The `workflows` job runs `go run github.com/rhysd/actionlint/cmd/actionlint@v1.7.12`, which also checks every `run:` script with the shellcheck of the Ubuntu runner image, and zizmor 1.32.0 through `zizmorcore/zizmor-action` with online audits, annotations and without SARIF upload. Any finding fails the job. A zizmor finding that does not apply is suppressed only with an inline `# zizmor: ignore[<audit>]` comment and an explanation next to it; the `release` job of `deploy.yml` suppresses `artipacked`, because it pushes with the credentials that its checkout persists and uploads no artifacts. Renovate updates the pinned action digests, the `postgres` image digest and the zizmor action; update the actionlint and zizmor versions in the job by hand. The planner records the checkout revision, comparison and selections in logs and the job summary. New shared validation dependencies must update the planner inputs.

CI caches dependencies and build output with the GitHub Actions cache. The `quality`, `go`, `protos`, `e2e` and `workspace` jobs cache the pnpm store through `actions/setup-node` with `cache: pnpm`, keyed by the `pnpm-lock.yaml` hash. The `go` job caches the Go module and build caches through `actions/setup-go` with `cache: true`, keyed by the `go.sum` hash; `-count=1` keeps every test run uncached, so the cache only skips downloads and recompilation. The `protos` job caches the Go module and build caches of the buf CLI and the protoc plugins that `go run` builds, keyed by the hash of `scripts/protos.sh` and `protos/buf.gen.yaml`, which pin their versions; the key differs from the `go` job key, so the two jobs do not race to save different caches under one key. The `workspace` job does not use the Go cache, because `actions/setup-go` cannot restore without saving and it would save a different cache under the `go` job key. The `rust` job uses `Swatinem/rust-cache` for `~/.cargo`, the dependency build output in `target/` and `~/.cache/cef`, keyed by the toolchain and the Cargo manifests and lockfile; only pushes to `main` save it, and pull requests restore it. The pnpm and Go caches save a new entry after any run that misses the key, including a pull request that changes the lockfile or `go.sum`. GitHub scopes a cache saved by a pull request to that pull request's ref, so it cannot replace the caches that `main` and other pull requests restore. The deployment workflow uses no caches, because its jobs build and deploy with deployment credentials. Turbo task output is not cached between runs.

Every `CI.yml` job sets `timeout-minutes`, so a hung service, download or test fails its job and `ci-result` instead of running until the six-hour GitHub default: `changes` 10, `quality` 15, `go` 20, `protos` 10, `rust` 45, `e2e` 20, `workspace` 20, `workflows` 10 and `ci-result` 5 minutes. Each limit is at least three times the longest observed run of the job without caches. Raise a limit in the same change that makes a job legitimately slower.

Each CI run records the validation revision, comparison revisions, commands and results in its logs and job summary. Runtime and platform acceptance must be added with the owning project. CI does not build `delidev` bundles or mobile targets. CI runs the e2e suites of `delino-site`, `delino-docs`, `delino-accounts` and `ownsand-console` against their development servers. The `workspace` job builds these apps with their package `build` scripts but does not deploy them; the [deployment workflow](#deployment-workflow) builds and deploys them. The workspace unit tests, including those of `delino-accounts`, `delino-ui`, `ownsand-sdk` and `ownsand-console`, run in the `workspace` job whenever the planner selects it. Passing shared fixtures does not establish runtime or release acceptance.

The `ci-result` job aggregates validation through `needs`, including `changes`, `quality`, `go`, `protos`, `rust`, `e2e`, `workspace` and `workflows`. It runs with `always()` so dependency failures do not skip the aggregate check. Failed or cancelled dependencies fail `ci-result`. The `changes` job must succeed; a skipped `quality`, `go`, `protos`, `rust`, `e2e`, `workspace` or `workflows` job passes only when the planner did not select it; the `go` output selects both `go` and `protos`. Successful dependencies and other skipped dependencies pass. Every new PR validation job must be included in `ci-result.needs`. The aggregate job runs on Ubuntu for the same PR, main-push and manual-dispatch events.

## Deployment environments

The repository allows exactly two GitHub deployment environments. Do not create more environments, and do not split an environment by app, server, stage or branch.

| Environment    | Deploys                                                                  |
| -------------- | ------------------------------------------------------------------------ |
| `static-sites` | Every static site under `apps/`, including Cloudflare Pages deployments. |
| `servers`      | Every backend service under `servers/`.                                  |

Each deployment job sets `environment` to the environment of its deployable kind. A workflow that deploys both kinds uses separate jobs. Store deployment credentials as secrets of the matching environment, not as repository secrets. PR validation jobs do not reference a deployment environment. A new deployable joins the existing environment of its kind; a deployable of another kind needs a change to this contract first.

`.github/workflows/deploy.yml` is the first workflow that uses both environments. Protection rules of both environments: deployments are allowed only from the `main` branch, and no required reviewers are configured, because a maintainer starts every deployment by hand. Environment secrets:

| Environment    | Secret                      | Use                                                                                                   |
| -------------- | --------------------------- | ----------------------------------------------------------------------------------------------------- |
| `servers`      | `DIGITALOCEAN_ACCESS_TOKEN` | DigitalOcean API token with read and write access to the container registry. It pushes server images. |
| `servers`      | `DIGITALOCEAN_REGISTRY`     | Name of the DigitalOcean Container Registry (the part after `registry.digitalocean.com/`).            |
| `servers`      | `DROPLET_HOST`              | Public IPv4 address or DNS name of the shared Droplet.                                                |
| `servers`      | `DROPLET_SSH_PRIVATE_KEY`   | Private SSH key of the `deploy` user on the Droplet.                                                  |
| `servers`      | `DROPLET_SSH_KNOWN_HOSTS`   | `known_hosts` lines with the SSH host keys of the Droplet. The job accepts no other host key.         |
| `static-sites` | `CLOUDFLARE_API_TOKEN`      | Cloudflare API token with the `Cloudflare Pages: Edit` permission.                                    |
| `static-sites` | `CLOUDFLARE_ACCOUNT_ID`     | Cloudflare account ID of the Pages projects.                                                          |

## Deployment workflow

### Hosting targets

| Deployable kind | Hosting                         | `deploy.target` value |
| --------------- | ------------------------------- | --------------------- |
| Server          | The shared DigitalOcean Droplet | `droplet`             |
| Static site     | Cloudflare Pages                | `cloudflare-pages`    |
| Database        | PlanetScale Postgres            | none                  |

A workspace package is a deployable when its `package.json` has a `deploy` field. Its package name must match `^(?!.*\.\.)[a-z0-9][a-z0-9._-]*$` (no scope and no two consecutive dots), because the workflow uses it in file paths, artifact names and tags, and the release script tags every deployable `<name>@<version>`, which Git rejects as a reference name when it contains `..`. The name of a `droplet` deployable must also be a container image repository name, `^[a-z0-9]+(?:(?:\.|_|__|-+)[a-z0-9]+)*$` (alphanumeric runs joined by one `.`, `_`, `__` or hyphens, with no leading or trailing separator), because the deploy workflow builds its image with `docker build --tag <name>:<sha>`; a `cloudflare-pages` deployable has no image and keeps only the first rule. The name of every other workspace package that a release can include, a package without a `deploy` field, must also form a valid Git tag `<name>@<version>`, because the release step tags every release whose version advances (see the `release` job below): the name must not contain `..`, `@{`, a space, an ASCII control character or one of `~ ^ : ? * [ \`, must not start with `-` or `/`, must not contain `//`, and no `/`-separated component may start with `.` or, except the last one, end with `.lock`. The scope and slash of `@scope/name` stay valid. A deployable that fails its own name rules keeps that diagnostic. The plan fails for a release (including a `none` release) whose name breaks this rule, and `deploy-plan.mjs --check` fails for any workspace package whose name breaks it, so the pull request that adds or renames the package fails before a release can; `--check` skips a non-deployable package whose manifest has no string name. The plan and `deploy-plan.mjs --check` fail with a diagnostic that names the package (or its directory when the manifest has no usable name) and the rule that failed. No two deployables may name the same Droplet service, Droplet host name or Pages project; the plan fails when they do. `deploy.target` selects the hosting target. A `droplet` deployable must be under `servers/` and sets three fields: `deploy.service`, the service name (lowercase letters, digits and inner hyphens, at most 63 characters), which names its container, its Docker network alias and its env file; `deploy.hostname`, the lowercase fully qualified public host name that the reverse proxy routes to it; and `deploy.port`, an integer from 1024 to 65535, the port that the server listens on inside its container. Two services may use the same port, because each container has its own network namespace. A `cloudflare-pages` deployable must be under `apps/` and sets `deploy.project` to its Cloudflare Pages project name, which must match `^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$` (lowercase letters, digits and hyphens, beginning and ending with a letter or digit) because Cloudflare rejects other names only after the build, so the plan and `--check` fail first; the optional `deploy.output` is the build output directory relative to the package and defaults to `dist`; it must name a directory inside the package, not the package root (`""` or `.`) or a path outside it, and it must not contain a control character (including tab, line feed and carriage return), DEL or a backslash, because the deploy workflow carries it through tab-separated and line-separated transports that cannot represent them. A Droplet deployable also has a `Dockerfile` in its package root, reads its listen address from the `ADDR` environment variable and answers `GET /healthz` with a success status when it can serve traffic. The image build context contains only the `Dockerfile`, the package `dist/` directory, `servers/LICENSE` as `LICENSE` and the Go toolchain `LICENSE` as `GO-LICENSE`; the `Dockerfile` copies both license files into the image, so the deployed image carries the FSL-1.1-ALv2 terms and notice and the BSD-3-Clause notice of the statically linked Go standard library and runtime that the [license contract](repository-license-contract.md#distribution) requires.

### Release selection with Changesets

[Changesets](https://github.com/changesets/changesets) (`@changesets/cli`, configured in `.changeset/config.json`) selects the packages of a deployment. Add a changeset with `pnpm changeset` in each pull request whose change must be deployed, and select every changed package and its bump type. Private packages are versioned and tagged (`privatePackages.version` and `privatePackages.tag`); nothing is published to a registry. `delidev` is in the `ignore` list, because `changeset version` would change only its npm manifest and not the Cargo and Tauri versions of the native app. A changeset that lists only `delidev` stays pending and releases nothing; a changeset that lists `delidev` together with another package fails the plan. Remove `delidev` from `ignore` when its native versioning is supported. Changesets adds a dependent of a released package to the release only in some cases. It adds a dependent through `dependencies` or `peerDependencies` with a new version when it must update the dependency range (for example `workspace:*`, with `updateInternalDependencies: patch`). It does not add a dependent whose range still matches the new version (for example `workspace:~` within a 0.x minor version, or `workspace:^` from 1.0.0 on). It adds a dependent only through `devDependencies` with release type `none`, and an explicit `none` changeset has the same effect: the package keeps its version. Do not rely on dependent selection: when a dependent site or server must be rebuilt and deployed, select it in the changeset explicitly. Every listed deployable is deployed, but only releases whose version advances get a tag, because the tag of an unchanged version can already exist.

### Run

A maintainer starts `deploy.yml` from the Actions tab or with `gh workflow run deploy.yml --ref main`. The workflow has only the `workflow_dispatch` trigger and no inputs, and it fails on every ref other than `refs/heads/main`. One deployment runs at a time (concurrency group `deploy`, no cancellation). A dispatch from another ref gets its own concurrency group, so it fails in `plan` without replacing a pending `main` deployment in the queue.

1. `plan` fails when `.github/workflows/deploy.yml` or `scripts/ci/` differs between the dispatch revision and the current `main`, because GitHub runs the workflow file of the dispatch revision while the jobs check out the scripts of the planned revision; start a new deployment in that case. It checks out the current `main` (not the dispatch revision, so a run that waited in the concurrency queue does not see changesets that the previous run consumed), records the deployed revision, runs `changeset status --output` and runs `scripts/ci/deploy-plan.mjs`. The planner reads every workspace package, keeps the releases of the pending changesets, keeps the deployables among them and orders them. Servers come before static sites, because the static sites call the servers. Within one kind, every workspace dependency comes before its dependents. A workspace dependency is an entry in `dependencies`, `devDependencies`, `peerDependencies` or `optionalDependencies` that uses the `workspace:` protocol, including `workspace:<name>@<range>` and relative `workspace:../<directory>` aliases, also through packages that are not selected; pnpm links a workspace package only through that protocol, so plain ranges and registry aliases add no edge; among the packages whose dependencies are already ordered or deployed in an earlier stage, the alphabetically first one comes next. A workspace dependency cycle, an unknown target, a target outside its workspace root or a missing service or project name fails the plan. With no pending changesets, every later job is skipped. The later jobs check out the recorded revision. `plan` also records the Git blob SHA of every planned changeset file. `deploy-servers`, `deploy-static-sites` and `release` run `scripts/ci/check-pending-changesets.sh` at the start, and `scripts/ci/deploy-targets.sh`, which runs both deploy loops and fails when its target list is empty or malformed, runs it again right before each provider upload (after the site build, or after the server image push and before the Droplet deploy step), so a changeset withdrawn while an earlier target deploys or the current target builds stops the upload. A rerun of failed jobs reuses the outputs of the original `plan` job, so this check fails the job when the plan is stale: when `main` no longer contains the planned revision (GitHub compare status other than `identical` or `ahead`), when `main` changed (or renamed away) a `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `.changeset/config.json` since the plan (the release job would then refuse to version and tag the deployment) or changed so many files that the compare list may be truncated (300), when a newer run of `deploy.yml` on `main` has started (status `in_progress` or `completed`; the check reads the run list page by page until it reaches its own run; a newer run whose first attempt still waits in the concurrency queue does not count; a cancelled run, or a rerun that waits in the queue, counts only when a job of one of its attempts started; the check reads every page of the job list), when a planned changeset file is no longer on `main`, or when its blob on `main` differs from the plan. Each check reads the `.changeset` directory of `main` once (the GitHub contents API lists up to 1,000 files; when the listing is full, a planned file that is missing from it is looked up on its own) and compares all planned files locally, so the number of GitHub API requests does not grow with the number of changesets. Start a new deployment instead of rerunning a stale run. Only HTTP 404 means that a changeset is gone; the check retries other GitHub API errors twice (three attempts in total, `CHECK_RETRY_DELAY` seconds apart, 5 seconds by default) and then fails with the API error. The workflow and the `release` job (whose job permissions replace the workflow permissions) have `actions: read` for the run and job lists.
2. `build-servers` checks out the planned revision with Git LFS objects and builds every selected server in parallel, one matrix job per server, with `pnpm exec turbo run build --filter=<package>` and `CGO_ENABLED=0`, `GOOS=linux` and `GOARCH=amd64`. It builds the `linux/amd64` container image `<package>:<revision>` from the build context with `docker build` and uploads it as a compressed `docker save` archive. The job has no deployment environment and no secrets. One failed build stops the run before any deployment; `deploy-servers` also waits for `build-static-sites`, so a failed site build stops the run before the first upload as well.
3. `deploy-servers` (environment `servers`) logs in to DigitalOcean Container Registry with `DIGITALOCEAN_ACCESS_TOKEN` and writes an SSH client configuration for the host alias `droplet` (user `deploy`, the key and pinned host keys from the environment secrets, `StrictHostKeyChecking yes`, `BatchMode yes`). `scripts/ci/deploy-targets.sh servers` then deploys the servers one at a time in plan order. For each server it loads the saved image, pushes it as `registry.digitalocean.com/<registry>/<service>:<revision>`, reads the manifest digest of the pushed tag from the registry (`docker buildx imagetools inspect`) and fails when there is none. After the stale-plan check it runs `scripts/ci/droplet-deploy.sh` on the Droplet with `ssh droplet bash -s -- <service> <image>@<digest> <port> <hostname>`, the script on standard input, so the Droplet always runs the script of the planned revision. That script pulls the image by digest and starts a new container next to the running one, on the `delino` network under the network alias `<service>`, with the env file `/srv/delino/env/<service>.env`, `ADDR=:<port>`, the label `io.delino.service=<service>` and the restart policy `unless-stopped`. It fails before it starts the container when the env file is missing or sets `ADDR`. It waits up to 120 seconds until `GET http://<container-address>:<port>/healthz` returns a success status, and fails at once when the container stops. It then writes the route `/srv/delino/caddy/sites/<service>.caddy` (`<hostname>` to `<service>:<port>`, with a 10-second `lb_try_duration` retry) and reloads Caddy when the route changed. Only then does it stop the old containers of the service (`SIGTERM`, then `SIGKILL` after 30 seconds) and remove them. When the health check or the reload fails, it prints the last 200 log lines of the new container, removes it, restores the previous route and fails; the old container keeps serving. While both containers run, the network alias resolves to both, so the switch drops no request that the retry window covers. The script records the deployed image in `/srv/delino/state/<service>.current` and the image before it in `<service>.previous`, and removes images that no container uses. Its exit code is the deployment verdict.
4. `deploy-static-sites` (environment `static-sites`) runs after the servers, also when no server is selected. The sites build in the separate `build-static-sites` job, which has no deployment environment and no secrets, because the build runs third-party build plugins: it checks out the planned revision with Git LFS objects, builds every selected site in plan order (`deploy-targets.sh build-static-sites`) and uploads only the build output as an artifact. `deploy-static-sites` checks out the planned revision on a fresh runner, installs the locked dependencies with `--ignore-scripts`, unpacks only the planned output directories of that artifact into a directory outside the checkout (`SITES_ROOT`), so the artifact cannot replace a script that runs with the secrets, and fails when the output contains anything other than regular files and directories (Wrangler would follow a symlink), and only uploads and polls; no build code runs next to the Cloudflare and GitHub tokens. The build uses `pnpm exec turbo run build --filter=<package>`; the deploy step uploads the output with `pnpm exec wrangler pages deploy <output> --project-name <project> --branch main`. Wrangler is an exact root `devDependency`, so the lockfile pins it and its dependencies. Wrangler exits 0 also when it cannot determine the final deployment status, so the job uses `scripts/ci/deploy-provider.sh` to read the deployment ID from the `WRANGLER_OUTPUT_FILE_PATH` output and to poll the Cloudflare Pages deployment API until the deployment is in the `production` environment and its `deploy` stage reports `success`. A preview deployment (for example when the project's production branch is not `main`), a `failure` or `canceled` stage, five failed status reads in a row, or 10 minutes without a result fails the job. The Pages projects are Direct Upload projects with `main` as the production branch.
5. `release` runs `scripts/ci/deploy-release.sh` only when every selected deployment succeeded, also when the pending changesets contain only `none` releases. When `changeset version` changes nothing (only changesets of ignored packages are pending), it creates no commit or tag. Otherwise it runs `changeset version`, which consumes the deployed changesets and writes the versions and changelogs, and then `pnpm install --lockfile-only`, because a new version can change a `workspace:<version>` range. It commits the result as `chore(release): version deployed packages` on top of the deployed revision and creates an annotated `<package>@<version>` tag on that version commit for every release whose version advances; an existing tag fails the job. The plan has already checked that every release name forms a valid Git tag (see the package name rules above), so a name that Git rejects fails the plan, not this job. Each tag therefore holds exactly the deployed tree plus the version files, and the tag message records the deployed revision. The job pushes the version commit to `main` and the tags in one atomic push. The push carries a lease on the expected `main` tip (first the deployed revision), so a `main` that was rewound or rewritten is never fast-forwarded back. When the push is rejected because `main` moved forward from the deployed revision, it first checks that every planned changeset is unchanged on the fetched `main` and that no package manifest, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `.changeset/config.json` changed since the deployed revision (either case fails the job without a push and needs a new deployment), then cherry-picks the version commit onto the new `main` and tries again, up to three attempts in total; changesets merged during the deployment stay pending. In that case `main` gets the cherry-picked copy, and the tags stay on the original version commit, which is not part of the `main` history. Any other rejection, such as a ruleset denial or an existing remote tag, fails the job at once.

The `release` job pushes with `GITHUB_TOKEN` and `contents: write`. A branch ruleset on `main` must allow GitHub Actions to push the version commit. Pushes with `GITHUB_TOKEN` do not start other workflows, so `CI.yml` does not run for the version commit. Deployment does not roll back: when a later deployable fails, the earlier deployables of the run stay deployed, no version commit or tag is pushed, and the next run deploys the same changesets again.

The PlanetScale Postgres database has no job in the workflow. The database stage comes before the servers. Add it together with the migration tool that the owning server contract selects.

`scripts/ci/deploy-plan.test.mjs` covers the planner. `scripts/ci/deploy-scripts.test.mjs` covers the stale-plan check against a stubbed `gh`, the provider helper against a stubbed `curl`, the deploy loops against stubbed CLIs (including a changeset withdrawn during a build), the Droplet deploy script against stubbed `docker` and `curl` (health check failure, a stopped container, a rejected route and invalid arguments or env files), the Caddy start script against a stubbed `docker` (a missing, running, stopped or different-image container and a failing Docker command), and the release script against a local bare remote, including a moved, rewound or manifest-changing `main`, an existing tag, `none` releases and ignored packages. Both run in `pnpm test:tooling`. The deploy shell scripts need Bash 4.4 or newer and refuse to run on older Bash; their fixtures are skipped there (for example on the Bash 3.2 that macOS ships). The provider wait commands also need GNU coreutils `timeout` (or `gtimeout`); their fixtures are skipped without it. The deploy fixtures also need `jq`, which the Ubuntu runners provide, and are skipped without it.

The job summaries record the deployed revision, the ordered deployables, the Droplet services, host names and image digests, the Pages projects and deployment IDs, the version commit on `main`, the tagged version commit and the tags. Each deploy job reads only the secrets of its own environment.

### Droplet

Every server runs as a container on one shared DigitalOcean Droplet (Ubuntu 24.04 LTS, `linux/amd64`). The Droplet also runs the Caddy reverse proxy container, which listens on TCP ports 80 and 443 and UDP port 443, terminates TLS with automatic Let's Encrypt certificates for every route host name and forwards plain HTTP/1.1 to the server containers on the `delino` Docker network. The deployment publishes no other host ports; a server that needs another public port (for example UDP for STUN) needs a change to this contract and to `scripts/ci/droplet-deploy.sh` before its first deployment.

Provision a new Droplet once:

1. Create the Droplet and a DigitalOcean Cloud Firewall that allows inbound TCP 22, TCP 80, TCP 443 and UDP 443 and denies all other inbound traffic. SSH stays open to all addresses, because GitHub-hosted runners have no fixed addresses; the `deploy` user accepts only its key.
2. Point the DNS record of every server host name to the Droplet address.
3. Run `scripts/droplet/provision.sh <deploy-public-key-file> <acme-email>` as root on the Droplet. It installs Docker Engine from the Docker apt repository, sets the `local` log driver (rotated logs), creates the `deploy` user with the given key as its only `authorized_keys` entry (`restrict` option) and adds it to the `docker` group, creates `/srv/delino` (`env/` with mode 0700, `caddy/`, `caddy/sites/`, `state/`), writes `/srv/delino/caddy/Caddyfile` (ACME email and `import sites/*.caddy`), creates the `delino` network and then runs `scripts/droplet/start-caddy.sh` with the digest-pinned Caddy image, which keeps the certificates in the `caddy-data` volume. The script can run again, and `start-caddy.sh` handles the Caddy container in three cases: when the container is missing or uses another image than the pinned one, it removes the container if present and creates it (the only case that recreates it); when the container has the pinned image and is stopped (as after `docker stop`), it starts the container without recreating it; and when the container has the pinned image and is running, it reloads the configuration without recreating it. A failing `docker run`, `docker start` or `docker exec` makes `provision.sh` exit non-zero with the Docker diagnostic. Membership in the `docker` group is equivalent to root access on the Droplet, so the `deploy` private key is a production root credential.
4. As the `deploy` user, run `docker login registry.digitalocean.com` with a DigitalOcean API token that has read access to the registry, so that the Droplet can pull server images.
5. Create `/srv/delino/env/<service>.env` (mode 0600, owner `deploy`) for every server, with the configuration and secrets that its server contract lists, before its first deployment. The env file must not set `ADDR`.
6. Store the `servers` environment secrets. Get the host keys for `DROPLET_SSH_KNOWN_HOSTS` from the Droplet console (`/etc/ssh/ssh_host_*_key.pub`), not from an unverified network scan.

Roll a service back with the image in `/srv/delino/state/<service>.previous`: run `ssh deploy@<droplet> bash -s -- <service> <image> <port> <hostname> < scripts/ci/droplet-deploy.sh` from a checkout of `main`. The rollback uses the same health check and switch as a deployment; it does not change versions or tags. Delete old images from the registry with the DigitalOcean registry garbage collection when the registry storage limit requires it, and keep the images in the `.current` and `.previous` state files of every service.

## Assets and licensing

Every repository-owned `dist` directory is ignored generated output and must be removed after validation. Assets at least 512 KiB require exact-path Git LFS attributes and hydration before use. There are no LFS assets yet.
