# Repository Workflow Contract

## Scope

The repository contains shared instructions, skills, documentation templates, formatting infrastructure, two static Rspress sites ([`delino-site`](project-delino-site.md) and [`delino-docs`](project-delino-docs.md)) and the [`delino-accounts`](project-delino-accounts.md) project with an Rsbuild web app and a Go API server, the shared React UI component package [`delino-ui`](project-delino-ui.md), and the [`delidev`](project-delidev.md) desktop and mobile app with a Tauri app crate. The root `Cargo.toml` defines the Rust workspace; its only member is `apps/delidev/src-tauri`. The repository has no generated protocol bindings. `.github/workflows/deploy.yml` deploys the servers and static sites according to the [deployment workflow](#deployment-workflow) below and uses only the [deployment environments](#deployment-environments) below.

## Agent skills

`.agents/skills/` owns the shared workspace-local agent skills. `.claude/skills` is a tracked relative symlink to `../.agents/skills` so that Claude Code discovers the same skills as Codex. Add, edit and remove skills only in `.agents/skills/`; do not replace the symlink with a copy or add Claude-only skill directories. Checkouts on platforms without symlink support (for example, Windows without `core.symlinks`) get a plain file instead and do not expose the skills to Claude Code.

## Installation

Use Node.js 24 from `.nvmrc` and pnpm 10.26.2 from `package.json`. The Go toolchain selected by the root `go.mod` (Go 1.26.1 or later) is also a prerequisite for the root `pnpm build`, `pnpm dev`, `pnpm lint` and `pnpm test` tasks, because they include `servers/accounts-api`, whose package scripts call `go`. Rust code uses the toolchain named in root `rust-toolchain` through rustup and the root Cargo workspace; root `cargo test` runs its tests. The workspace builds the CEF runtime of `delidev`, so it needs the Linux packages, macOS and Windows tools and the disk space listed in the [delidev contract](apps-delidev-foundation.md#build-and-test); the first build downloads the CEF distribution. Rust is not a prerequisite of the root pnpm tasks, because no package script calls `cargo`. Git 2.32 or newer is a local prerequisite for `pnpm test:tooling`: the `scripts/ci` fixtures isolate fixture repositories from the developer's global Git configuration with `GIT_CONFIG_GLOBAL`, which older Git ignores, so they fail with a clear error that names the found version on older Git. All Go code belongs to the single root module `github.com/delinoio/mono`; nested `go.mod` and `go.work` files are not used. Run `pnpm install --frozen-lockfile`. The prepare script installs Lefthook through `scripts/install-git-hooks.sh`. Archives without Git metadata skip hook installation, including archives extracted inside another Git work tree, because the installer runs only when the project directory is the root of its own work tree. Linked worktrees may use their shared Git hooks directory; unrelated custom hook paths remain protected. A missing custom hook path stays protected when the installer runs under `sh`, `dash` or `bash`, including `bash --posix`. In the shared hooks directory the installer forces the Lefthook installation, which disables Lefthook's protection of an existing `pre-commit.old` backup. The installer therefore exits with an error that names both files, and leaves them unchanged, when `pre-commit` is not managed by Lefthook and `pre-commit.old` already exists. Move or merge one of the two files and run the installer again. A Lefthook-managed `pre-commit` with an existing backup, a backup without a current hook, and a custom hook without a backup are installed as before; the custom hook becomes the backup.

## Task orchestration

The pinned `turbo` dependency and root `turbo.json` orchestrate packages selected by `pnpm-workspace.yaml`: `apps/*`, `packages/*` and `servers/*`. The workspace packages are `apps/delino-site`, `apps/delino-docs`, `apps/delino-accounts`, `apps/delidev`, `packages/delino-ui` and `servers/accounts-api`; commands only run tasks that exist in package scripts. Go server packages wrap the Go toolchain in their package scripts and disable Turbo caching for their tasks because the toolchain and module cache are not declared inputs.

Root `pnpm build`, `pnpm dev`, `pnpm lint`, `pnpm typecheck` and `pnpm test:e2e` delegate to `turbo run`. The `test:e2e` task runs app end-to-end suites, is uncached and declares its pass-through environment according to the [e2e contract](repository-e2e-contract.md). Root `pnpm test` runs workspace tests and the repository-wide `test:tooling` task. The latter runs the existing formatter and hook fixtures directly and is registered as `//#test:tooling`. It is uncached so each invocation checks the current Git and hook environment. `prepare`, `format` and `format:check` remain direct commands: hook installation has side effects, and formatting depends on Git revisions, staged changes and untracked files rather than package inputs.

Root `pnpm dev` starts all workspace development servers together through the unfiltered `turbo run dev` command. Each workspace package that owns a development server exposes it through its `dev` script. Packages without a development server do not need a `dev` script. Package-specific development is available through an explicit filtered command; the root command always selects all packages. It currently starts the Rspress development servers of `delino-site` and `delino-docs`, the Rsbuild development servers of `delino-accounts` and the `delidev` frontend, and the `accounts-api` Go server. Root `pnpm dev` does not start the `delidev` native shell; use `pnpm --filter delidev tauri dev` for it.

Define each workspace task in its owning `package.json`. Declare workspace dependencies so Turbo can order tasks: builds depend on dependency builds, tests depend on dependency builds, and lint and typecheck tasks depend on their corresponding dependency tasks. Build output defaults to `dist/**`; packages with other outputs must override them in a package-local `turbo.json` that extends `//`. Declare any additional test reports or incremental compiler outputs there. Development tasks are persistent and uncached.

Turbo uses strict environment mode by default. Package contracts and package-local task configuration must declare environment variables, ignored configuration inputs and shared root inputs that affect results before enabling their caching. Keep side-effecting or environment-dependent tasks uncached when their inputs cannot be fully declared. Do not route Git-sensitive formatting through cached tasks or pass credentials through global environment wildcards. Development tasks pass the configuration variables that their owning package contract defines through task-level `passThroughEnv` in that package's `turbo.json`, so root `pnpm dev` honors shell-provided values like the package-specific commands. Use `passThroughEnv`, not `env`, so the values stay out of the hashes of these uncached tasks, and list only variables of the package that owns the task. Add a variable that a development server reads to the owning package's `turbo.json` in the same change. The `scripts/ci/turbo-env.test.mjs` fixture checks the resolved `dev` task definitions with a Turbo dry run. Remote caching is not configured. `.turbo/` is ignored local state; generated `dist` directories remain subject to the cleanup rule below.

For a package subset, use `pnpm exec turbo run <task> --filter=<package>`. Use `pnpm exec turbo run <task> --dry=json` to inspect the graph without running tasks. Root-only fixture execution is also available as `pnpm test:tooling`. New runtime projects must add their own contracts and package scripts before these commands can establish runtime acceptance.

## Formatting

Root `pnpm format` writes fixes and `pnpm format:check` checks without rewriting. Both use pinned Rstack and `rstack.config.ts`. The formatter resolves the repository root with `git rev-parse --show-toplevel` and uses it for every selector, the shared-exclusion probe and the Rstack run, so starting `scripts/ci/format-changed.mjs` from a subdirectory selects and formats the same repository-wide files as starting it from the root. Default local selection compares the merge base of `origin/main` and HEAD, including staged changes, working changes and untracked files. Explicit `--base <sha> --head <sha>` arguments select that committed comparison. Local `--all` selects existing tracked files, each path once in sorted order even when a conflicted merge leaves it unmerged in several index stages. Before the first commit, use `--staged`. Every selector matches the supported file extensions case-insensitively, so `notes.MD`, `Component.TSX` and `data.JSON` are selected like their lowercase spellings; the shared exclusions still decide which selected paths Rstack skips. The Lefthook glob needs no uppercase variants because Lefthook matches it case-insensitively on Linux (checked with Lefthook 2.2.2); macOS behavior is unchecked, and the script filter stays the authoritative one. A checkout whose own path is not valid UTF-8 cannot be used as the repository root, because that path cannot be passed to a child process: the formatter fails before it selects any file with a `ci_format_error` that names the checkout path with each invalid byte escaped as `\xNN` and asks to move or rename the checkout.

Lefthook runs `node scripts/ci/format-changed.mjs --staged --write` with `stage_fixed: true`. It preserves unstaged edits, supports initial commits and rejects parser failures. The hook supports `git add` followed by a plain `git commit`, `git commit -a` and `git commit -i`, including from a linked worktree; each formats the staged content and stages the fixes in the same commit. Git runs the hook of a pathspec commit (`git commit <path>`, `git commit --only` and `git commit --amend <path>`) against a throwaway `next-index-*.lock` index and later writes the real index from its own pre-hook snapshot, so a fix staged by the hook would leave HEAD formatted and the real index stale (`MM`). The formatter therefore detects that index through `GIT_INDEX_FILE` and runs the staged selection in check mode without writing or staging. It passes when nothing needs formatting and otherwise exits 2 with a `ci_format_error` that tells the user to run `git add` on the files and a plain `git commit`; because check mode also exits non-zero for parser failures, the message covers both causes. A pathspec run stopped by `SIGTERM`, `SIGINT` or `SIGHUP` keeps the `128 + signal` exit code (143, 130 or 129) with only the `ci_format_signal` event and is not reported as a formatting or parser failure. Select files with NUL-separated Git paths, skip deletions, symlinks and gitlinks, and preserve imported skills, generated files and lockfiles through shared exclusions. Staged deletions, staged paths with an unsupported extension, staged paths recorded as symlinks (mode `120000`) or gitlinks (mode `160000`, which have no blob to format) and staged paths that the shared exclusions skip (for example a skip-worktree lockfile removed from the working tree; Rstack evaluates the exclusions for a path that does not exist on disk through `--stdin-filepath`) are skipped even when their working-tree path is missing, as the unstaged selectors skip them. Every such exemption applies before the missing-path failure, but a staged added, modified, renamed or type-changed formattable path that is missing from the working tree (removed after `git add`, behind a replaced parent directory or outside a sparse checkout) fails the hook with a `ci_format_error` naming the path, so a staged blob cannot bypass formatting. The same failure applies to a staged added, modified, renamed or type-changed formattable path that exists in the working tree as a non-regular entry, such as a directory that replaced the file, a symlink that the index does not record as one, a FIFO, a socket or a device: the `ci_format_error` names the path and the observed entry type, and the path is skipped silently only when the shared exclusions skip it. Git path lists are read as bytes and each name is checked with `node:buffer` `isUtf8` (not a fatal `TextDecoder`, which would strip a leading byte order mark from a valid name), because Rstack cannot address a file name that is not valid UTF-8. A staged or explicit-comparison (`--base`/`--head`) added, modified, renamed or type-changed formattable path that is present but whose name is not valid UTF-8 (for example the Latin-1 name `caf\xe9.ts` on Linux) fails with a `ci_format_error` that names the path with each invalid byte escaped as `\xNN`, states that the name is not valid UTF-8 and asks for a rename, instead of reporting the path as missing from the working tree. This check runs after the unsupported-extension, symlink, gitlink and shared-exclusion exemptions (the exclusion probe uses the lossy name, which keeps the valid directory prefixes), so those paths stay silent skips, and an explicit-comparison path that the range deletes stays skipped. The planner does not run the exclusion probe, because it runs without installed dependencies and cannot evaluate the shared exclusions: it selects formatting for such a present formattable path, and the `quality` job's formatter gives the verdict, skipping the path when the shared exclusions skip it and otherwise failing with the `ci_format_error` described above. An explicit-comparison formattable path that the range changes and the validation index tracks but whose working-tree entry is gone (removed, behind a replaced parent directory or a symlink loop, or outside a sparse checkout) is skipped when the shared exclusions skip it, as the staged and default local selectors skip it, and otherwise fails with a `ci_format_error` naming the path, because the comparison validates the full checkout. The planner does not run the exclusion probe, because it runs without installed dependencies and cannot evaluate the shared exclusions: it selects formatting for such a present formattable path, and the `quality` job's formatter gives the verdict, skipping the path when the shared exclusions skip it and otherwise failing with the `ci_format_error` described above. Selectors compare paths by their bytes, not by a lossy decoding: each byte that is not part of a valid UTF-8 sequence is held as a distinct escaped value, so a name that is not valid UTF-8 never equals the valid name that contains U+FFFD in its place. A rename from the raw `caf\xe9.ts` to the valid `caf�.ts` therefore selects the valid replacement, and the deleted or exempt raw name neither marks the replacement as invalid nor exempts it. `--all` and default local changed-file selection keep skipping such a path silently; this is a documented limitation until Rstack can format such names. The checkout path itself is subject to the same limitation. Linux file systems hold these names; APFS and Windows reject or normalize them, so the fixtures skip there. Unstaged deletions in `--all` and local changed-file selection stay skipped. Every selector (`--staged`, `--all`, explicit comparison and default local) skips a path that the validation index records as a symlink (mode `120000`) or a gitlink (mode `160000`), even when the checkout materialized it as a regular file (a symlink on Windows without symlink support or with `core.symlinks=false`, or a gitlink replaced by a regular file), so the placeholder bytes and the recorded mode stay unchanged. The mode comes from the current index (`git ls-files --stage -z`), never from the comparison head, and works before the first commit.

CI requires an explicit comparison and rejects local `--staged` and `--all` modes. Outside CI, the formatter also rejects `--all` combined with `--base`, `--head`, `TURBO_SCM_BASE` or `TURBO_SCM_HEAD`: it exits with status 2 and a `ci_format_error` before it selects or rewrites any file, because `--all` has no comparison to honor. An unset, empty or case-insensitive `false` CI value means local execution; every other nonempty value enables CI restrictions.

## Validation

Run `pnpm test` for formatter, hook and change-planning fixtures. CI plans affected fixtures and formatting on Ubuntu for pull requests, main pushes and manual dispatch. The `quality` job runs plain `pnpm format:check` with `TURBO_SCM_BASE` and `TURBO_SCM_HEAD` set to the resolved comparison; the formatter reads that environment as the explicit comparison. The `--base <sha> --head <sha>` arguments are the equivalent local form and select the same files. PR comparisons use the pull request base and head. Push comparisons use the prior and current commits. Manual comparisons use the merge base with `origin/main`; an optional `base` input selects another existing revision. A root push has no previous commit, so CI creates a local empty-tree comparison commit without pushing it. No full manual mode or macOS runners are configured.

The `changes` job resolves that comparison and runs `scripts/ci/plan.mjs` without installing dependencies. It publishes `base`, `head`, `format`, `fixtures`, `quality`, `go`, `rust` and `e2e` outputs. Formatting uses the existing formatter's changed-file selection; Rstack still owns exclusions, so a change that touches only a supported file with an uppercase or mixed-case extension (for example `notes.MD`) still publishes `format: true`. A present formattable path whose name is not valid UTF-8 and a formattable path that the comparison changes but that is missing from the working tree also publish `format: true` without an exclusion probe; the `quality` job's formatter decides whether the shared exclusions skip it or it fails. When the planner fails, for example because a comparison revision does not exist or the comparison is unset or malformed, it prints one `ci_format_error` record on stderr like the formatter, exits with code 2, prints no `ci_plan` record and writes no outputs and no summary record, and the `changes` job fails, which fails `ci-result`. Fixtures run for changes, deletions or renames affecting `scripts/ci/`, `scripts/install-git-hooks.sh`, `.github/workflows/CI.yml`, `.nvmrc`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `rstack.config.ts`, `lefthook.yml`, any `turbo.json` (the root file or a workspace package file) or the `package.json` placed directly inside a workspace package under `apps/`, `packages/` or `servers/`. Adding, removing or renaming a workspace package changes the packages that the Turbo fixtures resolve, so a nested `package.json` deeper in a package does not select fixtures. In pull request and manual comparisons, documentation-only changes select formatting without fixtures. The `quality` job runs when either check is selected, and on every push to `refs/heads/main` because the planner always selects fixtures there, and passes the exact comparison to formatting. In pull request and manual comparisons, empty comparisons or changes with no validation inputs skip `quality`. The `go` output is selected when a changed, deleted or renamed path is a `.go` file, `go.mod` or `go.sum`, and for every `push` event to `refs/heads/main` regardless of the comparison. The `rust` output is selected when a changed, deleted or renamed path is a `.rs` file, a `Cargo.toml` or `Cargo.lock` at any depth, root `rust-toolchain` or `.rustfmt.toml`, or any path inside a `src-tauri/` directory (a Tauri crate compiles its configuration, capabilities and icons into the binary), and for every `push` event to `refs/heads/main` in the same way. The `fixtures` and `e2e` outputs are selected for every `push` event to `refs/heads/main` regardless of the comparison in the same way, which also runs `quality`. Branch-wide cancellation can cancel a main-push run before its Go, Rust, fixtures or e2e jobs finish, and the next push compares only against its own parent, so the planner reads the runner-provided `GITHUB_EVENT_NAME` and `GITHUB_REF` and runs the Go checks, the Rust checks, the fixtures and the e2e suites against each main-push head; a later documentation-only push therefore cannot pass `ci-result` with Go, Rust, fixtures or e2e skipped. Pull request and manual comparisons keep affected selection, and the other outputs are unchanged. The `format` output stays derived from the comparison for every event, so this selection does not cover formatting that a cancelled main-push run lost: the formatter still compares only the range of the surviving push. The planner logs the reasons in the `goReason`, `rustReason`, `fixturesReason` and `e2eReason` fields (`diff` or `main-push`) of its record without publishing them as outputs; `main-push` means the output is true only because of the main push and the comparison alone did not select it. The `go` job then runs `gofmt -l` on tracked `.go` files and `go vet ./...` and `go test ./...` in the root Go module, and records the result in the job summary. The `rust` job installs `pkg-config` and `libgtk-4-dev`, installs the `rust-toolchain` toolchain with `rustfmt` and `clippy`, runs `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings` and `cargo test --workspace --locked` in the root Cargo workspace on the Linux desktop target, and records the result in the job summary. It downloads the CEF distribution on every run because CI has no cache. It does not run `tauri build`, launch the app or build the macOS, Windows, Android or iOS targets. The `e2e` output is selected when a changed, deleted or renamed path is inside an `apps/<app>/` package, or is `.github/workflows/CI.yml`, `.nvmrc`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` or `turbo.json`. The `e2e` job installs Chromium and runs every app suite with `pnpm test:e2e`, as the [e2e contract](repository-e2e-contract.md#ci) describes. It reads the `AI_GATEWAY_API_KEY` repository secret and excludes tests tagged `agent` when the secret is not available. The planner records the checkout revision, comparison and selections in logs and the job summary. New shared validation dependencies must update the planner inputs.

Each CI run records the validation revision, comparison revisions, commands and results in its logs and job summary. Runtime and platform acceptance must be added with the owning project. CI does not build `delidev` bundles or mobile targets. CI runs the e2e suites of `delino-site`, `delino-docs` and `delino-accounts` against their development servers. CI does not build these apps or run the `delino-accounts` or `delino-ui` unit tests; the [deployment workflow](#deployment-workflow) builds and deploys them. Passing shared fixtures does not establish runtime or release acceptance.

The `ci-result` job aggregates validation through `needs`, including `changes`, `quality`, `go`, `rust` and `e2e`. It runs with `always()` so dependency failures do not skip the aggregate check. Failed or cancelled dependencies fail `ci-result`. The `changes` job must succeed; a skipped `quality`, `go`, `rust` or `e2e` job passes only when the planner did not select it. Successful dependencies and other skipped dependencies pass. Every new PR validation job must be included in `ci-result.needs`. The aggregate job runs on Ubuntu for the same PR, main-push and manual-dispatch events.

## Deployment environments

The repository allows exactly two GitHub deployment environments. Do not create more environments, and do not split an environment by app, server, stage or branch.

| Environment    | Deploys                                                                  |
| -------------- | ------------------------------------------------------------------------ |
| `static-sites` | Every static site under `apps/`, including Cloudflare Pages deployments. |
| `servers`      | Every backend service under `servers/`.                                  |

Each deployment job sets `environment` to the environment of its deployable kind. A workflow that deploys both kinds uses separate jobs. Store deployment credentials as secrets of the matching environment, not as repository secrets. PR validation jobs do not reference a deployment environment. A new deployable joins the existing environment of its kind; a deployable of another kind needs a change to this contract first.

`.github/workflows/deploy.yml` is the first workflow that uses both environments. Protection rules of both environments: deployments are allowed only from the `main` branch, and no required reviewers are configured, because a maintainer starts every deployment by hand. Environment secrets:

| Environment    | Secret                  | Use                                                                |
| -------------- | ----------------------- | ------------------------------------------------------------------ |
| `servers`      | `RAILWAY_TOKEN`         | Railway project token of the production environment.               |
| `static-sites` | `CLOUDFLARE_API_TOKEN`  | Cloudflare API token with the `Cloudflare Pages: Edit` permission. |
| `static-sites` | `CLOUDFLARE_ACCOUNT_ID` | Cloudflare account ID of the Pages projects.                       |

## Deployment workflow

### Hosting targets

| Deployable kind | Hosting              | `deploy.target` value |
| --------------- | -------------------- | --------------------- |
| Server          | Railway              | `railway`             |
| Static site     | Cloudflare Pages     | `cloudflare-pages`    |
| Database        | PlanetScale Postgres | none                  |

A workspace package is a deployable when its `package.json` has a `deploy` field. `deploy.target` selects the hosting target. A `railway` deployable must be under `servers/` and sets `deploy.service` to its Railway service name. A `cloudflare-pages` deployable must be under `apps/` and sets `deploy.project` to its Cloudflare Pages project name; the optional `deploy.output` is the build output directory relative to the package and defaults to `dist`. A Railway deployable also has a `Dockerfile` and a `railway.json` in its package root. The Railway build context contains only these two files and the package `dist/` directory.

### Release selection with Changesets

[Changesets](https://github.com/changesets/changesets) (`@changesets/cli`, configured in `.changeset/config.json`) selects the packages of a deployment. Add a changeset with `pnpm changeset` in each pull request whose change must be deployed, and select every changed package and its bump type. Private packages are versioned and tagged (`privatePackages.version` and `privatePackages.tag`); nothing is published to a registry. Each release lists the internal dependents of the released package. A dependent through `dependencies` or `peerDependencies` gets a new version (`updateInternalDependencies: patch`). A dependent only through `devDependencies` is listed with release type `none`, and an explicit `none` changeset has the same effect: the package keeps its version. Every listed deployable is deployed again, but only releases whose version advances get a tag, because the tag of an unchanged version can already exist.

### Run

A maintainer starts `deploy.yml` from the Actions tab or with `gh workflow run deploy.yml --ref main`. The workflow has only the `workflow_dispatch` trigger and no inputs, and it fails on every ref other than `refs/heads/main`. One deployment runs at a time (concurrency group `deploy`, no cancellation).

1. `plan` checks out the current `main` (not the dispatch revision, so a run that waited in the concurrency queue does not see changesets that the previous run consumed), records the deployed revision, runs `changeset status --output` and runs `scripts/ci/deploy-plan.mjs`. The planner reads every workspace package, keeps the releases of the pending changesets, keeps the deployables among them and orders them. Servers come before static sites, because the static sites call the servers. Within one kind, every workspace dependency (`dependencies`, `devDependencies`, `peerDependencies` and `optionalDependencies`) comes before its dependents; ties use alphabetical order. A workspace dependency cycle, an unknown target, a target outside its workspace root or a missing service or project name fails the plan. With no pending changesets, every later job is skipped. The later jobs check out the recorded revision.
2. `build-servers` builds every selected server in parallel, one matrix job per server, with `pnpm exec turbo run build --filter=<package>` and `CGO_ENABLED=0`, `GOOS=linux` and `GOARCH=amd64`. It uploads the build context as a tar archive, which keeps the executable mode. One failed build stops the run before any deployment.
3. `deploy-servers` (environment `servers`) deploys the servers one at a time in plan order with `railway up <context> --path-as-root --no-gitignore --ci --service <service>`. The `--ci` mode waits for the deployment result and fails on a failed build or deployment. Railway runs the `railway.json` health check before it switches traffic.
4. `deploy-static-sites` (environment `static-sites`) runs after the servers, also when no server is selected. It builds each selected site in plan order with `pnpm exec turbo run build --filter=<package>` and uploads the output with `wrangler pages deploy <output> --project-name <project> --branch main`. The Pages projects are Direct Upload projects with `main` as the production branch.
5. `release` runs only when every selected deployment succeeded, also when the pending changesets contain only `none` releases. It runs `changeset version`, which consumes the deployed changesets and writes the versions and changelogs, and then `pnpm install --lockfile-only`, because a new version can change a `workspace:<version>` range. It commits the result as `chore(release): version deployed packages`, creates an annotated `<package>@<version>` tag on that commit for every release whose version advances and pushes the commit to `main` and the tags in one atomic push. When the push is rejected because `main` moved during the deployment, it cherry-picks the same version commit onto the new `main` and tries again, up to three attempts in total; changesets merged during the deployment stay pending. Any other rejection, such as a ruleset denial or an existing tag, fails the job at once. The tag message records the deployed revision.

The `release` job pushes with `GITHUB_TOKEN` and `contents: write`. A branch ruleset on `main` must allow GitHub Actions to push the version commit. Pushes with `GITHUB_TOKEN` do not start other workflows, so `CI.yml` does not run for the version commit. Deployment does not roll back: when a later deployable fails, the earlier deployables of the run stay deployed, no version commit or tag is pushed, and the next run deploys the same changesets again.

The PlanetScale Postgres database has no job in the workflow. The database stage comes before the servers. Add it together with the migration tool that the owning server contract selects.

The job summaries record the deployed revision, the ordered deployables, the Railway services, the Pages projects, the version commit and the tags. Each deploy job reads only the secrets of its own environment.

## Assets and licensing

Every repository-owned `dist` directory is ignored generated output and must be removed after validation. Assets at least 512 KiB require exact-path Git LFS attributes and hydration before use. There are no LFS assets yet.

## Dependency updates

Renovate extends `github>delinoio/renovate-config`. Ordinary updates and lockfile maintenance use Monday 00:00–04:00 in `Asia/Seoul`; vulnerability updates retain the inherited immediate security policy. Follow the dependency security contract and retain unresolved findings in pull requests, Linear issues or CI records.
