# Repository Environment Contract

## Configuration ownership

The public repository contains no secret values, Infisical project identifiers or production credentials. Infisical is the secret provider for local development only, as [Local development injection](#local-development-injection) describes; deployed servers keep reading the env files that the [deployment workflow](repository-workflow-contract.md#deployment-workflow) describes. Each service defines its configuration schema, validation, local defaults and credential boundaries in its domain contract. The [`accounts-api` contract](servers-accounts-api-foundation.md) owns the API server configuration, and the [`delino-accounts` web app contract](apps-delino-accounts-foundation.md) owns the web app build configuration.

Servers under `servers/` read their runtime configuration from environment variables without a project or service prefix, for example `DATABASE_URL`, `LOGTO_ISSUER` and `CORS_ORIGINS`, not `OWNSAND_DATABASE_URL`. Each server runs as its own process with its own environment, so a prefix adds no isolation. This rule applies to the configuration that a deployed server reads. It does not apply to command-line tools, device-side programs, SDKs or web app builds, which share an environment with other programs, or to the variables that opt in to tests.

## Local state

Never commit `.infisical.yaml`, `.infisical.json`, `.dev-environment/`, real `.env` files or user, production, release and signing credentials. Service-local `.env.example` files may contain names, validation guidance, placeholders and safe loopback defaults only. Do not add a root environment example.

## Local development injection

Package `dev` scripts that read configuration run their development command through the shared launcher `scripts/dev/with-infisical.mjs`:

```sh
node ../../scripts/dev/with-infisical.mjs --path=/<folder> -- <command> [args...]
```

| Package           | Directory              | `dev` command after `--`                               | Infisical folder        |
| ----------------- | ---------------------- | ------------------------------------------------------ | ----------------------- |
| `accounts-api`    | `servers/accounts-api` | `node scripts/dev.mjs`                                 | `/servers/accounts-api` |
| `ownsand-api`     | `servers/ownsand-api`  | `node scripts/dev.mjs`                                 | `/servers/ownsand-api`  |
| `sandrun-api`     | `servers/sandrun-api`  | `node scripts/dev.mjs`                                 | `/servers/sandrun-api`  |
| `delino-accounts` | `apps/delino-accounts` | `node node_modules/portless/dist/cli.js run --prefix=` | `/apps/delino-accounts` |
| `ownsand-console` | `apps/ownsand`         | `node node_modules/portless/dist/cli.js run --prefix=` | `/apps/ownsand`         |
| `sandrun-console` | `apps/sandrun`         | `node node_modules/portless/dist/cli.js run --prefix=` | `/apps/sandrun`         |

The Infisical folder of a package is its directory relative to the repository root, with a leading `/`. The folder tree therefore mirrors the repository layout: `/servers/` holds server folders and `/apps/` holds frontend folders. The folder follows the directory, not the package name; for example, `ownsand-console` lives in `apps/ownsand` and uses `/apps/ownsand`. When a package directory moves or is renamed, move its Infisical folder and update `--path` in the same change.

For the frontends behind portless (see [Frontend development URLs](#frontend-development-urls)), the launcher wraps portless in `dev`, not the `dev:app` script: portless reads the `dev:app` script text to add `--port` and `--host` to `rsbuild dev`, and a launcher command in front of `rsbuild` would stop that detection. The injected variables reach `dev:app` through the environment of portless, also with `PORTLESS=0`. Running `dev:app` alone does not inject them.

`delino-site`, `delino-docs` and the `delidev` frontend read no configuration that Infisical supplies, so their `dev` scripts do not use the launcher. A package that starts to read configuration adds the launcher with its own folder, the package directory as described above, in the same change, and adds a row to this table.

Injection mode:

- `infisical`: the repository root contains `.infisical.yaml`, the Infisical CLI project configuration. The launcher does not read the `.infisical.json` file that older CLI versions write. The launcher runs `infisical export --env=dev --path=<folder> --format=json --silent --log-level=warn --log-destination=stderr` in the repository root, where the CLI finds the project configuration, with no standard input. It then starts the command with the fetched variables added over the inherited environment. The fetched values stay in the launcher's memory; the launcher writes no file. Injection is then required: when the CLI is not on `PATH`, the user is not logged in (the CLI cannot ask interactively without standard input) or the fetch fails or prints output that is not the JSON array of the `export` command, the launcher exits with status 1 and the development command does not start.
- `direct`: no project configuration exists. The launcher runs the command directly with the inherited environment and logs a `dev_env_direct` record. A checkout without Infisical access, for example an external contributor's, uses this mode with shell variables and the service-local files that the owning contract documents.

Setup for maintainers with access to the development project:

1. Install the [Infisical CLI](https://infisical.com/docs/cli/overview) and run `infisical login` against the team's Infisical instance.
2. Run `infisical init` in the repository root and select the development project. Use a CLI version that writes `.infisical.yaml`; if the checkout has only an `.infisical.json` from an older version, run `infisical init` again with a current version. Git ignores both files. Each checkout and each linked worktree needs its own copy, because the launcher reads only the repository root of the checkout. Do not set `general.domain` (or `domain`) to an instance that the team does not operate: the CLI sends its credentials to that host.
3. Keep each package's development variables in the `dev` environment, in the package's folder from the table above. A folder holds only the variables of its own package: server credentials never enter a frontend folder, and a frontend folder holds only public `PUBLIC_` build values, because they are inlined into the browser bundle.

A maintainer can explicitly invoke the workspace skill [`setup-infisical-dev`](../.agents/skills/setup-infisical-dev/SKILL.md) for these steps; agents do not start it automatically. The skill checks the CLI, the login and the project configuration, fills the `dev` folders of the packages in the table above with the values it can determine from the repository, and asks the user for the values that only the user can supply. It follows the rules below.

Rules:

- The environment is always `dev`. The launcher passes `--env=dev` explicitly, so a default environment or a Git-branch mapping in the local project configuration cannot select a staging or production environment. Production values stay in the deployment env files and are not stored in the `dev` environment.
- Infisical values override variables that are already set in the shell, as `infisical run` does. For a value that differs for one developer, use an Infisical personal override instead of a shell variable. Rsbuild keeps a non-empty process value over the value of the same name in a `.env` file, so a non-empty injected value also overrides the service-local `.env` files of the frontends. On Windows, where environment variable names are case-insensitive, an injected value also replaces every inherited variable whose name differs only by case (an injected `fixture_value` replaces an inherited `FIXTURE_VALUE`), so the command receives one value per name and never the stale inherited one. On POSIX systems differently cased names stay distinct.
- The launcher never takes the names that `infisical run` reserves from Infisical: `HOME`, `PATH`, `PS1`, `PS2`, `PWD`, `EDITOR`, `XAUTHORITY`, `USER`, `TERM`, `TERMINFO`, `SHELL`, `MAIL` and names that start with `XDG_` or `LC_`. On Windows the comparison ignores case, so a `path` or `Home` entry cannot replace the inherited `Path` or `HOME`, and two entries that differ only by case count as one variable (the later entry wins); on POSIX systems only the exact spellings are reserved. It also skips names that are not valid variable names (`[A-Za-z_][A-Za-z0-9_]*`) and values that contain a NUL character. Skipped entries are only counted in the `dev_env_infisical` record.
- The CLI reads `LOG_LEVEL`, `LOG_DESTINATION` and `LOG_FORMAT` for its own logs, and the servers use `LOG_LEVEL` too. The launcher removes these three variables from the CLI's environment, so a shell value such as `LOG_LEVEL=debug` does not make the CLI log debug records; the development command still receives them. On Windows the removal ignores case (`Log_Level` is `LOG_LEVEL`), so the CLI receives none of them under any casing; on POSIX systems only the uppercase spellings are removed.
- Do not define `PORTLESS` or `PORTLESS_*` in a development folder. The portless proxy and its settings belong to the developer's machine, and the root `pnpm dev` proxy preflight runs before any injection, so a value from Infisical would reach `portless run` but not the preflight (see [Frontend development URLs](#frontend-development-urls)).
- Do not define a variable that fixes a development listen address or port (for example `ADDR`, `STUN_ADDR` or `METRICS_ADDR`) in a development folder; development servers keep the fixed loopback ports of [Process boundaries](#process-boundaries).
- Injection happens inside each package task, after Turborepo filters the task environment. The `passThroughEnv` lists in package `turbo.json` files therefore apply to shell values only, and root `pnpm dev`, package-filtered Turbo runs and `pnpm --filter <package> dev` inject the same values. Turbo strict mode removes `INFISICAL_*` variables (for example `INFISICAL_TOKEN`) from the task environment, so root `pnpm dev` uses the CLI login of the user. The CLI login reaches the task through `HOME` and, for the system keyring on Linux, `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR`, which Turbo passes.
- Builds, tests, end-to-end suites, CI and deployments do not use this injection. End-to-end suites start `rsbuild` or `rspress` directly with the variables that their configuration passes, according to the [e2e contract](repository-e2e-contract.md#app-under-test).
- The launcher logs structured records on standard error (`dev_env_infisical`, `dev_env_direct`, `dev_env_signal`, `dev_env_usage_error` and `dev_env_failed`) with the mode, environment, folder, configuration file name and the counts of injected and skipped variables. It never logs variable names or values; never print injected values in development command logs either.

Process handling: the CLI exits before the development command starts, and the command runs in the launcher's process group, as a command that a package script starts directly does. The launcher does not forward signals. It records `SIGINT`, `SIGTERM`, `SIGQUIT` and `SIGHUP` in a `dev_env_signal` record instead of exiting, waits for the command and exits with the command's status. A terminal Ctrl-C therefore reaches the development command exactly once, from the terminal, and does not abort the graceful shutdown of a server launcher. A Turborepo forced stop (`SIGKILL` to the task's process group) also stops the command. On POSIX, the `accounts-api`, `ownsand-api` and `sandrun-api` launchers run each build and server phase under a supervisor in a separate process group. When the launcher exits during a phase, the supervisor stops the phase group, including its descendants. See the service foundation contracts. A signal before the command starts, for example during the fetch, prevents the start; the launcher then exits with `128 + <signal number>`. A signal sent only to the launcher's process ID does not reach the command; signal the process group instead. The launcher does not use `infisical run`: that command stays the parent of the development command and forwards every signal to it, so a terminal Ctrl-C would reach the command twice, and moving the command into its own process group to prevent that would let it survive a Turborepo forced stop. A command must be an executable on `PATH`; on Windows `shell: false` cannot start the `.cmd` shims in `node_modules/.bin`, so package scripts start JavaScript tools as `node <package bin file>`. `scripts/dev/with-infisical.test.mjs` tests both modes with a fake CLI, including the single signal delivery, the forced stop of the process group and a signal during the fetch; the root `test:tooling` task runs it. Both `scripts/dev` launchers (`with-infisical.mjs` and `rspress-preview.mjs`) run their `main` through `import.meta.main`, which needs Node.js 24.2 or later, so starting a launcher through a symlinked file or directory path behaves like starting it by its real path; importing a launcher for tests does not run `main`.

## Billing integration credentials

Billing adds configuration to three packages, and all of it is implemented. Their contracts own the names, defaults and validation: [`accounts-api`](servers-accounts-api-foundation.md#configuration) (the database, Logto, the Logto Management API machine-to-machine credential, Paddle, Resend, the metrics listener and `USAGE_SERVICE_CLIENTS`, which maps the application IDs of the consuming services to their service IDs and holds no secret), [`ownsand-api`](servers-ownsand-api-foundation.md#configuration) (the `delino-accounts` API origin, the Logto token endpoint, its machine-to-machine credential and the metrics listener; without the credential, usage reporting stays idle in development) and the [`delino-accounts` web app](apps-delino-accounts-foundation.md#interfaces-and-contracts) (`PUBLIC_PADDLE_CLIENT_TOKEN` and `PUBLIC_PADDLE_ENVIRONMENT`).

- Paddle and Resend use separate development and production credentials. The `dev` folders of Infisical hold only Paddle `sandbox` credentials (`PADDLE_ENVIRONMENT=sandbox`, and `PUBLIC_PADDLE_ENVIRONMENT=sandbox` for the web app) and a Resend API key for development. Production Paddle and Resend credentials exist only in the Droplet env files of the [deployment workflow](repository-workflow-contract.md#droplet).
- The Paddle API key, the Paddle webhook secret, the Resend API key and the machine-to-machine client secrets never enter a frontend folder. The Paddle client-side token is public and belongs in the `/apps/delino-accounts` folder.
- Each server uses its own machine-to-machine application and secret; services never share one.
- `.env.example` files list the new names with placeholders only.

## Process boundaries

Use explicit argument arrays and `shell: false` for child processes. Document any required platform shim. Forward termination signals and wait for owned child processes to exit. Documentation servers must declare a fixed loopback port and fail on conflicts. Application development servers follow the same rule: `delino-docs` uses `127.0.0.1:13500`, `delino-site` uses `127.0.0.1:13600`, `delino-accounts` uses `127.0.0.1:13100`, `accounts-api` uses `127.0.0.1:18100`, `ownsand-api` uses `127.0.0.1:18300` for HTTP and `127.0.0.1:13478` for STUN over UDP, `sandrun-api` uses `127.0.0.1:18400` for HTTP and `127.0.0.1:19400` for metrics, the `delidev` frontend uses `127.0.0.1:13200`, the OwnSand web console (`ownsand-console`) uses `127.0.0.1:13300` and the SandRun web console (`sandrun-console`) uses `127.0.0.1:13400` by default. The `delidev` frontend binds to the address in `TAURI_DEV_HOST` instead of the loopback address when the Tauri CLI sets it for a physical Android or iOS device, according to the [delidev contract](apps-delidev-foundation.md#build-and-test). End-to-end suites start their own development server on a free loopback port, according to the [e2e contract](repository-e2e-contract.md#app-under-test). The fixed ports of the frontend apps in [Frontend development URLs](#frontend-development-urls) apply to their `dev:app` scripts and to `preview`.

### Frontend development URLs

The purpose is that developers open each app by a name and never need to remember its port. The `dev` script of `delino-accounts`, `ownsand-console`, `sandrun-console`, `delino-docs` and `delino-site` is `portless run --prefix=`, which runs [portless](https://github.com/vercel-labs/portless); each app pins the devDependency `portless` `0.18.1`. portless starts the app's `dev:app` script, which holds the real development server command, on a free loopback port from 4000 to 4999. It passes that port in `PORT`, sets `HOST=127.0.0.1` and `PORTLESS_URL`, and serves the app through a local reverse proxy at a stable name:

| App               | portless name     | URL with the default proxy          | `dev:app` and `PORTLESS=0` |
| ----------------- | ----------------- | ----------------------------------- | -------------------------- |
| `delino-accounts` | `accounts.delino` | `https://accounts.delino.localhost` | `http://127.0.0.1:13100`   |
| `ownsand-console` | `ownsand.delino`  | `https://ownsand.delino.localhost`  | `http://127.0.0.1:13300`   |
| `sandrun-console` | `sandrun.delino`  | `https://sandrun.delino.localhost`  | `http://127.0.0.1:13400`   |
| `delino-docs`     | `docs.delino`     | `https://docs.delino.localhost`     | `http://127.0.0.1:13500`   |
| `delino-site`     | `delino`          | `https://delino.localhost`          | `http://127.0.0.1:13600`   |

- Each app's `package.json` sets the name and the script in its `portless` key. Do not use a root `portless.json` or a root `portless` script: root `pnpm dev` runs `turbo run dev` after the proxy preflight below, and Turbo runs `portless` in each app package.
- The URL is the same in every checkout. In a linked Git worktree, portless adds the last `/` segment of the branch to the name by default (for example `https://fix-ui.docs.delino.localhost`). The empty `--prefix=` turns off this label, because a URL that changes with the branch must be looked up again. `package.json` cannot carry a comment, so this contract records the reason. The portless configuration has no field for it.
- One checkout at a time runs each app. When another process already serves the name, `dev` fails with `"<name>.localhost" is already registered by a running process (PID <pid>)`, like a fixed port that is in use.
- The development server still binds only to `127.0.0.1` and keeps `strictPort`. portless adds `--port` and `--host` flags to `rsbuild dev`. Rspress gets no flags, so `rspress.config.ts` reads `PORT` only when `PORTLESS_URL` is also set; a `PORT` that the shell exports does not move the fixed port of `dev:app`. `rspress preview` reads `process.env.PORT` and `process.env.HOST` before its flags and before `builderConfig.server`, so the `preview` scripts of `delino-docs` and `delino-site` run `node ../../scripts/dev/rspress-preview.mjs` instead of `rspress preview`. The launcher resolves the Rspress CLI from the package directory (`@rspress/core`, `bin.rspress`), removes `PORT` and `HOST` from a copy of the environment, starts `node <bin file> preview [args...]` with `shell: false` and the inherited standard streams, and exits with the child's exit code (`128 + <signal number>` when a signal ended the child). The configuration's `127.0.0.1` address, fixed port and `strictPort` therefore apply to `preview` whatever the shell exports, and a busy fixed port stops the command with a non-zero exit and the `Port <n> is occupied` message. Windows has no `env -u PORT` and cannot start a `node_modules/.bin` shim with `shell: false`, so the launcher is the one form that works on every platform. Like the [Infisical development launcher](#local-development-injection), it does not forward signals: it records `SIGINT`, `SIGTERM`, `SIGQUIT` and `SIGHUP` in a `rspress_preview_signal` record and waits, because the Rspress process is in the same process group and receives a terminal Ctrl-C itself, once. It logs a `rspress_preview_env` record (variable names only) when it removes a variable and a `rspress_preview_failed` record when it cannot find or start the CLI. `scripts/dev/rspress-preview.test.mjs` covers it against a fake `@rspress/core`. Remove the launcher when Rspress prefers its flags and configuration over `PORT` and `HOST` in `preview`.
- `PORTLESS=0`, `PORTLESS=false` and `PORTLESS=skip` make `dev` run `dev:app` on its fixed loopback port without the proxy. On POSIX, portless still starts the app in a separate process group. The `dev` task of each of these apps passes `PORTLESS` and `PORTLESS_*` through Turbo strict mode and no `PORT`, so portless settings from the shell reach portless also through root `pnpm dev`.
- Root `pnpm dev` runs `scripts/dev/start-dev.mjs`. The launcher calls the proxy preflight in `scripts/dev/start-portless-proxy.mjs` before it starts `turbo run dev`. The preflight runs `portless proxy start` once, from the pinned portless of the first app (in directory order) whose `dev` script runs portless (`portless ...`, or `node node_modules/portless/dist/cli.js ...` directly or behind the [Infisical development launcher](#local-development-injection)), in the developer's terminal and before Turbo starts any task. That command returns at once when the proxy already runs. Without the preflight, each `portless run` that finds no running proxy starts its own: the apps then generate the local certificate authority into the same state directory at the same time, each asks for `sudo` for port 443 and for the trust store, and every app except the one whose start wins exits before it registers its name. The preflight does nothing when `PORTLESS` is `0`, `false` or `skip`, or when no app runs portless. When `portless proxy start` fails, for example because `sudo` has no terminal, the preflight prints a `portless_proxy_start_failed` record and exits with its status, so root `pnpm dev` stops before it starts the development servers; set `PORTLESS_UNPRIVILEGED=1` or `PORTLESS=0`, or start the proxy from an interactive terminal first. When portless serializes concurrent proxy starts, remove the early start. Keep the state directory resolution while a relative override still depends on the app working directory. `scripts/ci/start-portless-proxy.test.mjs` covers preflight against a fake portless CLI.
- Shared state directory. Root `pnpm dev` resolves a nonempty relative `PORTLESS_STATE_DIR` against the selected app directory. This is the working directory that preflight uses for `portless proxy stop` and `portless proxy start`. PID lookup, proxy stop and start, and the Turbo app tasks use the resulting absolute path. The launcher passes an absolute override through as supplied. An unset or empty override uses the portless default `~/.portless`. `scripts/ci/start-portless-proxy-state-dir.test.mjs` covers preflight and two app working directories.
- Outdated proxy: `portless proxy start` also accepts a proxy that an older portless started, for example a global installation, and that proxy can keep running for weeks. portless 0.15.8 watches the routes file itself, but portless 0.18.1 replaces that file with a rename, so after the first route change the old proxy never reloads its routes: it answers 404 for apps that register later and 502 for apps that moved to another port, and only an app whose route it read before keeps working. Before the start, the preflight therefore reads the proxy PID from the shared portless state directory, reads the process command with `ps` and finds the version of the portless package that the process runs. When that version is older than the pinned version, it prints a `portless_proxy_outdated` record and runs `portless proxy stop` from the pinned portless, which asks for `sudo` in the terminal when the proxy runs as root, and then starts the pinned proxy. The new proxy reads the routes file, so apps that already run keep their names. When the stop fails, the preflight prints a `portless_proxy_stop_failed` record and exits with its status; stop the proxy from an interactive terminal, then run root `pnpm dev` again. The preflight keeps a proxy of the pinned or a newer version, and a proxy whose version it cannot read (no recorded PID, no `ps` as on Windows, or a path with a space in the command). Remove this check when the repository no longer needs to replace a proxy from a portless version that watches the routes file itself, or when portless restarts an outdated proxy by itself.
- The proxy and its state (`~/.portless` by default) belong to the developer's machine, not to the repository. With the default proxy (HTTPS with HTTP/2 on port 443), the first start creates a local certificate authority, adds it to the system trust store and can ask for `sudo`. Root `pnpm dev` asks for it through the preflight in the terminal. Package commands such as `pnpm --filter <app> dev` and `pnpm exec turbo run dev` do not run the preflight; start the proxy once from an interactive terminal before them, for example with `pnpm --filter delino-docs exec portless proxy start`, because a task without a terminal cannot answer the prompt. `PORTLESS_UNPRIVILEGED=1` selects a proxy that never asks for `sudo` and serves plain HTTP on port 80; on Linux it needs `net.ipv4.ip_unprivileged_port_start` at or below 80. Keep the proxy on port 443 or 80: a `PORTLESS_PORT` of another value adds that port to every URL. portless refuses a state directory that a group or other users can write to, or that is under such a directory.
- The root launcher invokes the installed Turbo CLI with Node.js, inherited standard streams and no shell. Turbo receives terminal Ctrl-C directly in the shared process group. On POSIX, a supervisor can send `SIGTERM` to the Node PID running `scripts/dev/start-dev.mjs`. The launcher relays `SIGTERM` once to the CLI, waits for it to exit and returns its status. A group `SIGTERM` still counts as one shutdown request in native Turbo. The outer package manager can have a different PID.
- On POSIX, portless forwards SIGINT, SIGTERM and SIGHUP to the app's process group and waits for the app to exit. Use Ctrl-C on root `pnpm dev` or on `pnpm --filter <app> dev` to stop the development server. When Turbo itself receives SIGTERM, which happens on Ctrl-C of `pnpm exec turbo run dev`, it sends SIGKILL to the task process group immediately after SIGINT. If that kills portless before it forwards the signal, the development server can keep running outside the task group.
  - For a proxied launch, run `pnpm --filter delino-docs exec portless prune` (any of these apps works) with the original portless state directory. If the launch used `PORTLESS_STATE_DIR`, set it to the same resolved absolute path for prune. Prune uses stale route records in that directory to find and stop recorded app process groups.
  - For a bypassed launch, find the listener on the app's fixed loopback port in the table above. For `delino-docs`, run `lsof -nP -iTCP:13500 -sTCP:LISTEN` and find the PID for `127.0.0.1:13500`. Set `pid` to that PID. Use `ps -p "$pid" -o command=` and `lsof -a -p "$pid" -d cwd` to verify that it is the development server for the intended app and checkout. Once verified, run `kill -TERM "$pid"`. Check that the listener has exited before retrying the development command. Bypass creates no route record, so prune cannot find the listener even with the original state directory. The `--force` flag changes the signal from SIGTERM to SIGKILL for recorded groups.
- `delidev` does not use portless: the Tauri `build.devUrl` and physical Android and iOS devices (`TAURI_DEV_HOST`) need its fixed address. The server packages do not use portless either: `ownsand-api` needs HTTP/2 without TLS (h2c) and UDP for STUN, `sandrun-api` serves h2c too, and the portless proxy connects to backends over HTTP/1.1 and serves HTTP only.
