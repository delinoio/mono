# cmds-sandrun-cli foundation contract

## Scope

This contract owns the SandRun command-line interface, component `sandrun-cli`, of [`sandrun`](project-sandrun.md) at `cmds/sandrun/`. The binary name is `sandrun`. The entry point is `cmds/sandrun/main.go`; `cmds/sandrun/internal/cli` holds the commands and `cmds/sandrun/internal/mcpserver` the MCP server. The credential file (`cmds/internal/credstore`) and the Logto device flow (`cmds/internal/logto`) are shared with the [OwnSand CLI](cmds-ownsand-cli-foundation.md). It lets people inspect the queue, the runners and the device pool, manage organizations, runner profiles, integrations and personal API keys, and use dev sessions from a terminal. `sandrun mcp` serves the same dev session functions to coding agents as a local MCP server.

## Runtime and Language

- Language: Go in the root module `github.com/delinoio/mono`. Logging: `log/slog`.
- The CLI uses the [Go SDK](packages-sandrun-sdk-foundation.md). It must not import code from `servers/`.
- The MCP server uses the official MCP Go SDK `github.com/modelcontextprotocol/go-sdk` (owner approval recorded in the [project index](project-sandrun.md#open-decisions)).
- Distribution: release artifacts for Linux, macOS and Windows on `amd64` and `arm64`. The CLI is pure Go (`CGO_ENABLED=0`) and builds for every target with `GOOS=<os> GOARCH=<arch> go build -trimpath -ldflags "-s -w -X github.com/delinoio/mono/cmds/sandrun/internal/cli.Version=<version>" ./cmds/sandrun`; `sandrun version` prints the version (`dev` without the flag). CI vets and tests the CLI on Linux, macOS and Windows runners and vets the other architecture of macOS and Windows (see the [workflow contract](repository-workflow-contract.md#validation)). Release (recorded): `deploy.yml` releases the CLI as the `github-release` deployable `sandrun-cli` (`cmds/sandrun/package.json`, a release-only workspace package without scripts) when a pending changeset selects it, according to the [workflow contract](repository-workflow-contract.md#binary-releases): the GitHub Release `sandrun-cli@<version>` holds `sandrun-<GOOS>-<GOARCH>` (`.exe` on Windows) for all six targets, built without cgo and with `-X github.com/delinoio/mono/cmds/sandrun/internal/cli.Version=<version>`, so `sandrun version` prints the release version. The release also holds the root `LICENSE` and `NOTICE`, `GO-LICENSE`, `THIRD-PARTY-LICENSES.txt` and `SHA256SUMS`. The darwin executables carry a Developer ID signature with the hardened runtime (identifier `io.delino.sandrun`, no entitlements) and are notarized. No package repository publishes the CLI yet.

## Users and Operators

- Organization owners, admins and members who sign in with Logto or use a personal API key.
- Coding agents (for example Claude Code and OpenAI Codex) that start `sandrun mcp` as an MCP server on the machine where they work, on Linux, macOS or Windows.

- `sandrun login` uses the Logto device authorization flow, like the [OwnSand CLI](cmds-ownsand-cli-foundation.md). The CLI is a Logto native application. Recorded application registration and scopes: the CLI sends `POST <endpoint>/oidc/device/auth` with its application ID, the scopes `openid offline_access sandrun:use` plus the extra scopes in `SANDRUN_LOGTO_SCOPES`, and the API resource `https://sandrun.api.delino.io` (`SANDRUN_LOGTO_RESOURCE` overrides it). It then exchanges the refresh token with the `refresh_token` grant and the `resource` parameter, refreshes the access token one minute before it expires and stores each rotated refresh token, with the same polling, expiry and session rules as the OwnSand CLI. The tenant endpoint and the application ID are configuration (`SANDRUN_LOGTO_ENDPOINT` and `SANDRUN_LOGTO_APP_ID`). The CLI has no built-in production values, because the shared tenant has no registered SandRun CLI application yet. Before the first release, register a native application with device flow and `offline_access` (application ID `<sandrun-cli-logto-app-id>`, placeholder), and record its ID here. `sandrun:use` is the scope that the [control plane](servers-sandrun-api-foundation.md#authentication) requires in user access tokens.
- `sandrun login` writes the verification URL and user code to standard error before it starts polling for tokens. If this write fails, login exits with status `1` before sending a token request and leaves any stored credentials intact. If standard error accepts the diagnostic, the diagnostic includes the original write error.
- `SANDRUN_LOGTO_ENDPOINT` requires an HTTP or HTTPS tenant URL with a hostname. The URL can include an explicit port, a path prefix, or a trailing slash. Login rejects a missing hostname, a query, or a fragment before sending any request to Logto. A query or fragment delimiter (`?` or `#`) is invalid even without a value. The error omits the configured URL.
- Before a refresh, the CLI and MCP server reload the stored credentials. If another process refreshed the same session and its access token is valid for more than one minute, they use that access token. Otherwise they refresh with the stored refresh token. They publish a refresh result only if the store still holds the session and refresh token used for the request. If another process has already stored a newer rotation, they discard the result and use the newer credentials. After an `invalid_grant` response for a refresh token, they check for a newer rotation if another attempt is available. If the store still holds the same token, they check again every 50 milliseconds for up to 5 seconds or until the request is cancelled. If a rotation appears, they use its access token or refresh with its refresh token. Each access token request makes at most three refresh requests. If the store stays unchanged, they report the error and direct the user to `sandrun login`.
- Credential storage: a file in the user configuration directory that only the user can read, with the same [credential storage and lock rules](cmds-ownsand-cli-foundation.md#authentication) as the OwnSand CLI: `<user config dir>/sandrun/credentials.json` (`SANDRUN_CONFIG_DIR` overrides the directory). The organization of `sandrun org use` is in `config.json` in the same directory, which holds no secret.
- `--org` selects the organization. Without `--org`, the CLI uses `SANDRUN_ORG` and then the organization that `sandrun org use` stored. With a personal API key, the organization is the key's organization: the CLI cannot read it from the key, so the user selects it in the same way, and another organization gets `not_found`. `sandrun org use` checks the organization with `GetOrganization` when it uses Logto tokens.
- In text output, `sandrun org list` marks the selected organization with `*` regardless of UUID letter case.
- Personal API key: when the environment variable `SANDRUN_API_KEY` is set, the CLI uses it instead of the stored Logto tokens, like `OWNSAND_API_KEY` in the OwnSand CLI. Commands outside `sandrun session` and `sandrun mcp` then fail with the server's `permission_denied`.
- `sandrun api-key create` prints the secret once on standard output and the other fields on standard error, so that a script can capture only the secret.
- `sandrun session create <profile-name> [--label <text>] [--wait <duration>]` prints the dev session. With `--wait`, it waits until the session is `RUNNING` or ends, the duration passes, or polling fails. After the wait, the command prints the latest dev session it read. If polling read no session, the command prints the session returned by `CreateDevSession`. `sandrun session exec`, `sync` and `download` follow the exit status rules of `ownsand sandbox exec`, `file read` and `file write` where they apply, and use the Go SDK helpers. `sandrun session sync <session-id> [<local-dir>] [--force]` defaults to the current directory. `sandrun session download <session-id> <guest-path> <local-path>`.
- `sandrun profile update <profile-id>` changes only the fields whose flags are set, with one `UpdateRunnerProfile` request. `--image` and `--template` set the `source` path. When one or two resource flags are set, the mask includes the matching paths for `--vcpu` (`resources.vcpu_count`), `--memory-mib` (`resources.memory_mib`) or `--disk-gib` (`resources.disk_gib`). The API keeps the current values for omitted resources. When all three flags are set, the mask uses the `resources` path to replace all three values.
- Deploy SandRun API support for the individual resource paths before publishing the CLI that uses them. The [deployment workflow](repository-workflow-contract.md#deployment-workflow) deploys the API before publishing binaries when the same run includes both releases.
- For `sandrun integration create` and `sandrun integration update`, use `--pool-name` for `cursor` and `--outpost-name` for `devin`. A flag for a different vendor exits with status `2` and names the flag and its allowed vendor. The CLI rejects the flag before reading vendor credentials or sending a create or update request. For updates, the CLI first reads the integration to determine its vendor. The update request includes the `settings` path only when the matching flag is set.
- Credentials (the OwnSand API key and agent integration credentials) are read from standard input or from a file named by a `--*-file` flag. The CLI never accepts a credential as a command-line argument, because other local users can read process arguments. `sandrun ownsand link --ownsand-org <id> [--api-key-file <path>]` reads the OwnSand API key; one trailing line break is removed. `sandrun integration create --vendor <vendor> --name <name> [--credentials-file <path>]` and `sandrun integration update <id> --credentials-file <path> | --credentials-stdin` read the vendor credentials as one JSON object with the protobuf field names of the vendor credentials message, for example `{"environment_key": "...", "webhook_secret": "...", "api_key": "..."}` for `openai-codex`. An invalid input is a usage error whose message never quotes the input.
- The first Ctrl-C cancels the command context. If the command stays blocked on credential input, press Ctrl-C again to exit.
- GitHub installation needs a browser. In text mode, `sandrun github install-url` prints the URL on standard output, then prints the browser instruction and expiry on standard error. If the URL write fails, the command reports the write error on standard error and exits with status `1`. The console callback completes the link.
- Output: tables by default and `--output json` for scripts. Output uses ANSI color by default; `--no-color` and the `NO_COLOR` environment variable turn color off. Lists read every page and print one table, or with `--output json` one object with the list field of the list response (for example `{"organizations": [...]}`); records print as `key: value` lines or as the protobuf JSON mapping with the protobuf field names. `sandrun session create --wait` and `sandrun session wait` exit with `1` when the dev session ends or the wait passes before it is `RUNNING`. If polling fails or the caller interrupts the wait after creation, `sandrun session create --wait` also exits with `1`. After creation, `sandrun session create --wait` prints the latest session on standard output in the selected format. If polling read no session, it prints the created session. The command reports any wait failure on standard error. Text-mode `sandrun session exec` and `sandrun session attach` exit with the ownsand exec statuses: `255` for a stream failure or lost output, `125` when the sandbox ended, `127` when the command could not start, `124` for the exec timeout, `128` plus N for signal N, otherwise the exit code. An interrupt exits with `130` and prints the `sandrun session attach` command that continues the output. `sandrun session sync` and `sandrun session download` exit with `1` for every failure, including limit and path rule failures.
- **Recorded decision (text output escaping).** Text mode escapes record keys and values, table headers and table cells before the CLI adds color. Line feed, carriage return and tab appear as `\n`, `\r` and `\t`. Other C0 controls, DEL, C1 controls and invalid UTF-8 bytes appear as `\xNN`. Other nonprintable Unicode characters, including bidirectional formatting characters and line and paragraph separators, appear as `\uXXXX` or `\UXXXXXXXX`. Printable Unicode and space separators stay unchanged. JSON retains the original values. Text mode preserves raw command streams from `sandrun session exec` and `sandrun session attach` and the one-time secret on standard output. The secret's metadata on standard error follows the record escaping rule.
- In JSON mode, `sandrun session exec` and `sandrun session attach` print one object per line. Events include `stdout` and `stderr` with `offset` and `data`, and `output_truncated` with `missing_stdout` and `missing_stderr`. The initial exec also reports `started`. The CLI prints a final `exited`, `failed`, `sandbox_ended` or `stream_error` object. It exits with `0` after a final result and with `255` after a `stream_error` or lost output. The `stream_error` object sets `outcome_unknown` to true when the server returns `not_found` on attach and the SDK received no start event during the call.
- If a local write of streamed output or a JSON result fails, `sandrun session exec` and `sandrun session attach` exit with status `1`. They report the original write error if standard error accepts the diagnostic. The CLI omits the `stream_error` event for a local write failure.
- The resume command appears on standard error and keeps explicit `--org`, `--api-url` and `--output` values. Omitted options use the normal defaults when the command runs. The CLI quotes the arguments for POSIX shells on Linux and macOS and for PowerShell on Windows. The command uses the normal credential sources.
- The CLI decodes JSON `data` as UTF-8 independently for stdout and stderr. The `offset` is the offset of the first byte represented by that line. The CLI holds an incomplete character at the end of a chunk for the next contiguous chunk of the same stream and emits no `data` line for an empty decoded chunk. It replaces invalid bytes with U+FFFD. If bytes are missing or the stream ends, it emits any pending bytes of the affected stream as a replacement character before the next chunk, truncation event or final result. On interrupt, the attach command starts each stream with pending bytes at its first pending byte.
- Exit codes: `0` on success, `1` on an operational error, and `2` on invalid usage.
- Explicit help and `sandrun version` write to standard output. If a write fails, the CLI exits with status `1` and reports the original error on standard error when possible. Without arguments, the CLI attempts to print usage to standard error and exits with status `2`.
- Environment variables: `SANDRUN_API_KEY`, `SANDRUN_API_URL` (default `https://sandrun.api.delino.io`), `SANDRUN_ORG`, `SANDRUN_CONFIG_DIR`, `SANDRUN_LOGTO_ENDPOINT`, `SANDRUN_LOGTO_APP_ID`, `SANDRUN_LOGTO_RESOURCE`, `SANDRUN_LOGTO_SCOPES` and `NO_COLOR`.

### MCP server

`sandrun mcp` serves the Model Context Protocol over standard input and output for one coding agent. The agent's MCP configuration starts it, for example `sandrun mcp --org <organization-id> --pass-env NPM_TOKEN`. It has no network listener.

- The server uses `SANDRUN_API_KEY` when set. Otherwise, it looks up stored Logto tokens on each tool call that needs a client until initialization succeeds. Without a usable credential, the tool returns an error that tells the user to run `sandrun login` or set `SANDRUN_API_KEY`. Running `sandrun login` lets the next call use the stored tokens without a server restart. The server reuses the client after initialization and refreshes its Logto access token as the CLI does.
- `--pass-env NAME` (repeatable) names local environment variables that the server adds to every `exec` call. The server reads their values from its own environment when it runs the command, so the values never pass through the agent's model context. A tool call cannot add names to this list. When a named variable is not set, the server leaves it out and reports its name, without a value, in the tool result.
- Standard output carries only MCP messages. Logs go to standard error.
- Dev sessions do not depend on the server process. When it exits, its dev sessions stay until they are deleted or their TTL ends; `list_sessions` finds them again.
- Tool waits: a tool call waits at most 50 seconds. OpenAI Codex stops an MCP tool call after 60 seconds by default (`tool_timeout_sec`), so 50 seconds leaves time for the response. The `wait_seconds` arguments accept 0 to 50, with a default of 50.
- Each call to `list_profiles`, `create_session`, `list_sessions`, `get_session` or `delete_session` uses one deadline for client setup and all RPCs. This includes each page of a list and the profile lookup before session creation. An earlier caller deadline or cancellation also stops the call.
- With a positive wait, `wait_session` returns a running or terminal state as soon as it reads that state. If the tool deadline expires first, the tool returns the last state it read or a `deadline_exceeded` error if it has no state. A zero wait makes one lookup without polling. The lookup stops at the 50-second cap or at an earlier caller deadline.
- The `exec` tool accepts `timeout_seconds` as a whole number of seconds from 0 to 9223372036, inclusive. A positive value stops the command after that many seconds. A value of 0 or an omitted argument gives the command no timeout.

| Tool              | Arguments                                                                                                                    | Result                                                                                                                                                                                                              |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_profiles`   | none                                                                                                                         | The `DEV_SESSION` runner profiles: name, guest OS, resources, workspace path, TTLs and maximum queue wait.                                                                                                          |
| `create_session`  | `profile` (name), optional `label`                                                                                           | The dev session ID and state. Returns at once; a session without free capacity is `QUEUED`.                                                                                                                         |
| `wait_session`    | `session_id`, optional `wait_seconds`                                                                                        | The state after the session became `RUNNING`, ended, or the wait passed. The agent calls it again while the state is `QUEUED` or `STARTING`.                                                                        |
| `list_sessions`   | optional `include_ended`                                                                                                     | The caller's own dev sessions with ID, profile, guest OS, state, label and times.                                                                                                                                   |
| `get_session`     | `session_id`                                                                                                                 | One dev session.                                                                                                                                                                                                    |
| `delete_session`  | `session_id`                                                                                                                 | The final state.                                                                                                                                                                                                    |
| `exec`            | `session_id`, `command` (argument array), optional `cwd`, `env` (map), `timeout_seconds` (stops the command), `wait_seconds` | When the command ends within the wait: the exit code or signal, `timed_out`, and the output. Otherwise: the `exec_id`, `running: true`, the output so far and the next offsets. The command keeps running.          |
| `exec_output`     | `session_id`, `exec_id`, `stdout_offset`, `stderr_offset`, optional `wait_seconds`                                           | The output from the given offsets, and the result when the command ended within the wait.                                                                                                                           |
| `sync`            | `session_id`, optional `local_path` (default: the server's working directory), optional `force`, optional `wait_seconds`     | When the sync ends within the wait: the numbers of uploaded, deleted and skipped files, the bytes sent and the warnings. Otherwise: a `transfer_id` and the progress; the transfer continues in the server process. |
| `download`        | `session_id`, `guest_path` (absolute, or relative to the workspace path), `local_path`, optional `wait_seconds`              | When the download ends within the wait: the local path, the file count and the bytes. Otherwise: a `transfer_id` and the progress.                                                                                  |
| `transfer_status` | `transfer_id`, optional `wait_seconds`                                                                                       | The progress or the result of a sync or download that this server process runs. A transfer stops when the server process exits; a later sync sends the same files again.                                            |

- In `exec_output`, output or a missing output range confirms that an exec can be reported as `running: true`. A terminal result or definite upstream error ends the wait immediately. When the requested wait expires without confirmation, the tool allows up to 10 more seconds within the 50-second cap. Keepalives leave the attach unconfirmed. If the grace period ends without confirmation, the tool returns `deadline_exceeded` with instructions to retry with the same exec ID and offsets.
- The `exec` and `exec_output` results preview the first 8 KiB and up to the last 24 KiB of newly received bytes for each stream. A gap clears the bytes kept for the end of that stream's preview. The result decodes preview text as UTF-8 and replaces invalid bytes. If any received bytes are left out of the preview, `omitted` gives the absolute byte range from the end of the preview's first portion to the start of its last portion, or to the next offset if the last portion is empty. The agent can read omitted bytes with `exec_output` while the OwnSand agent still keeps them (the last 8 MiB of each stream, until 10 minutes after the command ends). An omitted range can span a gap between the two portions. `output_truncated` reports the missing ranges separately.
- Implementation: the server uses the MCP Go SDK `github.com/modelcontextprotocol/go-sdk` v1.8.0 with typed tool handlers, so the tool input and output schemas follow the argument and result structures. Results are JSON objects. A dev session has `session_id`, `profile`, `guest_os`, `state`, `end_reason`, `label`, `workspace_path` and the times. An exec result has `exec_id`, `running`, `exit_code` or `signal`, `timed_out`, `failure_reason`, `sandbox_ended`, `stdout` and `stderr` (`text`, the byte range `from` and `to`, and `omitted`), `next_stdout_offset`, `next_stderr_offset`, `output_truncated` and `missing_env`. A transfer result has `transfer_id`, `kind`, `running` and `progress`, or the `sync` or `download` result. When the wait of `exec` passes before the started event, the server waits for that event for at most 10 more seconds within the 50-second cap, so that the returned `exec_id` names a command that runs. When the started event does not come in that time, `exec` returns a `deadline_exceeded` error that names the `exec_id` and says that the command may not run; it does not return `running`. `--pass-env` values replace values of the same name in the `env` argument. The `sync` and `download` transfers run on the server process context, not on the tool call. `local_path` arguments that are relative start at the server's working directory.
- Errors: tool errors carry the Connect error code and a message for the agent, for example `resource_exhausted` for the per-user dev session limit, `failed_precondition` for a session that is not `RUNNING` or a sync lock, and the paths that break a sync or download limit.
- Interactive input (stdin and terminals) is not supported, because OwnSand `v1` exec has no stdin.

## Storage

Only the stored Logto tokens and the selected organization in the user configuration directory. The MCP server keeps transfer progress only in memory. Sync state lives in the guest manifest, not on the local machine.

## Security

- The CLI sends tokens only to the configured API origin and the Logto tenant.
- The CLI never prints a stored token or a credential, except the new secret of `sandrun api-key create` once.
- The CLI never accepts a personal API key as a command-line argument; it reads `SANDRUN_API_KEY` from the environment.
- The MCP server never returns token, API key or `--pass-env` values in tool results.

## Logging

`--verbose` writes structured debug logs to standard error. `sandrun mcp` always logs to standard error. Logs never contain tokens, credentials, command arguments, environment values, command output or file contents.

## Build and Test

- Package scripts wrap the Go toolchain. Record them with the implementation. The CLI is not a workspace package, like the OwnSand CLI, so it has no package scripts. The commands (from the repository root): `go test ./cmds/sandrun/...` (the session, sync and MCP exec tests run the fake guest with the local `sh`, `tar` and `git` and skip on Windows hosts), `go vet ./cmds/sandrun/...` and `GOOS=windows` and `GOOS=darwin` `go vet ./cmds/sandrun/...` for the other targets.
- The tests use the fake `sandrun-api` `go/sandrun/sandruntest` of the [Go SDK](packages-sandrun-sdk-foundation.md#go-sdk-surface) and the in-memory transport of the MCP Go SDK.
- Tests cover argument parsing, credential input from standard input and files, `SANDRUN_API_KEY` precedence, output formats and error exit codes against a fake `sandrun-api`. The session tests cover a create wait deadline before the first read, a permanent error on the first or a later poll, caller cancellation, and a standalone wait deadline before the first read.
- Exec JSON tests cover UTF-8 split across contiguous chunks, offsets for both streams, replacement before truncation or a final result, and attach after an interrupt with pending bytes. The fake guest tests also check that text mode preserves the original bytes.
- Refresh rotation tests use two token sources over one credential store and a fake Logto issuer. They cover adopting a valid access token without an issuer request, refreshing with the stored token, discarding a stale response, and recovering from `invalid_grant` when publication precedes or follows the rejection. They also cover the unchanged store, cancellation, sign-out, session replacement and the three-request limit.
- MCP server tests against a fake `sandrun-api`: the tool list and schemas, the 50-second wait limit, `exec` with a command that ends within the wait and one that does not, `exec_output` from offsets with omitted ranges, `--pass-env` values that never appear in tool results, sync and download through `transfer_status`, and error mapping.
