# packages-ownsand-sdk foundation contract

## Scope

This contract owns the two OwnSand SDKs of [`ownsand`](project-ownsand.md):

- `packages/ownsand-sdk/`: TypeScript SDK, component `ownsand-sdk-ts`, workspace package `ownsand-sdk`.
- `packages/ownsand-sdk-go/`: Go SDK, component `ownsand-sdk-go`, import path `github.com/delinoio/mono/packages/ownsand-sdk-go`. The package root (Go package `ownsand`) holds the Go SDK client: client construction, the service wrappers, the sandbox handle and the data path selection below (see [Go SDK client](#go-sdk-client)). Its subpackages hold the [shared data path packages](#shared-go-packages).

Both SDKs give programs and the [CLI](cmds-ownsand-cli-foundation.md) one client for the public API of the [protos contract](protos-ownsand-api-contract.md), including the data path. Both use Apache-2.0.

## Runtime and Language

- TypeScript SDK: ES modules for Node.js 24 (the `.nvmrc` baseline). It uses Connect for ECMAScript v2 with the TypeScript bindings generated from the schemas. The generated TypeScript code lives in `packages/ownsand-sdk/src/gen/delino/ownsand/v1/` (`<file>_pb.ts`, protobuf-es v2 messages, enums and service descriptors), which the shared formatter excludes. Recorded generation decision: the package-local buf template `packages/ownsand-sdk/buf.gen.yaml` runs `protoc-gen-es` (`target=ts`, `import_extension=ts`) from the package's `node_modules`, pinned as the exact devDependency `@bufbuild/protoc-gen-es` `2.16.0`, equal to the `@bufbuild/protobuf` runtime `2.16.0`; change them together. `scripts/protos.sh generate` and `check` cover these bindings according to the [protos contract](protos-ownsand-api-contract.md#build-and-test), and need `pnpm install` first. The package exports its source (`.` is `src/index.ts`, `./gen/*` is `src/gen/delino/ownsand/v1/*.ts`) to workspace consumers, and `publishConfig.exports` names the `dist/` build for a later publication. Browser support of the SDK client is not part of this version; the web console imports only the generated bindings (`ownsand-sdk/gen/*`) and uses them with `@connectrpc/connect-query` directly.
- Recorded transport decision: the TypeScript SDK uses the `@connectrpc/connect-web` transport (Connect protocol, binary protobuf) over the runtime's `fetch`, which Node.js 24 provides; every public RPC, including the relay, is unary or server-streaming, so no HTTP/2-only client is needed. The SDK wraps `fetch` to refuse every URL outside the configured origin and to count the bytes of each relay response body for the 90-second idle rule.
- Go SDK: Go in the root module. It uses the committed Go bindings in `protos/delino/ownsand/v1/` and does not generate code.
- Node.js has no built-in WebRTC implementation. Recorded decision: the TypeScript SDK bundles no WebRTC library. It implements the peer-to-peer data path against the W3C `RTCPeerConnection` API and uses the runtime's `globalThis.RTCPeerConnection` when the runtime has one, or a W3C-compatible constructor that the caller passes in the `webrtc` client option (for example from a WebRTC library that the caller chooses and audits). In a runtime without WebRTC and without that option, which includes plain Node.js 24, the SDK is relay-only and never calls `GetIceServers` or `OpenSession`; the `webrtc: false` option forces the same. Forcing `PEER_TO_PEER` without a WebRTC implementation fails at handle creation with a configuration error.
- The Go SDK uses pion (`github.com/pion/webrtc/v4` `v4.2.26`) for the peer-to-peer data path. The owner approved it with the OwnSand implementation; see [Dependencies and Integrations](#dependencies-and-integrations).

## Shared Go packages

The control plane, the device agent, the guest helper, the CLI and the Go SDK must implement the data path rules identically, so the rules live once in Apache-2.0 subpackages of `packages/ownsand-sdk-go/`. The [project index](project-ownsand.md#licensing-and-code-sharing) allows the control plane to import them; they never import `servers/`. They log nothing.

| Import path                                                     | Content                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `github.com/delinoio/mono/packages/ownsand-sdk-go/uuidv7`       | UUID v7 generation (strictly increasing within a process: a 12-bit counter in `rand_a` that starts from a random value each millisecond), canonical parsing that rejects other versions and variants, and timestamp extraction.                                                                                                                                   |
| `github.com/delinoio/mono/packages/ownsand-sdk-go/datapath`     | `DataFrame` kinds (`PayloadKind`, `NewFrame`, `ValidateFrame`, `ConsumesCredit`), the size limits, the data channel codec (`AppendFrame`, `EncodeMessages`, `Decoder`), `MarshalFrame` and `UnmarshalFrame` for relay and guest messages, credit windows (`SendWindow`, `ReceiveWindow`, `FrameCost`) and the operation ID admission window (`CheckOperationID`). |
| `github.com/delinoio/mono/packages/ownsand-sdk-go/relaybinding` | `RelayRequestBinding` construction from exec, read and write requests, its explicit field-number-order encoding, the request digest, and the golden vectors in `relaybinding/testdata/request-digest-vectors.json`.                                                                                                                                               |
| `github.com/delinoio/mono/packages/ownsand-sdk-go/validate`     | Request rules shared by the control plane, the agent and the SDKs: exec request size, IDs and salt, read and write requests, labels, TTLs, resources, sandbox source, network mode, create requests, device limits and the effective vCPU limit, enrollment token TTL and page size.                                                                              |

Recorded decisions of these packages:

- Data channel codec: a frame is a varint length followed by the encoded `DataFrame`. The `Decoder` reads the length prefix, rejects a declared length above 1 MiB plus 64 KiB before it buffers the body and stays failed after any error (an oversized length, a length prefix longer than 10 bytes or a body that is not a valid `DataFrame`); the receiver then closes the data channel. `EncodeMessages` splits each frame into messages of at most 16 KiB. A receiver may get several frames in one message and one frame across several messages.
- `ValidateFrame` requires a known kind that equals the payload kind, `stream_id` 0 with an empty `sandbox_id` for `RELAY_KEEPALIVE` and `SUPPORTED_FRAME_KINDS`, and a `stream_id` other than 0 for every other kind. It returns `UnknownKindError` for a kind of a newer schema, which a receiver ignores on `stream_id` 0 and answers with an error frame on another stream.
- Flow control: `FrameCost` is the protobuf size of the encoded `DataFrame`, without the data channel length prefix, for the payload kinds and zero otherwise. `ReceiveWindow` grants its capacity (at least one maximum frame), fails a frame beyond the outstanding credit with `ErrWindowExceeded` and returns exactly the freed bytes as the next window update; `SendWindow` blocks a sender until enough credit arrives. A window never exceeds 2^40 bytes.
- Operation ID admission: `CheckOperationID` admits an unknown ID whose UUID v7 timestamp is less than 15 minutes old (an ID exactly 15 minutes old is expired) and at most 5 minutes in the future (exactly 5 minutes is admitted), with millisecond precision. It returns `not_found` for an expired ID, `failed_precondition` for a future ID and `invalid_argument` for a value that is not a UUID v7. The 30-minute memory of ended IDs is the agent's own state.
- Request digest: `relaybinding.Encode` writes the fields in field-number order with `protowire`, omits zero scalar fields, keeps every element of `command` (also empty strings) and encodes a present `timeout` also when it is zero. `env` entries are sorted by key bytes, not by UTF-16 code units. A test checks that the encoding equals the protobuf runtime's deterministic encoding. The golden vector file lists language-neutral requests (`exec`, `read_file` or `write_file`, with the salt in hexadecimal and `env` in an arbitrary order), the encoded binding and the digest in hexadecimal; the TypeScript SDK must reproduce every vector. Regenerate it with `go test ./packages/ownsand-sdk-go/relaybinding -run TestGoldenVectors -update`. `DigestOfFirstRequest` returns `ErrNoDigest` for an `AttachExec` request and for a `WriteFile` chunk without path and salt; the agent then compares the grant digest with the recorded digest of the operation.
- Validation: every failure is `invalid_argument` with the field path and the rule, never the value. A binding salt has exactly 32 bytes. A guest path must be absolute for some guest OS (`/...`, a UNC path such as `\\server\share` or a Windows drive path such as `C:\...`); the guest helper applies the rules of its own OS. `UpdateDeviceLimits` accepts zero for `vcpu_count`, `memory_mib` and `disk_gib` (a device with zero limits gets no sandboxes) and rejects negative values. `page_size` 0 means 50, values above 200 are reduced to 200, and negative values are invalid. The effective vCPU limit is computed in 64-bit integers.

## Go SDK client

The Go SDK client lives in the package root `ownsand`. Recorded decisions of the implementation:

- Construction: `ownsand.New(ownsand.Options{...})` takes `BaseURL` (default `https://ownsand.api.delino.io`; an origin without path, query or user info), exactly one of `APIKey` and `TokenSource` (a function that returns a current Logto access token), `OrganizationID`, an optional `HTTPClient`, an optional `*slog.Logger` and the forced `Transport` (`TransportAuto`, `TransportPeerToPeer` or `TransportRelay`). Without a credential it reads `OWNSAND_API_KEY`; without an organization it reads `OWNSAND_ORG`. It reads no other environment variables. An RPC that needs an organization fails with `ErrNoOrganization` before it is sent; a request that sets `organization_id` overrides the default.
- HTTP: the client speaks HTTP/2. An `https://` origin negotiates it with ALPN; an `http://` origin (a local control plane, for example `http://127.0.0.1:8300`) uses HTTP/2 without TLS with prior knowledge (h2c), because the control plane serves h2c. The client never follows redirects, so the `Authorization: Bearer` header reaches only the configured origin, and errors never contain the credential (a message that contains it is redacted, with the Connect code kept).
- Service wrappers: `Organizations()`, `Members()`, `Devices()`, `APIKeys()`, `Sandboxes()`, `Snapshots()` (with templates) and `DataPath()` wrap every public RPC with the generated request and response messages and fill `organization_id` from the client default. The relay RPCs are internal to the sandbox handle.
- Sandbox handle: `Client.CreateSandbox` validates the request with the shared `validate` package before it sends anything (missing TTL or resources fail locally), generates one `idempotency_key` and retries a lost response (a transport interruption, `unavailable` or `deadline_exceeded`) with the same key for up to 60 seconds. `Client.Sandbox(org, id)` opens a handle for an existing sandbox. The handle has `Get`, `WaitStable` (polls `GetSandbox` until `RUNNING`, `PAUSED`, `FAILED` or `DELETED`), `Pause`, `Resume`, `Delete`, `Snapshot`, `Exec`, `AttachExec`, `ReadFile`, `ReadFileBytes`, `WriteFile`, `WriteFileBytes`, `Transport` and `Close`.
- Exec results: `Exec` returns an `ExecResult` of kind `exited` (exit code or signal, `TimedOut`), `failed` (the `ExecFailureReason` and message) or `sandbox_ended` (the `SandboxEndReason`), with `Incomplete` set after lost output, or a `*DataPathError` (with `OutcomeUnknown` when `AttachExec` returns `not_found` after `started`). A `*DataPathError` for an error status that the agent or the control plane reported wraps a `*connect.Error` on both transports: on peer-to-peer the SDK builds it from the error frame's `ErrorDetail`, with its code, its message and the `ErrorDetail` as a Connect error detail, so `connect.CodeOf` and `(*connect.Error).Details` give the same result as on the relay. Events reach `ExecParams.OnEvent` in order: `started` once, `stdout` and `stderr` chunks with their offsets and `output_truncated` with the missing byte ranges.
- Peer-to-peer: the handle calls `GetIceServers` and `OpenSession` only when an operation needs a session, creates one ordered, reliable data channel labelled `ownsand-data` (negotiated in band) as the offerer, gathers all candidates before it sends the offer and waits up to 10 seconds for the channel to open. Each request (an exec, an attach, a read call or one write chunk) uses a new `stream_id`, starting at 1, on the shared session. The data channel has no application credit windows (the relay window frames are relay only); SCTP flow control and a 4 MiB send buffer limit apply back-pressure. One receive callback serves every stream of the session and queues up to 64 frames for each stream. When the queue of one stream stays full for 10 seconds, because its consumer does not return (for example an `OnEvent` callback that waits for another operation on the same handle), the callback fails that stream instead of blocking the other streams; the operation then continues on a new stream from its delivered offsets, with the rules of a transport interruption. A session-end frame on any `stream_id` ends the whole session; a channel that closes without one, an ICE failure or an invalid byte stream is a failure that moves the handle to the relay (unless the transport is forced to peer-to-peer, where the next operation opens a new session). `OpenSession` errors `unauthenticated`, `permission_denied`, `not_found` and `invalid_argument` end the operation; `failed_precondition` (a sandbox that is not `RUNNING`, for example a paused sandbox whose exec output is still attachable) uses the relay for that attempt without moving the handle; other errors move the handle to the relay. A frame from the agent that fails `ValidateFrame` on an open stream (a kind of a newer schema, or a kind that does not match its payload) ends only the operation of that stream at once, with a `*DataPathError`, after the frames that arrived before it; such a frame on `stream_id` 0 or on a stream that is not open is ignored.
- Relay: each operation has its own grant and recovery state. The SDK detects a transport interruption as an error that is not a Connect wire error (no valid terminal status), and cancels a relay server stream that receives no response byte for 90 seconds; the byte counter wraps the HTTP response body, so a large frame in transit counts as activity. A relay stream that the agent rejects at its capacity (`resource_exhausted`) keeps the grant; every other retryable failure renews it with `replaces_grant_id`. `resource_exhausted` honours the `retry_after` of the `ErrorDetail` that the server attaches as a Connect error detail. Back-off starts at 250 milliseconds and doubles up to 5 seconds within the window. The retry window of an `AuthorizeRelay` call outside recovery starts with its first attempt, and each attempt runs only for the time left in its window (the operation's recovery window, or that own window): the SDK cancels an attempt whose response has not arrived when the window ends and ends the operation with a `*DataPathError`, also for a caller without a deadline. It cancels the attempt with a timer and does not send the bound as a Connect request timeout.
- File transfer: the write sends the `finish` fields with the last data chunk (one call with no data for an empty file), carries the path and the salt only on the first call and sends one chunk at a time. The default mode is `0644`. A read writes only complete chunks, skips bytes it already delivered and fails on a gap.
- Timing values (10-second open timeout, 10-second stream queue timeout, 60-second recovery window, 90-second stall timeout, the 14-minute plus 30-second and 5-minute plus 30-second renewal margins, the 60-second idle grant rule and the 5-minute 30-second `WriteFile` attempt deadline) are internal constants; the tests run the same logic with scaled-down values.

## Users and Operators

- Programs that use an organization API key: CI jobs, AI agents and services.
- People who use a Logto access token that their own program obtained.
- The [CLI](cmds-ownsand-cli-foundation.md), which is built on the Go SDK.

## Interfaces and Contracts

### Client construction

- The client takes the API origin (default `https://ownsand.api.delino.io`) and one credential: an API key or a function that returns a current Logto access token.
- Without an explicit credential, both SDKs read the `OWNSAND_API_KEY` environment variable. They read no other environment variables for credentials.
- The client takes an optional organization ID and uses it for every RPC that needs one; without it, the SDKs read `OWNSAND_ORG`. A call can override it. An RPC that needs an organization fails before it is sent when neither is set.
- The client never logs or includes the credential in errors.
- TypeScript surface (recorded): `new OwnSandClient({ origin, apiKey | accessToken, organizationId, transport, webrtc, logger })`. The service clients are `organizations`, `members`, `devices`, `apiKeys`, `sandboxes`, `snapshots`, `dataPath` and `relay` (the generated Connect clients); a missing `organization_id` in a unary request is filled from the client default, and a call that sets it overrides the default. `client.sandbox(id)` returns a handle and `client.createSandbox(...)` creates one. The TypeScript SDK reads only `OWNSAND_API_KEY` and `OWNSAND_ORG` from the environment.

### Operations

The SDKs expose the public services of the [protos contract](protos-ownsand-api-contract.md#public-services) with idiomatic names, and a sandbox handle with these operations:

- `create`, `get`, `list`, `delete`, `pause`, `resume`.
- `exec`: returns a stream of stdout and stderr chunks and the exit code or the signal. A command that could not start is a distinct `failed` result with its reason, not an exit code and not a data path error. A command that the exec `timeout` stopped has the `timed_out` flag set on its result. An exec that ends with a `sandbox_ended` event is a distinct result with the `SandboxEndReason`. A data path failure is an error, never an exit code. When a continuation loses output (`output_truncated`), the stream reports a truncation event with the missing offsets, and the result is marked incomplete; the SDK never presents truncated output as complete.
- `readFile` and `writeFile` (Go: `ReadFile` and `WriteFile`): stream contents in chunks and accept readers and byte buffers. `writeFile` uploads in chunks and finishes the write only after the last chunk, as the [file transfer contract](protos-ownsand-api-contract.md#file-transfer) requires. The SDK keeps the `write_id`, the offset and the chunk or `finish` request that is not acknowledged yet. After a failure or a session end, it sends that exact request again, on the new session or on the relay, before it reads more input.
- `snapshot`, plus snapshot export and template operations.

`create` requires `idleTtl` and `maxTtl` (Go: `IdleTTL` and `MaxTTL`; TypeScript: milliseconds) and the resources. The SDK generates one `idempotency_key` for each logical create and reuses it for every retry of that create. The SDKs do not supply a default TTL.

### Data path

- For exec and file operations, an SDK that supports peer-to-peer calls `GetIceServers` and then `OpenSession` once per sandbox handle and tries a WebRTC data channel to the agent. A relay-only SDK, and a client with the transport forced to `RELAY`, does not call `OpenSession`; it uses the relay directly.
- Relay: for each exec, file read and file write, the SDK calls `AuthorizeRelay` on the control plane with the operation kind, the `exec_id`, `read_id` or `write_id`, and the request digest of the [protos contract](protos-ownsand-api-contract.md#relay-grants), and then calls the `RelayService` RPCs of that operation on the configured API origin with its own credential and the returned grant ID. To attach to an exec that it did not start or whose request fields it no longer has, it uses an `ATTACH_EXEC` grant with only the `exec_id`. It uses the grant only for that operation. It measures the grant's remaining lifetime from `expires_in` on its monotonic clock from receipt, so a caller clock offset does not change renewal. When it must start a new stream (at a stream rotation, at the next `WriteFile` chunk or `ReadFile` call of the operation, or in recovery) and either the grant has expired or expires before the new stream can end (within the control plane's 14-minute relay stream limit plus 30 seconds for a server stream, and within the 5-minute call limit plus 30 seconds for a `WriteFile` chunk), or the last stream of the operation ended more than 60 seconds ago (the agent may have released the idle grant and closed its relay connection), so in practice at every rotation, it renews it with `AuthorizeRelay` for the same operation and `replaces_grant_id` set to the grant that it renews; it never renews while a stream of the old grant is open. Because the SDK renews only when no stream of the old grant is open, a `GRANT_REPLACED` on its own stream means that another renewal replaced the grant, and the SDK handles it as a failure under relay recovery. When it renews a grant outside recovery (before the next `WriteFile` chunk or `ReadFile` call), it applies the same authorization retries as at startup and in recovery (`unavailable`, `resource_exhausted` and an `AuthorizeRelay` call that ends with a transport interruption without a valid terminal status) within a 60-second window, and keeps the same `authorization_id` and `replaces_grant_id` for each retry. The agent may release a grant after 60 seconds without an open stream; the SDK then gets `GRANT_INVALID` and renews it through recovery.
- Relay events: the SDK consumes the relay `accepted` and `keepalive` events internally and never passes them to the caller. It reports one `started` event per exec and drops the `started` event that an `AttachExec` continuation repeats, so the caller and the [CLI](cmds-ownsand-cli-foundation.md) JSON output see the same events on both transports. A relay stream that fails with `resource_exhausted` because the agent is at its stream or credit capacity counts as a retryable failure under relay recovery.
- Stream rotation: a relay stream that the agent accepted (with its `accepted` event) and that ends with an OK status and no final event is a routine rotation at the control plane's relay stream limit. The SDK continues the operation at once with the continuation rules below, as often as needed, and a rotation does not count as a failure.
- Relay recovery: a failure is a relay RPC that ends with a transport interruption and no valid terminal Connect status (for example, a connection that closes during a control plane restart and surfaces as `aborted`, or a stream that ends without its end-of-stream message), or that fails with `unavailable` (for example with `AGENT_CHANNEL_LOST` or `GRANT_INVALID` after a control plane deployment ended the grant, or no relay connection from the agent), or a `WriteFile` call that fails with `deadline_exceeded` because the call, including the upload and the agent's result, took longer than the control plane's 5-minute relay limit (the SDK resends the same unacknowledged chunk with the same `write_id`). After a failure, the SDK starts one recovery window of 60 seconds. In that window it discards the grant, calls `AuthorizeRelay` again and continues the operation, and it repeats these steps with back-off while `AuthorizeRelay` or the continuation fails with `unavailable` or ends with a transport interruption without a valid terminal status, while the continuation ends again with a transport interruption without a valid terminal status (an `aborted` status that the guest helper returns explicitly, for example for a file that changed during a read, is terminal), or `AuthorizeRelay` fails with `resource_exhausted` (it waits at least the retry delay in the error detail), or the first relay attempt or a continuation fails with `resource_exhausted` because the agent is at its stream or credit capacity (it retries with back-off). The SDK applies the same `unavailable` and `resource_exhausted` retries, and the retry of an `AuthorizeRelay` call that ends with a transport interruption without a valid terminal status (with the same `authorization_id` and `replaces_grant_id`), within a 60-second window, to the first `AuthorizeRelay` of an operation, so an operation that starts during a control plane deployment waits for the agent to reconnect. It keeps retrying while the sandbox is `UNREACHABLE`, because a control plane deployment makes the device offline until the agent reconnects. It stops at once on a terminal sandbox state, on any other error from `AuthorizeRelay` or from the relay, or when the caller cancels, and ends the operation with that error; it also ends the operation with the last error when the window ends. For a server-streaming continuation, the window's clock stops while a continuation that the agent accepted (with its `accepted` event) stays open and keeps receiving frames; a stream that receives no byte of its response body (not even of a relay `keepalive` or of a large chunk still in transit) for 90 seconds counts as a transport interruption, and the SDK cancels it and continues from the delivered offsets, and the window ends when the continuation delivers data (exec output, an exec result or a complete file chunk; the resume offset advances only after a complete chunk) or, under the rule below, when an accepted continuation ends with a clean rotation; an interrupted continuation without data resumes the same window. When an accepted continuation ends again without data, the clock resumes, so repeated interruptions at the same offset end the operation within the window. The control plane's own relay `keepalive` events do not count. The window ends when the caller receives data or a terminal operation result, or when an accepted continuation ends with a clean stream rotation; a `paused` event from an accepted `AttachExec` continuation ends the window too, and the SDK then waits for the sandbox to resume, end or the caller to cancel, as the [exec state rules](protos-ownsand-api-contract.md#sandbox-state-rules) require; an `accepted` event only pauses it, also for a silent command, whose accepted continuation can stay open with keepalives as long as needed. Each `WriteFile` attempt has an SDK-side deadline of 5 minutes 30 seconds; when it passes without a response, the SDK cancels the attempt and treats it as a retryable transport interruption while the caller's context is active. For a `WriteFile` chunk, one recovery budget of 60 seconds applies to the unacknowledged chunk until the agent acknowledges it: the SDK starts a new attempt only while that budget lasts, an attempt that started in time may run until the control plane's 5-minute relay `WriteFile` call limit, which includes the agent's result, and only an acknowledged chunk resets the budget. The SDK sends the chunks of one `write_id` one at a time. Every renewal, in recovery or not, passes the grant that it replaces as `replaces_grant_id`. It generates a new `authorization_id` for each `AuthorizeRelay` request and reuses it for every retry of that request after a lost response or a retryable result (`unavailable` or `resource_exhausted`), so that a grant that the agent installed late is returned and not created twice. The continuation rules are: an exec before `started` with `AttachExec` from offset zero first, and with the identical `ExecRequest` only when `AttachExec` fails with `not_found` (on a `PAUSED` sandbox without an exec record, the SDK ends the recovery window and waits for the sandbox to resume; on resume, it authorizes again if needed and sends the identical `ExecRequest` while the `exec_id` is still within the expired operation ID rules), an exec after `started` with `AttachExec` from the received stdout and stderr offsets, a read with the same `read_id`, path and salt from the next undelivered offset, and a write with its unacknowledged chunk or `finish` request. It never resends a request that would deliver bytes that the caller already received.
- The SDK sends its API key or Logto access token, also on relay RPCs, only to the configured API origin.
- When the data channel does not open within 10 seconds, or fails during a session, the SDK uses the relay RPCs for that sandbox handle. The SDK never runs an exec again, because the command may have run. It continues the exec with the same rules as relay recovery: before the `started` event arrives, it tries `AttachExec` from offset zero first and sends the identical `ExecRequest` (the same `exec_id` makes this safe) only when `AttachExec` fails with `not_found`; after `started`, it continues with `AttachExec`. The SDK generates the `exec_id` before it sends an exec, so it can continue an exec that was in progress with `AttachExec` on the relay, also when the stream ended before the `started` event. It generates a `read_id` for each file read and continues the read from the next offset with the same `read_id`. After `started` was received, or for an attach-only caller without the original request, an `AttachExec` that fails with `not_found` ends the exec with a data path error and an unknown outcome; before `started`, the SDK sends the identical `ExecRequest` as described above.
- A relay stream can end before the operation ends because of the control plane's relay stream limits, a control plane restart or a session-end frame. The SDK continues it with `AttachExec` or `ReadFile` from the next offset without a visible error, after a new `AuthorizeRelay` when the grant expired or a session-end frame ended the stream. A `ReadFile` that fails with `not_found` because its `read_id` expired is a visible error.
- After any session end (15 minutes idle, the 1-hour absolute expiry, a revocation or the agent losing its channel), the SDK opens a new session only when an operation is open or the caller starts one, so that an idle handle never keeps the sandbox active. It then calls `GetIceServers` and `OpenSession` and tries peer-to-peer again; a handle on the relay calls `AuthorizeRelay` again. It continues every operation that was open on the ended session on the new session: an exec with `AttachExec` from the received offsets, a file read with the same `read_id` from the next offset and a file write with its unacknowledged request. When a new session cannot be authorized, those operations end with that authorization error. Only an ICE failure, or a new session that cannot open, moves the handle to the relay. The SDK recognizes a session end by the session-end frame that the agent sends before it closes the data channel; a data channel that closes without that frame is a failure. A revoked credential then fails with `unauthenticated` or `permission_denied`, and a user whose membership ended gets `not_found`, according to the [control plane authorization rules](servers-ownsand-api-foundation.md#authorization).
- The caller can force a transport (`PEER_TO_PEER` or `RELAY`) for tests. The SDK reports the transport in use.
- Both transports carry the same `DataFrame` messages and give the same results.
- Recorded classification of the TypeScript SDK: a transport interruption without a valid terminal status is a failed `fetch` or response body read (Connect reports it with the original error as `cause`), a server stream without its end-of-stream message, a stream that the SDK cancelled at the 90-second idle limit or at the `WriteFile` attempt deadline, and an `aborted` status without an OwnSand `ErrorDetail`. An `aborted` status that carries an `ErrorDetail` is an explicit, terminal result. A relay stream that ends with OK before `accepted` is a failure under relay recovery. The back-off between recovery attempts starts at 500 milliseconds and doubles up to 5 seconds within the window; a `paused` sandbox is polled with `GetSandbox` from every 2 seconds up to every 10 seconds.
- Peer-to-peer data channel (recorded, both SDKs): the caller is the offerer and creates one data channel labeled `ownsand-data`, ordered and reliable (no `maxRetransmits` or `maxPacketLifeTime`), not pre-negotiated. Signaling is non-trickle: the offer is sent after ICE gathering completes. The ICE servers come from `GetIceServers`. The caller allocates `stream_id` values from 1 in increasing order within a session. The data channel uses no credit windows; it relies on the SCTP flow control of the reliable channel, and the sender waits while the channel buffers more than 1 MiB. An `OpenSession` that fails with `unauthenticated`, `permission_denied`, `not_found`, `invalid_argument` or `failed_precondition` is an authorization error that ends the operation; any other `OpenSession` failure, an ICE gathering that does not complete in 10 seconds and a data channel that does not open within 10 seconds of the start of the session move the handle to the relay.

## Storage

The SDKs persist nothing. They keep sessions and credentials in memory only.

## Security

- Credentials stay in memory. The SDKs never write them to disk or logs.
- The SDKs connect only to the configured API origin (also for the relay), the STUN servers that `GetIceServers` returns and the agent's ICE candidates.
- The data channel accepts only the DTLS fingerprint in the agent's answer that `OpenSession` returned over the authenticated control plane connection.

## Logging

The SDKs log nothing by default. An optional logger receives RPC names, sandbox IDs, transport selection, durations and Connect codes, never credentials, exec content or file content.

## Dependencies and Integrations

- Upstream: the [control plane](servers-ownsand-api-foundation.md) (API, relay and STUN) and the [protos contract](protos-ownsand-api-contract.md).
- Peers: the [device agent](cmds-ownsand-agent-foundation.md#data-path).
- Downstream: the [CLI](cmds-ownsand-cli-foundation.md) uses the Go SDK.
- Publication: the workspace package is named `ownsand-sdk` and is `private`, so neither pnpm nor Changesets publishes it. The npm package name and publication workflow of the TypeScript SDK stay an [open decision](project-ownsand.md#open-decisions); the repository publishes no packages to a registry today. The Go SDK needs no publication, because it is part of the root Go module.
- New dependencies: Connect and protobuf runtimes for both languages and pion for Go; the owner approved them with the OwnSand implementation. Go SDK pins: `github.com/pion/webrtc/v4` `v4.2.26` (released 2026-10-28) with its pion modules, and `golang.org/x/net` `v0.62.0`, `golang.org/x/crypto` `v0.58.0` and `golang.org/x/sys` `v0.49.0`, raised above the versions that pion requires because `govulncheck` reported reachable or known advisories in the older versions. TypeScript SDK pins (exact versions, each released at least two weeks before it was pinned): `@bufbuild/protobuf` `2.16.0`, `@connectrpc/connect` `2.3.0` and `@connectrpc/connect-web` `2.3.0` (runtime), and `@bufbuild/protoc-gen-es` `2.16.0` (generation). The TypeScript SDK adds no WebRTC library (see [Runtime and Language](#runtime-and-language)). Record the audit result of each dependency change (`govulncheck`, `pnpm audit`) in the pull request, according to the [dependency security contract](repository-dependency-security-contract.md).
