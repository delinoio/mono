# packages-ownsand-sdk foundation contract

## Scope

This contract owns the two OwnSand SDKs of [`ownsand`](project-ownsand.md):

- `packages/ownsand-sdk/` (`planned`): TypeScript SDK, component `ownsand-sdk-ts`.
- `packages/ownsand-sdk-go/` (`planned`): Go SDK, component `ownsand-sdk-go`, import path `github.com/delinoio/mono/packages/ownsand-sdk-go`.

Both SDKs give programs and the [CLI](cmds-ownsand-cli-foundation.md) one client for the public API of the [protos contract](protos-ownsand-api-contract.md), including the data path. Both use Apache-2.0.

## Runtime and Language

- TypeScript SDK: ES modules for Node.js 24 (the `.nvmrc` baseline). It uses Connect for ECMAScript with the TypeScript bindings generated from the schemas. Record where the generated TypeScript code lives with the first schema. Browser support is not part of this version; the web console uses the generated bindings with `@connectrpc/connect-query` directly.
- Go SDK: Go in the root module. It uses the committed Go bindings in `protos/delino/ownsand/v1/` and does not generate code.
- Node.js has no built-in WebRTC implementation, so the TypeScript SDK's peer-to-peer data path needs a WebRTC library. The library is an open decision and a new dependency. Until it is approved, the TypeScript SDK uses the relay only.
- The Go SDK uses pion for the peer-to-peer data path. pion is a new dependency that needs owner approval.

## Users and Operators

- Programs that use an organization API key: CI jobs, AI agents and services.
- People who use a Logto access token that their own program obtained.
- The [CLI](cmds-ownsand-cli-foundation.md), which is built on the Go SDK.

## Interfaces and Contracts

### Client construction

- The client takes the API origin (default `https://ownsand.api.delino.io`) and one credential: an API key or a function that returns a current Logto access token.
- Without an explicit credential, both SDKs read the `OWNSAND_API_KEY` environment variable. They read no other environment variables for credentials.
- The client takes an optional organization ID and uses it for every RPC that needs one; without it, the SDKs read `OWNSAND_ORG`. A call can override it. An RPC that needs an organization fails before it is sent when neither is set.
- The client never logs or includes the credential in errors.

### Operations

The SDKs expose the public services of the [protos contract](protos-ownsand-api-contract.md#public-services) with idiomatic names, and a sandbox handle with these operations:

- `create`, `get`, `list`, `delete`, `pause`, `resume`.
- `exec`: returns a stream of stdout and stderr chunks and the exit code or the signal. A command that could not start is a distinct `failed` result with its reason, not an exit code and not a data path error. A command that the exec `timeout` stopped has the `timed_out` flag set on its result. An exec that ends with a `sandbox_ended` event is a distinct result with the `SandboxEndReason`. A data path failure is an error, never an exit code. When a continuation loses output (`output_truncated`), the stream reports a truncation event with the missing offsets, and the result is marked incomplete; the SDK never presents truncated output as complete.
- `readFile` and `writeFile` (Go: `ReadFile` and `WriteFile`): stream contents in chunks and accept readers and byte buffers. `writeFile` uploads in chunks and finishes the write only after the last chunk, as the [file transfer contract](protos-ownsand-api-contract.md#file-transfer) requires. The SDK keeps the `write_id`, the offset and the chunk or `finish` request that is not acknowledged yet. After a failure or a session end, it sends that exact request again, on the new session or on the relay, before it reads more input.
- `snapshot`, plus snapshot export and template operations.

`create` requires `idleTtl` and `maxTtl` (Go: `IdleTTL` and `MaxTTL`) and the resources. The SDK generates one `idempotency_key` for each logical create and reuses it for every retry of that create. The SDKs do not supply a default TTL.

### Data path

- For exec and file operations, an SDK that supports peer-to-peer calls `GetIceServers` and then `OpenSession` once per sandbox handle and tries a WebRTC data channel to the agent. A relay-only SDK, and a client with the transport forced to `RELAY`, does not call `OpenSession`; it uses the relay directly.
- Relay: for each exec, file read and file write, the SDK calls `AuthorizeRelay` on the control plane with the operation kind, the `exec_id`, `read_id` or `write_id`, and the request digest of the [protos contract](protos-ownsand-api-contract.md#relay-tickets), and then calls the `RelayService` RPCs of that operation at the returned relay origin with the `CALLER` relay ticket. To attach to an exec that it did not start or whose request fields it no longer has, it uses an `ATTACH_EXEC` grant with only the `exec_id`. It uses the ticket only for that operation. It measures the ticket's remaining lifetime from `expires_in` on its monotonic clock from receipt, so a caller clock offset does not change renewal. When it must start a new stream (at a stream rotation, at the next `WriteFile` chunk or `ReadFile` call of the operation, or in recovery) and the ticket has expired or expires before the new stream can end, or the last stream of the operation ended more than 60 seconds ago (the agent may have released the idle grant and closed its relay connection) (within the relay server's 14-minute stream limit plus 30 seconds for a server stream, and within the 5-minute call limit plus 30 seconds for a `WriteFile` chunk), so in practice at every rotation, it renews it with `AuthorizeRelay` for the same operation and `replaces_ticket_id` set to the ticket that it renews; it never renews while a stream of the old grant is open. Because the SDK renews only when no stream of the old grant is open, a `GRANT_REPLACED` on its own stream means that another renewal replaced the grant, and the SDK handles it as a failure under relay recovery. When it renews a ticket outside recovery (before the next `WriteFile` chunk or `ReadFile` call), it applies the same authorization retries as at startup and in recovery (`unavailable`, `resource_exhausted` and an `AuthorizeRelay` call that ends with a transport interruption without a valid terminal status) within a 60-second window, and keeps the same `authorization_id` and `replaces_ticket_id` for each retry. The agent may release a ticket's grant after 60 seconds without an open stream; the SDK then gets `GRANT_INVALID` and renews it through recovery.
- Stream rotation: a relay stream that the agent accepted (with its `accepted` event) and that ends with an OK status and no final event is a routine rotation at the relay server's stream limit. The SDK continues the operation at once with the continuation rules below, as often as needed, and a rotation does not count as a failure.
- Relay recovery: a failure is a relay RPC that ends with a transport interruption and no valid terminal Connect status (for example, a connection that closes during a relay server restart and surfaces as `aborted`, or a stream that ends without its end-of-stream message), or that fails with `unavailable` (for example with `AGENT_CHANNEL_LOST` or `GRANT_INVALID` after a control plane deployment ended the grant, a connection failure during a relay server restart, or no connection from the agent), or with `unauthenticated` from the relay origin (for example, a ticket that expired in transit), or a `WriteFile` call that fails with `deadline_exceeded` because the call, including the upload and the agent's result, took longer than the relay server's 5-minute limit (the SDK resends the same unacknowledged chunk with the same `write_id`). After a failure, the SDK starts one recovery window of 60 seconds. In that window it discards the ticket, calls `AuthorizeRelay` again and continues the operation, and it repeats these steps with back-off while `AuthorizeRelay` or the continuation fails with `unavailable` or ends with a transport interruption without a valid terminal status, while the continuation fails with `unauthenticated` from the relay origin (an `unauthenticated` from the control plane is terminal) or ends again with a transport interruption without a valid terminal status (an `aborted` status that the guest helper returns explicitly, for example for a file that changed during a read, is terminal), or `AuthorizeRelay` fails with `resource_exhausted` (it waits at least the retry delay in the error detail). The SDK applies the same `unavailable` and `resource_exhausted` retries, and the retry of an `AuthorizeRelay` call that ends with a transport interruption without a valid terminal status (with the same `authorization_id` and `replaces_ticket_id`), within a 60-second window, to the first `AuthorizeRelay` of an operation, so an operation that starts during a control plane deployment waits for the agent to reconnect. It keeps retrying while the sandbox is `UNREACHABLE`, because a control plane deployment makes the device offline until the agent reconnects. It stops at once on a terminal sandbox state, on any other error from `AuthorizeRelay` or from the relay, or when the caller cancels, and ends the operation with that error; it also ends the operation with the last error when the window ends. For a server-streaming continuation, the window's clock stops while a continuation that the agent accepted (with its `accepted` event) stays open and keeps receiving frames; a stream that receives no frame (not even a relay `keepalive`) for 90 seconds counts as a transport interruption, and the SDK cancels it and continues from the delivered offsets, and the window ends only when the continuation delivers data (exec output, an exec result or a file chunk). When an accepted continuation ends again without data, the clock resumes, so repeated interruptions at the same offset end the operation within the window. The relay server's own `keepalive` events do not count. The window ends when the caller receives data or a terminal operation result, or when an accepted continuation ends with a clean stream rotation; a `paused` event from an accepted `AttachExec` continuation ends the window too, and the SDK then waits for the sandbox to resume, end or the caller to cancel, as the [exec state rules](protos-ownsand-api-contract.md#sandbox-state-rules) require; an `accepted` event only pauses it, also for a silent command, whose accepted continuation can stay open with keepalives as long as needed. Each `WriteFile` attempt has an SDK-side deadline of 5 minutes 30 seconds; when it passes without a response, the SDK cancels the attempt and treats it as a retryable transport interruption while the caller's context is active. For a `WriteFile` chunk, one recovery budget of 60 seconds applies to the unacknowledged chunk until the agent acknowledges it: the SDK starts a new attempt only while that budget lasts, an attempt that started in time may run until the relay server's 5-minute `WriteFile` call limit, which includes the agent's result, and only an acknowledged chunk resets the budget. The SDK sends the chunks of one `write_id` one at a time. Every renewal, in recovery or not, passes the ticket that it replaces as `replaces_ticket_id`. It generates a new `authorization_id` for each `AuthorizeRelay` request and reuses it for every retry of that request after a lost response or a retryable result (`unavailable` or `resource_exhausted`), so that a grant that the agent installed late is returned and not created twice. The continuation rules are: an exec before `started` with `AttachExec` from offset zero first, and with the identical `ExecRequest` only when `AttachExec` fails with `not_found` (on a `PAUSED` sandbox without an exec record, the SDK ends the recovery window and waits for the sandbox to resume; on resume, it authorizes again if needed and sends the identical `ExecRequest` while the `exec_id` is still within the expired operation ID rules), an exec after `started` with `AttachExec` from the received stdout and stderr offsets, a read with the same `read_id`, path and salt from the next undelivered offset, and a write with its unacknowledged chunk or `finish` request. It never resends a request that would deliver bytes that the caller already received.
- The SDK sends the ticket only to the returned relay origin, and sends its API key or Logto access token only to the configured API origin.
- When the data channel does not open within 10 seconds, or fails during a session, the SDK uses the relay RPCs for that sandbox handle. The SDK never runs an exec again, because the command may have run. It continues the exec with the same rules as relay recovery: before the `started` event arrives, it tries `AttachExec` from offset zero first and sends the identical `ExecRequest` (the same `exec_id` makes this safe) only when `AttachExec` fails with `not_found`; after `started`, it continues with `AttachExec`. The SDK generates the `exec_id` before it sends an exec, so it can continue an exec that was in progress with `AttachExec` on the relay, also when the stream ended before the `started` event. It generates a `read_id` for each file read and continues the read from the next offset with the same `read_id`. After `started` was received, or for an attach-only caller without the original request, an `AttachExec` that fails with `not_found` ends the exec with a data path error and an unknown outcome; before `started`, the SDK sends the identical `ExecRequest` as described above.
- A relay stream can end before the operation ends because of the relay server's stream limits, a relay server restart or a session-end frame. The SDK continues it with `AttachExec` or `ReadFile` from the next offset without a visible error, after a new `AuthorizeRelay` when the ticket expired or a session-end frame ended the stream. A `ReadFile` that fails with `not_found` because its `read_id` expired is a visible error.
- After any session end (15 minutes idle, the 1-hour absolute expiry, a revocation or the agent losing its channel), the SDK opens a new session only when an operation is open or the caller starts one, so that an idle handle never keeps the sandbox active. It then calls `GetIceServers` and `OpenSession` and tries peer-to-peer again; a handle on the relay calls `AuthorizeRelay` again. It continues every operation that was open on the ended session on the new session: an exec with `AttachExec` from the received offsets, a file read with the same `read_id` from the next offset and a file write with its unacknowledged request. When a new session cannot be authorized, those operations end with that authorization error. Only an ICE failure, or a new session that cannot open, moves the handle to the relay. The SDK recognizes a session end by the session-end frame that the agent sends before it closes the data channel; a data channel that closes without that frame is a failure. A revoked credential then fails with `unauthenticated` or `permission_denied`, and a user whose membership ended gets `not_found`, according to the [control plane authorization rules](servers-ownsand-api-foundation.md#authorization).
- The caller can force a transport (`PEER_TO_PEER` or `RELAY`) for tests. The SDK reports the transport in use.
- Both transports carry the same `DataFrame` messages and give the same results.

## Storage

The SDKs persist nothing. They keep sessions and credentials in memory only.

## Security

- Credentials stay in memory. The SDKs never write them to disk or logs.
- The SDKs connect only to the configured API origin, the relay origin that `AuthorizeRelay` returns, the STUN servers that `GetIceServers` returns and the agent's ICE candidates.
- The data channel accepts only the DTLS fingerprint in the agent's answer that `OpenSession` returned over the authenticated control plane connection.

## Logging

The SDKs log nothing by default. An optional logger receives RPC names, sandbox IDs, transport selection, durations and Connect codes, never credentials, exec content or file content.

## Dependencies and Integrations

- Upstream: the [control plane](servers-ownsand-api-foundation.md), the [relay server](servers-ownsand-relay-foundation.md) and the [protos contract](protos-ownsand-api-contract.md).
- Peers: the [device agent](cmds-ownsand-agent-foundation.md#data-path).
- Downstream: the [CLI](cmds-ownsand-cli-foundation.md) uses the Go SDK.
- Publication: the npm package name and publication workflow of the TypeScript SDK are an [open decision](project-ownsand.md#open-decisions); the repository publishes no packages to a registry today. The Go SDK needs no publication, because it is part of the root Go module.
- New dependencies: Connect and protobuf runtimes for both languages, pion for Go and a WebRTC library for Node.js. Each needs owner approval.

## Change Triggers

- Update this contract with every public RPC change in the [protos contract](protos-ownsand-api-contract.md).
- Update the [CLI contract](cmds-ownsand-cli-foundation.md) when the Go SDK surface that the CLI uses changes.
- Update [project-ownsand.md](project-ownsand.md) when the package paths, the publication target or the data path changes.
- Update `packages/AGENTS.md` only under the [instruction-update policy](README.md#instruction-update-policy).
