# apps-ownsand-console foundation contract

## Scope

This contract owns the OwnSand web console, component `ownsand-console`, of [`ownsand`](project-ownsand.md) at `apps/ownsand/` (workspace package `ownsand-console`). The console is served at `https://ownsand.delino.io`. It manages organizations, members, devices, enrollment tokens, API keys, the agent version policy and the billing account link, shows the billing status and usage, and lists sandboxes. It uses Apache-2.0.

## Runtime and Language

- Rsbuild React single-page application in TypeScript, like the [`delino-accounts` web app](apps-delino-accounts-foundation.md). It is an authenticated application, so it uses Rsbuild instead of Rspress.
- Deployment: static output on Cloudflare Pages through the [deployment workflow](repository-workflow-contract.md#deployment-workflow). The `deploy` field of `apps/ownsand/package.json` names the Pages project `ownsand-console`, which must exist before the first deployment, and its `buildEnv` maps `PUBLIC_LOGTO_ENDPOINT` to the repository variable `LOGTO_ENDPOINT` and `PUBLIC_LOGTO_APP_ID` to `OWNSAND_CONSOLE_LOGTO_APP_ID`, so a production build always has the sign-in configuration and a missing variable fails the deployment (see [Deployment environments](repository-workflow-contract.md#deployment-environments)). The production build uses the defaults of `PUBLIC_API_ORIGIN` and `PUBLIC_LOGTO_SCOPES`. `public/_headers` sets `X-Content-Type-Options`, `Referrer-Policy` and `X-Frame-Options: DENY`; the output has no top-level `404.html`, so Cloudflare Pages serves the single-page-application fallback.
- Server state: React Query with `@connectrpc/connect-query` and the TypeScript bindings from the [protos contract](protos-ownsand-api-contract.md), imported from the workspace package `@delino/ownsand-protos` (`@delino/ownsand-protos/v1/<file>_pb`). The console imports only the generated bindings and does not depend on the SDK client. The transport is `@connectrpc/connect-web` with the binary Connect protocol. Queries retry only `unavailable` (twice); mutations never retry. A mutation invalidates the queries of every service whose data it changes: removing a device also invalidates the sandbox and snapshot queries (its sandboxes end, and the snapshots and templates that exist only on it are deleted), and creating or deleting a sandbox also invalidates the device queries (the device allocation changes; a sandbox that is still `DELETING` after `DeleteSandbox` invalidates them again when its polled state settles). These extra invalidations are not awaited, so the page that follows does not wait for them. After `RemoveDevice` succeeds, the console refreshes device, sandbox and snapshot queries in the background. If the confirmation is still current, the console opens the organization's Devices page even while the device detail refresh is pending. Creating a sandbox does not await the invalidation of the sandbox list either: the dialog closes and the console opens the new sandbox from the `CreateSandbox` response while the list refetches in the background. After a successful `CreateOrganization` call, the console refreshes the organization list and the switcher in the background, even if the user dismissed the create form. The console opens the new organization's Sandboxes page when the response contains a UUID v7 organization ID and the submitting form is still open. If the response lacks a valid ID, the open form keeps the entered name and tells the user to close it and check the organization list before retrying. Leaving an organization and deleting one navigate to `/` first and refresh the cache afterwards without waiting for it: the caller has no access to the organization after the call, so waiting for a refetch of its queries would fail with `not_found` and render the "It was not found, or you no longer have access to it." notice before the navigation. A page shows the full-page error notice only when its query has no loaded data (the first load failed) or the error is terminal: `not_found`, `permission_denied` or `unauthenticated`, which a retry cannot fix, so loaded data must not stay on screen. Every other error of a refetch (a network failure, `unavailable`, `internal`, a deadline) is transient: React Query keeps the loaded data next to the error, so the organization shell and each page keep their content, navigation, open dialogs and typed values mounted and show a non-blocking "The last refresh failed" notice with "Try again" above the content. The next successful fetch clears the notice. One shared helper in `src/components/ui.tsx` (`QueryBoundary`, with `showsFullError` and `RefreshFailedNotice` for the shell and the pages that keep their own layout) owns this rule; retry, `staleTime` and polling are unchanged.
- Routing: a small history-API router in `src/router.tsx` with the route IDs below; no routing library.
- UI components: [`delino-ui`](packages-delino-ui-foundation.md).
- Development URL: `pnpm --filter ownsand-console dev` runs the console through portless at `https://ownsand.delino.localhost`, in every checkout. `dev:app`, and `dev` with `PORTLESS=0`, use the fixed port `127.0.0.1:13300` (`strictPort`). Both are recorded in the [environment contract](repository-environment-contract.md#frontend-development-urls). Sign-in in development uses the console origin of the run, so the Logto development application must list `https://ownsand.delino.localhost/callback` and `https://ownsand.delino.localhost` (and the `http://127.0.0.1:13300` equivalents for `dev:app`).

## Users and Operators

Organization owners, admins and members who sign in with Logto. API keys do not sign in to the console.

## Interfaces and Contracts

- The console calls the control plane only through its absolute origin. It reads the origin from `PUBLIC_API_ORIGIN` and uses `https://ownsand.api.delino.io` when the value is not set. It must not import source from `servers/`.
- Authentication: the console is a Logto single-page application (`@logto/react`) that requests access tokens for the API resource `https://ownsand.api.delino.io`. The sign-in redirect URI is `<console origin>/callback` and the post sign-out redirect URI is the console origin; register both in the Logto application. The Logto SDK keeps its session in the browser. Recorded decision: the console always requests the scope `ownsand:use`, which the [control plane](servers-ownsand-api-foundation.md#authentication) requires in every user access token. The tenant endpoint, the application ID and any extra scopes are build-time configuration (`PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, `PUBLIC_LOGTO_SCOPES`, space-separated), because the Logto application registration is not recorded yet. The deployment workflow maps them to the repository variables `LOGTO_ENDPOINT` (`PUBLIC_LOGTO_ENDPOINT`) and `OWNSAND_CONSOLE_LOGTO_APP_ID` (`PUBLIC_LOGTO_APP_ID`), as the Deployment entry above and [Deployment environments](repository-workflow-contract.md#deployment-environments) describe, and a variable that is unset or blank stops the deployment build before Turbo runs, so the source carries no default for them. A local build without the endpoint or the application ID shows that sign-in is not configured instead of failing, but a supplied endpoint that is not a valid origin fails the build or development server whether or not the application ID is set. The Logto SDK reports `isLoading` for every token request, not only while it restores the session, so the console reports loading to its pages only until the SDK has restored the session for the first time. A token request that a page makes must not unmount that page; otherwise the page mounts again, requests the token again, and the console renders without end. `useHandleSignInCallback` reports nothing when no sign-in redirect is pending, and `@logto/react` exposes neither its client nor `isSignInRedirected`. Recorded decision: the callback page decides once on mount whether a redirect is pending by applying the rule of `isSignInRedirected` to the SDK's stored sign-in session in `sessionStorage` (key `logto:<application ID>:signInSession`, or the legacy key `logto:<application ID>`; the session's `redirectUri` must equal the origin and path of the address for the session to count as pending; a stored value that is not JSON, or not an object whose `redirectUri`, `codeVerifier` and `state` are all strings, is an unreadable session, which the SDK client rejects with `sign_in_session.invalid`). The hook of `@logto/react` awaits `isSignInRedirected` outside its error handling, so for an unreadable session it would raise an unhandled rejection and leave the page blank. The callback page therefore does not mount the hook for an unreadable session: it shows the sign-in error notice, stays on `/callback`, and removes the pending invitation secret. The console does not delete the unreadable session; the next sign-in start overwrites it. It does not rely on `isLoading`, which is `false` for a render while a real redirect starts, and it does not read `code`, `state` or `error` from the address, because the SDK ignores them without a stored session. A visit with no redirect pending navigates with `replace` to the post-sign-in target. Remove this check when `@logto/react` exposes the client or the pending state. When a request fails with `unauthenticated`, which includes an ended Logto session whose token request fails (the SDK keeps reporting the user as signed in, so the signed-out view never shows), the error notice offers "Sign in with Delino" instead of "Try again"; the console never signs the user in or out automatically and clears no token. On the invitation page that sign-in first stores the pending invitation secret again, because the accept handler deleted the stored copy after the failure, so the secret survives the Logto sign-in redirect. A sign-in that fails before the redirect starts (for example because the Logto tenant is unreachable) does not reject: the Logto SDK stores the error and resolves. `Auth.signInFailed` is true when a new SDK error appears while the latest `signIn` call runs; an earlier error and the errors of token requests or the callback never set it, and the next `signIn` call clears it. The signed-out screen, "Sign in to accept" on the invitation page and every "Sign in with Delino" button of an ended-session notice (including the one on the invitation page) then show the fixed alert "Sign-in did not start. Check your connection and try again." next to the button, never the SDK error text, keep the button usable, and keep the pending invitation secret for the retry.
- Build-time variables (all public, inlined into the bundle, listed in `apps/ownsand/.env.example`): `PUBLIC_API_ORIGIN` (default `https://ownsand.api.delino.io`; an http or https origin without credentials, path, query, fragment or backslash, written exactly as `scheme://host[:port][/]`; the URL parser reads a backslash as a path separator and also accepts other slash counts after the scheme (`https:///host/a/..`, `https:host/a/..`) while it resolves dot segments away, so the check applies to the written text and rejects every such form. The written authority cannot contain an at-sign, an ASCII tab or an ASCII line break (CR or LF). Errors identify the variable and omit its value. `PUBLIC_LOGTO_ENDPOINT` follows the same rules), `PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, `PUBLIC_LOGTO_SCOPES` and `PUBLIC_OWNSAND_MOCK_API` (`true` or `false`). A plugin of `rsbuild.config.ts` (`src/config-plugin.ts`) validates them before compilation and fails the build or development server on an invalid value; it decides whether the build is a production build from the resolved Rsbuild mode (for example `--mode production`), not from the inherited `NODE_ENV`, because the bundle's `import.meta.env.PROD` follows the resolved mode. The development task passes them through Turbo `passThroughEnv`, and the build task declares them as `env`.
- Mock API (recorded decision): `PUBLIC_OWNSAND_MOCK_API=true` runs the console against an in-browser fake control plane (`src/mock/mock-api.ts`, a Connect router transport with seeded organizations, devices, sandboxes, snapshots, members, billing statuses and usage that applies the role matrix and the billing enforcement of resource creation) and the [scheduler](servers-ownsand-api-foundation.md#scheduler) rules of `CreateSandbox`: the guest OS comes from the source (a base image boots its own guest, a snapshot keeps its guest, a template has the guest of its snapshot, and a missing or unspecified source, an unknown snapshot or an unknown template fails with `invalid_argument` or `not_found`), a device can run the sandbox only when it advertises that guest in `capabilities.guest_oses` and, for a base-image source, lists the image in `capabilities.built_base_images`, an explicit `placement.device_id` is an exclusive selection, so an ID that names no visible device (a removed device included) fails with `not_found`, a device that cannot run the source fails with `failed_precondition`, a device that is not `ONLINE` fails with `unavailable`, and none of them creates a sandbox, stores the idempotency key or moves the request to another device, while a request without a device ID runs on the first `ONLINE` device that can run the source (and fails with `failed_precondition` when none can), and a fake signed-in user, for local UI work and the [end-to-end suite](#build-and-test). Every mock list that pages (`ListOrganizations`, `ListInvitations`, `ListEnrollmentTokens`, `ListApiKeys`, `ListSandboxes`, `ListSnapshots` and `ListTemplates`) follows the control plane: ascending ID order, 50 rows by default and at most 200, a token after every full page even when no row follows, no token after a short page, and `invalid_argument` for a negative `page_size` or a `page_token` that is not the opaque token of an ID (the unpadded base64url form of `v1:` and a UUID v7). `ListSnapshots` filters by `sandbox_id` and `device_id` before it pages, and `ListSandboxes` filters by state, device and `include_ended`. The mock creates every ID with a counter after the timestamp, so the ID order is the creation order and a created sandbox, snapshot, token or key is listed last. The console trims the setting once (`normalizeMockFlag` in `src/config.ts`) for both `readConsoleConfig` and the value that `rsbuild.config.ts` inlines, so the mock sign-in and the mock transport always follow the same decision. A build whose resolved mode is production rejects the setting (`true` after trimming) before compilation, whatever `NODE_ENV` the build inherits, and the mock module is a separate chunk that the minifier removes from every other build.
- The mock `CreateSandbox` applies the TTL rules in the [RPC contract](protos-ownsand-api-contract.md#create-request). It rejects missing, malformed or out-of-range TTLs with `invalid_argument` before it looks up the idempotency key or selects a device. The mock adds each full duration to the same creation timestamp, preserving nanoseconds in both initial deadlines.
- The mock `ListDevices` rejects an explicit `UNSPECIFIED` or unknown state with `invalid_argument` and the message `invalid state: must be a device state`. It accepts every defined nonzero state, even when no device matches. When the caller omits the state, the mock lists devices other than `REMOVED`.
- A successful mock `CreateSandbox` reserves its idempotency key for 24 hours in that organization, as specified in the [RPC contract](protos-ownsand-api-contract.md#create-request). During that period, the same parameters return the original sandbox and different parameters return `already_exists`. A replay keeps the original expiry. At or after expiry, a successful create with the same key starts a new reservation and keeps the original sandbox. A failed create leaves the expired key available.
- The mock API follows the control plane for member roles: `UpdateMemberRole` accepts only `ROLE_ADMIN` and `ROLE_MEMBER` and fails with `invalid_argument` for an omitted, unspecified, unknown or `ROLE_OWNER` role before it looks up the member, and a valid role for the current owner fails with `permission_denied`. `ListEnrollmentTokens` returns `EXPIRED` (a copy; the stored record stays pending) for an unused, unrevoked token at or after its `expire_time`, and keeps the state of a used or revoked token. `RevokeEnrollmentToken` of an already revoked token returns it unchanged, and a used token fails with `failed_precondition`. `AcceptInvitation` treats a pending invitation at or after its `expire_time` like an unknown secret (`not_found`, before the already-a-member check) and leaves the invitation pending and the memberships unchanged. `TransferOwnership` to the caller fails with `invalid_argument` after the owner check and before any change, so the roles and the billing status stay as they were.
- The mock `RemoveMember` checks caller permissions first. For an authorized caller, it returns `invalid_argument` with `invalid user_id: is required` for an empty ID or `not_found` with `member not found` for an unknown member. Both errors leave the member list unchanged.
- The mock `ListInvitations` checks organization membership and requires an owner or admin. It filters for pending invitations whose expiry is later than the request's cutoff before applying pagination. Listing leaves stored invitations and memberships intact.
- The mock `RevokeInvitation` uses the same pending and expiry check after it authorizes the caller and looks up the invitation. At or after expiry, or if the invitation is already accepted or revoked, it returns `failed_precondition` with `only a pending invitation can be revoked`. The rejection leaves the stored invitation and memberships unchanged.
- The mock `RevokeApiKey` authorizes the caller and looks up the key before changing it. The first successful call records `revoke_time`. Later calls to `RevokeApiKey` and `ListApiKeys` return that recorded time.
- The mock `RemoveDevice` records the same `end_time` for every sandbox it marks `DELETED` with `DEVICE_REMOVED` in one call. It preserves the lifecycle data of already deleted sandboxes and sandboxes on other devices.
- Account settings: the console links to `https://accounts.delino.io`. It has no profile or account pages.
- Member display names: `ListMembers` returns the display name of each member, which the control plane reads from the `delino-accounts` API. The console does not call the `delino-accounts` API and needs no token for it. It shows the Logto user ID when a member has no display name. It does not store profiles.
- Failed pages: an error notice offers no "Try again" button for `not_found` or `invalid_argument`, because the same request fails the same way; the organization failure notice always links to `/` ("Go to your organizations"), and the top bar switcher shows the placeholder "Choose an organization" instead of the raw ID when the route organization is not in a complete organization list (while pages still load or a later page fails with a transient error, it keeps the route ID); unit and end-to-end tests cover these cases.

- Recorded console behavior: the sandbox list filters by state and device and shows ended sandboxes only on request (`include_ended`), with "Show more" paging through `page_token`. An explicit continuation request takes priority over an in-flight poll for the selected organization and filters. While that continuation is pending, repeated activations and poll ticks do not start another request for it. A failed "Show more" request keeps the loaded rows and shows its error with a "Try again" button next to "Show more"; the button requests the failed `page_token` again (it does not read the first page again), a success appends the rows once and clears the error, and a terminal error (`not_found`, `permission_denied` or `unauthenticated`) still replaces the list with the full error notice; an `UNREACHABLE` sandbox shows its last known state. The create dialog requires the idle TTL (minutes) and the maximum TTL (hours, at most 168), checks that the idle TTL is not longer than the maximum TTL, takes the source (base image, template or ready snapshot), resources (the vCPU count is a whole number from 1 to 2147483647, the positive `int32` range of the request. Memory (MiB) is a whole number from 1 to 9007199254740991 (2^53 - 1), the largest value that the form holds exactly. Disk (GiB) is a whole number from 1 to 8589934591, the [control-plane limit](protos-ownsand-api-contract.md#create-request). An empty, decimal or out-of-range resource value shows a field error and prevents the create request; the memory field of the dialog has a minimum of 256 MiB and a `step` of 1, because the UI SDK also snaps a typed value to the `step` on Enter and blur: the arrow keys and the buttons move by 1, Shift moves by 256 and a typed 1000 stays 1000), network mode, an optional device and labels (`key=value` lines, with the warning that every member and API key can read them; a U+0000 character in a key or a value shows a field error on the Labels field and sends no request, as the control plane rejects it), and generates one UUID v7 `idempotency_key` for each opened dialog, which every retry of that create reuses. A ready snapshot in the source select reads `Snapshot <first 8 and last 4 characters of the id> · <creation time>` (the `ShortId` text), because UUID v7 ids that are created in the same 65.5 seconds share their first 8 characters; the option value stays `snapshot:<full id>`. Other lists request `page_size` 200 and show the first page unless described otherwise. The sandbox page shows a positive TTL below one second in whole milliseconds (`500 ms`) and a positive TTL below one millisecond as `<1 ms`, so it never reads as `0 s`; an absent TTL shows `—` and an exact zero shows `0 s`. The Source row of the sandbox page shows a template as `Template <name>` with the template id in the title of the name, and a snapshot as `Snapshot <ShortId text>` with the full id in its title; the page looks the name up in the first `ListTemplates` page (`page_size` 200) only for a template source, and while that request loads or fails, or when the page does not hold the template (deleted, or beyond the first page), the row shows `Template <ShortId text>` without a loading state, an error notice or a retry.

## Storage

The console stores nothing except the Logto SDK session state in the browser. It never stores API keys or enrollment tokens in browser storage. The only exception for invitation secrets is the short `sessionStorage` use during the sign-in redirect described above.

## Security

- Secrets appear once and are never stored by the console, except the short `sessionStorage` use of an invitation secret during the sign-in redirect described in [Interfaces and Contracts](#interfaces-and-contracts). The dialog opens with the focus on `Copy` (a `data-autofocus` attribute), not on `Done`, so one Enter or Space copies the secret and keeps the dialog open; one `Tab` reaches `Done`, and `Done`, `Esc` and a click outside still close it. The order of the buttons does not change.
- Destructive actions (device removal, API key revocation, enrollment token revocation, invitation revocation, organization deletion, ownership transfer and billing unlink) need an explicit confirmation step. Revoking a pending enrollment token and revoking a pending invitation each open a confirmation dialog first (Cancel first and focused, no request until the user confirms): the titles `Revoke token <token prefix>…?` and `Revoke invitation <invitation prefix>…?` name the displayed prefix, the confirm buttons read "Revoke token" and "Revoke invitation", the success toasts stay, and a failed revoke keeps the dialog open with its error notice and retries on a second confirm without an error toast.
- Every repeated row button has an accessible name that starts with its visible text and adds the visible identifier of its row, so a list of equal labels is distinguishable by name: `Export snapshot <short id>`, `Make template from snapshot <short id>` and `Delete snapshot <short id>` (the `ShortId` text), `Delete template <name> from snapshot <short id>`, `Revoke enrollment token <token prefix>`, `Revoke API key <name> (<key prefix>)`, `Remove <display name>` and `Revoke <role> invitation <invitation prefix>`; the visible text, the variants and the behavior do not change, and the snapshot delete confirmation reads `Delete the snapshot <short id>?`.
- When a confirmed action removes the element that opened a dialog (removing a member, revoking an invitation or an API key, transferring ownership), or navigates to another page (deleting or creating an organization), and nothing else holds the focus, the focus moves to the page heading (`main h1`) once the dialog has closed, instead of falling back to the page body. Every page heading has `tabindex="-1"`, so it is a focus target and not a Tab stop. The fallback never moves a focus that sits on an element, and it does not run on the first render.
- The console shows no exec output or file contents; it has no exec or file features in this version.

## Logging

The console sends no logs to a service in this version. Browser console messages never contain tokens or secrets.

- Global anchor styles: the unlayered `a`, `a:hover` and `a:focus-visible` rules in `src/index.css` use `a:where(:not(.dui-button))`, which excludes Button anchors and keeps the specificity of the plain `a` rules (one-class rules such as `.list-link` and `.button-link` still win), so the "Open billing" toast action (a `delino-ui` `Button` rendered as an anchor) keeps white text on the accent background in light and dark mode, while other links keep the link color and the hover underline. `src/anchor-style-guard.test.ts` guards the selectors and `e2e/toast-action-color.e2e.ts` and `e2e/anchor-rule-specificity.e2e.ts` check the computed colors.
