# apps-ownsand-console foundation contract

## Scope

This contract owns the OwnSand web console, component `ownsand-console`, of [`ownsand`](project-ownsand.md) at `apps/ownsand/` (workspace package `ownsand-console`). The console is served at `https://ownsand.delino.io`. It manages organizations, members, devices, enrollment tokens, API keys, the agent version policy and the billing account link, shows the billing status and usage, and lists sandboxes. It uses Apache-2.0.

## Runtime and Language

- Rsbuild React single-page application in TypeScript, like the [`delino-accounts` web app](apps-delino-accounts-foundation.md). It is an authenticated application, so it uses Rsbuild instead of Rspress.
- Deployment: static output on Cloudflare Pages through the [deployment workflow](repository-workflow-contract.md#deployment-workflow). The `deploy` field of `apps/ownsand/package.json` names the Pages project `ownsand-console`, which must exist before the first deployment, and its `buildEnv` maps `PUBLIC_LOGTO_ENDPOINT` to the repository variable `LOGTO_ENDPOINT` and `PUBLIC_LOGTO_APP_ID` to `OWNSAND_CONSOLE_LOGTO_APP_ID`, so a production build always has the sign-in configuration and a missing variable fails the deployment (see [Deployment environments](repository-workflow-contract.md#deployment-environments)). The production build uses the defaults of `PUBLIC_API_ORIGIN` and `PUBLIC_LOGTO_SCOPES`. `public/_headers` sets `X-Content-Type-Options`, `Referrer-Policy` and `X-Frame-Options: DENY`; the output has no top-level `404.html`, so Cloudflare Pages serves the single-page-application fallback.
- Server state: React Query with `@connectrpc/connect-query` and the TypeScript bindings from the [protos contract](protos-ownsand-api-contract.md), imported from the workspace package `@delino/ownsand-protos` (`@delino/ownsand-protos/v1/<file>_pb`). The console imports only the generated bindings and does not depend on the SDK client. The transport is `@connectrpc/connect-web` with the binary Connect protocol. Queries retry only `unavailable` (twice); mutations never retry. A mutation invalidates the queries of every service whose data it changes: removing a device also invalidates the sandbox and snapshot queries (its sandboxes end, and the snapshots and templates that exist only on it are deleted), and creating or deleting a sandbox also invalidates the device queries (the device allocation changes; a sandbox that is still `DELETING` after `DeleteSandbox` invalidates them again when its polled state settles). These extra invalidations are not awaited, so the page that follows does not wait for them. Creating a sandbox does not await the invalidation of the sandbox list either: the dialog closes and the console opens the new sandbox from the `CreateSandbox` response while the list refetches in the background. Creating an organization works the same way: the console opens the new organization's Sandboxes page from the `CreateOrganization` response and refreshes the organization list and the switcher in the background. Leaving an organization and deleting one navigate to `/` first and refresh the cache afterwards without waiting for it: the caller has no access to the organization after the call, so waiting for a refetch of its queries would fail with `not_found` and render the "It was not found, or you no longer have access to it." notice before the navigation. A page shows the full-page error notice only when its query has no loaded data (the first load failed) or the error is terminal: `not_found`, `permission_denied` or `unauthenticated`, which a retry cannot fix, so loaded data must not stay on screen. Every other error of a refetch (a network failure, `unavailable`, `internal`, a deadline) is transient: React Query keeps the loaded data next to the error, so the organization shell and each page keep their content, navigation, open dialogs and typed values mounted and show a non-blocking "The last refresh failed" notice with "Try again" above the content. The next successful fetch clears the notice. One shared helper in `src/components/ui.tsx` (`QueryBoundary`, with `showsFullError` and `RefreshFailedNotice` for the shell and the pages that keep their own layout) owns this rule; retry, `staleTime` and polling are unchanged.
- Routing: a small history-API router in `src/router.tsx` with the route IDs below; no routing library.
- UI components: [`delino-ui`](packages-delino-ui-foundation.md).
- Development URL: `pnpm --filter ownsand-console dev` runs the console through portless at `https://ownsand.delino.localhost`, in every checkout. `dev:app`, and `dev` with `PORTLESS=0`, use the fixed port `127.0.0.1:13300` (`strictPort`). Both are recorded in the [environment contract](repository-environment-contract.md#frontend-development-urls). Sign-in in development uses the console origin of the run, so the Logto development application must list `https://ownsand.delino.localhost/callback` and `https://ownsand.delino.localhost` (and the `http://127.0.0.1:13300` equivalents for `dev:app`).

## Users and Operators

Organization owners, admins and members who sign in with Logto. API keys do not sign in to the console.

## Interfaces and Contracts

- The console calls the control plane only through its absolute origin. It reads the origin from `PUBLIC_API_ORIGIN` and uses `https://ownsand.api.delino.io` when the value is not set. It must not import source from `servers/`.
- Authentication: the console is a Logto single-page application (`@logto/react`) that requests access tokens for the API resource `https://ownsand.api.delino.io`. The sign-in redirect URI is `<console origin>/callback` and the post sign-out redirect URI is the console origin; register both in the Logto application. The Logto SDK keeps its session in the browser. Recorded decision: the console always requests the scope `ownsand:use`, which the [control plane](servers-ownsand-api-foundation.md#authentication) requires in every user access token. The tenant endpoint, the application ID and any extra scopes are build-time configuration (`PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, `PUBLIC_LOGTO_SCOPES`, space-separated), because the Logto application registration is not recorded yet. The deployment workflow maps them to the repository variables `LOGTO_ENDPOINT` (`PUBLIC_LOGTO_ENDPOINT`) and `OWNSAND_CONSOLE_LOGTO_APP_ID` (`PUBLIC_LOGTO_APP_ID`), as the Deployment entry above and [Deployment environments](repository-workflow-contract.md#deployment-environments) describe, and a variable that is unset or blank stops the deployment build before Turbo runs, so the source carries no default for them. A local build without the endpoint or the application ID shows that sign-in is not configured instead of failing, but a supplied endpoint that is not a valid origin fails the build or development server whether or not the application ID is set. The Logto SDK reports `isLoading` for every token request, not only while it restores the session, so the console reports loading to its pages only until the SDK has restored the session for the first time. A token request that a page makes must not unmount that page; otherwise the page mounts again, requests the token again, and the console renders without end. `useHandleSignInCallback` reports nothing when no sign-in redirect is pending, and `@logto/react` exposes neither its client nor `isSignInRedirected`. Recorded decision: the callback page decides once on mount whether a redirect is pending by applying the rule of `isSignInRedirected` to the SDK's stored sign-in session in `sessionStorage` (key `logto:<application ID>:signInSession`, or the legacy key `logto:<application ID>`; the session's `redirectUri` must equal the origin and path of the address for the session to count as pending; a stored value that is not JSON, or not an object whose `redirectUri`, `codeVerifier` and `state` are all strings, is an unreadable session, which the SDK client rejects with `sign_in_session.invalid`). The hook of `@logto/react` awaits `isSignInRedirected` outside its error handling, so for an unreadable session it would raise an unhandled rejection and leave the page blank. The callback page therefore does not mount the hook for an unreadable session: it shows the sign-in error notice, stays on `/callback`, and removes the pending invitation secret. The console does not delete the unreadable session; the next sign-in start overwrites it. It does not rely on `isLoading`, which is `false` for a render while a real redirect starts, and it does not read `code`, `state` or `error` from the address, because the SDK ignores them without a stored session. A visit with no redirect pending navigates with `replace` to the post-sign-in target. Remove this check when `@logto/react` exposes the client or the pending state. When a request fails with `unauthenticated`, which includes an ended Logto session whose token request fails (the SDK keeps reporting the user as signed in, so the signed-out view never shows), the error notice offers "Sign in with Delino" instead of "Try again"; the console never signs the user in or out automatically and clears no token. On the invitation page that sign-in first stores the pending invitation secret again, because the accept handler deleted the stored copy after the failure, so the secret survives the Logto sign-in redirect. A sign-in that fails before the redirect starts (for example because the Logto tenant is unreachable) does not reject: the Logto SDK stores the error and resolves. `Auth.signInFailed` is true when a new SDK error appears while the latest `signIn` call runs; an earlier error and the errors of token requests or the callback never set it, and the next `signIn` call clears it. The signed-out screen, "Sign in to accept" on the invitation page and every "Sign in with Delino" button of an ended-session notice (including the one on the invitation page) then show the fixed alert "Sign-in did not start. Check your connection and try again." next to the button, never the SDK error text, keep the button usable, and keep the pending invitation secret for the retry.
- Build-time variables (all public, inlined into the bundle, listed in `apps/ownsand/.env.example`): `PUBLIC_API_ORIGIN` (default `https://ownsand.api.delino.io`; an http or https origin without credentials, path, query, fragment or backslash, written exactly as `scheme://host[:port][/]`; the URL parser reads a backslash as a path separator and also accepts other slash counts after the scheme (`https:///host/a/..`, `https:host/a/..`) while it resolves dot segments away, so the check applies to the written text and rejects every such form; `PUBLIC_LOGTO_ENDPOINT` follows the same rule), `PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, `PUBLIC_LOGTO_SCOPES` and `PUBLIC_OWNSAND_MOCK_API` (`true` or `false`). A plugin of `rsbuild.config.ts` (`src/config-plugin.ts`) validates them before compilation and fails the build or development server on an invalid value; it decides whether the build is a production build from the resolved Rsbuild mode (for example `--mode production`), not from the inherited `NODE_ENV`, because the bundle's `import.meta.env.PROD` follows the resolved mode. The development task passes them through Turbo `passThroughEnv`, and the build task declares them as `env`.
- Mock API (recorded decision): `PUBLIC_OWNSAND_MOCK_API=true` runs the console against an in-browser fake control plane (`src/mock/mock-api.ts`, a Connect router transport with seeded organizations, devices, sandboxes, snapshots, members, billing statuses and usage that applies the role matrix and the billing enforcement of resource creation) and the [scheduler](servers-ownsand-api-foundation.md#scheduler) rules of `CreateSandbox`: the guest OS comes from the source (a base image boots its own guest, a snapshot keeps its guest, a template has the guest of its snapshot, and a missing or unspecified source, an unknown snapshot or an unknown template fails with `invalid_argument` or `not_found`), a device can run the sandbox only when it advertises that guest in `capabilities.guest_oses` and, for a base-image source, lists the image in `capabilities.built_base_images`, an explicit `placement.device_id` is an exclusive selection, so an ID that names no visible device (a removed device included) fails with `not_found`, a device that cannot run the source fails with `failed_precondition`, a device that is not `ONLINE` fails with `unavailable`, and none of them creates a sandbox, stores the idempotency key or moves the request to another device, while a request without a device ID runs on the first `ONLINE` device that can run the source (and fails with `failed_precondition` when none can), and a fake signed-in user, for local UI work and the [end-to-end suite](#build-and-test). Every mock list that pages (`ListOrganizations`, `ListEnrollmentTokens`, `ListApiKeys`, `ListSandboxes` and `ListSnapshots`) follows the control plane: ascending ID order, 50 rows by default and at most 200, a token after every full page even when no row follows, no token after a short page, and `invalid_argument` for a negative `page_size` or a `page_token` that is not the opaque token of an ID (the unpadded base64url form of `v1:` and a UUID v7). `ListSnapshots` filters by `sandbox_id` and `device_id` before it pages, and `ListSandboxes` filters by state, device and `include_ended`. The mock creates every ID with a counter after the timestamp, so the ID order is the creation order and a created sandbox, snapshot, token or key is listed last. The console trims the setting once (`normalizeMockFlag` in `src/config.ts`) for both `readConsoleConfig` and the value that `rsbuild.config.ts` inlines, so the mock sign-in and the mock transport always follow the same decision. A build whose resolved mode is production rejects the setting (`true` after trimming) before compilation, whatever `NODE_ENV` the build inherits, and the mock module is a separate chunk that the minifier removes from every other build.
- The mock API follows the control plane for member roles: `UpdateMemberRole` accepts only `ROLE_ADMIN` and `ROLE_MEMBER` and fails with `invalid_argument` for an omitted, unspecified, unknown or `ROLE_OWNER` role before it looks up the member, and a valid role for the current owner fails with `permission_denied`. `ListEnrollmentTokens` returns `EXPIRED` (a copy; the stored record stays pending) for an unused, unrevoked token at or after its `expire_time`, and keeps the state of a used or revoked token. `RevokeEnrollmentToken` of an already revoked token returns it unchanged, and a used token fails with `failed_precondition`. `AcceptInvitation` treats a pending invitation at or after its `expire_time` like an unknown secret (`not_found`, before the already-a-member check) and leaves the invitation pending and the memberships unchanged. `TransferOwnership` to the caller fails with `invalid_argument` after the owner check and before any change, so the roles and the billing status stay as they were.
- Account settings: the console links to `https://accounts.delino.io`. It has no profile or account pages.
- Member display names: `ListMembers` returns the display name of each member, which the control plane reads from the `delino-accounts` API. The console does not call the `delino-accounts` API and needs no token for it. It shows the Logto user ID when a member has no display name. It does not store profiles.

- Recorded console behavior: the sandbox list filters by state and device and shows ended sandboxes only on request (`include_ended`), with "Show more" paging through `page_token`. A failed "Show more" request keeps the loaded rows and shows its error with a "Try again" button next to "Show more"; the button requests the failed `page_token` again (it does not read the first page again), a success appends the rows once and clears the error, and a terminal error (`not_found`, `permission_denied` or `unauthenticated`) still replaces the list with the full error notice; an `UNREACHABLE` sandbox shows its last known state. The create dialog requires the idle TTL (minutes) and the maximum TTL (hours, at most 168), checks that the idle TTL is not longer than the maximum TTL, takes the source (base image, template or ready snapshot), resources (the vCPU count is a whole number from 1 to 2147483647, the `int32` range of the request; memory (MiB) and disk (GiB) are whole numbers from 1 to 9007199254740991 (2^53 - 1), the largest value that the form holds exactly. An empty, decimal or out-of-range value shows a field error and sends no request, so the serializer never fails with the generic notice and no value is rounded; the memory field of the dialog has a minimum of 256 MiB and a `step` of 1, because the UI SDK also snaps a typed value to the `step` on Enter and blur: the arrow keys and the buttons move by 1, Shift moves by 256 and a typed 1000 stays 1000), network mode, an optional device and labels (`key=value` lines, with the warning that every member and API key can read them; a U+0000 character in a key or a value shows a field error on the Labels field and sends no request, as the control plane rejects it), and generates one UUID v7 `idempotency_key` for each opened dialog, which every retry of that create reuses. A ready snapshot in the source select reads `Snapshot <first 8 and last 4 characters of the id> · <creation time>` (the `ShortId` text), because UUID v7 ids that are created in the same 65.5 seconds share their first 8 characters; the option value stays `snapshot:<full id>`. Every option of the source select (base image, template and snapshot) shows its readable text in the trigger and in the list on every open, also after hover, focus and a reopened dialog, and its value (`base:<n>`, `template:<id>` or `snapshot:<id>`) is never shown, because `SelectOption` of `delino-ui` derives the label from its children. The organization list, the organization switcher, the enrollment token list and the API key list read every page instead (see the organization switcher entry and the enrollment token and API key entries). Other lists request `page_size` 200 and show the first page. The sandbox list, the sandbox page and the snapshot list refetch every 3 seconds while a sandbox they show is `CREATING` or `DELETING`, or a snapshot is `CREATING`, `DELETING` or `EXPORTING`, because the control plane returns from these operations before the agent finishes them. The sandbox page shows a positive TTL below one second in whole milliseconds (`500 ms`) and a positive TTL below one millisecond as `<1 ms`, so it never reads as `0 s`; an absent TTL shows `—` and an exact zero shows `0 s`.
- Recorded console behavior: the sandbox page actions (Pause, Resume and Take snapshot) return their request Promise from `onClick`, so the `delino-ui` button stays pending until the request and the refresh that follows settle. Repeated mouse or keyboard activations while a request is in flight send one request and keep the keyboard focus on the button. After a success or a failure the button accepts a new submission while the sandbox is running or paused. A test holds the `CreateSnapshot` response to cover this.
- Recorded console behavior: the agent version policy form (Settings) and the device limits form (device page) accept one save at a time. From the submit until the request and the refetch that follows it have settled (the mutation awaits its `onSuccess` refetch), the "Save policy" and "Save limits" buttons and every field of the form are disabled, and a synchronous in-flight guard ignores a second submission in the same tick. The fields cannot change while the refetch copies the saved values into the form, so that readback never erases an edit made after the submit. A failed save re-enables the form and keeps the draft as the user left it. Tests hold the update response, and the refetch after it, to cover this. The device limits form keeps only the fields that the user edited as its draft, and an untouched field always shows the fetched limit: a refresh of the device that changes the limits updates the untouched fields, keeps the edited ones and leaves the next save to send all four values as shown. A successful save drops the submitted edits, so the form shows the fetched limits again, and the form of another device never inherits an edit.
- The invitation secret arrives in the URL fragment of the invitation link, so it does not reach Cloudflare Pages logs. The link is `<console origin>/invitations/accept#secret=<secret>`. The console removes the fragment from the address bar (`history.replaceState`) after it reads it. When the user is not signed in, the console keeps the secret in `sessionStorage` (key `ownsand.pending-invitation`) only for the Logto sign-in redirect, because the fragment does not survive the redirect. It deletes the secret from `sessionStorage` when `AcceptInvitation` returns, also when the call fails, but only when the request belongs to the invitation link that the page still shows: a request of an earlier link that settles after a newer link opened (its success or its failure) does not delete the secret that the newer link saved for its sign-in redirect. It also deletes it when the user leaves the invitation flow: by navigating inside the console to another route, by loading the console at a route outside the flow (the console checks the initial route on start-up), by a failed Logto callback and by signing out (also in the mock). When the call fails, the page shows the error and keeps the "Accept invitation" button and the secret in memory (not in `sessionStorage`), so that the user can try again by hand, because the control plane leaves the invitation unused after a failure. The console never retries automatically and shows no separate retry button. A page without a secret shows the missing-invitation-link screen. In a build without a sign-in configuration (no Logto registration and not mock mode), a page with a secret shows the notice "Sign-in is not configured for this build." instead of the "Sign in to accept" button, stores nothing in `sessionStorage`, and still removes the fragment from the address bar. Opening a new link on the page clears the error of the previous one. Opening a new invitation link drops the stored secret from an earlier link, and the sign-in return still reads the secret that was saved for that redirect. The invitation route and the callback route are the invitation flow. The sign-in redirect and its return, and a reload of the invitation page, are part of the flow and do not delete the secret. A successful `AcceptInvitation` invalidates the cached member and organization queries, also when it finishes after the user left the page (that late success does not navigate), so the organization switcher and the organization list show the joined organization within the 10 second stale time. The console navigates to the new organization without waiting for the refetch.
- New secrets (invitation links, enrollment tokens, API keys) appear once in a dialog with a copy action and a statement that they will not appear again.
- Per-device admin settings UI (recorded decision): the `device` route. Its first section lists the platform, agent version and update state, last-seen time, host capacity, supported guests and the allocation. The limits section has the vCPU, memory (MiB) and disk (GiB) limits and a vCPU overcommit select from 100% to 400% in steps of 25, with a live "Effective vCPU limit" (floor of vCPU limit × percentage / 100, in integers) and a save button. The memory and disk limits are text inputs (`inputMode="numeric"`) that hold the digits of the stored `int64` values, so a value above 2^53 stays exact when another limit is saved or when it is edited: the console parses them with `BigInt` and accepts only digits (after trimming) from 0 to 9223372036854775807, and a negative, decimal, non-numeric or larger value shows the field error "<Memory or Disk> limit must be a whole number from 0 to 9223372036854775807." without a request. The save button calls `ReplaceDeviceLimits` with all four values set, so an explicit `0` is saved as zero and the page never relies on the implicit presence of the legacy `UpdateDeviceLimits`; a limit without a value is reported and not sent as a zero. A danger zone removes the device after a confirmation. Members see the same values read-only. The `devices` list shows the allocated vCPUs as `<allocated> of <effective> (<limit> × <ratio>)`, where `<allocated>` is the exact `DeviceAllocation.vcpu_total_count` (a bigint in the SDK; the console falls back to the `int32` `vcpu_count` when an older server leaves it absent, and the device page shows the same value) and `<effective>` is the exact `Device.effective_vcpu_limit_count` (an `int64`, so a bigint in the SDK; for example `2147483648`), and `0` for a device with zero limits; the console never reads the capped `int32` `effective_vcpu_limit` field. The "Add a device" action of the `devices` list, for `admin` and above, leads to the enrollment tokens.
- Organization switcher: a select in the top bar lists the caller's organizations and keeps the current section when it switches. The organization list and the switcher share one cached infinite query of `ListOrganizations` (`page_size` 200, one `useOrganizations` hook): the console sends each response's `next_page_token` as the next `page_token` until a response has none, so a final empty page after a full page ends the loop, and it combines the pages in the server's order with each organization's `caller_role`. A failed later-page request does not make the list look complete: the list keeps the loaded organizations and shows that some are not shown yet with a "Try again" button, and the switcher shows an entry that reports the missing organizations and retries when selected; the console requests a failed page again only on that retry. Every `OrganizationService` invalidation (an accepted invitation, a membership or settings change, an organization creation) refetches the cached pages from the first one, so a new membership shows up on whichever page the server returns it. The top bar also links to `https://accounts.delino.io` ("Account settings") and signs out.
- The console hides actions that the user's role does not allow, and the control plane still enforces every permission. It reads the role from `Organization.caller_role` of `GetOrganization` and applies the [authorization matrix](servers-ownsand-api-foundation.md#authorization): enrollment tokens, API keys, invitations, member roles and removal, device limits and removal and agent version policy changes for `admin` and above; leaving for `admin` and `member`; ownership transfer and deletion for `owner`. An `admin` cannot change or remove the `owner`. When the caller's role does not allow the route's section (the minimum role in the route table), for example after the organization switcher keeps the API keys section in an organization where the caller is a `member`, or from a bookmark, the console shows a permission notice with a link to the sandboxes instead of the page.
- Billing, with `BillingService` of the [protos contract](protos-ownsand-api-contract.md#billing):
  - Banner: every member sees a banner at the top of every organization page while the organization is `BLOCKED` or `SUSPENDED`. It names the state and the reason (no linked billing account, or missing payment of the linked billing account), shows the suspension time while the organization is blocked (`suspend_time`, 3 days after the block start) and the time it was suspended while it is suspended, says which actions are rejected (blocked: creating sandboxes, snapshots, templates and enrollment tokens, resuming sandboxes and exporting snapshots; suspended: also exec, file transfers, sessions and relay connections, and running sandboxes are paused), and links to `https://accounts.delino.io`. Without a link, it also links the `owner` to the `settings` route and tells other roles that the owner must link a billing account. The console reads `GetBillingStatus` for the current organization and again after any call fails with a billing reason.
  - Billing reason detection (recorded decision): an RPC error is a billing rejection when its code is `resource_exhausted` and one of its `ErrorDetail` details has a `billing_reason` other than `UNSPECIFIED` (`billingReasonOf` in `src/api.ts`). `watchBillingErrors` in `src/api.ts` subscribes to the query and mutation caches of the React Query client and invalidates every `GetBillingStatus` query after such a failure.
  - Billing section of the `settings` route, for `owner` and `admin`: the linked billing account name, its balance (marked as debt when it is negative), this UTC month's total cost, and the usage and cost for each meter (relay egress, R2 storage, Class A RPCs and Class B RPCs) from `GetBillingUsage`, with a link to `https://accounts.delino.io` for payments, top-ups and billing account management. Without a link (`GetBillingStatus` reports `linked` false), the section shows the link flow (`owner`) or a notice that the owner must link a billing account (`admin`) instead and does not call `GetBillingUsage`, which fails with `failed_precondition` then. Usage that the control plane has not reported yet (about the last 5 to 10 minutes) is not included, and the section says so. Members do not see the section.
  - Link flow, for the `owner` only: a dialog lists the billing accounts from `ListLinkableBillingAccounts` (the first page of 200, where the user is `owner` or `admin` in `delino-accounts`) as options with the name and the role, focuses the first option, and links the selected one with `LinkBillingAccount`; when the list is empty, it explains that the user can create a billing account at `https://accounts.delino.io` and disables the link button. Unlinking needs a confirmation that says the organization becomes blocked at once. The `Unlink billing account` action is part of the linked view for the `owner` while `GetBillingUsage` is loading or has failed, not only after it succeeds: the confirmation then has the generic title "Unlink the billing account?" and the usage "Try again" button stays. The ownership transfer confirmation says that the transfer removes the billing link. Link and unlink invalidate every `BillingService` query, and the ownership transfer invalidates them too.
  - A mutation that fails with a billing reason shows the server message with its link and is never retried: error notices render `https://accounts.delino.io` in the message as a link and offer no "Try again" button, and toasts add an "Open billing" link action.
  - Amounts are `bigint` micro-USD values and are never converted to `number` for arithmetic (`src/format.ts`). Rounding is for display only and rounds half away from zero; a value that rounds to zero shows without a sign. Balances and totals show in USD with 2 decimals, with a leading minus for debt (`-$1.23`). A usage cost of zero or of at least $0.01 in magnitude shows with 2 decimals; a nonzero usage cost below $0.01 (below 10,000 micro-USD) shows exactly, with up to 6 decimals and without trailing zeros (at least 2 decimals remain, for example `$0.005` and `$0.000001`), so it needs no rounding. R2 storage usage shows in GiB-months from the byte-second quantity, with the GiB-month of the [project index](project-ownsand.md#billing) (2^30 bytes for 730 hours, so a quantity divided by 2^30 × 2,628,000), with 3 decimals, and a positive quantity below 0.0005 GiB-months shows as "less than 0.001 GiB-months". Relay egress shows in the largest binary unit (KiB to EiB, 2 decimals) in which it shows as at least 1.00, and RPC usage in exact calls. All billing text is in English.
- The enrollment token list reads every page of `ListEnrollmentTokens` (`page_size` 200), because the control plane lists tokens in ascending ID order, so a new token is on the last page and an administrator must be able to revoke it. It follows the continuation token like the organization list: a status says "Loading more enrollment tokens" while later pages load, a failed later-page request keeps the loaded tokens and shows "Some enrollment tokens are not shown yet." with "Try again" (window focus and reconnect do not request the failed page again), a repeated token on a page boundary is shown once, a create or a revoke reads the list again from the first page, and the empty state shows only when the control plane has no token. The list is keyed by organization, so changing the organization shows no token of the previous one. The mock `ListEnrollmentTokens` pages like the control plane (50 rows by default, at most 200, ascending creation order, a token after every full page, `invalid_argument` for an unknown token) and `CreateEnrollmentToken` appends the new token last.
- The API key list reads every page of `ListApiKeys` (`page_size` 200) the same way, because the control plane lists keys in ascending ID order, so a new key is on the last page and an administrator must be able to revoke it: a status "Loading more API keys" while later pages load, a failed later-page request keeps the loaded keys and shows "Some API keys are not shown yet." with "Try again", a repeated key on a page boundary is shown once, a create or a revoke reads the list again from the first page, the empty state shows only when the control plane has no key, and the list is keyed by organization. The mock `ListApiKeys` pages like the control plane and `CreateApiKey` appends the new key last.
- The member list and the New owner picker of the ownership transfer read every page of `ListMembers` (`page_size` 200) through one shared `useMembers` hook, so a member after the first 200 is listed and can get a role change or a removal, and the owner can pick any non-owner member as the new owner. They share one cached infinite query and follow the continuation token like the API key list: a status "Loading more members" while later pages load, a failed later-page request keeps the loaded members and shows "Some members are not shown yet." with "Try again" (the picker offers only the loaded non-owner members meanwhile), a repeated member on a page boundary is shown once, and a response without a token sends no further request. A role change, a removal or an ownership transfer reads the list again from the first page. The mock `ListMembers` returns every member in one page; the paging is covered by unit tests with a transport that cuts the pages.
- Enrollment token lifetimes offered: 1, 6, 12 and 24 hours. The token dialog says to pass the token to `ownsand-agent enroll` on standard input, not as an argument.
- UX follows the Toss Design Guidelines: plain surfaces on a neutral background, one primary action per view, plain-language copy and generous touch targets, with `delino-ui` components and its `--dui-*` tokens (light and dark). Dialogs close with `Esc`. At 760 px and narrower, the organization pages use one column and the section list above the content scrolls inside itself, so no page scrolls the document sideways at 320 px and wider (only a table inside `.table-wrap` scrolls inside itself); from 761 px a 220 px side column with a vertical list returns. A form with a single critical input (organization name, API key name, template name) focuses it when it opens. Closing such a dialog with `Esc`, Cancel or a click outside returns focus to the button that opened it, and so does `Done` or `Esc` on the one-time API key dialog. Destructive confirmations put the cancel button first. A confirmation dialog or form dialog shows no error from an earlier attempt: a retry clears the notice and every new opening starts without one, including after a failure that arrived once the dialog was closed with `Esc`, Cancel or a click outside. A failure that arrives while the dialog is open still shows its notice. A confirmation button is disabled while its request runs, so one opening sends the action once. The result of a request belongs to the opening that sent it: when that opening ended with `Esc`, Cancel, a click outside or a close, a late success does not close the next opening, which can be for another target, and a late failure shows no notice on it, also for the same target; the request itself keeps running. The same holds for the redirect of a confirmed request: removing a device, deleting an organization and leaving an organization navigate only while the opening that sent the request is still current, so a success that arrives after `Esc`, Cancel, a click outside or an unmount neither changes the route nor adds a history entry, also when a newer confirmation is open. The cache refresh of the success is not part of the opening and still runs. Every form dialog (organization, sandbox, API key, enrollment token, invitation link, template and billing link) has its own submission state for each opening: a dismissal ends the opening, a new opening starts with no pending or error state, and a late result of an earlier request neither shows an error in the new opening, closes it, nor clears the pending state of the request that the new opening sent. A late success of a dismissed opening also does not open its one-time secret, token or link dialog or navigate to the created organization or sandbox; the created object is listed and its secret cannot be shown again, so an API key, enrollment token or invitation from a dismissed opening can only be revoked from the list. The cache refresh and the success toast of the billing link still run.

## Storage

The console stores nothing except the Logto SDK session state in the browser. It never stores API keys or enrollment tokens in browser storage. The only exception for invitation secrets is the short `sessionStorage` use during the sign-in redirect described above.

## Security

- Secrets appear once and are never stored by the console, except the short `sessionStorage` use of an invitation secret during the sign-in redirect described in [Interfaces and Contracts](#interfaces-and-contracts).
- Destructive actions (device removal, API key revocation, organization deletion, ownership transfer and billing unlink) need an explicit confirmation step.
- The console shows no exec output or file contents; it has no exec or file features in this version.

## Logging

The console sends no logs to a service in this version. Browser console messages never contain tokens or secrets.
