# servers-tide-api foundation contract

## Scope

This contract owns the `tide-api` control plane of [`tide`](project-tide.md) at `servers/tide-api/`. The control plane is the system of record for tide organizations, memberships, OwnSand links, GitHub installations, agent integrations, runner profiles, requests, runners, personal API keys and audit events. It receives demand from GitHub, from the agent vendors and from users who ask for dev sessions, keeps one queue per organization, creates and deletes runners through the OwnSand API, and starts the runner programs in them. For dev sessions, it relays the owner's commands and file transfers to the OwnSand data path.

The control plane runs no sandbox and stores no runner output, dev session command output or dev session file contents. It is licensed under `FSL-1.1-ALv2` according to the [license contract](repository-license-contract.md).

Layout, following the `accounts-api` server conventions:

- `servers/tide-api/cmd/tide-api/`: process entry point. The same binary also serves the Claude Code `spawn-runner` hook command: started under the name `spawn-runner` or as `tide-api spawn-runner`, it runs as the hook ([Claude Code](#claude-code)).
- `servers/tide-api/internal/`: `config` (configuration), `server` (the HTTP handler, `GET /healthz` and CORS), `api` (the Connect handlers, the authentication interceptor, authorization, personal API keys, audit events, rate limits and the extension hooks), `auth` (Logto access tokens and the `tide_` and `tdi_` secrets), `authz` (the authorization matrix), `secrets` (credential encryption), `ratelimit`, `lease` (the instance lease and the lease-scoped components), `jobs` (the daily jobs), `db` (the Postgres pool and the migrations, with the `dbtest` harness), `app` (the wiring and the extension registry), `layers` (the extensions in their registration order), `ownsandclient` (the OwnSand client interface over the OwnSand Go SDK, its instrumentation and the `ownsandfake` test fake), `link` (the OwnSand link), `integration` (agent integrations), `profile` (runner profiles), `work` (the queue, the dispatcher, the runner lifecycle, the workload adapter interface and `WorkService`), `devsession` (`DevSessionService`, the dev session relay and the `DEV_SESSION` adapter), `githubapi` (the GitHub REST client of the tide GitHub App, with the `githubfake` test fake), `github` (`GitHubService`, `POST /webhooks/github`, the `GITHUB_JOB` adapter and the redelivery job), `webhook` (the delivery ID store and the helpers that every webhook endpoint shares), `agent` (the `AGENT_SESSION` adapter, the vendor watchers, the vendor claims and the guest helpers; `agent/vendorhttp` is the vendor HTTP client, `agent/cursor`, `agent/devin`, `agent/claude` and `agent/codex` are the vendor adapters with their `cursorfake`, `devinfake`, `claudefake` (a fake orchestrator) and `codexfake` (a fake Agents API and a webhook sender) test fakes; `agent/codex` also serves `POST /webhooks/openai/{integration_id}`), `metrics` and `testenv` (in-process integration tests).
- `servers/tide-api/package.json`, `turbo.json`, `.env.example` and `Dockerfile`: workspace wiring, the `deploy` field and the container image.

## Runtime and Language

- Language: Go in the root module `github.com/delinoio/mono`. Import path: `github.com/delinoio/mono/servers/tide-api/...`. Logging: `log/slog`.
- Runtime: one long-running process. It serves HTTP with Connect handlers and the webhook endpoints on the `ADDR` that the deployment sets, and its metrics in the Prometheus format on a separate `METRICS_ADDR`.
- Replicas: the service runs as exactly one replica. A deployment briefly runs the new container next to the old one, so only the instance that holds a lease row in Postgres runs the dispatcher, the vendor watchers, the Claude Code orchestrator processes and the reconciliation jobs. The old instance releases the lease when it starts to drain and stops these components at that moment. The lease expires 30 seconds after its last renewal, and the holder renews it every 10 seconds. RPCs and webhooks work on both instances, because they only read and write Postgres.
- Deployment target: a Docker container on the shared DigitalOcean Droplet, deployed by the [deployment workflow](repository-workflow-contract.md#deployment-workflow) with the `deploy` target `droplet`, like `accounts-api`. Production origin: `https://tide.api.delino.io`. The Caddy reverse proxy terminates TLS and proxies to the container. tide needs no public port other than HTTPS. The `deploy` field of `servers/tide-api/package.json` sets the service `tide-api`, the host name `tide.api.delino.io`, the container port `8080` (the deployment sets `ADDR=:8080`), the upstream protocol `h2c` and `needs` `ownsand-api`, so a deployment run that also deploys `ownsand-api` deploys it first and stops before `tide-api` when it fails, because tide creates runners and relays dev sessions through the OwnSand API. `needs` only orders the run: a run that selects only `tide-api` does not deploy `ownsand-api`. The configuration and secrets are in the env file `/srv/delino/env/tide-api.env` on the Droplet, which must not set `ADDR`. Like `accounts-api`, the image carries the FSL-1.1-ALv2 `LICENSE`, the Go toolchain `GO-LICENSE` and `THIRD-PARTY-LICENSES.txt` (the license files of every third-party Go module that `./servers/tide-api/cmd/tide-api` links) in `/usr/share/licenses/tide-api/`.
- Container image: the image contains the `claude` binary at a pinned version of at least 2.1.224, because the [Claude Code adapter](#claude-code) runs the Claude Code orchestrator in the container.
  - Implementation (recorded decision, `servers/tide-api/Dockerfile`): Claude Code 2.1.323 of the stable channel for `linux-x64`, at `/usr/local/bin/claude`. A build stage on `debian:12-slim` downloads the release signing key from `https://downloads.claude.ai/keys/claude-code.asc` and checks its fingerprint `31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE`, verifies the detached signature `manifest.json.sig` of `https://downloads.claude.ai/claude-code-releases/2.1.323/manifest.json` with gpg, checks that the manifest lists the SHA-256 that the Dockerfile pins for `linux-x64`, downloads `linux-x64/claude` and checks that SHA-256 and `claude --version`. This is the binary integrity check of the [Claude Code setup documentation](https://code.claude.com/docs/en/setup). The native build needs glibc, so the runtime base is `gcr.io/distroless/cc-debian12:nonroot` (pinned by digest) instead of `distroless/static`. The image carries the Claude Code license notice in `/usr/share/licenses/claude/NOTICE`. An update sets `CLAUDE_VERSION` to a stable release of at least 2.1.299 (the orchestrator flag `--shutdown-drain-sec`) and copies its manifest's `linux-x64` checksum into `CLAUDE_SHA256`. The orchestrator gets `DISABLE_AUTOUPDATER=1`, so only the pinned build runs.
- Database: PlanetScale Postgres, according to the repository defaults.
- Development ports: `127.0.0.1:18400` for HTTP (the default of `ADDR`) and `127.0.0.1:19400` for metrics (the development launcher sets `METRICS_ADDR` when it is unset). The [environment contract](repository-environment-contract.md#process-boundaries) lists them.
- Lease-scoped components: a later layer registers each background component (the dispatcher, a vendor watcher, a Claude Code orchestrator, a reconciler) with the extension registry of `servers/tide-api/internal/app`. The lease holder starts the components when it acquires the lease, restarts a component that returns early with exponential backoff (1 second to 1 minute) and stops all components before it releases or loses the lease. The daily jobs (retention deletes and re-encryption after a key rotation) are one such component: they run when the instance acquires the lease and then every 24 hours.

## Interfaces and Contracts

List handlers validate enum filters after authorization and before querying the list. See the [Connect RPC API contract](protos-tide-api-contract.md#general-rules).

- Business APIs: the public services of the [protos contract](protos-tide-api-contract.md).
- Webhook endpoints: see [Webhooks](#webhooks).
- Operational endpoints: `GET /healthz` without authentication returns `200` with `{"status":"ok"}` while the process can serve HTTP requests. `GET /metrics` on `METRICS_ADDR` serves the metrics in the Prometheus format; see [Metrics](#metrics).
- Browser access: CORS allows only `https://tide.delino.io` in production and the console's loopback development origin locally.

### Authentication

- Every public RPC accepts a Logto access token for the API resource `https://tide.api.delino.io`. The server validates the signature, issuer, expiry, audience and required scopes according to the [authentication contract](repository-auth-contract.md#token-validation), and rejects ID tokens.
- The RPCs of `DevSessionService` also accept a [personal API key](#personal-api-keys) in the `Authorization: Bearer` header. Every other RPC rejects a personal API key with `permission_denied`. The server tells the two credentials apart by the `tide_` prefix. An invalid personal API key gets `unauthenticated` on every RPC.
- Logto registration (recorded decision): the API resource `https://tide.api.delino.io` defines the scope `tide:use`, and every RPC requires it in the access token. Roles in an organization come from tide's own memberships, not from token scopes. The [web console](apps-tide-console-foundation.md) and the [CLI](cmds-tide-cli-foundation.md) request access tokens for this resource with this scope. The server rejects a token whose `typ` is not `at+jwt` (ID tokens) and a machine-to-machine token whose `sub` equals its `client_id`, like `ownsand-api`. The control plane needs no Logto application for token validation.
- The webhook endpoints accept no Logto token. They accept only deliveries with a valid sender signature; see [Webhooks](#webhooks).

### Authorization

The server authorizes every RPC that takes an `organization_id` with the caller's membership in that organization. A user without a membership gets `not_found`. The server loads every target entity with that organization in the query, so a request for an entity of another organization returns `not_found`.

A personal API key authorizes as its user in the organization of the key. The server checks the user's current membership and role for each call, so a key never has more permissions than its user. A key of one organization used with another `organization_id` gets `not_found`.

`CreateOrganization`, `ListOrganizations` and `AcceptInvitation` take no `organization_id` and need no membership. They follow the same rules as in [OwnSand](servers-ownsand-api-foundation.md#authorization).

| Action                                                                                                                                            | `owner`                   | `admin`                   | `member`                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- | ------------------------- | ------------------------- |
| Delete the organization, transfer ownership                                                                                                       | yes                       | no                        | no                        |
| Organization settings (the per-user dev session limit)                                                                                            | yes                       | yes                       | no                        |
| Invitations, member roles, removal of another member                                                                                              | yes                       | yes                       | no                        |
| Remove the caller's own membership (leave the organization)                                                                                       | no                        | yes                       | yes                       |
| OwnSand link, GitHub installations, agent integrations and their credentials                                                                      | yes                       | yes                       | no                        |
| Create, change and delete runner profiles                                                                                                         | yes                       | yes                       | no                        |
| Delete a runner                                                                                                                                   | yes                       | yes                       | no                        |
| Cancel a request                                                                                                                                  | yes                       | yes                       | no                        |
| Read the organization, members, the link and integration state (never credentials), runner profiles, requests, runners, capacity and audit events | yes                       | yes                       | yes                       |
| Create, list and revoke the caller's own personal API keys                                                                                        | yes                       | yes                       | yes                       |
| Create a dev session, list dev session profiles, read the metadata of every dev session of the organization                                       | yes                       | yes                       | yes                       |
| Run commands and transfer files in a dev session                                                                                                  | owner of the session only | owner of the session only | owner of the session only |
| Delete a dev session                                                                                                                              | any                       | any                       | own only                  |

- In the dev session rows, "owner of the session" is the user who created the dev session, not the organization role `owner`. No role, including `owner` and `admin`, can run commands or transfer files in another user's dev session.
- A personal API key can call only the dev session rows and nothing else; it cannot create, list or revoke API keys.
- An organization has exactly one `owner`, with the same ownership rules as OwnSand.
- Invitations are one-time secrets that expire after 7 days. The server stores only their hashes.

### OwnSand link

- An admin links the tide organization to an OwnSand organization with `SetOwnSandLink`. The request carries the OwnSand organization ID and an OwnSand organization API key.
- The server validates the link before it stores it: it calls OwnSand `ListDevices` for that organization with that key. A key of another organization fails there with `not_found`, so a stored link always matches its key.
- One OwnSand organization links to at most one tide organization. `SetOwnSandLink` fails with `already_exists` when another tide organization links the same OwnSand organization ID.
- `SetOwnSandLink` on a linked organization replaces the API key. A change of the OwnSand organization ID needs `RemoveOwnSandLink` first.
- Implementation (recorded decisions): the key must have the `osk_` prefix. The validation call counts against the `SetOwnSandLink` rate limit before it reaches OwnSand. An `unauthenticated`, `not_found` or `permission_denied` answer of the validation fails with `invalid_argument`, and `unavailable` with `unavailable`. The stored key is encrypted with the associated data of the organization ([Secrets](#secrets)). An OwnSand call that fails with `unauthenticated` marks the link `INVALID` only when the key that failed is still the stored key; a new `SetOwnSandLink` makes the link `ACTIVE` again. `RemoveOwnSandLink` first marks the link as being removed, so the dispatcher creates no new runner, then runs the clean-up steps that need OwnSand, and then deletes the link and the key in one transaction. When a clean-up step or the deletion transaction fails, the mark is cleared and the call fails; the admin calls it again.
- OwnSand client (recorded decision): `tide-api` calls OwnSand through the OwnSand Go SDK with one client per organization, built from the decrypted key and cached until the key changes. The data path uses the OwnSand relay, not a peer-to-peer session: `tide-api` relays one operation per RPC, so a session per call would add only setup time. `OWNSAND_API_ORIGIN` selects the OwnSand API ([Configuration](#configuration)).
- `RemoveOwnSandLink` stops dispatch, ends every queued request with `CANCELED`, deletes every runner of the organization as described in [Runner lifecycle](#runner-lifecycle), and then deletes the stored key.
- When OwnSand rejects the key with `unauthenticated` (for example, after an admin revoked it in OwnSand), the server marks the link `INVALID`, stops dispatch for the organization and keeps queued requests until their maximum queue wait. The console shows the state.
- Sandboxes of tide runners carry the OwnSand labels `tide.organization-id`, `tide.runner-id` and `tide.runner-profile-id`. Labels hold no secrets.

### GitHub App integration

tide uses one GitHub App that Delino owns, on github.com only.

App permissions:

- Organization permission "Self-hosted runners": read and write. tide needs it to list runner groups, to create JIT runner configurations with `POST /orgs/{org}/actions/runners/generate-jitconfig` and to remove runners.
- Repository permission "Actions": read. GitHub sends `workflow_job` events only to apps with this permission.
- Repository permission "Metadata": read, which GitHub requires for every app.
- Subscribed events: `workflow_job` and `installation`.

Installation and linking:

1. An admin calls `CreateGitHubInstallUrl`. The server returns the installation URL of the app with a `state` value. The `state` binds the tide organization and the admin's user ID, expires after 10 minutes and is single-use.
2. The admin installs the app on a GitHub organization. The app requests user authorization during installation, so GitHub redirects to the console callback with `installation_id`, `code` and `state`.
3. The console calls `LinkGitHubInstallation` with these values. The server checks the `state`, exchanges the `code` for a GitHub user access token, and accepts the link only when `GET /user/installations` with that token lists the installation and the installation's account is an organization. The server discards the user access token after this check.
4. The admin selects the runner group of the installation with `UpdateGitHubInstallation`. The default is the `Default` runner group. GitHub's runner group settings control which repositories can use the runners; tide does not change them.

- One GitHub installation links to exactly one tide organization. A tide organization can link several installations.
- Installations of personal accounts fail with `failed_precondition`, because tide registers only organization-level runners.
- When GitHub sends an `installation` event with `deleted` or `suspend`, the server marks the installation inactive, ends its queued requests with `CANCELED` and deletes its runners that wait for a job.

Job matching:

- A runner profile of kind `GITHUB_JOB` has the GitHub label `tide-<profile name>`.
- A `workflow_job` `queued` event creates a request only when the job's labels consist of exactly one label `tide-<profile name>` of an existing runner profile of the linked tide organization, optionally with `self-hosted`. The server ignores every other job, so that a tide runner never waits for a job whose other labels it does not have.
- The request key is the GitHub job ID. A repeated event for the same job ID does not create a second request.

GitHub, not tide, assigns a queued job to a runner with matching labels. A runner that tide started for one job can take another job with the same label. Therefore:

- A runner pool is one pair of a GitHub installation and a runner profile. tide registers organization-level runners, so a runner of one GitHub organization can never take a job of another GitHub organization, even with the same label. Each `GITHUB_JOB` request and each `GITHUB_JOB` runner records its GitHub installation, and every rule below counts runners and requests per runner pool.
- The dispatcher starts runners per runner pool. The oldest `QUEUED` requests of a runner pool count as covered while the pool has the same number of runners in `CREATING`, `PREPARING` or `WAITING_FOR_WORK`. The dispatcher dispatches only uncovered requests.
- Each runner registers in the GitHub organization of its installation, with the runner group of that installation and the GitHub runner name `tide-<runner_id>`. A `workflow_job` `in_progress` event names this runner. The server then binds the job's request to that runner and marks both `RUNNING` and `BUSY`.
- A `workflow_job` `completed` event ends the request. When the job never started (for example, the workflow was cancelled), the request ends with `CANCELED`. The server then compares the runner pool's runners in `CREATING`, `PREPARING` or `WAITING_FOR_WORK` with all of its remaining `QUEUED` requests, not only with its uncovered requests. When the pool has more of these runners than remaining `QUEUED` requests, the server removes the newest surplus runners: it removes the GitHub runner registration and then deletes the sandbox. When GitHub refuses the removal because the runner took a job meanwhile, the runner stays.
- GitHub does not retry failed webhook deliveries by itself. Every 5 minutes, the lease holder lists the recent deliveries of the app webhook and requests a redelivery of each failed delivery of the last 24 hours.

Implementation (recorded decisions):

- GitHub client: `servers/tide-api/internal/githubapi` on `net/http` without a third-party client. It sends `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2026-03-10`. The app JWT is RS256 with `iat` 60 seconds in the past, `exp` 9 minutes ahead and `iss` the client ID. Installation access tokens (`POST /app/installations/{installation_id}/access_tokens`) are cached per installation until 5 minutes before their `expires_at`, and a `401` drops the cached token. Every GitHub API error is logged with its operation and HTTP status; tokens, OAuth codes, JIT configurations and response bodies are never logged.
- Installation URL: `<GITHUB_WEB_ORIGIN>/apps/<GITHUB_APP_SLUG>/installations/new?state=<state>`. The `state` is 32 random bytes in unpadded base64url. Only its SHA-256 hash is stored, with the organization, the user and the expiry; a daily job deletes expired states.
- `LinkGitHubInstallation` consumes the state before it calls GitHub, so a failed link (for example a rejected code) needs a new installation URL. A state of another user or organization, an unknown, used or expired state fails with `invalid_argument` and is not consumed. The code exchange is `POST <GITHUB_WEB_ORIGIN>/login/oauth/access_token` with `Accept: application/json`; an answer without `access_token` fails with `invalid_argument`. `GET /user/installations` must list the installation with the app ID of the configured app, or the call fails with `permission_denied`; the account must have `target_type` and `account.type` `Organization` (GitHub's example payload pairs them inconsistently), or the call fails with `failed_precondition`; a suspended installation fails with `failed_precondition`. The `Default` runner group is the group with `default` true (or the name `Default`), read with `GET /orgs/{org}/actions/runner-groups`. A second link of a linked installation fails with `already_exists`. `LinkGitHubInstallation` counts against a rate limit of 10 calls per user per minute with a burst of 10, the values of the OwnSand link validation. GitHub errors fail with `unavailable`.
- `ListGitHubInstallations` and `UnlinkGitHubInstallation` read or change only stored state and work without a GitHub App configuration. `ListGitHubRunnerGroups` calls GitHub, so it needs the role of the installation management (`owner` or `admin`), like `UpdateGitHubInstallation`, which checks with GitHub that the runner group exists. Both need an `ACTIVE` installation (`failed_precondition` otherwise).
- `UnlinkGitHubInstallation` first removes the GitHub registrations of the installation's runners that wait for a job, while the app can still reach the installation (a GitHub error fails the call with `unavailable` and keeps the link). Then one transaction deletes the link, ends the QUEUED requests of its runner pools with `CANCELED` and `INTEGRATION_REMOVED`, ends their `STARTING` and `RUNNING` requests with `ENDED` and `INTEGRATION_REMOVED` (tide gets no further events for them), and deletes the waiting runners with `CLEAN_UP`. A runner whose removal GitHub refused took a job and finishes it.
- Runner pools: the pool key of `GITHUB_JOB` requests and runners is the GitHub numeric installation ID. A request stores its GitHub job (installation, job, workflow run, repository full name and job name) for the API.
- Webhook events: `queued` labels are compared without case. `in_progress` creates the request first when its `queued` delivery was lost, and binds only a runner `tide-<runner_id>` of the same runner pool and profile that waits for work; other runner names leave the request until `completed`. An `in_progress` event can come before tide stored the end of the runner start (the runner is still `PREPARING`); the runner then changes to `BUSY` at once and keeps the exec ID of its program when the start ends, so tide follows the program and deletes the sandbox when it exits. GitHub documents no field that shows that a job never started, so tide decides: a `completed` job started when tide bound it to a runner or when the event names a tide runner of the pool (a lost or late `in_progress`); it then ends with `ENDED` and `COMPLETED`, otherwise with `CANCELED` and `CANCELED_BY_SOURCE`. A `completed` event of a matching job without a request (its `queued` delivery failed and its redelivery can still come) creates the request and ends it at once, so a late `queued` or `in_progress` delivery of the job finds an ended request and starts no runner. `waiting` and other actions are ignored. A `workflow_job` delivery holds a share lock of the installation link while it applies the job, so it waits for a concurrent `installation` event or unlink that ends the work of the link, and then ignores the job of the inactive or removed link. The `completed` effects are stored before the answer; the surplus removal runs after the answer, because GitHub counts a delivery that takes more than 10 seconds as failed.
- Surplus runners: the comparison keeps the profile's warm count as a reserve in addition to the remaining `QUEUED` requests, so the rule does not delete the warm runners of the pool. A `422` answer of `DELETE /orgs/{org}/actions/runners/{runner_id}` counts as the refusal of a runner that took a job (see the gaps below). A runner whose registration removal fails for another reason also stays; the next `completed` event of the pool tries again. The removal decides on the current state of each runner, not on the earlier list, because a runner can finish its start meanwhile: under a row lock of the runner, a runner with a recorded registration keeps it until GitHub accepts its removal, and a runner without one changes to `DELETING`. The start records the registration under the same lock; when the runner is no longer `PREPARING` then, the start removes the registration and does not start the runner program.
- Warm runners: a `GITHUB_JOB` profile keeps its warm count in each runner pool of an `ACTIVE` installation. In a pool, the runners in `CREATING`, `PREPARING` or `WAITING_FOR_WORK` without a request beyond the pool's `QUEUED` requests are its warm runners; they are registered and wait for any job of the pool. A runner registers with the label of its profile when it starts. After a profile rename, the runners of the pool that wait with the old label get no jobs of the new label, so every `queued` and `completed` event of the profile and pool deletes them with `CLEAN_UP` (registration first; a runner whose removal GitHub refuses took a job and stays), and the dispatcher starts runners with the new label. When OwnSand has no capacity for a request, the dispatcher may reclaim them like other warm runners (see [Queue and dispatch](#queue-and-dispatch)): it takes the newest of them, removes the GitHub registration first and then deletes the runner with `WARM_RECLAIMED`; a runner whose removal GitHub refuses took a job and stays, and the dispatcher tries the next warm runner.
- `installation` events: `deleted` marks the link `DELETED` and `suspend` marks it `SUSPENDED`; both end the work of its runner pools like an unlink, without the GitHub calls (GitHub gives the app no token for the installation then; GitHub removes JIT runners that never connect by itself). `unsuspend` makes a `SUSPENDED` link `ACTIVE` again, because GitHub delivers the installation's events again; a `DELETED` link stays. Every `installation` event updates the stored account login. The admin removes a `DELETED` link with `UnlinkGitHubInstallation`.
- Organization deletion: the work layer's clean-up removes the GitHub registration of each runner before it deletes the sandbox, while the links still exist; the links are deleted with the organization rows.
- Redelivery: the job lists `GET /app/hook/deliveries?per_page=100&status=failure` with the app JWT and follows the `Link` `rel="next"` cursor until a delivery is older than 24 hours. It groups the deliveries by `guid` (a redelivery keeps the GUID of its delivery), skips a group with a successful delivery or whose GUID tide recorded (tide records a delivery ID before it answers `2xx`), and requests a redelivery of the newest delivery of each other group with `POST /app/hook/deliveries/{delivery_id}/attempts`. GitHub redelivers only deliveries of the past 3 days, so the 24-hour window stays inside that limit.
- Gaps in the GitHub documentation and how tide handles them:
  - The answer of `DELETE /orgs/{org}/actions/runners/{runner_id}` for a runner that runs a job is not documented; the endpoint documents only `204` and `422`. tide treats every `422` as "the runner took a job" and does not read the message. A `404` counts as removed.
  - The cause of `409` from `generate-jitconfig` is not documented. tide assumes a runner with the same name (from an earlier start attempt of the same runner): it looks up `GET /orgs/{org}/actions/runners?name=tide-<runner_id>`, removes that runner and tries once more. A start also removes the registration of an earlier attempt of the same runner that tide recorded.
  - `installation_id` on the callback of the installation-time user authorization is documented only for the Setup URL, and GitHub warns that it can be spoofed. tide accepts it only after `GET /user/installations` with the user's token lists it. `setup_action` is not documented and is ignored.
  - The web-flow error answer of the code exchange is not documented; any answer without `access_token` counts as a rejected code.
  - The order of `GET /app/hook/deliveries` (newest first) is not stated explicitly; the official example script relies on it, and so does tide.
  - The exact automatic labels of a JIT runner are not documented. tide sends only `tide-<profile name>`; GitHub adds `self-hosted` and the OS and architecture labels itself.
  - The exit code of a JIT runner after its job and a way to turn off the runner self-update in JIT mode are not documented. tide treats any exit of the runner program as the end of the runner and does not try to turn the update off.
  - When GitHub removes a JIT runner that never ran a job is not documented. tide removes the registration itself whenever it deletes a waiting runner.
  - A GitHub organization rename changes the login that the organization endpoints use. tide refreshes the login from every `installation` event; there is no subscription for organization renames, so a rename can make GitHub calls of the installation fail until the next `installation` event or a new link.

### Agent integrations

An agent integration holds the vendor credentials and settings of one vendor account or pool. A runner profile of kind `AGENT_SESSION` names one agent integration. An organization can have several integrations of the same vendor.

| Vendor         | Demand source in tide                                                                         | Credential that stays in tide               | Credential that enters the runner          | Runner program                                                                     | Guest OSes                  |
| -------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------- | --------------------------- |
| `CLAUDE_CODE`  | The `spawn-runner` hook of a Claude Code orchestrator that `tide-api` runs per integration    | Environment key                             | The single-use work order of the session   | `claude self-hosted-runner`, one session                                           | `LINUX`, `MACOS`            |
| `CURSOR`       | The pending-request stream of the Cursor self-hosted pool, with claims through the Cursor API | None in addition                            | Service account API key (`CURSOR_API_KEY`) | `agent worker --pool <pool> [options] start`, one session                          | `LINUX`, `MACOS`, `WINDOWS` |
| `OPENAI_CODEX` | OpenAI `agent.session.action_required` webhooks with `environment_connection`                 | Webhook secret, API key (`api.agents.read`) | Environment key (`CODEX_API_KEY`)          | `codex exec-server --remote <url> --environment-id <id>`                           | See below                   |
| `DEVIN`        | The watch stream of the Devin Fleet API, with claims through the Fleet API                    | API token with `account.outposts.write`     | Outpost token (`DEVIN_OUTPOSTS_TOKEN`)     | `devin worker start --session=<id> --outpost=<id> --acceptor-id=<id>`, one session | `LINUX`, `MACOS`, `WINDOWS` |

- Each runner serves one session and then its program exits. tide never gives a runner to a second session.
- tide validates the guest OS of an `AGENT_SESSION` runner profile against this table. OpenAI documents no host OS for `codex exec-server`. The Codex adapter implementation records the guest OSes that it verified, and tide accepts only those. Interim rule (recorded decision): the Codex adapter has install and start scripts for Linux and macOS guests (the candidate guest OSes, `profile.CodexCandidateGuestOSes`), but it was verified only against fakes, so no guest OS is verified (`profile.VerifiedCodexGuestOSes` is empty), and `CreateRunnerProfile` and `UpdateRunnerProfile` reject every `AGENT_SESSION` profile of an `OPENAI_CODEX` integration with `invalid_argument`. See [OpenAI Codex](#openai-codex) for how an acceptance run adds a verified guest OS.
- Credentials (recorded decision): each credential is encrypted with the associated data of its integration and credential kind ([Secrets](#secrets)). `UpdateAgentIntegration` with the path `credentials` needs at least one non-empty credential of the integration's vendor. A daily job of the lease holder re-encrypts the credentials and the OwnSand keys of old keys after a key rotation.
- Cursor workers on Windows need Git Bash in the guest image.
- The exact command lines, flags and API endpoints come from the vendor documentation at implementation time. Record them in this contract with the adapter implementation. [Cursor and Devin](#cursor-and-devin) records them for Cursor and Devin.

#### Claude Code

- For each `CLAUDE_CODE` integration, the lease holder runs `claude self-hosted-runner orchestrator` as a child process with a hooks directory that contains the tide `spawn-runner` hook. The orchestrator uses the environment key; the key never enters a runner.
- The hook is the `tide-api` binary in hook mode. It sends the order ID, the session ID, the spawn reason and the work order to the parent process over a Unix domain socket in the container, which is not reachable from the network. Its exit code follows the spawn-runner exit-code contract of the Claude Code documentation: `0` after tide stored the request together with its work order (or stored the same order ID before), `1` (retryable) when tide could not store both, and `2` (non-retryable, the session is blocked until its user sends a message or an Owner retries it) only for a spawn request that tide can never serve.
- The work order is a single-use secret that expires with its spawn request. tide stores it encrypted with the [secrets](#secrets) rules, in the same transaction as the request, and hands it to at most one runner program. tide deletes the stored work order when it hands it to the runner, when the runner of the request becomes `BUSY` or when the request ends. A runner start that fails before the runner received the work order returns the request to the queue, and the next runner uses the stored work order while it is valid. A new lease holder reads the stored work order, so a deployment does not make a queued Claude Code request undispatchable.
- A runner gets the work order of its session and starts `claude self-hosted-runner` with it as the Claude Code reference documents. The runner serves that session and exits.
- The parent process restarts a crashed orchestrator with exponential backoff (1 second to 1 minute) and logs each restart.
- When tide ends a request without a runner (for example, at the maximum queue wait), the Claude Code orchestrator rules decide whether Anthropic sends a new spawn request for the session: Anthropic sends one with a new order ID after the expected spawn time.

Implementation (recorded decisions, package `servers/tide-api/internal/agent/claude`; verified against the Claude Code documentation of 2026-11-22 and the `--help` output of Claude Code 2.1.323, with the `claudefake` orchestrator and a shell script in place of `claude` only):

- Orchestrator: `claude self-hosted-runner orchestrator --hooks-dir <run directory>/hooks --health-port 0 --hook-timeout 30 --hook-concurrency 4 --expected-spawn-seconds 900 --shutdown-drain-sec 40`. `--health-port 0` turns off the health listener, because several orchestrators share the container and its default port 8080 is the port of `tide-api`. `--min-idle` keeps its default 0 (no pre-warming). The environment of the orchestrator is only `PATH`, `HOME`, `TMPDIR`, `LANG`, `TZ`, the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and their lowercase forms) and `SSL_CERT_FILE` and `SSL_CERT_DIR` of `tide-api`, plus `SELF_HOSTED_RUNNER_ENVIRONMENT_SECRET` (the environment key; the variable carries the value, so no key file exists), `TIDE_SPAWN_SOCKET` (the hook socket) and `DISABLE_AUTOUPDATER=1`. The secrets of `tide-api` (`DATABASE_URL`, `TIDE_SECRET_KEYS`, the GitHub App variables) never reach the orchestrator or the hook.
- Run directory: a new directory `tc<random>` in `os.TempDir()` with mode `0700` for each orchestrator run. It holds `hooks/spawn-runner`, a symbolic link to the `tide-api` binary, and the Unix socket `sock` (mode `0600`), and it is deleted when the orchestrator stops. The socket path must stay below 104 bytes, so `TMPDIR` must be short.
- Lifecycle: the orchestrators follow the watcher set of the [shared implementation](#cursor-and-devin): an orchestrator runs while the integration's organization has an `ACTIVE` OwnSand link that is not being removed and a runner profile names the integration. A change of the integration's settings or credentials restarts it with the new values; a removed or `INVALID` link, the deletion of the last profile, organization deletion and the end of the lease stop it. A stop sends one `SIGTERM` to the orchestrator alone, keeps the hook socket open while the orchestrator drains its running hooks, and kills the orchestrator 55 seconds later (the drain plus 15 seconds, the documented stop timeout). An orchestrator that exits or does not start is restarted after the backoff, counts `tide_claude_orchestrator_restarts_total` and logs `claude_orchestrator_restart` (not `vendor_watch_reconnect`). The orchestrator's output is logged line by line as `claude_orchestrator_output`, with e-mail addresses and JWT-like values masked.
- Hook mode: `tide-api` is the hook when it is started under the name `spawn-runner` or with `spawn-runner` as its first argument; it then reads no configuration. It reads `CLAUDE_RUNNER_ORDER_ID`, `CLAUDE_RUNNER_SESSION_ID`, `CLAUDE_RUNNER_SESSION_UUID`, `CLAUDE_RUNNER_ATTEMPT`, `CLAUDE_RUNNER_SPAWN_REASON` and the file in `CLAUDE_RUNNER_WORK_ORDER_FILE` (at most 64 KiB), sends them as one JSON line to the socket in `TIDE_SPAWN_SOCKET` or, without it, to `sock` in the parent of its own hooks directory, and waits at most 20 seconds for the answer. It reads no other variable (`CLAUDE_RUNNER_ACCOUNT_EMAIL` is personal data) and writes only a short message without secrets to stderr, which the orchestrator logs and shows as the spawn error.
- Socket: `tide-api` accepts a connection only from a process with its own user ID (`SO_PEERCRED` on Linux; on other systems the directory and socket permissions limit it) and serves hooks with a context that outlives the orchestrator's stop, so hooks of the drain are still stored.
- When the socket cannot accept a connection, `tide-api` logs `claude_hook_accept_failed` for the integration and retries with exponential backoff from 5 milliseconds to 1 second. A successful accept resets the delay. Closing the socket ends the accept loop without an error log, and teardown cancels any pending retry.
- Exit codes (vendor-doc conflict, resolved in favor of the Claude Code documentation, which defines `2` and higher as non-retryable; the contract had only `0` and `1`): `0` when tide stored the request and its work order, and when tide stored the same order ID before (a redelivery must create at most one workload); `1` when `tide-api` does not answer, the store fails, no runner profile names the integration yet, or the work order file is missing or empty; `2` only for a request that no retry can fix: a missing or invalid `CLAUDE_RUNNER_ORDER_ID`, a missing `CLAUDE_RUNNER_SESSION_ID` (a pre-warming request, which tide does not serve) or an invalid session ID. Each spawn request is logged as `claude_spawn_request` with the order ID, the session ID, the spawn reason, the attempt, the result and the request ID.
- Request key (vendor-doc conflict): the request key is the order ID, not the session ID as this contract said before. Every re-request of a session carries the same session ID with a new order ID, and the documentation requires the order ID as the deduplication key. The claim row records the order ID as the vendor request ID, the session ID as its scope and the spawn reason as its marker. The request goes to the oldest profile that names the integration.
- Work order (vendor-doc conflict: this contract reused the stored work order after any failed start and after a lease handover, but the work order registers exactly one runner, expires with the spawn request's lease of `--expected-spawn-seconds`, and the documentation says not to retry the workload because Anthropic sends a new spawn request with a new order ID):
  - tide stores the work order encrypted with the associated data `claude_work_order` and the request ID, in the transaction that creates the request.
  - The request's maximum queue wait is capped at the expected spawn time (15 minutes): a request whose work order expired ends with `EXPIRED` and `MAX_QUEUE_WAIT` instead of waiting until the profile's maximum queue wait, because no runner can register with it any more.
  - A start failure before the runner received the work order (the sandbox creation, the installation, the credential file) keeps the stored work order, so the next start attempt, also on a new lease holder, uses it while the request is younger than the expected spawn time.
  - Right after tide wrote the work order to the runner's credential file, and before it starts the runner program, it deletes the stored work order. A failure after that point ends the request with `FAILED` and `RUNNER_START_FAILED` instead of a retry with the same work order. A start that finds no stored work order also ends the request that way, and a start after the expected spawn time ends it with `EXPIRED` and `MAX_QUEUE_WAIT`.
  - Daily re-encryption does not apply: a stored work order lives at most 15 minutes, so a key rotation needs no job for it.
- Lease handover: the new lease holder starts its own orchestrators while the old one drains; the documentation allows several orchestrator replicas and gives each spawn request to exactly one of them.
- Runner program: `claude self-hosted-runner --capacity 1 --base-dir "$HOME/claude-runner" --health-port 0 --release-idle-session-min 30 --retire-at <epoch>`, with the work order in `SELF_HOSTED_RUNNER_ENVIRONMENT_SECRET` from the credential file. The runner releases its session after 30 idle minutes (recorded decision) and exits `0`, which ends the request with `ENDED` and `COMPLETED`; the session resumes with a new spawn request at its user's next message. `--retire-at` is the runner's creation time plus the `max_ttl` in its stored `CreateSandbox` request minus 5 minutes. This lets the runner release its session before OwnSand deletes the sandbox. tide omits `--retire-at` when that time is a minute or less away or the stored TTL is unavailable. `--kill-session-after-min` is not set, because `--retire-at` bounds the session. The default `--base-dir` `/workspace` needs a writable root directory, so the base directory is in the home directory.
- `BUSY`: Anthropic documents no API through which tide sees that a runner registered. The work order binds the runner to its one session, so the claim poller marks a runner that waits for work `BUSY` at its next round.
- Release: Claude Code has no claim to give back; a spawn request that tide does not serve expires with its lease.

Gaps in the Claude Code documentation (NOT DOCUMENTED; tide implements them defensively):

- Whether the orchestrator passes its own environment to the hook. tide sets `TIDE_SPAWN_SOCKET` and also finds the socket from the hook's path, which the orchestrator runs as `${hooks-dir}/spawn-runner`.
- Hook arguments and standard input: tide assumes none.
- The lifetime of a work order other than "expires with the lease". tide does not parse the JWT; it counts the expected spawn time from the hook's request.
- The exit codes of `claude self-hosted-runner` other than `0` after an idle release. Every other result ends the request with `FAILED` and `RUNNER_LOST`, like the other vendors.

#### Cursor and Devin

- The lease holder keeps one watch stream per integration. When a pending request arrives, the server claims it and creates a tide request. When tide ends the request before a runner took the session, the server releases the claim through the vendor API.
- After a watch stream ends, the server reconnects with exponential backoff (1 second to 1 minute) and lists the pending requests again, so that no request is lost.

Shared implementation (recorded decisions, package `servers/tide-api/internal/agent`):

- One `AGENT_SESSION` adapter serves every vendor. It selects the vendor by the request source, or for a warm runner by the vendor of the profile's integration. Claude Code and OpenAI Codex push their demand to tide (the `spawn-runner` hook, webhooks) instead of offering it for a claim: they create the request and its claim row with `Hub.CreateDirectTx` in their own transaction without a claim at the vendor, so the shared adapter, the claim poller and the release path serve them too. A vendor that pushes its demand runs no watcher (OpenAI Codex); the Claude Code watcher is its orchestrator process.
- Watchers: the lease holder runs a watcher for each `CURSOR` and `DEVIN` integration whose organization has an `ACTIVE` OwnSand link that is not being removed and at least one runner profile that names the integration. It checks this set every 5 seconds, so a change on any instance applies. A change of the integration's settings or credentials restarts the watcher with the new values. An `INVALID` or removed link, the deletion of the last profile and the deletion of the organization stop the watcher; organization deletion stops it before the deletion transaction.
- Reconnects: a watch that fails or ends unexpectedly reconnects after the backoff and increments `tide_vendor_watch_reconnects_total{vendor}`. A scheduled end (the Cursor re-list interval, a Cursor `410 Gone`, the documented Devin stream end) lists again at once and does not count, so that the "Vendor or orchestrator loss" alert counts only failures. Each reconnect is logged as `vendor_watch_reconnect` with `cause` `scheduled` or `error`.
- Claims: tide claims a vendor request with a worker ID (Cursor) or acceptor ID (Devin) `tide-<request_id>` before it creates the request, and stores the claim in `agent_claims` in the same transaction as the request. The claim row holds the vendor request ID, the worker ID, the scope (Cursor pool name, Devin outpost ID) and the demand marker (Cursor `createdAtMs`, Devin `metadata.created_at`); it holds no credential or token. A repeated event of a request that tide holds claims it again with the same worker ID; a conflict changes nothing. A claim conflict for a new request means that another worker holds it, and tide creates no request.
- Source key: the vendor request ID for the first request of a vendor request, and `<vendor request ID>#<n>` for a later request, because a Cursor follow-up and a Devin resume reuse the ID after the earlier request ended. n is one more than the highest suffix of the stored requests of the vendor request (the first request counts as 1), so a key stays unused after the retention job deleted older requests.
- Several profiles that name one integration: the requests go to the oldest `AGENT_SESSION` profile that names it (creation time, then ID). The other profiles get no requests and can keep warm runners.
- A request that a user canceled in tide before a runner took it declines its vendor entry: tide does not claim the same vendor entry (same demand marker) again. tide reads this from the end reason of the newest request of the vendor request (`CANCELED_BY_USER` without a start time), which the cancellation commits. Thus the rule also applies when the claim poller releases the claim after a restart, or before the cancellation's own release step.
- Release: when tide ends a request (cancellation, maximum queue wait, start failures, profile deletion, link removal, organization deletion), the adapter releases the claim at once; a claim poller on the lease holder retries every 10 seconds until the vendor confirms. The poller also releases the claim of a request whose runner program exited, and asks the vendor every 10 seconds whether the runner program of a `STARTING` request took its session; then the runner becomes `BUSY` and the request `RUNNING`. Organization deletion releases the claims of queued requests before the deletion transaction, while the credentials still exist. When the vendor does not confirm a release (for example, it answers `503`), the deletion stops and keeps the organization, its credentials and the claim, so that the admin can try again. For the same reason, `DeleteAgentIntegration` fails with `failed_precondition` while tide holds a claim of the integration, for example the claim of a busy runner that outlived the deletion of its profile, or a claim whose release failed. The poller releases these claims, and then the deletion is possible. The vendor APIs identify a claim only by the vendor request ID, so a late release of an earlier claim would end the claim of a follow-up. Thus, when a follow-up of a vendor request arrives while tide still holds the claim of its ended earlier request, tide releases the earlier claim first and claims nothing until the vendor confirms. On each instance, the claim and the release calls of one vendor request run one at a time.
- Program exit: exit code `0` ends the request with `ENDED` and `COMPLETED`. Any other result (a non-zero exit code, a signal, a timeout, an exec failure) ends it with `FAILED` and `RUNNER_LOST`, like a lost sandbox; the vendor decides whether the session runs again. In both cases tide deletes the sandbox and the poller releases a claim that the vendor still holds.
- Runner credential: tide creates the runner directory (`/tmp/tide-runner-<runner_id>` with mode `0700` on Linux and macOS, `C:\ProgramData\tide\runners\<runner_id>` with an ACL that grants only the exec user on Windows), writes the credential to its `credential` file (mode `0600`) with an OwnSand file write, and starts the program with a script that reads the file into the program's environment variable, deletes the file, changes to the home directory and appends the program's output to `runner.log` in the same directory. The credential is never in an exec command, an exec environment, a log record or the claim row. The tide-only credential never enters the guest.
- Vendor API calls use the shared client `agent/vendorhttp` (standard library only). It logs every answer that is not 2xx as `vendor_api_error` with the vendor, the operation and the HTTP status, and never logs credentials, bodies or query values.
- Configuration: the vendor API origins are fixed (`https://api.cursor.com`, `https://api.devin.ai`, `https://api.openai.com`); only tests replace them through the layer options. The adapters add no environment variable.

Cursor (verified against the vendor documentation of 2026-11-22 with a fake of the Cursor API only):

- API: `https://api.cursor.com` with the service account API key in Basic authentication (the key as user name, an empty password). The key needs the `agent` scope. Endpoints: `GET /v0/private-workers/pending-requests?pool=<pool>&limit=100&pageToken=<t>`, then `GET /v0/private-workers/pending-requests/stream?pool=<pool>&cursor=<streamCursor>` (SSE), `POST /v0/private-workers/claim` with `{"id","workerId"}`, `POST /v0/private-workers/claims/{id}/fail` with `{"message"}`, `POST /v0/private-workers/claims/{id}/release` and `GET /v0/private-workers?workerIds=<ids>` (at most 100 IDs).
- Watch: tide lists every page, admits each request without `claimedWorkerId`, and follows the stream from the list's `streamCursor`. It lists again 4 minutes plus up to 30 seconds after the list (the cursor expires 5 minutes after the list) and after `410 Gone`. `created` events are admitted; `claimed`, `claimed_offline`, `expired` and `heartbeat` change nothing.
- Runner program (vendor-doc conflict, resolved in favor of the Cursor reference): the options come before `start`. tide runs `agent worker --pool <pool> --worker-dir <home> --idle-release-timeout 600 start` with `CURSOR_API_KEY` from the credential file and `CURSOR_AGENT_WORKER_ID` equal to the claim's `workerId`. The idle release timeout of 10 minutes (recorded decision; Cursor's default is 1 hour) keeps the worker for follow-up messages and then lets it exit with code `0`.
- `BUSY`: a worker that `GET /v0/private-workers` reports as connected (`connectedAtMs`) or in use (`isInUse`).
- End before a runner took the session (vendor-doc conflict: "release" alone returns the request to the queue): tide calls `fail` with a message that names the reason, which ends the user's waiting turn and frees the claim. When Cursor answers `400` (no turn waits, or the worker is connected), tide calls `release`. Other claims (the session ran, or tide lost a race) are released with `release`. `404` counts as done; `400 Worker in use` and `5xx` are retried by the poller.
- Install: Linux and macOS `curl https://cursor.com/install -fsS | bash` when `agent --version` fails; Windows PowerShell `irm 'https://cursor.com/install?win32=true' | iex` when `Get-Command agent` fails. Prepare fails with a clear message when the guest lacks `curl` or `bash` (Linux, macOS) or Git for Windows with Git Bash (Windows; the worker does not start without it).

Devin (verified against the vendor documentation of 2026-11-22 with a fake of the Fleet API only):

- API: `https://api.devin.ai` with the v3 service-user API token as `Authorization: Bearer`. The token needs `account.outposts.write` and stays in tide. Endpoints: `GET /opbeta/outposts` (tide resolves `outpost_name` to the outpost whose `spec.name` or `metadata.outpost_id` equals it, because the queue filter takes an outpost ID), `GET /opbeta/outposts/devins?outpost=<id>&phase=pending&first=200&cursor=<c>` until `has_next_page` is false, `GET /opbeta/outposts/devins?outpost=<id>&watch=true&cursor=<c>` (SSE with `{type, object, cursor}`), `GET /opbeta/outposts/devins/{session_id}`, `POST .../{session_id}/claim` and `POST .../{session_id}/release` with `{"acceptor_id"}`, and `POST .../{session_id}/operator-message` with `{"message"}`.
- Watch: a `pending` entry is admitted. A pending entry with an open tide request means that tide's claim lapsed (for example at `status.claim_deadline`); tide claims it again with the same acceptor ID. An entry that another acceptor claimed, and a `DELETED` entry, end a `QUEUED` request with `CANCELED` and `CANCELED_BY_SOURCE`; a request whose runner already started ends with the program exit. An entry that tide's acceptor ID holds with `session_status` `running` makes the runner `BUSY`; the poller also reads the entries of `STARTING` requests.
- Runner program (vendor-doc conflict, resolved in favor of the orchestration guide): an orchestrator that claims first runs `devin worker start --session=<session_id> --outpost=<outpost_id> --acceptor-id=<claim acceptor_id>`, not `--once`, because `--once` without `--session` claims any session of the queue. The worker gets only `DEVIN_OUTPOSTS_TOKEN` (the outpost token) from the credential file and runs in the home directory, so repositories go under `<home>/repos`.
- Release: after the worker exits, tide releases the claim when `session_status` is `suspended` or `terminated`, or 2 minutes after the request ended, because the status can lag the exit. A session that tide gives up before a worker took it first gets an operator message that names the reason. A released session returns to the Devin queue at once, so tide treats it as new demand (`#<n>` source key), except after a user cancellation.
- Install: Linux and macOS `curl -fsSL https://cli.devin.ai/install.sh | bash` when `command -v devin` fails; Windows PowerShell `irm https://static.devin.ai/cli/setup.ps1 | iex` when `Get-Command devin` fails. Prepare fails with a clear message when the guest lacks `git` (required by Devin workers), `curl` or `bash`, or when the platform is macOS on x64 or Windows on a CPU other than x64 (Devin has no worker binary for them). OwnSand already prevents these platforms: macOS guests run only on Apple silicon, and Windows guests run only on amd64.

Gaps in the vendor documentation (NOT DOCUMENTED; tide implements them defensively):

- Cursor: the install path of `agent` (tide adds `$HOME/.local/bin` to `PATH` on Linux and macOS and reloads the machine and user `PATH` on Windows), a minimum CLI version, the status code of a second claim while a live claim exists (tide treats `409` as "another worker holds it"), a `409` for a lost response of tide's own claim (tide creates no request; the claim expires at Cursor), whether `createdAtMs` changes for a follow-up turn (the decline rule compares it), and claimed-but-offline entries (`claimedWorkerId`, only with `workerReadyTimeoutSeconds` above 0), which tide does not adopt. At most 4 streams can run per service account, so more than 4 integrations with one key fail to watch. The session-token claim option (`sessionToken`, `--auth-token-file`) would keep the API key out of the guest; this contract keeps `CURSOR_API_KEY` as the runner credential.
- Devin: the install path of `devin` (tide adds `$HOME/.local/bin` and `$HOME/.devin/bin` to `PATH`), the shape and paging of `GET /opbeta/outposts` (tide accepts `items`, `cursor` and `has_next_page` like the queue list), the length of the claim deadline, the release status codes (tide counts 2xx, `404` and other 4xx except `429` as done and retries `429` and 5xx), the worker exit codes, what removes an entry (`DELETED`), whether the v3 API token can replace the outpost token, and whether the installers run without a terminal. A resumed session (`spec.kind` `resume`) expects the working directory and `~/.devin/worker` of the earlier worker, which a new sandbox does not have; Devin then warns about missing stamp files.

#### OpenAI Codex

- Each `OPENAI_CODEX` integration has its own webhook URL `https://tide.api.delino.io/webhooks/openai/<integration_id>` (the origin is `PUBLIC_ORIGIN`) and webhook secret. The admin registers this URL in the OpenAI project.
- An `agent.session.action_required` event with the required action type `environment_connection` creates a request. The request key is the OpenAI session ID and environment ID.
- OpenAI waits at most 5 minutes for the executor, so the maximum queue wait of an `OPENAI_CODEX` runner profile must not exceed 5 minutes.
- OpenAI documents that an idle event alone does not show that a session ended. The runner of a Codex session ends when the executor process exits, or at the runner profile's `max_ttl`.

Implementation (recorded decisions, package `servers/tide-api/internal/agent/codex`; verified against the OpenAI documentation of 2026-11-22 and the `codex exec-server --help` output of `@openai/codex` 0.173.0-alpha.4, with the `codexfake` Agents API and the fake OwnSand only):

- Credentials (vendor-doc conflict: this contract named only the webhook secret as the credential that stays in tide). The webhook carries only the session ID and the action type, and the session read needs an OpenAI API key with `api.agents.read`, so an `OPENAI_CODEX` integration has three credentials: the webhook secret (`whsec_...`) and the API key, which stay in tide, and the environment key, which enters the runner as `CODEX_API_KEY`. The [protos contract](protos-tide-api-contract.md#agent-integration-messages) adds the API key as `OpenAiCodexCredentials.api_key` and `AGENT_CREDENTIAL_API_KEY`; `CreateAgentIntegration` requires it. The lifecycle guide asks to keep the signing secret and the session-read credential separate from the environment key.
- Signature ([Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md), which OpenAI follows): the headers `webhook-id`, `webhook-timestamp` (Unix seconds) and `webhook-signature` are required. The signed content is `<webhook-id>.<webhook-timestamp>.<raw body>`, the key is the base64 (standard alphabet) decoding of the secret after `whsec_` (a secret without the prefix is used as its bytes, like the OpenAI SDKs), and the signature is the base64 of HMAC-SHA256. `webhook-signature` is a space-separated list; any `v1,<signature>` entry may match, compared in constant time. The timestamp must be within 5 minutes of the server time in both directions (the default of the OpenAI SDKs; the guide gives no number).
- Answers: `200` after the commit; `401` (`invalid_signature`) for a missing or invalid signature, a timestamp outside the tolerance, an unknown integration ID and an integration of another vendor, which have no secret to verify with; `413` for a body over 1 MiB; `400` for a missing or invalid `webhook-id` or a signed body that does not parse; `500` (`failed`) when the session read or the store fails, which records nothing, so OpenAI delivers the event again (it retries for up to 72 hours). A recorded `webhook-id` answers `200` without a session read. Each delivery is logged as `openai_webhook_delivery` with the delivery ID, the event type, the result, the status, the integration, organization, request and runner IDs and the session ID, never the body.
- Connection requests: for `agent.session.action_required` with `environment_connection`, tide reads `GET https://api.openai.com/v1/agents/sessions/{session_id}` with `Authorization: Bearer <API key>` and `OpenAI-Beta: agents=v1` (the header of the OpenAI SDKs for the Agents API beta) before the transaction, with a 5-second timeout. It creates a request only when the session still lists an `environment_connection` required action, its `environment` has `type` `self_hosted`, an ID and an `https` `remote_url`, the organization has an `ACTIVE` OwnSand link that is not being removed and a runner profile names the integration; otherwise it records the delivery as `ignored`. The source key is `<session_id>:<environment_id>`; while a request of the session is open, a new connection request creates nothing, and after it ended a new one gets `#<n>`. The claim row holds the session ID, the environment ID as its scope, the remote URL and the session's `workspace_directory`. A deleted session (`404`) is ignored.
- Session failures: for `agent.session.failed`, tide reads the session. When it is still `failed`, a `QUEUED` request of the session ends with `CANCELED` and `CANCELED_BY_SOURCE`, a started one with `FAILED` and `CANCELED_BY_SOURCE`, and its runner is deleted (`CLEAN_UP`), because the lifecycle guide asks to release the compute of a failed session. Other events and other required actions are recorded as `ignored`.
- Runner program: Start creates the session's `workspace_directory` with `mkdir -p` when the session names one (an absolute path; the guest exec user must be able to create it), writes the environment key to the credential file and runs `codex exec-server --remote <environment.remote_url> --environment-id <environment.id>` with `CODEX_API_KEY` from the file, in the home directory, with `$HOME/.local/bin` and the bin directory of the Node.js that tide installs on `PATH`. The Node.js bin directory comes first, so that the executor uses the Node.js that tide installed and not an older one of the guest.
- `BUSY`: the API clears the `environment_connection` action when the executor connects, so the claim poller reads the session of each `STARTING` request every 10 seconds and marks the runner `BUSY` when the session is not `failed` and lists no `environment_connection` action.
- End: an executor exit with code `0` ends the request with `ENDED` and `COMPLETED`, any other result with `FAILED` and `RUNNER_LOST`. The executor's exit behavior is not documented, so the profile's `max_ttl` is the planned end: an OwnSand TTL end of the sandbox ends the runner with `DELETED` and `SANDBOX_ENDED` and the request with `ENDED` and `SESSION_TTL_EXPIRED`. Admins choose a `max_ttl` that fits their sessions.
- Executor exit (recorded decision): `codex exec-server --exit-on-stdin-close` exists in the CLI help and the source, not in the guide. tide does not use it, because OwnSand execs give the program no standard input that tide controls.
- Version (vendor-doc conflict between the guide and the npm tags): the self-hosted guide installs `npm install -g @openai/codex@alpha`; on 2026-11-22 `latest` was 0.171.0 and `alpha` 0.173.0-alpha.4. The stable 0.171.0 has `exec-server --remote --environment-id`, but whether OpenAI supports the stable line with the Agents API is not documented. tide follows the guide's channel and pins the exact version `0.173.0-alpha.4` ([version policy](#runner-installation)); the Renovate custom manager follows the `alpha` dist-tag.
- Release: OpenAI has no claim to give back; a session that tide does not serve fails its submission after the 5-minute connection wait.
- Guest OSes: the adapter has POSIX scripts for Linux and macOS; Prepare fails a Windows guest (exit code 18). Verified guest OSes: none. The interim rule of [Agent integrations](#agent-integrations) stays until an acceptance run verifies one. An acceptance run adds a verified guest OS like this: run a build of `tide-api` whose layers accept the guest OS under test (the layer option `CodexGuestOSes`, which the integration tests use, or a local change of `profile.VerifiedCodexGuestOSes`), and run the full session lifecycle (webhook, runner start, executor connection, `BUSY`, end) on a real OwnSand device of that guest OS with a real OpenAI project. When it passes, the same change adds the guest OS to `profile.VerifiedCodexGuestOSes` (only Linux and macOS can pass) and to this section, with the run in the pull request or Linear issue.

Gaps in the OpenAI documentation (NOT DOCUMENTED; tide implements them defensively):

- The host OSes of `codex exec-server` (the guide shows only Linux paths and containers; npm has Linux, macOS and Windows builds): see the interim rule.
- Whether `codex exec-server` exits when a session ends or goes idle: tide relies on `max_ttl`, a session failure and the executor's own exit.
- Whether the stable `@openai/codex` line works with the Agents API: tide pins the `alpha` channel.
- Whether the 5-minute connection wait clears the `environment_connection` action when it expires: then the poller marks the runner `BUSY` although no executor connected, and the runner ends at its exit or `max_ttl`.
- Routing of events when several handlers share a project: the cookbook filters on an agent ID, which tide does not have. tide serves every self-hosted session of the project whose webhook names the integration, so admins use a dedicated OpenAI project per integration.
- When `required_actions[].environment_id` differs from `environment.id`: tide uses `environment.id` and `environment.remote_url`, as the lifecycle guide says.

### Runner profiles

| Field                  | Rule                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                 | Lowercase kebab-case, 1 to 40 characters, unique in the organization. For `GITHUB_JOB`, the GitHub label is `tide-<name>`.                                                                                                                                                                                                                                                                                          |
| `workload_kind`        | `GITHUB_JOB`, `AGENT_SESSION` or `DEV_SESSION`. Cannot change after creation.                                                                                                                                                                                                                                                                                                                                       |

Cannot change after creation.                                                                                                                                                                                                                                                                                                              |

Dev session file sync writes into it, and it is the default working directory of dev session commands.                                                                                                                                                      |

For `DEV_SESSION`, any of the three.                                                                                                                                                                                                                                          |
| `source`               | An OwnSand base image of `guest_os`, or an OwnSand template ID whose guest OS is `guest_os`. | `resources`            | The OwnSand rules apply. The inclusive ranges are 1 to 1024 for `vcpu_count`, 1 to 16777216 for `memory_mib` and 1 to 1048576 for `disk_gib`. The first violation returns `invalid_argument` with `invalid resources.<field>: must be greater than zero` or `invalid resources.<field>: must be at most <limit>`.                                              |

Dev sessions use the same rule, so that builds and tests can download dependencies.                                                                                                                                                                                                               |
| `idle_ttl`, `max_ttl`  | Passed to OwnSand, with the OwnSand rules (`max_ttl` at most 7 days). The running runner program keeps the sandbox active, so `idle_ttl` deletes a sandbox only after its program ended. A dev session has no runner program: every command and file operation restarts the OwnSand idle clock, and a running command keeps the sandbox active, so `idle_ttl` deletes a dev session that nobody used for that time. |
| `priority`             | `HIGH`, `NORMAL` or `LOW`. Default: `HIGH` for `GITHUB_JOB`, `NORMAL` for `AGENT_SESSION` and `DEV_SESSION`.                                                                                                                                                                                                                                                                                                        |
| `max_queue_wait`       | Required. Greater than zero and at most 24 hours; at most 5 minutes for an `OPENAI_CODEX` integration.                                                                                                                                                                                                                                                                                                              |
| `warm_count`           | 0 to 10. Default `0`. The same rule applies to `DEV_SESSION`.                                                                                                                                                                                                                                                                                                                                                       |

- A change of a runner profile applies to runners that start after the change. Running runners keep their settings.
- Validation details (recorded decisions): a Windows `workspace_path` is `X:\` followed by a relative path with `\` separators; a Linux or macOS `workspace_path` starts with `/`. Neither has a `.` or `..` segment, an empty segment or a trailing separator, because sync keeps its manifest and lock next to the workspace. A template `source` is checked with OwnSand (the template exists and its snapshot has the profile's `guest_os`) when the organization has an `ACTIVE` OwnSand link; without one, OwnSand checks it when a runner starts. `idle_ttl`, `max_ttl` and `max_queue_wait` must be whole milliseconds, because tide stores them in milliseconds. `network_mode` and `priority` are required in updates; `CreateRunnerProfile` fills an unset `priority` with the default of the workload kind.
- `UpdateRunnerProfile` accepts the mask paths `name`, `workspace_path`, `guest_os`, `source`, `resources`, `resources.vcpu_count`, `resources.memory_mib`, `resources.disk_gib`, `network_mode`, `idle_ttl`, `max_ttl`, `priority`, `max_queue_wait` and `warm_count`. The `resources` path replaces all three resource values. Each individual resource path updates only the named value.
- On each attempt, the API applies the mask to the current stored profile and validates the whole result before writing. If the stored profile changes after the API reads it, the API reads it again and reapplies the mask. When the profile changes during three attempts in a row, the update fails with `failed_precondition`.
- Deleting a runner profile ends its queued requests with `CANCELED` and deletes its warm runners and its runners that wait for work. Busy runners finish their work.

### Personal API keys

- Every member can create personal API keys for themselves in an organization with `ApiKeyService.CreateApiKey`, with a name (1 to 64 characters) and an optional expiry time. A key without an expiry stays valid until it is revoked. Each user lists and revokes only their own keys.
- Secret format: `tide_` followed by 32 random bytes from a cryptographically secure source in unpadded base64url, like the [OwnSand API keys](servers-ownsand-api-foundation.md#authentication). `CreateApiKey` returns the secret once.
- The server stores only the SHA-256 hash of the secret and a short non-secret prefix for display. A lookup hashes the presented value, loads the row by that hash and compares the stored hash in constant time. A value with the `tide_` prefix but a wrong shape gets `unauthenticated`.
- A revoked or expired key gets `unauthenticated`. The server records the last use time of each key with at most one write per key per minute. Only an accepted use counts: a valid key that an RPC other than `DevSessionService` rejects does not change the last use time.
- The display prefix is `tide_` and the first 4 characters after it, like the invitation display prefix (`tdi_` and 4 characters). The rate limit of authentication failures keys on it.
- When a membership ends (removal by an admin or leaving), the server revokes every key of that user in that organization in the same transaction. It then ends the user's dev sessions of the organization as described in [Dev sessions](#dev-sessions). The dev session layer does this through the membership end hook of the core: one step in the same transaction and one step after the commit.
- Organization deletion revokes every key of the organization and records an `API_KEY_REVOKED` audit event for each, then deletes the keys with the organization.

### Dev sessions

A dev session gives one user a sandbox of a chosen guest OS for builds and tests. The user, or a coding agent for the user, picks a `DEV_SESSION` runner profile by name. The admin decides the guest OS, source, resources, workspace path, TTLs, priority, maximum queue wait and warm count in the profile.

Creation and queueing:

- `CreateDevSession` takes the runner profile ID and an optional label (at most 100 characters, for display). It creates a request of kind `DEV_SESSION` with the caller as the session owner and returns at once with the dev session ID (the request ID) and the request state. It never waits for capacity.
- The request uses the [queue](#queue-and-dispatch) with the profile's priority and maximum queue wait, like every other request. When no capacity is free, it stays `QUEUED`; when its maximum queue wait ends, it ends with `EXPIRED`.
- `GetDevSession` and `ListDevSessions` return the state. The SDKs and the MCP server wait for readiness by repeated `GetDevSession` calls.
- Per-user limit: the organization setting `max_dev_sessions_per_user` is unset by default, which means no limit. An admin can set it to a positive integer. It counts the user's dev sessions in `QUEUED`, `STARTING` and `RUNNING`. `CreateDevSession` fails with `resource_exhausted` when the user already has that many. Lowering the setting ends no existing dev session.

Lifecycle:

- Dispatch is the same as for `AGENT_SESSION` requests: the dispatcher assigns a warm runner of the profile or creates a sandbox. In `PREPARING`, tide creates the profile's `workspace_path` in the guest when it is missing. tide installs and starts no runner program.
- When the runner is ready, the runner changes to `BUSY` and the request to `RUNNING`. The request is `STARTING` from runner assignment until then. Only a `RUNNING` dev session accepts commands and file transfers; other states get `failed_precondition`.
- `DeleteDevSession` by the session owner, or by an `owner` or `admin` of the organization, ends a queued dev session with `CANCELED` and the end reason `CANCELED_BY_USER`, and ends a starting or running dev session with `ENDED` and the end reason `SESSION_DELETED` after tide deletes its sandbox. Running commands end with the sandbox.
- When OwnSand deletes the sandbox at its `idle_ttl` or `max_ttl`, the runner changes to `DELETED` with `SANDBOX_ENDED`, and the request ends with `ENDED` and the end reason `SESSION_TTL_EXPIRED`. Other OwnSand end reasons follow step 6 of the [runner lifecycle](#runner-lifecycle): the runner changes to `FAILED` and the request ends with `FAILED` and `RUNNER_LOST`.
- When the owner's membership ends, the server ends the owner's queued dev sessions with `CANCELED` and the end reason `MEMBER_REMOVED`, and deletes the sandboxes of the others, which end with `ENDED` and `MEMBER_REMOVED`.
- A dev session does not depend on the client that created it. When the MCP server or the CLI exits, the dev session stays until it is deleted or its TTL ends.
- Implementation (recorded decisions): `CreateDevSession` serializes the caller's creations in an organization with a lock of the caller's membership, so two parallel calls cannot pass the per-user limit together. It also holds a shared lock of the runner profile row until it commits, so a concurrent `DeleteRunnerProfile` either cancels the new request or makes the call fail with `not_found`. `DeleteDevSession` ends the request and marks the runner `DELETING` in one transaction, then deletes the sandbox before it answers. It locks the session's open runner and then the request (the lock order of the engine) and decides on the locked state, so a session that the dispatcher started meanwhile has its runner deleted and is not only canceled; when OwnSand fails, the lease holder retries the sandbox deletion. When the owner's membership ends, the same transaction that revokes the API keys ends the dev sessions, and the sandboxes are deleted after the commit, with the same retry.

### Dev session commands

- `ExecDevSession` (server-streaming) runs one command in the guest. The request carries the dev session ID, a client-generated `exec_id` (UUID v7), the argument array, an environment map, an optional working directory (an absolute guest path, or a path relative to `workspace_path`; the default is `workspace_path`) and an optional timeout. The server checks the caller and the session state, then calls the OwnSand exec through the OwnSand Go SDK with the organization's OwnSand API key and forwards the event stream.
- `AttachDevSessionExec` (server-streaming) continues the event stream of an exec from given stdout and stderr offsets, with OwnSand `AttachExec`.
- The tide exec event messages carry the same information as the OwnSand exec events (`started`, `output_truncated`, `stdout` and `stderr` chunks with offsets, `exited` with an exit code or signal and `timed_out`, `failed` with a reason, `sandbox_ended`), in tide's own schema. The OwnSand rules apply without change: the command runs independently of the stream, the agent keeps the last 8 MiB of each output stream and the exit result for 10 minutes after the command ends, and stdin is not supported.
- The command, environment and resolved working directory together must encode to at most 256 KiB. If they exceed this limit, `ExecDevSession` returns `invalid_argument` with the size limit in the message.
- tide ends each forwarded stream before it has run for 14 minutes, with an OK status and no final event, and sends a keepalive event at least every 60 seconds while the command produces no output. The client continues with `AttachDevSessionExec`.
- Environment values in exec requests are not stored, not logged and not added to audit events. They can carry secrets that a local `tide mcp` process passes from its own environment.
- Implementation (recorded decisions): a forwarded stream ends after 13 minutes and 30 seconds, and a keepalive goes out when no event went out for 30 seconds. A relative `working_directory` or file `path` is joined to the runner's `workspace_path` with the separator of the guest OS; an absolute path is used unchanged. The `exec_id` is sent in lowercase. `dev_session_exec_ended` log records carry the result, exit code or signal, the failure reason and the duration, never the command or the environment.

### Dev session file transfer

- `WriteDevSessionFile` (unary) writes one chunk of at most 1 MiB to an absolute guest path at an offset, and `ReadDevSessionFile` (server-streaming) streams a guest file from an offset. The server forwards them to OwnSand `WriteFile` and `ReadFile` with the OwnSand operation ID rules: the caller generates the `write_id` or `read_id`.
- The server applies no file size limit of its own. The clients enforce the transfer limits of [sync](#dev-session-sync) and [download](#dev-session-download) before they start a transfer, because the limits protect the bandwidth of the shared Droplet.
- `WriteDevSessionFile` returns `invalid_argument` if the offset plus the chunk length exceeds the maximum signed 64-bit integer.
- If OwnSand rejects a read or write because it does not match the recorded operation, tide returns `failed_precondition` with the message `Restart the file transfer from the beginning with a new operation ID.` Use a new `read_id` or `write_id` for the restarted transfer.
- Relay state (recorded decision): the OwnSand binding salt of a relayed read or write is derived from its `read_id` or `write_id` with the primary key of `TIDE_SECRET_KEYS` (HMAC-SHA256), so every call of one operation uses the same salt on every instance. A `ReadDevSessionFile` call that ends at the stream limit sends no end message; the client continues with the same `read_id` from its next offset. `tide-api` keeps the OwnSand write of each `write_id` in memory between `WriteDevSessionFile` calls and drops it 20 minutes after its last chunk or after the final chunk. After a deployment handover, the next chunk opens the write again on the new instance with the same salt, so the write continues; a write that OwnSand already dropped (15 minutes without a chunk) fails with `not_found`, and the client starts the file again with a new `write_id`. A rotation of the primary key during a transfer changes the salt; the client then starts the transfer again.

#### Dev session sync

The Go SDK implements sync for the CLI and the MCP server. Sync copies a local working tree into the profile's `workspace_path`:

1. The local root is a directory in a Git working tree. The file list is the output of `git ls-files --cached --others --exclude-standard` for that directory: tracked files and untracked files that are not ignored. Ignored files are never sent. A local directory that is not in a Git working tree fails before any transfer. Submodule entries are not entered; sync reports them as skipped.
2. The client reads the guest manifest `<workspace_path>.tide-sync.json` (next to the workspace, not in it). The manifest lists each synced relative path with its size, SHA-256 and mode. A missing or unreadable manifest counts as empty.
3. The client hashes the local files and computes the changed and new files, and the deleted files (in the manifest, but not in the local list). Files that the guest created and that are not in the manifest, such as build output, stay.
4. The client rejects the sync before any upload when a changed file is larger than 100 MiB or the changed files together are larger than 2 GiB. The error lists the paths and sizes that break the limit.
5. The client rejects the sync before any upload when two local paths differ only in case and the guest OS is `WINDOWS` or `MACOS`, or when a path is not valid on a `WINDOWS` guest (reserved names or characters). The error lists the paths.
6. The client takes the sync lock: it creates the directory `<workspace_path>.tide-sync.lock` with one exec, which fails when the directory exists. A sync that finds the lock fails with `failed_precondition` and tells the caller that another sync runs. `--force` (CLI) or `force` (MCP) removes a lock that a stopped sync left. After the client takes the lock, it reads the manifest again. When the manifest changed after the first read, for example because another sync ended in that time, the client does steps 3 and 4 again with the new manifest. When nothing then changes, it releases the lock and ends.
7. The client packs the changed files into one tar archive, uploads it with `WriteDevSessionFile` to a temporary file next to the workspace, extracts it into `workspace_path` with the guest's `tar` (part of Linux, macOS and Windows 10 and later), deletes the deleted files, writes the new manifest, removes the archive and releases the lock.

- Contents are copied byte for byte. Sync converts no line endings.
- Linux and macOS guests keep the executable bit. Windows guests ignore modes.
- Symbolic links are created as links. When a Windows guest cannot create a link, sync reports the path as a warning and continues.
- A sync that stops before step 7 ends leaves the old manifest, so the next sync sends the same files again. A sync is idempotent.

#### Dev session download

The Go SDK implements download for the CLI and the MCP server. Download copies a guest file or directory to a local path:

- A directory is packed in the guest with `tar` into a temporary archive next to the workspace, downloaded with `ReadDevSessionFile` and extracted locally. The client removes the guest archive after the download.
- The client rejects the download when one file is larger than 500 MiB or the transfer is larger than 2 GiB in total. It checks the size of a single file or of the archive before it reads it, and checks each archive entry during extraction.
- Local extraction rejects entries with absolute paths, entries that resolve outside the local destination and symbolic links that point outside it. It writes to a temporary location and moves the result into place only after the download succeeds.
- Download never changes the local working tree unless the caller names a destination in it.

### Queue and dispatch

- The queue holds the requests in `QUEUED` state of all runner profiles of one organization. The order is: priority (`HIGH` first), then the time when tide created the request (oldest first), then the request ID.
- The dispatcher runs a pass for an organization when a request arrives, a runner ends, a sandbox of the organization ends, a runner profile changes, and at least every 15 seconds.
- In each pass, the dispatcher goes through the uncovered requests in queue order:
  1. When a warm runner of the request's profile exists, it assigns that runner to the request.
  2. Otherwise, it calls OwnSand `CreateSandbox` without `device_id`, with the profile's source, resources, network, TTLs and the tide labels. The OwnSand scheduler selects the device and applies the device limits, including the [vCPU overcommit](servers-ownsand-api-foundation.md#vcpu-overcommit).
  3. When OwnSand returns `unavailable`, the request stays in the queue. When warm runners of other profiles exist, the dispatcher deletes one of them (from the profile with the lowest priority first, then the oldest warm runner), so that the next pass may find capacity.
  4. When OwnSand returns `failed_precondition`, no device of the OwnSand organization can ever run the profile. The request ends with `FAILED` and the end reason `NO_ELIGIBLE_DEVICE`.
  5. The dispatcher continues with the next request. A request that does not fit does not block smaller requests behind it.
- The dispatcher creates warm runners only when the queue of the organization has no uncovered request, so that warm runners never take capacity from waiting requests.
- tide never preempts a runner that serves a request.
- Each `CreateSandbox` call uses an `idempotency_key` that tide generates and stores with the runner before the call, so a retry after a lost response does not create a second sandbox.
- A request that is still `QUEUED` when its `max_queue_wait` ends ends with `EXPIRED`. tide releases its vendor claim when one exists.
- Implementation (recorded decisions):
  - The dispatcher, one driver goroutine per open runner (the runner reconciler) and the gauge collector run as lease components. A change on the lease holder (a new request, a profile or link change, an ended runner) starts a pass at once; a change on another instance waits for the next periodic pass. On the lease holder, a runner's driver waits for the dispatcher to apply the first `CreateSandbox` result before it can retry.
  - A request of a binding workload kind (`DEV_SESSION`, `AGENT_SESSION`) stays `QUEUED` until OwnSand created its sandbox: the dispatcher stores the runner with the request and the idempotency key first, so a request that finds no capacity does not change state, and the stored runner keeps the next pass from dispatching it twice. The request is `STARTING` from the successful `CreateSandbox`, which also counts the start attempt.
  - `unavailable` removes the stored runner (no sandbox exists) and deletes at most one warm runner of another profile per pass. The warm runners of a runner pool count too (see [GitHub App integration](#github-app-integration)), and a runner that the workload adapter keeps (it took work meanwhile) is skipped for the next one. `invalid_argument`, `not_found` and `permission_denied` from `CreateSandbox` count as a start failure. These rules, and the `failed_precondition` rule, apply only to an error that OwnSand sent (a Connect wire error): OwnSand answers an error only before it commits a sandbox. An error that the client made from a transport failure or from the HTTP status of an intermediary (for example a proxy's 503, which the client reads as `unavailable`) is an uncertain result, because the sandbox may exist. Any other error or a lost response keeps the runner `CREATING`, and its driver repeats `CreateSandbox` with the same key. Each `CreateSandbox` call ends after 15 seconds without an answer; that end is an uncertain result, and it also ends the organization's dispatcher pass, so an OwnSand call that stalls cannot stop the dispatch and the maximum queue wait checks of other organizations. The runner stores the `CreateSandbox` request of its first call, and every retry sends that request unchanged: OwnSand binds the key to the request parameters, so a request rebuilt from a profile that changed or was deleted meanwhile would fail with `already_exists`.
  - A warm-fill start failure waits at least one dispatcher interval before another warm attempt for the profile. Each failure doubles the wait up to 10 minutes. After three consecutive permanent OwnSand creation rejections, tide logs that warm fill stopped. Updating the profile or setting the OwnSand link again restarts warm fill. A runner that becomes ready clears the backoff before the stop. Tide stores the retry state across dispatcher lease changes. Requests can still start runners while warm fill waits or is stopped.
  - A request's `priority` is the profile's priority when the request arrives.
  - Workload adapters: the `work.Adapter` interface holds what the contract leaves to a workload kind: whether the dispatcher binds a runner to one request (`BindsAtDispatch`) or starts runners for a runner pool (`PoolKey`, `GITHUB_JOB`), preparation of the guest (`Prepare`), the start of the runner program with its credential (`Start`), the request outcome of a program exit, a sandbox end and a runner deletion, and the release of a vendor claim. A layer that receives demand creates requests with `Engine.CreateRequest` (unique per organization, source and source key) and reports progress with `Engine.MarkBusy` and `Engine.EndRequest`. The `DEV_SESSION`, `GITHUB_JOB` and `AGENT_SESSION` adapters exist (`AGENT_SESSION` serves Cursor and Devin; see [Cursor and Devin](#cursor-and-devin)); a request of a kind without an adapter, or of a vendor without an adapter, waits until its maximum queue wait. Optional adapter interfaces: `RegistrationRemover` (removes a registration outside OwnSand before the engine deletes a sandbox: in `DELETING`, after a start failure and in the clean-ups; an error keeps the sandbox and the deletion is repeated), `WarmPooler` (the runner pools in which a kind without `BindsAtDispatch` keeps its warm count; without it, such a kind gets no warm runners), `WarmReclaimer` (deletes a warm runner of such a pool for a reclamation, after it removed the registration outside OwnSand; without it, these warm runners are not reclaimed) and `RequestDecorator` (kind-specific fields of request responses, such as the GitHub job). `Engine.MarkBusyTx`, `Engine.EndRequestTx`, `Engine.PoolSurplus` and `Engine.DeleteIdleRunnerTx` let a webhook store its effects in its delivery's transaction and remove surplus runners of a pool.

### Runner lifecycle

1. `CREATING`: tide created the OwnSand sandbox and waits until it is `RUNNING`.
2. `PREPARING`: tide checks for the runner program in the guest and installs it when it is missing (see [Runner installation](#runner-installation)). For `DEV_SESSION`, tide creates the `workspace_path` instead and installs nothing. A warm runner then changes to `WARM` and waits for a request.
3. For `DEV_SESSION`, a runner that has a request changes to `BUSY` at once; see [Dev sessions](#dev-sessions). For the other kinds, when the runner has a request (or, for `GITHUB_JOB`, when the dispatcher starts it for its profile), tide writes the runner credential to a guest file that only the runner process reads and starts the runner program with an OwnSand exec. The program writes its output to a log file in the guest, not to the exec stream, so that the exec stream carries only the exit result. The runner is then `WAITING_FOR_WORK`.
4. `BUSY`: the runner program took its job or session.
5. When the runner program exits, or when a dev session is deleted, tide deletes the sandbox (`DELETING`, then `DELETED`). tide follows each runner exec with OwnSand `AttachExec` and resumes it after each relay stream rotation. When tide misses the exit, the profile's `idle_ttl` deletes the sandbox.
6. When OwnSand ends the sandbox for another reason (TTL, device removal, `LOST_ON_DEVICE`), the runner changes to `FAILED` with the OwnSand end reason. An `AGENT_SESSION` request of that runner ends with `FAILED`; the vendor decides whether the session runs again. A `GITHUB_JOB` request ends when GitHub sends the `completed` event.
7. A failure in steps 1 to 3 changes the runner to `FAILED`, deletes the sandbox and returns its request to `QUEUED` with its original queue time. After 3 failed attempts for the same request, the request ends with `FAILED` and the end reason `RUNNER_START_FAILED`.

- Deleting a `GITHUB_JOB` runner that waits for a job first removes its GitHub runner registration in the GitHub organization of its installation.
- `GITHUB_JOB` implementation (recorded decisions): `Start` creates the JIT configuration with the name `tide-<runner_id>`, the runner group of the installation and the label `tide-<profile name>`, and stores only the GitHub runner ID. It writes the JIT configuration with the OwnSand file write to the runner directory with mode `0600` and starts the runner with one exec that reads the file, deletes it and starts the runner; the exec stream carries only the exit result, and the program output goes to `tide-runner.log` in the runner directory (see [Runner installation](#runner-installation)). The runner program exit keeps the request, because GitHub ends it with the `completed` event; an OwnSand sandbox end fails the runner (`SANDBOX_ENDED`) and keeps the request for the same reason, and so does a deletion of a busy runner. The registration removal before a sandbox deletion gives up, and the deletion goes on, when the installation is unlinked or inactive, when GitHub refuses with `422` (the job then ends with the sandbox), on another `4xx` answer except `429`, and 10 minutes after the runner became `DELETING`; other errors repeat the deletion.
- An admin can delete any runner with `DeleteRunner`. tide locks the runner before it checks the state, so a concurrent transition to another active state cannot prevent deletion. tide deletes the sandbox and ends the work in it. If the runner is already deleting or has ended, the call returns the current runner and writes no new deletion audit event.
- Implementation (recorded decisions): a driver checks the sandbox state every 10 seconds and waits at most 30 minutes for a `CREATING` sandbox to be `RUNNING`. A runner that was created for a request that ended before the work started (for example, a dev session that was deleted meanwhile) is deleted with `CLEAN_UP`. `RemoveOwnSandLink`, `DeleteRunnerProfile` and `DeleteOrganization` delete their runners with `CLEAN_UP` before the transaction that ends the queued requests: the link removal ends them with `CANCELED` and `INTEGRATION_REMOVED`, the profile deletion with `PROFILE_DELETED` and the organization deletion with `CANCELED_BY_USER`. A sandbox that OwnSand no longer accepts the key for is left to its `idle_ttl`. A deleted runner without a stored sandbox ID (its `CreateSandbox` response was lost or is still in flight) stays `DELETING` until tide repeats `CreateSandbox` with the stored request and key: tide deletes the sandbox that this call returns, and an error answer of OwnSand means that the key created nothing. The repeated call can create a sandbox when no earlier call did; tide then deletes it at once. A runner that ends while it still has a sandbox to delete (after a start failure, or when a `CreateSandbox` response arrives after the runner ended) is marked for clean-up in the same transaction, and the reconciler retries the sandbox deletion until OwnSand deletes the sandbox, the link is removed or OwnSand rejects the key.
- `WatchQueue` (recorded decision): a trigger gives every write of a request or runner a new change number; the stream reads the changes every second on any instance, sends a keepalive after 25 seconds without an event and ends after 13 minutes and 30 seconds. The dispatcher removes the row of a `CREATING` runner after an `unavailable` answer of OwnSand, and the stream has no removal event, so the stream checks each `CREATING` runner without a sandbox that it sent: when the row is gone, it sends that runner once more with the state `DELETED` and the end reason `CLEAN_UP`. `ListRequests` uses an offset page token, because its order is the queue order.

### Runner installation

- When a runner program is missing in the guest, tide installs it with an OwnSand exec before it starts the runner:
  - GitHub Actions runner: the official release archive from `github.com/actions/runner` at the version that tide pins.
  - `claude`: the official Claude Code installer, at least version 2.1.224.
  - Cursor `agent`: the official Cursor CLI installer.
  - `codex`: the `@openai/codex` npm package at the version that tide pins. The guest needs Node.js. When the guest has no Node.js, tide first installs the official Node.js 24 distribution at the version that tide pins.
  - `devin`: the official Devin CLI installer.
- tide installs the runner programs on every guest OS that the runner profile allows for its workload kind and vendor: Linux, macOS and Windows.
- Version policy (recorded decision):
  - Pinned programs: the GitHub Actions runner, `codex` and Node.js. tide-api pins an exact version of each in its source. Renovate updates the pins through a custom manager that the runner implementation adds to `renovate.json`.
  - Unpinned programs: `claude`, Cursor `agent` and `devin`. tide installs the version that the official installer gives at installation time. tide checks the minimum version only for `claude` (2.1.224). Cursor `agent` and `devin` have no minimum version.
  - tide uses a program that the guest already has (for example, from an OwnSand template) at its installed version, also when that version differs from the pin. tide installs the program again only when its version is lower than the minimum version. Only `claude` has a minimum version.
- An admin can make starts faster: create an OwnSand sandbox from the base image, let tide or the admin install the runner programs, save it as an OwnSand template and set it as the runner profile's `source`. tide then finds the program and skips the installation.
- The exact install commands per guest OS come from the vendor documentation. The runner implementation records them here, together with the guest OSes on which it verified them.
- Cursor `agent` and `devin`: [Cursor and Devin](#cursor-and-devin) records the install commands for Linux, macOS and Windows. They are verified only against fakes of the vendor APIs and of OwnSand; no real Linux, macOS or Windows guest ran them yet.

`claude` (recorded implementation, `servers/tide-api/internal/agent/claude`):

A `claude` whose `claude --version` is 2.1.224 or later is used at its version. Windows is not a Claude Code runner host; Prepare fails it (exit code 15), and profiles cannot select it.

`codex` and Node.js (recorded implementation, `servers/tide-api/internal/agent/codex/install.go`):

The source pins the SHA-256 of `node-v24.22.3-linux-x64.tar.gz`, `node-v24.22.3-linux-arm64.tar.gz`, `node-v24.22.3-darwin-x64.tar.gz` and `node-v24.22.3-darwin-arm64.tar.gz` from `https://nodejs.org/dist/v24.22.3/SHASUMS256.txt`. Two Renovate custom managers in `renovate.json` update `CodexVersion` (following the npm `alpha` dist-tag) and `NodeVersion` (below 25); the Node.js pull request note asks for the new checksums, and `TestNodeChecksums` fails until the checksum table has the pinned version.
- Linux and macOS, one `/bin/sh -c` exec: a working `codex` (`codex --version`) is used at its installed version. Otherwise, when the guest has no Node.js 16 or later with `npm` (the `engines.node` of `@openai/codex`), the script selects the archive by `uname -s` and `uname -m` (`x86_64` or `amd64` gives `x64`, `aarch64` or `arm64` gives `arm64`), downloads it from `https://nodejs.org/dist/v24.22.3/` with `curl -fsSL --retry 3` (or `wget -q`), compares `sha256sum` (or `shasum -a 256`) with the pinned value, and extracts it with `tar xzf --strip-components 1` into `$HOME/.local/share/tide/node-v24.22.3`, whose `bin` directory the install and start scripts put first on `PATH`, before `$HOME/.local/bin` and the guest's `PATH`, so that it wins over a Node.js below 16 of the guest. After the extraction the script clears the shell's command hash (`hash -r`). Then `npm install -g "@openai/codex@0.173.0-alpha.4"` runs with `NPM_CONFIG_PREFIX=$HOME/.local`, so no root access is needed. Exit codes: 10 no `curl` or `wget`, 11 no `tar`, 12 a failed download or extraction, 13 a checksum mismatch, 14 a failed `npm install`, 15 no `codex` afterwards, 16 a platform without an official archive, 17 a musl libc guest (Node.js publishes no official musl archive for both architectures; use a template with Node.js), 18 Windows.

Verification of the `claude` and `codex` install scripts: unit tests run them with stub programs, and the integration tests run them against the fake OwnSand, which runs no command. On 2026-11-22 the two scripts also ran once in a `debian:12-slim` container (not an OwnSand guest) as a non-root user: they installed Node.js 24.22.3, `codex-cli 0.173.0-alpha.4` and Claude Code 2.1.330. No OwnSand Linux or macOS guest ran them yet.

GitHub Actions runner (recorded implementation, `servers/tide-api/internal/github/install.go`):

- Pinned version: `2.338.2` (the latest stable release when it was pinned). The source pins the SHA-256 of each release archive from the release notes: `actions-runner-linux-x64-2.338.2.tar.gz`, `actions-runner-linux-arm64-2.338.2.tar.gz`, `actions-runner-osx-x64-2.338.2.tar.gz`, `actions-runner-osx-arm64-2.338.2.tar.gz`, `actions-runner-win-x64-2.338.2.zip` and `actions-runner-win-arm64-2.338.2.zip` from `https://github.com/actions/runner/releases/download/v2.338.2/`. The Renovate custom manager in `renovate.json` updates `RunnerVersion`; its pull request note asks for the checksums of the new archives, and a unit test fails until the checksum table has the pinned version.
- Runner directory: `/opt/actions-runner` on Linux and macOS, `C:\actions-runner` on Windows (the release notes recommend a short root folder on Windows). An OwnSand template with the runner in that directory skips the installation; tide checks only that `run.sh` and `bin/Runner.Listener` (`run.cmd` and `bin\Runner.Listener.exe` on Windows) exist and uses the installed version.
- Linux and macOS installation, one `/bin/sh -c` exec: select the archive by `uname -m` (`x86_64` or `amd64` gives `x64`, `aarch64` or `arm64` gives `arm64`; other architectures fail), download it with `curl -fsSL --retry 3` (or `wget -q` without curl), compare `sha256sum` (or `shasum -a 256`) with the pinned value, extract it with `tar xzf` into `/opt/actions-runner.partial`, run `./bin/installdependencies.sh` there on Linux only (the .NET dependencies through the distribution's package manager), and move the directory to `/opt/actions-runner`. A failed exec is a start failure.
- Windows installation, one `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -Command` exec: select the archive by `PROCESSOR_ARCHITEW6432` or `PROCESSOR_ARCHITECTURE` (`AMD64` or `ARM64`), download it with `Invoke-WebRequest -UseBasicParsing` (TLS 1.2), compare `Get-FileHash -Algorithm SHA256`, extract it with `System.IO.Compression.ZipFile` into `C:\actions-runner.partial`, move it to `C:\actions-runner` and remove the inherited permissions with `icacls` so that only `SYSTEM` and the Administrators can read the directory.
- Start on Linux and macOS: `/bin/sh -c` reads `/opt/actions-runner/.tide-jitconfig`, deletes it, and runs `RUNNER_ALLOW_RUNASROOT=1 exec ./run.sh --jitconfig "$cfg" >>/opt/actions-runner/tide-runner.log 2>&1` in the runner directory. `RUNNER_ALLOW_RUNASROOT=1` is set because the guest helper may run execs as root, which `run-helper.sh` refuses otherwise (shown only by the runner source, `src/Misc/layoutroot/run-helper.sh.template`).
- Start on Windows: PowerShell reads and deletes `C:\actions-runner\.tide-jitconfig` and runs `cmd.exe /d /c "run.cmd --jitconfig <value> >> tide-runner.log 2>&1"` in the runner directory. `run.cmd --jitconfig` is shown only by the runner source (`run.cmd` passes its arguments to `run-helper.cmd`); the GitHub docs show only `run.sh`. `cmd.exe` writes the log, because PowerShell 5.1 turns redirected native standard error into errors.
- The JIT configuration is on the command line of the runner process while it runs, as `run.sh --jitconfig` requires; the sandbox serves only that runner. The file mode `0600` limits the file on Linux and macOS; Windows ignores modes, so the directory permissions limit it there.
- Verified guest OSes: none on real devices yet. The commands are covered only by unit tests and by the integration tests with the OwnSand and GitHub fakes, which run no command. The acceptance on real Linux, macOS and Windows guests records the guest OSes here.

### Webhooks

| Endpoint                                 | Sender | Verification                                                                                                                                                                                                       |
| ---------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /webhooks/github`                  | GitHub | HMAC-SHA256 of the raw body with the app webhook secret, from `X-Hub-Signature-256`, constant-time.                                                                                                                |
| `POST /webhooks/openai/{integration_id}` | OpenAI | The OpenAI webhook signature (Standard Webhooks: HMAC-SHA256 of `<webhook-id>.<webhook-timestamp>.<raw body>`) with the integration's webhook secret, any `v1` entry, a timestamp within 5 minutes, constant-time. |

- The server verifies the signature before it parses the payload. A delivery with a missing or invalid signature gets `401` and creates nothing.
- The server records the delivery ID and ignores a repeated delivery.
- The server stores the event in the same transaction that changes the request, and then answers `2xx`. It does not wait for the dispatcher.
- Webhook bodies are limited to 1 MiB.
- Implementation (recorded decisions): the shared package `servers/tide-api/internal/webhook` owns the `webhook_deliveries` table (sender and delivery ID, kept 7 days by a daily job). A webhook layer mounts its endpoint with `app.Registry.Handle`, reads the body with `webhook.ReadBody`, verifies the signature, records the delivery ID with `webhook.Record` in the transaction of the event's effects, and counts the delivery with `metrics.WebhookDelivery`. A repeated delivery ID gets `2xx` and changes nothing; an event that tide does not act on is recorded too. A delivery that fails inside tide gets `500` and records nothing, so the redelivery repeats it. `POST /webhooks/github` answers `204` after the commit, `401` for a missing or invalid `X-Hub-Signature-256` (the legacy SHA-1 header is not accepted), `413` for a body over 1 MiB, `400` for a missing `X-GitHub-Delivery` or a body that does not parse, and `503` without a GitHub App configuration. The delivery log record `github_webhook_delivery` carries the delivery ID, the event and action, the result, the status, the GitHub installation and job IDs and the tide organization, request and runner IDs, never the body.
- `tide_webhook_deliveries_total` `result` values: `processed`, `ignored`, `duplicate`, `invalid_signature`, `invalid_payload`, `too_large`, `not_configured` and `failed`; `sender` is `github` or `openai`.
- `POST /webhooks/openai/{integration_id}`: [OpenAI Codex](#openai-codex) records the signature check, the answers and the log record. The session read runs before the transaction that records the `webhook-id`, so a failed read records nothing.

### Secrets

- Organization credentials are the OwnSand API key and the credentials of each agent integration. Claude Code work orders of queued requests use the same encryption, with the associated data of their request. The server encrypts each one with AES-256-GCM before it stores it. The encryption key comes from the service secret `TIDE_SECRET_KEYS`, which holds one or more keys with IDs. Each stored value records the ID of its key, so that the operator can add a new key and re-encrypt stored values.
- `TIDE_SECRET_KEYS` format (recorded decision): a comma-separated list of `<key ID>:<key>` entries. A key ID is 1 to 32 ASCII letters, digits, `-` or `_`, and a key is 32 random bytes in base64 (standard or URL alphabet, with or without padding). The first entry is the primary key, which encrypts every new value; the server decrypts with every listed key. Each value is bound to its owner with GCM associated data (for example the kind of credential and the organization ID), so a value copied to another row does not decrypt.
- Key rotation: the operator adds the new key as the first entry and keeps the old keys after it, and deploys. The daily re-encryption jobs of the lease holder, which each layer that stores encrypted values registers, re-encrypt the values of the old keys with the primary key and log how many they changed. When no value uses an old key, the operator removes it and deploys again. A missing or invalid `TIDE_SECRET_KEYS` stops the server at startup.
- The API accepts credentials only in set operations and never returns them. Read operations return only whether a credential is set and when it was set.
- The GitHub App ID, private key, client ID, client secret and webhook secret are service secrets of the deployment, according to the [environment contract](repository-environment-contract.md).
- The server decrypts a credential only for the call that uses it, and passes a runner credential only to the runner that needs it, as the [agent integrations table](#agent-integrations) shows. The OwnSand API key, the GitHub App private key, the Claude Code environment key, the Devin API token, the OpenAI webhook secret and the OpenAI API key never enter a runner, a runner's exec command or environment, or a guest file. The Claude Code environment key is only in the environment of its orchestrator process, never in a file.
- GitHub JIT runner configurations are secrets. tide creates one right before it starts the runner and never stores it.

### Capacity view

`GetCapacity` returns, for each device of the linked OwnSand organization, the data that OwnSand `ListDevices` returns about state, limits, the effective vCPU limit and allocation, together with the number of tide runners on the device by state. The console uses it to show how the device pool is used.

### Metrics

The server records its metrics with the OpenTelemetry SDK through the shared `servers/internal/telemetry` package, like `accounts-api` ([accounts-api metrics](servers-accounts-api-foundation.md#metrics)). `GET /metrics` on `METRICS_ADDR` serves them in the Prometheus format through the OpenTelemetry Prometheus exporter. Caddy does not route `METRICS_ADDR`, so the endpoint is not public. Metric labels never contain organization IDs, user IDs, repository names or other user data.

If `METRICS_ADDR` is empty, Tide starts without a metrics listener. If the configured address cannot bind, startup fails before the lease workers start. If the listener fails permanently after binding, Tide logs the cause, stops the lease workers and releases the lease, and then drains public HTTP within the shutdown timeout. The process exits with a nonzero status and logs the original listener error, even if a termination signal arrives during the same shutdown. A clean signal shutdown exits successfully.

| `tide_runners`                            | gauge     | `kind`, `guest_os`, `state`   |

- Implementation status: `tide_ownsand_calls_total`, `tide_requests`, `tide_request_queue_wait_seconds` (recorded when a request leaves `QUEUED`), `tide_requests_ended_total`, `tide_runners`, `tide_runner_start_seconds` (creation until `WARM`, `WAITING_FOR_WORK` or `BUSY`), `tide_dev_session_execs_total`, `tide_dev_session_transfer_bytes_total` `tide_webhook_deliveries_total` (GitHub and OpenAI), `tide_vendor_watch_reconnects_total` (`vendor` `CURSOR` or `DEVIN`) and `tide_claude_orchestrator_restarts_total` (an orchestrator that exited or did not start) are recorded; the lease holder records the two gauges every 15 seconds.

- A webhook delivery that the server rejects for a missing or invalid signature counts with `result` `invalid_signature`.

When the OTLP endpoint is configured, the shared telemetry package sends the metrics over OTLP to Grafana Cloud, the default observability backend ([repository defaults](repository-defaults.md#default-technology-choices)), as for `accounts-api`.

- Retention (recorded decision): the default metrics retention of the Grafana Cloud plan. tide sets no other retention.
- Dashboard (recorded decision): one tide dashboard, committed as Grafana dashboard JSON under `servers/tide-api/` (`planned`). It shows the queue, the runners, the OwnSand calls, the webhook deliveries and the dev session transfer bytes. The implementation records the file path and how the dashboard gets to Grafana Cloud.
- Alerts (recorded decision): Grafana Cloud alert rules send notifications to the Grafana Cloud contact point that operators manage. The repository does not record the notification channel.

| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Runner start failures       | The increase of `tide_requests_ended_total` with `end_reason` `RUNNER_START_FAILED` in 15 minutes is 1 or more.                    |
| OwnSand call errors         | In 10 minutes, more than 5% of `tide_ownsand_calls_total` has a `code` other than `ok`.                                            |
| Webhook signature failures  | The increase of `tide_webhook_deliveries_total` with `result` `invalid_signature` in 5 minutes is more than 10.                    |
| Vendor or orchestrator loss | The increase of `tide_vendor_watch_reconnects_total` or of `tide_claude_orchestrator_restarts_total` in 15 minutes is more than 5. |

### Audit events

The server records audit events for: organization creation and deletion, ownership transfer, invitations, member role changes and removals, OwnSand link changes, GitHub installation links and changes, agent integration creation, credential replacement and deletion, runner profile changes, request cancellation by a user, runner deletion by a user, organization setting changes, personal API key creation and revocation (including the revocation when a membership ends), dev session creation and dev session deletion by a user. A dev session event names the session owner and, for a deletion by another user, the deleting user. Each event has the actor, the action, the target entity and the time. Audit events never contain credentials, command arguments, environment values, command output or file contents.

### Organization deletion

`DeleteOrganization` revokes every personal API key of the organization, ends every queued request with `CANCELED`, deletes every runner as described in [Runner lifecycle](#runner-lifecycle), stops the Claude Code orchestrators and vendor watchers of the organization, removes the GitHub installation links, and then deletes the stored credentials. tide cannot uninstall the GitHub App; the console tells the owner to uninstall it in GitHub.

- Each layer does its part through an organization deletion hook of the core, registered in the order above: a step before the deletion transaction that may call OwnSand or GitHub (a failure stops the deletion and keeps the organization, so the step is idempotent), a step in the transaction under the organization row lock, and a step after the commit. The core then revokes the personal API keys, records the audit events and deletes the organization row with its memberships, invitations and keys.

## Storage

- PlanetScale Postgres tables: organizations (with the organization settings), memberships, invitations, OwnSand links, GitHub installations, agent integrations, runner profiles, requests (with the dev session owner and label), runners, personal API keys (hash, display prefix, owner, name, expiry, last use, revocation), webhook deliveries, the lease and audit events. The core migration `00001_core.sql` creates the organizations, memberships, invitations, personal API keys, audit events and the lease; `00002_configuration.sql` creates the OwnSand links, agent integrations with their encrypted credentials and runner profiles; `00003_work.sql` creates the requests and runners; `00004_github.sql` creates the webhook deliveries (shared by every webhook sender), the GitHub installation links, the single-use installation states (hashes only), the GitHub job of each `GITHUB_JOB` request and the GitHub runner registration ID and label of each `GITHUB_JOB` runner; `00005_agent_claims.sql` creates the vendor claims of agent session requests (see [Cursor and Devin](#cursor-and-devin)); `00006_openai_api_key.sql` allows the credential `AGENT_CREDENTIAL_API_KEY`; `00007_agent_claim_endpoint.sql` adds the non-secret endpoint (the OpenAI remote URL) and workspace directory of a claim. The requests table holds the encrypted Claude Code work order. Each later layer adds its own migration with the next free five-digit version, and its organization tables reference the organization with `ON DELETE CASCADE`, so organization deletion removes them.
- Requests store the vendor or GitHub key (GitHub job ID, Claude Code session ID, Cursor or Devin request ID, OpenAI session and environment ID) with a unique constraint per organization and source, so that a repeated event or claim cannot create a second request.
- Webhook delivery IDs are kept for 7 days.
- Retention of ended records (recorded decision): an ended request (including an ended dev session) and an ended runner are kept for 30 days after they end, and then a daily job of the lease holder deletes them. This is the same period as for ended OwnSand sandboxes.
- Retention of audit events (recorded decision): 90 days, the same as OwnSand. A daily job of the lease holder deletes older events. Organization deletion does not delete audit events early.
- Migration tool (recorded decision): [goose](https://github.com/pressly/goose) (`github.com/pressly/goose/v3`), like `accounts-api`, with SQL migrations embedded from `servers/tide-api/internal/db/migrations/`. Migrations are forward-only, as in `accounts-api`.
- Backup policy (recorded decision): the default automatic backups of PlanetScale Postgres, with no custom backup schedule. A backup is made every 12 hours and kept for 2 days, and point-in-time recovery is available in that period ([PlanetScale Postgres backups](https://planetscale.com/docs/postgres/backups)).
- tide stores no runner output, no dev session command, environment, output or file content, and no JIT configuration. It stores a Claude Code work order only encrypted and only until tide hands it to the runner, the runner of the request is `BUSY` or the request ends; see [Claude Code](#claude-code).

## Configuration

The server reads these environment variables without a service prefix. It removes only ASCII white space from the start and end of each configuration value. Empty values count as unset. A value that fails validation stops the server at startup, and the error never contains a secret value.

| Variable                      | Required | Default                         | Rule                                                                                                           |
| ----------------------------- | -------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `ADDR`                        | no       | `127.0.0.1:18400`               | `host:port` of the HTTP/1.1 and h2c listener. The deployment sets it.                                          |
| `LOG_LEVEL`                   | no       | `info`                          | `debug`, `info`, `warn` or `error`.                                                                            |
| `DATABASE_URL`                | yes      |                                 | Postgres connection URL.                                                                                       |
| `RUN_MIGRATIONS`              | no       | `true`                          | Apply the embedded migrations at startup.                                                                      |
| `LOGTO_ISSUER`                | yes      |                                 | Logto issuer, `<tenant endpoint>/oidc`.                                                                        |
| `LOGTO_JWKS_URL`              | no       | `LOGTO_ISSUER` + `/jwks`        | Key set URL.                                                                                                   |
| `LOGTO_JWKS_FILE`             | no       | empty                           | Local key set file instead of the URL, for end-to-end test issuers.                                            |
| `LOGTO_AUDIENCE`              | no       | `https://tide.api.delino.io`    | Expected `aud`.                                                                                                |
| `CORS_ORIGINS`                | no       | `https://tide.delino.io`        | Comma-separated browser origins.                                                                               |
| `TRUST_PROXY_CLIENT_ADDRESS`  | no       | `false`                         | Client address from the last `X-Forwarded-For` entry, as in OwnSand.                                           |
| `ALLOW_DIRECT_CLIENT_ADDRESS` | no       | `false`                         | Client address from the TCP peer when the proxy setting is off. The development launcher sets `true`.          |
| `TIDE_SECRET_KEYS`            | yes      |                                 | Service secret; see [Secrets](#secrets).                                                                       |
| `METRICS_ADDR`                | no       | empty (listener off)            | `host:port` of the internal metrics listener. The development launcher sets `127.0.0.1:19400`.                 |
| `OTEL_*`                      | no       | empty (no OTLP export)          | Standard OpenTelemetry variables, read by the SDK through the shared telemetry package, as for `accounts-api`. |
| `OWNSAND_API_ORIGIN`          | no       | `https://ownsand.api.delino.io` | Origin of the OwnSand API, for example `http://127.0.0.1:18300` for a local `ownsand-api`.                     |
| `PUBLIC_ORIGIN`               | no       | `https://tide.api.delino.io`    | Public origin of `tide-api` in the webhook URLs that admins register.                                          |
| `GITHUB_APP_ID`               | no       | empty (GitHub layer off)        | Numeric ID of the tide GitHub App. Service secret group: set all six `GITHUB_APP_*` variables or none.         |
| `GITHUB_APP_CLIENT_ID`        | no       | empty                           | Client ID of the app: the issuer of the app JWT and the OAuth client of the code exchange.                     |
| `GITHUB_APP_CLIENT_SECRET`    | no       | empty                           | Service secret: the client secret of the app, for the OAuth code exchange.                                     |
| `GITHUB_APP_PRIVATE_KEY`      | no       | empty                           | Service secret: the app private key in PEM (PKCS #1 or PKCS #8). Literal `\n` sequences count as line breaks.  |
| `GITHUB_APP_WEBHOOK_SECRET`   | no       | empty                           | Service secret: the app webhook secret, at least 16 characters.                                                |
| `GITHUB_APP_SLUG`             | no       | empty                           | URL name of the app; the installation URL is `<GITHUB_WEB_ORIGIN>/apps/<slug>/installations/new`.              |
| `GITHUB_API_ORIGIN`           | no       | `https://api.github.com`        | Origin of the GitHub REST API. Only tests change it (a fake GitHub API).                                       |
| `GITHUB_WEB_ORIGIN`           | no       | `https://github.com`            | Origin of the installation page and of `POST /login/oauth/access_token`. Only tests change it.                 |

- When none of the six `GITHUB_APP_*` variables is set, the GitHub layer is off, so development setups without a GitHub App still start: the `GitHubService` RPCs fail with `failed_precondition` after authorization, `POST /webhooks/github` answers `503`, and no GitHub job is matched. Some but not all of the six variables stop the server at startup.
- Later layers add the vendor settings to this table with their implementation. The Cursor, Devin, Claude Code and OpenAI Codex adapters add no variable. The Claude Code orchestrators put their run directories in `TMPDIR` (default `/tmp`); a Unix socket path must stay below 104 bytes, so `TMPDIR` must be short.
- Member display names: `ListMembers` reads them through an optional display name source. The `delino-accounts` API has no display name RPC yet, as the [OwnSand contract](servers-ownsand-api-foundation.md#dependencies-and-integrations) records, so tide-api has no client or configuration for it and returns empty display names until that RPC exists.

## Security

- tide runs no customer code. Runner code runs only in OwnSand sandboxes on the organization's own devices.
- A runner can read the credential that tide gives to it. For Cursor, OpenAI Codex and Devin, that credential can connect workers or executors of that vendor account or pool. Admins should use credentials that are limited to the pool or environment that tide serves.
- The GitHub App never gets repository contents permissions. Jobs get their repository access from the `GITHUB_TOKEN` of the workflow, as with any self-hosted runner.
- Public repositories can use tide runners only when the admin allows them in the GitHub runner group settings.
- The `spawn-runner` hook socket accepts connections only from processes in the container: it is a Unix domain socket (mode `0600`) in a run directory with mode `0700`, and on Linux `tide-api` also checks that the peer runs with its own user ID. It is not reachable from the network.
- Dev sessions run code of their owner on the organization's devices, like the other runners. Only the session owner can run commands or read files in it, so code and secrets that a user copies into a dev session are not visible to other members through tide. Members who can reach the device or the OwnSand organization directly are outside this rule.
- A leaked personal API key gives access only to the dev sessions of its user and to dev session creation. The user or an admin who removes the membership revokes it.
- Rate limits (recorded decision, the same values as [OwnSand](servers-ownsand-api-foundation.md#security)): in-memory token buckets, which are service-wide because the service runs as one replica. A rejected call fails with `resource_exhausted`.
  - `AcceptInvitation`: 10 calls per invitation display prefix per minute and 10 calls per user per minute, each with a burst of 10.
  - The OwnSand link validation of `SetOwnSandLink`: 10 calls per user per minute with a burst of 10.
  - Personal API key authentication failures: 10 failures per key display prefix per minute with a burst of 10. Only failures take tokens, and a prefix without tokens is rejected before validation.
  - When the request has a client address: 120 calls per client address per minute with a burst of 60, in one bucket per address that these limits share. The client address comes from the same rule and the same configuration settings as in OwnSand (`TRUST_PROXY_CLIENT_ADDRESS` and `ALLOW_DIRECT_CLIENT_ADDRESS`); without a client address, this bucket does not apply.

## Logging

- Structured `log/slog` records with `organization_id`, `request_id`, `runner_id`, `runner_profile_id`, the OwnSand `sandbox_id`, the GitHub job ID and delivery ID, the vendor request ID, the dev session `exec_id`, `read_id` or `write_id`, and the personal API key ID where they apply.
- Log every dev session exec end with its result, exit code or failure reason and duration, and every relayed file operation with its size and duration.
- Log every request and runner state change with the previous state, the new state and the end reason.
- Log every OwnSand call result with the RPC and the Connect code, every GitHub API error with its status, every vendor watch reconnect and every orchestrator restart.
- Never log credentials, tokens, API key secrets, JIT configurations, work orders, webhook bodies, exec commands that carry credentials, runner output, or dev session command arguments, environment values, output and file contents.
- CLI-style output of the development launcher uses ANSI color by default, with the `NO_COLOR` opt-out.

## Build and Test

- The development launcher treats empty values and values made only of ASCII white space (space, tab, line feed, vertical tab, form feed and carriage return) as unset for `DATABASE_URL`, `CORS_ORIGINS`, `ALLOW_DIRECT_CLIENT_ADDRESS` and `METRICS_ADDR`. This matches the server's configuration rule. The launcher passes values made only of U+00A0 or U+3000 to the server unchanged.
- Package scripts wrap the Go toolchain like `accounts-api`. Before finishing a change, run `pnpm exec turbo run test --filter=tide-api`, `go vet ./...` and the `gofmt` check from `servers/AGENTS.md`.
- Postgres-backed tests (the `db`, `lease`, `jobs` and `api` integration tests) use `TIDE_TEST_DATABASE_URL`, a Postgres URL whose user may create databases. Each test creates and drops its own database; without the variable, these tests skip. The CI `go-test` job sets it. A local run: `TIDE_TEST_DATABASE_URL=postgres://postgres:<password>@127.0.0.1:<port>/postgres?sslmode=disable pnpm exec turbo run test --filter=tide-api`, for example against a `postgres:17` container.
- The database fixture fails the owning test if cleanup cannot open the admin connection or drop the generated database. The diagnostic includes the failed operation and database name and omits connection details and raw driver errors.
- Unit tests: queue order, coverage counting for GitHub profiles, warm runner rules, maximum queue wait, retry after runner start failure, runner profile validation (including `workspace_path`), webhook signature checks and duplicate deliveries, credential encryption with key rotation, the authorization matrix (including personal API keys on every service and dev session owner checks), personal API key format, hashing, expiry and revocation, the per-user dev session limit, and dev session end reasons.
- Integration tests with fakes of `ownsand-api`, the GitHub API and each vendor API: full request lifecycles for each workload kind and vendor, `unavailable` and `failed_precondition` from OwnSand, lost webhook deliveries with redelivery, cancelled jobs with surplus runner removal, vendor watch reconnects, a dev session that waits in the queue and starts, exec stream rotation and attach, relayed file reads and writes, dev session deletion by the owner and by an admin, TTL expiry, and the end of a membership with running dev sessions and keys.
- Implementation status of the Claude Code and OpenAI Codex tests: `servers/tide-api/internal/layers/agent_claude_test.go` runs against the `agent/claude/claudefake` orchestrator and the fake OwnSand: the full lifecycle (orchestrator arguments and environment, hook link, spawn request, encrypted work order, runner start with the work order, `BUSY`, exit, ended), deduplication on the order ID with a second order of the same session, the hook exit codes (pre-warming request, missing order ID, missing or empty work order, unreachable socket), the work order expiry, a start failure that keeps the work order, orchestrator restarts after a crash and a failed start, a restart with a new key, the stop at the last profile deletion and at organization deletion, and credential isolation (the environment key never reaches a guest file, an exec or the log; the work order reaches only the runner's credential file). `TestClaudeRealProcesses` builds the `tide-api` binary and runs it as the hook from a shell script in place of `claude`, with only the documented hook variables. `agent_codex_test.go` runs against `agent/codex/codexfake` and the fake OwnSand with the layer option that allows Linux and macOS profiles: the full lifecycle (webhook, session read, request, runner with only `CODEX_API_KEY`, `BUSY` when the connection action clears, exit, ended, a later connection request as `#2`), signatures (valid, wrong, another secret, another version, missing headers, stale and future timestamps, a rotated secret listed first), duplicate deliveries without a session read, a failed session read that the redelivery repairs, a deleted session, session failures, the `max_ttl` end and the interim profile rule. The package tests check the Standard Webhooks test vector, the install scripts with stub programs and the Node.js checksum table.
- Implementation status of the vendor tests: `servers/tide-api/internal/layers/agent_cursor_test.go` and `agent_devin_test.go` run against the httptest fakes `agent/cursor/cursorfake` and `agent/devin/devinfake` and the fake OwnSand: the full request lifecycle of each vendor (claim, request, runner, program exit, ended), claim release or `fail` at the maximum queue wait, at a cancellation and at a profile deletion, no second claim of a canceled entry, watch reconnects with a new list that finds a missed request, repeated events without a second request, organization deletion, and credential isolation (the runner gets only its runner credential, the Devin API token never reaches a guest file or exec, and no credential reaches the log).
