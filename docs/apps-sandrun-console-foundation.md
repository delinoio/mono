# apps-sandrun-console foundation contract

## Scope

This contract owns the SandRun web console, component `sandrun-console`, of [`sandrun`](project-sandrun.md) at `apps/sandrun/` (workspace package `sandrun-console`). The console is served at `https://sandrun.delino.io`. It manages SandRun organizations, members, the OwnSand link, GitHub installations, agent integrations and runner profiles, and shows the queue, the runners and the device pool.

## Runtime and Language

- Rsbuild React single-page application in TypeScript, like the [OwnSand console](apps-ownsand-console-foundation.md).
- Deployment: static output on Cloudflare Pages through the [deployment workflow](repository-workflow-contract.md#deployment-workflow). The `deploy` field of `apps/sandrun/package.json` names the Pages project `sandrun-console`, which must exist before the first deployment, and its `buildEnv` maps `PUBLIC_LOGTO_ENDPOINT` to the repository variable `LOGTO_ENDPOINT` and `PUBLIC_LOGTO_APP_ID` to `SANDRUN_CONSOLE_LOGTO_APP_ID`, so a production build always has the sign-in configuration and a missing variable fails the deployment (see [Deployment environments](repository-workflow-contract.md#deployment-environments)). The production build uses the defaults of `PUBLIC_API_ORIGIN` and `PUBLIC_LOGTO_SCOPES`.
- Server state: React Query with `@connectrpc/connect-query` and the TypeScript code from the [protos contract](protos-sandrun-api-contract.md).
- UI components: [`delino-ui`](packages-delino-ui-foundation.md).
- Development port: `127.0.0.1:13400` for `dev:app`, behind the portless name `sandrun.delino` (`https://sandrun.delino.localhost`), according to the [environment contract](repository-environment-contract.md#frontend-development-urls). The control plane allows both development origins in its local CORS configuration.

## Users and Operators

Organization owners, admins and members who sign in with Logto.

## Interfaces and Contracts

- The console calls the control plane only through its absolute origin. It reads the origin from `PUBLIC_API_ORIGIN` and uses `https://sandrun.api.delino.io` when the value is not set. It must not import source from `servers/`.
- Authentication: the console is a Logto single-page application (`@logto/react`) that requests access tokens for the API resource `https://sandrun.api.delino.io`. The Logto SDK keeps its session in the browser. The console reports loading to its pages only until the SDK has restored the session for the first time, so a token request never unmounts the page that made it.
- If Logto cannot start a redirect, the signed-out screen and session-ended notice show "Sign-in did not start. Check your connection and try again." as an alert. The sign-in action stays available after failure. Starting a retry clears the alert, which only reports a new error from the current attempt. The session-ended message and the signed-out invitation and GitHub setup instructions stay visible on their respective screens.
- The Logto hook checks the stored sign-in session outside its callback error handler. Invalid JSON or a value other than an object with string `redirectUri`, `codeVerifier` and `state` fields can cause an unhandled rejection. The console checks the configured application's session first and skips the hook for an unreadable session. It reads the legacy key only when the current key is absent. The next sign-in can overwrite the unreadable data. Remove the unreadable session guard when `@logto/react` handles that error itself. Replace the reader when the SDK exposes enough callback state to distinguish idle, pending and unreadable sessions.
- When a request fails with `Unauthenticated`, the error notice shows "Your session ended. Sign in again." and offers "Sign in with Delino" as its only recovery action. The button starts the Logto sign-in redirect. Other errors keep their retry action where the page offers one.
- Logto application registration (recorded with placeholders until the tenant registration exists):

  | Item                       | Value                                                                                                             |
  | -------------------------- | ----------------------------------------------------------------------------------------------------------------- |
  | Application type           | Single-page application                                                                                           |
  | Application ID             | `<sandrun-console-logto-app-id>` (`PUBLIC_LOGTO_APP_ID`)                                                          |
  | Tenant endpoint            | `<logto-tenant-endpoint>` (`PUBLIC_LOGTO_ENDPOINT`)                                                               |
  | Sign-in redirect URI       | `<console origin>/callback`, for example `https://sandrun.delino.io/callback`                                     |
  | Post sign-out redirect URI | `<console origin>`                                                                                                |
  | API resource               | `https://sandrun.api.delino.io`                                                                                   |
  | Scopes                     | `sandrun:use`, which the control plane requires; the console always requests it. `PUBLIC_LOGTO_SCOPES` adds more. |

  A build with an incomplete Logto registration and otherwise valid configuration shows that sign-in is not configured. A production build from the deployment workflow always has both values, because `deploy.buildEnv` maps them to repository variables. Register the single-page application in the shared Logto tenant and store its ID in the repository variable `SANDRUN_CONSOLE_LOGTO_APP_ID` before the first deployment.

- Build-time variables (all public, inlined into the bundle, listed in `apps/sandrun/.env.example`): `PUBLIC_API_ORIGIN` (default `https://sandrun.api.delino.io`), `PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, `PUBLIC_LOGTO_SCOPES` and `PUBLIC_SANDRUN_MOCK_API` (`true` or `false`). `rsbuild.config.ts` validates them and fails the build or development server on an invalid value. The Turbo `dev` task passes them through `passThroughEnv`, and the `build` task declares them as `env`.
- Write `PUBLIC_API_ORIGIN` and `PUBLIC_LOGTO_ENDPOINT` as HTTP or HTTPS origins in the form `scheme://host[:port][/]`. The console trims surrounding whitespace and rejects credentials, paths, queries, fragments and backslashes. It also rejects `@`, ASCII tabs and line breaks in the authority, and missing or extra slashes after the scheme, even when URL parsing would normalize the value to a bare origin. Configuration errors identify the setting and omit its value. Outside development mock mode, Rsbuild validates a nonblank `PUBLIC_LOGTO_ENDPOINT` even when `PUBLIC_LOGTO_APP_ID` is blank or missing.
- Mock API (recorded decision): `PUBLIC_SANDRUN_MOCK_API=true` runs the console against an in-browser fake control plane (`src/mock/mock-api.ts`, a Connect router transport with seeded organizations for each role, an `INVALID` OwnSand link, an organization without setup, requests, runners, devices, dev sessions, integrations and an invitation) that applies the role matrix, and a fake signed-in user whose session lives in `sessionStorage` like a provider session. Acme Robotics has a roster that spans two pages. The first continuation request fails once so the browser suite can exercise recovery. The mock serves the development server, the unit tests and the end-to-end suite. Rsbuild uses the resolved mode for both build-time validation and the browser bundle. If that mode is `production`, Rsbuild rejects the enabled flag before compilation regardless of the inherited `NODE_ENV`. The minifier removes the separate mock module from builds with the flag disabled.
- The mock follows the [API enum filter rules](protos-sandrun-api-contract.md#general-rules). After the organization lookup, it rejects undefined enum numbers in list filters with `invalid_argument` and names the field.
- The mock accepts issued GitHub installation state once for the issuing organization, before the returned ten-minute deadline. The fixed `mock-state` callback fixture remains available for development and tests.
- After consuming valid issued state, the mock returns `already_exists` if any organization in the transport already links the GitHub installation ID. The conflict leaves installations and audit history unchanged. Unlinking the installation frees the ID for another link.
- On each capacity request for an active OwnSand link, the mock counts the organization's open runners by device and state, using the [control plane's capacity rules](servers-sandrun-api-foundation.md#capacity-view). Devices without open runners have empty counts. Device metadata and allocation come from the seeded devices.
- The mock request, runner and dev session lists use a nonempty `states` filter as the selection of states. When `states` is empty, the lists include terminal rows only if `include_ended` is true. The mock applies all filters before pagination.
- When an installation is unlinked, the mock ends its unbound `GITHUB_JOB` runners in `CREATING`, `PREPARING`, `WARM` or `WAITING_FOR_WORK`. It records `DELETED`, `CLEAN_UP` and the end timestamp in runner history and publishes the runner update to live queue subscribers.
- When a membership ends, the mock cancels that member's queued dev sessions in the organization. Each session and its paired request receive `CANCELED`, `MEMBER_REMOVED` and the same end time. The mock publishes one queue update for each canceled request.
- The mock applies runner profile resource masks in request order. The `resources` path replaces all resource values, and each [nested resource path](protos-sandrun-api-contract.md#runner-profile-messages) changes only its named value. A missing or zero masked resource value or an unknown path returns `invalid_argument` before the mock saves the profile or records an audit event.
- For a runner that is deleting or has ended, `DeleteRunner` returns the stored runner without a queue update or audit event. For an active runner, the mock sets `DELETED` and `DELETED_BY_USER` immediately, records the end time, and emits one queue update and one deletion audit event.
- On each API key list request, the mock reports revoked keys as `REVOKED`, unrevoked keys at or past their expiry as `EXPIRED`, and all other keys as `ACTIVE`.
- The mock accepts personal API key creation with no expiry or with an expiry strictly after its clock. It compares seconds and nanoseconds and preserves the supplied expiry. An expiry at or before its clock returns `invalid_argument` without creating a key.
- The mock records the revocation time and one `API_KEY_REVOKED` audit event when a caller first revokes their key. Repeating the request returns the revoked key with its original revocation time and preserves the original audit event.
- On runner profile create and update, the mock applies the [control plane resource limits](servers-sandrun-api-foundation.md#runner-profiles). It requires valid, positive protobuf durations in whole milliseconds and preserves their seconds and nanos. The maximum TTL is at most 7 days, the idle TTL is at most the maximum TTL, and the maximum queue wait is at most 24 hours. Updates validate the profile after applying the field mask. Invalid values return `invalid_argument` before changing the profile or its audit history.
- The mock returns `invalid_argument` if a request omits the vendor credentials on integration creation or when the update mask includes `credentials`. A masked credential replacement must supply at least one non-empty credential of the matching vendor. The mock rejects these invalid requests before changing the integration list, integration fields or audit history. A valid replacement updates only the supplied non-empty fields and keeps the stored state and timestamp of each omitted credential. An update that omits `credentials` from its mask keeps the stored credential state and records no replacement event.
- After checking membership and role, the mock returns `not_found` with the message `OwnSand link not found` if a removal request finds no link. It leaves work and audit history unchanged. When the mock removes an OwnSand link, it cleans up the organization's runners, ends its active requests and records one removal event. A started dev session on a runner that begins deletion becomes `ENDED` with `SESSION_DELETED`. A started agent session on such a runner becomes `FAILED` with `RUNNER_LOST`. Remaining started requests become `FAILED`, and queued requests become `CANCELED`, both with `INTEGRATION_REMOVED`. Each updated request appears in history and in one queue stream event. Matching dev-session records use the same state, reason and end time.
- The personal API key and agent integration forms accept names of 1 to 64 Unicode code points after trimming surrounding whitespace. The organization creation form accepts 1 to 100 code points after trimming. The forms keep invalid input visible, show an error on the name field and send the trimmed name only after validation passes.
- Server state: the pages call the generated services with `@connectrpc/connect-query`. The `overview` route uses the `watchQueue` helper of the [TypeScript SDK](packages-sandrun-sdk-foundation.md) (`sandrun-sdk`) on the console transport for the reconnects and the gap handling.
- When a refresh of loaded data fails with a transient error, the console keeps the content, open dialogs and entered values. It shows “The last refresh failed” and “Try again” above the affected content until a fetch succeeds. A first-load failure or a `not_found`, `permission_denied` or `unauthenticated` error shows the full error notice for the affected view. If a request for the next page fails with a transient error, the list keeps its rows and offers a retry that requests that same page.
- The console links to the OwnSand console at `https://ownsand.delino.io`, and to the devices page of the linked OwnSand organization (`https://ownsand.delino.io/orgs/<ownsand_organization_id>/devices`).
- Account settings: the console links to `https://accounts.delino.io`. It has no profile or account pages.
- The console never calls `ownsand-api`. Device management (enrollment, device limits including the vCPU overcommit, device removal) stays in the [OwnSand console](apps-ownsand-console-foundation.md), and the SandRun console links to it.

- The `overview` route uses `WatchQueue` and reconnects automatically after a clean stream end or a retryable error. A terminal error discards any incomplete snapshot and shows a neutral `Disconnected` badge and the standard error notice. If no snapshot has completed, the console hides the loading indicators, waiting-request results and runner counts. A manual retry clears the error notice and restores `Connecting` and the loading indicators until the first snapshot completes. If a snapshot has already completed, the console keeps the last queue and runner counts on screen during a failure and shows `Reconnecting` after a gap or a manual retry. When a snapshot completes, the console shows its data and the badge shows `Live`. Waiting requests appear in queue order (priority, then queue time, then request ID).
- The home page, organization switcher and GitHub setup share one cached organization list. The console requests up to 200 organizations per page, follows each continuation token and publishes the complete list in server order. Creating an organization or accepting an invitation refreshes the list. When creation succeeds in the current dialog opening, the console closes the dialog and opens the overview for the organization ID in the response while the list refreshes.
- If the organization list fails on first load or returns a terminal refresh error, the top bar shows the full error notice in place of the organization selector and closes any open options. A transient refresh failure keeps the cached choices available with a retry notice. These notices affect only the switcher area. Switching organizations keeps the active section.
- Profiles, Requests, Runners and the Overview queue share one cached runner profile list per organization. The console requests up to 200 profiles per page and follows every continuation token before it publishes the complete list in server order. Creating, changing or deleting a profile refreshes the list. If a page fails, the console offers error recovery and leaves the work lists and queue usable. The profile filters are unavailable until the list loads successfully. Work rows show the short profile ID when the profile name is unavailable.
- When request pages overlap, the Requests table keeps the first row data and position for each request ID. **Show more** follows the server's continuation token even if the last page added no new rows. After a transient error, retry uses the failed page's token.
- Members, the ownership transfer picker, Audit and Dev Sessions share a cached roster for the active organization. The console follows every `ListMembers` continuation token. Members and the ownership transfer picker show each loaded user once in server order. If a continuation fails with a transient error, both views keep the loaded roster visible, mark the results as partial and let the user retry that page. A terminal error replaces the Members roster with the full error notice and makes the ownership choices unavailable. The notice offers a retry of the list for `not_found` and `permission_denied` and prompts the user to sign in for `unauthenticated`. Member and ownership changes refresh the roster.
- Audit and Dev Sessions load their tables independently of the roster. Audit updates actor and subject names as roster pages arrive. Dev Sessions updates owner names in the same way. Both tables show the user ID when a name is unavailable and keep names from loaded pages if a continuation fails.
- The `members` route follows every invitation page token for the current organization before it shows pending invitations or an empty state. If a page fails, the console shows an error and lets the user retry. After it creates or revokes an invitation, it refreshes the list from the first page.
- Changing a member role, revoking an invitation or selecting **Connect GitHub** can show the session-ended notice on the visit that started the request. The console keeps the page data visible and waits for the user to select **Sign in with Delino**. Sign-in does not repeat the failed request. Other failures use the action toast.
- Invitation links carry the secret in the URL fragment (`/invitations/accept#secret=<secret>`). The `invitation` route reads it, removes the fragment from the address bar at once and keeps the secret only in component state; it never stores it. A signed-out user sees the sign-in with a notice to open the link again after sign-in, because the console keeps no state across the Logto redirect.
- On the open invitation page, a new link clears prior errors or recovery and shows the form with the new secret. SandRun removes the fragment without reloading or changing the path or query. A fragment without a secret leaves the current view in place. The user must select **Join organization** to submit.
- A successful acceptance refreshes the organization list even if the user leaves the invitation page. The refresh cancels any pending list load and starts again from the first page when the list is in use. If the invitation visit and submission are still current, SandRun clears the submitted secret. It opens the joined organization's overview when the response includes a nonblank organization ID. If the organization or ID is missing or the ID is blank, SandRun replaces the form with the alert “You may have joined the organization.” and the **Go to your organizations** link, which opens the refreshed list. Editing the input, opening another invitation link, or leaving the page ends the current submission's ability to change the invitation view.
- The `github-setup` route reads `installation_id`, `code` and `state` and removes the query from the address bar at once. The installation ID must be a positive decimal integer through `9223372036854775807`, the signed `int64` maximum. If a callback value is missing or invalid, the route shows the invalid-address alert and skips organization selection and linking. The callback URL does not name the SandRun organization. After the complete list loads, the route calls `LinkGitHubInstallation` if the user is an `owner` or `admin` of exactly one organization, asks the user to choose if several are eligible, or displays an eligibility notice if none are eligible. If any page fails, the console offers the organization-load error recovery and keeps the callback values in memory. On success, the console refreshes GitHub integration data and replaces the callback history entry with the organization's `integrations` page if the original setup visit is still active. If the user leaves setup while linking is in progress, a successful response preserves their current page and history. After a failed link request, the console explains that the installation must start again from `integrations` because the `state` is single-use.
- Invitation links carry the secret in the URL fragment (`/invitations/accept#secret=<secret>`). The `invitation` route removes the fragment from the current history entry at once and preserves the path and query. The console keeps the secret only in component state. When signed out, the console discards the initial secret and any replacement fragments. The sign-in notice tells the user to open the link again after sign-in.
- On the signed-in invitation page, a new link clears the previous errors and replaces the input without reloading. A fragment without a secret leaves the input in place. The user must select **Join organization** to submit.
- A successful acceptance refreshes the organization list even if the user leaves the invitation page. The refresh cancels any pending list load and starts again from the first page when the list is in use. SandRun opens the joined organization's overview only if the user is still on the invitation page and has neither edited the submitted input nor opened another invitation link.
- The `github-setup` route reads `installation_id`, `code` and `state` and removes the query from the address bar at once. The installation ID must be a positive decimal integer through `9223372036854775807`, the signed `int64` maximum. If a callback value is missing or invalid, the route shows the invalid-address alert and skips organization selection and linking. The callback URL does not name the SandRun organization. After the complete list loads, the route calls `LinkGitHubInstallation` if the user is an `owner` or `admin` of exactly one organization, asks the user to choose if several are eligible, or displays an eligibility notice if none are eligible. Before linking, a transient organization refresh failure keeps the picker or eligibility notice visible with a retry action. A first-load or terminal refresh error shows the full error notice. The console keeps the callback values in memory. A successful refresh clears the manual choice if the organization is no longer eligible. After submission, the setup route stops requesting the organization list and continues to show the link operation status. On success, the console refreshes GitHub integration data and replaces the callback history entry with the organization's `integrations` page if the original setup visit is still active. If the user leaves setup while linking is in progress, a successful response preserves their current page and history. After a failed link request, the console explains that the installation must start again from `integrations` because the `state` is single-use.
- On the `integrations` route, "Show more" loads the next page of GitHub installations for the selected organization. A transient error on a later page keeps the loaded installations visible and lets the user retry that page. Owners and admins can manage installations on every loaded page.
- When the selected organization's refreshed role loses integration management permission, the console closes its OwnSand, GitHub and agent management dialogs and clears their drafts. The page remains available for reads. If permission returns, the user must open a new dialog. A refresh that preserves permission keeps an otherwise valid dialog and its draft.
- **Connect GitHub** opens the installation URL once if the user stays on the Integrations visit that started the request. A failure on that visit shows the action toast or the session-ended notice and enables **Connect GitHub** again. Leaving the page or switching organizations ends that visit, even if the user returns to the same page before the response arrives. The console ignores successes and failures from an ended visit.
- Empty states guide the first setup in this order: link OwnSand, connect GitHub or create an agent integration, create a runner profile. The Overview checklist and setup-aware empty states show the next step as soon as its prerequisites are known. An `ACTIVE` GitHub installation on any page or an existing agent integration advances setup to runner profiles. If the GitHub lookup cannot finish and no agent integration is known, the work-source step stays unknown. While the next step is unknown or after setup is complete, the console hides the checklist and uses the usual empty-state text.
- The OwnSand setup step requires an `ACTIVE` link. For an `INVALID` link, the Overview checklist keeps the OwnSand step incomplete. The checklist and setup-aware empty states direct the user to the selected organization's Integrations page to replace the OwnSand API key. If a successful lookup returns no link, both surfaces offer initial linking. A lookup with no data uses the usual fallback.
- When profile creation is the next setup step, the empty Runner profiles page asks organization members to contact an admin. Owners and admins can open the creation dialog from this page. Earlier setup steps still link to Integrations.
- The Overview requests device capacity only when the OwnSand link is `ACTIVE`. When the link is missing or inactive, the Device pool shows the next step and links to `integrations` without an error alert or retry button. An active link with no devices shows “No devices.” Link lookup and capacity request failures use the standard error and retry behavior.
- Requests and Overview refresh the displayed queue wait every 15 seconds using the local clock. Each refresh uses the request data already loaded. Queue wait measures from the queue timestamp to the start timestamp, to the end timestamp if the request ended before it started, or to the current time while it waits. Requests displays “—” when the queue timestamp is missing.
- When the OwnSand link is `INVALID`, every organization route shows a banner that explains that dispatch has stopped and links to `integrations`.
- The OwnSand API key replacement form targets the OwnSand organization linked when the form opens. If a successful refresh shows that the link is gone or points to another organization, the form clears the key and disables submission. Close the form and start again from Integrations.
- Credential forms accept a value once and never show it again. After a save, the form shows only that the credential is set and when.
- For an `OPENAI_CODEX` integration, the console shows the webhook URL to register in OpenAI.
- The `integrations` and `profiles` routes share one cached agent integration list for the active organization. The console follows every continuation token and shows integrations as their pages load.
- When editing an agent-session runner profile, Save stays unavailable until the console loads the vendor of the saved integration. The dialog keeps edits while the list loads or a failed page is retried. If the complete list loads successfully without the saved integration, the dialog explains why Save is unavailable.
- When you create or edit a dev-session runner profile, enter a Workspace path that follows the selected guest OS syntax and the [control plane workspace path rules](servers-sandrun-api-foundation.md#runner-profiles). An invalid path shows a field error and keeps the dialog open without sending a save request. You can replace an invalid path saved in an older profile in one edit. The console sends valid paths exactly as entered and omits the path for other workload kinds.
- The `profiles` route offers the default priority of the workload kind only when it creates a profile, because an update requires `HIGH`, `NORMAL` or `LOW`. The `dev-sessions` route shows no command, output or file content, and it does not run commands; commands and file transfers are available only through the CLI, the MCP server and the SDKs.

It offers the default priority of the workload kind only when it creates a profile, because an update requires `HIGH`, `NORMAL` or `LOW`. The `dev-sessions` route shows no command, output or file content, and it does not run commands; commands and file transfers are available only through the CLI, the MCP server and the SDKs.
- When creating or editing an OpenAI Codex runner profile, the console offers only verified guest OSes and clears a guest OS that the selected integration cannot use. While the verified list is empty, the console explains why and disables the guest OS field and Save action. Update the console's verified list in the same change as `profile.VerifiedCodexGuestOSes` in the [control plane](servers-sandrun-api-foundation.md#openai-codex). The control plane validates every save.
- When you create or edit a runner profile, enter whole numbers from 1 to 1024 for vCPUs, 1 to 16777216 MiB for memory, and 1 to 1048576 GiB for disk. The idle TTL, maximum TTL and maximum queue wait accept decimal minutes or hours that represent whole milliseconds. The idle TTL must be at most the maximum TTL when both values are valid. Invalid values show a field error and keep the dialog open without sending a request.
- The runner profile list shows positive maximum queue waits below one second as whole milliseconds.
- When the console updates a runner profile, it adds a separate [field mask path](protos-sandrun-api-contract.md#runner-profile-messages) for each resource value changed since the edit dialog opened. This preserves newer saves to untouched resource values. Saving an unchanged profile sends no update request. Creating a profile sends all resource values.
- The `api-keys` route shows a new secret once with a copy action and a notice that SandRun cannot show it again, and explains that the key works only for dev sessions. It lists the keys page by page with "Show more", so the console can show and revoke every key. If a key is created while the first list request is pending and no page has been cached, the console cancels that request and fetches the first page again.
- On the `settings` route, the per-user dev session limit shows the latest confirmed value until an admin edits it. The field accepts whole numbers from 1 to 2147483647 or an empty value to remove the limit. Invalid drafts remain visible after Enter or blur. A save attempt for an invalid draft shows the field error and sends no update. A refresh or failed save keeps the edit in the field. A valid edit sends an update only when it differs from the confirmed value. After a successful save, the field follows confirmed values again unless the admin made a newer edit.

- The organization layout supports viewports 320 px wide and wider. The navigation heading wraps long names, including names without spaces, to show the full name and role within the navigation. From 320 through 760 px, the section list scrolls horizontally above the page content. At 761 px and wider, the section list stacks vertically in a 220 px column.
- On Overview and Audit, Tab reaches the populated Waiting requests, Devices and Audit events tables. Each table shows a focus ring. When columns extend past the visible area, the left and right arrow keys scroll the table horizontally. Tab and Shift+Tab move focus past the table in either direction.
- UX follows the Toss Design Guidelines. Dialogs close with `Esc`. A form with a single critical input focuses it when it opens.
- Each form dialog opening starts without a pending request or a submission error. Only the opening that sent a request can show its error, finish its pending state, or act on its success by closing the form, navigating, or showing a one-time secret or link. A failure in the current opening allows a retry. Successful requests refresh the affected data even after dismissal. If the form is still open when key or invitation creation succeeds, the console closes it and shows the copyable result while the list refreshes. A list refresh failure leaves the result available until the user closes it. If the user dismisses the form before creation succeeds, the key or invitation appears in its list and the console does not show its secret or link.

## Localization

- The console follows the [localization contract](repository-localization-contract.md#react-apps) with the [`delino-i18n`](packages-delino-i18n-foundation.md) runtime. The source catalog is `apps/sandrun/i18n/messages/en.json`, the registry is `apps/sandrun/i18n/locales.json`, and `src/i18n.ts` creates the provider. `src/index.tsx` loads the selected catalog before the first render and wraps the whole console, so the sign-in, callback and setup pages are translated too.
- The language menu is in the top bar: at the start of the account links on signed-in pages, and alone in the top bar of the signed-out sign-in page and of a failed sign-in callback.
- Product, vendor and guest OS names, identifiers, commands, `runs-on` labels and server error text stay unchanged. Dates, durations and lists use `Intl` with the selected language.

## Storage

The console stores nothing except the Logto SDK session state in the browser (in a mock build, the fake session of the mock API) and the selected language under the `localStorage` key `delino.language`. It never stores credentials in browser storage. After removing the GitHub `state` and `code` from the address bar, the console keeps them only in memory for the current callback visit.

## Security

- Credential inputs use password-type fields and are cleared after submission.
- Destructive actions (OwnSand link removal, GitHub installation unlink, integration deletion, profile deletion, runner deletion, dev session deletion, API key revocation, organization deletion, ownership transfer) need an explicit confirmation step.
- The OwnSand removal confirmation applies to the displayed link. A successful refresh closes the confirmation if the link is missing or if its OwnSand organization ID or creation time changes. To remove a link after the confirmation closes, the admin opens a new confirmation.
- The result of a request belongs to the opening that sent it. A confirmation button is disabled while its request runs.
- A member removal confirmation closes if the caller loses permission, the target becomes ineligible, or a complete roster refresh omits the target. The user must open a new confirmation if eligibility returns. While a partial roster cannot resolve the target, the confirmation stays open with its submit button disabled.
- An ownership-transfer confirmation stays open while the roster is usable and the selected member remains eligible. If either condition fails, the confirmation closes. When the roster recovers, the owner must select **Transfer** again before they can confirm.
- Admins and members can read the roster while the caller ID is unavailable. The console offers **Leave organization** only to admins and members with a nonempty caller ID. If the ID is unavailable when they confirm, the console closes the dialog without sending a request, changing the route, or refreshing data. When the ID returns, they can open a new confirmation. A failed request keeps the current confirmation available for retry.
- After a successful leave or deletion, the console opens the organization list before it refreshes affected queries if the confirmation is still open. If the user dismisses the confirmation or moves to another page, the console refreshes the data and preserves their current URL and history. Removing another member refreshes the roster on Members.
- The console shows no runner output and no dev session output. It never stores an API key secret.

## Logging

The console sends no logs to a service in this version. Browser console messages never contain tokens or credentials.
