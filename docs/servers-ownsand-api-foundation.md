# servers-ownsand-api foundation contract

## Scope

This contract owns the `ownsand-api` control plane of [`ownsand`](project-ownsand.md) at `servers/ownsand-api/`. The control plane is the system of record for organizations, memberships, devices, credentials, sandbox records, snapshot records, templates, agent version policies and audit events, the billing usage counters and the usage outbox, and the billing status cache of each organization. It schedules sandboxes, sends commands to device agents, signals peer-to-peer data channels, authorizes and forwards the relay fallback of the data path, and serves STUN.

The control plane does not run sandboxes and stores no sandbox content. Sandbox content passes through it only on the [relay](#relay), in process memory. It is licensed under `FSL-1.1-ALv2` according to the [license contract](repository-license-contract.md).

Layout, following the `accounts-api` server conventions:

- `servers/ownsand-api/cmd/ownsand-api/`: process entry point.
- `servers/ownsand-api/internal/`: `config` (environment configuration), `db` (Postgres pool, embedded migrations in `db/migrations/`, test databases in `db/dbtest/`), `auth` (credential shapes, Logto access token validation, device nonces and signatures), `authz` (the authorization matrix), `ratelimit`, `events` (the control events table), `api` (Connect handlers, interceptors and audit events), `janitor` (retention jobs), `server` (HTTP handler, `/healthz` and CORS), `app` (wiring of handlers and background workers) and `testenv` (the in-process integration test environment). `hub` (agent channel registry and answer waiters), `lease` (the instance lease), `scheduler` (placement) and `objectstore` (R2 signed URLs and prefix deletion; an in-memory store for tests). The agent channel, sandbox and snapshot handlers, reconciliation and the control event processor are in `api`. `grants` (relay grants, limits, replacement and revocation matching), `relay` (agent relay connections, stream routing and credit windows) and `stun` (the STUN binding server). The data path, relay RPC and relay connection handlers are in `api` (`datapath.go` and `relay.go`).
- Billing: `billing` (the meters, windows and amounts, the RPC classification, the in-memory usage recorder, the shared usage counters, the window seal, the R2 storage sample, the usage outbox with its reporter and the metering metrics) and `accounts` (the `delino-accounts` usage client with the Logto machine-to-machine token source). The metering interceptor and the relay egress counters are in `api` (`metering.go`), and the internal metrics listener is in `cmd/ownsand-api`. The billing status cache with its poll, time-based suspensions, pending unlinks and status metrics is in `billing` (`status.go` and `statuses.go`); the enforcement checks, the `BillingService` handlers and the link removal of `TransferOwnership` and `DeleteOrganization` are in `api` (`billing.go`), and the suspension worker is in `api` (`billing_enforce.go`). The test fake of `delino-accounts` (a Logto token endpoint and `UsageService`) is `accounts/accountstest`.
- `servers/ownsand-api/package.json`, `turbo.json`, `.env.example`, `Dockerfile` and `scripts/dev.mjs`: workspace wiring, the container image and the development launcher. The `package.json` has no `deploy` field until the deployment workflow publishes the STUN UDP port (see [Runtime and Language](#runtime-and-language)).

## Runtime and Language

- Language: Go in the root module `github.com/delinoio/mono`. Import path: `github.com/delinoio/mono/servers/ownsand-api/...`.
- Runtime: one long-running process. It serves HTTP with Connect handlers on the `ADDR` that the deployment sets, and STUN on UDP port 3478. Logging: `log/slog`.
- Replicas: the service runs as exactly one replica. The agent channels, the agent relay connections, open sessions and pending and revocable relay grants live in process memory, so a request on another replica could not reach the agent. Record the cross-replica routing in this contract before the service runs more than one replica. The Droplet deployment stops the old container before it starts the new one (see [Deployment target](#runtime-and-language)), but two instances can still run at the same time, for example an old instance that was killed before it released the lease, or a process that an operator starts next to the deployed one, so an instance accepts agent channels and runs heartbeat timers and state transitions only while it holds a lease row in Postgres. The old instance releases the lease when it starts to drain, and the release deletes the instance's own row even when the instance never confirmed an acquisition whose database call failed or was canceled after the commit (it never deletes the row of another holder, and runs the lease-lost callback only for a confirmed ownership period); it also closes all its agent channels and agent relay connections at that moment, which ends their sessions, relay grants and relay RPCs; agents reconnect to the new instance. The new instance waits for the lease before it accepts agent channels, and then treats every `online` device as not heard from, so the 45-second offline rule applies to devices that do not reconnect. The scheduler, commands, `OpenSession`, `AuthorizeRelay`, the `RelayService` RPCs and `RelayAgentService.Connect` need a live agent channel in the serving instance: a device without one is not eligible, and a command, session, relay authorization, relay RPC or relay connection for it fails with `unavailable` before any record is created. `DeleteSandbox` is exempt: any instance records the pending delete, and the lease holder sends the delete command when the device reconnects. The lease expires 30 seconds after its last renewal, and the holder renews it every 10 seconds, so a crashed holder loses it. The holder does not wait for a renewal call to return: it stores the `expire_time` of its last successful renewal, bounds each renewal call by that time, and at that time it stops holding the lease whether or not a renewal is still pending. It then closes all its agent channels and agent relay connections, runs no heartbeat timers or state transitions, and refuses new agent channels, exactly as when it releases the lease. A renewal that fails with an error does not end ownership: the holder logs it and keeps the lease until that `expire_time`, and only a renewal that the database answers with a refusal ends ownership at once. A successful renewal before that time moves it to the `expire_time` of that renewal. The result of a renewal that started in an ownership period that has ended, for example a call that returns late, never restores the lease; the instance holds it again only after a new acquisition. The work that the instance runs when it gains the lease, for example reading the newest control event, is bound by the same `expire_time`, so that its database I/O cannot delay the loss transition and keep a channel that was admitted in the remaining ownership window open after that time.
- Deployment target: a Docker container on the shared DigitalOcean Droplet, deployed by the [deployment workflow](repository-workflow-contract.md#deployment-workflow) with the `deploy` target `droplet`, like `accounts-api`. Production origin: `https://ownsand.api.delino.io`. STUN URL: `stun:ownsand.api.delino.io:3478`. The `deploy` field of `servers/ownsand-api/package.json` sets the service `ownsand-api`, the host name `ownsand.api.delino.io`, the container port `8080` (the deployment sets `ADDR=:8080`), the upstream protocol `h2c` and the UDP port `3478`. The configuration and secrets are in the env file `/srv/delino/env/ownsand-api.env` on the Droplet, which must not set `ADDR`.
- Deployment order (recorded decision): only one container can publish UDP port 3478, so the deployment stops the old container (which releases the lease and closes its agent channels and relay connections) before it starts the new one, instead of the zero-downtime overlap of the other servers. The API does not answer from the stop until the new container passes its health check (after its migrations) and the route switches; callers and agents retry, and agents reconnect to the new instance. When the new container fails, the deployment removes it and starts the old one again ([deployment workflow](repository-workflow-contract.md#deployment-workflow)).
- TLS and proxy: the Caddy reverse proxy on the Droplet terminates TLS for `ownsand.api.delino.io` with a Let's Encrypt certificate and proxies to the container. The Caddy route of `ownsand-api` must proxy HTTP/2 without TLS (h2c) to the container, because `RelayAgentService.Connect` and `AgentService.Channel` are bidirectional streams and need HTTP/2 from end to end. The route must also not end a request or a stream before the limits of this contract end it (the 14-minute relay stream limit, the 5-minute `WriteFile` call deadline and the long-lived agent channel and relay connection). Recorded: the upstream protocol `h2c` makes the deploy script write the route with `transport http { versions h2c }`, and the [Caddy route checks](repository-workflow-contract.md#droplet) of the deployment workflow verified both properties: the upstream receives HTTP/2, a bidirectional stream works in full duplex, and one stream stayed open for 16 minutes, including 6 minutes in which the server wrote nothing, and three Caddy reloads. The route sets no stream timeout, so the limits of this contract end the streams. Caddy keeps its default 1-minute idle timeouts: it ends a stream whose request body sends nothing for 1 minute, and a stream whose client does not accept a write for 1 minute. The agent heartbeats every 15 seconds on the agent channel and the keepalive frame after 30 seconds on the relay connection keep the request bodies of both device streams active, and the server-streaming RPCs end their request body after the request message. A caller that stops reading a relay stream for 1 minute loses it and resumes it like any other interrupted stream.
- The DNS record of `ownsand.api.delino.io` points directly at the Droplet and must not go through an HTTP proxy (for example, a proxied Cloudflare record), because the STUN service needs the Droplet address and the relay connection needs HTTP/2 from end to end.
- Public RPCs are unary or server-streaming according to the [project transport rule](project-ownsand.md#protocol-and-api). Only the device-facing `RelayAgentService.Connect` and the [agent channel](#agent-channel) (a recorded Connect bidirectional stream; only its WebSocket fallback stays open) are long-lived bidirectional streams.
- Public UDP: STUN needs inbound UDP port 3478 on the Droplet. Recorded: the `deploy.udpPorts` field makes the [deployment workflow](repository-workflow-contract.md#droplet) publish UDP port 3478 of the container on the same host port (Docker forwards the datagrams with their source address, so `XOR-MAPPED-ADDRESS` is the caller's public address), and the DigitalOcean Cloud Firewall of the Droplet allows inbound UDP 3478.
- Database: PlanetScale Postgres, according to the repository defaults.
- Development ports: `127.0.0.1:18300` for HTTP (HTTP/1.1 and h2c, so that the bidirectional relay connection works without a proxy) and `127.0.0.1:13478` for STUN over UDP, recorded in the [environment contract](repository-environment-contract.md). The process serves HTTP/1.1 and HTTP/2 without TLS (Go `http.Server.Protocols` with unencrypted HTTP/2) on the same port, sets only a 10-second request header timeout, a 120-second idle timeout and a 30-second HTTP/2 write byte timeout (it closes an HTTP/2 connection that accepts no byte for 30 seconds while data waits to be written, so that a peer that stopped draining its socket cannot hold a response write forever), and sets no read or write timeout, because the agent channel and the relay connection are long-lived streams and relay server streams run up to 14 minutes; each RPC bounds its own lifetime. Every handler reads at most 2 MiB (`api.MaxRequestBytes`, set with Connect's read limit on the shared handler options) of each request message, counted after decompression and for each message of a stream, for the binary and the JSON codec. The largest legitimate request is a `WriteFile` with 1 MiB of file data, which is about 1.4 MB as JSON (base64) and 1 MiB plus identifiers as binary; the largest relay frame, `datapath.MaxFrameSize` (1 MiB plus 64 KiB), is smaller than the limit, and the other maxima (256 KiB of exec fields, 32 labels, a 64 KiB SDP offer, a state report of 5,000 sandboxes) are far below it. The limit applies before the interceptor chain, so an oversized or inflated request ends with `resource_exhausted` before authentication and takes no rate limit token, and an oversized message on the agent channel ends the stream with `resource_exhausted`. A unary RPC must also deliver its whole request body within 30 seconds of the start of the request (`api.Timing.UnaryBodyReadDeadline`): the `api.UnaryReadDeadline` handler arms a per-request read deadline through `http.ResponseController` before Connect reads the body and lifts it when the body ends, so a client that stalls or sends one byte per second ends with `deadline_exceeded` on HTTP/1.1 and HTTP/2, while a slow upload that completes in time and a handler that runs longer than the deadline are not affected. It does not apply to the agent channel, to `RelayAgentService.Connect` or to the `RelayService` RPCs, whose request gate keeps its own request deadline, and the server still sets no server-wide read timeout.
- Deployment status: the package declares no `deploy` field and has no changeset, because a server that needs a public port other than its reverse proxy route declares no `deploy` field until the [deployment workflow](repository-workflow-contract.md#deployment-workflow) supports that port (`servers/AGENTS.md`). The `Dockerfile` already follows the Droplet image layout of `accounts-api`.

### Authentication

The server accepts three kinds of credentials in the `Authorization: Bearer` header. It selects the validator from the credential shape and never tries a second validator after the first one rejects the credential.

| Principal kind | Credential                                                        | Validation                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `user`         | Logto access token (JWT)                                          | Signature, issuer, expiry, audience `https://ownsand.api.delino.io` and required scopes, according to the [authentication contract](repository-auth-contract.md#token-validation). ID tokens are rejected. Only end-user tokens become a `user` principal: no machine-to-machine application gets an OwnSand scope, and the change that adds token validation records the claim check that rejects machine-to-machine tokens. |
| `api_key`      | `osk_` followed by the secret                                     | SHA-256 hash lookup with a constant-time comparison. The key must not be revoked, and its organization must not be deleted.                                                                                                                                                                                                                                                                                                   |
| `device`       | `osd_` device session credential from `AgentService.Authenticate` | SHA-256 hash lookup with a constant-time comparison. Accepted only to open the agent channel and the agent relay connection (`RelayAgentService.Connect`) of its own device. The credential must not be expired, and the device must not be removed.                                                                                                                                                                          |

- The Logto API resource indicator is `https://ownsand.api.delino.io`. Recorded scope: every user RPC requires the scope `ownsand:use` in the access token. Roles inside an organization come from OwnSand's membership table, not from token scopes, so OwnSand defines no other scope.
- Logto application registrations: the [web console](apps-ownsand-console-foundation.md) is a single-page application and the [CLI](cmds-ownsand-cli-foundation.md) is a native application with the device authorization flow. Both request access tokens for the resource `https://ownsand.api.delino.io` with the scope `ownsand:use`. The control plane needs no Logto application for token validation. Its machine-to-machine application for the `delino-accounts` API, which usage reporting uses, gets the scope `accounts:report-usage` of the API resource `https://accounts.api.delino.io` ([API server contract](servers-accounts-api-foundation.md#authentication)), and the display name integration reuses it (see [Dependencies and Integrations](#dependencies-and-integrations)).
- Token validation (implemented with `github.com/go-jose/go-jose/v4`): the token must be a JWS signed with an ES256, ES384, ES512, RS256, RS384, RS512, PS256, PS384, PS512 or EdDSA key from the tenant key set (`<issuer>/jwks`, cached for 10 minutes after a successful fetch; the server makes at most one fetch attempt per minute, counted from the last attempt even when it failed, for a stale cache or an unknown key ID, so tokens with a cached key keep validating and other tokens fail with `unauthenticated` without a fetch during that minute), with the header `typ` `at+jwt` (RFC 9068 access tokens; Logto ID tokens have another type and audience), the configured issuer, the audience `https://ownsand.api.delino.io`, an `exp` claim (30 seconds of clock leeway for `exp` and `nbf`), a non-empty `sub` and the scope `ownsand:use`. Machine-to-machine check: Logto client credentials tokens carry the application ID as `sub`, equal to `client_id`, so the server rejects every token whose `sub` equals its `client_id`.
- Test issuer for end-to-end runs: `LOGTO_ISSUER` may name any issuer URL, and `LOGTO_JWKS_FILE` names a local JSON Web Key Set file that the server reads instead of fetching `<issuer>/jwks`. An end-to-end suite generates a key pair, writes its public key set to that file and signs access tokens with the header `typ` `at+jwt` and `kid` of that key, and the claims `iss` (the configured issuer), `aud` `https://ownsand.api.delino.io`, `sub`, `exp` and `scope` containing `ownsand:use`. Production never sets `LOGTO_JWKS_FILE`.
- API key and device session lookups hash the presented value with SHA-256, load the row by that hash and compare the stored hash in constant time. A value with a known prefix but a wrong shape is rejected by the validator of its prefix. An `ose_` or `osi_` value as a bearer credential is rejected. A valid `osd_` credential on any RPC other than `Channel` and `RelayAgentService.Connect`, and an API key or Logto token on those two, fails with `permission_denied`.
- The API key exception is recorded in the [project index](project-ownsand.md#identity-and-access). API keys are not accepted on `OrganizationService`, `MemberService`, `ApiKeyService`, the `BillingService` RPCs other than `GetBillingStatus` or these `DeviceService` RPCs: `CreateEnrollmentToken`, `ListEnrollmentTokens`, `RevokeEnrollmentToken`, `ReplaceDeviceLimits`, `UpdateDeviceLimits`, `RemoveDevice` and `UpdateAgentVersionPolicy`. For an RPC that takes an `organization_id`, the server first normalizes the ID to lowercase UUID text (any accepted hex case names the same organization; an invalid ID fails with `invalid_argument`), checks that the key belongs to that organization and returns `not_found` otherwise; only a key of that organization gets `permission_denied` from this restriction.
- UUID canonicalization: every handler normalizes the UUID v7 fields of its request to lowercase text at its entry (an invalid value fails with `invalid_argument`, and the order of the authorization and validation errors is unchanged) and uses only that text afterwards, so the two spellings of one UUID name one record and one request. This covers the organization, sandbox, device, snapshot, template, invitation, API key and enrollment token IDs, `placement.device_id`, the `source` snapshot and template IDs, the `idempotency_key` of `CreateSandbox` (which hashes and locks the lowercase request, so a retry in another hex case replays the sandbox instead of failing), and the `authorization_id`, the `read_id`, `write_id` and non-exec `operation_id` and the `replaces_grant_id` of the relay RPCs. The R2 clean-up prefixes of `DeleteOrganization`, `DeleteSnapshot` and `ExportSnapshot` failures use the lowercase text that the signed object keys use; the scheduler, the sandbox watchers, the grant registry, the agent commands, the relay grants and forwarded relay requests, the audit targets and every response carry lowercase text. The relay compares the organization, sandbox and operation IDs of a request with its grant by value. The lowercase-only `exec_id` rule (see [relay authorization](#data-path-signaling-and-relay)) is not relaxed: an `exec_id`, and the `operation_id` of an `EXEC` or `ATTACH_EXEC` grant, with an uppercase hex digit fails with `invalid_argument` and reserves no grant. The control plane forwards the lowercase spelling of `sandbox_id`, `read_id` and `write_id` to the agent, and the agent compares IDs and the request digest as text, so a caller that writes one of these fields in uppercase must compute the request digest over the lowercase text.
- Secret formats: API keys `osk_`, enrollment tokens `ose_`, invitation secrets `osi_` and device session credentials `osd_`, each followed by 32 random bytes from a cryptographically secure source in unpadded base64url. The prefixes let secret scanners and the credential selector recognize them. A relay grant ID is not a credential (see [Relay authentication](#relay-authentication)).

### Authorization

The server authorizes every RPC that takes an `organization_id` as follows. For a `user` principal, it loads the caller's membership in that organization and checks the role against the matrix below; a user without a membership gets `not_found`. For an `api_key` principal, it checks that the key belongs to that organization and checks the API key column of the matrix; a key of another organization gets `not_found`. In both cases, it loads every target entity with that organization in the query. A request for an entity of another organization returns `not_found`, not `permission_denied`, so that callers cannot discover entities of other organizations.

Three public RPCs take no `organization_id`. They accept only a Logto access token (`user` principal) and need no membership; an `api_key` or `device` credential on them fails with `permission_denied`:

- `CreateOrganization` creates the organization and the caller's `owner` membership in one transaction.
- `ListOrganizations` returns only the organizations in which the caller has a membership.
- `AcceptInvitation` takes the organization from the validated invitation, not from the request. An expired, revoked or used invitation fails with `not_found` and the same message. When the caller already has a membership in the organization, the call fails with `already_exists` and the invitation stays unused. The caller's Logto token is valid in this case, so the server does not use `unauthenticated`.

| Action                                                                                                              | `owner` | `admin` | `member` | API key |
| ------------------------------------------------------------------------------------------------------------------- | ------- | ------- | -------- | ------- |
| Delete the organization, transfer ownership                                                                         | yes     | no      | no       | no      |
| Invitations, member roles, removal of another member                                                                | yes     | yes     | no       | no      |
| Remove the caller's own membership (leave the organization)                                                         | no      | yes     | yes      | no      |
| Enrollment tokens, device removal, device limits, agent version policy changes                                      | yes     | yes     | no       | no      |
| API keys                                                                                                            | yes     | yes     | no       | no      |
| Read the organization, list members                                                                                 | yes     | yes     | yes      | no      |
| List and read devices and the agent version policy                                                                  | yes     | yes     | yes      | yes     |
| Sandboxes, exec, files, pause, resume, snapshots, templates, data path sessions, relay authorization and relay RPCs | yes     | yes     | yes      | yes     |
| Link and unlink a billing account, list linkable billing accounts                                                   | yes     | no      | no       | no      |
| Read the linked billing account, its balance and this month's usage (`GetBillingUsage`)                             | yes     | yes     | no       | no      |
| Read the billing status (`GetBillingStatus`)                                                                        | yes     | yes     | yes      | yes     |

- An organization has exactly one `owner`. An `admin` cannot change the role of the `owner` or remove the `owner`, and cannot grant `owner`. An `admin` can change the role of another `admin` and remove another `admin`. Only `TransferOwnership` makes another existing member the `owner`.
- Sandboxes, snapshots and templates belong to the organization, not to the member or API key that created them. Every member and API key of the organization can use them. The record keeps the creating principal for audit.
- Invitations are one-time secrets that expire after 7 days. `AcceptInvitation` creates the membership for the signed-in Logto user. OwnSand does not look up users by email address.

### Agent channel

- Enrollment: an admin creates an enrollment token with an expiry of at most 24 hours. The agent generates an Ed25519 key pair locally and calls `AgentService.Enroll` with the token and the public key. The server consumes the token in the same transaction that creates the device, so a token enrolls at most one device. Until the token's expiry, the server keeps the hash of the consumed token with the device ID and public key: a retry of `Enroll` with the same token and the same public key returns the same `device_id`, so an agent that lost the first response can continue. A retry with another public key fails like a used token. An expired, revoked or used token fails with `unauthenticated` and the same message, so that the response does not show which condition failed.
- Session: the agent calls `CreateChallenge`, signs the nonce with its private key and calls `Authenticate`. The nonce is single-use and expires after 60 seconds. The device session credential is needed only to open the channel and expires after 15 minutes. An open channel stays valid until it closes; the server checks the device state at each heartbeat and closes the channel when the device is removed. Before each new connection, the agent gets a new credential with `CreateChallenge` and `Authenticate`.
- Transport (recorded decision): `AgentService.Channel` is a Connect bidirectional stream of `ChannelRequest` and `ChannelResponse` messages over HTTP/2 on `https://ownsand.api.delino.io` (h2c from Caddy to the container; TLS HTTP/2 or h2c in tests), authenticated with `Authorization: Bearer osd_...`. Only the lease holder accepts it; other instances answer `unavailable`. Admission checks the lease and registers the channel in the in-memory hub as one step under the lease's ownership lock, and the transition that clears ownership takes the same lock before it closes every channel. A channel is therefore either registered before the transition and closed by it, or refused with `unavailable` before the server sends the configuration or changes the hub. Admission takes the device's in-process registration fence, which the offline write of a closing channel of the same device holds across database I/O, before it takes the ownership lock, so the lock never waits for database work and only the admission of that device waits for the fence. The lock is released before any database or stream I/O, so a late admission to a former holder cannot keep a channel on a non-holder. The server sends the configuration message first, answers each heartbeat with an acknowledgement, and closes the channel after 45 seconds without a heartbeat. Each channel has an outbound queue of 256 envelopes drained by one writer. When a send finds the queue full, it waits up to 5 seconds for room, because a burst such as the delete commands after a state report can legitimately queue more than 256 envelopes before the writer drains them. If the queue is still full after that wait, the agent does not read its channel: the server closes that channel with the cause `the agent channel closed because its outbound queue stayed full`, the send fails, and the close takes the normal disconnect path (the device becomes `OFFLINE` and its non-terminal sandboxes show as `unreachable`, only when it was the current channel). A stalled agent therefore blocks neither the channel handler, so heartbeats and the heartbeat timeout keep working, nor the control event worker, so the events of other devices wait at most that bounded time. The `agent_channel_disconnected` log record carries the cause and the channel generation, and an `agent_channel_writer_stalled` record marks a writer that is still blocked in a send 5 seconds after the disconnect (`Timing.WriterDrainTimeout`). The channel handler cannot return under an active send, because that would finish the response writer under the send (a data race and a panic in `net/http`), and the server sets no HTTP write timeout, because the channel is a long-lived stream. The handler therefore aborts the blocked write through the stream's `http.ResponseController` (a write deadline in the past, which resets the HTTP/2 stream), waits for the writer to end and logs `agent_channel_writer_ended`, so a stalled agent that keeps its stream open does not retain the handler, the writer, the inbound reader or the full queue. The WebSocket fallback for devices behind HTTP/1.1-only proxies stays an open decision, and the Caddy route properties (h2c and no early stream end) still need verification before the first deployment.
- Control event cursor (recorded decision): the lease holder polls `control_events` by `delivery_id`, not by `event_id`. `event_id` is allocated when the row is inserted, so a transaction that inserts first can commit after a later one, and a cursor on `event_id` would skip its event for good. A deferred constraint trigger assigns `delivery_id` at the end of the writing transaction: it takes the transaction-scoped advisory lock `0x6f776e5f6374` and then the next value of the sequence `control_events_delivery_id_seq` (`CACHE 1`). Postgres releases that lock only after the transaction is visible to other sessions, so a reader that sees delivery ID N + 1 also sees N, and transactions that write events commit one at a time (a transaction with several events takes the lock again for each of them). A rolled-back transaction leaves no event and no gap that a poll waits on. The poll returns up to 500 events in `delivery_id` order and advances its cursor to the last returned delivery ID, so no event is dispatched twice. When an instance acquires the lease, it sets the cursor to the newest `delivery_id` (`events.LatestID`) and dispatches only events that commit after that point: events from before the handover belong to channels of the previous holder, and reconnecting agents get their pending deletes again through the state report reconciliation (see Reconnection). Every lease acquisition and loss stores the cursor under a generation counter; a batch that is still in flight copies the counter with the cursor and, when the counter changed, stops before its next read, its next delivery and its cursor store, so a batch from an earlier lease period never replaces the cursor of a later one (deliveries that already returned are not undone). The event processor initializes an unset cursor (a failed read at acquisition, or the first poll after a loss) through the same counter without a lease transition: it reads the newest `delivery_id` under the generation that it copied at the start of the poll and stores it only when the generation is unchanged and the cursor is still unset, and it does not increment the counter, so a read that started in an earlier lease period never replaces or clears the cursor of a later one; a failed read leaves the cursor and the counter unchanged and the next poll repeats it. The trigger runs in the database, so an `INSERT` of the previous release, which knows only `event_id`, also receives a `delivery_id` during a rolling deployment, and the previous release keeps its `event_id` cursor until it stops. Migration `0006_control_events_delivery_id.sql` backfills `delivery_id = event_id`, starts the sequence above the largest existing value and adds a unique index on `delivery_id`. The janitor deletes an event only when it is older than the retention of 1 hour by `create_time` and its `delivery_id` is not above the processed cursor of the lease holder (see Retention): an event that the holder has not processed yet stays, however old it is, and an instance that does not hold the lease, or whose cursor is unset, deletes no control event. Because the cursor starts at `events.LatestID` on a lease handover, the events from before the handover become eligible after the retention, as the handover rule above states. The advisory lock key must differ from the migration runner's key.
- Implementation of the channel rules: a second channel of a device replaces the first (the first is closed, and its close does not change the device state). Only the close of the current channel marks the device `OFFLINE`. The device becomes `ONLINE` in the transaction that applies its state report, and only then is it eligible. While the lease holder has no channel for an `ONLINE` device (after a lease handover or a crash), a sweep every 5 seconds marks it `OFFLINE` when it was not heard from for 45 seconds, also when the lease holder has no channel at all (an empty channel registry excludes no device from the sweep). Reachability is not stored: a non-terminal sandbox shows as `UNREACHABLE` whenever its device is not `ONLINE`. Commands carry a UUID v7 `command_id`; the server remembers each sent command in memory, tagged with the generation of the channel that carried it, and applies its result when it arrives (also when no RPC waits for it). An export result is applied with a bounded retry after a transient database error (see the export recovery record). The record of a command is removed at once when its result arrives or when its enqueue fails. When a channel closes (for any cause, including the replacement of a channel), the server marks the records of that channel's generation for expiry and logs their number as `commands_marked_for_expiry` in `agent_channel_disconnected`, with the device and the generation. A marked record stays for a retention window of 2 minutes (`Timing.CommandGrace`), which covers the 45-second heartbeat timeout and the 30-second maximum agent reconnect backoff with margin, because the agent sends the result through its current channel, which can be a replacement channel of the same device. A result from the same device inside the window is applied once, as on an open channel. A sweep every 5 seconds (the offline sweep interval) removes the records whose window ended and logs their number as `agent_commands_expired`; a result for a removed record is ignored as an unknown command. Expiry synthesizes no command failure and changes no durable sandbox or snapshot state: the agent's next state report reconciles it as usual. A command sent on a channel that is already closing starts its window at once, and the records of a replacement channel are never marked by the close of an older channel, so the retained count does not grow without bound. Control events are polled every second by the lease holder and processed at once when the instance that wrote them is the lease holder. A removed device's channel receives the clean-up command and is closed after it. The agent's update target is evaluated after each capability report, after each state report and after each policy change, and an update command is sent only when the target (or the revocation recovery flag) differs from the last one sent on the channel. The instance lease is the `instance_leases` row `control-plane`.
- Implementation of the sandbox watch lifetime: an RPC that waits for a sandbox change (the wait of `DeleteSandbox` for a terminal state) registers an in-process watch before it reads the sandbox, so a change between the read and the wait is not lost, and polls the row every second as a fallback for changes made by other instances. Every wait iteration unregisters its watch on every exit (notification, poll, deadline, cancellation, read error or a terminal row). A notification (`fire`) closes the channels of all registrations of that sandbox and removes them, and an unregister after it is a no-op, so the registry holds no entry for a sandbox without a live waiter. When the wait ends for an offline device, the RPC returns the current sandbox and keeps the pending delete.
- Heartbeat: the agent sends a heartbeat every 15 seconds, and the server answers each heartbeat on the same channel with a heartbeat acknowledgement that carries the heartbeat's sequence number. The agent resets its 45-second channel-loss timer only for an acknowledgement on the current channel. Each agent channel of a device gets a new channel generation when it opens, and the server applies heartbeat, close, timeout and state report events only for the current generation. The server marks the device `offline` when the current channel closes or when no heartbeat arrives on it for 45 seconds; an event of an older channel never changes the device state. That also holds for a channel that closed as the current channel and whose clean-up is still running when a replacement channel registers: the lease holder serializes the offline write of the closing channel with the registration of a new channel of the same device through a per-device in-process fence (no migration), locks the device row first and the fence second, and writes `offline` only while the device has no registered channel. Either the replacement registered first and the write is skipped, or the write commits before the replacement's state report, which then sets the device `online`. At that point, the device's sandboxes in `creating`, `running`, `paused` or `deleting` state are shown as `unreachable` with their `last_known_state`. Sandboxes in `deleted` or `failed` state keep their state and end reason. The server stores reachability separately from the agent-reported state and revision: `unreachable` is the reported state of a non-terminal sandbox on an offline device, and the stored agent state and revision do not change. Capacity, the macOS limits and the identifier reservation count a sandbox by its stored agent state.
- Sandbox updates: each sandbox has a revision that the agent increases with every local change. Updates, state report entries and acknowledgements carry the revision, and the server applies an update only when its revision is higher than the stored one; it acknowledges a stale retry without applying it. A reconnection state report entry with the same revision as the stored one confirms the stored state and restores reachability; an entry with a lower revision is ignored. The agent sends a sandbox update for every local state change, including a TTL expiry or a lost VM, with the new state and, for an ended sandbox, its end reason. It also sends one when activity moves the idle deadline, at most once per minute for each sandbox, because peer-to-peer activity does not pass through the control plane and the agent, not the relay, tracks activity. The server stores the reported state and deadline and acknowledges each update; the agent resends an update until it is acknowledged. The server compares the sandbox and snapshot IDs of a state report with the stored IDs, and orders revision epochs, by UUID value, so an agent that spells a valid UUID v7 in uppercase hex gets the same result as with lowercase: a listed sandbox or snapshot is not treated as omitted, a later epoch wins over an earlier one whatever the spelling, and the server stores the epoch in lowercase canonical form.
- Device limits: the server sends the device limits in the configuration message when the channel opens and again after each `ReplaceDeviceLimits` or `UpdateDeviceLimits`. Any instance that commits a change of device limits or of the agent version policy also writes a configuration event to the Postgres event table that revocations use, and the lease holder sends the new configuration or target version to the agent. Each create command also carries the limits that the scheduler used, and the agent checks the create against the stricter of these and its last configuration.
- Device eligibility after reconnection: the device becomes `online`, and eligible for scheduling, only after the server has applied its reconnection state report.
- Reconnection: after `Authenticate`, the agent sends a full state report. The report lists every sandbox that the agent has a record of, including sandboxes that ended while the device was offline, with their end reasons. The server reconciles the stored state of each sandbox and snapshot of the device with the report, subject to the revision rule in [sandbox updates](#agent-channel). The revision is a pair of the agent's state epoch and a counter: the agent creates a new epoch when it starts with a lost or reset state directory and sends it with `Authenticate`, and a revision from a newer epoch is always newer. State changes that the server makes itself (`creating` at create, and the reconciliation results below) keep the stored revision and are replaced by the next agent revision. A delete request is stored as a pending delete apart from the agent state, and agent revisions never clear it: the server shows the sandbox as `deleting` while the delete is pending and the device is online, and as `unreachable` with `last_known_state` `DELETING` while the device is offline, sends the delete command again after every state report or sandbox update that still lists the sandbox as not deleted, and completes the delete when the agent reports that the VM is gone: the sandbox is reported as deleted, reported as `failed` (for example with `LOST_ON_DEVICE`), or no longer listed. A sandbox that ended as `failed` keeps that state and end reason. The delete command is idempotent on the agent. The transaction that records a pending delete also writes a delete event to the Postgres event table, so the lease holder sends the delete command to a connected device at once, from whichever instance accepted the request. The agent handles the commands of one sandbox in order: a delete for a sandbox whose create is still running cancels the create, or waits for it and then deletes the VM, and a delete that arrives before its create leaves a delete marker that makes the agent reject that create. The agent reports the sandbox as deleted only when no VM exists and no create for it can start.
- Device lock order: a full state report and `RemoveDevice` (and the device removal of an organization deletion) both change the device row and the sandbox rows of the device, so they take the locks in one order, device row before sandbox rows. The report's transaction first takes the organization row lock with `SELECT 1 FROM organizations WHERE organization_id = $1 FOR KEY SHARE` (see the organization lock order below), then runs `SELECT state, capabilities FROM devices WHERE device_id = $1 FOR UPDATE`, which also gives it the stored capabilities for the built base image merge, and keeps the lock to commit; the removal updates the device row first and then ends the sandboxes. The two therefore serialize without a deadlock (SQLSTATE `40P01`) in either order. A removal that committed first makes the report a no-op: when the device row or its organization is missing, or the device is `REMOVED`, when the lock is granted, the transaction changes nothing, so the report cannot make the device `online` again or replace the `DEVICE_REMOVED` end reason of a sandbox, and the server closes the agent channel without a state acknowledgement (like a heartbeat of a removed device); the agent learns of the removal at its next `Authenticate`. A report that took the lock first is applied completely, and the removal that waits for it then ends the sandboxes that are not terminal. Lock order of the other paths that lock a device: the organization row comes first (see the organization lock order below), the device row second, the sandbox rows third. `RemoveDevice` follows it too: after authorization it takes `FOR KEY SHARE` on the organization row (`not_found` when the organization is gone) and `FOR UPDATE` on the visible device row (`not_found` when missing), and it runs the removal only when the device is not yet `REMOVED`, so two concurrent removals of one device write one `DEVICE_REMOVED` audit event and one removal control event and keep the first tombstone timestamps, and a repeated call on a visible tombstone returns it without a write. The removal's `UPDATE` also carries a `state <> REMOVED` guard. No migration and no protocol change.
- Lost agent state: the epoch rule covers an agent that lost its sandbox records but kept its identity file. Before an agent reports a new epoch, it lists the VMs that its hypervisor still runs for it (each VM is tagged with its sandbox ID) and either recovers their records and TTL deadlines or stops and deletes them, so the report never omits a running VM and the server never releases capacity that a running VM uses. An agent that lost its device ID or private key cannot authenticate as the old device; it must enroll again as a new device. The old device stays `offline`, and an admin removes it, which starts the [removal tombstone](#device-removal-and-organization-deletion) rules. A sandbox whose state is `deleting`, or that is `unreachable` with `last_known_state` `deleting`, and that the report does not list changes to `deleted` with the end reason of its delete request. Any other sandbox that the server knows in a non-terminal state but the report does not list changes to `failed` with `LOST_ON_DEVICE`. A snapshot of the device that the report does not list loses its local copy: the server deletes its record, and the templates that reference it, unless it is exported, in which case the record stays without a local copy. The agent keeps the record of an ended sandbox until the server acknowledges a sandbox update or a state report that contains its terminal revision, so a sandbox that ended while the device was offline keeps its real end reason. `deleted` and `failed` are absorbing: the server never changes a sandbox that is already in one of them, whatever the revision of a later report, so its end reason stays. When a later report still lists a live VM for such a sandbox, the server keeps the terminal state and sends a delete command for the VM.
- Lost VMs: when the agent has a record of a sandbox in `creating`, `running` or `paused` state but its VM no longer exists (for example, after a host reboot, or after an agent restart, which stops every VM on every host OS), the agent reports the sandbox as `failed` with `LOST_ON_DEVICE` and releases its resources.
- Commands: the server sends create, delete, pause, resume, snapshot, export, import, clean-up and update commands with a command ID. The agent reports each result with that command ID. A command for an offline device fails immediately with `unavailable`; the server does not queue it. `DeleteSandbox` is the exception: on an offline device it records the pending delete and succeeds, and the server sends the delete command when the device reconnects.

### Scheduler

- A device is eligible for a create request when it is `online`, its host OS and architecture match the filters, it supports the requested guest (see [the agent capabilities](cmds-ownsand-agent-foundation.md#isolation)), its agent version is not revoked, its update state is not `INSTALLING`, it has not been in `PENDING_IDLE` for more than 24 hours (the server stores the time of the first `PENDING_IDLE` report as `pending_idle_since` in the device record, so the clock survives restarts and lease handovers) (so that a busy device can drain and install an update; running sandboxes end at their `max_ttl`, at most 7 days), the requested source is ready on it (for `base_image`, the device reports that base image as built; for a snapshot or template, see below), and its free capacity covers the requested resources. Free capacity is the device limit minus the resources of its `creating`, `running`, `paused` and `deleting` sandboxes. For vCPU, the device limit is the effective vCPU limit that the [vCPU overcommit rule](#vcpu-overcommit) gives. The requested disk must also fit in the free disk that the device last reported, minus the disk of `creating` sandboxes that it has not reported yet; the agent checks the free disk again before it creates or imports a disk and rejects the command with `resource_exhausted` when it does not fit. A `deleting` sandbox releases its resources only when the agent confirms the deletion, or when a state report shows that the sandbox is gone.
- A newly enrolled device has zero limits, so it is not eligible until an admin sets its limits with `ReplaceDeviceLimits`. Its `vcpu_overcommit_percent` starts at `100`.
- `ReplaceDeviceLimits` and the legacy `UpdateDeviceLimits` share one write path (`ActionManageDevices`, the numeric validation, one transaction that updates the four limits, writes the configuration event and the `DEVICE_LIMITS_CHANGED` audit record, and the notification to the lease holder). `ReplaceDeviceLimits` first rejects a missing field with `invalid_argument`, before any write; `UpdateDeviceLimits` reads a missing value as `0`. Both may set limits below the current allocation. The existing sandboxes keep running, and the device gets no new sandbox until its free capacity covers a request.
- For a `MACOS` guest, the device must also be an Apple silicon Mac with fewer than two macOS guests in `creating`, `running`, `paused` or `deleting` state, counted from the server's own sandbox records. This is the Virtualization.framework limit; Linux guests do not count toward it. A sandbox from a macOS snapshot or template also needs a device that reports support for the snapshot's macOS hardware model.
- macOS machine identifier: a macOS sandbox created from a snapshot or template uses the machine identifier of the VM that the snapshot was taken from. The macOS runtime change verified that a restored disk boots with a new identifier, and the agent now gives every cold boot a new identifier and restores a memory state only while no VM of the device uses the snapshot's identifier (see the [agent contract](cmds-ownsand-agent-foundation.md#pause-resume-and-snapshots)); removing the reservation below is a later control plane change. Until then, the scheduler reserves that identifier: a device is not eligible when any sandbox in `creating`, `running`, `paused` or `deleting` state, or in `unreachable` state with one of these as its `last_known_state`, uses the same identifier and whose `max_ttl` deadline has not passed (the agent enforces `max_ttl` also while it is offline, so the VM is gone after it). This includes the source VM and sandboxes from other snapshots of the same source, on any device. A sandbox that ended because its device was removed keeps its identifier reserved until `ConfirmRemoval` succeeds for that device or its `max_ttl` deadline passes, because the VM can still run on the offline device.
- The sandbox architecture is the device architecture. OwnSand does not emulate another architecture.
- The same rule picks the error code with or without `device_id`: a request fails with `unavailable` when a device could run it after a transient condition ends (offline, no live channel in the serving instance, capacity that running sandboxes hold, update state `INSTALLING`, `PENDING_IDLE` or `REVOKED_PENDING_IDLE` (a revoked version clears itself when the running sandboxes end and the update installs), or a macOS identifier that a running sandbox holds), and with `failed_precondition` when it exceeds the device limits themselves or breaks the OS, architecture, capability or source rules. Without `device_id`, the request gets `unavailable` when at least one enrolled device fails only transient conditions, and `failed_precondition` otherwise.
- Among eligible devices, the scheduler selects the one with the lowest allocated share of its most constrained resource, and breaks ties by the lowest `device_id`.
- With an explicit `device_id`, the scheduler checks the same conditions and does not select another device. It fails with the code that the error-code rule in this section gives for that device.
- A sandbox from a snapshot or template runs on the device that holds the snapshot locally, or on any eligible device with the same OS and architecture when the snapshot is exported. Memory state restores only on the device that took the snapshot, and only when the request's `vcpu_count`, `memory_mib` and network mode equal the snapshot's values, because the saved state includes the virtual devices. These conditions only allow an attempt: when the hypervisor reports that it cannot read the saved state (for example, after a save format change), the agent boots the snapshot disk cold, and the sandbox reports which restore path it used. In every other case the sandbox restores the disk and boots cold, until a runtime contract defines a compatibility check for memory state on other devices (for example, the CPU model for Firecracker-class snapshots). The scheduler prefers the snapshot device when memory state can restore there.
- The scheduler reserves the resources in the same transaction that creates the sandbox record, so two concurrent requests cannot both use the last free capacity of a device.
- A create first looks up its `idempotency_key`, right after authorization and before placement or the live-channel check: a known key with the same parameters returns the original sandbox even when its device is offline now.
- When the agent rejects a create command before it makes a VM (for example, with `resource_exhausted` after its free disk check), the server sets the sandbox to `failed` with `CREATE_FAILED` and releases its reservation. A lost command result is not a rejection: the sandbox stays `creating` until the agent reports it, because the VM may exist.
- Implementation decisions: the scheduler is a pure function (`internal/scheduler`). A create locks every non-removed device row of the organization, so concurrent creates in one organization serialize on placement and reservation. A device that has not sent a capability report is a transient (`unavailable`) case; a request whose guest OS, base image or macOS hardware model the reported capabilities do not include is permanent (`failed_precondition`). A `device_id` that names no device of the organization fails with `not_found`. The macOS machine identifier is tracked as a lineage: a macOS sandbox from a base image is its own lineage, a snapshot keeps the lineage of its source sandbox and a sandbox from that snapshot inherits it; the reservation checks the lineage on every device. A sandbox from an exported snapshot on a device without a copy gets the import command first (waiting at most 2 hours for its result) and the create command after a successful import; a failed import fails the sandbox with `CREATE_FAILED`. When the 2-hour wait ends while the device channel is still connected, the server fails the sandbox with `CREATE_FAILED` through the same guarded transition (only from `CREATING`), releases its reservation, notifies watchers and logs `import_timeout_create_failed`; it uses a bounded database context that does not depend on the expired wait, does not retry the import and never sends the create command afterwards. A late import success only records the snapshot copy. A closed channel keeps the reconnect reconciliation. The same rule covers the create command of a create without an import: when its send returns an error before the command is queued while the device channel is still connected (the request context ended while a full outbound queue held the send), the server fails the sandbox with `CREATE_FAILED` through the same guarded transition, releases its reservation and notifies watchers. It uses a bounded database context (5 seconds) that does not depend on the request context, and logs `create_send_failed` (a warning) or `create_send_fail_transition_failed` (an error). The RPC returns the failed record, and a replay of the same idempotency key returns that failed record, because the key stays bound to the sandbox. A send error on a closed channel, including one that a queue that stayed full closed, keeps the reconnect reconciliation, and a command whose send returned without an error is never undone: the agent owns its result. The create idempotency key binds the SHA-256 of the deterministic protobuf encoding of the request. Create requests with the same idempotency key serialize: a request whose first lookup of the key finds nothing starts the reservation transaction, takes a transaction-scoped Postgres advisory lock keyed by the organization and the key, and looks the key up again in that transaction before it resolves the source or places the sandbox. When another request committed the key while this one waited, this request returns that sandbox, or `already_exists` for other parameters, without a reservation, an audit event or a create command, so two identical overlapping requests for the last slot both return one sandbox instead of the loser failing with `unavailable`. A committed key still returns on the first lookup without a transaction. Only the create handler takes this lock, and it takes it before the device row locks and never waits for it while holding one, so the lock order stays acyclic.

### vCPU overcommit

Sandboxes that wait for most of their life (for example, coding-agent sessions that wait for model responses or for user input) reserve vCPUs that they rarely use. An admin can let the scheduler allocate more vCPUs than a device has in its vCPU limit.

- `vcpu_overcommit_percent` is part of the device limits. Valid values are `100` to `400` in steps of `25` (1.0 to 4.0 times the vCPU limit). `ReplaceDeviceLimits` and `UpdateDeviceLimits` reject other values with `invalid_argument`. A new device starts at `100`, which keeps the behavior without overcommit.
- Effective vCPU limit = floor(vCPU limit × `vcpu_overcommit_percent` / 100). The scheduler uses the effective vCPU limit for the free capacity rule in [Scheduler](#scheduler).
- One sandbox can never have more vCPUs than the vCPU limit itself. A create request with a larger `vcpu_count` fails with `failed_precondition` on that device, also when the effective vCPU limit is larger.
- Memory and disk are never overcommitted. Their limits apply unchanged.
- Lowering `vcpu_overcommit_percent` below the current allocation follows the same rule as lower limits: running sandboxes keep running, and the device gets no new sandbox until its free capacity covers a request.
- `ReplaceDeviceLimits`, `UpdateDeviceLimits`, `ListDevices` and `GetDevice` return the vCPU limit, `vcpu_overcommit_percent`, the effective vCPU limit and the allocated vCPUs, so that callers can see the overcommitted capacity. The server computes the effective vCPU limit once, in 64-bit integers, with the shared rule above and reports the exact value in `Device.effective_vcpu_limit_count` (0 for a device with zero limits, such as a newly enrolled device). It also fills the `int32` field `Device.effective_vcpu_limit` that v1 keeps for compatibility: the same value when it fits and 2147483647 when the exact value is larger, so the field never wraps to a negative number. See [the device limits contract](protos-ownsand-api-contract.md#device-limits). The device record stores only the limits, so this needs no database migration.
- The allocated vCPUs are the exact 64-bit sum over the CREATING, RUNNING, PAUSED and DELETING sandboxes of the device. The server sums in 64-bit integers, so valid reservations that sum above 2147483647 never raise a database integer overflow. `ListDevices`, `GetDevice`, `UpdateDeviceLimits` and `ReplaceDeviceLimits` report the exact sum in `DeviceAllocation.vcpu_total_count` and the `int32` field `DeviceAllocation.vcpu_count` with the same value when it fits and 2147483647 when the sum is larger. The scheduler uses the exact sum for the free capacity rule and for ranking devices by allocated share. A limit below the exact allocation gives the usual `unavailable` capacity outcome. See [the device limits contract](protos-ownsand-api-contract.md#device-limits).

### TTL

- `idle_ttl` and `max_ttl` are required. The server stores both deadlines and sends them to the agent with the create command. The agent owns the idle deadline after that and reports changes as described in [Agent channel](#agent-channel).
- The agent enforces both TTLs locally, so they apply even when the device is offline. When a TTL ends, the agent deletes the sandbox and reports `deleted` with `IDLE_TTL_EXPIRED` or `MAX_TTL_EXPIRED`: the reason of the earlier deadline, and `MAX_TTL_EXPIRED` when both deadlines are equal. The agent applies the same rule when it enforces passed deadlines after a restart.
- `max_ttl` counts from creation and includes paused time.
- The idle clock restarts at each exec start, exec end, file operation and resume. Opening a data path session is not activity. A running exec keeps the sandbox active. The idle clock does not run while the sandbox is paused.

### Data path signaling and relay

- `OpenSession` and `AuthorizeRelay` first register as pending on the lease holder, then authorize the caller, so a revocation event that the lease holder processes in between ends the pending session or grant as well. `OpenSession` then forwards the caller's SDP offer to the agent on the agent channel with the session ID, the principal and an absolute expiry, and returns the agent's answer. `AuthorizeRelay` instead sends a relay grant to the agent and returns the grant ID after the agent acknowledges the grant (see [relay authorization](#data-path-signaling-and-relay) below). The agent accepts the data channel only for a DTLS fingerprint that arrived in an offer from the control plane, and serves relay frames only for a grant ID of a grant that arrived from the control plane. The control plane therefore authenticates both peers of every data channel and authorizes every relay stream.
- Session end: the agent enforces the session limits on the peer-to-peer path, because peer-to-peer frames do not pass through the control plane. A session ends at the first of these events: 15 minutes without frames and without an open exec or file request (an open request counts as activity, and the agent sends a keepalive exec event at least every 60 seconds while an exec produces no output); the absolute expiry, 1 hour after `OpenSession`; a revocation message from the control plane; or the loss of the agent channel that signaled the session, which the agent detects when the channel closes or when it gets no heartbeat acknowledgement for 45 seconds. The control plane sends a revocation message for every open session and every revocable relay grant (see the grant terms below) of an API key when the key is revoked, of a user in an organization when that user's membership in that organization ends, and of a sandbox when the sandbox is deleted. Any instance can process the revoking request, so it writes a revocation event (the revoked API key, the ended membership or the deleted sandbox) to a Postgres table in the same transaction. The lease holder matches each event against its open peer-to-peer sessions and its revocable relay grants, and writes one session revocation for each match. A relay grant is revocable until its stream deadline plus the 60-second delivery margin (see the grant terms below), not only while it is admittable, because a stream admitted before the expiry can still run; and the lease holder delivers every pending revocation, with its revocation ID and its target (the session ID or the relay grant ID that it ends), to the agents and deletes it after the agent acknowledges that ID. The agent ends only the session or the relay streams of the grant that the target names. A revocation names the agent channel that signaled its session or sent its grant. The server also deletes it when that channel closes, when the session reaches its absolute expiry, when the grant stops being revocable, or when the device is removed, because the session or grant has ended in each case. The agent acknowledges a revocation also when the session or grant has already ended. Each session and each relay grant is bound to the agent channel that signaled or sent it: when that channel closes, including at a lease handover, the agent ends the session and the grant's relay streams at once with `AGENT_CHANNEL_LOST`, so no session or grant outlives the instance that knew about it. Before it closes the data channel or a relay stream, the agent sends a session-end frame with the reason (`IDLE`, `EXPIRED`, `REVOKED` or `AGENT_CHANNEL_LOST`, and on relay streams also `GRANT_INVALID` or `GRANT_REPLACED`). After any session end, the caller calls `OpenSession` again to continue on the peer-to-peer path, or `AuthorizeRelay` again to continue on the relay; a session end is not an ICE failure.
- Relay authorization: each relay grant covers one operation. `AuthorizeRelay` takes an `organization_id`, a `sandbox_id`, an operation kind (`RelayOperationKind`: `EXEC`, `ATTACH_EXEC`, `READ_FILE` or `WRITE_FILE`), the caller-generated operation ID of that kind (`exec_id`, `read_id` or `write_id`; for `EXEC` and `ATTACH_EXEC` the `exec_id` must be the lowercase text form of the UUID, and a value with an uppercase hex digit fails with `invalid_argument` before a grant is reserved, because the agent compares exec IDs as text) and, for `EXEC`, `READ_FILE` and `WRITE_FILE`, the request digest of the operation (an `ATTACH_EXEC` request carries no digest, so a caller that knows only the `exec_id` can attach), which the [protos contract](protos-ownsand-api-contract.md#relay-grants) defines (for `EXEC`, the command, environment, working directory and timeout; for `READ_FILE` and `WRITE_FILE`, the guest path). It applies the authorization matrix and the sandbox state rule of the operation: `READ_FILE` and `WRITE_FILE` need `RUNNING`, and `EXEC` and `ATTACH_EXEC` accept `RUNNING` or `PAUSED`, so that a caller can get the kept output of an exec on a paused sandbox with `AttachExec`. It needs a live agent channel for the sandbox's device, so it always runs on the lease holder.
- `AuthorizeRelay` creates a relay grant with a new grant ID (a UUID v7 that the control plane does not persist), the principal, the sandbox ID, the operation kind, ID and request digest, an expiry 15 minutes later and a stream deadline 30 minutes after creation. It sends the grant to the agent on the agent channel. After the agent acknowledges the grant, it returns the grant ID, the expiry and the remaining duration (`expires_in`), as the [protos contract](protos-ownsand-api-contract.md#relay-grants) lists. When the agent rejects the grant because of its per-device grant limit (`REJECTED_GRANT_LIMIT`), `AuthorizeRelay` fails with `resource_exhausted` and a retry delay; only that explicit rejection gives this result. When the agent does not acknowledge within 10 seconds, or when the control plane removes the pending grant before the agent acknowledges it (the agent channel closed, the grant was revoked or released, or it stopped being admittable), `AuthorizeRelay` fails with `unavailable` and no retry delay, and the caller retries with the same `authorization_id` according to the idempotency rule. The lease holder keeps that pending grant under its `authorization_id` until it stops being admittable (its expiry plus the 30-second admission tolerance): a late acknowledgement installs it, a late rejection removes it, and a retry with the same `authorization_id` waits for the outcome and returns the grant ID of the installed grant. The pending grant is registered before it is queued for the agent, so when the lease holder cannot queue it on a live agent channel (the outbound queue stays full until the caller's request context ends), it releases that exact reservation before it answers: it records a delivery failure outcome under the registry lock, wakes the calls that wait on the same `authorization_id` (they fail with `unavailable` as well, not with `resource_exhausted`), frees the `authorization_id` and, for a replacement, the predecessor's pending-successor link, and the predecessor stays installed. A retry with the same `authorization_id` then reserves and sends the grant again, and returns the new grant ID after the agent acknowledges it. A grant that was queued is never removed for this reason: it stays pending for a late acknowledgement and an identical retry returns the original grant ID. The lease holder logs the failed enqueue with the event `relay_grant_enqueue_failed` (grant ID, sandbox ID, operation kind, replacement flag and an error category: `channel_closed`, `context_canceled`, `context_deadline_exceeded` or `other`).
- Idempotency: each `AuthorizeRelay` carries an `authorization_id` (a UUID v7 that the caller generates for each logical request and reuses for every retry of that request, after a lost response or a retryable `unavailable` or `resource_exhausted` result). A retry with the same `authorization_id`, principal and request, while the grant it created is admittable, checks the caller's current authorization again and returns the same grant ID without a new grant. Independent requests use new `authorization_id` values and get separate grants.
- Replacement: an `AuthorizeRelay` may name, in `replaces_grant_id`, a revocable grant (one that still counts against the limits, also after its expiry) that the same caller holds for the same principal, sandbox, operation kind, operation ID and request digest. It first checks the caller's current authorization and then replaces that grant atomically with a new grant ID. The replacement does not use another slot of the grant limit: the predecessor and its pending successor share one reserved slot, both stay eligible for revocation until the agent's acknowledgement names the swap, and a predecessor has at most one pending successor (a second replacement request for it waits for the first or fails with `aborted`), so the operations of a device at the limit can renew their grants at a stream rotation and recover after a relay connection loss. The agent ends the open streams of the replaced grant with `GRANT_REPLACED`. The server checks the `authorization_id` first: a retry of a known request follows the idempotency rule above. A new request without `replaces_grant_id` always creates a separate grant and never ends another grant's streams, so two programs of one principal that attach to the same exec do not end each other's streams. The SDK sends only the grant ID that it received itself. When `replaces_grant_id` names no revocable grant of the same principal, sandbox, operation and digest (for example, after the agent channel was lost or the grant was released), `AuthorizeRelay` ignores it and creates a separate grant under the normal limits. Only when it performed the replacement does the control plane send `replaces_grant_id` to the agent with the new grant. The control plane takes the predecessor ID once, under the grant registry lock, when it builds the grant message, so the queued message keeps that ID even when the agent releases the predecessor before the message is sent; when the predecessor is already gone at that point, the field is absent. A successful acknowledgement that does not name the predecessor leaves the predecessor installed and frees its pending-successor link, so the predecessor can be replaced again. The control plane keeps the old grant in its set of revocable grants until the agent's acknowledgement names it as replaced, the agent releases it, its agent channel is lost, or it stops being revocable (its stream deadline plus the 60-second delivery margin), so a revocation still reaches the old grant's streams when the agent installed the new grant separately; and the agent swaps the grants atomically, according to the [agent contract](cmds-ownsand-agent-foundation.md#data-path).
- A grant authorizes every relay RPC of its operation until its expiry: retries of the same `ExecRequest`, `AttachExec` for the same `exec_id`, `ReadFile` calls for the same `read_id` and `WriteFile` chunks for the same `write_id`. Any other operation needs its own `AuthorizeRelay`, so each operation is authorized again. The agent checks the first request frame of each relay stream against the grant's operation kind, ID and request digest, rejects it when the grant's expiry plus the 30-second admission tolerance passed before that frame arrived, and applies the state rule of that request before it dispatches it: a new `Exec`, `ReadFile` or `WriteFile` on a sandbox that is not `RUNNING` fails with `failed_precondition`, according to the [protos contract](protos-ownsand-api-contract.md#sandbox-state-rules).
- The expiry (plus the agent's 30-second admission tolerance) is the last time at which the agent accepts the first request frame of a relay stream of the grant. A stream whose first request the agent accepted before the expiry continues, subject to revocation and channel loss, until the stream deadline, where the agent ends it with `EXPIRED`. The control plane ends each relay stream before 14 minutes (see [Relay streams](#relay-streams)), so the stream deadline ends only streams that a faulty control plane keeps open. A revocation ends the grant at once: the agent rejects new streams of the grant and ends its open relay streams with `REVOKED`, and a later `AuthorizeRelay` fails with the authorization error. Opening a relay grant is not sandbox activity.
- Renewal: the SDK renews the grant of an operation only when it must start a new stream with an expired or expiring grant (at a stream rotation, at the next `WriteFile` chunk or `ReadFile` call of the operation, or during recovery), never while a stream of the old grant is open, and only through replacement, with `replaces_grant_id`, so a renewal never needs another slot and never releases a grant that another caller holds.
- Release: the agent releases a grant when none of its relay streams is open and its operation has finished on the agent (the exec ended and its result was delivered on a relay stream, the read sent its final message, or the write sent its `finish` result), or when its last relay stream ended with an error that leaves no operation to continue (`not_found`, `permission_denied`, `already_exists` or `failed_precondition` for a request that the agent never started; an `AttachExec` `not_found` under an `EXEC` grant does not release it, because the caller may follow it with the identical `ExecRequest`), and reports the release on the agent channel. The lease holder then removes the grant from its set of revocable grants and from the limits below, and a later RPC of that operation needs a new `AuthorizeRelay` (for example, after a lost final response). The agent also releases a grant that has had no open stream for 60 seconds (counted from its installation or from the end of its last stream), and an expired grant as soon as its last admitted stream ends, so cancelled or abandoned operations do not hold slots; the operation itself stays resumable under a new grant. The stream deadline stays the last fallback.
- Limits: the lease holder keeps at most 256 revocable relay grants per device, and at most 32 of them for one principal, and accepts at most 10 `AuthorizeRelay` calls per second per principal; a request over either limit fails with `resource_exhausted` and a retry delay in the error detail, and the SDK retries it according to the [SDK contract](packages-ownsand-sdk-foundation.md#data-path). A grant counts until it is released, revoked, lost with its agent channel or stops being revocable, so the grant limits bound operations that run at the same time, including streams admitted before an expiry, not operations per 15 minutes. The agent applies the same per-device grant limit and rejects a grant over it, so a principal cannot grow agent memory without bound. Adjust the values with the implementation and record them here.
- Grant terms: a grant is revocable while it is not revoked or released, is bound to the agent's current agent channel and has not passed the later of its stream deadline plus 60 seconds and the time the control plane received the agent's acknowledgement plus the `stream_deadline_in` duration that it sent (the agent starts that duration when it receives the grant, which is before the acknowledgement, so the control plane never forgets a grant that the agent still serves; the agent enforces the stream deadline itself without tolerance). A revocable grant is also admittable (a live grant) until its expiry plus the agent's 30-second admission tolerance. Admission, the control plane's check at the start of each relay RPC and the agent's relay connection rule use admittable grants; revocation matching and the grant limits use revocable grants. Admittability is checked when the agent accepts the first request frame of a stream. A stream accepted under an admittable grant (an admitted stream) carries sandbox content after the expiry, until the stream ends, the grant is revoked, the agent channel is lost or the stream deadline arrives.
- The data path is selected by the client according to the [SDK contract](packages-ownsand-sdk-foundation.md#data-path). The server records `OpenSession` and `AuthorizeRelay` calls in logs and metrics with the `DataPathTransport` that each signals.
- Implementation decisions: sessions, relay grants and pending revocations live only in the lease holder's memory, bound to the agent channel generation that signaled or sent them, and are dropped when that channel closes. `OpenSession` accepts an SDP offer of at most 64 KiB and waits at most 30 seconds for the agent's answer (`unavailable` after that); an answer with an `ErrorDetail` ends the RPC with that code. A reused `authorization_id` with another request fails with `invalid_argument`. A replacement while the predecessor already has a pending successor fails with `aborted`. The per-device grant limit and the agent's `REJECTED_GRANT_LIMIT` fail with `resource_exhausted` and a 1-second `retry_after`, while the removal of a pending grant without an acknowledgement (for example when the agent channel closes) fails with `unavailable`; the 10 calls per second per principal limit gives the token bucket's delay. Relay RPCs that fail the grant check are limited to 10 per minute per principal (burst 10). Three rejections count, all against the one bucket of the calling principal (key: principal kind and ID): an unknown, expired, revoked or otherwise non-admittable grant (`unavailable` with `GRANT_INVALID`), a grant of another principal and a request whose organization, sandbox, operation kind or operation ID does not match the grant (both `permission_denied`). While the bucket has tokens, each rejection keeps its status and message; when it is empty, the RPC fails with `resource_exhausted` and the delay in `ErrorDetail.retry_after` instead. Other principals have their own buckets. An RPC with a valid grant takes no token, and so do rejections of the authorization matrix and of the credential. Revocation events (revoked API key, ended membership, deleted sandbox, removed device, deleted organization) are matched against the sessions and the revocable grants; each match is removed at once and gets one `SessionRevocation`, which stays pending until the agent acknowledges it, its channel closes, or its end time passes: the absolute expiry of a revoked session, or the end of the revocable time of a revoked grant. An agent that never acknowledges therefore leaves no record behind on an open channel. The lease holder deletes an expired pending revocation and logs `session_revocation_expired` (`revocation_id`, `device_id`, `target`, `expire_time`) when it sends another revocation, when it opens a session, and in the 5-second sweep that also expires command records.

### Relay authentication

- The relay uses no credential of its own. The control plane already holds every relay grant in the memory of the lease holder and validates the caller's and the agent's credentials itself, so it needs no signed relay ticket.
- `RelayService` RPCs carry the caller's own credential (a Logto access token or an API key) in the `Authorization: Bearer` header, validated as in [Authentication](#authentication), and the grant ID that `AuthorizeRelay` returned in the `Ownsand-Relay-Grant-Id` request header, according to the [protos contract](protos-ownsand-api-contract.md#relay-services). At the start of each RPC, the control plane applies the authorization matrix again and accepts the RPC only when the grant is admittable on this instance, its principal is the principal of the RPC (the same Logto `sub` or the same API key), and the request's `organization_id`, `sandbox_id`, operation kind and operation ID equal the grant's (the control plane checks the request fields when the request body arrives, and ends a mismatched RPC with a relay stream close). It fails an RPC for an unknown, non-admittable or revoked grant with `unavailable` and `GRANT_INVALID` in the error detail, like the agent's rejection, and a mismatch of principal, organization, sandbox or operation with `permission_denied`. The control plane checks the principal, then applies the authorization matrix, then compares the request fields. Each of these grant check rejections (unknown or non-admittable grant, principal mismatch, request mismatch) takes one token of the per-principal failed grant check bucket recorded in [Security](#security) and fails with `resource_exhausted` and `retry_after` when the bucket is empty; a valid grant takes none. The agent checks the sandbox, operation kind, operation ID and request digest again against its grant, and enforces the organization boundary through the sandbox of the grant, which the control plane issued for that organization. A stream that started under an admittable grant continues until it ends according to [Relay streams](#relay-streams).
- A grant ID is not a credential: it authorizes nothing without the credential of the grant's principal. It is not secret, but components log it only as an identifier and never with a credential.
- `RelayAgentService.Connect` carries an `osd_` device session credential of the device, validated as in [Authentication](#authentication). The agent gets a new credential with `CreateChallenge` and `Authenticate` before each new relay connection, like before each agent channel, because a credential expires 15 minutes after issue. The device key signature in `Authenticate` proves possession of the device key, so the relay connection needs no proof of its own.
- The control plane does not rely only on its own revocation check: the device agent stays the enforcement point for open streams. It admits a relay stream only for a grant ID of a live relay grant that the control plane sent on the agent channel (grant expiry blocks only new requests), and it ends the admitted streams of a grant when the control plane revokes it, when that agent channel closes or at the grant's stream deadline, according to the [agent contract](cmds-ownsand-agent-foundation.md#data-path).

### Relay

The relay is the fallback of the data path. The control plane forwards `DataFrame` messages between the caller's `RelayService` RPC and the agent's `RelayAgentService` connection in process memory. Relay data never passes through the agent channel. The relay origin is the control plane origin `https://ownsand.api.delino.io`; there is no separate relay origin.

#### Agent relay connections

- A device agent opens `RelayAgentService.Connect`, a bidirectional stream over HTTP/2, with its device session credential and sends its request headers with an initial keepalive frame at once. The control plane registers the connection for the credential's device only when the device has a current agent channel on this instance, and binds the connection to that agent channel generation. It closes the relay connection when that agent channel closes (also at a lease handover and when the device is removed), because the agent then ends every relay grant of that channel with `AGENT_CHANNEL_LOST`. The registration checks that channel again at the moment it swaps the connection in: a `Connect` whose agent channel was replaced meanwhile (a delayed handler of an old channel) gets `unavailable` and never replaces or closes the connection of the current channel.
- When `Connect` opens, each side sends the list of relay frame kinds that it supports in a frame on `stream_id` 0 (no list means the first-version set), and a sender uses a new kind only after the other side listed it. Both sides ignore an unknown frame kind on `stream_id` 0 and end a stream with an error frame for an unknown kind on any other stream, so either side can be updated first.
- Replacement: when a second connection for the same device registers, the control plane routes new RPCs to it, ends the RPCs on the older connection with `unavailable` and closes the older connection.
- Echo: a keepalive frame from the agent may ask for an echo, and the control plane answers it at once with a keepalive frame.
- Each side sends a keepalive frame after 30 seconds without an outbound frame, so one-way traffic never lets the other side's 90-second receive timeout expire. The control plane closes a connection that receives no byte for 90 seconds, and the agent treats 90 seconds without any received byte on the connection (not only a complete frame, because one large frame can take longer than that to arrive on a slow link) as a lost connection and reconnects while it holds a live grant, according to the [agent contract](cmds-ownsand-agent-foundation.md#data-path).
- When an agent relay connection closes, the control plane ends every RPC routed on it with `unavailable`.
- A revocation, a replacement, a stream deadline or an agent channel loss normally reaches the caller as an agent session-end frame (`REVOKED`, `GRANT_REPLACED`, `EXPIRED`, `AGENT_CHANNEL_LOST`). The agent never waits for the queue of its relay connection to send that frame: when the connection cannot take it at once (the agent's outbound queue is full because the control plane stopped reading), the agent closes the whole connection instead. The control plane then sees only the closed connection and ends every RPC routed on it with `unavailable`, without a session-end reason; the caller calls `AuthorizeRelay` again, which returns the authorization error for a revoked grant, and the agent reconnects under its normal rules. The agent channel and the grants of other callers stay available.
- Recorded decisions of the implementation: `RelayAgentService.Connect` is a Connect bidirectional stream over HTTP/2 with the `osd_` credential and registers only while the device has a current agent channel on this instance (`unavailable` otherwise); the control plane sends its supported frame kinds (every first-version kind) when the connection opens and replies to an echo request at once. Keepalives go out after 30 seconds without an outbound frame, and a connection that received no frame for 90 seconds is closed. Connect delivers whole messages, so the idle check counts complete frames; a single frame that takes longer than 90 seconds to arrive closes the connection, which the 1 MiB plus 64 KiB frame limit makes unlikely but does not exclude. The idle check runs apart from the writer, so a send that the peer's flow control blocks does not stall it. When the connection closes, the server fails a blocked send with a response write deadline in the past and returns from `Connect` only after the writer ended, so the HTTP/2 server never finishes the response while a send still writes to it; a socket write that the kernel buffers block ends through the write byte timeout.
- Device network requirement: the agent relay connection needs outbound TCP 443 to the control plane origin with HTTP/2 from end to end and no TLS interception. A WebSocket transport for `Connect`, for devices behind proxies that allow only HTTP/1.1, is an open decision; record it here, together with the [agent channel transport](#agent-channel), before such devices are supported.

#### Relay streams

- For each `RelayService` call, as soon as it has authenticated the caller and checked the grant in the request headers (before it receives a unary request body), the control plane allocates a `stream_id` that is unique among the open RPCs on that agent connection, sends a stream-open frame with the grant ID and the `sandbox_id`, translates the request into `DataFrame` messages and translates the agent's frames back into responses. The [protos contract](protos-ownsand-api-contract.md#data-path-framing) owns the frames.
- When no agent relay connection for the grant's device exists, the control plane waits up to 10 seconds for one, and then fails the RPC with `unavailable`.
- When the agent ends a stream with a session-end frame (including `GRANT_INVALID` for a stream open that names no live grant), the control plane ends the RPC with `unavailable` and the `SessionEndReason` in the error detail. The caller then calls `AuthorizeRelay` again, which returns the authorization error when the grant was revoked.
- Whenever a relay RPC ends for any reason other than an agent session-end or error frame (the caller cancels it or its connection fails, a stream rotation, the 30-second acceptance timeout, a request upload or `WriteFile` call deadline, or a request that does not match the grant), the control plane sends a relay stream close frame to the agent, according to the [protos contract](protos-ownsand-api-contract.md#data-path-framing). It never reuses a `stream_id` on one agent connection. The close frame is never dropped under outbound backpressure: each admitted stream reserves one place for its final frame (stream close frame, or the error frame for an unknown frame kind) in the connection's outbound queue, in addition to the 1024 places for ordinary frames, so ending the RPC never blocks and the frame waits behind the frames that are already queued until the writer sends it. The stream keeps its connection and grant admission slots until the writer has sent that frame (or the connection closed), so the pending close frames stay within the 64-stream connection limit and the 4-stream grant limit and a new stream is admitted only when a place is reserved for it. A session-end or error frame from the agent ends the RPC without a stream close frame and releases the slots at once.
- The control plane sends stream open frames in increasing `stream_id` order on one agent connection, because the agent drops, without a reply, a stream open frame whose `stream_id` is not above the highest one it has seen. For each agent connection, one open at a time allocates a `stream_id` and puts the stream open frame into the outbound queue; the next open starts after that. The grant checks, the stream limits and the credit windows still apply to each open, and concurrent opens for distinct grants each get the agent's first credit window. An open that waits for this order, or for room in a full outbound queue, ends when its RPC is canceled or the connection closes, and it then holds no stream slot of its grant or of the connection. The `stream_id` of an open that was canceled after allocation is not reused, so a later open gets a larger one. A sender that waits for the agent's credit does not hold this order, so it delays no other stream. The `relay_rpc` log record is unchanged and holds no frame payloads.
- A server stream sends a `keepalive` event at least every 60 seconds while it has nothing else to send, also before the agent's `accepted` event, so that caller-side proxies and NAT devices keep the connection. These rules apply to the server-streaming RPCs (`Exec`, `AttachExec` and `ReadFile`). The control plane ends each such stream whose request the agent accepted before 14 minutes have passed since it allocated the stream's `stream_id`, with an OK status and no final event (a stream rotation), so that every long operation is authorized again within a bounded time; the caller continues with the resume rules of the [protos contract](protos-ownsand-api-contract.md#exec). For `Exec`, `AttachExec` and `ReadFile`, the control plane must forward the complete request frame to the agent within 5 minutes after it allocated the `stream_id`, which covers the request upload and any wait for the agent's credit or for the shared connection; it fails a slower RPC with `deadline_exceeded` (or `unavailable` when it waited for the agent) and sends a relay stream close. A server stream that receives no `accepted` from the agent within 30 seconds after the control plane forwarded its complete request frame ends with `unavailable`, so a stalled admission never looks like a rotation; only a large frame extends that wait: a frame of an open stream on the connection whose encoding is at least 64 KiB moves the deadline to 30 seconds after the control plane received that frame, because the agent's request accepted notice cannot overtake a large frame already in transit. Keepalives, other connection-level frames and smaller frames never extend it, so a stalled admission ends within 30 seconds after the forward plus 30 seconds after each large frame (the credit windows bound the large frames) however many keepalives the agent sends. Because the agent admits a stream only up to the grant's expiry plus 30 seconds and the control plane ends each stream 14 minutes after it allocated the `stream_id`, the latest stream ends by the grant's expiry plus 30 seconds plus 14 minutes, which leaves at least 30 seconds before the 30-minute stream deadline. `WriteFile` has no acceptance event and is bounded only by its 5-minute call deadline.
- A `WriteFile` call must finish within 5 minutes, including the upload of its request body and the agent's result, and the control plane fails a slower call with `deadline_exceeded`. The SDKs retry the chunk with the same `write_id`.
- Implementation (deadline boundary): the relay handler options carry a Connect request gate, which runs after Connect has the request headers and before it reads the request body. The gate authenticates the caller with the credential policy of the interceptors (the authentication interceptor then does not authenticate again), checks the grant in the headers against the principal, authorizes the grant's organization, waits for the agent relay connection and allocates the stream, so every request deadline above counts from that allocation and includes the upload. The gate also sets a read deadline on the request body at that moment (`http.ResponseController.SetReadDeadline`, through a handler wrapper that makes the controller available, because a gate sees no response writer and net/http does not cancel a body read when the request context ends); a body that is not complete by then ends the RPC with `deadline_exceeded`. The handler lifts the read deadline after Connect decoded the request, so it never ends a stream that outlives the upload, and takes over the call, which keeps the absolute deadline from the gate for the forwarding of the request frame (server streams) or for the whole call (`WriteFile`). A call whose handler never ran (the body did not arrive in time or did not decode, or the client left) closes its stream when its RPC ends, and the agent sees a stream open frame, a stream close frame and no request frame. The checks that need request fields (organization, sandbox, kind and operation ID against the grant, and request validation) run in the handler after decoding, and a request that fails them also closes its stream. A gate rejection writes the same `rpc` log record as an interceptor rejection and allocates no stream. When a response writer does not support read deadlines, the control plane logs `relay_body_deadline_unsupported` and the upload is bounded only by the client and the connection, as before the gate. No wire or RPC signature changes.
- Recorded relay limits: the per-stream buffer toward the caller, and the first credit window granted to the agent, is 4 MiB; an agent relay connection has at most 64 open streams and a grant at most 4 (more fail with `resource_exhausted`), so the buffers of one connection stay below 256 MiB. Frames that carry no credit (request accepted, session end, error, stream close and stream open frames) bypass the credit window, so the control plane bounds them separately: one stream queue holds at most 4 such frames and at most 64 KiB of them in encoded bytes, which adds at most 64 KiB to the buffer of each stream. A compliant agent sends one request accepted frame and one terminal frame per stream, so it never reaches either limit, also when the caller is slow. Server streams send a `keepalive` event after 50 seconds without another event and rotate 13 minutes 50 seconds after the `stream_id` was allocated. The 30-second acceptance timer restarts only when the agent relay connection receives a large frame (at least 64 KiB encoded) of an open stream, because Connect delivers whole frames and the control plane cannot see a large frame in transit; this keeps a stream whose notice waits behind another stream's large frame alive, while keepalives and small frames cannot keep a stalled admission alive. Open: the timeout for a stalled caller that reads nothing. The control plane stops granting the agent credit for that stream, so the buffer stays bounded by 4 MiB, but the `stream_id` stays allocated until the RPC ends (at the latest at the rotation), because a blocked HTTP/2 write to the caller cannot be interrupted from the handler.
- Forwarding uses one bounded in-memory buffer for each stream. Toward the caller, the control plane grants the agent a credit window per stream that never exceeds the free space in that stream's buffer, and sends a relay window update as the caller consumes data, according to the [protos contract](protos-ownsand-api-contract.md#data-path-framing). A slow caller therefore slows only its own stream: the control plane never stops reading the shared agent connection, never drops a frame and never exceeds a buffer. An agent that sends beyond its window, or that queues more frames without credit than the per-stream limits above allow, breaks the protocol, and the control plane closes that agent relay connection, which ends every RPC routed on it with `unavailable`. An unknown frame kind on a stream still fails only that stream. Toward the agent, the control plane forwards request payload frames only within the credit window that the agent grants for each stream, and applies back-pressure to that caller's request body only. The control plane never writes relay frames to disk, to logs, to Postgres or to object storage. Record the per-connection buffer limit, the concurrency limits per agent connection and per grant, and the timeout after which the control plane ends a stream whose caller has read nothing (a stalled reader that holds a buffer and a `stream_id`) here before the relay implementation. The relay shares the Droplet's network, memory and CPU with the other servers on it, so these limits also bound the relay's share of the Droplet.
- A control plane restart or deployment ends every open relay RPC and agent relay connection. Callers continue with the resume rules, and agents reconnect while they hold a live grant.

### STUN

- The control plane answers STUN binding requests ([RFC 8489](https://www.rfc-editor.org/rfc/rfc8489.html)) on UDP port 3478 without authentication, at `stun:ownsand.api.delino.io:3478`. It does not offer TURN and does not relay media or data over UDP. STUN needs the public UDP port that [Runtime and Language](#runtime-and-language) requires from the deployment workflow; until the workflow publishes it, `ownsand-api` is not deployed.
- The STUN URL is control plane configuration, so a change of the STUN address needs no client release. Callers get the STUN server URLs from `DataPathService.GetIceServers` before they create an offer, and agents get them in a configuration message on the agent channel.
- Rate-limit STUN responses per source address. A binding response can be larger than its request ([RFC 8489 section 16.1.2](https://www.rfc-editor.org/rfc/rfc8489.html#section-16.1.2)), so the limit bounds the reflected traffic toward a spoofed address but does not remove it. Record the request and response byte budget per source address with the implementation.
- STUN implementation (recorded): `github.com/pion/stun/v3` `v3.1.7` decodes binding requests and builds the success response with `XOR-MAPPED-ADDRESS` (the datagram's source address) and `FINGERPRINT`; the same process serves HTTP and STUN. A binding request with comprehension-required attributes (types below 0x8000) that RFC 8489 does not define gets a binding error response with code 420 and `UNKNOWN-ATTRIBUTES` that lists exactly those types, plus `FINGERPRINT` ([RFC 8489 section 6.3.1](https://www.rfc-editor.org/rfc/rfc8489.html#section-6.3.1)); the byte budget below covers this response, and unknown optional attributes are ignored. Attributes after `MESSAGE-INTEGRITY` (or after `MESSAGE-INTEGRITY-SHA256` when `MESSAGE-INTEGRITY` is absent) are ignored too, except `MESSAGE-INTEGRITY-SHA256` and `FINGERPRINT` ([RFC 8489 section 9](https://www.rfc-editor.org/rfc/rfc8489.html#section-9)), so they never count as unknown. Other messages get no answer, including a datagram whose first two header bits are not zero ([RFC 8489 section 5](https://www.rfc-editor.org/rfc/rfc8489.html#section-5)); the server counts it as invalid. The listen address is `STUN_ADDR` (default `127.0.0.1:13478` for the standalone binary; the container image sets `STUN_ADDR=0.0.0.0:3478` so that a published UDP port reaches the listener, and an explicit `STUN_ADDR` overrides it). Recorded byte budget: responses to one source IP stay within 1024 bytes per second with a burst of 4096 bytes (`STUN_RATE_LIMIT_BYTES_PER_SECOND` and `STUN_RATE_LIMIT_BURST_BYTES`), about 25 binding responses per second sustained; requests over the budget are dropped. A `stun_stats` record every minute reports the request, response, rate-limited and invalid counts.

### Device removal and organization deletion

- `RemoveDevice` marks the device `removed` and invalidates its session credentials in the same transaction. The server closes the open channel after it sends a clean-up command. An offline agent receives the removal notice from `Authenticate` at its next connection. In both cases, the agent deletes its local sandboxes, snapshots and locally built images, then calls `AgentService.ConfirmRemoval` with a nonce from `CreateChallenge` signed by its device key, and only then deletes its device key and stops. A removed device may use `CreateChallenge` nonces only to get the removal notice from `Authenticate` and to call `ConfirmRemoval`; `Authenticate` returns only the removal notice to a removed device. The agent retries `ConfirmRemoval` after a lost response; after a success, the tombstone is gone and a retry gets an unknown-device answer, which the agent treats as a confirmed removal. A removed device can never get a session credential again.
- The non-terminal sandboxes of a removed device change to `deleted` with `DEVICE_REMOVED`, or with `ORGANIZATION_DELETED` when the removal is part of `DeleteOrganization`. Sandboxes that are already `deleted` or `failed` keep their state and end reason. The server deletes the records of snapshots that exist only on the removed device, and the templates that reference them. An exported snapshot is organization data: its record stays, without a local copy, until it is deleted or the organization is deleted.
- Removal tombstone: the server keeps the device ID, its public key, the `removed` state and the tombstone expiry (`expires_at`, 1 year after the removal commits) after removal, also after organization deletion, until `ConfirmRemoval` succeeds or 1 year after the removal, whichever comes first. Every lookup treats a tombstone whose `expires_at` has passed as absent, so the device becomes unknown at the deadline. The server schedules the deletion of each tombstone at its `expires_at`, and a daily job deletes tombstones whose scheduled deletion was missed. The tombstone holds no other data: the retained columns are `device_id`, `organization_id` (for organization-scoped reads), `public_key`, `state`, `create_time`, `remove_time` and `tombstone_expire_time`. Every other device column is inventory (name, host OS, architecture, agent version, update state and target, pending-idle time, capabilities, limits and vCPU overcommit, state epoch and last-seen time), and a database trigger on `devices` scrubs it on every insert or update of a row whose state is `removed`, so the removal transaction and any late writer (a capability report, a state report that merges built images, a heartbeat that records update fields) cannot keep or restore it. The scrub writes the neutral value of the initial column default: an empty string, `0`, `100` for `vcpu_overcommit_percent` and `NULL` for nullable columns. A migration scrubs the tombstones that exist before the trigger. The API shape does not change: for a tombstone, `RemoveDevice`, `GetDevice` and `ListDevices` return `state` `removed` with the retained identifiers and `create_time`, and blank `name`, `agent_version`, `capabilities`, limits (so `effective_vcpu_limit` is `0`) and update, last-seen and pending-idle fields; no caller can rely on the device name or limits of a removed device (the audit event keeps the device ID). It lets `Authenticate` return the removal notice to an agent that was offline during the removal. An agent that returns after its tombstone was deleted, and that never received the removal notice, is an unknown device; it keeps its data until an operator runs `ownsand-agent reset`. An agent that already received the notice and finished its clean-up treats an unknown-device answer to `ConfirmRemoval` as a confirmed removal, because a lost `ConfirmRemoval` response leaves no tombstone to confirm against.
- Billing: organization deletion keeps the usage counters and outbox rows of the organization until they are reported, and its debt stays on the billing account. `DeleteOrganization` and `TransferOwnership` remove the billing link of the organization, as [Billing links](#billing-links) describes.
- `DeleteOrganization` marks the organization deleted, revokes its API keys, enrollment tokens and invitations, removes its devices as above, stops issuing signed URLs for the organization, aborts its open multipart uploads, deletes its exported snapshots from R2 and then deletes its records, except the device removal tombstones, the audit events and the R2 clean-up job state. A clean-up job retries R2 deletions until they succeed and logs each failure. After every signed upload URL of the organization has expired (15 minutes after the last one was issued), the job deletes the organization prefix once more and then deletes its own state. Audit events of the organization stay for 90 days.
- Implementation: `DeleteOrganization` runs in one transaction. It removes every device of the organization like `RemoveDevice` (sandboxes end with `ORGANIZATION_DELETED`, one `SANDBOX_DELETED` audit event each, no `DEVICE_REMOVED` audit event), writes the `ORGANIZATION_DELETED` audit event and an organization revocation event, deletes the organization row, which deletes its other records through the foreign keys, and only then records an R2 clean-up job for the prefix `organizations/<organization_id>/` whose final sweep runs 15 minutes after the job is recorded. The job is recorded after the row deletion because the cascade waits for every signing transaction that holds a snapshot row of the organization (see the signing lock in [Storage](#storage)); the job's `final_sweep_after` is therefore never earlier than the expiry of any URL that was signed for the prefix. No signed URL can be issued for the organization after that commit, because its snapshot records are gone. The R2 clean-up worker that runs the job is added with the snapshot export implementation.
- Organization lock order: `DeleteOrganization` and `TransferOwnership` both decide on the `owner` role, so each takes the organization row lock (`SELECT 1 FROM organizations WHERE organization_id = $1 FOR UPDATE`, a query that returns a row) after a cheap unlocked authorization pre-check and before the authoritative owner check, and keeps it until the transaction commits or rolls back. The pre-check keeps API keys, non-members and non-owners from queueing on the lock; its result is not authoritative. If the organization no longer exists when the lock is granted, the RPC fails with `not_found` and writes nothing. The transaction then reads the memberships again (read committed gives that statement a fresh snapshot), so a transfer that committed first makes the former owner's deletion fail with `permission_denied` (no deletion audit event and no R2 clean-up job), and a deletion that committed first makes the transfer fail with `not_found`. No migration is needed. Other organization-level mutations that must serialize with deletion take the same row lock. The state report transaction takes `FOR KEY SHARE` on the organization row of the device (read without a lock beforehand) before its device row lock, so it never waits for a deletion while it holds a device or snapshot lock: a deletion removes the devices of the organization one at a time and locks the exported snapshots of each, which the report of another device locks too when it recovers a snapshot copy, and the report that holds its device row while it waits for such a snapshot would deadlock with the deletion that waits for that device row. A report that waits for a deletion finds no organization and changes nothing; a deletion that waits for a report starts after the report committed. `Enroll` follows the same order, organization before token: it reads the token's organization without a lock, takes `SELECT 1 FROM organizations WHERE organization_id = $1 FOR KEY SHARE`, then locks the token row (`FOR UPDATE`), reads it again and validates the hash, organization, expiry, revocation and use under both locks. `FOR KEY SHARE` lets enrollments of one organization run together and conflicts with the deletion's `FOR UPDATE`, so a deletion that waits for an enrollment lists the committed new device (a new statement snapshot under read committed) and removes it, and an enrollment that waits for a deletion finds no organization. An unknown token, a token whose organization is gone and a token that a deletion removed in the meantime all fail with the same `unauthenticated` invalid-token error and create no device. The deletion's cascade to the tokens follows the same organization-then-token order, so the two paths do not deadlock. `CreateSandbox`, `CreateSnapshot` and `CreateTemplate` follow the same order: each takes `SELECT 1 FROM organizations WHERE organization_id = $1 FOR KEY SHARE` (`not_found` when the organization is gone) at the start of its transaction, before it locks any device row (`CreateSandbox`, after the idempotency advisory lock and the in-transaction key lookup), the sandbox row (`CreateSnapshot`) or the snapshot row (`CreateTemplate`). The inserted sandbox, snapshot or template row takes the same share through its foreign key, so without the early lock the create would hold a child row while it waits for the deletion's `FOR UPDATE`, and the deletion would wait for that child row: a deadlock (`40P01`) and an internal error. With the order, a create that commits first is deleted with the organization, and a create that waits for a deletion fails with `not_found`. The creates of one organization share the lock and still run together; authorization, idempotency, error codes and audit events do not change, and no migration is needed. `AcceptInvitation` takes the same share (read without a lock beforehand) before it locks the invitation row and checks the invitation again under both locks, so a deletion that committed first gives the invitation `not_found`. `CreateInvitation`, `CreateEnrollmentToken`, `UpdateAgentVersionPolicy` (with or without a stored policy row) and `CreateApiKey` take the same `FOR KEY SHARE` in their transaction after the authorization and the input and billing checks, immediately before their insert, so a call that waits for a deletion in flight fails with `not_found` once the deletion commits, not with a foreign key violation (`23503`) that surfaced as an internal error. They lock no child row before the insert, so they cannot deadlock with the deletion, and a caller who is not a member or whose role does not allow the action still gets `not_found` or `permission_denied` before any wait; `CreateEnrollmentToken` still returns `resource_exhausted` for a blocked organization. Their audit and control events stay in the same transaction, and no migration is needed.

### Agent version policy

- The server holds one default target agent version per platform. It reads them, and the list of revoked versions, from the signed release manifest: it fetches the manifest from the release host, verifies the signature with the same public keys as the agent, and stores the releases in its agent releases table. The default target of a platform is the version that the manifest marks as default. The organization policy is `FOLLOW_DEFAULT`, `PIN` with a version, or `HOLD`. `UpdateAgentVersionPolicy` rejects a pin to a revoked version with `invalid_argument`. When the running or pinned version of a device is revoked, the server sends the default target version for that device, regardless of `HOLD` or `PIN`, and marks the target as a revocation recovery, so the agent installs it also when it is lower than the running version.
- The server sends the target version that results from the policy on the agent channel. The [agent contract](cmds-ownsand-agent-foundation.md#agent-updates) owns verification and the conditions for installation.
- Ordinary default targets never downgrade: under `FOLLOW_DEFAULT` (also when the organization has no stored policy) the server sends the platform default only when it is strictly newer than the running version of the device, ordered by the shared [`internal/semver`](repository-workflow-contract.md#shared-internal-go-packages) comparison that the agent uses (a version has three numeric components `MAJOR.MINOR.PATCH`, an optional leading `v` and an optional `-` pre-release suffix; `1.10.0` is newer than `1.9.0`, and `1.9.0-rc.1` is older than `1.9.0`). A default that is equal to or lower than the running version, for example after the operator rolled the default back, produces no update command. When the default or the running version does not parse, the server cannot order them, sends no ordinary default target and logs the warning `agent_update_skipped` with `device_id`, `reason` `version_not_comparable`, `default_version`, `running_version` and `error`. This check applies to no other target: a `PIN` target is sent as pinned, also when it is lower than the running version, without the revocation recovery mark; `HOLD` sends no automatic target while the running version is not revoked, but it withdraws a queued update (below); and a revocation recovery sends the default unconditionally with the recovery mark. The policy modes and the stored schema do not change (no database migration); the agent channel gains one command, `withdraw_agent_update`.
- Hold withdrawal (recorded decision): under `HOLD`, when no revocation recovery applies (neither the running version nor, for `PIN`, the pinned version is revoked), the server sends the `withdraw_agent_update` command (`WithdrawAgentUpdateCommand`, a separate command variant) instead of staying silent, because an agent may still hold a verified update that an earlier target queued and would install it when the device becomes idle. The evaluation runs when the channel reconciles (also after a reconnect or a lease handover) and when the policy changes. The channel handler and the control event processor can evaluate the same channel at the same time, so each evaluation, from reading the policy to queueing its command, runs under one per-channel lock; a decision that read an older policy never sends its command after the command of a newer decision. The server remembers the last update decision per channel, so it sends the withdrawal at most once per channel and `HOLD` period; a change back to `FOLLOW_DEFAULT` (or to `PIN`) then sends the valid target again, and a later `HOLD` sends a new withdrawal. A revoked running version under `HOLD` still gets the default target with the revocation recovery mark and no withdrawal. The withdrawal applies only to work that has not started: once the agent reports `INSTALLING` it answers `failed_precondition` and the installation completes (see the [agent contract](cmds-ownsand-agent-foundation.md#agent-updates)). Mixed versions: the server sends the command without capability negotiation. An agent from before the command answers `UNIMPLEMENTED`; the server only logs it (`agent_command_sent` and `agent_command_result` with `command` `withdraw_agent_update` and `result` `ERROR_CODE_UNIMPLEMENTED`) and does not retry, so such an agent keeps its queued update until it is upgraded, and the hold takes effect only for agents that support the command. A control plane from before the command never sends it, so an upgraded agent behaves as before.
- `ListDevices` reports each agent version and `AgentUpdateState`.
- The `agent_releases` table holds one row per version and platform (host OS and architecture) with its default and revoked flags; a partial unique index allows one default per platform. The manifest format and the release signing tool are open decisions of the [agent contract](cmds-ownsand-agent-foundation.md#agent-updates), so the manifest fetcher is not implemented and the table is filled only by operators and tests until that decision is recorded. `UpdateAgentVersionPolicy` rejects `PIN` without a version, a version for `FOLLOW_DEFAULT` or `HOLD`, an unspecified mode and a version that is revoked on any platform with `invalid_argument`; a pin to a version that the table does not know is accepted. A `pinned_version` that contains U+0000 is also rejected with `invalid_argument`, because PostgreSQL text cannot store it.

### Billing

Status: implemented: [metering](#metering), [usage reporting](#usage-outbox-and-reporting), the [status cache](#billing-status-cache), [enforcement](#enforcement), the [suspension](#suspension-and-resume), the [billing links](#billing-links), the `BillingService` handlers and the [billing metrics](#billing-metrics). The [project index](project-ownsand.md#billing) owns the prices, the meters and the enforcement phases. The [protos contract](protos-ownsand-api-contract.md#billing) owns the RPC classification, `BillingService` and the billing error reasons. The control plane reports usage to, and reads billing statuses from, the `UsageService` of the [`delino-accounts` protos contract](protos-delino-accounts-api-contract.md#services-and-scopes), with the service ID `OWNSAND`.

#### Metering

- Windows are aligned 5-minute UTC windows `[t, t + 5m)`. An event counts in the window of its time: a call when it ends, relay bytes when the relay writes them, and the R2 storage sample of each window.
- Calls: each public RPC that a Logto access token or an API key authenticated (for `AgentService.Enroll`, its enrollment token) and that ends with an OK status counts once for its organization, in the class of the [protos contract classification](protos-ownsand-api-contract.md#billing). A call that fails authentication, authorization, validation or billing enforcement, or that ends with any other status, does not count. A test covers every procedure of every generated `ownsandv1connect` service descriptor, so a new RPC fails the test until it is classified.
- Relay egress: the bytes of the Connect messages that the relay writes toward the caller for `Exec`, `AttachExec` and `ReadFile` (every response message, including the Connect envelope, the frame and event payloads and the relay `accepted` and `keepalive` events) and toward the agent on its relay connection for `WriteFile` request frames, for the organization of the relay grant. The TLS and HTTP/2 framing that the HTTP server and Caddy add is not visible to the process and is not counted. Exec request frames toward the agent and every byte that enters the Droplet are not counted.
- R2 storage: in each window, the control plane samples the stored bytes of the organization's exported snapshots (the part sizes of each snapshot in the export state `EXPORTED`) and counts them as byte-seconds: stored bytes × 300.
- Amounts: the quantity of each (organization, meter, window) is exact. The amount is computed once per window and rounded up (ceil) to a whole micro-USD, with a 128-bit intermediate so that no product overflows:

| Meter          | Quantity     | Amount in micro-USD                                                                                   |
| -------------- | ------------ | ----------------------------------------------------------------------------------------------------- |
| `RELAY_EGRESS` | bytes        | ceil(bytes × 90,000 / 2^30) ($0.09 per GiB)                                                           |
| `R2_STORAGE`   | byte-seconds | ceil(byte-seconds × 30,000 / (2^30 × 3,600 × 730)) ($0.03 per GiB-month, 730 GiB-hours per GiB-month) |
| `CLASS_A_RPC`  | calls        | ceil(calls × 45 / 10) ($4.50 per million calls)                                                       |
| `CLASS_B_RPC`  | calls        | ceil(calls × 36 / 100) ($0.36 per million calls)                                                      |

- A window with a quantity of 0 produces no report.
- Each instance adds its counts to shared counter rows in Postgres at least every 30 seconds and at a graceful shutdown. Known limit: a process that stops without a graceful shutdown loses the counts that it had not written yet (at most about 30 seconds of usage).
- Implementation of the call meter (recorded): the metering interceptor runs inside the logging interceptor and outside the authentication interceptor, also for the relay RPCs whose request gate authenticates first. After the handler returns OK, it counts the call for the organization that the handler authorized (the `organization_id` of the request; the key's organization for an API key; the token's organization for `Enroll`). A call with a device credential or without a principal (other than `Enroll`) is not counted, and an OK call of a billed class without an organization is logged as `billing_rpc_without_organization` and not counted. A server-streaming relay RPC counts when its stream ends with OK, which includes a rotation; a stream that the caller cancels does not count.
- Implementation of the relay egress meter (recorded): toward the caller, a response writer around the `RelayService` handler counts every byte that the Connect handler writes to the response body after `Exec`, `AttachExec` or `ReadFile` matched its grant, so the count includes compression, the codec and the end-of-stream message; a call that fails before it matched its grant writes no billable byte. Toward the agent, a writer around the agent relay connection counts the bytes of each response write, and the single relay writer bills the bytes that the send of a `WriteFile` request frame wrote. Each write counts in the window of its time.
- Implementation of the R2 storage sample (recorded): the lease holder samples the window that contains the current time at its first tick in the window (every 10 seconds). The `usage_storage_samples` row of the window makes the sample happen once across instances and lease handovers. Known limit: a window in which no instance held the lease is not sampled, so an outage of the lease holder of more than 5 minutes charges no storage for that time.
- Counts of sealed windows (recorded): a counter write that would add to a window that is already sealed adds to the oldest open window instead and logs `billing_usage_late_count_moved`, so a count is never lost and a sealed amount never changes. Counter writes hold the `usage_seal_state` row in share mode and the seal holds it for update, so the two never interleave. Known limit: when the outcome of a counter write is unknown (the connection broke during the commit), its retry can count those counts twice.

#### Usage outbox and reporting

- The lease holder seals a window 1 minute after it ends: it computes the amount of each (organization, meter, window) and writes it to the usage outbox with the key (organization, meter, window start). The amount of a row never changes after sealing, so a retry never reports a window with another amount.
- The reporter sends unreported rows every 5 minutes and after each seal, in `ReportUsage` batches of at most 500, with a Logto machine-to-machine access token (client credentials at `LOGTO_TOKEN_ENDPOINT`, resource `https://accounts.api.delino.io`, scope `accounts:report-usage`). The idempotency key is (`OWNSAND`, organization, meter, window start).
- A failed report is retried with exponential back-off from 1 second up to 5 minutes until `accounts-api` accepts it. A `duplicate` or `unattributed` result counts as accepted. Usage is never dropped: the outbox survives restarts, deployments, rollbacks and `accounts-api` outages.
- Outbox and counter rows have no foreign key to the organization, so organization deletion keeps them until they are reported. Retention (recorded): the janitor deletes an outbox row 35 days after `accounts-api` accepted it; an unreported row is never deleted. It deletes storage sample records after 1 day.
- Each accepted `ReportUsage` response hands its `statuses` to the [status cache](#billing-status-cache).
- Implementation (recorded): the lease holder seals and reports; the seal and the report pass check the lease every 10 seconds, so after a lease handover the new holder continues: an instance without the lease wakes the reporter every 10 seconds, so a new holder reports the due rows that an earlier holder left in the outbox within about one tick even when it seals no new window, and only an instance that holds the lease waits the 5-minute interval (or until the earliest next attempt time) between passes. The seal is idempotent across instances (it holds the `usage_seal_state` row for update), and a report that two instances send is a duplicate with the same amount. The reporter also runs a pass at the earliest next attempt time of an unreported row. It accepts a response only when it has one result per report, in request order, with the echoed key; any other response is a failed report. A `ReportUsage` batch is ordered by window start, organization and meter.
- Without a machine-to-machine credential (`LOGTO_TOKEN_ENDPOINT`, `ACCOUNTS_M2M_CLIENT_ID` and `ACCOUNTS_M2M_CLIENT_SECRET` unset, as in development and the existing end-to-end suite), metering, the seal and the outbox still run, and the reporter stays idle and logs `billing_usage_reporter_disabled` once at startup. A later process with the credential reports the rows. The token source caches each access token until 1 minute before it expires (half its lifetime when that is shorter) and requests a new one after `accounts-api` answers `unauthenticated`.

#### Billing status cache

- One row per organization holds the linked billing account ID (empty without a link), the phase (`ALLOWED`, `BLOCKED` or `SUSPENDED`), the reason, the block start, the suspension time, the last status sync time and the status sequence. A separate row holds the poll cursor.
- Without a link, the control plane decides the status itself: the organization is `BLOCKED` with `BILLING_ACCOUNT_REQUIRED` from its block start, and `SUSPENDED` 3 days later. The block start is the creation of the organization, the removal of its link, or, for organizations that exist when billing is deployed, the migration that adds billing. An organization that a still-running previous release creates during the deployment gets its unlinked status from a database trigger when the creation commits (see [Storage](#storage)), with the creation as the block start, or the migration that adds billing when the creation is earlier.
- With a link, the status comes from `accounts-api`: from each `ReportUsage` response and from `ListBillingStatusChanges`, which the lease holder polls every minute with the stored cursor. A successful poll also refreshes the sync time of every linked organization, because a poll without changes still proves that the cached status is current.
- When an organization in non-payment links a billing account that is also in non-payment, the control plane keeps the earlier block start, so a link does not restart the 3-day period.
- Gated RPCs read only the cache; they never call `accounts-api`.
- Fail open: during an `accounts-api` outage the control plane enforces the last cached status. When the sync time of a linked organization is more than 1 hour old, it lifts the RPC gates for the organization (the [enforcement](#enforcement) checks treat it as `ALLOWED`, and `GetBillingStatus` reports `ALLOWED`) and logs the warning `billing_status_stale`. Fail open never pauses or resumes sandboxes (see [Suspension and resume](#suspension-and-resume)). Metering and reporting continue.
- Implementation (recorded): `CreateOrganization` inserts the status row in its transaction. The stored phase is the confirmed status; a `BLOCKED` row whose block start is 3 days old counts as `SUSPENDED` at once for the gates, the suspension worker and the phase metric, and the lease holder stores the `SUSPENDED` phase within 10 seconds and logs it (`billing_status_changed` with `source` `time`). A status from `accounts-api` is applied only when its billing account equals the cached link and its sequence is not lower than the cached one (an equal sequence refreshes only the sync time); while the organization stays in non-payment, the cache keeps the earlier of the cached and the reported block start. The poll runs on the lease holder at its first step and every minute after it, in pages of 200; the cursor advances after each applied page, and after the last page the poll sets the sync time of every linked organization to the poll start time. A failed poll is retried at the next minute. The `billing_status_stale` warning is logged at most once per organization and instance every 10 minutes.
- Without the machine-to-machine credential, the poll and the pending unlinks stay idle and the server logs `billing_status_sync_disabled` once; the `BillingService` RPCs that need `accounts-api` fail with `unavailable`, so organizations without a link stay blocked. Development and end-to-end runs point the server at a local or fake `accounts-api` (see [Configuration](#configuration)).

#### Enforcement

| Phase       | Rejected RPCs                                                                                                                                                            | `BillingReason`                                          |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| `BLOCKED`   | `CreateSandbox`, `ResumeSandbox`, `CreateSnapshot`, `ExportSnapshot`, `CreateTemplate`, `CreateEnrollmentToken` and `AgentService.Enroll` (for the token's organization) | `ACCOUNT_REQUIRED` without a link, `BLOCKED` with a link |
| `SUSPENDED` | The `BLOCKED` list and `Exec`, `AttachExec`, `ReadFile`, `WriteFile`, `OpenSession` and `AuthorizeRelay`                                                                 | `SUSPENDED`                                              |

- The check runs after authentication and authorization and before any record changes. The call fails with `resource_exhausted` and the `ErrorDetail` of the [protos contract](protos-ownsand-api-contract.md#billing), whose message includes `https://accounts.delino.io`.
- Every other RPC stays allowed, including reads, deletions, `PauseSandbox`, every `BillingService` RPC and the agent channel. A relay stream or data channel session that is already open is not ended by a phase change; new relay grants and sessions are rejected while `SUSPENDED`.
- Implementation (recorded): each gated handler reads the cache row without a lock right after its authorization: `CreateSandbox` before the request validation and the idempotency lookup (a replay of an earlier create is rejected too), `ResumeSandbox` before the sandbox lookup, `CreateTemplate` and `CreateEnrollmentToken` inside their transactions, `Enroll` after the token validation under the organization and token locks and before the retry of a used token, `AuthorizeRelay` before its rate limit, and the four relay RPCs in the relay request gate after the grant's organization is authorized and before the relay stream opens. The message is `billing account required: …`, `billing blocked: …` or `billing suspended: …` and ends with `https://accounts.delino.io`; the `ErrorDetail` has the code `RESOURCE_EXHAUSTED` and no `retry_after`, in binary protobuf and in Connect JSON.

#### Suspension and resume

- The suspension worker acts only on confirmed statuses: a status that `accounts-api` reported for a linked organization, or the local status of an organization without a link. The fail-open rule lifts only the RPC gates; it never pauses or resumes sandboxes, so billing-paused sandboxes stay paused during an outage and resume only after a confirmed recovery.
- When an organization becomes `SUSPENDED`, the lease holder pauses each of its `RUNNING` sandboxes as `PauseSandbox` does and marks it as paused by billing (a persisted flag on the sandbox). It also pauses a sandbox that becomes `RUNNING` later while the organization stays suspended, for example after its device reconnects. It retries a pause that fails because the device is offline when the device reconnects.
- When `accounts-api` confirms that the organization is `ALLOWED` again (the balance is above 0 and the subscription is active), the lease holder resumes only the sandboxes that are marked as paused by billing and are still `PAUSED`, and clears the mark. Sandboxes that a caller paused stay paused. A sandbox that ended meanwhile is not resumed.
- Exported R2 snapshots are never deleted for non-payment; their storage keeps adding usage and debt.
- Implementation (recorded): the suspension worker runs on the lease holder every 10 seconds and after each status change that this instance committed, with at most 8 pause or resume commands in flight. It sets `sandboxes.paused_by_billing` before it sends the pause, so a crash between the pause and the mark cannot leave an unmarked billing pause; a sandbox whose device has no live agent channel waits for a later pass. A caller's `PauseSandbox` clears the mark when it sends its pause command, so the sandbox stays paused after the recovery. The worker clears the mark after a resumed sandbox is `RUNNING`; after a confirmed recovery, a marked sandbox that is not `PAUSED` any more (it ended, or it never paused) only loses the mark, and a marked `PAUSED` sandbox with a pending delete keeps it until it ends. Revalidation (recorded): a pass selects its targets once, and a target can wait for one of the 8 slots while a status change commits. The pause and the resume therefore check the confirmed status again before they act, with the same conditions that select the targets: the pause sets the mark only while the organization is `SUSPENDED` or `BLOCKED` for at least 3 days (one statement that checks the phase and sets the mark), and checks the phase again right before it sends the pause command; the resume checks right before it sends the resume command, and right before it clears the mark of a sandbox that is not `PAUSED` any more, that the organization is still `ALLOWED` and, for the command, that the sandbox is still marked, `PAUSED` and has no pending delete. Obsolete work is dropped without a command and without an error, so a recovery that commits before a queued pause reaches its slot leaves no mark and sends no pause, and a new suspension that commits before a queued resume sends no resume and keeps the mark. The check is not a lock: a status change that commits between the last check and the moment the command is queued is not suppressed. Such a pause is resumed by the next pass after the recovery, and a mark without a pause is removed by that pass (a marked sandbox that is not `PAUSED` loses its mark); a resume in that window is followed by a pause in the next pass. The phase policy and the agent protocol do not change. Logs: `billing_sandbox_marked`, `billing_sandbox_paused`, `billing_sandbox_resumed` and their `_failed`, `_deferred` and `_stale` (dropped by a recheck, debug level) variants, and `billing_sandbox_unmarked`.

#### Billing links

- `LinkBillingAccount` requires the organization `owner`. The control plane calls `LinkOrganization` with the caller's Logto user ID and the organization name as `organization_name` (the display name for the billing account members), and `accounts-api` checks that the user is `owner` or `admin` of the billing account. A `permission_denied`, `not_found` or `already_exists` answer is returned to the caller unchanged; an organization that is linked to another billing account must be unlinked first. After a successful link, the control plane updates the cache row from the status in the `LinkOrganization` response and returns the phase and the billing account name.
- `UnlinkBillingAccount` requires the organization `owner`. It calls `UnlinkOrganization`, and the organization becomes `BLOCKED` with `BILLING_ACCOUNT_REQUIRED`; the block starts at the unlink unless the organization was already in non-payment.
- `TransferOwnership` and `DeleteOrganization` remove the link in their own transaction and call `UnlinkOrganization`. When `accounts-api` is unavailable, the control plane records a pending unlink and retries it until it succeeds. After a transfer, the organization stays blocked until the new owner links a billing account.
- `ListLinkableBillingAccounts` calls `ListManageableBillingAccounts` with the caller's Logto user ID. `GetBillingUsage` fails with `failed_precondition` for an organization without a link and otherwise calls `GetOrganizationBilling`; usage that the control plane has not reported yet is not included. Both fail with `unavailable` while `accounts-api` is unavailable. `GetBillingStatus` reads only the cache, and every member and API key of the organization may call it.
- `BillingService` RPCs are never billed and never gated.
- Implementation (recorded): `LinkBillingAccount` and `UnlinkBillingAccount` run in one transaction that takes the organization row `FOR NO KEY UPDATE` after the unlocked authorization pre-check and before the authoritative owner check, then the status row `FOR UPDATE`, and calls `accounts-api` inside it. The mode serializes them with each other, with `TransferOwnership` and `DeleteOrganization` (`FOR UPDATE`) and with the pending unlinks, while the creates of the organization (`FOR KEY SHARE`) keep running. A link to another billing account than the cached link fails with `already_exists` before `accounts-api` is called. A pending unlink of the organization is sent first, so its retry never removes the new link; when it fails, the link fails with `unavailable`. `LinkOrganization` answers `permission_denied`, `not_found`, `already_exists` and `invalid_argument` reach the caller; every other failure of an `accounts-api` call is `unavailable` and logs `billing_accounts_call_failed`. `GetBillingUsage` maps a `not_found` answer to `failed_precondition`.
- Pending unlinks (recorded): `TransferOwnership` and `DeleteOrganization` remove the cached link and record a `billing_pending_unlinks` row in their transaction, and send the unlink once after the commit (10-second timeout). The lease holder retries due rows at every 10-second step of its status worker (not only at the 1-minute poll) with exponential back-off from 1 second to 5 minutes; each attempt takes the organization row `FOR NO KEY UPDATE` when the organization still exists. An `UnlinkBillingAccount` that `accounts-api` accepted deletes an older pending row of the organization.

## Storage

- PlanetScale Postgres tables (plus `instance_leases` for the lease, `control_events`, `r2_cleanup_jobs`, `snapshot_parts`, `snapshot_copies` and `sandbox_create_keys`): organizations, memberships, invitations, devices, device limits, enrollment tokens, API keys, sandboxes, snapshots, templates, agent version policies, agent releases and audit events.
- Retention of ended records: a `deleted` or `failed` sandbox record is kept for 30 days after it ends, and longer while it still reserves a macOS machine identifier, and then a daily job deletes it. `ListSandboxes` hides ended sandboxes unless the state filter asks for them. Every entity uses a UUID v7 primary key, and every organization-owned table has an `organization_id` column that every query filters on.
- Secret columns hold only SHA-256 hashes of enrollment tokens, invitation secrets, API keys and device session credentials, plus a short non-secret prefix for display. Devices store only their public key.
- `DeleteSnapshot` of a snapshot whose export has started (any export state other than `NOT_EXPORTED`), and the deletion of such a snapshot record by device removal or reconciliation, cancels the export, stops issuing signed URLs for it, aborts its open multipart uploads, deletes its objects under `organizations/<organization_id>/snapshots/<snapshot_id>/` and keeps its clean-up state until it deletes that prefix once more after every signed upload URL for it has expired.
- Implementation: each exported part is one object `organizations/<organization_id>/snapshots/<snapshot_id>/attempts/<attempt_id>/<part_number>` that the agent uploads with a presigned `PUT` (AWS Signature Version 4, path-style `<endpoint>/<bucket>/<key>`, region `auto`, 15 minutes), so no multipart upload exists to abort. The attempt ID is the command ID of the export attempt (see the export recovery record below). The export part size is `SNAPSHOT_PART_SIZE_BYTES` (default 64 MiB). A snapshot has at most 10,000 parts (the per-request limit stays), so the largest exportable snapshot is the part size times 10,000: about 48.8 GiB at 5 MiB and 625 GiB at the default. The agent counts the parts of the packed archive and rejects an export that needs more before it requests any upload URL, so no object is uploaded and the snapshot ends as `EXPORT_FAILED`. Upload URLs are issued only to the agent channel that owns the export attempt while the snapshot is `EXPORTING` (a replacement channel gets a `failed_precondition` grant without URLs) and address only the objects of that attempt; download URLs only to the agent channel that runs an import the server assigned for that snapshot, on a device of the organization with the snapshot's OS and architecture, while the snapshot is `EXPORTED`. A compatible device without an assigned import, a different device, a replacement channel of the importing device that got no new assignment, and the importing channel after its import ended get a `failed_precondition` grant without URLs, and the download signer is not called. Active imports: `importThenCreate` records each import in memory by channel (the connection, not only the device), snapshot and import command ID before it sends the command, and clears the record when the import result arrives, the command send fails, the import wait expires or the channel closes. When the import wait expires on a channel that stays connected, including while the import command or the following create command waits for room in a full outbound queue, the server sets the sandbox to `failed` with `CREATE_FAILED` and releases its capacity; a closed channel keeps reconnect reconciliation as the owner of the sandbox. A restart or a lease handover drops the records together with the channels. The server logs each denied request as `signed_url_denied` with `device_id`, `snapshot_id`, `operation` and `reason`, and never logs a signed URL or credential. Signing lock: the eligibility check and the signing of one signed URL request run in one transaction that reads the snapshot row with `FOR SHARE`; the transaction ends before the grant is written to the agent channel, so a slow channel never holds the lock. Snapshot deletion (`DeleteSnapshot`, device removal and reconciliation) and organization deletion delete the snapshot row first, which waits for a signer that holds the row, and record the R2 clean-up job after that deletion, so `final_sweep_after` (the job's recording time plus 15 minutes) is never earlier than the latest URL expiry. A request that loses the race finds no snapshot row and gets `not_found` and no URL. The signer takes no device or organization row lock, so it adds no lock order of its own; a transaction that locks a device row and snapshot rows keeps the device row first. The clean-up job is recorded only if the delete removed a row whose export had started (the `export_state` of the deleted row decides). The clean-up worker deletes a prefix by listing it (`ListObjectsV2`) and deleting each object, retries a failure with exponential backoff up to 1 hour and logs each failure, and deletes the prefix once more after `final_sweep_after` (15 minutes after the job started, when no URL for the prefix can be valid). Without R2 configuration, `ExportSnapshot` fails with `failed_precondition` and the clean-up jobs wait.
- Export recovery (recorded): the `ExportSnapshot` claim stores the command ID of the new attempt (`export_command_id`, which is also the attempt ID in the object keys) and the ID of the agent channel that receives the command (`export_channel_id`) on the snapshot row, in the same `UPDATE` that sets `EXPORTING`; the command is sent with that command ID. Both columns are nullable and are added by a forward migration; they are `NULL` for a snapshot that was never exported. The channel ID is a UUID v7 that the hub assigns to every registered channel (`Conn.ID`). The in-memory channel generation restarts with the process, so only the channel ID tells a channel from the one that owns an export across a control plane restart. Rules:
  - A state report fails the export of a listed snapshot that the reporting device holds when the snapshot is `EXPORTING` and its owner channel is not the reporting channel: the report sets `EXPORT_FAILED` under the snapshot row lock and records an R2 clean-up job for the abandoned attempt's prefix (`.../attempts/<attempt_id>/`). The same applies when the agent restarts, when a replacement channel takes over, and when the control plane restarts over the same database. A snapshot that the report does not list keeps the existing rule (its record is deleted with a clean-up job for the whole snapshot prefix).
  - A repeat `ExportSnapshot` for an `EXPORTING` snapshot returns `EXPORTING` and sends no command while the device's live channel is the owner (or the device has no live channel, so the owner cannot be judged). If the device's live channel is not the owner (the channel was replaced while the claim committed, so no state report of the new channel failed the export), the call fails the attempt like the state report and starts a new one. A repeat call for an `EXPORTED` snapshot returns it unchanged. A retry of an `EXPORT_FAILED` snapshot claims a new attempt and sends exactly one new export command.
  - `applyExportResult` applies a result only while the row is `EXPORTING` and `export_command_id` equals the result's command ID. A result of an earlier attempt (a late result after a retry) is logged as `export_result_stale` and changes neither the state nor the part manifest; the part manifest of an attempt is validated before it replaces the stored one. A result that carries an error, no parts or an invalid part (a part number outside `1..10000`, a SHA-256 that is not 32 bytes, a negative size, or a part number that appears more than once) fails the attempt with a clean-up job for its prefix, so the snapshot is never left `EXPORTING` because the manifest insert violated the part number key.
  - Result application retry: the record of the export command is removed before the result is applied, and an `EXPORTING` row whose owner channel is live is released by neither a repeat `ExportSnapshot` nor the owner's state report, so the server retries the application of an export result after a transient database error instead of dropping it. Transient errors are lost or refused connections, serialization failures and deadlocks, an unavailable lock, a server shutdown or restart, a read-only replica after a failover and resource exhaustion (SQLSTATE classes `08`, `40` and `53`, and `55P03`, `25006`, `57P01`, `57P02` and `57P03`, and connection-level network errors); every other error, such as a constraint violation, is permanent and is applied once and logged as `agent_command_result_apply_failed`. The channel read loop retries with a backoff that starts at 250 milliseconds and doubles up to 2 seconds, for at most 15 seconds (`Timing.ExportApplyRetryWindow` and `Timing.ExportApplyRetryBackoff`), which stays below the 45-second heartbeat timeout because the loop reads no heartbeat meanwhile; the retry also ends when the channel closes. Each attempt reruns the snapshot row lock and the command ID check, so the retry of an ambiguous commit, after a newer attempt or after the deletion of the snapshot stores at most one valid manifest or none. A recovered retry applies the original result on the same channel without a second export command and logs `export_result_apply_retry` per failed attempt and `export_result_apply_recovered`. When the window ends while the channel is still the device's current channel, the server logs `export_result_apply_abandoned` and closes the channel, so the state report of the replacement channel fails the attempt with a clean-up job as described above and an explicit `ExportSnapshot` retry sends a new command. Other command kinds are applied once as before.
  - A failed command send marks the attempt `EXPORT_FAILED` only while the row still names its command ID and is `EXPORTING`, so a send failure of an earlier attempt cannot change a retry. The update uses a bounded database context (5 seconds) that does not depend on the request context, because a canceled request is a common cause of the send failure; without it the attempt would stay `EXPORTING` and block retries while the channel is live. The update retries after a transient database error (the same classification as the result application retry above) with the same backoff (`Timing.ExportApplyRetryBackoff`) inside that 5-second budget (`Timing.ExportFailTimeout`), logging `export_fail_transition_retry` per failed attempt; an update that affects no row (a newer attempt, a deleted snapshot, or an attempt that a state report already failed) counts as resolved, changes no other row and closes no channel, and the outcome is logged as `export_failed` with `applied` and `attempts`. When a permanent error or the end of the budget leaves the attempt `EXPORTING` while the channel that was meant to receive the command is still the device's current channel, the server closes that channel, because no repeat `ExportSnapshot` and no state report of the owner would release the claim while it stays live: the state report of the replacement channel then fails the abandoned attempt (`owner_channel_replaced`) and an explicit retry sends a new command. The server never closes a channel that is no longer the current channel of its device. The response stays `unavailable`, and the failure is logged as `export_fail_transition_failed` (an error, with the old attempt's `command_id`, `attempts` and `channel_closed`). No clean-up job is recorded on this direct path, because the agent never received the command and no upload URL exists for the attempt.
  - Downloads resolve the part keys from the `export_command_id` of the `EXPORTED` row (the successful attempt).
  - `DeleteSnapshot`, device removal, reconciliation and organization deletion keep recording the whole-snapshot (or organization) prefix, which covers every attempt. The abandoned-attempt jobs reuse the same clean-up worker and its sweeps; their `final_sweep_after` is computed under the snapshot row lock, after the last upload URL of the attempt could be signed.
  - Logs: `export_started` (`snapshot_id`, `command_id`, `channel_id`), `export_completed`, `export_result_apply_retry`, `export_result_apply_recovered`, `export_result_apply_abandoned`, `export_failed` (`snapshot_id`, `command_id`, `reason`: `owner_channel_replaced`, `send_failed`, `no_parts`, `invalid_part` or `agent_error_<code>`), `export_fail_transition_retry`, `export_fail_transition_failed` and `export_result_stale`; `signed_url_denied` also carries `channel_id`. No RPC or agent message changes.
  - A `CreateSnapshot` whose command send fails before it is queued (queue full, request canceled, channel closed) moves the committed `CREATING` record to `FAILED` with the same bounded database context, and only while it is still `CREATING`. The RPC returns `unavailable`. The outcome is logged as `snapshot_create_send_failed` (a warning, with `applied`) or `snapshot_create_fail_transition_failed` (an error).
- Local copies (recorded): every deletion of a snapshot record (`DeleteSnapshot`, reconciliation and device removal) writes a `snapshot deleted` control event for each device that holds a copy (the original device and the `snapshot_copies` rows), and the lease holder sends the `delete_snapshot` agent command to each connected device. The result is only logged. A state report that lists a snapshot without a record gets the command again, because the server creates every snapshot record before its create or import command; this also covers a device that was offline, a deletion that the agent could not finish before it restarted, and an older agent that answered `UNIMPLEMENTED`. Copy recovery: the only other writer of a `snapshot_copies` row is the in-memory result of the import command, which a lost channel or a restart loses, so the state report transaction also creates the row (`ON CONFLICT DO NOTHING`, so a repeated report leaves one row) for each listed copy in `READY` state of a snapshot that is `READY` and `EXPORTED`, belongs to the device's organization, matches the device's host OS and architecture, and whose original copy is not on the reporting device. A `REMOVED` device gets no row. The transaction takes the organization lock `FOR KEY SHARE` and then locks the device row (see the device lock order above), then the sandbox rows of the device, then the candidate and own snapshot rows of the device in one statement in `snapshot_id` order; the snapshot row lock conflicts with the lock of `DeleteSnapshot`, so the two orders are consistent: when the report commits first, the deletion reads the recovered row and records a `snapshot deleted` event for the device, and when the deletion commits first, the report finds no record, creates no row and the unknown-snapshot rule above sends the stale-copy delete command. A tracked copy that the report omits still loses its row. The `agent_state_report` log line carries `recovered_copies`, the number of rows that the report created. The recovery needs no schema change.
- Exported snapshots use Cloudflare R2 with signed URLs, according to the repository default. Object keys start with `organizations/<organization_id>/snapshots/<snapshot_id>/`, so organization deletion can remove them by prefix. Signed upload and download URLs expire after 15 minutes and are issued only to the agent channel that runs the export or to which the server assigned the import (see the implementation record above); the agent asks for fresh part URLs on the agent channel while the export or import runs. The snapshot record stores the SHA-256 of each exported part; the import command carries these hashes over the agent channel, so the importing agent never trusts hashes stored in R2.
- Migration tool (recorded decision): [goose](https://github.com/pressly/goose) (`github.com/pressly/goose/v3`), the same tool as `accounts-api`, with SQL migrations embedded from `internal/db/migrations/`. Each file is named `<version>_<name>.sql` (zero-padded version) and has a `-- +goose Up` section and no down section; a statement that contains a semicolon inside its body (a `$$` function body) stays between `-- +goose StatementBegin` and `-- +goose StatementEnd`. goose applies each pending file once, in version order, in its own transaction while it holds a Postgres session advisory lock with the key `0x6f776e73616e64`, so instances that start together apply each migration once. goose records the applied versions in `goose_db_version`. Migrations are forward-only and are never edited after they reach `main`; a change adds a new file. The server applies pending migrations at startup unless `RUN_MIGRATIONS=false`. Because the old container keeps serving while the new one starts during a deployment, every migration must stay compatible with the code of the previous release (expand first, contract in a later release).
- Migration sessions (recorded): goose writes the application time of a migration into `goose_db_version.tstamp`, a `timestamp` column without a time zone, from `now()` of the session. The server opens the migration sessions with their own connections (not the request pool) and `TimeZone=UTC`, so the column holds UTC whatever the database time zone is, and a migration reads it with `tstamp AT TIME ZONE 'UTC'`.
- Switch from the earlier runner (recorded): until goose, an embedded runner in `internal/db` applied the same files and recorded them in `schema_migrations`. No deployed database used it, so the server has no step that copies that history; a local database that the earlier runner created must be dropped and created again. The files got their goose annotations once with this change, and migration `0009` reads the time of `0008` from `goose_db_version` instead of `schema_migrations`; the SQL is otherwise unchanged.
- Open decision: the backup policy. Record it here, and add the database stage to the [deployment workflow](repository-workflow-contract.md#deployment-workflow), before the first deployment; the service is not deployed yet.
- Billing tables: migration `0007_billing_usage.sql` adds `usage_counters` (organization, meter, window start and quantity), `usage_outbox` (organization, meter, window start, quantity, amount in micro-USD, seal time, attempts, next attempt time and report time; the primary key is the organization, the meter and the window start), `usage_seal_state` (one row with the start of the oldest open window) and `usage_storage_samples` (one row per sampled window). `meter` stores the `BillingMeter` value. Usage counters and outbox rows have no foreign key to the organization. Migration `0008_billing_status.sql` adds `organization_billing` (one row per organization with `ON DELETE CASCADE`: the linked billing account or `NULL`, the `BillingPhase` and `BillingReason` values, the block start, the suspension time, the status sync time and the status sequence; it inserts a row for every existing organization, `BLOCKED` with `ACCOUNT_REQUIRED` from the migration time), `billing_status_cursor` (one row with the poll cursor and the last poll time), `billing_pending_unlinks` (organization, former billing account, attempts and next attempt time; no foreign key, so a deleted organization keeps its row until the unlink succeeds) and the `sandboxes.paused_by_billing` flag.
- Legacy-writer compatibility (recorded): migration `0009_billing_status_legacy_writers.sql` keeps every organization linkable while the previous release, which inserts an organization without a status row, still runs during a rolling deployment (the backfill of `0008` is only a snapshot, and the billing-aware code treats an organization without a status row as missing, so such an organization could never link a billing account). In one transaction it takes `LOCK TABLE organizations IN SHARE ROW EXCLUSIVE MODE` (it waits for the inserts that began earlier, and later inserts wait until it commits, so no insert falls between the backfill and the trigger), installs the deferred constraint trigger `organizations_billing_status_insert` (`AFTER INSERT ON organizations`, `DEFERRABLE INITIALLY DEFERRED`) and backfills the organizations that still have no status row. At the commit of the inserting transaction the trigger inserts the unlinked status (`BLOCKED` with `ACCOUNT_REQUIRED`, the block start is the `create_time` of the organization, the suspension time is 72 hours later) with `ON CONFLICT (organization_id) DO NOTHING` and only while the organization still exists, so the row that a billing-aware writer inserts in its transaction wins, and an organization that is created and deleted in one transaction gets no row. The backfill starts the block at the later of the `create_time` of the organization and the application time of migration `0008` in `goose_db_version` (`tstamp` read as UTC), because billing was not enforced earlier; it leaves every existing row, link and timestamp unchanged. Recovery rule: an organization without a status row can only exist when a writer bypassed the trigger, and the only recovery is a new migration that inserts the missing rows the same way; the application never creates the row on demand. The trigger and its function `create_organization_billing_status` stay until a later contract migration drops them, which is allowed once no release before `0008` can run against the database.
- Enum columns store the numeric values of the protobuf enums. Device removal tombstones and audit events have no foreign key to the organization, so they survive organization deletion; every other organization-owned table references the organization with `ON DELETE CASCADE`, and organization deletion deletes those records in its transaction.
- Scrub trigger numbering (recorded): the device tombstone scrub is migration `0005`; it hard-codes the numeric value of `DEVICE_STATE_REMOVED` (`3`, see [the protobuf contract](protos-ownsand-api-contract.md)) because a migration is immutable and independent of generated code. A change of that enum value needs a new migration.
- Retention jobs run every hour on every instance (each statement is idempotent), except the control event job: consumed nonces, device sessions and create idempotency keys after their expiry, device tombstones after `expires_at` (lookups already treat them as absent), audit events after 90 days, ended sandboxes 30 days after they ended unless they still reserve a macOS machine identifier, control events after 1 hour once the lease holder has processed them (the control event job runs only on the instance that holds the lease and has a processed cursor, and deletes only events with a `delivery_id` up to that in-memory cursor; the cursor is not persisted, and an unprocessed event is never deleted by its age), usage outbox rows 35 days after `accounts-api` accepted them, and storage sample records after 1 day. The hourly run covers both the scheduled tombstone deletion and the daily catch-up job of [Device removal and organization deletion](#device-removal-and-organization-deletion).

## Security

- Accept only the credentials in [Authentication](#authentication). Never accept Logto ID tokens.
- Return each secret once in the response that issues it. Never store or log a secret in plain text. A relay grant ID is not a secret: an identical `AuthorizeRelay` retry with the same `authorization_id`, after the caller's authorization is checked again, returns the same grant ID while its grant is admittable, because the caller may have lost the first response.
- Isolate organizations in every query, as [Authorization](#authorization) requires.
- `AgentService` RPCs carry no bearer credential except `Channel` (and `RelayAgentService.Connect`, which also uses the `osd_` credential): `Enroll` authenticates with the enrollment token in the request body, `CreateChallenge` names a device ID and returns a nonce, `Authenticate` and `ConfirmRemoval` authenticate with a nonce signed by the device key (the signed message is the purpose label `ownsand-authenticate` or `ownsand-confirm-removal` followed by the nonce, and the server checks that the label matches the RPC), and `Channel` uses the `osd_` credential. `CreateChallenge` returns a nonce for any device ID without checking that the device exists. `Authenticate` and `ConfirmRemoval` tell an unknown, removed or enrolled device apart, which shows anonymous callers whether a device ID exists. The server normalizes the device ID to lowercase text before it builds the per-device rate-limit key (`challenge:`, `authenticate:` or `confirm-removal:` plus the ID), so every spelling of one device ID shares one bucket per RPC. This exposure is accepted: device IDs are random UUID v7 values that only members and API keys of the organization can list, the calls are rate-limited, and an agent whose clean-up finished needs the unknown-device answer. Nonces are stateless: a nonce is the device ID, a random value and an expiry, authenticated with the nonce key, a secret that every instance shares (rotate it with an overlap that accepts the previous key for 60 seconds), so `CreateChallenge` stores nothing and unauthenticated callers cannot use up a device's nonces. The server records a nonce only when `Authenticate` or `ConfirmRemoval` consumes it, until its expiry, to reject replays.
- Rate-limit `Enroll`, `CreateChallenge`, `Authenticate`, `ConfirmRemoval`, `AcceptInvitation` and API key validation failures per device ID, per credential prefix and per client address. Rate-limit relay RPCs that fail the grant check in [Relay authentication](#relay-authentication) the same way: an unknown or non-admittable grant, a grant of another principal and a request that does not match the grant all take a token from one per-caller bucket (see the recorded limits below). The Caddy reverse proxy on the Droplet terminates the HTTP connection, so the client address of an HTTP request comes from a header that Caddy sets; record the header and the rule that trusts only the value that Caddy appends in the change that adds rate limiting, after it is verified with the Caddy route of `ownsand-api`. Until then, limits are keyed per device ID and prefix only. STUN receives UDP directly, so its client address is the datagram's source address; the UDP port publication must keep the client's source address, because a STUN binding response that reports another address is wrong. Record the limits here with the implementation.
- Recorded limits (in-memory token buckets, which are service-wide because the service runs as one replica; rejected calls fail with `resource_exhausted` and the retry delay in `ErrorDetail.retry_after`): `CreateChallenge`, `Authenticate` and `ConfirmRemoval` 10 calls per device ID per minute with a burst of 10; `Enroll` the same per enrollment token display prefix; `AcceptInvitation` the same per invitation display prefix and per user; API key validation failures the same per key display prefix (only failures take tokens, and a prefix without tokens is rejected before validation); and, when the request has a client address (see the client address rule below), 120 calls per client address per minute with a burst of 60 across these RPCs. That is one token bucket per client address, keyed by the address alone and shared by the device RPCs, `AcceptInvitation` and API key validation failures: a call of any of these categories takes a token from the same balance, and a valid API key validation takes none.
- Recorded client address rule: the server resolves a typed client address mode once at startup and logs it as `client_address_mode` on the `server_started` event. `TRUST_PROXY_CLIENT_ADDRESS=true` selects the verified proxy mode (`verified_proxy`), which takes precedence: the client address is the last entry of the last `X-Forwarded-For` header, which is the value that Caddy appends; other entries and earlier headers are client-controlled and ignored. A missing or invalid final value gives no client address and never falls back to the TCP peer, because the peer is the proxy. Otherwise `ALLOW_DIRECT_CLIENT_ADDRESS=true` selects the direct mode (`direct`): the client address is the TCP peer host and forwarded headers are ignored. With neither setting (the default, mode `none`), requests have no client address, so the per-client bucket does not apply, while the per-device, per-user and per-prefix limits still do. Keep both settings `false` in production until the Caddy route of `ownsand-api` is verified to append the header, then set `TRUST_PROXY_CLIENT_ADDRESS=true`; until then, production limits are keyed per device ID and prefix only, because every TCP peer is the proxy. The development launcher (`pnpm --filter ownsand-api dev`), the Go test environment and the end-to-end harness opt in to the direct mode; a direct launch of the built binary must set `ALLOW_DIRECT_CLIENT_ADDRESS=true` to opt in.
- Billing: the control plane never calls Paddle, never stores payment data and keeps no balance. It sends `delino-accounts` only organization IDs, organization names (as `organization_name` of a link), Logto user IDs, meters, windows, quantities and amounts. The machine-to-machine client secret and access tokens are never logged; a failed token request logs only the HTTP status and the OAuth error code. The fail-open rule of the [status cache](#billing-status-cache) lets an organization use OwnSand for longer than its billing status allows during an `accounts-api` outage of more than 1 hour; metering continues, so the usage is still charged.
- Sandbox content never passes through the agent channel and is never stored by the control plane. On the relay, the control plane forwards it in process memory only, according to [Relay streams](#relay-streams).
- Relay grants bind a grant ID to one sandbox, one operation, its request digest, one principal and one agent channel. The control plane and the Caddy reverse proxy, which terminates TLS, can read and change relayed content (exec output, environment values in exec requests and file chunks). The request digest prevents them from running another command or using another guest path than the caller authorized, but the contracts trust the control plane and the Droplet for the confidentiality and integrity of the relayed content itself. The agent rejects a relay stream open for an expired, revoked or unknown grant, and a relay frame of any other sandbox or operation. A stream that opened before the grant expired continues until its stream deadline unless a revocation or the loss of the agent channel ends it first.
- The Droplet's clock is synchronized with NTP, because grant admission and the relay stream limits compare times with fixed tolerances. The Droplet hardening, its SSH access, its operating system update policy and its DigitalOcean Cloud Firewall rules (including the inbound UDP 3478 rule for STUN) are owned by the [deployment workflow](repository-workflow-contract.md#deployment-workflow).
- Configuration and secrets (database URL, R2 credentials, release manifest settings, the nonce key, the STUN rate limit, the metrics listen address, the OTLP endpoint and headers, and the Logto machine-to-machine credential for the `delino-accounts` API) come from the service's env file on the Droplet (`/srv/delino/env/ownsand-api.env`), which maintainers keep, according to the [environment contract](repository-environment-contract.md) and the [deployment workflow](repository-workflow-contract.md#deployment-workflow). The deployment sets `ADDR`. Their values never appear in `.env.example`; it lists their names with placeholders only, according to the environment contract.

## Logging

- Structured JSON logs on standard output with `log/slog`, like `accounts-api`. A non-empty `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` also sends the records at or above `LOG_LEVEL` through the `otelslog` log bridge to the OpenTelemetry SDK, which exports them over OTLP/HTTP. `server_started` records whether the OTLP export of metrics (`otlp_metrics_export`) and logs (`otlp_logs_export`) is on.
- One record per RPC with the procedure, principal kind, principal ID (Logto `sub`, API key ID or device ID), organization ID, Connect code and duration.
- Agent channel events: enrollment, authentication result, connect, disconnect, offline transition, state report counts, command ID and result.
- Data path events: session ID or relay grant ID, sandbox ID, signaled transport, grant acknowledgement result and duration, and the failed enqueue of a relay grant (`relay_grant_enqueue_failed`).
- Relay: one record per relay RPC with the procedure, grant ID, principal kind and ID, organization ID, sandbox ID, device ID, Connect code, frame counts, byte counts and duration. Agent relay connection events: device ID, connect, disconnect, replacement and the number of RPCs that each disconnect ended.
- STUN: aggregate request and rate-limit counts, not one record per request.
- Billing: structured `billing_*` records. Implemented with metering: `billing_usage_sealed` (each sealed outbox row with its quantity and `amount_usd_micros`), `billing_usage_reported` (each accepted row with its `result`, `billing_account_id` and attempt), `billing_usage_report_failed` (each row of a failed report with the attempt, the Connect `code` and the `next_attempt_time`), `billing_usage_late_count_moved`, `billing_storage_sample_taken`, `billing_usage_flush_failed`, `billing_usage_seal_failed`, `billing_usage_reporter_disabled` and `billing_rpc_without_organization`; each carries `organization_id`, `meter` (the stable meter ID) and `window_start` when it concerns one row. Implemented with the status cache and enforcement: `billing_status_changed` (each phase or link change with `source` `report`, `poll`, `link`, `unlink`, `transfer`, `delete` or `time`, `from_phase`, `to_phase`, `linked`, `reason`, `billing_account_id` and `blocked_since`), `billing_rpc_rejected` (`phase` and `reason`), `billing_status_stale`, `billing_status_poll_failed`, `billing_status_apply_failed`, `billing_status_advance_failed`, `billing_status_sync_disabled`, `billing_status_missing`, `billing_accounts_call_failed` (`op` and `code`), `billing_unlink_failed`, `billing_unlink_confirmed`, `billing_unlink_pending`, `billing_sandbox_marked`, `billing_sandbox_paused`, `billing_sandbox_pause_failed`, `billing_sandbox_pause_deferred`, `billing_sandbox_resumed`, `billing_sandbox_resume_failed`, `billing_sandbox_resume_deferred`, `billing_sandbox_unmarked` and `billing_enforcement_failed`. They carry the relevant fields among `organization_id`, `billing_account_id`, `meter`, `window_start`, `sandbox_id` and the result. They never carry tokens or the machine-to-machine secret.
- Never log tokens, API keys, enrollment tokens, invitation secrets, device session credentials, signed URLs, SDP bodies, relay frames, exec commands, environment values, exec output or file contents.

- Required export recovery tests: a fake agent that accepts the export command and withholds the result, with the channel replaced and with the control plane recreated over the same database (`testenv.Env.Restart`), must end `EXPORT_FAILED`, and an explicit retry must send exactly one new command and reach `EXPORTED` with the new part manifest; a late result of the first attempt must leave the retry's state and part manifest alone while the two attempts' upload URLs address different objects and download URLs address the successful attempt's objects; a repeat `ExportSnapshot` and a state report on the owning channel send no command. A send failure of an export (a saturated channel with a request that ends first) with a transient database fault injected into the failure update must end `EXPORT_FAILED` on the same open channel after retries and a repeat export must send exactly one command; with a permanent fault or an exhausted budget it must close the owning channel so that the replacement channel's state report fails the attempt, record no clean-up job on the direct path, and a zero-row update (a newer attempt, a deleted snapshot, an attempt that a state report already failed) must change no other row and close no channel. The end-to-end suite kills the agent and the control plane in the middle of an export and checks the same recovery with the real agent.
- Required relay tests:
  - Relay authentication: a relay RPC with the credential of another principal, of a revoked API key or of a user whose membership ended; an unknown, expired (also within and past the 30-second admission tolerance) or revoked grant ID; a mismatched organization, sandbox, operation kind or operation ID; the failed grant check limit shared by the unknown grant, principal mismatch and request mismatch rejections, with its retry delay, a second principal with its own bucket, and valid grants that take no token; `RelayAgentService.Connect` with an expired `osd_` credential, with the credential of a removed device, of another device, or for a device without a current agent channel; and closing the relay connection when its agent channel closes.
  - Agent relay connections: replacement, the 10-second wait for an agent relay connection (also a cold connection that registers within it), the 90-second idle close, a single frame that takes longer than 90 seconds to arrive while bytes keep arriving, echo replies, the supported frame kinds exchanged when `Connect` opens, and closing an agent relay connection that sends beyond its credit window.
  - Streams and flow control: stream keepalive, stream rotation with an OK status before 14 minutes, relay stream close frames and `stream_id` non-reuse, per-stream credit windows with one slow and one fast caller on the same device, an exec request upload longer than 30 seconds followed by immediate acceptance, a stalled request upload that ends with `deadline_exceeded` after 5 minutes, which for each of `Exec`, `AttachExec`, `ReadFile` and `WriteFile` leaves the agent with a stream open frame, a stream close frame and no request frame, a slow upload within the budget that succeeds, a `WriteFile` call whose upload and wait for the result share one budget, a grant rejection from the headers alone before the body arrives, a complete upload whose forwarding waits for agent credit and ends after 5 minutes, an acceptance timer that keepalives and small frames do not extend and that a large frame from the agent extends, with a concurrent `ReadFile` and `Exec`, a relay stream close sent for the acceptance timeout, the upload deadline and a request that does not match the grant, a `WriteFile` call that runs longer than 30 seconds, a `ReadFile` that the agent accepts at once and whose first chunk arrives after 30 seconds, the 5-minute `WriteFile` call deadline including the agent's result, session-end frames, and forwarding without persistence.
  - STUN binding responses with the client's source address, STUN rate limiting, and relay log redaction.

## Dependencies and Integrations

- Upstream: Logto shared tenant, PlanetScale Postgres, Cloudflare R2, the `delino-accounts` API (billing usage reports, the status sync, links and billing reads; and member display names).
- Telemetry dependencies: the OpenTelemetry Go modules recorded in the [accounts-api contract](servers-accounts-api-foundation.md#dependencies-and-integrations). `govulncheck ./servers/...` reported no vulnerability in code that the server calls when they were added (only the unresolved GO-2026-5932 below).
- Billing dependency: `github.com/prometheus/client_golang` `v1.25.0` for the internal metrics listener (since the move to the OpenTelemetry SDK, it only serves the registry of the Prometheus exporter), with its module dependencies `github.com/prometheus/client_model` `v0.6.3`, `github.com/prometheus/common` `v0.72.0`, `github.com/prometheus/procfs` `v0.22.0`, `github.com/beorn7/perks` `v1.0.1`, `github.com/cespare/xxhash/v2` `v2.3.0` and `github.com/munnerz/goautoneg`. `govulncheck ./servers/ownsand-api/...` reported no vulnerability in code that the server calls when it was added (only the unresolved GO-2026-5932 of `golang.org/x/crypto` below, which the server does not call). The `delino-accounts` token source uses only the Go standard library. The `delino-accounts` client uses the generated bindings of the [`delino-accounts` protos contract](protos-delino-accounts-api-contract.md) and the existing Connect runtime.
- Migration dependency: `github.com/pressly/goose/v3` `v3.30.1` (with its `lock` and `database` packages), already in the root Go module for `accounts-api` ([API server contract](servers-accounts-api-foundation.md#dependencies-and-integrations)). The server also uses `github.com/jackc/pgx/v5/stdlib` from the existing `pgx` module to give goose a `database/sql` handle. The `govulncheck` result for the server is in the pull request that added goose to it.
- Go dependencies (approved by the owner with the OwnSand implementation, each version released at least two weeks before it was pinned; `govulncheck ./servers/ownsand-api/...` reported no vulnerabilities when they were added): `github.com/jackc/pgx/v5` `v5.12.0` (Postgres driver and pool, with its `github.com/jackc/puddle/v2` `v2.2.3`, `pgpassfile`, `pgservicefile`, `golang.org/x/sync` and `golang.org/x/text` dependencies) and `github.com/go-jose/go-jose/v4` `v4.1.9` (JWS and JSON Web Key Set parsing for Logto access tokens), and with the relay `github.com/pion/stun/v3` `v3.1.7` (STUN messages; it brings `pion/dtls/v3` `v3.1.5`, `pion/transport/v4` `v4.1.0`, `pion/logging` and `wlynxg/anet` as module dependencies). `golang.org/x/crypto` was raised to `v0.58.0` (with `x/sys` `v0.49.0`, `x/text` `v0.43.0` and `x/sync` `v0.24.0`) to fix the advisories that govulncheck reported for `v0.48.0`. Unresolved: GO-2026-5932 in `golang.org/x/crypto` `v0.58.0` is fixed only in a newer pseudo-version and in `v0.59.0`, which was less than two weeks old; govulncheck reports that the server code does not call it. Raise `x/crypto` when a fixed release is old enough. Connect and protobuf are recorded in the [protos contract](protos-ownsand-api-contract.md#runtime-and-language).
- Platform: the shared DigitalOcean Droplet, its Caddy reverse proxy and DigitalOcean Cloud Firewalls, according to the [deployment workflow](repository-workflow-contract.md#deployment-workflow).
- Downstream: [device agent](cmds-ownsand-agent-foundation.md) (agent channel, relay connections and STUN), [CLI](cmds-ownsand-cli-foundation.md), [web console](apps-ownsand-console-foundation.md) and [SDKs](packages-ownsand-sdk-foundation.md).
- Protocol schemas: [protos contract](protos-ownsand-api-contract.md).
- `delino-accounts` billing: the control plane is a consuming service of the `delino-accounts` usage-report API (it calls every `UsageService` RPC: `ReportUsage`, `ListBillingStatusChanges`, `LinkOrganization`, `UnlinkOrganization`, `ListManageableBillingAccounts` and `GetOrganizationBilling`), as recorded in the [API server contract](servers-accounts-api-foundation.md#users-and-operators) and described in [Billing](#billing). Deploy `accounts-api` with the billing APIs before the `ownsand-api` revision that reports usage.
- `delino-accounts`: the console links to `https://accounts.delino.io`. The control plane reads member display names from the `delino-accounts` API server-to-server with its own Logto machine-to-machine credential, only for members of the organization in the `ListMembers` request, as recorded in the [API server contract](servers-accounts-api-foundation.md#users-and-operators). When that API is unavailable, `ListMembers` returns the members without display names instead of failing. The control plane does not store the profiles. The `delino-accounts` API has no display name RPC yet, so the control plane has no client for it and `ListMembers` returns empty display names until both exist.
