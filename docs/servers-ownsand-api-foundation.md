# servers-ownsand-api foundation contract

## Scope

This contract owns the `ownsand-api` control plane of [`ownsand`](project-ownsand.md) at `servers/ownsand-api/`. The control plane is the system of record for organizations, memberships, devices, credentials, sandbox records, snapshot records, templates, agent version policies and audit events. It schedules sandboxes, sends commands to device agents, signals peer-to-peer data channels, authorizes and forwards the relay fallback of the data path, and serves STUN.

The control plane does not run sandboxes and stores no sandbox content. Sandbox content passes through it only on the [relay](#relay), in process memory. It is licensed under `FSL-1.1-ALv2` according to the [license contract](repository-license-contract.md).

Layout, following the `accounts-api` server conventions:

- `servers/ownsand-api/cmd/ownsand-api/`: process entry point.
- `servers/ownsand-api/internal/`: configuration, HTTP and Connect handlers, authentication, authorization, scheduler, agent channel, data path signaling, relay grants, the agent relay connection registry, frame forwarding, the STUN listener, storage and audit packages. Storage is `internal/store` (with the embedded migrations in `internal/store/migrations/`), the authorization matrix is `internal/authz`, the single-instance lease is `internal/lease` and the retention and R2 clean-up jobs are `internal/jobs`.
- `servers/ownsand-api/package.json`, `turbo.json`, `.env.example`, `Dockerfile` and `scripts/dev.mjs`: workspace wiring, the container image and the development launcher. `package.json` declares no `deploy` field yet: according to `servers/AGENTS.md`, a server that needs a public port other than its reverse proxy route declares none until the deployment workflow supports that port (UDP 3478 for STUN). Add the field (`target` `droplet`, `service` `ownsand-api`, `hostname` `ownsand.api.delino.io`) in the change that adds the UDP port publication to the deployment workflow.

## Runtime and Language

- Language: Go in the root module `github.com/delinoio/mono`. Import path: `github.com/delinoio/mono/servers/ownsand-api/...`.
- Runtime: one long-running process. It serves HTTP with Connect handlers on the `ADDR` that the deployment sets, and STUN on UDP port 3478. Logging: `log/slog`.
- Replicas: the service runs as exactly one replica. The agent channels, the agent relay connections, open sessions and pending and revocable relay grants live in process memory, so a request on another replica could not reach the agent. Record the cross-replica routing in this contract before the service runs more than one replica. A deployment briefly runs the new container next to the old one, so an instance accepts agent channels and runs heartbeat timers and state transitions only while it holds a lease row in Postgres. The old instance releases the lease when it starts to drain and closes all its agent channels and agent relay connections at that moment, which ends their sessions, relay grants and relay RPCs; agents reconnect to the new instance. The new instance waits for the lease before it accepts agent channels, and then treats every `online` device as not heard from, so the 45-second offline rule applies to devices that do not reconnect. The scheduler, commands, `OpenSession`, `AuthorizeRelay`, the `RelayService` RPCs and `RelayAgentService.Connect` need a live agent channel in the serving instance: a device without one is not eligible, and a command, session, relay authorization, relay RPC or relay connection for it fails with `unavailable` before any record is created. `DeleteSandbox` is exempt: any instance records the pending delete, and the lease holder sends the delete command when the device reconnects. The lease expires 30 seconds after its last renewal, and the holder renews it every 10 seconds, so a crashed holder loses it.
- HTTP serving: the process serves HTTP/1.1 and HTTP/2 without TLS (h2c) on `ADDR` with the Go standard library (`http.Server.Protocols` with unencrypted HTTP/2 enabled), so it needs no `golang.org/x/net` dependency. It sets no server-wide read or write timeout, because the agent channel, the agent relay connection and the relay server streams are long-lived and the handlers enforce their own limits; `ReadHeaderTimeout` is 10 seconds and `IdleTimeout` 120 seconds.
- Lease: the lease is the row `ownsand-api` of the `service_leases` table. An instance takes it when it is free, expired or already its own, compares expiry with the database clock, renews it every 10 seconds with a 30-second expiry and deletes it when it starts to drain.
- Deployment target: a Docker container on the shared DigitalOcean Droplet, deployed by the [deployment workflow](repository-workflow-contract.md#deployment-workflow) with the `deploy` target `droplet`, like `accounts-api`. Production origin: `https://ownsand.api.delino.io`. STUN URL: `stun:ownsand.api.delino.io:3478`.
- TLS and proxy: the Caddy reverse proxy on the Droplet terminates TLS for `ownsand.api.delino.io` with a Let's Encrypt certificate and proxies to the container. The Caddy route of `ownsand-api` must proxy HTTP/2 without TLS (h2c) to the container, because `RelayAgentService.Connect` is a bidirectional stream and needs HTTP/2 from end to end. The route must also not end a request or a stream before the limits of this contract end it (the 14-minute relay stream limit, the 5-minute `WriteFile` call deadline and the long-lived agent channel and relay connection). Verify both properties of the route and record them in this contract before the relay implementation.
- The DNS record of `ownsand.api.delino.io` points directly at the Droplet and must not go through an HTTP proxy (for example, a proxied Cloudflare record), because the STUN service needs the Droplet address and the relay connection needs HTTP/2 from end to end.
- Public RPCs are unary or server-streaming according to the [project transport rule](project-ownsand.md#protocol-and-api). Only the device-facing `RelayAgentService.Connect` and the [agent channel](#agent-channel) (`AgentService.Channel`) are long-lived bidirectional streams.
- Public UDP: STUN needs inbound UDP port 3478 on the Droplet. The [deployment workflow](repository-workflow-contract.md#deployment-workflow) publishes only HTTP through Caddy (TCP 80 and 443) today and publishes no other host port. The workflow contract must add the publication of UDP port 3478 for `ownsand-api` and the matching DigitalOcean Cloud Firewall rule before the first deployment of `ownsand-api`.
- Deployment status and open items: `ownsand-api` is not deployed. Before its first deployment: (1) the [deployment workflow](repository-workflow-contract.md#deployment-workflow) must publish UDP 3478 for STUN, keeping the client source address, and the DigitalOcean Cloud Firewall must allow it; (2) the Caddy route must be changed and verified to proxy h2c to the container and to keep long-lived streams (the workflow contract says Caddy forwards plain HTTP/1.1 to the containers today, which cannot carry `AgentService.Channel` or `RelayAgentService.Connect`); (3) `package.json` must then declare the `deploy` field; (4) the database stage and the backup policy must be decided (see [Storage](#storage)); (5) the Logto API resource, its `ownsand:access` permission and the application registrations must be created; (6) the client address header for rate limits must be verified with the Caddy route. Until then this contract describes an implementation that was validated only with in-process tests.
- Database: PlanetScale Postgres, according to the repository defaults. The driver is `github.com/jackc/pgx/v5` `v5.12.0` (owner-approved), with its pool `pgxpool`; `govulncheck` reported no vulnerabilities when it was added.
- Development ports: `127.0.0.1:8300` for HTTP (h2c, so that the bidirectional relay connection works without a proxy), recorded in the [environment contract](repository-environment-contract.md), and `127.0.0.1:3478` (`planned`) for STUN over UDP, which the change that adds the STUN listener records there.

## Interfaces and Contracts

- Business APIs: the public services, `AgentService`, and the relay services `RelayService` and `RelayAgentService` of the [protos contract](protos-ownsand-api-contract.md).
- Operational endpoint: `GET /healthz` without authentication returns `200` with `{"status":"ok"}` while the process can serve HTTP requests.
- Browser access: CORS allows only `https://ownsand.delino.io` in production and the console's loopback development origin locally.

### Authentication

The server accepts three kinds of credentials in the `Authorization: Bearer` header. It selects the validator from the credential shape and never tries a second validator after the first one rejects the credential.

| Principal kind | Credential                                                        | Validation                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `user`         | Logto access token (JWT)                                          | Signature, issuer, expiry, audience `https://ownsand.api.delino.io` and required scopes, according to the [authentication contract](repository-auth-contract.md#token-validation). ID tokens are rejected. Only end-user tokens become a `user` principal: no machine-to-machine application gets an OwnSand scope, and the change that adds token validation records the claim check that rejects machine-to-machine tokens. |
| `api_key`      | `osk_` followed by the secret                                     | SHA-256 hash lookup with a constant-time comparison. The key must not be revoked, and its organization must not be deleted.                                                                                                                                                                                                                                                                                                   |
| `device`       | `osd_` device session credential from `AgentService.Authenticate` | SHA-256 hash lookup with a constant-time comparison. Accepted only to open the agent channel and the agent relay connection (`RelayAgentService.Connect`) of its own device. The credential must not be expired, and the device must not be removed.                                                                                                                                                                          |

- The Logto API resource indicator is `https://ownsand.api.delino.io` (`OWNSAND_API_RESOURCE`). Every `user` RPC requires the single scope (Logto permission) `ownsand:access` of that resource; OwnSand's own roles then authorize the action. The console, CLI and SDK request that scope. The Logto application registrations (the console single-page application and the CLI native application) and the creation of the API resource and its permission in the shared tenant are not done yet; record their application IDs here when they are registered.
- Token validation uses only the Go standard library: the server reads the issuer `<LOGTO_ENDPOINT>/oidc` and the JWKS from `<LOGTO_ENDPOINT>/oidc/jwks` (cached, refreshed on an unknown key ID at most every 30 seconds and at least every 10 minutes), accepts the RS, PS, ES and EdDSA signature algorithms of the JWKS keys and rejects `none` and every other algorithm, allows 30 seconds of clock skew for `exp` and `nbf`, and rejects a token whose `typ` header is present and not `at+jwt`. Machine-to-machine check: Logto sets `sub` to the application ID in a machine-to-machine access token, so the server rejects a token that has no `client_id` claim or whose `sub` equals its `client_id`. Without `LOGTO_ENDPOINT`, the server rejects every Logto token.
- The API key exception is recorded in the [project index](project-ownsand.md#identity-and-access). API keys are not accepted on `OrganizationService`, `MemberService`, `ApiKeyService` or these `DeviceService` RPCs: `CreateEnrollmentToken`, `ListEnrollmentTokens`, `RevokeEnrollmentToken`, `UpdateDeviceLimits`, `RemoveDevice` and `UpdateAgentVersionPolicy`. For an RPC that takes an `organization_id`, the server first checks that the key belongs to that organization and returns `not_found` otherwise; only a key of that organization gets `permission_denied` from this restriction.
- Secret formats: API keys `osk_`, enrollment tokens `ose_`, invitation secrets `osi_` and device session credentials `osd_`, each followed by 32 random bytes from a cryptographically secure source in unpadded base64url. The prefixes let secret scanners and the credential selector recognize them. A relay grant ID is not a credential (see [Relay authentication](#relay-authentication)).

### Authorization

The server authorizes every RPC that takes an `organization_id` as follows. For a `user` principal, it loads the caller's membership in that organization and checks the role against the matrix below; a user without a membership gets `not_found`. For an `api_key` principal, it checks that the key belongs to that organization and checks the API key column of the matrix; a key of another organization gets `not_found`. In both cases, it loads every target entity with that organization in the query. A request for an entity of another organization returns `not_found`, not `permission_denied`, so that callers cannot discover entities of other organizations.

Three public RPCs take no `organization_id`. They accept only a Logto access token (`user` principal) and need no membership; an `api_key` or `device` credential on them fails with `permission_denied`:

- `CreateOrganization` creates the organization and the caller's `owner` membership in one transaction.
- `ListOrganizations` returns only the organizations in which the caller has a membership.
- `AcceptInvitation` takes the organization from the validated invitation, not from the request. An expired, revoked or used invitation fails with `not_found` and the same message. When the caller already has a membership in the organization, the call fails with `already_exists` and the invitation stays unused. The caller's Logto token is valid in this case, so the server does not use `unauthenticated`.

| Action                                                                                                              | `owner` | `admin` | `member` | API key |
| ------------------------------------------------------------------------------------------------------------------- | ------- | ------- | -------- | ------- |
| Delete the organization, transfer ownership                                                                         | yes     | no      | no       | no      |
| Invitations, member roles, removal of another member                                                                | yes     | yes     | no       | no      |
| Remove the caller's own membership (leave the organization)                                                         | no      | yes     | yes      | no      |
| Enrollment tokens, device removal, device limits, agent version policy changes                                      | yes     | yes     | no       | no      |
| API keys                                                                                                            | yes     | yes     | no       | no      |
| Read the organization, list members                                                                                 | yes     | yes     | yes      | no      |
| List and read devices and the agent version policy                                                                  | yes     | yes     | yes      | yes     |
| Sandboxes, exec, files, pause, resume, snapshots, templates, data path sessions, relay authorization and relay RPCs | yes     | yes     | yes      | yes     |

- An organization has exactly one `owner`. An `admin` cannot change the role of the `owner` or remove the `owner`, and cannot grant `owner`. An `admin` can change the role of another `admin` and remove another `admin`. Only `TransferOwnership` makes another existing member the `owner`.
- Sandboxes, snapshots and templates belong to the organization, not to the member or API key that created them. Every member and API key of the organization can use them. The record keeps the creating principal for audit.
- Invitations are one-time secrets that expire after 7 days. `AcceptInvitation` creates the membership for the signed-in Logto user. OwnSand does not look up users by email address.

### Agent channel

- Enrollment: an admin creates an enrollment token with an expiry of at most 24 hours. The agent generates an Ed25519 key pair locally and calls `AgentService.Enroll` with the token and the public key. The server consumes the token in the same transaction that creates the device, so a token enrolls at most one device. Until the token's expiry, the server keeps the hash of the consumed token with the device ID and public key: a retry of `Enroll` with the same token and the same public key returns the same `device_id`, so an agent that lost the first response can continue. A retry with another public key fails like a used token. An expired, revoked or used token fails with `unauthenticated` and the same message, so that the response does not show which condition failed.
- Session: the agent calls `CreateChallenge`, signs the nonce with its private key and calls `Authenticate`. The nonce is single-use and expires after 60 seconds. The device session credential is needed only to open the channel and expires after 15 minutes. An open channel stays valid until it closes; the server checks the device state at each heartbeat and closes the channel when the device is removed. Before each new connection, the agent gets a new credential with `CreateChallenge` and `Authenticate`.
- Transport (owner decision): a Connect bidirectional stream, `AgentService.Channel` at `https://ownsand.api.delino.io/delino.ownsand.v1.AgentService/Channel`, over HTTP/2 (h2c from Caddy to the container), authenticated with `Authorization: Bearer osd_...`. There is no WebSocket transport in this version, so a device behind a proxy that allows only HTTP/1.1 cannot connect. Timeouts: the 45-second heartbeat rule below; the channel has no other deadline. The verification of the Caddy route is still open (see [Runtime and Language](#runtime-and-language)).
- Message order when the channel opens (the simplest reading of the contracts): the server sends the configuration message first; the agent sends an optional capability report and then its full state report; the server applies the report, acknowledges it with its `report_id` and only then marks the device `online`. The server acknowledges heartbeats from the first message on. Only the lease holder accepts channels, and only after its control event consumer has recorded its starting position; other instances answer `unavailable`.
- A new channel of a device replaces the older one, which the server closes; only the current generation's close or heartbeat timeout marks the device `offline`. On the lease holder, a sweeper marks `online` devices `offline` when no heartbeat arrived for 45 seconds and they have no channel on this instance, which applies the 45-second rule after a lease handover.
- Revision order: the current epoch of a device is the `state_epoch` of its latest `Authenticate`. A reported revision of another epoch is older than the stored one; a reported revision of the current epoch is newer than a stored revision of another epoch, and otherwise the counters decide.
- Control events: every instance writes them to the `control_events` table in the transaction of the change; the lease holder polls the table every 500 milliseconds and starts after the newest event when it takes the lease, because the reconnection state reports and the configuration sent at channel open cover what earlier events carried. Control events are deleted after 24 hours.
- Command waits: `PauseSandbox`, `ResumeSandbox` and `DeleteSandbox` wait up to 60 seconds for the agent; a command result with an `error_code` fails the RPC with that Connect code. Any `error_code` on a create command result is treated as a rejection before a VM exists (`CREATE_FAILED`).
- Heartbeat: the agent sends a heartbeat every 15 seconds, and the server answers each heartbeat on the same channel with a heartbeat acknowledgement that carries the heartbeat's sequence number. The agent resets its 45-second channel-loss timer only for an acknowledgement on the current channel. Each agent channel of a device gets a new channel generation when it opens, and the server applies heartbeat, close, timeout and state report events only for the current generation. The server marks the device `offline` when the current channel closes or when no heartbeat arrives on it for 45 seconds; an event of an older channel never changes the device state. At that point, the device's sandboxes in `creating`, `running`, `paused` or `deleting` state are shown as `unreachable` with their `last_known_state`. Sandboxes in `deleted` or `failed` state keep their state and end reason. The server stores reachability separately from the agent-reported state and revision: `unreachable` is the reported state of a non-terminal sandbox on an offline device, and the stored agent state and revision do not change. Capacity, the macOS limits and the identifier reservation count a sandbox by its stored agent state.
- Sandbox updates: each sandbox has a revision that the agent increases with every local change. Updates, state report entries and acknowledgements carry the revision, and the server applies an update only when its revision is higher than the stored one; it acknowledges a stale retry without applying it. A reconnection state report entry with the same revision as the stored one confirms the stored state and restores reachability; an entry with a lower revision is ignored. The agent sends a sandbox update for every local state change, including a TTL expiry or a lost VM, with the new state and, for an ended sandbox, its end reason. It also sends one when activity moves the idle deadline, at most once per minute for each sandbox, because peer-to-peer activity does not pass through the control plane and the agent, not the relay, tracks activity. The server stores the reported state and deadline and acknowledges each update; the agent resends an update until it is acknowledged.
- Device limits: the server sends the device limits in the configuration message when the channel opens and again after each `UpdateDeviceLimits`. Any instance that commits a change of device limits or of the agent version policy also writes a configuration event to the Postgres event table that revocations use, and the lease holder sends the new configuration or target version to the agent. Each create command also carries the limits that the scheduler used, and the agent checks the create against the stricter of these and its last configuration. Because the configuration event can reach the lease holder after a create that the scheduler placed with the new limits, the server sends the current configuration on the agent channel right before each create command, so the agent never checks a create against older limits than the command's.
- Device eligibility after reconnection: the device becomes `online`, and eligible for scheduling, only after the server has applied its reconnection state report.
- Reconnection: after `Authenticate`, the agent sends a full state report. The report lists every sandbox that the agent has a record of, including sandboxes that ended while the device was offline, with their end reasons. The server reconciles the stored state of each sandbox and snapshot of the device with the report, subject to the revision rule in [sandbox updates](#agent-channel). The revision is a pair of the agent's state epoch and a counter: the agent creates a new epoch when it starts with a lost or reset state directory and sends it with `Authenticate`, and a revision from a newer epoch is always newer. State changes that the server makes itself (`creating` at create, and the reconciliation results below) keep the stored revision and are replaced by the next agent revision. A delete request is stored as a pending delete apart from the agent state, and agent revisions never clear it: the server shows the sandbox as `deleting` while the delete is pending and the device is online, and as `unreachable` with `last_known_state` `DELETING` while the device is offline, sends the delete command again after every state report or sandbox update that still lists the sandbox as not deleted, and completes the delete when the agent reports that the VM is gone: the sandbox is reported as deleted, reported as `failed` (for example with `LOST_ON_DEVICE`), or no longer listed. A sandbox that ended as `failed` keeps that state and end reason. The delete command is idempotent on the agent. The transaction that records a pending delete also writes a delete event to the Postgres event table, so the lease holder sends the delete command to a connected device at once, from whichever instance accepted the request. The agent handles the commands of one sandbox in order: a delete for a sandbox whose create is still running cancels the create, or waits for it and then deletes the VM, and a delete that arrives before its create leaves a delete marker that makes the agent reject that create. The agent reports the sandbox as deleted only when no VM exists and no create for it can start.
- Lost agent state: the epoch rule covers an agent that lost its sandbox records but kept its identity file. Before an agent reports a new epoch, it lists the VMs that its hypervisor still runs for it (each VM is tagged with its sandbox ID) and either recovers their records and TTL deadlines or stops and deletes them, so the report never omits a running VM and the server never releases capacity that a running VM uses. An agent that lost its device ID or private key cannot authenticate as the old device; it must enroll again as a new device. The old device stays `offline`, and an admin removes it, which starts the [removal tombstone](#device-removal-and-organization-deletion) rules. A sandbox whose state is `deleting`, or that is `unreachable` with `last_known_state` `deleting`, and that the report does not list changes to `deleted` with the end reason of its delete request. Any other sandbox that the server knows in a non-terminal state but the report does not list changes to `failed` with `LOST_ON_DEVICE`. A snapshot of the device that the report does not list loses its local copy: the server deletes its record, and the templates that reference it, unless it is exported, in which case the record stays without a local copy. The agent keeps the record of an ended sandbox until the server acknowledges a sandbox update or a state report that contains its terminal revision, so a sandbox that ended while the device was offline keeps its real end reason. `deleted` and `failed` are absorbing: the server never changes a sandbox that is already in one of them, whatever the revision of a later report, so its end reason stays. When a later report still lists a live VM for such a sandbox, the server keeps the terminal state and sends a delete command for the VM.
- Lost VMs: when the agent has a record of a sandbox in `creating`, `running` or `paused` state but its VM no longer exists (for example, after a host reboot, or after an agent restart, which stops every VM on every host OS), the agent reports the sandbox as `failed` with `LOST_ON_DEVICE` and releases its resources.
- Commands: the server sends create, delete, pause, resume, snapshot, export, import, clean-up and update commands with a command ID. The agent reports each result with that command ID. A command for an offline device fails immediately with `unavailable`; the server does not queue it. `DeleteSandbox` is the exception: on an offline device it records the pending delete and succeeds, and the server sends the delete command when the device reconnects.

### Scheduler

- A device is eligible for a create request when it is `online`, its host OS and architecture match the filters, it supports the requested guest (see [the agent capabilities](cmds-ownsand-agent-foundation.md#isolation)), its agent version is not revoked, its update state is not `INSTALLING`, it has not been in `PENDING_IDLE` for more than 24 hours (the server stores the time of the first `PENDING_IDLE` report as `pending_idle_since` in the device record, so the clock survives restarts and lease handovers) (so that a busy device can drain and install an update; running sandboxes end at their `max_ttl`, at most 7 days), the requested source is ready on it (for `base_image`, the device reports that base image as built; for a snapshot or template, see below), and its free capacity covers the requested resources. Free capacity is the device limit minus the resources of its `creating`, `running`, `paused` and `deleting` sandboxes. The requested disk must also fit in the free disk that the device last reported, minus the disk of `creating` sandboxes that it has not reported yet; the agent checks the free disk again before it creates or imports a disk and rejects the command with `resource_exhausted` when it does not fit. A `deleting` sandbox releases its resources only when the agent confirms the deletion, or when a state report shows that the sandbox is gone.
- A newly enrolled device has zero limits, so it is not eligible until an admin sets its limits with `UpdateDeviceLimits`.
- `UpdateDeviceLimits` may set limits below the current allocation. The existing sandboxes keep running, and the device gets no new sandbox until its free capacity covers a request.
- For a `MACOS` guest, the device must also be an Apple silicon Mac with fewer than two macOS guests in `creating`, `running`, `paused` or `deleting` state, counted from the server's own sandbox records. This is the Virtualization.framework limit; Linux guests do not count toward it. A sandbox from a macOS snapshot or template also needs a device that reports support for the snapshot's macOS hardware model.
- macOS machine identifier: a macOS sandbox created from a snapshot or template uses the machine identifier of the VM that the snapshot was taken from. Until the macOS runtime change verifies that a restored disk boots with a new identifier, the scheduler reserves that identifier: a device is not eligible when any sandbox in `creating`, `running`, `paused` or `deleting` state, or in `unreachable` state with one of these as its `last_known_state`, uses the same identifier and whose `max_ttl` deadline has not passed (the agent enforces `max_ttl` also while it is offline, so the VM is gone after it). This includes the source VM and sandboxes from other snapshots of the same source, on any device. A sandbox that ended because its device was removed keeps its identifier reserved until `ConfirmRemoval` succeeds for that device or its `max_ttl` deadline passes, because the VM can still run on the offline device.
- The sandbox architecture is the device architecture. OwnSand does not emulate another architecture.
- The same rule picks the error code with or without `device_id`: a request fails with `unavailable` when a device could run it after a transient condition ends (offline, no live channel in the serving instance, capacity that running sandboxes hold, update state `INSTALLING`, `PENDING_IDLE` or `REVOKED_PENDING_IDLE` (a revoked version clears itself when the running sandboxes end and the update installs), or a macOS identifier that a running sandbox holds), and with `failed_precondition` when it exceeds the device limits themselves or breaks the OS, architecture, capability or source rules. Without `device_id`, the request gets `unavailable` when at least one enrolled device fails only transient conditions, and `failed_precondition` otherwise.
- Among eligible devices, the scheduler selects the one with the lowest allocated share of its most constrained resource, and breaks ties by the lowest `device_id`. Implementation (`internal/scheduler`): the share is the largest of allocated vCPU, memory and disk divided by the device limit; a device where memory state can restore is preferred before the share; permanent conditions are evaluated before transient ones, so a device that breaks both gives `failed_precondition`; a free disk shortage is transient. The reservation transaction locks the organization's candidate device rows in `device_id` order.
- With an explicit `device_id`, the scheduler checks the same conditions and does not select another device. It fails with the code that the error-code rule in this section gives for that device.
- A sandbox from a snapshot or template runs on the device that holds the snapshot locally, or on any eligible device with the same OS and architecture when the snapshot is exported. Memory state restores only on the device that took the snapshot, and only when the request's `vcpu_count`, `memory_mib` and network mode equal the snapshot's values, because the saved state includes the virtual devices. These conditions only allow an attempt: when the hypervisor reports that it cannot read the saved state (for example, after a save format change), the agent boots the snapshot disk cold, and the sandbox reports which restore path it used. In every other case the sandbox restores the disk and boots cold, until a runtime contract defines a compatibility check for memory state on other devices (for example, the CPU model for Firecracker-class snapshots). The scheduler prefers the snapshot device when memory state can restore there.
- The scheduler reserves the resources in the same transaction that creates the sandbox record, so two concurrent requests cannot both use the last free capacity of a device.
- A create first looks up its `idempotency_key`, right after authorization and before placement or the live-channel check: a known key with the same parameters returns the original sandbox even when its device is offline now.
- When the agent rejects a create command before it makes a VM (for example, with `resource_exhausted` after its free disk check), the server sets the sandbox to `failed` with `CREATE_FAILED` and releases its reservation. A lost command result is not a rejection: the sandbox stays `creating` until the agent reports it, because the VM may exist.

### TTL

- `idle_ttl` and `max_ttl` are required. The server stores both deadlines and sends them to the agent with the create command. The agent owns the idle deadline after that and reports changes as described in [Agent channel](#agent-channel).
- The agent enforces both TTLs locally, so they apply even when the device is offline. When a TTL ends, the agent deletes the sandbox and reports `deleted` with `IDLE_TTL_EXPIRED` or `MAX_TTL_EXPIRED`: the reason of the earlier deadline, and `MAX_TTL_EXPIRED` when both deadlines are equal. The agent applies the same rule when it enforces passed deadlines after a restart.
- `max_ttl` counts from creation and includes paused time.
- The idle clock restarts at each exec start, exec end, file operation and resume. Opening a data path session is not activity. A running exec keeps the sandbox active. The idle clock does not run while the sandbox is paused.

### Data path signaling and relay

- `OpenSession` and `AuthorizeRelay` first register as pending on the lease holder, then authorize the caller, so a revocation event that the lease holder processes in between ends the pending session or grant as well. `OpenSession` then forwards the caller's SDP offer to the agent on the agent channel with the session ID, the principal and an absolute expiry, and returns the agent's answer. `AuthorizeRelay` instead sends a relay grant to the agent and returns the grant ID after the agent acknowledges the grant (see [relay authorization](#data-path-signaling-and-relay) below). The agent accepts the data channel only for a DTLS fingerprint that arrived in an offer from the control plane, and serves relay frames only for a grant ID of a grant that arrived from the control plane. The control plane therefore authenticates both peers of every data channel and authorizes every relay stream.
- Session end: the agent enforces the session limits on the peer-to-peer path, because peer-to-peer frames do not pass through the control plane. A session ends at the first of these events: 15 minutes without frames and without an open exec or file request (an open request counts as activity, and the agent sends a keepalive exec event at least every 60 seconds while an exec produces no output); the absolute expiry, 1 hour after `OpenSession`; a revocation message from the control plane; or the loss of the agent channel that signaled the session, which the agent detects when the channel closes or when it gets no heartbeat acknowledgement for 45 seconds. The control plane sends a revocation message for every open session and every revocable relay grant (see the grant terms below) of an API key when the key is revoked, of a user in an organization when that user's membership in that organization ends, and of a sandbox when the sandbox is deleted. Any instance can process the revoking request, so it writes a revocation event (the revoked API key, the ended membership or the deleted sandbox) to a Postgres table in the same transaction. The lease holder matches each event against its open peer-to-peer sessions and its revocable relay grants, and writes one session revocation for each match. A relay grant is revocable until its stream deadline plus the 60-second delivery margin (see the grant terms below), not only while it is admittable, because a stream admitted before the expiry can still run; and the lease holder delivers every pending revocation, with its revocation ID and its target (the session ID or the relay grant ID that it ends), to the agents and deletes it after the agent acknowledges that ID. The agent ends only the session or the relay streams of the grant that the target names. A revocation names the agent channel that signaled its session or sent its grant. The server also deletes it when that channel closes, when the session reaches its absolute expiry, when the grant stops being revocable, or when the device is removed, because the session or grant has ended in each case. The agent acknowledges a revocation also when the session or grant has already ended. Each session and each relay grant is bound to the agent channel that signaled or sent it: when that channel closes, including at a lease handover, the agent ends the session and the grant's relay streams at once with `AGENT_CHANNEL_LOST`, so no session or grant outlives the instance that knew about it. Before it closes the data channel or a relay stream, the agent sends a session-end frame with the reason (`IDLE`, `EXPIRED`, `REVOKED` or `AGENT_CHANNEL_LOST`, and on relay streams also `GRANT_INVALID` or `GRANT_REPLACED`). After any session end, the caller calls `OpenSession` again to continue on the peer-to-peer path, or `AuthorizeRelay` again to continue on the relay; a session end is not an ICE failure.
- Relay authorization: each relay grant covers one operation. `AuthorizeRelay` takes an `organization_id`, a `sandbox_id`, an operation kind (`RelayOperationKind`: `EXEC`, `ATTACH_EXEC`, `READ_FILE` or `WRITE_FILE`), the caller-generated operation ID of that kind (`exec_id`, `read_id` or `write_id`) and, for `EXEC`, `READ_FILE` and `WRITE_FILE`, the request digest of the operation (an `ATTACH_EXEC` request carries no digest, so a caller that knows only the `exec_id` can attach), which the [protos contract](protos-ownsand-api-contract.md#relay-grants) defines (for `EXEC`, the command, environment, working directory and timeout; for `READ_FILE` and `WRITE_FILE`, the guest path). It applies the authorization matrix and the sandbox state rule of the operation: `READ_FILE` and `WRITE_FILE` need `RUNNING`, and `EXEC` and `ATTACH_EXEC` accept `RUNNING` or `PAUSED`, so that a caller can get the kept output of an exec on a paused sandbox with `AttachExec`. It needs a live agent channel for the sandbox's device, so it always runs on the lease holder.
- `AuthorizeRelay` creates a relay grant with a new grant ID (a UUID v7 that the control plane does not persist), the principal, the sandbox ID, the operation kind, ID and request digest, an expiry 15 minutes later and a stream deadline 30 minutes after creation. It sends the grant to the agent on the agent channel. After the agent acknowledges the grant, it returns the grant ID, the expiry and the remaining duration (`expires_in`), as the [protos contract](protos-ownsand-api-contract.md#relay-grants) lists. When the agent rejects the grant because of its per-device grant limit, `AuthorizeRelay` fails with `resource_exhausted` and a retry delay; when the agent does not acknowledge within 10 seconds, `AuthorizeRelay` fails with `unavailable`. The lease holder keeps that pending grant under its `authorization_id` until it stops being admittable (its expiry plus the 30-second admission tolerance): a late acknowledgement installs it, a late rejection removes it, and a retry with the same `authorization_id` waits for the outcome and returns the grant ID of the installed grant.
- Idempotency: each `AuthorizeRelay` carries an `authorization_id` (a UUID v7 that the caller generates for each logical request and reuses for every retry of that request, after a lost response or a retryable `unavailable` or `resource_exhausted` result). A retry with the same `authorization_id`, principal and request, while the grant it created is admittable, checks the caller's current authorization again and returns the same grant ID without a new grant. Independent requests use new `authorization_id` values and get separate grants.
- Replacement: an `AuthorizeRelay` may name, in `replaces_grant_id`, a revocable grant (one that still counts against the limits, also after its expiry) that the same caller holds for the same principal, sandbox, operation kind, operation ID and request digest. It first checks the caller's current authorization and then replaces that grant atomically with a new grant ID. The replacement does not use another slot of the grant limit: the predecessor and its pending successor share one reserved slot, both stay eligible for revocation until the agent's acknowledgement names the swap, and a predecessor has at most one pending successor (a second replacement request for it waits for the first or fails with `aborted`), so the operations of a device at the limit can renew their grants at a stream rotation and recover after a relay connection loss. The agent ends the open streams of the replaced grant with `GRANT_REPLACED`. The server checks the `authorization_id` first: a retry of a known request follows the idempotency rule above. A new request without `replaces_grant_id` always creates a separate grant and never ends another grant's streams, so two programs of one principal that attach to the same exec do not end each other's streams. The SDK sends only the grant ID that it received itself. When `replaces_grant_id` names no revocable grant of the same principal, sandbox, operation and digest (for example, after the agent channel was lost or the grant was released), `AuthorizeRelay` ignores it and creates a separate grant under the normal limits. Only when it performed the replacement does the control plane send `replaces_grant_id` to the agent with the new grant. The control plane keeps the old grant in its set of revocable grants until the agent's acknowledgement names it as replaced, the agent releases it, its agent channel is lost, or it stops being revocable (its stream deadline plus the 60-second delivery margin), so a revocation still reaches the old grant's streams when the agent installed the new grant separately; and the agent swaps the grants atomically, according to the [agent contract](cmds-ownsand-agent-foundation.md#data-path).
- A grant authorizes every relay RPC of its operation until its expiry: retries of the same `ExecRequest`, `AttachExec` for the same `exec_id`, `ReadFile` calls for the same `read_id` and `WriteFile` chunks for the same `write_id`. Any other operation needs its own `AuthorizeRelay`, so each operation is authorized again. The agent checks the first request frame of each relay stream against the grant's operation kind, ID and request digest, rejects it when the grant's expiry plus the 30-second admission tolerance passed before that frame arrived, and applies the state rule of that request before it dispatches it: a new `Exec`, `ReadFile` or `WriteFile` on a sandbox that is not `RUNNING` fails with `failed_precondition`, according to the [protos contract](protos-ownsand-api-contract.md#sandbox-state-rules).
- The expiry (plus the agent's 30-second admission tolerance) is the last time at which the agent accepts the first request frame of a relay stream of the grant. A stream whose first request the agent accepted before the expiry continues, subject to revocation and channel loss, until the stream deadline, where the agent ends it with `EXPIRED`. The control plane ends each relay stream before 14 minutes (see [Relay streams](#relay-streams)), so the stream deadline ends only streams that a faulty control plane keeps open. A revocation ends the grant at once: the agent rejects new streams of the grant and ends its open relay streams with `REVOKED`, and a later `AuthorizeRelay` fails with the authorization error. Opening a relay grant is not sandbox activity.
- Renewal: the SDK renews the grant of an operation only when it must start a new stream with an expired or expiring grant (at a stream rotation, at the next `WriteFile` chunk or `ReadFile` call of the operation, or during recovery), never while a stream of the old grant is open, and only through replacement, with `replaces_grant_id`, so a renewal never needs another slot and never releases a grant that another caller holds.
- Release: the agent releases a grant when none of its relay streams is open and its operation has finished on the agent (the exec ended and its result was delivered on a relay stream, the read sent its final message, or the write sent its `finish` result), or when its last relay stream ended with an error that leaves no operation to continue (`not_found`, `permission_denied`, `already_exists` or `failed_precondition` for a request that the agent never started; an `AttachExec` `not_found` under an `EXEC` grant does not release it, because the caller may follow it with the identical `ExecRequest`), and reports the release on the agent channel. The lease holder then removes the grant from its set of revocable grants and from the limits below, and a later RPC of that operation needs a new `AuthorizeRelay` (for example, after a lost final response). The agent also releases a grant that has had no open stream for 60 seconds (counted from its installation or from the end of its last stream), and an expired grant as soon as its last admitted stream ends, so cancelled or abandoned operations do not hold slots; the operation itself stays resumable under a new grant. The stream deadline stays the last fallback.
- Limits: the lease holder keeps at most 256 revocable relay grants per device, and at most 32 of them for one principal, and accepts at most 10 `AuthorizeRelay` calls per second per principal; a request over either limit fails with `resource_exhausted` and a retry delay in the error detail, and the SDK retries it according to the [SDK contract](packages-ownsand-sdk-foundation.md#data-path). A grant counts until it is released, revoked, lost with its agent channel or stops being revocable, so the grant limits bound operations that run at the same time, including streams admitted before an expiry, not operations per 15 minutes. The agent applies the same per-device grant limit and rejects a grant over it, so a principal cannot grow agent memory without bound. Adjust the values with the implementation and record them here.
- Grant terms: a grant is revocable while it is not revoked or released, is bound to the agent's current agent channel and has not passed the later of its stream deadline plus 60 seconds and the time the control plane received the agent's acknowledgement plus the `stream_deadline_in` duration that it sent (the agent starts that duration when it receives the grant, which is before the acknowledgement, so the control plane never forgets a grant that the agent still serves; the agent enforces the stream deadline itself without tolerance). A revocable grant is also admittable (a live grant) until its expiry plus the agent's 30-second admission tolerance. Admission, the control plane's check at the start of each relay RPC and the agent's relay connection rule use admittable grants; revocation matching and the grant limits use revocable grants. Admittability is checked when the agent accepts the first request frame of a stream. A stream accepted under an admittable grant (an admitted stream) carries sandbox content after the expiry, until the stream ends, the grant is revoked, the agent channel is lost or the stream deadline arrives.
- Implementation choices (the simplest reading where the contracts leave a wire detail open): a grant's `stream_deadline` is its creation time plus 30 minutes and its `expires_at` the creation time plus 15 minutes; the `RelayGrant` message carries the full `expires_in` (15 minutes) and `stream_deadline_in` (30 minutes) because the control plane sends it right after creating it; the `AuthorizeRelayResponse.expires_in` is the remaining duration when the response is sent. The per-principal limit of 32 counts the grants of one principal on one device. `OpenSession` waits up to 15 seconds for the agent's answer and fails with `unavailable` after that, or with the agent's `error_code`. A retry with a known `authorization_id` but a different operation fails with `already_exists`. The retry delay in `RetryDetail` is 1 second, or the rate limiter's own wait when it is longer. A revocation that arrives between the pending registration and the result fails the call with `permission_denied`.
- The data path is selected by the client according to the [SDK contract](packages-ownsand-sdk-foundation.md#data-path). The server records `OpenSession` and `AuthorizeRelay` calls in logs and metrics with the `DataPathTransport` that each signals.

### Relay authentication

- The relay uses no credential of its own. The control plane already holds every relay grant in the memory of the lease holder and validates the caller's and the agent's credentials itself, so it needs no signed relay ticket.
- `RelayService` RPCs carry the caller's own credential (a Logto access token or an API key) in the `Authorization: Bearer` header, validated as in [Authentication](#authentication), and the grant ID that `AuthorizeRelay` returned in the `Ownsand-Relay-Grant-Id` request header, according to the [protos contract](protos-ownsand-api-contract.md#relay-services). At the start of each RPC, the control plane applies the authorization matrix again and accepts the RPC only when the grant is admittable on this instance, its principal is the principal of the RPC (the same Logto `sub` or the same API key), and the request's `organization_id`, `sandbox_id`, operation kind and operation ID equal the grant's (the control plane checks the request fields when the request body arrives, and ends a mismatched RPC with a relay stream close). It fails an RPC for an unknown, non-admittable or revoked grant with `unavailable` and `GRANT_INVALID` in the error detail, like the agent's rejection, and a mismatch of principal, organization, sandbox or operation with `permission_denied`. The agent checks the sandbox, operation kind, operation ID and request digest again against its grant, and enforces the organization boundary through the sandbox of the grant, which the control plane issued for that organization. A stream that started under an admittable grant continues until it ends according to [Relay streams](#relay-streams).
- A grant ID is not a credential: it authorizes nothing without the credential of the grant's principal. It is not secret, but components log it only as an identifier and never with a credential.
- `RelayAgentService.Connect` carries an `osd_` device session credential of the device, validated as in [Authentication](#authentication). The agent gets a new credential with `CreateChallenge` and `Authenticate` before each new relay connection, like before each agent channel, because a credential expires 15 minutes after issue. The device key signature in `Authenticate` proves possession of the device key, so the relay connection needs no proof of its own.
- The control plane does not rely only on its own revocation check: the device agent stays the enforcement point for open streams. It admits a relay stream only for a grant ID of a live relay grant that the control plane sent on the agent channel (grant expiry blocks only new requests), and it ends the admitted streams of a grant when the control plane revokes it, when that agent channel closes or at the grant's stream deadline, according to the [agent contract](cmds-ownsand-agent-foundation.md#data-path).

### Relay

The relay is the fallback of the data path. The control plane forwards `DataFrame` messages between the caller's `RelayService` RPC and the agent's `RelayAgentService` connection in process memory. Relay data never passes through the agent channel. The relay origin is the control plane origin `https://ownsand.api.delino.io`; there is no separate relay origin.

#### Agent relay connections

- A device agent opens `RelayAgentService.Connect`, a bidirectional stream over HTTP/2, with its device session credential and sends its request headers with an initial keepalive frame at once. The control plane registers the connection for the credential's device only when the device has a current agent channel on this instance, and binds the connection to that agent channel generation. It closes the relay connection when that agent channel closes (also at a lease handover and when the device is removed), because the agent then ends every relay grant of that channel with `AGENT_CHANNEL_LOST`.
- The control plane sends its supported kinds frame as its first frame. It answers a frame of an unknown kind on a stream with an error frame (`unimplemented`) and ends that RPC. It tracks received bytes below the Connect message layer, so the 90-second idle rule counts any byte and the acceptance timer can pause while a frame is in transit.
- When `Connect` opens, each side sends the list of relay frame kinds that it supports in a frame on `stream_id` 0 (no list means the first-version set), and a sender uses a new kind only after the other side listed it. Both sides ignore an unknown frame kind on `stream_id` 0 and end a stream with an error frame for an unknown kind on any other stream, so either side can be updated first.
- Replacement: when a second connection for the same device registers, the control plane routes new RPCs to it, ends the RPCs on the older connection with `unavailable` and closes the older connection.
- Echo: a keepalive frame from the agent may ask for an echo, and the control plane answers it at once with a keepalive frame.
- Each side sends a keepalive frame after 30 seconds without an outbound frame, so one-way traffic never lets the other side's 90-second receive timeout expire. The control plane closes a connection that receives no byte for 90 seconds, and the agent treats 90 seconds without any received byte on the connection (not only a complete frame, because one large frame can take longer than that to arrive on a slow link) as a lost connection and reconnects while it holds a live grant, according to the [agent contract](cmds-ownsand-agent-foundation.md#data-path).
- When an agent relay connection closes, the control plane ends every RPC routed on it with `unavailable`.
- Device network requirement: the agent relay connection needs outbound TCP 443 to the control plane origin with HTTP/2 from end to end and no TLS interception. A WebSocket transport for `Connect`, for devices behind proxies that allow only HTTP/1.1, is an open decision; record it here, together with the [agent channel transport](#agent-channel), before such devices are supported.

#### Relay streams

- For each `RelayService` call, as soon as it has authenticated the caller and checked the grant in the request headers (before it receives a unary request body), the control plane allocates a `stream_id` that is unique among the open RPCs on that agent connection, sends a stream-open frame with the grant ID and the `sandbox_id`, translates the request into `DataFrame` messages and translates the agent's frames back into responses. The [protos contract](protos-ownsand-api-contract.md#data-path-framing) owns the frames.
- When no agent relay connection for the grant's device exists, the control plane waits up to 10 seconds for one, and then fails the RPC with `unavailable`.
- When the agent ends a stream with a session-end frame (including `GRANT_INVALID` for a stream open that names no live grant), the control plane ends the RPC with `unavailable` and the `SessionEndReason` in the error detail. The caller then calls `AuthorizeRelay` again, which returns the authorization error when the grant was revoked.
- Whenever a relay RPC ends for any reason other than an agent session-end or error frame (the caller cancels it or its connection fails, a stream rotation, the 30-second acceptance timeout, a request upload or `WriteFile` call deadline, or a request that does not match the grant), the control plane sends a relay stream close frame to the agent, according to the [protos contract](protos-ownsand-api-contract.md#data-path-framing). It never reuses a `stream_id` on one agent connection.
- A server stream sends a `keepalive` event at least every 60 seconds while it has nothing else to send, also before the agent's `accepted` event, so that caller-side proxies and NAT devices keep the connection. These rules apply to the server-streaming RPCs (`Exec`, `AttachExec` and `ReadFile`). The control plane ends each such stream whose request the agent accepted before 14 minutes have passed since it allocated the stream's `stream_id`, with an OK status and no final event (a stream rotation), so that every long operation is authorized again within a bounded time; the caller continues with the resume rules of the [protos contract](protos-ownsand-api-contract.md#exec). For `Exec`, `AttachExec` and `ReadFile`, the control plane must forward the complete request frame to the agent within 5 minutes after it allocated the `stream_id`, which covers the request upload and any wait for the agent's credit or for the shared connection; it fails a slower RPC with `deadline_exceeded` (or `unavailable` when it waited for the agent) and sends a relay stream close. A server stream that receives no `accepted` from the agent within 30 seconds after the control plane forwarded its complete request frame ends with `unavailable`, so a stalled admission never looks like a rotation; the control plane pauses that 30-second timer while it is receiving a frame from the agent on the connection, because the agent's request accepted notice cannot overtake a large frame already in transit. Because the agent admits a stream only up to the grant's expiry plus 30 seconds and the control plane ends each stream 14 minutes after it allocated the `stream_id`, the latest stream ends by the grant's expiry plus 30 seconds plus 14 minutes, which leaves at least 30 seconds before the 30-minute stream deadline. `WriteFile` has no acceptance event and is bounded only by its 5-minute call deadline.
- A `WriteFile` call must finish within 5 minutes, including the upload of its request body and the agent's result, and the control plane fails a slower call with `deadline_exceeded`. The SDKs retry the chunk with the same `write_id`.
- Forwarding uses one bounded in-memory buffer for each stream. Toward the caller, the control plane grants the agent a credit window per stream that never exceeds the free space in that stream's buffer, and sends a relay window update as the caller consumes data, according to the [protos contract](protos-ownsand-api-contract.md#data-path-framing). A slow caller therefore slows only its own stream: the control plane never stops reading the shared agent connection, never drops a frame and never exceeds a buffer. An agent that sends beyond its window breaks the protocol, and the control plane closes that agent relay connection. Toward the agent, the control plane forwards request payload frames only within the credit window that the agent grants for each stream, and applies back-pressure to that caller's request body only. The control plane never writes relay frames to disk, to logs, to Postgres or to object storage. Limits (recorded with the implementation, `internal/relay`): the per-stream buffer and initial window toward the caller is 2 MiB (at least one maximum frame); the per-connection buffer limit is 64 MiB, the sum of the stream buffers, so one agent relay connection carries at most 32 concurrent relay RPCs; one grant has at most 4 concurrent relay RPCs on the relay; a further RPC fails with `resource_exhausted` and a retry delay. A stalled reader is a caller to whom one response message cannot be written for 60 seconds (a per-write deadline on the HTTP/2 stream); the control plane then ends the RPC and sends a relay stream close. At most 1024 frames wait toward one agent connection and at most 4096 frames toward one caller stream; an agent that exceeds either is disconnected. Failed relay grant checks are rate-limited per principal (a burst of 10, then one per second). The relay shares the Droplet's network, memory and CPU with the other servers on it, so these limits also bound the relay's share of the Droplet.
- Implementation notes: Connect decodes the request message of a relay RPC before the handler runs, so the control plane checks the request against the grant before it allocates a `stream_id`; a mismatched request is rejected with `permission_denied` before any relay stream opens and therefore needs no relay stream close frame. The 5-minute request upload bound is a read deadline on the HTTP/2 request stream, set when the request arrives; the 5-minute bound to forward the request frame covers the waits for the relay connection and for the agent's credit. The control plane also sends a relay stream close after it forwarded a final event (`exited`, `failed`, `sandbox_ended`, `paused`, the read's final message or the write result), so the agent can release the stream without a timer.
- A control plane restart or deployment ends every open relay RPC and agent relay connection. Callers continue with the resume rules, and agents reconnect while they hold a live grant.

### STUN

- The control plane answers STUN binding requests ([RFC 8489](https://www.rfc-editor.org/rfc/rfc8489.html)) on UDP port 3478 without authentication, at `stun:ownsand.api.delino.io:3478`. It does not offer TURN and does not relay media or data over UDP. STUN needs the public UDP port that [Runtime and Language](#runtime-and-language) requires from the deployment workflow; until the workflow publishes it, `ownsand-api` is not deployed.
- The STUN URL is control plane configuration, so a change of the STUN address needs no client release. Callers get the STUN server URLs from `DataPathService.GetIceServers` before they create an offer, and agents get them in a configuration message on the agent channel.
- Rate-limit STUN responses per source address. A binding response can be larger than its request ([RFC 8489 section 16.1.2](https://www.rfc-editor.org/rfc/rfc8489.html#section-16.1.2)), so the limit bounds the reflected traffic toward a spoofed address but does not remove it. Record the request and response byte budget per source address with the implementation.
- The STUN server is `github.com/pion/stun/v3` `v3.1.7` (owner-approved), in process (`internal/stunserver`), listening on `STUN_ADDR` (default `127.0.0.1:3478`; the deployment must listen on the published address). Callers and agents get the URLs of `OWNSAND_STUN_URLS` (default `stun:ownsand.api.delino.io:3478`). It answers only binding requests of at most 548 bytes with `XOR-MAPPED-ADDRESS` and `FINGERPRINT` (a response is at most 64 bytes) and drops everything else silently. Rate limit per source IP address: a burst of 20 requests, then 5 per second, so one source address receives at most 320 response bytes per second after the burst; rate-limited requests get no answer. It logs aggregate counts once a minute. Adding `pion/stun` raised the minimum versions of its indirect modules `golang.org/x/crypto` to `v0.59.0` and `golang.org/x/sys` to `v0.50.0`, because `govulncheck` reported module-level advisories for the versions it selected; after the bump `govulncheck ./...` reports no vulnerabilities.

### Device removal and organization deletion

- `RemoveDevice` marks the device `removed` and invalidates its session credentials in the same transaction. The server closes the open channel after it sends a clean-up command. An offline agent receives the removal notice from `Authenticate` at its next connection. In both cases, the agent deletes its local sandboxes, snapshots and locally built images, then calls `AgentService.ConfirmRemoval` with a nonce from `CreateChallenge` signed by its device key, and only then deletes its device key and stops. A removed device may use `CreateChallenge` nonces only to get the removal notice from `Authenticate` and to call `ConfirmRemoval`; `Authenticate` returns only the removal notice to a removed device. The agent retries `ConfirmRemoval` after a lost response; after a success, the tombstone is gone and a retry gets an unknown-device answer, which the agent treats as a confirmed removal. A removed device can never get a session credential again.
- The non-terminal sandboxes of a removed device change to `deleted` with `DEVICE_REMOVED`, or with `ORGANIZATION_DELETED` when the removal is part of `DeleteOrganization`. Sandboxes that are already `deleted` or `failed` keep their state and end reason. The server deletes the records of snapshots that exist only on the removed device, and the templates that reference them. An exported snapshot is organization data: its record stays, without a local copy, until it is deleted or the organization is deleted.
- Removal tombstone: the server keeps the device ID, its public key, the `removed` state and the tombstone expiry (`expires_at`, 1 year after the removal commits) after removal, also after organization deletion, until `ConfirmRemoval` succeeds or 1 year after the removal, whichever comes first. Every lookup treats a tombstone whose `expires_at` has passed as absent, so the device becomes unknown at the deadline. The server schedules the deletion of each tombstone at its `expires_at`, and a daily job deletes tombstones whose scheduled deletion was missed. The tombstone holds no other data. It lets `Authenticate` return the removal notice to an agent that was offline during the removal. An agent that returns after its tombstone was deleted, and that never received the removal notice, is an unknown device; it keeps its data until an operator runs `ownsand-agent reset`. An agent that already received the notice and finished its clean-up treats an unknown-device answer to `ConfirmRemoval` as a confirmed removal, because a lost `ConfirmRemoval` response leaves no tombstone to confirm against.
- `DeleteOrganization` marks the organization deleted, revokes its API keys, enrollment tokens and invitations, removes its devices as above, stops issuing signed URLs for the organization, aborts its open multipart uploads, deletes its exported snapshots from R2 and then deletes its records, except the device removal tombstones, the audit events and the R2 clean-up job state. A clean-up job retries R2 deletions until they succeed and logs each failure. After every signed upload URL of the organization has expired (15 minutes after the last one was issued), the job deletes the organization prefix once more and then deletes its own state. Audit events of the organization stay for 90 days.

### Agent version policy

- Release manifest ingestion is not implemented: the [agent contract](cmds-ownsand-agent-foundation.md#agent-updates) does not define the manifest format yet. Until it does, the agent releases table stays empty, `GetAgentVersionPolicy` returns no default versions and a pin is rejected only for a version that the table marks revoked.
- The server holds one default target agent version per platform. It reads them, and the list of revoked versions, from the signed release manifest: it fetches the manifest from the release host, verifies the signature with the same public keys as the agent, and stores the releases in its agent releases table. The default target of a platform is the version that the manifest marks as default. The organization policy is `FOLLOW_DEFAULT`, `PIN` with a version, or `HOLD`. `UpdateAgentVersionPolicy` rejects a pin to a revoked version with `invalid_argument`. When the running or pinned version of a device is revoked, the server sends the default target version for that device, regardless of `HOLD` or `PIN`, and marks the target as a revocation recovery, so the agent installs it also when it is lower than the running version.
- The server sends the target version that results from the policy on the agent channel. The [agent contract](cmds-ownsand-agent-foundation.md#agent-updates) owns verification and the conditions for installation.
- `ListDevices` reports each agent version and `AgentUpdateState`.

## Storage

- PlanetScale Postgres tables: organizations, memberships, invitations, devices (with their limits), device removal tombstones, enrollment tokens, device session credential hashes, consumed nonces, API keys, sandboxes, snapshots, templates, agent version policies, agent releases, audit events, the service lease, the control event table that revocations, configuration changes, pending deletes and removals use, R2 clean-up jobs and the expiry of the last signed upload URL per snapshot. Enum columns store the protobuf enum numbers. Tables that outlive the organization row (tombstones, audit events and clean-up jobs) have no foreign key to it.
- Retention of ended records: a `deleted` or `failed` sandbox record is kept for 30 days after it ends, and longer while it still reserves a macOS machine identifier, and then a daily job deletes it. `ListSandboxes` hides ended sandboxes unless the state filter asks for them. Every entity uses a UUID v7 primary key, and every organization-owned table has an `organization_id` column that every query filters on.
- Secret columns hold only SHA-256 hashes of enrollment tokens, invitation secrets, API keys and device session credentials, plus a short non-secret prefix for display. Devices store only their public key.
- `DeleteSnapshot` of a snapshot whose export has started (any export state other than `NOT_EXPORTED`), and the deletion of such a snapshot record by device removal or reconciliation, cancels the export, stops issuing signed URLs for it, aborts its open multipart uploads, deletes its objects under `organizations/<organization_id>/snapshots/<snapshot_id>/` and keeps its clean-up state until it deletes that prefix once more after every signed upload URL for it has expired.
- Exported snapshots use Cloudflare R2 with signed URLs, according to the repository default. Each part is one object `organizations/<organization_id>/snapshots/<snapshot_id>/part-<n>` (five-digit, 1-based), uploaded with a presigned `PUT`, so the control plane uses no multipart uploads and has none to abort. A signed URL request names at most 100 parts numbered 1 to 10000. The R2 client (`internal/r2`) signs with AWS Signature Version 4 using only the Go standard library, region `auto`, path-style URLs, with the settings `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`; without them `ExportSnapshot` answers `unavailable`. The clean-up jobs list a prefix and delete each object. Object keys start with `organizations/<organization_id>/snapshots/<snapshot_id>/`, so organization deletion can remove them by prefix. Signed upload and download URLs expire after 15 minutes and are issued only to the agent of the device that runs the export or import; the agent asks for fresh part URLs on the agent channel while the export or import runs. The snapshot record stores the SHA-256 of each exported part; the import command carries these hashes over the agent channel, so the importing agent never trusts hashes stored in R2.
- Migration tool: an in-house runner over the SQL files embedded with `embed.FS` from `internal/store/migrations/` (`<version>_<name>.sql`). At startup, before the server listens, it takes a Postgres advisory lock, applies each missing version in its own transaction together with its row in `schema_migrations`, and refuses to start when the database has a version that the binary does not know. It adds no dependency.
- Open decisions: the backup policy, and the database stage of the [deployment workflow](repository-workflow-contract.md#deployment-workflow). Record them before the first deployment.
- Retention jobs (`internal/jobs`): a daily job deletes audit events after 90 days, ended sandboxes 30 days after they end (except those that still reserve a macOS machine identifier), expired tombstones, device session credentials and consumed nonces, idempotency keys after 24 hours and control events after 24 hours. A scheduler also deletes each tombstone at its `expires_at`. The R2 clean-up job retries every minute and logs each failure; until R2 is configured, jobs stay pending and each run logs `r2_cleanup_pending_unconfigured`.

## Security

- Accept only the credentials in [Authentication](#authentication). Never accept Logto ID tokens.
- Return each secret once in the response that issues it. Never store or log a secret in plain text. A relay grant ID is not a secret: an identical `AuthorizeRelay` retry with the same `authorization_id`, after the caller's authorization is checked again, returns the same grant ID while its grant is admittable, because the caller may have lost the first response.
- Isolate organizations in every query, as [Authorization](#authorization) requires.
- `AgentService` RPCs carry no bearer credential except `Channel` (and `RelayAgentService.Connect`, which also uses the `osd_` credential): `Enroll` authenticates with the enrollment token in the request body, `CreateChallenge` names a device ID and returns a nonce, `Authenticate` and `ConfirmRemoval` authenticate with a nonce signed by the device key (the signed message is the purpose label `ownsand-authenticate` or `ownsand-confirm-removal` followed by the nonce, and the server checks that the label matches the RPC), and `Channel` uses the `osd_` credential. `CreateChallenge` returns a nonce for any device ID without checking that the device exists. `Authenticate` and `ConfirmRemoval` tell an unknown, removed or enrolled device apart, which shows anonymous callers whether a device ID exists. This exposure is accepted: device IDs are random UUID v7 values that only members and API keys of the organization can list, the calls are rate-limited, and an agent whose clean-up finished needs the unknown-device answer. Nonces are stateless: a nonce is the device ID, a random value and an expiry, authenticated with the nonce key, a secret that every instance shares (rotate it with an overlap that accepts the previous key for 60 seconds), so `CreateChallenge` stores nothing and unauthenticated callers cannot use up a device's nonces. The server records a nonce only when `Authenticate` or `ConfirmRemoval` consumes it, until its expiry, to reject replays. Nonce encoding: version byte `1`, the 16-byte device UUID, 16 random bytes, the expiry as 8-byte big-endian Unix seconds and an HMAC-SHA256 over those bytes with the nonce key (`OWNSAND_NONCE_KEY`, at least 32 bytes, base64). During a rotation the previous key is set in `OWNSAND_NONCE_KEY_PREVIOUS` and removed 60 seconds after every instance runs with the new key. An unknown device gets `not_found`, a bad, expired or replayed nonce or a bad signature gets `unauthenticated`, and `ConfirmRemoval` of an enrolled device gets `failed_precondition`.
- Rate-limit `Enroll`, `CreateChallenge`, `Authenticate`, `ConfirmRemoval`, `AcceptInvitation` and API key validation failures per device ID, per credential prefix and per client address. Rate-limit relay RPCs that fail the grant check in [Relay authentication](#relay-authentication) the same way. The Caddy reverse proxy on the Droplet terminates the HTTP connection, so the client address of an HTTP request comes from a header that Caddy sets; record the header and the rule that trusts only the value that Caddy appends in the change that adds rate limiting, after it is verified with the Caddy route of `ownsand-api`. Until then, limits are keyed per device ID and prefix only. Implemented limits: `CreateChallenge`, `Authenticate` and `ConfirmRemoval` are limited per device ID to a burst of 20 and then one per second; `Enroll` is limited per enrollment token display prefix to a burst of 10 and then one per 6 seconds; API key and device credential validation failures are limited per credential display prefix (the first 10 characters) to a burst of 10 and then one per 6 seconds, after which validation answers `resource_exhausted` without a lookup. Failed `AcceptInvitation` calls are limited the same way per invitation secret display prefix. STUN receives UDP directly, so its client address is the datagram's source address; the UDP port publication must keep the client's source address, because a STUN binding response that reports another address is wrong. Record the limits here with the implementation.
- Sandbox content never passes through the agent channel and is never stored by the control plane. On the relay, the control plane forwards it in process memory only, according to [Relay streams](#relay-streams).
- Relay grants bind a grant ID to one sandbox, one operation, its request digest, one principal and one agent channel. The control plane and the Caddy reverse proxy, which terminates TLS, can read and change relayed content (exec output, environment values in exec requests and file chunks). The request digest prevents them from running another command or using another guest path than the caller authorized, but the contracts trust the control plane and the Droplet for the confidentiality and integrity of the relayed content itself. The agent rejects a relay stream open for an expired, revoked or unknown grant, and a relay frame of any other sandbox or operation. A stream that opened before the grant expired continues until its stream deadline unless a revocation or the loss of the agent channel ends it first.
- The Droplet's clock is synchronized with NTP, because grant admission and the relay stream limits compare times with fixed tolerances. The Droplet hardening, its SSH access, its operating system update policy and its DigitalOcean Cloud Firewall rules (including the inbound UDP 3478 rule for STUN) are owned by the [deployment workflow](repository-workflow-contract.md#deployment-workflow).
- Configuration and secrets (database URL, R2 credentials, release manifest settings, the nonce key, the STUN rate limit and the Logto machine-to-machine credential for the `delino-accounts` API) come from the service's env file on the Droplet (`/srv/delino/env/ownsand-api.env`), which maintainers keep, according to the [environment contract](repository-environment-contract.md) and the [deployment workflow](repository-workflow-contract.md#deployment-workflow). The deployment sets `ADDR`. Their values never appear in `.env.example`; it lists their names with placeholders only, according to the environment contract.

## Logging

- Structured JSON logs on standard output with `log/slog`, like `accounts-api`.
- One record per RPC with the procedure, principal kind, principal ID (Logto `sub`, API key ID or device ID), organization ID, Connect code and duration.
- Agent channel events: enrollment, authentication result, connect, disconnect, offline transition, state report counts, command ID and result.
- Data path events: session ID or relay grant ID, sandbox ID, signaled transport, grant acknowledgement result and duration.
- Relay: one record per relay RPC with the procedure, grant ID, principal kind and ID, organization ID, sandbox ID, device ID, Connect code, frame counts, byte counts and duration. Agent relay connection events: device ID, connect, disconnect, replacement and the number of RPCs that each disconnect ended.
- STUN: aggregate request and rate-limit counts, not one record per request.
- Never log tokens, API keys, enrollment tokens, invitation secrets, device session credentials, signed URLs, SDP bodies, relay frames, exec commands, environment values, exec output or file contents.

## Build and Test

Package scripts, following `accounts-api`:

- `pnpm exec turbo run build --filter=ownsand-api` (`go build` into `dist/ownsand-api`), `lint` (`go vet ./...`), `test` (`go test ./...` followed by the development launcher tests in `scripts/*.test.mjs`) and `dev` (`scripts/dev.mjs`, which builds and runs the server and forwards termination signals like the `accounts-api` launcher).
- Postgres tests: storage and handler tests, and the launcher tests that start a server, need Postgres. They run when `OWNSAND_TEST_DATABASE_URL` names a Postgres server where the test user may create databases (each test creates and drops its own database), and are skipped otherwise; for example `docker run --rm -d -e POSTGRES_PASSWORD=test -p 127.0.0.1:55432:5432 postgres:17` with `OWNSAND_TEST_DATABASE_URL=postgres://postgres:test@127.0.0.1:55432/postgres?sslmode=disable`. Pure-logic tests (authorization matrix, token validation, credential formats, validation, configuration and rate limits) need no database and always run. CI provides no Postgres service yet, so CI runs only the pure-logic tests.
- From the repository root: `gofmt` check, `go vet ./...` and `go test ./...`, according to `servers/AGENTS.md`.
- Required tests: the authorization matrix for every RPC with each principal kind, cross-organization access, enrollment with an expired, reused and revoked token, a removed device that tries to authenticate (also after organization deletion), `ConfirmRemoval` and tombstone expiry, API key and member authorization on every RPC, the final R2 sweep after organization deletion, TTL validation, scheduler eligibility (including the macOS guest limit and `deleting` sandboxes) and concurrent reservation, session and relay grant revocation, the live grant and `AuthorizeRelay` rate limits with their retry delay, grant release after the operation finishes (more than 256 sequential operations on one device), `authorization_id` retries after a lost response, a stale `replaces_grant_id` after agent channel loss, replacement at the grant limit with two grants for the same exec, simultaneous replacement requests with a delayed acknowledgement at the grant limit, revocation retention when the grant acknowledgement arrives late, the per-principal grant limit, an `AttachExec` `not_found` that keeps the `EXEC` grant, `AuthorizeRelay` without a grant acknowledgement, and log and audit redaction.
- Required relay tests:
  - Relay authentication: a relay RPC with the credential of another principal, of a revoked API key or of a user whose membership ended; an unknown, expired (also within and past the 30-second admission tolerance) or revoked grant ID; a mismatched organization, sandbox, operation kind or operation ID; `RelayAgentService.Connect` with an expired `osd_` credential, with the credential of a removed device, of another device, or for a device without a current agent channel; and closing the relay connection when its agent channel closes.
  - Agent relay connections: replacement, the 10-second wait for an agent relay connection (also a cold connection that registers within it), the 90-second idle close, a single frame that takes longer than 90 seconds to arrive while bytes keep arriving, echo replies, the supported frame kinds exchanged when `Connect` opens, and closing an agent relay connection that sends beyond its credit window.
  - Streams and flow control: stream keepalive, stream rotation with an OK status before 14 minutes, relay stream close frames and `stream_id` non-reuse, per-stream credit windows with one slow and one fast caller on the same device, an exec request upload longer than 30 seconds followed by immediate acceptance, a stalled request upload that ends with `deadline_exceeded` after 5 minutes, a complete upload whose forwarding waits for agent credit and ends after 5 minutes, an acceptance timer paused while a large frame from the agent is in transit with a concurrent `ReadFile` and `Exec`, a relay stream close sent for the acceptance timeout, the upload deadline and a request that does not match the grant, a `WriteFile` call that runs longer than 30 seconds, a `ReadFile` that the agent accepts at once and whose first chunk arrives after 30 seconds, the 5-minute `WriteFile` call deadline including the agent's result, session-end frames, and forwarding without persistence.
  - STUN binding responses with the client's source address, STUN rate limiting, and relay log redaction.

## Dependencies and Integrations

- Upstream: Logto shared tenant, PlanetScale Postgres, Cloudflare R2, the `delino-accounts` API (member display names).
- Platform: the shared DigitalOcean Droplet, its Caddy reverse proxy and DigitalOcean Cloud Firewalls, according to the [deployment workflow](repository-workflow-contract.md#deployment-workflow).
- Downstream: [device agent](cmds-ownsand-agent-foundation.md) (agent channel, relay connections and STUN), [CLI](cmds-ownsand-cli-foundation.md), [web console](apps-ownsand-console-foundation.md) and [SDKs](packages-ownsand-sdk-foundation.md).
- Protocol schemas: [protos contract](protos-ownsand-api-contract.md).
- `delino-accounts`: the console links to `https://accounts.delino.io`. The control plane reads member display names from the `delino-accounts` API server-to-server with its own Logto machine-to-machine credential, only for members of the organization in the `ListMembers` request, as recorded in the [API server contract](servers-accounts-api-foundation.md#users-and-operators). When that API is unavailable, `ListMembers` returns the members without display names instead of failing. The control plane does not store the profiles. The `delino-accounts` RPC for display profiles does not exist yet, so the control plane uses a source that is always unavailable and `ListMembers` returns empty display names; replace it with a client of that RPC, authenticated with the Logto machine-to-machine credential, in the change that adds the RPC.
