# apps-tide-console foundation contract

## Scope

This contract owns the tide web console, component `tide-console`, of [`tide`](project-tide.md) at `apps/tide/` (workspace package `tide-console`). The console is served at `https://tide.delino.io`. It manages tide organizations, members, the OwnSand link, GitHub installations, agent integrations and runner profiles, and shows the queue, the runners and the device pool.

## Runtime and Language

- Rsbuild React single-page application in TypeScript, like the [OwnSand console](apps-ownsand-console-foundation.md).
- Deployment: static output on Cloudflare Pages through the [deployment workflow](repository-workflow-contract.md#deployment-workflow). The `deploy` field of `apps/tide/package.json` names the Pages project `tide-console`, which must exist before the first deployment, and its `buildEnv` maps `PUBLIC_LOGTO_ENDPOINT` to the repository variable `LOGTO_ENDPOINT` and `PUBLIC_LOGTO_APP_ID` to `TIDE_CONSOLE_LOGTO_APP_ID`, so a production build always has the sign-in configuration and a missing variable fails the deployment (see [Deployment environments](repository-workflow-contract.md#deployment-environments)). The production build uses the defaults of `PUBLIC_API_ORIGIN` and `PUBLIC_LOGTO_SCOPES`.
- Server state: React Query with `@connectrpc/connect-query` and the TypeScript code from the [protos contract](protos-tide-api-contract.md).
- UI components: [`delino-ui`](packages-delino-ui-foundation.md).
- Development port: `127.0.0.1:13400` for `dev:app`, behind the portless name `tide.delino` (`https://tide.delino.localhost`), according to the [environment contract](repository-environment-contract.md#frontend-development-urls). The control plane allows both development origins in its local CORS configuration.

## Users and Operators

Organization owners, admins and members who sign in with Logto.

## Interfaces and Contracts

- The console calls the control plane only through its absolute origin. It reads the origin from `PUBLIC_API_ORIGIN` and uses `https://tide.api.delino.io` when the value is not set. It must not import source from `servers/`.
- Authentication: the console is a Logto single-page application (`@logto/react`) that requests access tokens for the API resource `https://tide.api.delino.io`. The Logto SDK keeps its session in the browser. The console reports loading to its pages only until the SDK has restored the session for the first time, so a token request never unmounts the page that made it.
- If Logto cannot start a redirect, the signed-out screen and session-ended notice show "Sign-in did not start. Check your connection and try again." as an alert. The sign-in action stays available after failure. Starting a retry clears the alert, which only reports a new error from the current attempt. The session-ended message and the signed-out invitation and GitHub setup instructions stay visible on their respective screens.
- The Logto hook checks the stored sign-in session outside its callback error handler. Invalid JSON or a value other than an object with string `redirectUri`, `codeVerifier` and `state` fields can cause an unhandled rejection. The console checks the configured application's session first and skips the hook for an unreadable session. It reads the legacy key only when the current key is absent. The next sign-in can overwrite the unreadable data. Remove the unreadable session guard when `@logto/react` handles that error itself. Replace the reader when the SDK exposes enough callback state to distinguish idle, pending and unreadable sessions.
- When a request fails with `Unauthenticated`, the error notice shows "Your session ended. Sign in again." and offers "Sign in with Delino" as its only recovery action. The button starts the Logto sign-in redirect. Other errors keep their retry action where the page offers one.
- Logto application registration (recorded with placeholders until the tenant registration exists):

  | Item                       | Value                                                                                                          |
  | -------------------------- | -------------------------------------------------------------------------------------------------------------- |
  | Application type           | Single-page application                                                                                        |
  | Application ID             | `<tide-console-logto-app-id>` (`PUBLIC_LOGTO_APP_ID`)                                                          |
  | Tenant endpoint            | `<logto-tenant-endpoint>` (`PUBLIC_LOGTO_ENDPOINT`)                                                            |
  | Sign-in redirect URI       | `<console origin>/callback`, for example `https://tide.delino.io/callback`                                     |
  | Post sign-out redirect URI | `<console origin>`                                                                                             |
  | API resource               | `https://tide.api.delino.io`                                                                                   |
  | Scopes                     | `tide:use`, which the control plane requires; the console always requests it. `PUBLIC_LOGTO_SCOPES` adds more. |

  A build with an incomplete Logto registration and otherwise valid configuration shows that sign-in is not configured. A production build from the deployment workflow always has both values, because `deploy.buildEnv` maps them to repository variables. Register the single-page application in the shared Logto tenant and store its ID in the repository variable `TIDE_CONSOLE_LOGTO_APP_ID` before the first deployment.

- Build-time variables (all public, inlined into the bundle, listed in `apps/tide/.env.example`): `PUBLIC_API_ORIGIN` (default `https://tide.api.delino.io`), `PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, `PUBLIC_LOGTO_SCOPES` and `PUBLIC_TIDE_MOCK_API` (`true` or `false`). `rsbuild.config.ts` validates them and fails the build or development server on an invalid value. The Turbo `dev` task passes them through `passThroughEnv`, and the `build` task declares them as `env`.
- Write `PUBLIC_API_ORIGIN` and `PUBLIC_LOGTO_ENDPOINT` as HTTP or HTTPS origins in the form `scheme://host[:port][/]`. The console trims surrounding whitespace and rejects credentials, paths, queries, fragments and backslashes. It also rejects missing or extra slashes after the scheme, even when URL parsing would normalize the value to a bare origin. Outside development mock mode, Rsbuild validates a nonblank `PUBLIC_LOGTO_ENDPOINT` even when `PUBLIC_LOGTO_APP_ID` is blank or missing.
- Mock API (recorded decision): `PUBLIC_TIDE_MOCK_API=true` runs the console against an in-browser fake control plane (`src/mock/mock-api.ts`, a Connect router transport with seeded organizations for each role, an `INVALID` OwnSand link, an organization without setup, requests, runners, devices, dev sessions, integrations and an invitation) that applies the role matrix, and a fake signed-in user whose session lives in `sessionStorage` like a provider session. Acme Robotics has a roster that spans two pages. The first continuation request fails once so the browser suite can exercise recovery. The mock serves the development server, the unit tests and the end-to-end suite. Rsbuild uses the resolved mode for both build-time validation and the browser bundle. If that mode is `production`, Rsbuild rejects the enabled flag before compilation regardless of the inherited `NODE_ENV`. The minifier removes the separate mock module from builds with the flag disabled.
- The mock accepts issued GitHub installation state once for the issuing organization, before the returned ten-minute deadline. The fixed `mock-state` callback fixture remains available for development and tests.
- The mock returns `invalid_argument` if a request omits the vendor credentials on integration creation or when the update mask includes `credentials`. It rejects the request before changing the integration list, integration fields or audit history. An update that omits `credentials` from its mask can leave the credentials unset in the request and keeps the stored credential state.
- The personal API key and agent integration forms accept names of 1 to 64 Unicode code points after trimming surrounding whitespace. The organization creation form accepts 1 to 100 code points after trimming. The forms keep invalid input visible, show an error on the name field and send the trimmed name only after validation passes.
- Server state: the pages call the generated services with `@connectrpc/connect-query`. The `overview` route uses the `watchQueue` helper of the [TypeScript SDK](packages-tide-sdk-foundation.md) (`tide-sdk`) on the console transport for the reconnects and the gap handling.
- When a refresh of loaded data fails with a transient error, the console keeps the content, open dialogs and entered values. It shows “The last refresh failed” and “Try again” above the affected content until a fetch succeeds. A first-load failure or a `not_found`, `permission_denied` or `unauthenticated` error shows the full error notice for the affected view. If a request for the next page fails with a transient error, the list keeps its rows and offers a retry that requests that same page.
- The console links to the OwnSand console at `https://ownsand.delino.io`, and to the devices page of the linked OwnSand organization (`https://ownsand.delino.io/orgs/<ownsand_organization_id>/devices`).
- Account settings: the console links to `https://accounts.delino.io`. It has no profile or account pages.
- The console never calls `ownsand-api`. Device management (enrollment, device limits including the vCPU overcommit, device removal) stays in the [OwnSand console](apps-ownsand-console-foundation.md), and the tide console links to it.

| `dev-sessions`  | `/orgs/:organizationId/dev-sessions` | Dev sessions of the organization with owner, profile, guest OS, state and end reason. Delete for the session owner, and for `admin` on every session. | `member`     |
| `api-keys`      | `/orgs/:organizationId/api-keys`     | The signed-in user's personal API keys: create (shows the secret once), list and revoke.                                                              | `member`     |
| `audit`         | `/orgs/:organizationId/audit`        | Audit events.                                                                                                                                         | `member`     |

- The `overview` route uses `WatchQueue` and reconnects automatically after a clean stream end or a retryable error. If a terminal error stops the stream after the console has shown a complete snapshot, the console keeps the last queue and runner counts on screen with a neutral `Disconnected` badge and an error notice. After a gap or a manual retry, the badge shows `Reconnecting` while the console keeps the last state. When the new snapshot is complete, the console replaces the data and the badge returns to `Live`. It shows the waiting requests in queue order (priority, then queue time, then request ID).
- The home page, organization switcher and GitHub setup share one cached organization list. The console requests up to 200 organizations per page, follows each continuation token and publishes the complete list in server order. Creating an organization or accepting an invitation refreshes the list.
- Profiles, Requests, Runners and the Overview queue share one cached runner profile list per organization. The console requests up to 200 profiles per page and follows every continuation token before it publishes the complete list in server order. Creating, changing or deleting a profile refreshes the list. If a page fails, the console offers error recovery and leaves the work lists and queue usable. The profile filters are unavailable until the list loads successfully. Work rows show the short profile ID when the profile name is unavailable.
- Members, the ownership transfer picker, Audit and Dev Sessions share a cached roster for the active organization. The console follows every `ListMembers` continuation token. Members and the ownership transfer picker show each loaded user once in server order. If a page fails, these views identify partial results and let the user retry the failed page. Member and ownership changes refresh the roster.
- Audit and Dev Sessions load their tables independently of the roster. Audit updates actor and subject names as roster pages arrive. Dev Sessions updates owner names in the same way. Both tables show the user ID when a name is unavailable and keep names from loaded pages if a continuation fails.
- The `members` route follows every invitation page token for the current organization before it shows pending invitations or an empty state. If a page fails, the console shows an error and lets the user retry. After it creates or revokes an invitation, it refreshes the list from the first page.
- Invitation links carry the secret in the URL fragment (`/invitations/accept#secret=<secret>`). The `invitation` route reads it, removes the fragment from the address bar at once and keeps the secret only in component state; it never stores it. A signed-out user sees the sign-in with a notice to open the link again after sign-in, because the console keeps no state across the Logto redirect.
- On the open invitation page, a new link clears the previous errors and replaces the input. Tide removes the fragment without reloading or changing the path or query. A fragment without a secret leaves the input in place. The user must select **Join organization** to submit.
- A successful acceptance refreshes the organization list even if the user leaves the invitation page. The refresh cancels any pending list load and starts again from the first page when the list is in use. Tide opens the joined organization's overview only if the user is still on the invitation page and has neither edited the submitted input nor opened another invitation link.
- The `github-setup` route reads `installation_id`, `code` and `state` and removes the query from the address bar at once. The installation ID must be a positive decimal integer through `9223372036854775807`, the signed `int64` maximum. If a callback value is missing or invalid, the route shows the invalid-address alert and skips organization selection and linking. The callback URL does not name the tide organization. After the complete list loads, the route calls `LinkGitHubInstallation` if the user is an `owner` or `admin` of exactly one organization, asks the user to choose if several are eligible, or displays an eligibility notice if none are eligible. If any page fails, the console offers the organization-load error recovery and keeps the callback values in memory. On success, the console refreshes GitHub integration data and replaces the callback history entry with the organization's `integrations` page if the original setup visit is still active. If the user leaves setup while linking is in progress, a successful response preserves their current page and history. After a failed link request, the console explains that the installation must start again from `integrations` because the `state` is single-use.
- On the `integrations` route, "Show more" loads the next page of GitHub installations for the selected organization. A transient error on a later page keeps the loaded installations visible and lets the user retry that page. Owners and admins can manage installations on every loaded page.
- **Connect GitHub** opens the installation URL once if the user stays on the Integrations visit that started the request. Leaving the page or switching organizations ends that visit, even if the user returns to the same page before the response arrives.
- Empty states guide the first setup in this order: link OwnSand, connect GitHub or create an agent integration, create a runner profile. The Overview checklist and setup-aware empty states show the next step as soon as its prerequisites are known. Either a GitHub installation or an agent integration is enough to advance to runner profiles. While the next step is unknown or after setup is complete, the console hides the checklist and uses the usual empty-state text.
- The Overview requests device capacity only when the OwnSand link is `ACTIVE`. When the link is missing or inactive, the Device pool shows the next step and links to `integrations` without an error alert or retry button. An active link with no devices shows “No devices.” Link lookup and capacity request failures use the standard error and retry behavior.
- When the OwnSand link is `INVALID`, every organization route shows a banner that explains that dispatch has stopped and links to `integrations`.
- The OwnSand API key replacement form targets the OwnSand organization linked when the form opens. If a successful refresh shows that the link is gone or points to another organization, the form clears the key and disables submission. Close the form and start again from Integrations.
- Credential forms accept a value once and never show it again. After a save, the form shows only that the credential is set and when.
- For an `OPENAI_CODEX` integration, the console shows the webhook URL to register in OpenAI.
- The `integrations` and `profiles` routes share one cached agent integration list for the active organization. The console follows every continuation token and shows integrations as their pages load.
- The `profiles` route requires `workspace_path` for `DEV_SESSION` profiles. It offers the default priority of the workload kind only when it creates a profile, because an update requires `HIGH`, `NORMAL` or `LOW`. The `dev-sessions` route shows no command, output or file content, and it does not run commands; commands and file transfers are available only through the CLI, the MCP server and the SDKs.
- When you create or edit a runner profile, enter whole numbers from 1 to 1024 for vCPUs, 1 to 16777216 MiB for memory, and 1 to 1048576 GiB for disk. The idle TTL, maximum TTL and maximum queue wait accept decimal minutes or hours that represent whole milliseconds. The idle TTL must be at most the maximum TTL when both values are valid. Invalid values show a field error and keep the dialog open without sending a request.
- The `api-keys` route shows a new secret once with a copy action and a notice that tide cannot show it again, and explains that the key works only for dev sessions. It lists the keys page by page with "Show more", so the console can show and revoke every key.
- On the `settings` route, the per-user dev session limit shows the latest confirmed value until an admin edits it. A refresh or failed save keeps the edit in the field, including when the admin clears it to remove the limit. Saving sends an update only when the edit differs from the confirmed value. After a successful save, the field follows confirmed values again unless the admin made a newer edit.
- Organization deletion tells the owner to uninstall the GitHub App in GitHub, because tide cannot uninstall it.
- The console hides actions that the user's role does not allow; the control plane still enforces every permission.
- At widths of 320 px and wider, the home organization list wraps names as needed so the full name and role badge fit inside each row.
- The organization layout supports viewports 320 px wide and wider. From 320 through 760 px, the section list scrolls horizontally above the page content. At 761 px and wider, the section list stacks vertically in a 220 px column.
- On Overview and Audit, Tab reaches the populated Waiting requests, Devices and Audit events tables. Each table shows a focus ring. When columns extend past the visible area, the left and right arrow keys scroll the table horizontally. Tab and Shift+Tab move focus past the table in either direction.
- UX follows the Toss Design Guidelines. Dialogs close with `Esc`. A form with a single critical input focuses it when it opens.
- Each form dialog opening starts without a pending request or a submission error. Only the opening that sent a request can show its error, finish its pending state, or act on its success by closing the form, navigating, or showing a one-time secret or link. A failure in the current opening allows a retry. Successful requests refresh the affected data even after dismissal. A key or invitation created after dismissal appears in its list, and the console cannot show its secret or link again.

## Storage

The console stores nothing except the Logto SDK session state in the browser (in a mock build, the fake session of the mock API). It never stores credentials in browser storage. After removing the GitHub `state` and `code` from the address bar, the console keeps them only in memory for the current callback visit.

## Security

- Credential inputs use password-type fields and are cleared after submission.
- Destructive actions (OwnSand link removal, GitHub installation unlink, integration deletion, profile deletion, runner deletion, dev session deletion, API key revocation, organization deletion, ownership transfer) need an explicit confirmation step.
- The result of a request belongs to the opening that sent it. A confirmation button is disabled while its request runs.
- After a successful leave or deletion, the console opens the organization list before it refreshes affected queries if the confirmation is still open. If the user dismisses the confirmation or moves to another page, the console refreshes the data and preserves their current URL and history. Removing another member refreshes the roster on Members.
- The console shows no runner output and no dev session output. It never stores an API key secret.

## Logging

The console sends no logs to a service in this version. Browser console messages never contain tokens or credentials.

## Build and Test

- Package scripts: `dev` (portless, started as `node node_modules/portless/dist/cli.js run --prefix=` through the shared `scripts/dev/with-infisical.mjs` with the Infisical folder `/apps/tide`, according to the [environment contract](repository-environment-contract.md#local-development-injection)), `dev:app` (`rsbuild dev`, which portless starts), `build` (`rsbuild build` into the ignored `dist/`), `preview`, `lint` and `typecheck` (`tsc --noEmit`), `test` (`rstest run` with `happy-dom`) and `test:e2e` (`e2e run`). They run through root Turborepo tasks.
- Unit tests cover the configuration rules, the router, the role matrix and the dev session delete rule, the runner profile form rules (`workspace_path` for `DEV_SESSION`, guest OS path syntax, the OpenAI Codex queue wait, the update mask, the default priority only on create), the queue view across a gap and a manual retry, the queue order, the setup steps, the GitHub callback parsing and address removal, the invitation link handling and the Logto auth bridge, and render the console against the mock API: role-based navigation and actions, the `INVALID` banner, credential forms with password fields that show only "Set at", the OpenAI Codex webhook URL, the `runs-on` label, the GitHub callback, a reconnect of the live overview, the setup guidance, confirmations of destructive actions, and a one-time API key secret that never reaches browser storage and closes with `Esc`.
- Unit tests cover sign-in session classification and the Logto callback with no pending redirect, a pending redirect, a failed callback and unreadable sessions under either storage key for signed-in and signed-out clients.
- Unit tests cover sign-in after an `Unauthenticated` response on the organizations page and in the organization shell, and retry actions for other failures.
- Runner profile tests cover resource ranges, whole-number validation, idle TTL comparison, request serialization at the resource limits, exact serialization of whole-millisecond durations, and field errors that prevent create and edit requests.
- End-to-end suite: `apps/tide/e2e/` according to the [e2e contract](repository-e2e-contract.md), against the development server with the mock flag enabled. The app command uses Node to run the Rsbuild CLI with `dev --no-env --mode development`, `NODE_ENV=production` and a padded `PUBLIC_TIDE_MOCK_API=true` value. The `--no-env` option keeps local `.env` files out of the run. The suite uses the local mock. It does not test a deployed control plane, GitHub or Logto.
- Refresh tests cover the organization layout, open forms, the one-time API key secret, affected list and section boundaries, and retries after a failed request for the next page.

## Dependencies and Integrations

- Upstream: `tide-api`, Logto, `delino-ui`, the generated TypeScript code (`@delino/tide-protos`) and the TypeScript SDK (`tide-sdk`).
- Dependencies: the exact pins of the [OwnSand console](apps-ownsand-console-foundation.md#dependencies-and-integrations) (`@connectrpc/connect` and `@connectrpc/connect-web` `2.3.0`, `@connectrpc/connect-query` `2.3.1`, `@tanstack/react-query` `5.106.1`, `@bufbuild/protobuf` `2.16.0`, `@logto/react` `4.1.3`, React `19.3.1`, and the same development tools). The console adds no new third-party dependency.
- Links to the OwnSand console and to `https://accounts.delino.io`.
