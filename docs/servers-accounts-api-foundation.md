# servers-accounts-api foundation contract

## Scope

This contract owns the `accounts-api` component of [`delino-accounts`](project-delino-accounts.md) at `servers/accounts-api/`:

- `servers/accounts-api/cmd/accounts-api/`: process entry point.
- `servers/accounts-api/internal/config/`: environment configuration loading and validation.
- `servers/accounts-api/internal/server/`: HTTP handler, routes, CORS, middleware and the connection observer that logs requests rejected before the handler runs.
- `servers/accounts-api/internal/app/`: wiring of the Connect services, their interceptors and the HTTP handler. `cmd/accounts-api` and the integration tests build the handler through it.
- `servers/accounts-api/internal/api/`: Connect service implementations (`BillingAccountService`, `CreditService`, `BillingUsageService` and `UsageService`), the RPC log interceptor, roles, billing audit events and page tokens.
- `servers/accounts-api/internal/auth/`: Logto access token validation and the Connect interceptor that applies the scope and token kind of each service; `auth/authtest/` is a test Logto issuer.
- `servers/accounts-api/internal/directory/`: Logto Management API client that reads user profiles, and its fake for tests.
- `servers/accounts-api/internal/email/`: email sender abstraction, the Resend sender, the fake for tests and the email templates.
- `servers/accounts-api/internal/billing/`: the credit ledger, the subscription, manual and automatic top-ups, the Paddle webhook handler, usage reports and their attribution, the billing status of linked organizations, billing notifications and the background worker.
- `servers/accounts-api/internal/paddle/`: the minimal Paddle Billing API client and the webhook signature verification; `paddle/paddletest/` is a fake Paddle API for tests.
- `servers/accounts-api/internal/metrics/`: the OpenTelemetry metrics and the internal metrics listener. The shared `servers/internal/telemetry` package sets up the OpenTelemetry SDK.
- `servers/accounts-api/internal/db/`: Postgres pool, embedded goose migrations in `internal/db/migrations/` and the test database helper `internal/db/dbtest/`.
- `servers/accounts-api/internal/testenv/`: in-process server for the Postgres-backed integration tests.
- `servers/accounts-api/.env.example`: configuration names and safe loopback defaults.
- `servers/accounts-api/package.json` and `turbo.json`: workspace task wiring and the `deploy` field.
- `servers/accounts-api/Dockerfile`: runtime image of the Droplet deployment.
- `servers/accounts-api/scripts/`: development launcher (`dev.mjs`) and its process-level tests.

The API server is the system of record for account and billing information: billing accounts, members, invitations, credit grants, the ledger, subscriptions, organization links, usage reports and billing statuses. It is licensed under `FSL-1.1-ALv2` according to the [license contract](repository-license-contract.md).

## Runtime and Language

- Language: Go, in the repository root module `github.com/delinoio/mono`. The import path of the server packages is `github.com/delinoio/mono/servers/accounts-api/...`. The `go` directive in the root `go.mod` selects the toolchain version.
- Runtime: one long-running HTTP server process with the dependencies in [Dependencies and Integrations](#dependencies-and-integrations), a billing worker and an internal metrics listener on `METRICS_ADDR` (see [Metrics](#metrics)). Every 30 seconds, and at once after a usage deduction queues an automatic top-up, the worker charges queued automatic top-ups, fails top-ups that waited too long for their result, expires credit grants, records the suspension of linked organizations whose suspension time has passed, queues credit expiry notices, delivers billing emails and refreshes the linked-organization metrics. Several instances may run it at the same time, because every task locks what it changes.
- Startup: the server validates the configuration, creates the Postgres pool, applies the pending migrations unless `RUN_MIGRATIONS=false`, and only then listens, so `GET /healthz` answers only after the migrations. The pool connects on first use: with `RUN_MIGRATIONS=false` the server starts without contacting the database, and RPCs fail until it is reachable. A failed migration stops the server with a non-zero status. The server binds the public listener and, when `METRICS_ADDR` is set, the metrics listener before it starts the billing worker, so a listener that cannot be bound stops the server with a non-zero status before any billing work, and thus any Paddle call, starts.
- Logging: `log/slog`.
- HTTP timeouts: `newServer` in `cmd/accounts-api` sets fixed constants on the `http.Server`. They are not configuration variables, so they have no `.env.example` entry and no Turbo `passThroughEnv` entry.
  - `ReadHeaderTimeout` is 10 seconds: the time a client has to send the request headers.
  - `ReadTimeout` is 30 seconds and covers the whole request read, headers and body. `net/http` clears the header deadline after the headers arrive, so without `ReadTimeout` a client that declares a body and then sends nothing would hold the connection open forever. `ReadTimeout` must stay greater than or equal to `ReadHeaderTimeout`.
  - `WriteTimeout` is 30 seconds for writing a response.
  - `IdleTimeout` is 120 seconds: a keep-alive connection that is waiting for the next request is closed after this time.
  - `WriteTimeout` limits the lifetime of every response, so a long-lived streaming RPC must lift or extend it for that handler (`http.ResponseController.SetWriteDeadline`) in the change that adds the stream.
- Deployment target: the Droplet service `accounts-api` on the shared DigitalOcean Droplet, deployed by the [deployment workflow](repository-workflow-contract.md#deployment-workflow). The `deploy` field sets the host name `accounts.api.delino.io` and the container port `8080`. The workflow builds a static `linux/amd64` binary with `CGO_ENABLED=0`; `servers/accounts-api/turbo.json` passes `CGO_ENABLED`, `GOOS` and `GOARCH` through to the uncached `build` task. The `Dockerfile` copies `dist/accounts-api`, the FSL-1.1-ALv2 `LICENSE` (`/usr/share/licenses/accounts-api/LICENSE`) and the Go toolchain BSD-3-Clause notice (`/usr/share/licenses/accounts-api/GO-LICENSE`) into the digest-pinned `gcr.io/distroless/static-debian12:nonroot` image and runs it as the `nonroot` user. The deployment checks `GET /healthz` before the reverse proxy sends traffic to the new container, and Docker restarts the container when the process exits (restart policy `unless-stopped`).
- Configuration source: the env file `/srv/delino/env/accounts-api.env` on the Droplet, which maintainers keep. The deployment sets `ADDR` to `:8080` from the `deploy` field, so the env file must not set `ADDR`. Secrets are also in the env file; they never enter the repository or the GitHub environment.
- TLS termination: the Caddy reverse proxy on the Droplet terminates TLS for `accounts.api.delino.io` and forwards plain HTTP/1.1 to the container.

No browser origin is needed.

This needs an `AccountService` RPC that returns the display profiles of a list of users, and a scope for it. Record the RPC and the scope here in the change that adds them. No browser origin is needed.
- Operators who deploy and monitor the server.

## Interfaces and Contracts

- Production origin: `https://accounts.api.delino.io`.
- Operational endpoints:

| Endpoint ID      | Method and path                  | Authentication               | Response                                                                |
| ---------------- | -------------------------------- | ---------------------------- | ----------------------------------------------------------------------- |
| `healthz`        | `GET /healthz`                   | none                         | `200` with `{"status":"ok"}` while the process can serve HTTP requests. |
| `paddle-webhook` | `POST /webhooks/paddle`          | Paddle signature             | See [Paddle webhook](#paddle-webhook).                                  |
| `metrics`        | `GET /metrics` on `METRICS_ADDR` | none; internal listener only | Prometheus format of the metrics. See [Metrics](#metrics).              |

- Connect-only exception: `POST /webhooks/paddle` is a plain HTTP endpoint, because Paddle does not call Connect RPC. It is the only plain HTTP endpoint besides the operational endpoints.
- Request size limits: every Connect procedure reads at most 1 MiB of a request message (`connect.WithReadMaxBytes`, the constant `maxRequestBytes` in `internal/api`), counted after decompression, so a gzip request that inflates over 1 MiB is rejected like a plain one. connect-go reads the message before it runs the interceptors, so the server rejects an oversized request with `resource_exhausted` (HTTP `429`) before it checks the Logto token and before the `auth_rejected` log record; it does not buffer more than the limit. The limit leaves the largest valid request (`ReportUsage` with 500 reports, about 163 KiB in protojson) a wide margin. `POST /webhooks/paddle` keeps its own limit of 1 MiB and answers `413` (see [Paddle webhook](#paddle-webhook)). Time limits are separate: the server timeouts bound the duration of a request, not its size.
- Business APIs: Connect RPC services generated from `protos/delino/accounts/v1/`, served under their Connect paths (`/delino.accounts.v1.<Service>/<Rpc>`). The [protos contract](protos-delino-accounts-api-contract.md) owns every RPC, message and enum.

| Service ID              | Status      | Responsibility                                                                                                 |
| ----------------------- | ----------- | -------------------------------------------------------------------------------------------------------------- |
| `AccountService`        | planned     | Read and update the profile and preferences of the signed-in Logto user.                                       |
| `BillingAccountService` | implemented | Billing accounts, members, roles, email invitations and ownership transfer.                                    |
| `CreditService`         | implemented | Balance, credit grants, ledger, the Paddle subscription, manual and automatic top-ups, alerts and invoices.    |
| `BillingUsageService`   | implemented | Linked organizations and the monthly usage of a billing account by service, organization and meter, for users. |
| `UsageService`          | implemented | Usage reports, billing statuses, organization links and organization billing reads, for services only.         |

### Authentication

- Status: implemented. `auth.DefaultPolicy` maps every service of the protos contract to its scope and token kind; a procedure of a service without an entry is denied with `permission_denied`. A service is reachable only after the server mounts its handler.
- The server is the Logto API resource `https://accounts.api.delino.io`. It validates every access token according to the [authentication contract](repository-auth-contract.md#token-validation): signature, issuer, expiry, the audience `https://accounts.api.delino.io` and the scope of the RPC. ID tokens are rejected.

| Scope                   | Token kind                      | Services                                                           |
| ----------------------- | ------------------------------- | ------------------------------------------------------------------ |
| `accounts:billing`      | End-user access token           | `BillingAccountService`, `CreditService` and `BillingUsageService` |
| `accounts:report-usage` | Machine-to-machine access token | `UsageService`                                                     |

- A missing, expired or otherwise invalid token, and an ID token, fail with `unauthenticated`. A valid token without the scope of the service fails with `permission_denied`.
- Validation follows the [authentication contract](repository-auth-contract.md#token-validation): the JWS signature with a key of the issuer's key set (`<LOGTO_ISSUER>/jwks`, fetched on the first token, cached for 10 minutes and fetched again at most once a minute, also for an unknown key ID), the RFC 9068 token type `at+jwt` (an ID token has another type and the client ID as audience), `iss` equal to `LOGTO_ISSUER`, `aud` containing `LOGTO_AUDIENCE`, `exp` and `nbf` with 30 seconds of clock leeway, and a non-empty `sub`.
- Logto client credentials tokens carry the application ID as `sub`, equal to `client_id`. The server accepts `UsageService` calls only with such a machine-to-machine token, and rejects machine-to-machine tokens on the user services, with `permission_denied` in both cases. Only the machine-to-machine applications of consuming services get the role that holds `accounts:report-usage`.
- Service mapping: the server maps each machine-to-machine client ID (the `client_id` claim) to the `ServiceId` values that it may use through `USAGE_SERVICE_CLIENTS` (see [Configuration](#configuration)). A `UsageService` request for another service fails with `permission_denied`, and a client without a mapping gets `permission_denied` for every `UsageService` RPC, also for `ListManageableBillingAccounts`, which names no service. The check runs after the request fields are validated and is logged as `usage_client_not_mapped` or `usage_client_service_denied` with the client ID.
- Logto application registrations: the [web app](apps-delino-accounts-foundation.md) is a single-page application that requests `accounts:billing`. Each consuming service has its own machine-to-machine application. The server itself has a machine-to-machine application for the Logto Management API (`LOGTO_M2M_CLIENT_ID`), which it uses only to read Logto user profiles: the primary email of the caller of `AcceptInvitation` and the display names (`name`) of `ListMembers`. The application needs the Management API role of the tenant.
- Logto Management API (recorded decision): `LOGTO_MANAGEMENT_ENDPOINT` is the default Logto endpoint of the tenant, `https://<tenant-id>.logto.app`, not a custom domain. The server gets a token from `<endpoint>/oidc/token` with the client credentials grant, HTTP Basic client authentication, the resource `<endpoint>/api` and the scope `all`, caches it until 1 minute before it expires, and reads `GET <endpoint>/api/users/{userId}`. A `401` renews the token once. An unknown user (`404`) is a user without an email address; any other failure of `AcceptInvitation` is `unavailable`, and a display name that cannot be read is empty. `ListMembers` reads at most 8 profiles at the same time and waits at most 5 seconds for them.
- Browser access: CORS allows only the origins in `CORS_ORIGINS`: `https://accounts.delino.io` in production and the local web app origins in development (see [Development Launcher](#development-launcher)). The server compares the `Origin` header with the canonical form of each configured origin, so an entry with an upper-case host or the default port matches the origin that the browser sends. A preflight from an allowed origin gets `204` with the Connect request headers, `GET, POST` and a 2-hour `Access-Control-Max-Age`; a preflight from another origin gets `403`, and other requests from another origin get no CORS headers.
- The Paddle webhook accepts no Logto credential. Its Paddle signature authenticates only the delivery of an event from Paddle. It gives no access to any RPC.

### Billing accounts and members

- A billing account is a separate entity. Any signed-in Logto user can create one and becomes its `owner`.

| Action                                                                                          | `owner` | `admin` | `viewer` |
| ----------------------------------------------------------------------------------------------- | ------- | ------- | -------- |
| Delete the billing account, transfer ownership                                                  | yes     | no      | no       |
| Payment method, subscription, manual top-up, automatic top-up, alerts and organization links    | yes     | yes     | no       |
| Invitations, roles of admins and viewers, removal of admins and viewers, renaming               | yes     | yes     | no       |
| Invoices and invoice links (they carry the payer's address)                                     | yes     | yes     | no       |
| Read the balance, credit grants, ledger, subscription, usage, settings and linked organizations | yes     | yes     | yes      |

- Access errors: a caller that is not a member of the named billing account gets `not_found`, also when the account exists, and a deleted billing account is `not_found` for every RPC. A member whose role does not allow the action gets `permission_denied`.
- A billing account has exactly one `owner`. Nobody can change the role of the `owner` or remove the `owner` (`failed_precondition`), and nobody can grant `owner` with a role change or an invitation. Only `TransferOwnership` makes another existing member the `owner`, and the previous owner becomes `admin`. Every `admin` and `viewer` may remove itself.
- Owners and admins invite by email address with the role `admin` or `viewer`; a second pending invitation for the same address fails with `already_exists`. The server sends the invitation email through Resend with a link to the [web app](apps-delino-accounts-foundation.md) that carries a one-time invitation token (`bai_` followed by 32 random bytes in unpadded base64url). An invitation expires 7 days after it is created. `AcceptInvitation` accepts the token only for a signed-in user whose Logto primary email equals the invited address (ASCII case folding), and creates the membership for that Logto user ID; another user gets `permission_denied`, and the invitation stays pending. An unknown token is `not_found`; an accepted, revoked or expired invitation is `failed_precondition`. The server stores only the SHA-256 hash of the token.
- One billing account can pay for several organizations of several Delino services. A change of members has no effect on existing links.
- `DeleteBillingAccount` succeeds only when the balance is 0 or more and no organization is linked; otherwise it fails with `failed_precondition`. It cancels the Paddle subscription at once, forfeits the remaining credit (credits are not refunded), ends every membership and pending invitation and marks the billing account deleted. Financial records and audit events stay for the retention period (see [Storage](#storage)).
  - The cancellation (`POST /subscriptions/{id}/cancel` with `effective_from: immediately`) runs in the deletion transaction. When Paddle is unavailable the deletion fails with `unavailable`, and when Paddle rejects the cancellation it fails with `failed_precondition`; nothing changes in either case. A subscription that Paddle does not know any more counts as canceled.
  - The forfeited credit leaves the balance as one `EXPIRY` ledger entry for each grant with remaining credit (recorded decision: the ledger has no separate forfeiture kind). Queued automatic top-ups fail and automatic top-up turns off.
  - Paddle webhooks for a deleted billing account add no credit and remove none. A subscription that a checkout creates after the deletion is logged as `billing_subscription_of_deleted_account` for operators, who cancel it in the Paddle dashboard.
- The [protos contract](protos-delino-accounts-api-contract.md) records the exact request rules, limits and error codes of every RPC.
- Implementation rules (recorded decisions):
  - Every change of members, invitations, the name or the deletion state locks the billing account row first, so changes of one billing account serialize.
  - A mutation reads the caller's membership in a statement that starts after it holds the billing account lock, so a role change, removal or ownership transfer that committed while the mutation waited for the lock applies to it: a removed caller gets `not_found`, a caller whose role no longer allows the action gets `permission_denied`.
  - A request `user_id` (`UpdateMemberRole`, `RemoveMember`, `TransferOwnership`, `LinkOrganization` and `ListManageableBillingAccounts`) that is empty, longer than 256 bytes, not valid UTF-8 or contains a NUL character is `invalid_argument` before any query, because Postgres cannot store `U+0000` in text; an unknown ordinary user ID keeps its result (`not_found` or an empty list).
  - Access checks run in this order: the request fields (`invalid_argument`), the membership (`not_found`), the role (`permission_denied`) and then the state of the target (`not_found`, `failed_precondition`, `already_exists`).
  - `CreateInvitation` commits the invitation first and sends the invitation email after that transaction has committed, so a rolled-back transaction never sends an email for an invitation that does not exist. When Resend accepts the email, a second transaction records the `invitation_created` audit event. When the send fails, the server revokes the invitation in a compensating transaction under the billing account lock (`revoke_time` set, `invitation_revoked` audit event with `reason` `delivery_failed`) and fails the RPC with `unavailable`. The failed invitation therefore ends revoked, has no `invitation_created` audit event and no longer blocks a new invitation for its address, so the caller recovers by inviting again. If the server stops between the commit and the send, or the compensating transaction fails, the invitation stays pending without an email; an owner or admin revokes it with `RevokeInvitation` and invites again. If Resend accepted the email but the `invitation_created` audit event cannot be stored, the server revokes the invitation with `reason` `audit_failed` and fails the RPC with `internal`. The Resend idempotency key `invitation/<invitation_id>` makes a repeated send of one invitation one email; every new invitation has a new ID and so gets its own email.
  - Two addresses are the same address for the pending-invitation check and for `AcceptInvitation` when they are equal after ASCII letters are lower-cased; other characters are compared unchanged. An expired invitation no longer blocks a new invitation for its address.
  - `AcceptInvitation` checks the token before it reads the caller's Logto profile: an empty token is `invalid_argument`, a token that is not well formed or unknown is `not_found`, and an accepted, revoked or expired invitation is `failed_precondition`. Then a caller without a primary email, or with another one, is `permission_denied`, and an existing member is `already_exists`. The server checks the invitation again inside the transaction, after it locked the billing account and after the Logto lookup, with a fresh clock reading; an invitation that expired during the lookup or the lock wait is `failed_precondition` and leaves the invitation, membership and audit rows unchanged. The membership `create_time`, the invitation `accept_time`, the audit event time and the response member `create_time` use that reading.
  - Page tokens are unsigned base64url JSON that binds the position to the RPC and its scope (the caller for `ListBillingAccounts`, the billing account otherwise). A token of another RPC, caller or billing account, and any value that does not decode, is `invalid_argument`. A forged token can only select another position in a result that the caller may read. A position with a negative time (`t`) or a NUL character in its sort key (`a`) is also `invalid_argument`, because no server-issued token has one and Postgres cannot store `U+0000` in text; the time `0` of `ListMembers` and any later time stay valid. `ListMembers` orders by join time and then by user ID.
  - A removed member and every member of a deleted billing account leave no membership row; the billing audit events keep the history.

### Payments and credits

- Payment provider (recorded decision): [Paddle](https://www.paddle.com/), the merchant of record, in the `sandbox` or `production` environment that `PADDLE_ENVIRONMENT` selects. The server calls the Paddle API with a minimal hand-written HTTP client; it uses no Paddle SDK.
- Charges are USD only and tax-exclusive. When a user buys $X of credit, Paddle adds the tax on top, and the balance receives the full $X.
- Conversion: Paddle amounts are whole USD cents. The server converts cents to micro-USD by multiplying by 10,000, only at the payment boundary. The conversion is exact and needs no rounding. Every amount that the server sends to Paddle is a whole number of cents; a requested amount that is not a multiple of 10,000 micro-USD fails with `invalid_argument`.
- Subscription: an active $10/month Paddle subscription (`PADDLE_SUBSCRIPTION_PRICE_ID`) is required for any billable use of a consuming service. `StartSubscription` creates the Paddle transaction with the billing account ID in its custom data, and the web app opens the Paddle.js checkout with it. Each successful subscription payment adds a $10 credit grant. A canceled subscription stays active until the end of the paid period, and `ResumeSubscription` removes a scheduled cancellation before then. The subscription becomes `ACTIVE` only after the verified payment webhook; while it is `PENDING`, `StartSubscription` returns the open checkout transaction again.
- Manual top-up: owners and admins add credit with a one-time charge on the subscription (`POST /subscriptions/{id}/charge` with `effective_from: immediately`, on `PADDLE_TOP_UP_PRODUCT_ID`), only while the subscription is `ACTIVE`. The amount is at least $25 and at most $10,000, in whole cents. The caller's `idempotency_key` (UUID v7) makes a retry within 24 hours return the first result without a second charge.
- Automatic top-up: off by default. An owner or admin turns it on with a threshold of at least $10, an amount of at least $25 and at most $10,000 and a required monthly cap of at least the amount. Other settings fail with `invalid_argument`.
  - It runs when a usage deduction makes the balance fall below the threshold. At most one automatic top-up is in flight for each billing account.
  - The monthly cap counts only automatic top-ups in a UTC calendar month; the subscription and manual top-ups do not count. A top-up that would exceed the cap does not run. An automatic top-up belongs to the UTC month of its cap time (`top_ups.cap_time`): the queue time while it is queued, and the claim time once the worker claims it. The claim checks the cap and sets the cap time with the same timestamp in the same transaction under the billing account lock, so a top-up queued before the end of a UTC month and claimed after it counts in the month of the claim, and the cap and `month_to_date_usd_micros` of that month include it. `create_time` stays the queue time. A row without a cap time (every row from before migration `00006`) counts in the month of its `create_time`.
  - The worker revalidates the current settings when it claims a queued top-up, before the Paddle call. A queued top-up that the current settings no longer allow (automatic top-up is off, its amount is above the current amount, or the monthly cap leaves no room for it, not counting the top-up itself) fails with the reason `settings_changed` without a Paddle call. This failure does not count toward the 2 failures in a row and sends no email. A queued top-up that the settings still allow charges its queued amount once. A top-up that Paddle already has (charging, accepted or with an unknown result) keeps waiting for its webhook or timeout whatever the settings say.
  - The server charges the amount with `POST /subscriptions/{id}/charge` (`effective_from: immediately`). A charge that Paddle rejects, for example because the subscription is `past_due` or its next billing period starts within 30 minutes, and a failed payment count as failed automatic top-ups.
  - After 2 failed automatic top-ups in a row, automatic top-up turns off, and owners and admins get an email. A successful automatic top-up and enabling the setting reset the count.
- Credit is added only by verified Paddle webhooks, never by the charge call or the checkout.
- Credit grants: each subscription payment, manual top-up and automatic top-up creates a grant that expires 12 months after the purchase. Usage consumes the grant that expires first (FIFO). A new grant first pays off any debt (a negative balance), and only the rest becomes usable credit. Owners and admins get an email 7 days before a grant expires. Expired credit leaves the balance as an `EXPIRY` ledger entry.
- Refunds: credits are non-refundable. Support can refund only manually in the Paddle dashboard. The refund webhook removes the matching credit with a `REFUND` ledger entry, and the balance can go negative.
- Debt: usage is always deducted, also below zero. A negative balance is debt.
- Low-balance alert: when automatic top-up is off, owners and admins get one email each time the balance falls below the alert threshold. Owners and admins set the threshold (at least $0). The default is $10.
- Invoices (owner and admin only): `ListInvoices` lists the completed Paddle transactions without links, and `GetInvoiceUrl` returns a short-lived link to the Paddle invoice PDF of one transaction, from Paddle `GET /transactions/{id}/invoice` on demand.
- Implementation rules (recorded decisions):
  - Every credit change locks the billing account row first and keeps `billing_accounts.balance_usd_micros` equal to the ledger in the same transaction. While the balance is zero or more it equals the remaining credit of the grants; while it is negative no grant has remaining credit. Every credit change first removes the credit of grants that expired, so usage never consumes expired credit, also when the worker is late. `GetBalance` leaves out expired credit that the worker has not removed yet. `GetBalance` reads the balance, the credit that is due and the grants in one SQL statement, so both fields of a response share one read snapshot: a concurrent credit change cannot pair the balance of one state with the grants of another.
  - FIFO: usage consumes grants in `expire_time` order, then by grant ID. A grant expires 12 calendar months after its creation, in UTC; its `create_time` is the time of the verified webhook.
  - Paddle calls: the checkout transaction is `POST /transactions` with one unit of `PADDLE_SUBSCRIPTION_PRICE_ID`, `collection_mode: automatic` and the custom data `billing_account_id`. Cancellation is `POST /subscriptions/{id}/cancel` with `effective_from: next_billing_period`, and `ResumeSubscription` sends `PATCH /subscriptions/{id}` with `scheduled_change: null`. A top-up is `POST /subscriptions/{id}/charge` with `effective_from: immediately`, `on_payment_failure: prevent_change` and one non-catalog price on `PADDLE_TOP_UP_PRODUCT_ID` (`tax_mode: external`, the amount in cents) whose custom data carries the top-up ID (`top_up_id`) and the billing account ID. Paddle collects the charge at once with the payment method of the subscription; with `prevent_change` a declined payment fails the call with `subscription_payment_declined`. The response holds the subscription only, so the webhook of the resulting transaction (origin `subscription_charge`) is matched to the top-up through `items[].price.custom_data.top_up_id`. A charge transaction without a known top-up ID becomes a `MANUAL_TOP_UP` grant.
  - Paddle outcomes: a `4xx` answer other than `401`, `403`, `404` and `429` is a rejection; `401`, `403`, `429` and a request that was not sent changed nothing at Paddle; a `5xx` answer, a timeout or a broken connection has an unknown result. The status of an answer decides the outcome even when its body cannot be read: the client keeps the status without a code, type or request ID, so an unreadable `429` changed nothing and an unreadable `5xx` stays unknown, while a `2xx` answer with an unreadable body stays unknown. A rejected, `past_due` (`subscription_update_when_past_due`) or too-soon (`subscription_next_billed_at_too_soon`, the next billing period within 30 minutes) charge, a failed payment webhook and a top-up without a result after 1 hour count as failed automatic top-ups. A charge that changed nothing at Paddle fails an automatic top-up without counting toward the shutoff.
  - Manual top-up: the RPC records the top-up under the billing account lock before it calls Paddle, so a concurrent retry with the same key charges nothing again. A repeated key returns success after Paddle accepted the charge, `failed_precondition` after a rejection and `unavailable` while the result is unknown. When Paddle changed nothing (`401`, `403` or `429`) the top-up is removed and the call fails with `unavailable`, so a retry with the same key charges. The Paddle call is not canceled when the client disconnects. The Paddle call (at most 20 seconds) and the transaction that records its outcome (at most 10 seconds, started after the call returned) have separate deadlines, so a call that used its whole budget (a timeout) still records the unknown result; the outcome update applies only to a top-up that is still `charging`, so a webhook that finalized it first stays authoritative. An outcome transaction that exceeds its own deadline returns the database error to the caller (the automatic worker stops its run), and the top-up stays `charging` for the 1-hour timeout to resolve; a retry with the same key then sends no second charge. Automatic top-ups use the same two deadlines.
  - Automatic top-up trigger: a usage deduction with a positive amount after which the balance is below the threshold queues one, unless one is in flight (queued, charging, accepted or with an unknown result), the subscription is not `ACTIVE` or `PAST_DUE`, or the monthly cap would be exceeded. So a deduction after a failed top-up tries again, and 2 failures in a row turn the setting off. The cap and `month_to_date_usd_micros` count the automatic top-ups of the UTC month that did not fail, including those in flight.
  - A top-up that failed by timeout still completes when its verified webhook arrives later: the credit is added, and a completed automatic top-up resets the failure count.
  - Credit amounts: a subscription payment adds 10 USD. A top-up adds the transaction subtotal minus discounts (`details.totals`), which is tax exclusive, in cents times 10,000; a difference from the requested amount is logged as `billing_top_up_amount_mismatch`. Only USD transactions add credit.
  - Subscription status: Paddle `active` and `trialing` map to `ACTIVE`, `past_due` and `paused` to `PAST_DUE` and `canceled` to `CANCELED`. A subscription entity older than the stored one (`updated_at`) is ignored, as is another subscription while the current one is `ACTIVE` or `PAST_DUE`, and, while a new checkout is `PENDING` with an open checkout transaction and no Paddle subscription ID, an entity of any earlier subscription in any status (`active`, `trialing`, `past_due`, `paused` or `canceled`). Only a subscription whose entity names the checkout transaction (`transaction_id` on `subscription.created`) or whose Paddle subscription ID was not recorded for the billing account before the event (for example a `subscription.updated` of the new subscription that arrives before its `subscription.created`) completes the checkout. IDs recorded earlier, including those that a late payment recorded, count as earlier subscriptions; the server logs `billing_subscription_entity_ignored` with the billing account, Paddle subscription and checkout transaction IDs and leaves the row unchanged. A canceled entity never replaces a `PENDING` row. A verified subscription payment also makes the subscription `ACTIVE`, in case the transaction webhook arrives first. While the subscription is `PENDING` with an open checkout transaction and no Paddle subscription ID, only the payment of that checkout transaction does so. The verified payment of another transaction, for example a late renewal of a canceled earlier subscription, still adds its credit grant once and records its Paddle subscription for billing account lookup, but leaves the row `PENDING` with the same checkout transaction and `cancel_at_period_end` unchanged; the server logs `billing_subscription_payment_ignored` with the billing account, Paddle subscription and transaction IDs. A `PENDING` row without a checkout transaction becomes `ACTIVE` from the first verified subscription payment.
  - Refunds and chargebacks: an `adjustment.created` or `adjustment.updated` event with the action `refund` or `chargeback` and the status `approved` removes its tax-exclusive subtotal, at most the credit of the purchase that is not removed yet, with one `REFUND` entry. The credit comes first from the grant of the purchase, then from the other grants in FIFO order, and the rest makes the balance negative. Each adjustment ID applies once. Paddle does not order its notifications, so an approved adjustment whose purchase has no credit grant yet is stored as pending (adjustment ID, purchase transaction ID, action and tax-exclusive amount) and acknowledged without a balance change. The webhook that creates the grant of the purchase applies the pending adjustments, oldest first, in the same transaction through the same refund accounting, with the same cap, `REFUND` entries and `credit_refunds` rows, and deletes the pending rows. So the final ledger effect is the same in either delivery order. A pending adjustment of a purchase that never creates a grant has no balance effect; it stays stored, and expiring such rows is not part of this contract. A purchase's grant and its adjustments are serialized by a transaction-scoped advisory lock on the Paddle transaction ID, taken before the billing account lock in both paths, so overlapping deliveries neither lose nor repeat a reversal.
  - Low-balance alert: with automatic top-up off, the first decrease of the balance (usage, expiry or refund) below the alert threshold queues one email; the next one follows only after the balance has reached the threshold again or the threshold has changed.

### Paddle webhook

- `POST /webhooks/paddle` verifies the `Paddle-Signature` header (`ts=<unix time>;h1=<hex HMAC-SHA256 of "<ts>:<raw body>" with PADDLE_WEBHOOK_SECRET>`) in constant time before it parses the payload, and rejects a timestamp more than 5 minutes from the server time. A missing or invalid signature gets `401` and changes nothing. While Paddle rotates the secret a header can carry several `h1` values; one match is enough. The body is limited to 1 MiB.
- The server records each Paddle event ID and ignores a repeated event, so a replayed webhook adds no credit. Each purchase transaction also adds at most one grant, also when it arrives in another event.
- The server applies the event (credit grant, refund, subscription status or failed payment) in the same transaction that records the event ID, and then answers `200`. A failure rolls everything back, including the event ID, and answers `500`, so Paddle delivers the event again.
- Applied event types: `transaction.completed` (credit), `transaction.payment_failed` (a failed top-up, or the payment-failed email for a failed renewal; failed attempts inside the checkout are ignored), every `subscription.*` event (status, period end and scheduled cancellation) and `adjustment.created` and `adjustment.updated` (refunds and chargebacks). Other event types are recorded and ignored.
- Billing account lookup: the checkout transactions and Paddle subscriptions that the server recorded, then the top-up ID of a one-time charge, and last the `billing_account_id` custom data, which must name an existing billing account. An event without a billing account is recorded as `unmatched`. An approved adjustment of a purchase without a grant is recorded as `pending` and logged as `billing_refund_pending` (event, transaction and adjustment IDs, action and amount, never the raw payload); the later application is logged as `billing_credit_refunded` with `from_pending` set.

### Usage reports and billing status

- `UsageService` implements the [usage reports](protos-delino-accounts-api-contract.md#usage-reports), the [billing status](protos-delino-accounts-api-contract.md#billing-status) and the [links](protos-delino-accounts-api-contract.md#links) of the protos contract: idempotent reports with the key (service, organization, meter, window start), attribution through the link history, unattributed usage, FIFO deductions that can make the balance negative, and the status rules `ALLOWED`, `BLOCKED` and `SUSPENDED` (3 days after the block starts).
- `ReportUsage` validates every report of a request before it applies any, and a window may end at most 1 minute after the server time. A repeated key with other values keeps the first values and is logged as a mismatch. A status poll with cursor 0 returns every linked organization, with at most one entry per organization, and an unlink adds no entry ([protos contract](protos-delino-accounts-api-contract.md#billing-status)).
- Concurrent reports for one billing account serialize on the billing account, so the balance, the grants and the automatic top-up trigger stay consistent.
- A status change of a linked organization sends an email to owners and admins when it becomes `BLOCKED` (with the suspension time, 3 days later) and when it becomes `SUSPENDED`.
- Implementation rules (recorded decisions):
  - `ReportUsage` applies the reports in request order, each in its own transaction, after the whole request was validated. An attributed report locks its billing account first, then claims its key in `usage_reports` (unique on service, organization, meter and window start) and deducts through the ledger in the same transaction, so a report and its deduction commit together. A concurrent report with the same key waits for the first one and returns its result as a duplicate. When a link or unlink changed the attribution between the read and the billing account lock, the report is attributed again. A report that finds no link takes a transaction-scoped advisory lock on the service and organization (`usage_attr:<service>:<organization ID>`) before its last attribution read and holds it until it stores the unattributed row, and a new link takes the same lock after its billing account lock and holds it until commit. So a link that overlaps the window of such a report either commits before the report's last read, which then finds it and attributes the report again, or inserts after the unattributed row is stored; a report is never stored as unattributed while a committed overlapping link exists at its insert. Lock order: the billing account row first, then the organization lock; the unattributed path takes only the organization lock and the attributed path only the billing account lock, so they cannot deadlock. Attributing a report whose unattributed row committed before a later link is not part of this rule. A new link receives its `link_time` (and the time of its audit event) after it holds both the billing account lock and the organization lock, from a clock read taken then, not from the read at the start of the request; a link that waited for a report that stored an unattributed row therefore starts after that report committed, so a first link cannot start inside the window of a completed unattributed report, which is replayed as unattributed on a retry. A rename of an existing link keeps the request time, and the link-history selection of an attribution does not change.
  - Attribution: the link of the organization whose `[link_time, unlink_time)` overlaps the window; of several, the one with the latest link time. A report of a link to a billing account that was deleted later is still charged to it.
  - Billing standing: a billing account is in good standing while its subscription is `ACTIVE` and its balance (without credit that expired but that the worker has not removed yet) is greater than zero. `billing_accounts.nonpayment_since` records the start of the uninterrupted non-payment. Every transaction that changes the balance or the subscription (usage deductions, credit grants, expiry, refunds, Paddle subscription events, cancel and resume) recomputes the statuses of the current links of the billing account under its lock, and so does a new link.
  - Sequences: a status change takes the next value of the per-service row in `billing_status_sequences` and holds its lock until the transaction commits, so sequences become visible in commit order and a poll cursor never skips a change. The lock order is the billing account, then the sequence rows in service order.
  - Suspension: the worker records due suspensions every 30 seconds. `ListBillingStatusChanges`, `ReportUsage`, `LinkOrganization`, `GetOrganizationBilling` and `ListLinkedOrganizations` also record a due suspension of the links that they return before they read, so no response reports `BLOCKED` after the suspension time. Each call records all due suspensions that match its filter (a service, a list of billing accounts, or both), not only the first ones: it selects the billing accounts with due `BLOCKED` links in batches of 100 in billing account ID order, after the last account of the previous batch, and recomputes each account in its own transaction. The cursor only moves forward, so the loop ends even when an account stays due after its recomputation. A call without due links runs one query and recomputes nothing. A call that recomputed accounts logs `billing_suspend_due` with the number of accounts and batches.
  - Blocked and suspended emails: one notification per link and block start (deduplication keys `organization_blocked/<organization_link_id>/<blocked_since in Unix microseconds>` and `organization_suspended/<organization_link_id>/<blocked_since in Unix microseconds>`). A new link to a billing account that is not in good standing is `BLOCKED` at once from its link time and sends the blocked email too.
  - `LinkOrganization` locks the billing account, then the current link of the organization. A concurrent link of the organization to another billing account that commits first makes the later one fail with `already_exists` (the partial unique index of current links). `UnlinkOrganization` locks the billing account of the current link, then sets its unlink time.
  - Pagination: `ListManageableBillingAccounts` orders by billing account ID with a page token bound to the user ID; `ListLinkedOrganizations` orders by link time and link ID; `ListUsageSummary` binds its page token to the billing account and the month.
  - Usage summary snapshot: `ListUsageSummary` computes the total amount of the month and the rows of the page in one SQL statement, so the total and the rows of a response come from the same set of committed reports. A page without rows (an empty month or a page after the last row) still returns the total.
  - Saturated sums: the monthly sums of `GetOrganizationBilling` and `ListUsageSummary` (the quantity and the amount of each meter or row, and the total amount) are computed in Postgres as `numeric` and saturate at `9223372036854775807` before the `bigint` cast, so a month whose reports add up beyond the `int64` range returns that value instead of an `internal` error. `ReportUsage` and the stored `usage_reports` rows are not changed; they keep each report exact.

### Emails

- Delivery: Resend, with the API key `RESEND_API_KEY` and the sender `EMAIL_FROM`, in English, as plain text and simple HTML. A sender abstraction (`email.Sender`) has a fake for tests that records the messages. Each message carries a `kind` tag and a Resend idempotency key.
- Recipients are the `owner` and `admin` members of the billing account, except the invitation, which goes to the invited address.

| Email                       | Trigger                                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Invitation                  | `CreateInvitation`                                                                                                        |
| Payment failed              | A failed automatic top-up, a manual top-up that failed after Paddle accepted the charge, or a failed subscription renewal |
| Automatic top-up turned off | The second failed automatic top-up in a row                                                                               |
| Low balance                 | The balance falls below the alert threshold while automatic top-up is off                                                 |
| Blocked                     | A linked organization becomes `BLOCKED`; includes the suspension time                                                     |
| Suspended                   | A linked organization becomes `SUSPENDED`                                                                                 |
| Credit expiry               | A credit grant expires in 7 days                                                                                          |

- The invitation email has no notification record: it is sent once by `CreateInvitation` after the invitation committed (see [Billing accounts and members](#billing-accounts-and-members)). The other emails are sent by the billing worker. The server records each notification with a deduplication key in the transaction of the event that causes it, so a retried event never queues one notification twice: `payment_failed/top_up/<top_up_id>`, `payment_failed/subscription/<paddle_transaction_id>` (one email for each failed renewal transaction, also when Paddle retries it), `auto_top_up_disabled/<top_up_id>`, `low_balance/<billing_account_id>/<count>`, `credit_expiry/<credit_grant_id>`, `organization_blocked/<organization_link_id>/<blocked_since>` and `organization_suspended/<organization_link_id>/<blocked_since>` (the block start in Unix microseconds).
- The blocked and suspended emails name the service, the organization name that the service sent (HTML-escaped) and the organization ID, the reason, and for a block the suspension time in UTC.
- Delivery: the worker reads the primary email of each current `owner` and `admin` from the Logto Management API when it sends, and records each recipient that received the notification, so a retry sends only to the others. A failed profile read or send for one recipient does not stop the others: the worker still tries every later recipient in the same attempt, and the attempt counts as failed with the first error. A canceled or expired run context stops the attempt. The Resend idempotency key is `<deduplication key>/<user ID>`. A member without a primary email is skipped. A failed delivery is retried after 1, 2, 4 and more minutes (at most 1 hour) and abandoned after 10 attempts. Notifications of a deleted billing account are abandoned. The emails link to `<WEB_ORIGIN>/billing/<billing_account_id>`; a manual top-up that Paddle rejects in the response sends no email, because the caller sees the error.
- The invitation email links to `<WEB_ORIGIN>/billing/invitations/accept#token=<token>`, names the billing account (HTML-escaped), the role and the expiry time in UTC, and asks the recipient to sign in with the address that received it.

### Metrics

The server records its metrics with the OpenTelemetry SDK through the shared `servers/internal/telemetry` package. `GET /metrics` on `METRICS_ADDR` serves them in the Prometheus text format through the OpenTelemetry Prometheus exporter on an internal listener, a separate HTTP server with its own registry; the public handler never serves `/metrics`. The listener is reachable only on the Droplet's `delino` Docker network: the deployment publishes no host port for it, and Caddy never routes it, so it is never reachable through a public origin. An empty `METRICS_ADDR` turns the listener off. The metrics cover at least usage reports, Paddle webhooks, top-up attempts and failures, emails and the number of linked organizations for each billing status. Metric labels never contain billing account IDs, organization IDs, user IDs, email addresses or Paddle IDs. Record the metric names and labels here in the change that adds them. A scraper, dashboards and alerts are out of scope.

| Metric                                  | Labels and values                                                                                                                                                                                                                                                                |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accounts_paddle_webhooks_total`        | `event_type` (`transaction.completed`, `transaction.payment_failed`, `adjustment.created`, `adjustment.updated`, `subscription`, `other` or `unknown`) and `result` (`applied`, `duplicate`, `ignored`, `pending`, `unmatched`, `invalid_signature`, `invalid_payload`, `error`) |

- The instrument names have no `_total` suffix. The Prometheus exporter adds it to counters, so `GET /metrics` serves the names in the table. The exporter leaves out the instrumentation scope labels, so each series has only the labels in the table, and it adds a `target_info` series with the resource attributes.
- The OpenTelemetry Go runtime instrumentation adds the Go runtime metrics, for example `go_goroutine_count`, `go_memory_used_bytes` and `go_memory_gc_goal_bytes`. The server has no process metrics (`process_*`).
- OTLP export: when `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` is not empty, the server also sends the metrics over OTLP/HTTP to that endpoint, for example the Grafana Cloud OTLP gateway, every 60 seconds (the SDK default, which `OTEL_METRIC_EXPORT_INTERVAL` changes). The `service.name` resource attribute is `accounts-api` unless `OTEL_SERVICE_NAME` or `OTEL_RESOURCE_ATTRIBUTES` sets another value. Without an endpoint, no telemetry leaves the process. The OpenTelemetry SDK reads these variables and the other standard `OTEL_EXPORTER_OTLP_*` variables itself; configuration validation does not check them. A malformed `OTEL_RESOURCE_ATTRIBUTES` value stops the server at startup; an endpoint that cannot be reached only produces export failures.
- The SDK reports export failures as `telemetry_export_failed` records on standard output only. At exit, after the background tasks stop, the server flushes the OTLP export for at most 5 seconds.

### Identifiers and money

- Identifiers: persisted entities use UUID v7. User-owned records reference the Logto user ID (`sub`).
- Money: all amounts are `int64` micro-USD values with a `_usd_micros` suffix, according to the [billing contract](repository-billing-contract.md). The only provider conversion is the exact cents conversion in [Payments and credits](#payments-and-credits). `accounts-api` does no per-unit pricing: the consuming services compute and round each usage amount and document the rounding in their own contracts.

Unicode white space, such as U+00A0 (no-break space) and U+3000 (ideographic space), is not removed, so a value that contains it is not valid, also when the whole value consists of such characters. The server matches `LOG_LEVEL` against the level names with ASCII letter case folding only (`INFO` and `iNfO` select `info`). Any other character makes the value not valid, so a value that lower-cases to a level name only under Unicode case mapping, such as `İNFO` (U+0130 followed by `NFO`), stops the server at startup like any other invalid value.
- `ADDR` accepts an empty host (all interfaces), an IP address (IPv6 in brackets, with an optional zone) or an RFC 1123 hostname; configuration validation checks only the host syntax, so a hostname that does not resolve still fails when the server starts listening.
- Root `pnpm dev` and `pnpm exec turbo run dev --filter=accounts-api` pass every variable of the table above from the shell to the server through Turbo `passThroughEnv` in `servers/accounts-api/turbo.json`. Add every new configuration variable to that list in the change that makes the server read it. Values from the Infisical `/servers/accounts-api` development folder do not need that list, because the injection runs inside the task, and they override shell values.
- Production must set `ADDR` explicitly for its deployment target. The default listens on loopback only.
- Paddle and Resend use separate sandbox and production credentials. Development uses only the Paddle `sandbox` environment and Resend test credentials, according to the [environment contract](repository-environment-contract.md#billing-integration-credentials).

## Storage

The database is PlanetScale Postgres, according to the repository defaults. File uploads, such as invoice documents, use Cloudflare R2 with signed URLs according to the repository defaults unless this contract documents another choice. Invoices stay in Paddle: the server stores no invoice documents and fetches the Paddle invoice link on demand.

- Driver: `github.com/jackc/pgx/v5` (`pgxpool`). goose runs on a `database/sql` handle over the same pool (`pgx/v5/stdlib`).
- Migration tool (recorded decision): [goose](https://github.com/pressly/goose) (`github.com/pressly/goose/v3`) with SQL migrations embedded from `internal/db/migrations/`, named `<5-digit version>_<name>.sql` with a `-- +goose Up` section and no down section. goose records the applied versions in `goose_db_version`. Migrations are forward-only and are never edited after they reach `main`; a change adds a new file. The server applies pending migrations at startup unless `RUN_MIGRATIONS=false`, under a Postgres session advisory lock with the key `0x6163636f756e7473`, so instances that start together apply each migration once. The old container keeps serving while the new one starts during a deployment, so every migration must stay compatible with the code of the previous release (expand first, contract in a later release).
- Tables: `billing_accounts` (name, `balance_usd_micros`, creation, update and deletion times), `billing_account_members` (one row per current membership; a partial unique index allows at most one `owner`), `billing_account_invitations` (token SHA-256, the address as entered and its comparison key, role, inviter, creation, expiry, acceptance and revocation times), `organization_links` (one row per link with its link and unlink times; a partial unique index allows one current link per service organization) and `billing_audit_events` (kind, actor, optional target user and invitation, JSON details).
- Credit tables (migration `00002_credits.sql`): `credit_grants` (source, original, remaining and refunded credit, the unique Paddle transaction, creation, expiry and expiry notice times), `ledger_entries` (append-only; kind, signed amount, balance after, Paddle transaction, grant and the usage fields), `subscriptions` (one row per billing account with the status, the current Paddle subscription and customer, the open checkout transaction, the scheduled cancellation, the period end and the `updated_at` of the latest applied Paddle entity), `paddle_checkouts` and `paddle_subscriptions` (every checkout transaction and Paddle subscription with its billing account), `paddle_events` (processed event IDs with their result), `credit_refunds` (one row per applied Paddle adjustment), `top_ups` (manual and automatic top-ups with their status, failure reason, idempotency key and, for automatic top-ups, the nullable `cap_time` that sets the UTC month of the monthly cap, added by migration `00006_top_up_cap_time.sql`, which must be applied before the worker that reads it runs; a partial unique index allows one automatic top-up in flight per billing account), `credit_settings` (automatic top-up and alert settings; a billing account without a row has the defaults) and `billing_notifications` with `billing_notification_deliveries` (notifications with their deduplication keys and the recipients that received them). Every credit change maintains `billing_accounts.balance_usd_micros` from the ledger in the same transaction.
- Usage tables (migration `00003_usage.sql`): `usage_reports` (one row per idempotency key with the quantity, the amount, the attributed billing account and link and the `USAGE` ledger entry; unattributed reports have none), `billing_status_sequences` (the last status sequence of each service), the billing status columns of `organization_links` (status, reason, block start, suspension time, sequence and update time of the current link) and `billing_accounts.nonpayment_since`.
- Pending adjustment table (migration `00004_pending_credit_adjustments.sql`): `pending_credit_adjustments` (one row per approved Paddle adjustment whose purchase had no credit grant yet, with the purchase transaction ID, action and tax-exclusive amount in micro-USD; the grant of the purchase applies and deletes it in its own transaction).
- Complete billing status constraint (migration `00005_organization_link_status_complete.sql`): replaces the `organization_links_status_complete` check of `00003_usage.sql`, which compared nullable columns and so accepted a NULL `billing_status` or `status_reason` next to a non-null sequence or timestamp. The constraint now states `IS NOT NULL` for both columns, so a link row has no status at all, an `ALLOWED` status with the reason `none`, a sequence and no timestamps, or a `BLOCKED` or `SUSPENDED` status with a reason other than `none`, a sequence, a block start and a suspension time. Rows written by the billing status worker already satisfy it.
- The server stores Paddle customer, subscription, transaction and event IDs only. It never stores card data.
- Billing audit events record member, role, invitation, ownership, settings, subscription, top-up and link changes with the actor's Logto user ID. Implemented kinds: `billing_account_created`, `billing_account_renamed`, `billing_account_deleted`, `invitation_created` (after the email was accepted), `invitation_revoked` (with `details.reason` `delivery_failed` or `audit_failed` when the server revokes an invitation that `CreateInvitation` could not deliver or audit), `invitation_accepted`, `member_role_changed`, `member_removed`, `ownership_transferred`, `subscription_started` (a new checkout), `subscription_canceled`, `subscription_resumed`, `top_up_requested` (a new manual top-up, with its ID and amount), `auto_top_up_settings_updated` and `alert_settings_updated` (with the new values), `organization_linked` (with the service, the organization ID and name; the actor is the user that the service named), `organization_link_renamed` (a repeated link with another organization name) and `organization_unlinked` (the actor is the machine-to-machine application ID of the calling service, with `actor_kind` `machine_to_machine` in the details). Their details hold names, roles, amounts and Paddle IDs, never email addresses or tokens. Changes that Paddle webhooks and the worker make have no actor and are logged instead.
- Retention (recorded decision): usage records, the ledger, credit grants and billing audit events are kept for 7 years. Deleting a billing account (a soft delete) or unlinking or deleting an organization keeps these records. The first version has no job that deletes records after the retention period.
- Backup policy (recorded decision): the default automatic backups of PlanetScale Postgres, with no custom backup schedule. A backup is made every 12 hours and kept for 2 days, and point-in-time recovery is available in that period ([PlanetScale Postgres backups](https://planetscale.com/docs/postgres/backups)).
- Database stage (recorded decision): the [deployment workflow](repository-workflow-contract.md#deployment-workflow) has no separate database job. The new container applies the pending migrations at startup before its health check passes, so a failed migration fails the deployment and the old container keeps serving.

## Security

- Accept only Logto access tokens as API credentials. Do not accept ID tokens. The Paddle webhook is the only endpoint that accepts another proof, the Paddle signature, and only for the delivery of a Paddle event (see [Authentication](#authentication)).
- Payment card data stays with the payment provider. The server stores provider references, not raw card numbers.
- The server never logs secrets, tokens, authorization codes, application secrets, API keys, card data, payment details, invitation tokens or email bodies. It does not log email addresses at the `info` level.
- Secrets, such as the database URL, Logto Management API credentials, the Paddle API key and webhook secret, the Resend API key and the OTLP headers (`OTEL_EXPORTER_OTLP_HEADERS`), follow the [environment contract](repository-environment-contract.md): Infisical for development and the Droplet env file for production. They never appear in `.env.example`.

## Graceful Shutdown

- `SIGINT` or `SIGTERM` stops the listener from accepting new connections and starts a drain that waits at most 10 seconds (`shutdownTimeout`) for in-flight requests.
- The signal does not cancel request contexts. Request contexts derive from a server-lifetime context, so handlers that honour `r.Context()` finish their work normally while the server drains.
- The server releases its signal registration as soon as it observes the first signal, before it logs `server_shutdown_started` and starts the drain. A second `SIGINT` or `SIGTERM` during the drain therefore uses the default disposition and terminates the process immediately, with the signal as its exit cause, instead of waiting for the drain to finish. A single signal still drains in-flight requests and exits with status 0 once they finish.
- The server cancels the server-lifetime context only after the drain ends. A handler that outlives the 10-second drain observes a cancelled request context at that point, the shutdown is reported as failed, and the process exits with a non-zero status.
- After the drain the server stops the billing worker and the metrics listener and waits for them. The worker stops between steps; a Paddle charge that has started runs to its end (the call at most 20 seconds, then the write of its result at most 10 seconds) so that its result is recorded. The metrics listener drains for at most 5 seconds.

## Logging

- The server writes structured JSON logs to standard output with `log/slog`. These are service logs for log aggregation, not interactive CLI output, so they do not use ANSI color.
- When `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` is not empty, the logger also sends each record at or above `LOG_LEVEL` to the OpenTelemetry SDK through the `otelslog` log bridge, which exports the records in batches over OTLP/HTTP. Standard output receives every record in both cases.
- Startup logs the listen address, the log level and whether the OTLP export of metrics (`otlp_metrics_export`) and logs (`otlp_logs_export`) is on. Shutdown logs the signal-driven start and the result. A listener failure is never discarded, even when it races with the shutdown signal: the process exits with a non-zero status and logs the error.
- Every HTTP request produces one `http_request` log with `method`, `path`, `status`, `duration_ms` and `bytes` fields. `status` is the first committed response status (the one the client receives), `200` for an implicit body write, and informational `1xx` responses other than `101` do not count as committed. A status code outside `100` to `999` is never committed, because `net/http` panics on it before it writes a response, so a handler that writes one is logged like a handler that panics before any status. A request whose handler panics is logged too: `status` is `500` when no response status was committed before the panic and the committed status otherwise. A flush (`http.ResponseController.Flush` or `http.Flusher`) commits `200` when no status was committed, so a handler that flushes and then panics is logged with the status the client received. A successful hijack only transfers the connection: `net/http` sends nothing for it, and the handler may write a raw response with any status or none, which the logger cannot observe. The record of a hijacked request therefore adds a boolean `hijacked` field with the value `true`, `status` is the status committed before the hijack or `200` when none was (a value that is not a client-observed status for that connection, and never `101` unless the handler wrote it before the hijack), a status written after the hijack is ignored, and a later panic is not logged as `500`. Records of requests that do not hijack have no `hijacked` field. The panic is not recovered by the logger, so `net/http` still aborts the connection. `bytes` is the number of response body bytes that `net/http` accepted from the handler. It equals the body the client receives for a response that completes. `net/http` buffers the response and discards the buffered part when the handler panics or the client disconnects, so the count can exceed what the client received; the buffered bytes of a panicking handler are counted although `net/http` discards them. It is `0` for a `HEAD` request even though the handler writes the body it would send for the equivalent `GET`; the status is the same as for that `GET`.
- A server-wide `OPTIONS *` request is logged like every other request, with `path` `*`. `net/http` would otherwise answer it before the configured handler runs, so the server construction sets `DisableGeneralOptionsHandler` and the handler answers it inside the request logger: `200` with `Content-Length: 0` and an empty body. The handler reads at most 4 KiB of request body, as the `net/http` built-in does; a larger body closes the connection after the response. Other requests with the request target `*` are rejected with `400` by the router and are logged too.
- A request whose `Expect` header is not empty and does not contain the `100-continue` token (for example `Expect: a-pony`) is rejected by `net/http` with `417 Expectation Failed` and a closed connection before it calls the handler. It is logged like every other request: one `http_request` record with its `method` and `path` (never routed, so `/missing` stays `/missing`), `status` `417` and `bytes` `0`. The `417` response, its `Connection: close` header and the connection closure are unchanged. The server serves a listener wrapped by `server.ObserveListener`, and `newServer` sets `ConnContext`, `ConnState`, `MaxHeaderBytes` and `DisableGeneralOptionsHandler` for it. `DisableGeneralOptionsHandler` is a requirement of the observer: when it is left `false`, `net/http` answers a server-wide `OPTIONS *` request itself, so that request is not logged, a later `417` on the same connection gets no `http_request` record, and the `duration_ms` of later `http_request_rejected` records on that connection is measured from the `OPTIONS *` request (`MaxHeaderBytes` is `server.MaxHeaderBytes`, the `net/http` default of 1 MiB, and the observer derives its limit from the same constant):
  - The observer tees the inbound bytes of each connection, synchronously and before `net/http` reads them, into an incremental parser that holds at most one request head in memory (the head limit of `net/http`, which is 1 MiB plus 4096 bytes for the first head of a connection; a later head on a kept-alive connection may be up to 4096 bytes larger, because `net/http` does not charge to it the bytes that its keep-alive wait after the previous response already buffered, so the observer allows that much more for every head after the first). It parses each head with `http.ReadRequest`, skips `Content-Length` and chunked bodies (chunk-size lines and trailers are limited to 4096 bytes each) and queues at most 1024 parsed requests that `net/http` has read but not yet dispatched. It stores only the method, the path and whether the `Expect` header is unsupported, never header values or bodies, and it starts no goroutine, so it releases everything when `net/http` closes the connection.
  - The request logger tells the observer when a handler call starts and ends, which dequeues the oldest request. The observer logs the oldest queued request when `net/http` writes a `417` response with `Connection: close` while no handler call or response of a handler is in progress and that request has an unsupported `Expect` header. The record is written once, before the response is written, as the request logger does. A request that `net/http` never answers with `417` (a client that disconnects, an earlier request that closes the connection, a shutdown, a request `net/http` rejects as malformed) produces no `http_request` record from the observer; a request that `net/http` rejects before it exists as a request produces an `http_request_rejected` record (see below).
  - If the bytes do not parse as `net/http` parses them (a malformed or oversized head, an invalid chunked body, a full queue), the observer stops parsing for that connection. A later `417` on that connection may then be missing from the logs, but a request is never logged as `417`-rejected unless `net/http` sent the `417`. The detection of `http_request_rejected` records below does not depend on the parser, so it keeps working after the parser stopped, with one exception: a `header_read_timeout` record needs the parser to be waiting for a request head, so it is not written for a connection whose parser stopped while `net/http` kept the connection open.
  - `net/http` discards up to 4 leading CR or LF bytes before a request line when the previous request on the connection was a `POST`, so the parser tracks the method of the last head that parsed and skips the same bytes in that case, wherever the reads split them. A `417` after a `POST` and a leading empty line is logged as for any other request. After another method, at the start of the connection, or with a fifth leading CR or LF byte, `net/http` answers `400` (an `http_request_rejected` record) and the parser stops.
- The one exception to the one-`http_request`-record-per-request rule is a request that `net/http` rejects before a request exists, such as a malformed request line. It has no reliable method and path, so it is not an `http_request` record. The observer logs it as one `http_request_rejected` record at `INFO` level, the level of `http_request`, so `LOG_LEVEL=warn` and `LOG_LEVEL=error` hide it like every `http_request` record. The record has these fields and no others besides the standard `time`, `level` and `msg`:
  - `reason`: one of the values below (the Go type is `server.RejectionReason`).
  - `status`: the status that `net/http` sent to the client, or `0` when it sent no response (`header_read_timeout`).
  - `duration_ms`: the time from the first byte of the rejected request (or from the connection being accepted when no byte arrived) to the rejection, in milliseconds. The request waits behind earlier pipelined requests on the connection, so it starts when the last handler finished if that was later.
  - There is no `method`, `path` or `bytes` field: none of them is known, or can be trusted, before the request parses, and the record never contains header values, the request line or the body.

  | `reason`                        | Rejection by `net/http`                                                                                                                 | `status` |
  | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | -------- |
  | `malformed_request`             | A malformed request line or header, a missing or malformed `Host` header, or a malformed partial line when `ReadHeaderTimeout` expires. | `400`    |
  | `request_header_too_large`      | A request head over `MaxHeaderBytes`.                                                                                                   | `431`    |
  | `unsupported_transfer_encoding` | A `Transfer-Encoding` other than `chunked`.                                                                                             | `501`    |
  | `unsupported_protocol_version`  | An HTTP version that `net/http` does not serve over HTTP/1.x, such as `HTTP/2.0` in the request line.                                   | `505`    |
  | `header_read_timeout`           | The client did not send a complete request head within `ReadHeaderTimeout`, and `net/http` closed the connection without a response.    | `0`      |
  | `rejected`                      | Any other status that `net/http` answers directly (not produced by a known request today).                                              | observed |
  - `net/http` answers the `400`, `431`, `501` and `505` cases itself, with one write to the raw connection of a response that has a fixed shape: `HTTP/1.1 <status> <status text>` (optionally `: <detail>`), exactly the headers `Content-Type: text/plain; charset=utf-8` and `Connection: close`, and a text body, with no `Date` and no `Content-Length`. The observer recognizes that write on the outbound bytes once the response of the last handler call is complete and logs it once, before the response is written, like the request logger. A response written by a handler always carries `Date`, so it never has this shape, and bytes of a handler's own response body are never taken for it even when they look like it: `net/http` flushes the buffered end of a handler's response after the handler returned, so the observer treats the response as in progress until `net/http` reports the connection idle through `ConnState`; a `400` written by the handler (the router rejecting the request target `*`) stays an `http_request` record. The response and the connection closure are unchanged. `net/http` closes the connection after each of these responses, so a connection logs at most one `http_request_rejected` record.
  - When `ReadHeaderTimeout` expires, `net/http` either closes the connection without any response or answers `400` and closes it, depending on the bytes after the last line break of the head it has received. It parses that partial line as if it were complete: an empty tail (a line boundary), a valid request line or a valid header line closes the connection silently, and any other tail (for example `GET /hea`, `GE`, `GET / HTTP/1.1\r`, a cut header name such as `User-Ag`, or a lone `\r` after a header) gets the `400`. During a graceful shutdown `net/http` never sends the `400`. The observer does not copy that validation. It sees the timed-out read, which `net/http` makes with a deadline set by itself, and handles it when the parser was waiting for a request head and either no request head ever parsed on the connection, or at least four bytes of the next request had arrived after an earlier request (the leading CR and LF bytes that the parser skipped after a `POST` count as received). `net/http` waits for the first four bytes of a request after a response under `IdleTimeout` and arms `ReadHeaderTimeout` only once it has them, so a stall with fewer than four bytes of the next request is the keep-alive wait and is not logged, while on a connection that has not parsed a head any partly received head or empty wait counts. With nothing after the last line break (including the skipped leading bytes and a connection that sent nothing) it logs `header_read_timeout` with `status` `0` at once. With a partial line buffered it waits for `net/http`: the `400` is logged as `malformed_request` with `status` `400` like any other `400` of this kind, and when the connection closes without a response (reported through `ConnState` as closed) it logs `header_read_timeout` with `status` `0`, the start and fields unchanged, a moment after the read. Either way it is one record, whose `duration_ms` is measured from the first byte of the rejected request. A client that connects and sends nothing for `ReadHeaderTimeout` is therefore logged too (`status` `0`, `duration_ms` about the timeout), while one that connects and closes sooner is not. These are not logged: the timeout of the keep-alive wait between requests (`IdleTimeout`), which is a normal close, including a stall after one to three bytes of the next request; the timeout of a request body (`ReadTimeout`); a read that `net/http` interrupts itself with a deadline in the past after a request; and a connection that a handler hijacked. The server sets `ConnState` to `server.ConnState` so the observer learns about a hijack and never reports a hijacked connection's own reads, writes and deadlines, and about a closed connection with a pending header timeout.
  - A request that `net/http` rejects is never logged twice: a request that reaches the handler is logged by the request logger only, a `417` rejection stays an `http_request` record, and the `http_request_rejected` record is written at most once per connection.

- `net/http` internal errors, such as the report of a recovered handler panic with its stack trace and the report of a superfluous `WriteHeader` call, are logged as `ERROR` JSON records on standard output through `http.Server.ErrorLog`. They are never written as plain text to standard error, and they are not downgraded to `INFO` or dropped when `LOG_LEVEL` is `warn` or `error`. `http.ErrAbortHandler` panics stay unlogged, as `net/http` defines. The server is constructed in one place (`newServer` in `cmd/accounts-api`) so that this setting applies to every production server.
- Every RPC writes one `rpc` record with `procedure`, the Connect `code`, the caller's Logto `user_id` (empty when authentication failed) and `duration_ms`. Request and response messages are never logged.
- Authentication: a rejected call writes an `auth_rejected` record with `procedure`, `api_resource`, `reason` (`missing_token`, `malformed`, `token_type`, `unknown_key`, `signature`, `claims`, `no_policy`, `token_kind` or `missing_scope`) and the token's `user_id` when the token was valid. Key set loads and failures are `logto_jwks_loaded`, `logto_jwks_fetch_failed` and `logto_jwks_parse_failed`; Management API token loads are `logto_management_token_loaded`.
- Billing audit events are also logged as `billing_audit_event` records with `kind`, `billing_account_id`, `actor_user_id`, `target_user_id` and `invitation_id`. The record is written after the transaction that inserted the audit row has committed, never before, so a call that fails or rolls back logs no `billing_audit_event` record and has no audit row. A `CreateInvitation` whose email could not be sent has no `invitation_created` record or row; it logs `invitation_email_failed` and the `invitation_revoked` record of the revocation with `reason` `delivery_failed` (`invitation_revoke_failed` at `error` level when that revocation could not be stored). Unexpected failures are `rpc_internal_error` records with the operation and the error; clients get `internal` without the detail. Migrations write `db_migration_applied` per applied version, or `db_migrations_skipped`.
- Billing events: structured `billing_*` records. Emails write `billing_email_sent` (with the Resend email ID) or `billing_email_failed` (with an `error_kind` of `rate_limited` for a Resend 429 answer, `canceled` when the send context was canceled or expired, `network` for another transport failure including the HTTP client timeout, or `provider` for any other failure, never the provider message, which can quote the address); an email record carries the email kind and the billing account ID, never the address or the body. Webhooks write `billing_paddle_webhook` (with `paddle_event_id`, `event_type`, `result`, `billing_account_id` and `paddle_transaction_id`), `billing_paddle_webhook_rejected` (with the HTTP `status` and a `reason` such as `signature_missing`, `signature_mismatch` or `signature_stale`, never the header) or `billing_paddle_webhook_failed`. Top-ups write `billing_auto_top_up_queued`, `billing_auto_top_up_skipped` (with the `reason` `no_subscription`, `in_flight` or `monthly_cap`), `billing_top_up_charge` (with the `outcome` and the Paddle error code), `billing_top_up_completed`, `billing_top_up_failed` and `billing_auto_top_up_disabled`. Credit changes write `billing_credit_granted`, `billing_credit_expired` and `billing_credit_refunded`; subscription changes write `billing_subscription_checkout_created` and `billing_subscription_status_changed`; Paddle call failures write `billing_paddle_call_failed`; notifications write `billing_notification_queued`, `billing_notification_sent` and `billing_notification_failed` (with the attempt number, `abandoned`, `failed_recipients` and the first error); the worker writes `billing_worker_task_failed`. Usage reports write `billing_usage_reported` (with the `result` `charged` or `unattributed`, the quantity, the amount and the ledger entry ID), `billing_usage_report_duplicate` (`debug`) and `billing_usage_report_mismatch` (`warn`, a repeated key with another quantity or amount, with the first and the new values). Status changes write `billing_organization_blocked`, `billing_organization_suspended`, `billing_organization_resumed` or `billing_status_changed` (another field changed) with the `from` and `to` status, the `reason`, `blocked_since`, `suspend_time` and the `sequence`. Link changes write `billing_organization_linked` and `billing_organization_unlinked`. Billing records carry the relevant fields among `billing_account_id`, `service`, `organization_id`, `meter`, `window_start`, `paddle_transaction_id` and `paddle_event_id`, and never the invoice link, the Paddle API key or the webhook secret.

## Build and Test

Run from the repository root:

- `pnpm --filter accounts-api dev`: run the server through the development launcher `scripts/dev.mjs` (see [Development Launcher](#development-launcher)). The `dev` script starts the launcher through the shared `scripts/dev/with-infisical.mjs`, which injects the Infisical `dev` variables of the `/servers/accounts-api` folder when the checkout has a local Infisical project configuration, according to the [environment contract](repository-environment-contract.md#local-development-injection).
- `pnpm exec turbo run build --filter=accounts-api`: build the binary into `servers/accounts-api/dist/`.
- `pnpm exec turbo run lint --filter=accounts-api`: `go vet ./...`.
- `pnpm exec turbo run test --filter=accounts-api`: `go test ./...` followed by the launcher tests, `node --test "scripts/*.test.mjs"`.

The `build` script passes `-buildvcs=false`, so the binary carries no VCS stamping (`vcs.revision`, `vcs.time` and `vcs.modified` build settings). This is a workaround with the following boundaries:

- Reason: Go's default `-buildvcs=auto` discovery recognizes only a `.git` directory. In a linked Git worktree, where `.git` is a file, it walks up to an ancestor `.git` directory. When that ancestor is not a valid repository, `go build` fails with `error obtaining VCS status`; when it is a valid but unrelated repository, the binary is stamped with the wrong revision.
- Scope: the `accounts-api` `build` script and the `go build` step of the development launcher. The `lint` and `test` scripts do not stamp binaries and are unchanged.
- Removal condition: remove the flag when the Go toolchain recognizes the linked-worktree `.git` file, or when release builds move to a normal-clone job that needs VCS stamping.

### Development Launcher

`scripts/dev.mjs` replaces `go run ./cmd/accounts-api`. `go run` forwards only `SIGINT` and `SIGQUIT` to the compiled server and does not tie the server's lifetime to its own, so a `SIGTERM` sent to the `go run` process (`kill`, `timeout`, a supervisor, pnpm or Turbo) left the server listening without a graceful shutdown.

- The launcher builds the server with `go build -buildvcs=false -o <temporary directory>/accounts-api ./cmd/accounts-api`, then runs the binary as its direct child. The temporary directory is created under the operating system temporary directory and removed after the last child has exited, on every exit path that lets the launcher finish. A `SIGKILL` of the launcher is not such a path: it leaves the temporary directory and, as described below, the server behind.
- The server needs Postgres and the billing configuration. When `DATABASE_URL` is unset, empty or only ASCII white space, the launcher writes an `accounts_api_dev_skipped` JSON record to standard error and exits with status 0 without building, so root `pnpm dev` keeps running the other development servers on a machine without a database or a local Infisical configuration. The launcher uses the server's ASCII white space rule (see [Configuration](#configuration)), not Unicode white space removal: a value that consists only of Unicode white space, such as U+00A0, is not unset, so the launcher builds and starts the server, which rejects it.
- When `CORS_ORIGINS` is unset, empty or only ASCII white space, the launcher sets it to the production origin and the web app's development origins: `https://accounts.delino.io,http://127.0.0.1:13100,https://accounts.delino.localhost,http://accounts.delino.localhost`. When `WEB_ORIGIN` is unset, empty or only ASCII white space, it sets it to `https://accounts.delino.localhost`, so invitation links open the local web app. A portless proxy on a custom `PORTLESS_PORT` adds that port to the URL; set both variables to it there.
- Child processes use explicit argument arrays and `shell: false`. The working directory is `servers/accounts-api/`; standard streams and the other environment variables reach the server unchanged. The server configuration, its logs and `/healthz` are unchanged, and the production binary is built by the `build` script, not by the launcher.
- The launcher forwards `SIGINT`, `SIGTERM` and `SIGQUIT` to the active child (the build or the server) and writes an `accounts_api_dev_signal` JSON event to standard error. It does not handle `SIGHUP`. It waits for the child to exit, so after `SIGINT` or `SIGTERM` the server drains and logs `server_shutdown_started` and `server_shutdown_completed` before the launcher completes. `SIGQUIT` is the Go runtime's quit signal: the server prints one goroutine dump (`SIGQUIT: quit`) and exits at once without a graceful drain, so no `server_shutdown_completed` event is logged, and the launcher completes after the server has exited.
- On POSIX platforms the launcher starts each child (the build and the server) in its own process group (`detached: true`) and forwards each signal it receives once. A terminal Ctrl-C (or Ctrl-\) signals the whole foreground process group, so only the launcher receives it and the server receives exactly one `SIGINT` (or `SIGQUIT`). Without this, the server would receive the group signal directly and again from the forward; the server releases its signal registration on the first signal, so the duplicate would terminate it during the drain. A second Ctrl-C during the drain still reaches the launcher, is forwarded and terminates the server immediately, as described in Graceful Shutdown. On Windows `detached` is not used because it opens a separate console window instead of creating a process group; the Windows behavior is unchanged and not validated.
- Orphan outcome: the server is no longer in the launcher's process group, so a `SIGKILL` of the launcher, or a `SIGHUP` to its process group (closing the terminal), stops the launcher only and leaves the server running with its listening port. Stop such a server by its process ID. `SIGHUP` forwarding is not part of the launcher. `SIGQUIT` is not an orphan path: the launcher forwards it, waits for the server to exit and removes the temporary directory.
- A signal received before the build starts (while the temporary directory is being created) stops the launcher without starting the build. A signal received during the build stops the launcher after the build exits, even when the build succeeded. The server never starts after a termination request.
- Exit status: the status of the failed build, the server's own status (non-zero for an invalid configuration or an occupied port), or `128` plus the signal number after a forwarded signal (`130` for `SIGINT`, `131` for `SIGQUIT`, `143` for `SIGTERM`).
- The launcher tests build and run the real server with a free loopback port. They give it placeholder values for the required variables, an unreachable `DATABASE_URL` and `RUN_MIGRATIONS=false`, so the server starts without external services; they cover the process lifecycle, and the Go integration tests cover the APIs. They cover the skip without `DATABASE_URL`, the default and explicit development origins, a `SIGTERM` to the launcher alone, a process-group `SIGINT` with the real server, a process-group `SIGINT` delivered exactly once to a signal-counting server (the drain completes and the launcher exits `130`), a second process-group `SIGINT` during the drain that still ends the server immediately, a process-group `SIGQUIT` with the real server (one forwarded signal event, one goroutine dump, launcher exit `131`, no `server_shutdown_completed`, the port freed and the temporary directory empty), an occupied port, an invalid `LOG_LEVEL`, a build failure, a `SIGTERM` before the build starts (a preload module delays the temporary directory creation so the window is observable; the build and the server are never started) a `SIGTERM` during the build and a process-group `SIGQUIT` during the build (the server is never started and the launcher exits `131`). They use POSIX signals and are skipped on Windows. Because the server runs in its own process group, the test cleanup kills the launcher's children by process ID before it kills the launcher's process group, and it keeps the process IDs it recorded while the launcher was alive so a server orphaned by a dead launcher is still killed. Two tests cover this cleanup for a live launcher and for a dead launcher, so a failed or timed-out launcher test leaves no server process or listening port behind.
- The `go build` step carries the same `-buildvcs=false` workaround and removal condition as the `build` script above.
