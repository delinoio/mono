# cmds-ownsand-cli foundation contract

## Scope

This contract owns the OwnSand command-line interface, component `ownsand-cli`, of [`ownsand`](project-ownsand.md) at `cmds/ownsand/`. The binary name is `ownsand`. The entry point is `cmds/ownsand/main.go`; `cmds/ownsand/internal/cli` holds the commands. The credential file (`cmds/internal/credstore`) and the Logto device flow (`cmds/internal/logto`) are shared with the [tide CLI](cmds-tide-cli-foundation.md). The CLI uses Apache-2.0 and must not import code from `servers/`.

The device agent has its own commands; the [agent contract](cmds-ownsand-agent-foundation.md#commands) owns them.

## Runtime and Language

- Language: Go in the root module. The CLI is built on the [Go SDK](packages-ownsand-sdk-foundation.md).
- Targets: Linux, macOS and Windows on `amd64` and `arm64`. The CLI is pure Go and builds with `go build ./cmds/ownsand` for every target; CI runs `go vet` and `go test` on Linux, macOS and Windows runners, and vets the other architecture of macOS and Windows (see the [workflow contract](repository-workflow-contract.md#validation)). Locally, `GOOS=darwin` and `GOOS=windows` `go vet ./cmds/ownsand/...` check that the other targets compile. Release (recorded): `deploy.yml` releases the CLI as the `github-release` deployable `ownsand-cli` (`cmds/ownsand/package.json`) when a pending changeset selects it, according to the [workflow contract](repository-workflow-contract.md#binary-releases): the GitHub Release `ownsand-cli@<version>` holds `ownsand-<GOOS>-<GOARCH>` (`.exe` on Windows) for all six targets, built without cgo, with the root `LICENSE` and `NOTICE`, `GO-LICENSE`, `THIRD-PARTY-LICENSES.txt` and `SHA256SUMS`. The darwin executables carry a Developer ID signature with the hardened runtime (identifier `io.delino.ownsand`, no entitlements) and are notarized. The CLI has no version variable and no `version` command yet, so its executable does not report the release version (follow-up). No package repository (Homebrew, winget or a Linux package) publishes it yet.

## Users and Operators

- Organization owners, admins and members who sign in with Logto.
- Programs and CI jobs that use an organization API key.

## Interfaces and Contracts

### Authentication

- `ownsand login` signs in with the Logto device authorization flow: the CLI shows a verification URL and a user code, and the user completes the sign-in in a browser. The CLI is a Logto native application with device flow.
- Recorded decision (application and scopes): the CLI sends `POST <endpoint>/oidc/device/auth` with its application ID, the scopes `openid offline_access ownsand:use` (`ownsand:use` is the scope that the [control plane](servers-ownsand-api-foundation.md#authentication) requires in every user access token) plus any extra scopes in `OWNSAND_LOGTO_SCOPES`, and the API resource `https://ownsand.api.delino.io` (`OWNSAND_LOGTO_RESOURCE` overrides it); it polls `POST <endpoint>/oidc/token` with the device code grant at least every 5 seconds (longer after `slow_down`) until `access_denied`, `expired_token` or the device code expiry. The device code expiry is a local deadline of `expires_in` seconds after the device authorization response (10 minutes when `expires_in` is not positive). It bounds the wait between polls and every token request: the CLI starts no token request at or after the deadline, also not after `slow_down` has moved the next poll past it, cancels a token request that is still pending at the deadline, and then ends the login with the expiry error. Cancellation of the command or an earlier deadline of the command context ends the login with that cancellation, not with the expiry error. It then exchanges the refresh token with the `refresh_token` grant and the `resource` parameter for an access token whose audience is the API resource, according to the [Logto device flow](https://docs.logto.io/quick-starts/device-flow). It refreshes the access token one minute before it expires and stores each rotated refresh token. The tenant endpoint and the application ID are configuration (`OWNSAND_LOGTO_ENDPOINT` and `OWNSAND_LOGTO_APP_ID`); the CLI has no built-in production values, because the shared tenant has no registered OwnSand CLI application yet. Register a native application with device flow and `offline_access`, and record its ID here before the first release.
- `ownsand logout` deletes the stored tokens.
- `ownsand login` and `ownsand logout` take no operands, also none after the `--` terminator. A command with an operand fails with a usage error (exit status 2) before it contacts Logto or reads, changes or deletes the stored tokens.
- The stored tokens record the Logto endpoint, the application ID and the API resource that issued them, and the CLI refreshes them only at that endpoint with that application ID. When `OWNSAND_LOGTO_ENDPOINT` (compared without trailing slashes), `OWNSAND_LOGTO_APP_ID` or `OWNSAND_LOGTO_RESOURCE` is set to a value different from the stored one, a command that needs the tokens fails before it sends a request and tells the user to run `ownsand login` again; the CLI never sends a stored access token or refresh token under another Logto configuration. Unset variables use the stored values.
- When `OWNSAND_API_KEY` is set, the CLI uses the API key and ignores stored Logto tokens. Commands that API keys cannot use fail with the server's error: `permission_denied` for a forbidden operation in the key's own organization and for the commands without an organization, and `not_found` when `--org` names another organization.
- Credential storage: a file in the user configuration directory that only the user can read (mode `0600` on Linux and macOS, a user-only ACL on Windows). Recorded decision: the CLI does not use the OS keychain in this version, so that it needs no keychain dependency and behaves the same on headless Linux hosts. The file is `<os.UserConfigDir()>/ownsand/credentials.json` (`OWNSAND_CONFIG_DIR` overrides the directory). The CLI writes it atomically through a temporary file in the same directory that it restricts before it writes the tokens: mode `0600` in a `0700` directory on Linux and macOS, and on Windows a protected DACL that grants access only to the current user's SID (`golang.org/x/sys/windows`), which removes inherited entries. On Windows, the rename that replaces the file fails while another program (for example an antivirus scanner) holds the file open for a short time, so the CLI retries the rename for up to 2 seconds while it fails with access denied or a sharing violation. The Windows ACL is compiled and vetted but not verified on a Windows host. Every change of the credential file (login, logout and the publication of a refreshed token) runs under a cross-process lock, an advisory OS file lock on `credentials.lock` next to it (`flock` on Linux and macOS, `LockFileEx` on Windows through `golang.org/x/sys/windows`; the lock file holds no secret and stays in place). The lock is never held during a network request, and a wait for it ends with an error after 30 seconds. Each login stores a new random `session_id` in the file; files without the field still load and count as one session. A token refresh remembers the session it started from and, when it publishes the result, compares it under the lock with the stored session. When the credentials were removed (the user signed out) or another login replaced them, the CLI discards the refreshed tokens, does not write the file, and fails with a message that says the CLI is signed out or that the credentials were replaced and the command must run again; the same process keeps returning that error. An unchanged session stores the rotated refresh token as before. Logto rotates the refresh token on every refresh, so a process must not refresh with a refresh token that another process has already spent or publish a result over a newer rotation. A token source therefore reloads the stored credentials before every refresh: when the stored session still matches and its access token is valid for more than one minute, or its refresh token differs from the cached one, the source adopts the stored credentials and refreshes only when the stored access token still needs it, with the stored refresh token. The lock stays free during the network request, so the publication is a compare-and-swap: under the lock the CLI writes the refreshed tokens only when the stored session and the stored refresh token are those that it sent. When another process stored a newer rotation of the same session meanwhile, the CLI discards its own result, adopts the stored credentials and refreshes again only if they need it. When the token endpoint rejects the refresh token with `invalid_grant` and the stored refresh token differs from the one sent, the CLI retries with the stored one. When the stored refresh token is still the one sent, another process may have spent it without publishing the rotation yet (its refresh runs without the lock), so the CLI reloads the stored credentials every 50 milliseconds for at most 5 seconds, ends the wait when the request is cancelled, and retries with the stored refresh token as soon as the same session stores a new one. A removed or replaced session ends the wait with the sign-out or replaced-credentials error, as before. It makes at most 3 refresh requests for one access token request, and an `invalid_grant` with a store that is still unchanged after the wait is reported as a revoked token. The lock path is compiled and vetted for Windows but not verified on a Windows host.

### Commands

| Command group              | Subcommands                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------ |
| `ownsand org`              | `list`, `create`, `get`, `delete`, `transfer`                                        |
| `ownsand member`           | `list`, `invite`, `invitations`, `revoke-invitation`, `accept`, `set-role`, `remove` |
| `ownsand device`           | `list`, `get`, `set-limits`, `remove`                                                |
| `ownsand enrollment-token` | `create`, `list`, `revoke`                                                           |
| `ownsand api-key`          | `create`, `list`, `revoke`                                                           |
| `ownsand agent-version`    | `get`, `set`                                                                         |
| `ownsand sandbox`          | `create`, `get`, `list`, `delete`, `pause`, `resume`, `exec`                         |
| `ownsand file`             | `read`, `write`                                                                      |
| `ownsand snapshot`         | `create`, `get`, `list`, `delete`, `export`                                          |
| `ownsand template`         | `create`, `list`, `delete`                                                           |
| `ownsand billing`          | `status`                                                                             |

- The organization comes from `--org` or the `OWNSAND_ORG` environment variable. `ownsand org` commands that need no organization and `ownsand member accept`, which takes the organization from the invitation, ignore them.
- `sandbox create` generates one `idempotency_key` and reuses it when it retries the create after a lost response.
- `device list` shows the allocation as `<allocated>/<effective> vCPU`, with the exact allocated vCPUs from `DeviceAllocation.vcpu_total_count` (the CLI falls back to `vcpu_count` when an older server leaves it absent) and the exact effective vCPU limit from `Device.effective_vcpu_limit_count`. The field is 0 for a device with zero limits. The CLI never reads the capped `int32` field `effective_vcpu_limit`. See [device limits](protos-ownsand-api-contract.md#device-limits).
- `device set-limits` takes `--vcpu`, `--memory` in MiB, `--disk` in GiB and `--vcpu-overcommit` as a percentage (`100` to `400` in steps of `25`). It calls `ReplaceDeviceLimits` and sends all four [device limits](protos-ownsand-api-contract.md#device-limits) as present values: `--vcpu`, `--memory` and `--disk` are required, and an explicit `0` is sent as zero. When `--vcpu-overcommit` is absent, the CLI sends the current value of the device; an explicit value, including a negative one, is validated first and a value outside `100` to `400` in steps of `25` is a usage error before any request is sent. The usage error names the offending option (for example `--vcpu-overcommit`) and the field path. The CLI never calls the legacy `UpdateDeviceLimits`.
- `sandbox create` requires exactly one source flag (`--image linux|macos|windows`, `--snapshot <id>` or `--template <id>`), `--idle-ttl` and `--max-ttl`, `--vcpu`, `--memory` in MiB and `--disk` in GiB. Optional flags are `--device <id>`, `--os`, `--arch`, `--network outbound|none` and repeated `--label key=value`. It has no default TTL.
- `sandbox exec` streams stdout and stderr to the CLI's own standard streams and exits with the command's exit code when it is between 0 and 255. A nonzero code outside that range exits with status `255`, and a command that a signal ended exits with `128` plus the signal number (or `255` when that is above 255), so a failed command never exits with `0`. `--format json` keeps the exact value. When the data path fails, it exits with status `255` and a data path error on standard error.
- `member accept` reads the invitation secret from standard input or from the file named by `--secret-file`. It never accepts the secret as a command-line argument, because other local users can read process arguments.
- When an exec loses output (`output_truncated`), `sandbox exec` writes a warning with the missing offsets to standard error and exits with status `255` after the command ends.
- When the sandbox ended before the exec result (a `sandbox_ended` event), `sandbox exec` writes the end reason to standard error and exits with status `125`. The `--format json` events include `sandbox_ended` with the end reason.
- When the command could not start (a `failed` event), `sandbox exec` writes the reason to standard error and exits with status `127`. When the exec `timeout` ended (`timed_out` in the `exited` event), it exits with status `124`; `--format json` keeps the exit code or signal and the `timed_out` flag.
- In text mode, when more than one rule applies, the first one in this order sets the exit status (`--format json` uses only its own rule below): data path failure or lost output (`255`), sandbox ended before the result (`125`), command could not start (`127`), `timeout` ended (`124`), signal (`128` plus N), exit code.
- Exit status `255` means a data path failure or lost output, `127` means that the command could not start, `124` means that the exec `timeout` ended, and `128` plus N means a signal, but a guest command can also exit with any of these values. A script that must tell them apart uses `--format json`.
- `file read` writes the raw file contents to standard output or to the path in `--to`. With `--to`, the CLI writes to a temporary file in the destination's directory and renames it over the destination only after the read succeeds, so a failed read leaves an existing destination unchanged and leaves no partial file; the temporary file name does not depend on the destination name, so a destination name at the filesystem limit (for example 255 bytes) works; the rename keeps the permissions of a replaced file and replaces the target of a symbolic link, not the link. When the link is dangling (its target, possibly through a chain of links, does not exist), the rename creates the target and keeps the link; the CLI resolves the target as Linux and macOS do, on every target including Windows, so a relative target such as `alias/../out.txt` applies `..` to the real directory that the link `alias` points to, and when a directory of that target does not exist, the command fails, keeps the link and creates no file. On Windows, where path handling removes `missing\..` without a check of `missing`, the CLI itself checks that every directory of the link target exists before it creates a file. A destination name over the filesystem limit fails with the error of the operating system (for example `file name too long` on Linux and macOS, and `The filename, directory name, or volume label syntax is incorrect.` on Windows) and creates no file. An existing destination that is not a regular file, such as a device or a FIFO, is written in place. Opening a FIFO for writing waits for a reader; this wait ends when the command context is cancelled (for example by an interrupt), before the CLI sends any request, and the command ends with the cancellation error (`context canceled`) and exit status `1`. A FIFO with an attached reader receives the contents as before. `file write` reads from standard input or from the path in `--from`, and `--mode` is a nonzero octal file mode up to `07777` (default `0644`); a zero mode such as `0` or `0000`, which the SDK would replace with `0644`, exits with code 2 before any request. `--format` does not apply to these raw contents.
- Commands that create a secret (`member invite`, `enrollment-token create`, `api-key create`) print the secret once on standard output and the other fields on standard error, so that a script can capture only the secret. With `--format json`, they print one JSON object with the secret and the other fields on standard output.
- `--format json` prints machine-readable JSON for every command that prints data, except the raw file contents of `file read`. With `--format json`, `sandbox exec` prints one JSON object per line on standard output for each exec event (`started`, `stdout` and `stderr` chunks as UTF-8 text with invalid bytes replaced, or base64 with `--binary`, `output_truncated`, `exited` with exactly one of `exit_code` or `signal`, `failed` with the reason the command could not start, and a `data_path_error` event, which carries the `exec_id` of the exec when the failure knows it and omits it for a failure before the exec ID exists), and the CLI exits with `0` after an `exited`, `failed` or `sandbox_ended` event, and with `255` after a `data_path_error` event or an output loss, so the exit status of `--format json` shows only whether the CLI received the complete result. Recorded decision (text output chunks): the guest splits output without regard to character boundaries, so without `--binary` the CLI decodes each stream incrementally. It holds back an incomplete UTF-8 character at the end of a chunk and prints it with the next contiguous chunk of the same stream; the `offset` of a text chunk is the stream offset of the first byte that its `data` represents, and a chunk that holds only the start of a character prints no line. A held-back character becomes U+FFFD when bytes are missing after it (an `output_truncated` event or an offset gap) or when the output ends; the CLI then prints it as a separate chunk before the `output_truncated`, result or `data_path_error` event. The default is `--format text`.
- `billing status` shows the billing of the organization: the linked billing account (ID and name), the billing phase and reason, the block start and the suspension time from `GetBillingStatus`, and, for an organization `owner` or `admin`, the balance and this UTC month's usage and cost for each meter (relay egress, R2 storage, Class A RPCs and Class B RPCs) from `GetBillingUsage`. For a `member` and for an API key, it shows the status only, because `GetBillingUsage` accepts only an organization `owner` or `admin`. For an organization without a link, `GetBillingUsage` is not called (it would fail with `failed_precondition`). Amounts show in USD with 2 decimals, and usage costs below $0.01 with up to 6 decimals; rounding is for display only. `--format json` prints the protobuf JSON of both responses, with exact micro-USD amounts. Linking, unlinking, payments and top-ups stay on the web: when the organization is not linked, the command prints the link `https://accounts.delino.io` and says to link a billing account on the organization settings page of the console. Recorded decisions of the implementation: the CLI does not read the caller's role first. With an API key it never calls `GetBillingUsage`; as a user it calls `GetBillingUsage` for a linked organization and shows the status only when the call fails with `permission_denied` (a `member`) or `failed_precondition` (the link was removed between the two calls). Text mode prints `key: value` lines (organization, status, reason, billing account as `<name> (<id>)`, or `linked` or `not linked` without the usage, block start, suspension time, balance and month start) and a table of the meters (relay egress in GiB, R2 storage in GiB-months of 730 GiB-hours, Class A and Class B RPCs in calls, and the cost), followed by notes: the console settings page `https://ownsand.delino.io/orgs/<organization-id>/settings` and `https://accounts.delino.io` without a link, the rejected actions and `https://accounts.delino.io` while the organization is `BLOCKED` or `SUSPENDED`, and that only an `owner` or `admin` signed in as a user sees the balance and the usage. `--format json` prints one object `{"status": <GetBillingStatusResponse>, "usage": <GetBillingUsageResponse>}` on standard output (`usage` is absent when the command did not read it) and the notes on standard error. Display rounding is to nearest with halves away from zero; a cost below $0.01 that is not zero shows its exact micro-USD value without trailing zeros (at least 2 decimals), quantities use the same rule, and a value that rounds to zero shows without a sign.
- Billing errors: when the control plane rejects a command with a billing reason (`resource_exhausted` with `ACCOUNT_REQUIRED`, `BLOCKED` or `SUSPENDED`, see the [protos contract](protos-ownsand-api-contract.md#billing)), the CLI prints the server message, which includes `https://accounts.delino.io`, to standard error and does not retry. `sandbox exec` reports it as its data path failure (status `255`; a `data_path_error` event with `--format json`); every other command, including the `file` commands, exits with status `1`. The CLI detects the error with `ownsand.IsBillingError` of the [Go SDK](packages-ownsand-sdk-foundation.md#billing-errors) and prints `billing: <server message>`; it adds `; manage billing at https://accounts.delino.io` when the message lacks the link.
- Output uses ANSI color by default. `--no-color` and a non-empty `NO_COLOR` turn it off; an empty `NO_COLOR` counts as unset and keeps the color.
- Recorded decision (text output escaping): text mode never prints a control character from a server-supplied or user-supplied string, because a label, a name or a billing account name with an escape sequence, a carriage return or a newline could move the cursor, rewrite earlier output or forge a `key: value` line or a table row. The `key` and the value of every record line, every table cell (the table headers too) and the values of the `billing status` lines print through one escape rule: printable characters, including non-ASCII text and space separators, stay unchanged; line feed, carriage return and tab print as `\n`, `\r` and `\t`; every other C0 control character, DEL and C1 control character prints as `\xNN`; every other non-printable character (for example a bidirectional override, a line or paragraph separator or an unassigned code point) prints as `\uXXXX` (`\UXXXXXXXX` above U+FFFF); every byte of invalid UTF-8 prints as `\xNN`. Every record line then starts with a real field key and a table row stays on one line. A backslash prints unchanged, so the text form is for people; a script reads `--format json`, which keeps every value exact because JSON encoding escapes the values itself. The secret that a secret command prints on standard output is not escaped, because the script that captures it needs the exact bytes; the other fields of that command go through the same rule on standard error. The ANSI codes that the CLI adds itself for color are not part of the escaped text.
- Recorded decisions of the implementation:
  - Global flags, accepted before the command or among its flags: `--api-url` (`OWNSAND_API_URL`, default `https://ownsand.api.delino.io`; an `http://` origin uses h2c, for example `http://127.0.0.1:18300` for a local control plane), `--org` (`OWNSAND_ORG`), `--format text|json`, `--transport auto|peer-to-peer|relay` (`OWNSAND_TRANSPORT`, default `auto`), `--no-color` (`NO_COLOR`, honored only when non-empty) and `--verbose`. Flags may follow positional arguments; `--` ends flag parsing.
  - Help: `ownsand help`, `ownsand -h` and `ownsand --help` (also after global flags, for example `ownsand --no-color --help`) print the command usage on standard output and exit with `0`. `ownsand <command> <subcommand> --help` prints the flags of that subcommand on standard output and exits with `0`.
  - `sandbox exec [flags] <sandbox-id> [--] <command> [arguments]` takes `--env KEY=VALUE` (repeatable), `--cwd`, `--timeout` and `--binary`. The CLI stops reading its own flags at the first word of the command, so the command's flags pass through.
  - `sandbox create` waits by default until the sandbox is `RUNNING`, `PAUSED`, `FAILED` or `DELETED` and exits with status `1` for `FAILED`; `--wait=false` returns the `CREATING` record at once. Durations accept Go syntax and whole days (`7d`); a day count above `106751` (the most that `time.Duration` holds) is an invalid duration and a usage error.
  - `file read <sandbox-id> <guest-path> [--to <local-path>]`, `file write <sandbox-id> <guest-path> [--from <local-path>] [--mode 0644]`; `file write --format json` prints the written size.
  - Other exit statuses: `0` for success, `1` for an error of the API or the CLI, `2` for a usage error (also an invalid argument that the SDK rejects before it sends a request, such as a missing TTL or organization or a value of `--vcpu`, `--vcpu-overcommit` or `--page-size` outside the `int32` range, which the CLI rejects instead of wrapping it) and `130` when an interrupt cancels `sandbox exec` (the command keeps running in the sandbox).
  - `--format json` prints protobuf JSON with the proto field names for single records and list responses; text mode prints `key: value` lines for records and a table for lists, with the next page token on standard error. Text mode prints every integer value in full decimal form, never in exponent form (the `int32` value `2147483647` prints as `2147483647`, not `2.147483647e+09`), and `int64` values stay exact.
  - A failed write of a result to standard output (a full disk, a closed pipe or `/dev/full`) exits with status `1` and the write error on standard error, in text mode as well as in `--format json`. This covers the `key: value` lines of a record, every table (including the usage table of `billing status`) and the billing notes of `billing status`; the next page hint on standard error follows only a successful result. A secret command still writes the secret to standard output when the write of the other fields to standard error fails, and then exits with status `1`, so that a secret that the server issued once is never dropped.
  - `--format json` exec events: one object per line with `event` (`started`, `stdout`, `stderr`, `output_truncated`, `exited`, `failed`, `sandbox_ended`, `data_path_error`), `exec_id`, and per event `offset` with `data` or `data_base64`, `missing_stdout` and `missing_stderr` ranges (`from`, `to`), `exit_code` or `signal` with `timed_out`, `reason` (the lowercase enum value name, for example `program-not-found`), `message` and `transport`.

## Storage

- The credential file described in [Authentication](#authentication).
- No other persistent state. Sandbox content is never cached on disk.

## Security

- The CLI never prints stored tokens or API keys, except a new secret once at issue time.
- The CLI sends its API key and its Logto tokens only to the configured API origin, which also serves the relay, and the Logto tenant.

## Logging

`--verbose` writes `log/slog` records to standard error: RPC names, IDs, transport selection, Connect codes and durations. They never contain credentials, exec content or file content.

## Build and Test

- From the repository root: `gofmt` check, `go vet ./...` and `go test ./...`, according to `cmds/AGENTS.md`, plus `GOOS=darwin go vet ./cmds/ownsand/...` and `GOOS=windows go vet ./cmds/ownsand/...`. The tests run the commands in process against a fake control plane built on the generated `ownsandv1connect` handlers (relay transport) and a fake Logto tenant; the [SDK tests](packages-ownsand-sdk-foundation.md#build-and-test) cover the peer-to-peer path.
- Required billing tests: `billing status` for an `owner`, an `admin`, a `member` and an API key, linked and not linked, with text and JSON output, and a command rejected with each billing reason (message, link, exit status and no retry).
- Required tests: argument validation (missing TTL and resources), exit code propagation, the data path error exit status, secret printing to standard output only, `OWNSAND_API_KEY` precedence, credential file permissions, the store lock between processes, and a token refresh that finishes after a logout or a newer login (separate app instances over one store and a mock issuer that holds the refresh response), `login` and `logout` with an operand (usage error, credential file unchanged, no Logto request), and token sources of two processes over one store with a mock issuer that rotates refresh tokens (a refresh of one process is adopted by the other without a request, a refresh uses the stored refresh token, a stale result does not overwrite a newer rotation, an `invalid_grant` for a token that another process rotated is retried with the stored one, an `invalid_grant` for a rotation that the other process publishes only after the rejection is adopted during the bounded wait, a revoked token is reported after the bound, a cancelled request ends the wait at once, and a logout or newer login during the wait keeps its own error).

## Dependencies and Integrations

- Upstream: the [Go SDK](packages-ownsand-sdk-foundation.md), the [control plane](servers-ownsand-api-foundation.md) (API, relay and STUN) and the Logto shared tenant.
- Dependencies: only the Go standard library, the Go SDK and its dependencies, and `golang.org/x/sys` (already in the module graph through pion) for the Windows ACL. The CLI uses the standard `flag` package and no command framework.

## Change Triggers

- Update this contract when a public RPC in the [protos contract](protos-ownsand-api-contract.md) or the Go SDK surface changes the command set.
- Update [project-ownsand.md](project-ownsand.md) when the binary name or the distribution changes.
- Update `cmds/AGENTS.md` only under the [instruction-update policy](README.md#instruction-update-policy).
