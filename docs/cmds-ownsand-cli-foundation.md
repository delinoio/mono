# cmds-ownsand-cli foundation contract

## Scope

This contract owns the OwnSand command-line interface, component `ownsand-cli`, of [`ownsand`](project-ownsand.md) at `cmds/ownsand/`. The binary name is `ownsand`. The entry point is `cmds/ownsand/main.go`; `cmds/ownsand/internal/cli` holds the commands, `internal/credstore` the credential file and `internal/logto` the Logto device flow. The CLI uses Apache-2.0 and must not import code from `servers/`.

The device agent has its own commands; the [agent contract](cmds-ownsand-agent-foundation.md#commands) owns them.

## Runtime and Language

- Language: Go in the root module. The CLI is built on the [Go SDK](packages-ownsand-sdk-foundation.md).
- Targets: Linux, macOS and Windows on `amd64` and `arm64`. The CLI is pure Go and builds with `go build ./cmds/ownsand` for every target; CI runs `go vet` and `go test` on Linux, macOS and Windows runners, and vets the other architecture of macOS and Windows (see the [workflow contract](repository-workflow-contract.md#validation)). Locally, `GOOS=darwin` and `GOOS=windows` `go vet ./cmds/ownsand/...` check that the other targets compile. A release and distribution workflow for the binary does not exist yet; it needs a [workflow contract](repository-workflow-contract.md) change before the first release.

## Users and Operators

- Organization owners, admins and members who sign in with Logto.
- Programs and CI jobs that use an organization API key.

## Interfaces and Contracts

### Authentication

- `ownsand login` signs in with the Logto device authorization flow: the CLI shows a verification URL and a user code, and the user completes the sign-in in a browser. The CLI is a Logto native application with device flow.
- Recorded decision (application and scopes): the CLI sends `POST <endpoint>/oidc/device/auth` with its application ID, the scopes `openid offline_access ownsand:use` (`ownsand:use` is the scope that the [control plane](servers-ownsand-api-foundation.md#authentication) requires in every user access token) plus any extra scopes in `OWNSAND_LOGTO_SCOPES`, and the API resource `https://ownsand.api.delino.io` (`OWNSAND_LOGTO_RESOURCE` overrides it); it polls `POST <endpoint>/oidc/token` with the device code grant at least every 5 seconds (longer after `slow_down`) until `access_denied`, `expired_token` or the device code expiry; it then exchanges the refresh token with the `refresh_token` grant and the `resource` parameter for an access token whose audience is the API resource, according to the [Logto device flow](https://docs.logto.io/quick-starts/device-flow). It refreshes the access token one minute before it expires and stores each rotated refresh token. The tenant endpoint and the application ID are configuration (`OWNSAND_LOGTO_ENDPOINT` and `OWNSAND_LOGTO_APP_ID`); the CLI has no built-in production values, because the shared tenant has no registered OwnSand CLI application yet. Register a native application with device flow and `offline_access`, and record its ID here before the first release.
- `ownsand logout` deletes the stored tokens.
- The stored tokens record the Logto endpoint, the application ID and the API resource that issued them, and the CLI refreshes them only at that endpoint with that application ID. When `OWNSAND_LOGTO_ENDPOINT` (compared without trailing slashes), `OWNSAND_LOGTO_APP_ID` or `OWNSAND_LOGTO_RESOURCE` is set to a value different from the stored one, a command that needs the tokens fails before it sends a request and tells the user to run `ownsand login` again; the CLI never sends a stored access token or refresh token under another Logto configuration. Unset variables use the stored values.
- When `OWNSAND_API_KEY` is set, the CLI uses the API key and ignores stored Logto tokens. Commands that API keys cannot use fail with the server's error: `permission_denied` for a forbidden operation in the key's own organization and for the commands without an organization, and `not_found` when `--org` names another organization.
- Credential storage: a file in the user configuration directory that only the user can read (mode `0600` on Linux and macOS, a user-only ACL on Windows). Recorded decision: the CLI does not use the OS keychain in this version, so that it needs no keychain dependency and behaves the same on headless Linux hosts. The file is `<os.UserConfigDir()>/ownsand/credentials.json` (`OWNSAND_CONFIG_DIR` overrides the directory). The CLI writes it atomically through a temporary file in the same directory that it restricts before it writes the tokens: mode `0600` in a `0700` directory on Linux and macOS, and on Windows a protected DACL that grants access only to the current user's SID (`golang.org/x/sys/windows`), which removes inherited entries. The Windows ACL is compiled and vetted but not verified on a Windows host. Every change of the credential file (login, logout and the publication of a refreshed token) runs under a cross-process lock, an advisory OS file lock on `credentials.lock` next to it (`flock` on Linux and macOS, `LockFileEx` on Windows through `golang.org/x/sys/windows`; the lock file holds no secret and stays in place). The lock is never held during a network request, and a wait for it ends with an error after 30 seconds. Each login stores a new random `session_id` in the file; files without the field still load and count as one session. A token refresh remembers the session it started from and, when it publishes the result, compares it under the lock with the stored session. When the credentials were removed (the user signed out) or another login replaced them, the CLI discards the refreshed tokens, does not write the file, and fails with a message that says the CLI is signed out or that the credentials were replaced and the command must run again; the same process keeps returning that error. An unchanged session stores the rotated refresh token as before. The lock path is compiled and vetted for Windows but not verified on a Windows host.

### Commands

| Command group              | Subcommands                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------ |
| `ownsand org`              | `list`, `create`, `get`, `delete`, `transfer`                                        |
| `ownsand member`           | `list`, `invite`, `invitations`, `revoke-invitation`, `accept`, `set-role`, `remove` |
| `ownsand device`           | `list`, `get`, `set-limits`, `remove`                                                |
| `ownsand enrollment-token` | `create`, `list`, `revoke`                                                           |
| `ownsand api-key`          | `create`, `list`, `revoke`                                                           |
| `ownsand agent-version`    | `get`, `set`                                                                         |
| `ownsand sandbox`          | `create`, `get`, `list`, `delete`, `pause`, `resume`, `exec`                         |
| `ownsand file`             | `read`, `write`                                                                      |
| `ownsand snapshot`         | `create`, `get`, `list`, `delete`, `export`                                          |
| `ownsand template`         | `create`, `list`, `delete`                                                           |
| `ownsand billing`          | `status`                                                                             |

- The organization comes from `--org` or the `OWNSAND_ORG` environment variable. `ownsand org` commands that need no organization and `ownsand member accept`, which takes the organization from the invitation, ignore them.
- `sandbox create` generates one `idempotency_key` and reuses it when it retries the create after a lost response.
- `device list` shows the allocation as `<allocated>/<effective> vCPU`, with the exact allocated vCPUs from `DeviceAllocation.vcpu_total_count` (the CLI falls back to `vcpu_count` when an older server leaves it absent) and the exact effective vCPU limit from `Device.effective_vcpu_limit_count`. The field is 0 for a device with zero limits. The CLI never reads the capped `int32` field `effective_vcpu_limit`. See [device limits](protos-ownsand-api-contract.md#device-limits).
- `device set-limits` takes `--vcpu`, `--memory` in MiB, `--disk` in GiB and `--vcpu-overcommit` as a percentage (`100` to `400` in steps of `25`). It calls `ReplaceDeviceLimits` and sends all four [device limits](protos-ownsand-api-contract.md#device-limits) as present values: `--vcpu`, `--memory` and `--disk` are required, and an explicit `0` is sent as zero. When `--vcpu-overcommit` is absent, the CLI sends the current value of the device. The CLI never calls the legacy `UpdateDeviceLimits`.
- `sandbox create` requires exactly one source flag (`--image linux|macos|windows`, `--snapshot <id>` or `--template <id>`), `--idle-ttl` and `--max-ttl`, `--vcpu`, `--memory` in MiB and `--disk` in GiB. Optional flags are `--device <id>`, `--os`, `--arch`, `--network outbound|none` and repeated `--label key=value`. It has no default TTL.
- `sandbox exec` streams stdout and stderr to the CLI's own standard streams and exits with the command's exit code when it is between 0 and 255. A nonzero code outside that range exits with status `255`, and a command that a signal ended exits with `128` plus the signal number (or `255` when that is above 255), so a failed command never exits with `0`. `--format json` keeps the exact value. When the data path fails, it exits with status `255` and a data path error on standard error.
- `member accept` reads the invitation secret from standard input or from the file named by `--secret-file`. It never accepts the secret as a command-line argument, because other local users can read process arguments.
- When an exec loses output (`output_truncated`), `sandbox exec` writes a warning with the missing offsets to standard error and exits with status `255` after the command ends.
- When the sandbox ended before the exec result (a `sandbox_ended` event), `sandbox exec` writes the end reason to standard error and exits with status `125`. The `--format json` events include `sandbox_ended` with the end reason.
- When the command could not start (a `failed` event), `sandbox exec` writes the reason to standard error and exits with status `127`. When the exec `timeout` ended (`timed_out` in the `exited` event), it exits with status `124`; `--format json` keeps the exit code or signal and the `timed_out` flag.
- In text mode, when more than one rule applies, the first one in this order sets the exit status (`--format json` uses only its own rule below): data path failure or lost output (`255`), sandbox ended before the result (`125`), command could not start (`127`), `timeout` ended (`124`), signal (`128` plus N), exit code.
- Exit status `255` means a data path failure or lost output, `127` means that the command could not start, `124` means that the exec `timeout` ended, and `128` plus N means a signal, but a guest command can also exit with any of these values. A script that must tell them apart uses `--format json`.
- `file read` writes the raw file contents to standard output or to the path in `--to`. With `--to`, the CLI writes to a temporary file in the destination's directory and renames it over the destination only after the read succeeds, so a failed read leaves an existing destination unchanged and leaves no partial file; the temporary file name does not depend on the destination name, so a destination name at the filesystem limit (for example 255 bytes) works; the rename keeps the permissions of a replaced file and replaces the target of a symbolic link, not the link. When the link is dangling (its target, possibly through a chain of links, does not exist), the rename creates the target and keeps the link; the CLI resolves the target as Linux and macOS do, on every target including Windows, so a relative target such as `alias/../out.txt` applies `..` to the real directory that the link `alias` points to, and when a directory of that target does not exist, the command fails, keeps the link and creates no file. On Windows, where path handling removes `missing\..` without a check of `missing`, the CLI itself checks that every directory of the link target exists before it creates a file. A destination name over the filesystem limit fails with the error of the operating system (for example `file name too long` on Linux and macOS, and `The filename, directory name, or volume label syntax is incorrect.` on Windows) and creates no file. An existing destination that is not a regular file, such as a device or a FIFO, is written in place. `file write` reads from standard input or from the path in `--from`. `--format` does not apply to these raw contents.
- Commands that create a secret (`member invite`, `enrollment-token create`, `api-key create`) print the secret once on standard output and the other fields on standard error, so that a script can capture only the secret. With `--format json`, they print one JSON object with the secret and the other fields on standard output.
- `--format json` prints machine-readable JSON for every command that prints data, except the raw file contents of `file read`. With `--format json`, `sandbox exec` prints one JSON object per line on standard output for each exec event (`started`, `stdout` and `stderr` chunks as UTF-8 text with invalid bytes replaced, or base64 with `--binary`, `output_truncated`, `exited` with exactly one of `exit_code` or `signal`, `failed` with the reason the command could not start, and a `data_path_error` event, which carries the `exec_id` of the exec when the failure knows it and omits it for a failure before the exec ID exists), and the CLI exits with `0` after an `exited`, `failed` or `sandbox_ended` event, and with `255` after a `data_path_error` event or an output loss, so the exit status of `--format json` shows only whether the CLI received the complete result. Recorded decision (text output chunks): the guest splits output without regard to character boundaries, so without `--binary` the CLI decodes each stream incrementally. It holds back an incomplete UTF-8 character at the end of a chunk and prints it with the next contiguous chunk of the same stream; the `offset` of a text chunk is the stream offset of the first byte that its `data` represents, and a chunk that holds only the start of a character prints no line. A held-back character becomes U+FFFD when bytes are missing after it (an `output_truncated` event or an offset gap) or when the output ends; the CLI then prints it as a separate chunk before the `output_truncated`, result or `data_path_error` event. The default is `--format text`.
- `billing status` shows the billing of the organization: the linked billing account (ID and name), the billing phase and reason, the block start and the suspension time from `GetBillingStatus`, and, for an organization `owner` or `admin`, the balance and this UTC month's usage and cost for each meter (relay egress, R2 storage, Class A RPCs and Class B RPCs) from `GetBillingUsage`. For a `member` and for an API key, it shows the status only, because `GetBillingUsage` accepts only an organization `owner` or `admin`. For an organization without a link, `GetBillingUsage` is not called (it would fail with `failed_precondition`). Amounts show in USD with 2 decimals, and usage costs below $0.01 with up to 6 decimals; rounding is for display only. `--format json` prints the protobuf JSON of both responses, with exact micro-USD amounts. Linking, unlinking, payments and top-ups stay on the web: when the organization is not linked, the command prints the link `https://accounts.delino.io` and says to link a billing account on the organization settings page of the console. Recorded decisions of the implementation: the CLI does not read the caller's role first. With an API key it never calls `GetBillingUsage`; as a user it calls `GetBillingUsage` for a linked organization and shows the status only when the call fails with `permission_denied` (a `member`) or `failed_precondition` (the link was removed between the two calls). Text mode prints `key: value` lines (organization, status, reason, billing account as `<name> (<id>)`, or `linked` or `not linked` without the usage, block start, suspension time, balance and month start) and a table of the meters (relay egress in GiB, R2 storage in GiB-months of 730 GiB-hours, Class A and Class B RPCs in calls, and the cost), followed by notes: the console settings page `https://ownsand.delino.io/orgs/<organization-id>/settings` and `https://accounts.delino.io` without a link, the rejected actions and `https://accounts.delino.io` while the organization is `BLOCKED` or `SUSPENDED`, and that only an `owner` or `admin` signed in as a user sees the balance and the usage. `--format json` prints one object `{"status": <GetBillingStatusResponse>, "usage": <GetBillingUsageResponse>}` on standard output (`usage` is absent when the command did not read it) and the notes on standard error. Display rounding is to nearest with halves away from zero; a cost below $0.01 that is not zero shows its exact micro-USD value without trailing zeros (at least 2 decimals), quantities use the same rule, and a value that rounds to zero shows without a sign.
- Billing errors: when the control plane rejects a command with a billing reason (`resource_exhausted` with `ACCOUNT_REQUIRED`, `BLOCKED` or `SUSPENDED`, see the [protos contract](protos-ownsand-api-contract.md#billing)), the CLI prints the server message, which includes `https://accounts.delino.io`, to standard error and does not retry. `sandbox exec` reports it as its data path failure (status `255`; a `data_path_error` event with `--format json`); every other command, including the `file` commands, exits with status `1`. The CLI detects the error with `ownsand.IsBillingError` of the [Go SDK](packages-ownsand-sdk-foundation.md#billing-errors) and prints `billing: <server message>`; it adds `; manage billing at https://accounts.delino.io` when the message lacks the link.
- Output uses ANSI color by default. `--no-color` and `NO_COLOR` turn it off.
- Recorded decisions of the implementation:
  - Global flags, accepted before the command or among its flags: `--api-url` (`OWNSAND_API_URL`, default `https://ownsand.api.delino.io`; an `http://` origin uses h2c, for example `http://127.0.0.1:18300` for a local control plane), `--org` (`OWNSAND_ORG`), `--format text|json`, `--transport auto|peer-to-peer|relay` (`OWNSAND_TRANSPORT`, default `auto`), `--no-color` (`NO_COLOR`) and `--verbose`. Flags may follow positional arguments; `--` ends flag parsing.
  - `sandbox exec [flags] <sandbox-id> [--] <command> [arguments]` takes `--env KEY=VALUE` (repeatable), `--cwd`, `--timeout` and `--binary`. The CLI stops reading its own flags at the first word of the command, so the command's flags pass through.
  - `sandbox create` waits by default until the sandbox is `RUNNING`, `PAUSED`, `FAILED` or `DELETED` and exits with status `1` for `FAILED`; `--wait=false` returns the `CREATING` record at once. Durations accept Go syntax and whole days (`7d`); a day count above `106751` (the most that `time.Duration` holds) is an invalid duration and a usage error.
  - `file read <sandbox-id> <guest-path> [--to <local-path>]`, `file write <sandbox-id> <guest-path> [--from <local-path>] [--mode 0644]`; `file write --format json` prints the written size.
  - Other exit statuses: `0` for success, `1` for an error of the API or the CLI, `2` for a usage error (also an invalid argument that the SDK rejects before it sends a request, such as a missing TTL or organization or a value of `--vcpu`, `--vcpu-overcommit` or `--page-size` outside the `int32` range, which the CLI rejects instead of wrapping it) and `130` when an interrupt cancels `sandbox exec` (the command keeps running in the sandbox).
  - `--format json` prints protobuf JSON with the proto field names for single records and list responses; text mode prints `key: value` lines for records and a table for lists, with the next page token on standard error.
  - `--format json` exec events: one object per line with `event` (`started`, `stdout`, `stderr`, `output_truncated`, `exited`, `failed`, `sandbox_ended`, `data_path_error`), `exec_id`, and per event `offset` with `data` or `data_base64`, `missing_stdout` and `missing_stderr` ranges (`from`, `to`), `exit_code` or `signal` with `timed_out`, `reason` (the lowercase enum value name, for example `program-not-found`), `message` and `transport`.

## Storage

- The credential file described in [Authentication](#authentication).
- No other persistent state. Sandbox content is never cached on disk.

## Security

- The CLI never prints stored tokens or API keys, except a new secret once at issue time.
- The CLI sends its API key and its Logto tokens only to the configured API origin, which also serves the relay, and the Logto tenant.

## Logging

`--verbose` writes `log/slog` records to standard error: RPC names, IDs, transport selection, Connect codes and durations. They never contain credentials, exec content or file content.

## Build and Test

- From the repository root: `gofmt` check, `go vet ./...` and `go test ./...`, according to `cmds/AGENTS.md`, plus `GOOS=darwin go vet ./cmds/ownsand/...` and `GOOS=windows go vet ./cmds/ownsand/...`. The tests run the commands in process against a fake control plane built on the generated `ownsandv1connect` handlers (relay transport) and a fake Logto tenant; the [SDK tests](packages-ownsand-sdk-foundation.md#build-and-test) cover the peer-to-peer path.
- Required billing tests: `billing status` for an `owner`, an `admin`, a `member` and an API key, linked and not linked, with text and JSON output, and a command rejected with each billing reason (message, link, exit status and no retry).
- Required tests: argument validation (missing TTL and resources), exit code propagation, the data path error exit status, secret printing to standard output only, `OWNSAND_API_KEY` precedence, credential file permissions, the store lock between processes, and a token refresh that finishes after a logout or a newer login (separate app instances over one store and a mock issuer that holds the refresh response).

## Dependencies and Integrations

- Upstream: the [Go SDK](packages-ownsand-sdk-foundation.md), the [control plane](servers-ownsand-api-foundation.md) (API, relay and STUN) and the Logto shared tenant.
- Dependencies: only the Go standard library, the Go SDK and its dependencies, and `golang.org/x/sys` (already in the module graph through pion) for the Windows ACL. The CLI uses the standard `flag` package and no command framework.

## Change Triggers

- Update this contract when a public RPC in the [protos contract](protos-ownsand-api-contract.md) or the Go SDK surface changes the command set.
- Update [project-ownsand.md](project-ownsand.md) when the binary name or the distribution changes.
- Update `cmds/AGENTS.md` only under the [instruction-update policy](README.md#instruction-update-policy).
